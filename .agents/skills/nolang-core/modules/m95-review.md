# Review — `.no` 代码审查

> **定位**：对已有 `.no` 代码做审查，检查**语法正确性**与**代码风格**，给出正确合理的建议，
> 并**尽量直接给出可采用的最终代码**（而非只列问题）。审查对象是合法 Nolang 代码，
> 遵守全局黄金法则：**不改合法代码来「修」疑似编译器 bug**（见 [`m00-redlines.md`](m00-redlines.md)）。

## 何时使用

- 用户说「审查 / review / 检查这段代码 / 看看有没有问题 / 帮我改得更好」
- 要求检查语法是否正确、风格是否规范、有无潜在运行时陷阱
- 提交 / 发版前的 `.no` 代码自查（可与 `nolang-app` 的验证流程衔接）

审查 **Go 编译器代码** 不走本模块，改用 `nolang-compiler` + `debug`；
审查中发现**疑似编译器缺陷**，只报告 + 最小复现，不改写合法代码绕过（转 `nolang-compiler`）。

## 审查依据（唯一来源，按命中加载，不要整目录读）

本模块只定义**审查动作与清单**，不复制规则正文。具体规则查下列权威：

| 审查维度 | 依据 |
|---|---|
| 语法正确性（类型 / 函数 / 控制流 / match / struct / 模块 / 注解 / FFI） | [`m10-syntax.md`](m10-syntax.md) 路由到对应 `syntax/` 视图 |
| 代码风格（4 空格缩进、单语句行、`;` 注释、末尾单换行、`no fmt` fixed point） | [`syntax/10-data-types.md`](syntax/10-data-types.md) 格式与命名段 |
| 语言禁令（索引写 / 空串 / 越界读 / free / 协程 / match 同名 / overflow / 全局命名 / guard vs while） | [`m00-redlines.md`](m00-redlines.md) + `nolang-app` 应用红线 |
| std API 用法（是否用现成 API、签名是否正确） | [`m20-std.md`](m20-std.md) 路由到对应 `std/` 视图 |
| 包 / workspace / 构建配置 | [`m93-cli.md`](m93-cli.md) |
| 验收门禁与判据 | [`m40-verify.md`](m40-verify.md) |

## 工作流

### 1. 界定范围与上下文

- 确定审查目标（单文件 / 目录 / 片段）与目标包；定位最近的 `workspace.noml` / `package.noml`。
- 按维度从上方表格**只加载命中的依据**；纯风格审查不必读全部 syntax 视图。
- 记录 `./bin/no version`，确保用的是当前二进制而非裸 `no`（陈旧二进制会造成假象）。

### 2. 静态走查（按下面清单逐项过）

**语法正确性**
- 变量 / 函数签名、类型标注、赋值相容性；`?T` 解包与 `err` 分支是否被正确处理（断言 tag，不假设兜底值）。
- 函数体写法：命名输出参数就地改写、提前返回、循环与 match 臂闭合正确；每条语句独占一行。
- 跨模块：`#` / `use` 导入、模块前缀、导出是否与实际调用一致；`package.noml` 的 `name` 与 workspace 键一致。
- 注解：`#{...}` 拼写与作用域；`#{overflow=...}` 是否只挂在生效的下一行。

**代码风格**
- 4 空格缩进、每语句一行、`;` 注释标记、文件恰好一个末尾换行；命名四档（全局大写 / 模块私有 `_` 大写 / 局部小写 / `_buf` 非法）。
- 优先复用 std API，避免手工字节操作与重复造轮子；函数 / 变量命名是否表达意图。
- 判定是否 `no fmt` fixed point：`no fmt -d <file>` 应无差异（对 `src/std` 绝不 `-w`）。

**安全与陷阱**
- 索引写 `s[i] = v` / `t[i] = c` 全域禁用 → 改 `push` 家族 / `fill` / place-match / `[]byte` 构造。
- 空 `str` 的 `data == NULL` → 空串断言用长度 `0`，不对 `n > 0` 调 `eq`。
- `t[i]` / `s[i]` 越界读返回 `err` → 断言 tag，不假设 `-1`。
- 不写 `free`；协程用 `awy { r = co f() }`（`co` 组外非法）；match 臂绑定不同名；`?t` 解包优先 `it`。
- `(cond) { }` 是 while、`(cond) -> { }` 才是一次性 guard；模块内避免可变全局状态。

### 3. 动态验证（给出结论前必做）

```bash
./bin/no fmt -d <file>          # 风格：应无差异
./bin/no build -o tmp/<name> <file>   # 语法：编译通过
./bin/no run <file>             # 行为：运行符合预期
./bin/no test <test-file>       # 有测试时：ALL TESTS PASSED / rc=0
```

- 临时产物写项目 `tmp/`；判据只认明确标记（`ALL TESTS PASSED` / 超时 / 失败），其余按构建失败排查。
- 若编译失败是**疑似编译器缺陷**（合法代码却报错），不要改写代码绕过——记录最小复现，按 `nolang-compiler` 上报。

### 4. 输出（关键是给出最终代码）

按下面结构输出，**问题与建议都要落到可采用的最终代码**：

1. **结论**：`可直接使用` / `需修改 N 处` / `发现疑似编译器缺陷（附最小复现）`。
2. **问题清单**：表格列 `位置 | 类别（语法/风格/安全）| 问题 | 依据 | 修改`。
   - 每条指向唯一来源依据（如「违反红线：索引写」「`no fmt` 会改此处」），不空谈。
3. **最终代码**：默认给出**完整修正后的代码**（或精确 diff），让用户可直接采用；
   - 多处修改给整文件，单处小改可给 diff + 上下文；改动处用注释或说明标出。
   - 风格修改以 `no fmt` 输出为准，不手写与格式化器不一致的排版。
4. **验证结果**：贴出 `fmt -d` / `build` / `run` / `test` 的实际判据与退出码。
5. **不确定的点**：明确列出无法判断之处（如外部 API 语义、运行时行为），不臆测。

## 边界

- 审查 `.no` → 本模块；写 / 改 `.no` → `nolang-app`；改编译器 / std → `nolang-compiler`。
- 只审风格与语法、不改合法语义；涉及性能 / 架构的深改建议先与用户确认再动手。
- 与红线冲突时以 [`m00-redlines.md`](m00-redlines.md) 为准。
