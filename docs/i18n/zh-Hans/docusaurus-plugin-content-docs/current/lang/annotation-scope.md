# 注解与注释的作用域

`#{...}` 注解本身不带「我能管多大范围」的资讯——范围由**它附着在哪个节点上**决定。
这页把这件事固定下来：一个位置、一套判定、四个层级，再加一条「某个键可以只支持其中几层」
（`overflow` 就是只认 L3 的那个，见 §4.1），让作者、`no fmt`、`no vet`、codegen 与 LSP
对同一行注解给出同一个答案。

> 为什么必须固定：同一条 `#{overflow=wrap}`，若 `no vet` 认为它管整个函式、codegen
> 认为它只管下一行，就会出现「vet 全绿、运行期照样回 `err`」的静默语义漂移。
> 作用域不是注解的属性，而是**读者的共识**；共识不写下来就会各自漂。

---

## 1. 一个原则：作用域由宿主决定

注解只有两种合法位置（位置规则本身见 [`syntax.md`](syntax.md)〈注解位置〉）：

```no
; ① 上方：独占一行，置于目标之上
#{overflow=wrap}
x i8 = a + b

; ② 尾随：写在目标同一行的后方
x i8 = a + b #{overflow=wrap}

; 多行目标（函式、区块）的尾随写在收尾 `}` 之后
greet = () {
    print('hi')
} #{mac-arm64}
```

**两者完全等价**——同一个键、同一个宿主、同一个作用域，`no fmt` 也不会把一种改写成
另一种（尾随留在尾随，上方留在上方）。选哪种只看可读性：短述句用尾随更省一行，
需要给整段运算加注、或述句很长时用上方。

**写在目标前方同一行是编译错误**，不存在「前缀作用到后方」这条路：

```no
#{overflow = wrap} x i8 = a + b   ; ✗ 前缀 → 报错
```

判定分三步，每一步都只有一个答案：

| 步骤 | 问题 | 答案来源 |
| --- | --- | --- |
| 1 | 宿主是谁？ | 位置：上方的第一条非注解/非注解行陈述，或同一行的前一条陈述 |
| 2 | 宿主属于哪一层？该键支持这一层吗？ | §2 的表 + §4 的矩阵（不支持就是编译错误） |
| 3 | 覆盖到哪里？ | 宿主子树，减去内层硬边界（§3） |

---

## 2. 四个层级

| 层级 | 宿主 | 生效范围 | 写法示例 |
| --- | --- | --- | --- |
| **L0 模组级** | 档案头 | 本档案全部宣告与语句 | 档案最顶端，且与后续内容之间空一行 |
| **L1 宣告级** | 常量/全局变数、结构体、介面、标签列举、函式、方法 | 该宣告的整个定义（函式含函式体与全部巢状区块） | 紧贴宣告上方，或宣告行尾随 |
| **L2 区块级** | 协程组、if 组、`cond -> body`、match、`for`/计数/区间循环、裸块 | 该块体内全部语句（含巢状块，止于内层 L1 边界） | 紧贴块头那条语句上方，或写在块尾 `}` 之后 |
| **L3 单行级** | 单条陈述（`let`、赋值、`?=`、`return`、呼叫、`cond ->` 臂） | 该陈述自身及其运算式 | 紧贴陈述上方，或同行尾随 |

### L0 模组级

位置是**档案最开头**（前面没有任何语句或 import），且注解群组与第一条语句之间
**至少一个空行**——空行在这里是「作用域终止符」，表示这组注解不属于下一条陈述，
而属于整个档案。

```no
#{win-amd64}

; ↑ 空行 → 模组级：本档只在 Windows x86_64 编译
; 以下所有宣告与语句都在管辖内
helper = () {
    print('windows only')
}

label = 'win'
```

没有空行就是一般的 L1（附着首个宣告），这条边界让既有程式码不需迁移：

```no
#{buildin}
bool.to-str = () (out str) {
}
```

模组级只对「整档有意义」的键有用（目前只有平台键）；宣告键（`buildin`、`generic`、
`embed`…）出现在 L0 是错误，不是「扩大范围」。`overflow` 也不吃 L0——它只认 L3。

跨档案的配置不属于注解，写在 `package.noml`。

### L1 宣告级

```no
; 整个结构体：栏位布局由型别标记决定
#{inline}
holder {
    inl point
    out point
}

; 整个函式：进出日志自动带呼叫者
#{track-caller}
log.write = (msg str) {
    ...
}

; 整个常量宣告：嵌入目录（路径相对 package.noml）
#{embed='assets'}
ASSETS fs.embed

; 编译期剔除整棵子树（含函式体）
#{mac-arm64, linux-arm64}
greet = () {
    print('hello from unix')
}
```

L1 内部还有**成员粒度**：结构体栏位、标签列举变体、C 风格列举成员上的注解
（`a pt #{inline}`、`ok(v i64) #{inline}`）管的是该成员，不是整个型别。成员注解
同样只有两种位置：紧贴成员上方一行，或写在该成员同一行的后方（惯用尾随）。

### L2 区块级

宿主是「块头陈述」时，作用域是整个块体：

```no
; 整块被排除（不生成 IR，也不做型别检查）
#{win-amd64}
2 * {
    print('windows only')
}

; if 组同样以整组为单位
x = 1
#{win-amd64}
{
    x == 1 -> print('arm-1')
    -> print('arm-other')
}
```

四种块头都适用：协程组（`awy { ... }`）、if 组（`{ cond -> … }`）、单条件语句
（`cond -> body`）、match、`for` / 计数 / 区间循环。

`cond -> body` 的 body 若只是单条陈述，L2 与 L3 的结果相同；写成块才有区别。

**不是每个键都吃满四层。** 一个键可以只支持其中几层，写到它不支持的层是**编译错误**，
不是「多写一行的无害冗余」。目前唯一的受限键是 `overflow`：它只认 L3，理由见 §4.1。

### L3 单行级

```no
a i8 = 100
b i8 = 100
; 只管紧跟的下一条陈述（尾随写法 `c = a + b #{overflow=wrap}` 等价）
#{overflow=wrap}
c = a + b
c: {
    ok -> print('wrap:' - (it == -56).to-str())
    nil -> print('nil')
    err -> print('err')
}
```

区块内一个独立成行的注解只认「紧跟其后的那一条陈述」。中间夹着无关的注解行
（例如 `#{overflow=wrap}` 之后再来一个 `#{...}`）不会中断，仍找到第一条真正的陈述；
但若下一条注解本身也带同名键，则以前者不辖制任何陈述（后者胜）。

⚠️ **块 match `{ … }: { … }` 是「一条陈述」，不会被穿透**：注解写在它的 `{` 上方时，
宿主是那条块陈述本身，**不会**下沉到块内 `?=` 的算式（实测：`#{overflow=wrap}` 放在块外，
块内 `np ?= np + 1` 照样上溢 → `err`、目标被清零）。要把 `overflow` 套到块内算式，就写在
块内那条 `?=` 的正上方。两种消费形态的差异见 [syntax.md](syntax.md) 的
〈块 match 与值位 match 的取舍〉。

## 3. 继承、覆盖与硬边界

**由外向内继承，就近覆盖。** 对支持多层的键（平台键），L0 → L1 → L2 → L3 逐层生效；
同一节点上若出现同名键，后者覆盖前者（`#{mac-arm64} #{mac-arm64, win-amd64}`
以后者为准）。

**函式体是硬边界。** L2 块的作用域止于**语法子树**：它不沿呼叫关系扩散，也不进入任何
函式 / 方法 / 匿名函式的定义体。一个函式体内用什么模式，只由它自己的 L1 注解或内部
的 L3 注解决定，与呼叫它的那个块上的注解无关。

```no
; L1：整个函式连同函式体一起被剔除（macOS 上不生成 IR）
#{win-amd64}
windows-only = () {
    print('never compiled on mac')
}

; 没有自己的 L1 注解 → 任何平台都编译，也不会因为被谁呼叫而改变
always = () {
    print('always compiled')
}
```

理由：外层注解若能穿透进函式体，呼叫点上一行字就会静默改变被呼叫函式的语义——除错时
完全看不出来。L1 注解则相反：它就写在这个函式头上，是宣告的一部分。

**硬边界清单**（继承到此为止）：函式体、方法体、匿名函式/lambda 体、`#{c}` 外部宣告。
**非边界**（照常继承）：`{}` 裸块、if 组、match 臂、循环体。

## 4. 键 × 层级矩阵

`✓` 生效 ／ `✗` 非法（应报编译错误）／ `—` 对该层无意义（同样应报错，而不是静默丢弃）

| 键 | L0 模组 | L1 宣告 | L2 区块 | L3 单行 |
| --- | --- | --- | --- | --- |
| `overflow` | ✗ | ✗ | ✗ | ✓ |
| 平台键（`mac-arm64` 等） | ✓ | ✓ | ✓ | ✓ |
| `buildin` | ✗ | ✓ 函式 / 标签列举 / 布局结构体 | ✗ | ✗ |
| `inline` | ✗ | ✓ 结构体 / 栏位 / 变体 / 函式 | ✗ | ✓ 成员尾随 |
| `generic` | ✗ | ✓ 函式 / 结构体 | ✗ | ✗ |
| `track-caller` | ✗ | ✓ 函式 | ✗ | ✗ |
| `embed` | ✗ | ✓ 顶层 `let` | ✗ | ✗ |
| `bind` | ✗ | ✓ import 行 | ✗ | ✗ |
| `c` / `cpp` / `rust` | ✗ | ✓ 紧随的函式宣告 | ✗ | ✗ |
| `fmt-skip` | ✗ | ✗ | ✓ markdown 围栏块 | ✗ |
| 元资料（`derive` / `range` / `max` / `debug`…） | ✗ | ✓ 宣告 / 成员 | ✗ | ✗ |
| `index-out` | — | — | — | — 已于 D11 移除，出现即报错 |

「非法」与「无意义」都必须**报错**，不能静默失效：一条写在 for 回圈上方的
`#{buildin}` 若被悄悄忽略，作者会以为内建声明生效了。

### 4.0 `#{buildin}` 的三个载体，以及「布局结构体」的特殊性

`#{buildin}` 标在宣告上，但它对三种载体的语义完全不同：

| 载体 | 语义 | 例子 |
| --- | --- | --- |
| 函式 | 空体桩：编译器 / FFI 提供实现，Nolang 侧不生成函式体 | `#{buildin}`<br/>`fs.remove = (p str) (ok bool) { }` |
| 标签列举 | 变体供匹配与穷尽性检查，底层表示与构造由内建 runtime 提供 | `#{buildin}`<br/>`option { ok(v t), nil, err(e err.err), }` |
| **布局结构体** | **只是布局文档**：这份 `struct` 在语义上不存在，唯一产出是栏位型别（`t.len` 是 `u8`） | `#{buildin}`<br/>`txt { data [255]byte; len u8 }` |

第三种要单独说清楚，因为它与前两种的方向相反：函式桩与标签列举都是「编译器真的
要用这份声明」，而布局结构体是「编译器**不用**这份声明，它只是栏位型别的来源与
一份可读的布局说明」。真实布局与文档链接都在别处：

| 型别 | 真实布局的来源 | 文档 / 链接的来源 |
| --- | --- | --- |
| `str` | MIR 手写描述符 `%str-long = { i32 len, i32 cap, i8* data }` | `parser.BuiltinTypes()` |
| `vec` | MIR 手写描述符 `%vec = { i32 len, i32 cap, i64 data }` | `parser.BuiltinTypes()` |
| `txt` | MIR 手写描述符 `%txt = { [255 x i8] data, i8 len }` | `parser.BuiltinTypes()` |
| `arr` | 没有描述符：`[n]t` 就是裸聚合 `[N x T]`，`.len` 是编译期常量 `n` | `parser.BuiltinTypes()` |

`parser.BuiltinTypes()`（`src/parser/builtintype.go`）是「名字 → std 模组 → 模组文档
锚点 → 布局」的唯一登记表，LSP 的 hover / 跳转定义 / 补全与 `IsBuiltinLayoutStructName`
都读它。这正是为什么布局结构体**不再承担链接**：把它删掉，hover 与 F12 依然可用；
只是 checker 会失去 `t.len` 的栏位型别，所以目前保留。

由此得出两条硬性规则，任一被破坏都会立刻产生一份与真实布局矛盾的「影子结构体」：

1. **带 `#{buildin}` 的 struct 必须用内建布局名**（`str` / `vec` / `txt` / `arr`）。
   贴在别的 struct 上是错误：那份声明会被 MIR 当「布局由编译器持有」而跳过，
   栏位全部不生效，留给作者的是一堆 `unknown field`。
2. **用内建布局名宣告 struct 必须带 `#{buildin}`**。使用者若写一份裸的
   `str { … }`，它会被当成本模组的普通型别加前缀（`m.str`），codegen 于是生成
   一个与 `%str-long` 打架的 `%m_str`。

两条都由 `checker.ValidateBuiltinStructDecls` 报错（`1a8m445h` / `3lu6n4np`），
`no build` 与 `no vet` 都会命中。反过来，**只有** `#{buildin}` + 布局名的组合会被
模组前缀阶段与 MIR 的 `collectStructFields` 跳过（见 `src/build/module_prefix.go`
的 Phase 1 与 `src/mir/hir2mir.go` 的 `isBuiltinLayoutStruct`）——判据是「注解 +
名字」这个组合，不是名字本身。

### 4.1 为什么 `overflow` 只给 L3

`#{overflow}` 是**逐运算**的语义开关，不是宣告的元数据。它一旦允许写在函式或块上，
「某条运算实际用哪个模式」就取决于它离注解多远、中间有没有夹别的注解、叠了几层块——
读一行程式码要向上追溯才能回答，而 `no fmt` / `no vet` / codegen 三方维持同一个答案
极难（实测已经漂了，见 §7）。

而且它**不改型别**：结果恒为 `?T`。块级或函式级的 `wrap` 不会把 `?T` 变成 `T`，只会把
「溢出即 `err`」静默换成「静默回绕」——错误从「显式失败」变成「看起来成功的错值」，
这正是最不该由一行远处注解决定的事。

所以定死成一行一注解：

- 只认紧跟的那一条陈述；尾随写法（`x = a + b #{overflow=wrap}`）等价。
- 要整片生效就逐条写——`no fmt --fix=overflow` 与 LSP quickfix 产生的都是这个形式。
- 写在函式头、块头、档案头 → **编译错误**，不是「无效但无害」。

附带好处：注解永远与它管的那条陈述同屏，移动程式码时不会彼此脱离；`wrap` 也不会
因为一次缩排调整而意外覆盖到隔壁的运算。

## 5. 注释（`;` / `//` / `;;`）的作用域

注释不参与编译语意，归属只影响 `no fmt` 的排版与 API 文件的挂载。标记语法见
[`code-style.md`](code-style.md)〈注释标记〉。

| 注释 | 归属 |
| --- | --- |
| 行内（`x = 1 ; 说明`） | 该行 |
| 行上方连续注释行 | 紧跟的下一条陈述/宣告（L1 或 L3，同注解的宿主判定） |
| 与目标之间有空行 | 不归属任何节点，作为区块/档案的分隔说明（档案头除外，见 L0） |
| `;; … ;;` 块注释 | 只到自己的结束定界符，不跨作用域 |
| 注解与目标之间的注释 | 随目标走，输出顺序固定为「文件注释 → 注解 → 陈述」 |

`;` 与 `//` 语义相同；`no fmt` 保留原始标记不改写。文件注释的翻译锚点
（`[get](#args.get)`）必须是注释群组的**最后一行**，属于同一宿主，不能跨节点。

## 6. 四个读者必须一致

同一条注解，四个读者必须得到同一个作用域：

| 读者 | 需要知道的 |
| --- | --- |
| parser / codegen | 这个节点及其子树用哪个模式 |
| checker / `no vet` | 「已标注」的判定范围 |
| `no fmt` | 注解印回原位，不得跨宿主搬移 |
| LSP | hover/quickfix 插入的位置等于它实际生效的位置 |

由此推出四条不变量：

1. **标注判定一致**：codegen 认为「已标注」的范围，必然也是 `no vet` 认为已处理的范围，反之亦然。
2. **fmt 不搬移**：`no fmt` 只能在同一宿主内调整位置（上方 ↔ 尾随），跨宿主搬移等于改语义。
3. **失效必报**：注解落在没有对应语意的层级（见 §4 的 `✗` / `—`）时报错，不静默忽略。
4. **层级受限**：键只在矩阵允许的层级生效。`overflow` 写到 L0/L1/L2 时，四个读者都必须
   当它是**错误**——不能出现「vet 认、codegen 不认」这种分叉（现况见 §7）。

## 7. 现况与差距（2026-11-11 实测）

用 `bin/no` 逐项验证，形状统一为「两个 `i8 = 100` 相加，看结果是 `err` 还是 `-56`
（wrap）」；平台键用 `#{win-amd64}` 在 macOS 上验证是否被排除。

| 层级 | `overflow`（设计：仅 L3） | 平台键 | 宣告键 |
| --- | --- | --- | --- |
| L0 模组 | ✗ 设计禁止；目前会附着到首条陈述（等于 L1） | 未实作 | 未实作 |
| L1 宣告 | ✗ 设计禁止；**现况是漏洞**：`no vet` 认（整函跳过）、codegen 不认（仍 `err`） | ✓ 整棵子树排除 | ✓ |
| L2 区块 | ✗ 设计禁止；codegen 不认。`for` / if 组 / match 臂头能让 `no vet` 沿块闭嘴；**语句位置裸块 `{` 连闭嘴都做不到**（见下） | ✗ 块内仍参与编译 | — |
| L3 单行 | ✓ | ✓ | — |

实测证据：

```text
a-none.no    (无注解)                     → err
b-line.no    (陈述上方 #{overflow=wrap})   → result:true  (-56，生效)
c-fn.no      (函式上方 #{overflow=wrap})   → err           (vet: No issues found)
d-block.no   (for 上方 #{overflow=wrap})   → err ×2        (vet: 2 hints)

p1-block.no  (#{win-amd64} + 2 * {…})      → 块体仍执行    (未过滤)
p2-stmt.no   (#{win-amd64} + 单条 print)   → 该行被排除    (生效)
p4-fn.no     (#{win-amd64} + 函式宣告)     → 函式被排除    (生效)
p6-ifgroup.no(#{win-amd64} + if 组)        → 臂仍执行      (未过滤)

; 编译期对照：`for` 头加注解 vs 不加，15w45dqk 逐字相同
k2.no (for 头 #{overflow=wrap} + 体内 `x i8 = a + a`) → cannot assign ?i8 to i8
k3.no (删掉那一行，其余逐字相同)                       → cannot assign ?i8 to i8
```

裸块为什么连闭嘴都做不到：`parseAnnotationStatement` 的可附加目标只有 IDENT / USE /
IN / RARROW / 阵列型别方法，`{` 不在其中。所以下面这种写法里的注解既没挂到块上、也没
挂到块内陈述上——它退化成一条独立的 `AnnotationStatement`，对 parser、codegen、
`no vet` 三者都是死行：

```no
#{overflow=wrap}
{
    ...
}
```

`for` / if 组 / match 臂的头以识别符或 `in` 起首，才恰好落在可附加目标里。

三个要收紧的洞（`overflow` 的「只给 L3」尚未强制）：

1. **`no vet` 见到函式级 `overflow` 就跳过整个函式**（`walkStmtForOverflow` 的
   `fn.OverflowMode == ""` 短路）→ 检查全绿、执行期照旧 `err`。
2. **`no vet` 沿块向下继承**（`enclosingOverflow`）→ 块头一行注解让整个块闭嘴，
   即使 codegen 根本不认。
3. **parser / codegen 对 L1/L2 的 `overflow` 静默忽略**，不报错 → 作者无从得知它没生效。

存量盘点与处置（`src/std`，`no fmt --fix=overflow` 跑过三轮下推）：

| 类别 | 迁移前 | 第一轮后 | 第二轮后 | 第三轮后 |
| --- | --- | --- | --- | --- |
| `overflow` 注解行合计 | 4580 | 4083 | 3861 | 4080 |
| 其中是「挂不上任何节点」的死行 | 330（按形态计） | 87 | **0** | **0** |
| 被 `no vet` 报告、却标不了 | — | ~270 | 270 | **51** |

第一轮（2026-11-11）净变化：删 816 行作用域级注解，插入 325 行逐条注解。按 A/B 拆开看，
325 行里约 218 行是本来就缺标、与下推无关的站点（只跑插入、不摘遮蔽时同样会补这些），
约 97 行是块级意图被物化成逐条。

第二轮（2026-11-12）是**纯清扫**，成因是 `findFixTargetNode` 不下钻臂体、也没有「插完自检」：
381 行删除、159 行新增，**全部是 `#{...}` 注解行，0 行代码**（`diff` 逐行核对）。其中
159 行是「从块头/臂头挪到陈述上方」的位移，其余 222 行是把死行与多余的作用域级注解直接
删掉——这些位置本来就不生效，删掉不改任何编译/检查结果。

第二轮一并修掉的三个工具缺陷：

1. **`checker` 报行号塌到容器**：`walkExprForIntOverflow` 的 `emit` 混用了容器的
   `stmt.Pos().Line` 与运算子的 column，于是 `{ ... }` / if 组 / match 臂里每一处报告的
   行号都是 header 行。诊断指错位置只是表象，真问题是 `--fix` 的 `findFixTargetNode`
   取「包含该行的最内层陈述」，只能拿回容器，注解被插回块头。现在改取**运算子自身行**
   （`x.Token.Line`），token 行号缺失时回退容器行。
2. **不下钻臂体**：`findFixTargetNode` 原本刻意停在整个 match 陈述上方。现在下钻
   **块形式臂体**（`cond -> {` 的 `{ ... }`，含 `{ ... }: { ... }` 的 `BlockMatchStatement.Body`），
   行内臂体仍不下钻（`w i64 -> w + 1` 的陈述与臂模式同行，插到它上方等于插进 match、
   落在臂模式行之前）。
3. **插到挂不上的位置也照插**：`#{overflow}` 现在插完会**再解析一次自检**，把「插了但
   退化成一条独立 `AnnotationStatement`」的注解撤回（不再留死行）。撤回后第二趟 `--fix`
   拿到的源码不动，幂等保持。

第三轮（2026-11-12）动的是 parser：`parseAnnotationStatement` 的附加目标新增 **DOT**。
`.n = .n + 1` / `.cnt == 0 -> …` 这种以接收者起首的陈述与 `x = …` 是同一类（单条陈述、L3），
过去却不在附加目标之列 ⇒ 注解退化成独立 `AnnotationStatement`（死行），站点永远被报告、
`--fix` 插了也被自检撤回。放宽后 219 处站点拿到了 L3 注解（注解行 3861 → 4080），
标不了的从 270 降到 51。AST 形状因此改变（少一条 AnnotationStatement、目标陈述多一条
side-table 记录与 `OverflowMode`），`parser.ASTVersion` bump 到 `2026-11-12.1`，改完必须
`make gen no`。

**`{` 与 `(` 刻意没放宽**：`{`（语句位置裸块 / 带括号 match）与 `(`（`(cond) { }` 回圈头）
是 L2 区块宿主，而 `overflow` 的设计是只认 L3。放它们进来会让 `overflowAnnotatedNode`
对整个块提前返回，等于把 L2 语义合法化，与 §8「先收紧再放宽」的顺序冲突。剩下的 51 处
绝大多数是这两类，属 §8 第 4b 步。

验收口径（隔离树 A/B，同源同编译器、只差 `src/std`，逐档 `no vet`）：73 个受影响档
**全部 0 error**（无编译破坏），25 档的诊断变少、19 档变多——变多的全是摘掉遮蔽后暴露
的 `ovfhndld`「绑到 `?T` 但没宣告溢出取值」，属 §8 第 1 步的预期结果，不是新缺陷。
另有 9 条 `nolang-overflow-ineffective` 警告是工具原有的「补缺口」行为落在 bigint /
字串重载运算上的老问题，与下推无关。第二轮之后重跑 `bin/no run test-std/src/*.no` 全量
（zstd / tls / str / json / set / base32 …）**全部 PASSED**。

第三轮的重跑口径：`parser` 测试的 3 条红（`TestAnnotationsLiveOnAST` /
`TestCachedASTLowersToIdenticalHIR` / `TestBuildSemViewsMatchesFreshParse`）**在放宽前后
逐字相同**——`only 288 files parsed cleanly` 两次都一样，说明放宽没带来任何新的解析失败；
它们是并行工作中 parser/annotation 重构的在飞状态。`no fmt -d src/std` 的输出在放宽前后
**逐字节相同**，即 formatter 会把 `.` 上的注解原样打印回原位，没有格式漂移。`test-std/src`
的 heap / zstd / tls / json / set / map / regexp 全绿。

**残留 76 处臂头注解**（`#{overflow=wrap}` 紧接在 `cond -> {` 上方）：它们**不是死行**——
parser 会把臂级注解复制到臂体内每条陈述上，所以对臂体生效（实测：臂头一行注解让臂体
`r = i * 2` 闭嘴，只剩 header 条件那条照报）。但对**臂条件**本身无效（条件不是陈述）。
这 76 处维持原样：逐条插入拿不到它们（臂体站点已被闭嘴、不再被报告），而把它们摘掉再
补只会在 header 行原地折腾。

**仍被 `no vet` 报告、且当前语言无法标注的 51 处**（第二轮是 270 处，第三轮放宽 DOT 后
只剩这些）：目标陈述起首是 `{`（语句位置裸块 / 带括号 match）或 `(`（`(cond) { }` 回圈头），
以及少数臂 header 条件。它们今天**也**被报告（原来的注解本来就没生效），所以撤回不构成
回归；要清零得先做 §8 第 1–2 步（把 L2 的 `overflow` 判成错误），再决定要不要真的支援
L2——见 §8 第 4b 步。

抽查 `archive/bzip2.no:315` 这类位置，块头与块内**同时**有 `#{overflow=wrap}`：
块头那层当前不生效，真正工作的是块内逐条那层（`--fix=overflow` 已补过）。所以删除
块级层不改变语义；但删完再跑 `no vet`，会把「只靠外层注解闭嘴」的位置暴露出来——这正
是收紧的目的，不是副作用。实测 `crypto/rsa.no` 的 `ovfhndld` hint 由 19 条增到 22 条，
全部落在「绑到 `?T` 但没宣告溢出取值」的陈述上，语义未变。

L0 的存量影响：`src/**/*.no` 中以注解作为档案第一条有效行的有 21 个档，其中 17 个是
`#{js}`、其余是紧跟宣告的 `#{buildin}` 等——全部**没有**空行，按 §2 的 L0 判据
仍然是 L1，`no fmt` 与编译行为不变。`str.no` 有 2 处「注解 + 空行 + cond 臂」，
位于函式体内，不触发 L0 判据。

## 8. 收紧顺序

1. **先让 `no vet` 不再认 L1/L2 的 `overflow`**：删掉「函式级整函跳过」的短路，
   并把 `enclosingOverflow` 限制在同一陈述的子树内（不跨块向下传）。
2. **再让 parser 报错**：`#{overflow}` 落在 L0/L1/L2 → 编译错误，讯息指向「请逐条标注，
   或跑 `no fmt --fix=overflow`」。这一步会一次性暴露所有存量。
3. **清理存量**：`no fmt --fix=overflow` 已具备下推能力（摘掉作用域级那层，再按 checker
   的报告逐条补 L3），`src/std` 跑过三轮（见 §7 的存量表）。改完必须 `make gen no`（重烤
   blob 与 StdSigKey），且不得对 `src/std` 跑 `no fmt -w`——迁移只动注解行，用逐档
   `no fmt -fix=overflow -w <f>` 完成，`diff` 保证没有其它改动。
4. **放宽 parser 的附加目标**（第三轮已完成一半）：
   - **4a 已完成**：`parseAnnotationStatement` 接受 **DOT** 起首的陈述。`.n = .n + 1` /
     `.cnt == 0 -> …` 与 `x = …` 同属单条陈述（L3），过去却挂不上注解 ⇒ `src/std` 有 219 处
     `#{overflow=wrap}` 从未生效。放宽后标不了的从 270 降到 51，`parser.ASTVersion` bump 到
     `2026-11-12.1`。
   - **4b 待决策**：`{`（语句位置裸块 / 带括号 match）与 `(`（`(cond) { }` 回圈头）是 **L2
     区块宿主**。放宽它们等于给 `overflow` 合法化 L2 语义（`overflowAnnotatedNode` 会对整个
     块提前返回），与第 1–2 步的收紧方向相反。正确顺序是先做第 1–2 步（L2 的 `overflow`
     判错），再看剩下这 51 处要不要靠「改写成不带块的陈述」或「逐条补 arm body」解决，
     而不是无条件放开 `{` / `(`。
5. **其余键逐步收紧**：把宣告键（`buildin` / `generic` / `embed`…）写在 L2/L3 从
   「无效」改成「报错」。
6. 每一步都要保证 `no fmt` 幂等，且四个读者对同一份输入结论一致（§6）。
