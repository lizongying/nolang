# 文字列

Nolang の文字列（`str`）はヒープに割り当てられたバイト列で、さまざまな演算子とメソッドをサポートしています。

## 内部レイアウトと対外 API

`str` の記述子（`%str-long`）は 64 ビットプラットフォームでは **16 バイト**です：

```llvm
%str-long = type { i32, i32, i8* }   ; u32 len, u32 cap, data
```

| フィールド | 内部型 | 対外型 | 説明 |
|---|---|---|---|
| `len` | `u32`（LLVM `i32`） | `i64` | 論理的なバイト長；`s.len-bytes()`、`len(s)`、`s._len()` |
| `cap` | `u32`（LLVM `i32`） | `i64` | 実際の容量（str-long のみ有効）；`s.cap()`、`s._cap()` |
| `data` | `i8*` | `[]byte` / `*byte` | ヒープバッファを指す |

内部で `len` / `cap` を `u32` に狭めているのは、記述子を 24 バイトから 16 バイト（`i32` + `i32` + 8 バイト境界に整列されたポインタ）に縮小するためです。**対外 API はすべて引き続き `i64`** です。読み取り時は境界で `zext i32 -> i64`、書き込み時は `trunc i64 -> i32` が行われます。標準ライブラリやユーザープログラムはこの変換を意識する必要はありません（また、意識すべきでもありません）。`s.len-bytes()`、`s.len()`、`s.cap()`、`s._len()` / `s._cap()` / `s._set-len()` / `s._set-cap()` のシグネチャは `i64` のままです。

> ⚠️ 内部カウンタは `u32` なので、1 つの `str` の長さ／容量の上限は 4 GiB（`4294967295`）です。この値を超える `i64` を渡すと境界で切り詰められます。通常の文字列処理には影響しませんが、巨大なバッファを事前割り当てする前に自分でチェックしてください。
>
> `txt` は**今回の変更の影響を受けません**：引き続き固定 256 バイトの `{ [255 x i8] data, i8 len }` で、`cap` フィールドはなく、長さは 1 バイトです。

## 文字列演算子

### 連結（`-`）

`-` 演算子を使って文字列を連結します：

```no
; 字面量拼接
s = 'Hello' - ' ' - 'World'

; 與變量拼接
greeting = 'Hello, ' - name
```

### 繰り返し（`*`）

`*` 演算子を使って文字列を繰り返します：

```no
s = 'Hello' * 3
```

### 比較（`==` / `!=` / `str.compare`）

`str` は**等価比較のみを実装**しています。`==` / `!=` は実行時の `@str_eq` を使い、複数文字の文字列も完全に合法です。

関係演算子（<code>&lt;</code> `>` <code>&lt;=</code> `>=`）には**文字列の辞書順の意味はありません**。文字列に対して使うとコンパイルエラーになります：

- **合法**：**1 文字**の文字列リテラル `'a'` は暗黙的に `char`（コードポイント）として扱われ、別の 1 文字リテラルや `char`（`"a"`）と比較できます。
- **エラー**：複数文字の文字列——`'ab'`、`str` 変数、`str` を返す呼び出し（以前は**暗黙的に false を返していました**）。

辞書順が必要な場合は `str.compare(b)` を使ってください：

```no
s = 'abc'
b = 'abd'
c = s.compare(b); -1（s < b）/ 0（相等）/ 1（s > b）

'a' <= 'z'; true — 單字元字串隱式 char
ch >= 'a'; ch 為 char，OK
s < b; 編譯錯誤：多字元字串
s.compare(b) < 0; 正確寫法
```

## インデックスとスライス

**インデックス**：`s[i]` の推論型は **`?char`**（Unicode コードポイント）であり、`byte` ではありません。範囲外の場合は `err`（`code.index-out`）を返し、範囲内の場合は `ok(コードポイント)` を返します（整数の `+ - * / %` と同じ統一ルール）。複数バイトの文字を含む文字列では、`s[i]` は文字列の先頭から UTF-8 を前方に復号して i 番目のコードポイントまで数えます（下方のパフォーマンス説明を参照）。

```no
#{fmt-skip}
s = 'Hello World'
c = s[0]: { ok -> it  -> _ }   ; 'H' 的碼點（?char 必須顯式解包，空臂取 '\0'）
```

> `?char` を使う方法は 3 通りだけです（**`#{index-out=DEF}` は D11 で廃止・削除済み**で、残ったアノテーションはコンパイルエラーです。
> また「明示的な plain 型で plain に戻す」ような近道もなく、`c char = s[i]` も明示的な消費が必要です）：
> **match によるアンパック**（`x = s[i]: { ok -> it, -> _ }`。空のアームは `char` のゼロ値 `'\0'` を取ります）、
> **place-match による書き込み**（`s[i]: { ok -> it = x, -> _ }`）、または**省略形 `?=` による上方への伝播**（関数が `?T` の結果パラメータを持つ場合、
> または文がブロック match の本体内にある場合）。詳細と例は〈syntax · 安全なインデックス〉を参照してください。

**スライス**：`s[a..b]` は元の文字列の**ビュー**を返します。型は引き続き **`str`** です（メモリを共有し、コピーしません）。スライスの添字は `s[i]` と同様に**コードポイント位置**です：

```no
sub = s[6..]; 'World'
sub = s[6..11]; 'World'
sub = s[0..5); 'Hello'（左閉右開）
```

> スライスの添字は**コードポイント位置**であり、バイトオフセットではありません。バイトオフセットでのスライスが必要な場合（例：`s.byte(i)` と組み合わせて走査する場合）は `s.slice-bytes(start, end)` を使ってください。

```no
; 長度
n = s.len(); code point 數（Unicode 字符數）
n = s.count(); 同上（舊方法名，仍可用）
n = s.len-bytes(); byte 長度（UTF-8 位元組數）
; 注意：裸 s.len（結構體欄位）已不再支援，讀寫都會報錯；請改用 s.len() / s.len-bytes()
```

### 暗黙変換（char → str）

`char` は `str` に**暗黙変換**できます。そのコードポイントを UTF-8 エンコードして新しい文字列にします。したがって以下の書き方はすべて合法で、`char.to-str()` を手動で呼ぶ**必要はありません**：

```no
s = 'héllo'; 'h' 'é' 'l' 'l' 'o'（é 為多字節）

; 1) s[i] 的 char 直接賦值給 str 變數 → 隱式轉成單字元字串
a str = s[0]; 'h'

; 2) 切片結果本身型別已是 str，直接賦值即可
b str = s[0..1]; 'hé'（下標 0..1，兩端皆含）

; 3) char 參與字串拼接（-）時隱式轉為 str
msg = 'first: ' - s[0]; 'first: h'

; 4) char 與 str 比較時隱式轉為 str
ok = s[0] == 'h'; true
```

> **`'...'` は `str` リテラル、`"..."` は `char` リテラル**です——`'x'` が 1 つのコードポイントしか持たない場合でも、それは `str` です。したがって `+` / `-` の**両側がリテラル**のとき（`'...'` と `"..."` の組み合わせ）は、上記の暗黙変換が働き、結果は整数演算ではなく**連結**になります：
>
> ```no
> 'x' - "a"                ; "xa"（拼接；不是 120-97 = 23）
> "a" + 'x'                ; "ax"
> 'xy' + "a"               ; "xya"
> ```
>
> 片側でも**リテラルでない**値（char 変数、`s[i]`、整数）があると、1 文字の `'...'` は**バイト**として整数演算に参加します——これは意図的な仕様であり、数字文字の値を取得する慣用法が成立する理由です：
>
> ```no
> c char = "5"
> n = c - '0'              ; 5（位元組相減，不是 "50"）
> m = 'A' + 1              ; 66
> "z" - "a"                ; 25（兩側都是 char 字面量，char 相減）
> 'x' - c                  ; 23（c 是變數 → 位元組運算）
> ```
>
> 逆に言えば、バイトへの退化は**相手が整数か文字のときにのみ**起こります。相手が `bool`、`f64`、構造体のような**バイトの意味を持たない**値の場合、`'...'` は依然として文字列で、式全体が**連結**となり、相手は `to-str` で文字列化されます：
>
> ```no
> b = true
> 'x' - b                  ; "xtrue"（不是 120 - 1 = 119）
> 'x' - 1.5                ; "x1.5"
> 'x' - 'y'                ; "xy"（兩側都是字串字面量）
> ```
>
> そのため `'x' - b` は `str` に代入できます：`s str = 'x' - b` は `"xtrue"` になります。一方 `s str = 'x' - 1` は依然として拒否されます。それはバイト演算であり（結果は数値です）、型が合わないからです。

> 暗黙変換が `str` にエンコードするのは**単一のコードポイント**だけです。数値が欲しい場合は `char` そのものを使ってください（例：`print(c)` はそのコードポイントの 10 進値を出力します）。明示的な変換が欲しい場合は、引き続き `c.to-str()` が使えます（暗黙変換と等価です）。
>
> `char` は単一の Unicode スカラー値を表し、内部の記憶型は **`i32`** です（有効範囲 `0 ..= 0x10FFFF`）。
>
> `char` は**通常どおり整数演算に参加できます**（例：`z = a + 25`、`u = ch - 32`）。コードポイント値として i32 の幅で計算されます。整数の仲間とは異なり、デフォルトで `option<int>` を返さないため、「未処理の整数オーバーフロー」のコンパイルエラーは発生しません。
>
> **文字化の方法**：`char` を文字に変換する際は常に**コードポイントの 10 進値**を出力します（`"A"` → `65`、`"é"` → `233`）、
> また `print(c)` と文字列補間 `print('{c}')` の結果は**一致していなければなりません**。char の算術は**符号付き i32** で計算され、
> そのため `"x" - "y"` は `-1` となり、どちらの経路も `-1` を出力します（片方が `4294967295` を出力することはありません）。
> 有効なコードポイントは常に `0 ..= 0x10FFFF` の範囲にあり（第 31 ビットは 0）、その範囲では符号付き拡張と符号なし拡張は等価です。
> したがってこの規則が影響するのは、char 算術が範囲外になって得られた負の値だけです。**文字そのもの**が欲しいのであって数値ではない場合は、
> `c.to-str()`（`"A".to-str()` → `"A"`）を使ってください。これは別の操作です。

## ASCII の最適化とパフォーマンスのヒント

`str`/`txt` の添字 `s[i]` が取得するのは**i 番目のコードポイント（Unicode 文字）**であり、i 番目のバイトではありません。したがって、複数バイトの UTF-8 文字（中国語、絵文字、`é` など）を含む可能性のある文字列では、`s[i]` ごとに文字列の先頭から UTF-8 を前方へ走査し、i 番目のコードポイントまで数える必要があります。時間計算量は **O(n)** です。

コンパイラがその文字列が ASCII 文字（コードポイント 0～127）のみで構成されることを**証明**できれば、各バイトがちょうど 1 文字となり、`s[i]` は元のバイトを直接アドレス指定して **O(1)** に退化します。コンパイラは以下のルールで純粋な ASCII を証明します：

- 明示的なアノテーション：宣言や代入の場所に `#{ascii}` アノテーションを付ける
- ASCII 文字列リテラル（例：`'hello'`）を代入する
- 識別子の伝播：`b = a` とし、`a` が ASCII と証明済みなら `b` も ASCII となる
- 連結（`-`）の両側がともに ASCII と証明済みである

```no
; ASCII 字面量 → 编译器证明为纯 ASCII，s[i] 为 O(1)
name = 'hello'
c = name[1]; O(1)，取字节 'e'

; 含多字节字符 → 无法证明 ASCII，s[i] 为 O(n) 码点迭代
s = 'héllo'
c = s[1]; O(n)，取第 1 个码点 'é'（而非字节）
```

### パフォーマンス警告（LSP / `no vet`）

**ループ内で手動的にコードポイント添字で走査**する場合で、ASCII と証明されていない `str`/`txt` に対して（`for i <- [0..s.count()): { s[i] }` のようなコードポイント添字で文字を 1 つずつ取得する書き方）、`no vet` とエディタの LSP が **WARNING** レベルの静的警告を出します（構文は禁止せず、注意を促すだけです）。この書き方では `s[i]` ごとに文字列の先頭から UTF-8 を前方走査して i 番目のコードポイントを取得するため、ループ全体が **O(n²)** に退化します。

単発の `s[i]`（例：`s[5]`。O(n) が 1 回だけ）では警告され**ません**。直接 `for c <- s` で文字を走査する場合も警告され**ません**（下記を参照）。

より高速な方法への変更をおすすめします：

- 各文字を走査する必要がある場合は、`for c <- s` で前方走査を直接使ってください。これは推奨される O(n) の単一スキャン写法で、`s[i]` を繰り返す O(n²) を回避できます。コンパイラは **UTF-8 コードポイント（Unicode 文字）** 単位で進み、復号したコードポイント値をループ変数 `c` に格納します。意味は `for c <- s.to-chars()` と等価です：
  ```no
  c <- s: {
      ; c は現在のコードポイント、型は char（UTF-8 でデコード済み、バイトではない）
  }
  ```
- バイト単位のアクセスだけでよい場合（エンコード／デコード、ハッシュ、memcmp など）は、脱出ハッチ `s.byte(i)` を使ってください。これは常に i 番目のバイトを直接アドレス指定し、**常に O(1)** で、std の関数本体に入りません：
  ```no
  b = s.byte(0); 0 番目のバイトを取得、型は ?byte、O(1)
  out = 0
  b: {
      ok -> {
          out = it; 在界内：ok(byte)
      }

      -> {
          out = 0; 越界：nil（空臂合成零值）
      }
  }
  ```
  > `s.byte(i)` の結果は **`?byte`** です（2026-10-21 以降）。それまでの素のバイト読み取りは境界チェックを行わず、
  > 範囲外の添字は未定義動作でした。現在は範囲外の場合 `nil` を返します。ただし、これはコンテナの添字 `arr[i]` / `s[i]` が範囲外で `err`
  > （`code.index-out`）を返すのとは**異なります**。`s.byte(i)` はバイト単位の脱出ハッチであり、範囲外は「そのバイトは存在しない」ことを示すだけで、エラーではありません。
  > （design/option-unified.md §3.1 第 5 条を参照）。そのため `b i64 = s.byte(0)` は
  > `15w45dqk` を報告します。明示的な plain 注釈と option 呼び出しの組み合わせは暗黙のアンラップであり、ハードなコンパイルエラーです。
  > `?=`、2 段構えの match（`b = s.byte(0): { ok -> it, -> _ }`）、または `_ =` を使って消費してください。
  > `txt.byte(i)` も意味は同じです（`txt` の `byte` フィールド 1 がバイト長そのものです）。

> 標準ライブラリ（src/std）内部のバイトアクセスはすべて `s.byte(i)` に移行済みです。`str.no`/`txt.no` の UTF-8 エンコード／デコード（`decode-cp`）、比較（`compare`/`starts-with`/`ends-with`）、ハッシュ、スライスのコピー（`slice`/`repeat`/`trim`/`copy`）、`to-bytes`/`to-upper`/`to-lower`/`reverse`/`replace-char`/`count`/`index` などが含まれます。そのため `no vet` が標準ライブラリのファイルをスキップする必要はなくなりました。その他の `[]byte`／スライス／配列型の要素アクセス `x[i]` は元々要素（バイト）単位の添字であり、意味は変わらず、警告も出ません。

| 書き方 | 意味 | 計算量 | 説明 |
|---|---|---|---|
| `s[i]`（ASCII 証明済み） | i 番目のバイト = i 番目の文字 | O(1) | 自動的に証明され、変更不要 |
| `s[i]`（ASCII 未証明、ループ内） | i 番目のコードポイント | O(n²) アンチパターン | LSP 警告の対象 |
| `s[i]`（ASCII 未証明、ループ外） | i 番目のコードポイント | O(n) 1 回 | 警告なし |
| `s.byte(i)` | i 番目のバイト（`?byte`、範囲外は `nil`） | O(1) | バイトアクセス用の脱出ハッチ |
| `for c <- s` | コードポイントごと | O(n) 単一スキャン | 走査の第一候補、警告なし |

## 文字列のメソッド

```no
#{fmt-skip}
; 比較
ok = a.eq(b, n)               ; 相等比較（方法）
c = s.compare(b)              ; 字典序比較

; 查找（index/rindex 返回「碼點（字符）位置」，與 s[i] 一致）
pos = s.index(sub)             ; 首次出現的碼點下標，未找到 -1
pos = s.index-from(sub, k)     ; 從第 k 個碼點開始查找
pos = s.rindex(sub)            ; 最後一次出現的碼點下標
pos = s.rindex-from(sub, k)    ; 從第 k 個碼點反向查找
pos = s.last-index(sub)        ; rindex 的別名
ok  = s.contains(sub)          ; 是否包含
ok  = s.starts-with(sub)       ; 前綴判斷
ok  = s.ends-with(sub)         ; 後綴判斷
ok  = s.empty()                ; 是否為空

; 注意：index 系列返回的是「碼點位置」，因此 s[s.index(sub)] 取到的是 sub 的首字符，
;       與 s[i] 的碼點索引語義一致。例如 '日本語'.index('語') == 2，且 s[s.index('語')] == '語' 的碼點。
;       若需「碼點位置」切片，s.slice(start, end) 即碼點語義（與 s[i] 一致）；
;       若需「字節偏移」切片（如配合 s.byte 遍歷），用 s.slice-bytes(start, end)。
;       str 內部提供字節級查找 str.find-byte-from（供 split 等複用）。
;       注意：txt 型別的 slice/at 仍為字節語義（txt 是裸字節緩衝），與 str 語義分叉。

; 轉換
out = s.to-upper()             ; 轉大寫
out = s.to-lower()             ; 轉小寫
out = s.trim()                 ; 去首尾空白
out = s.trim-char(c)           ; 去指定字元
out = s.repeat(n)              ; 重複
out = s.reverse()              ; 反轉
out = s.slice(start, end)      ; 切片（下標為碼點位置，與 s[i] 一致）
out = s.slice-bytes(b, e)      ; 切片（下標為字節偏移，內部使用）
val = s.replace-char(old, new) ; 取代字元

; 轉換為其他型別
b = s.to-bytes()               ; 轉 []byte
v = s.to-i64()                 ; 轉 ?i64
v = s.to-f64()                 ; 轉 ?f64
v = s.to-bool()                ; 轉 ?bool

; 分割與連接
parts = s.split(sep)           ; 分割（返回 []str）
out = ss.join(sep)             ; []str 連接

; 複製與填充
dst = s.copy()                 ; 字串複製
s.fill(val byte)               ; 填充 byte 值
```

## 文字列と数値の変換

```no
; 數值轉字串（方法）
s = i64.to-str(); i64 轉字串
s = f64.to-str(); f64 轉字串
s = bool.to-str(); bool 轉 "true"/"false"
s = byte.to-str(); byte 轉字串
s = char.to-str(); char 轉字串

; 字串轉數值（返回 option）
v = s.to-i64(); 回傳 ?i64
v = s.to-i32(); 回傳 ?i32
v = s.to-u64(); 回傳 ?u64
v = s.to-f64(); 回傳 ?f64
```

## 添字書き込みは禁止されています（`str` 2026-11-11 / `txt` 2026-11-12）

> **`s[i] = v` はコンパイルエラー `idxwrite` です**。`with-cap` / `with-len` / `with-cap-len`
> いずれの基底でも例外はありません。**`txt` の `t[i] = c` も同様に禁止されています**（理由は下記）。
>
> `str` の理由：これは「範囲外への書き込みが確保済みバッファの外に出る」唯一の原因です。len=0 のバッファは直接書き込みで伸長するため、
> `i >= cap` に書き込むと確保領域を越えてしまいます。codegen の `ensureStrLongBuffer` による伸長ガードは元々
> このために設けられていました。直接書き込みの禁止後はこのガードにユーザーコードから到達できなくなり、防御的なコードとしてのみ残っています。
>
> `txt` の理由は異なりますが罪は同じです。`t[i] = c` はコードポイント単位で**再エンコードして書き戻す**ため、長さが書き込みに応じて暗黙に変化します
> （`i` がコードポイント数に等しい場合は追加と等価、255 を超える部分は暗黙に破棄されます）。txt にはヒープも拡張もありませんが、
> 「1 回の添字書き込みでこっそり長さが変わる」という点は同じ種類の危険です。

引き続き合法な 4 つの書き方：

```no
; ① 逐位元組「構造」：[]byte 緩衝承接，收尾整體轉回 str
b []byte = with-cap-len(n, n)
b[0] = 48
b[i] = src.byte(i): {
    ok -> it

    -> 0
}
s = b.slice(0, k).to-str(); 也可 b.to-str()（整段）

; ② 原位「覆寫」既有內容：str.fill 把 len 個位元組全填成同一個值，長度不變
s = 'hello'
s.fill(72); 'HHHHH'

; ③ 下標寫只剩 place-match（以「讀」作閘門：i >= len 時靜默跳過，不增長、不越界）
s[i]: {
    ok -> it = v
    -> _
}

; ④ 要變長：用 push 家族（顯式、可審計的一次呼叫）
s.push("中");      按碼點追加（UTF-8）
s.push-str('de');  按位元組追加（原地擴容）
```

> ⚠️ **place-match は「コードポイント」のゲートであり、バイトのゲートではありません。** そのゲートの出自は `s[i]` という
> **読み取り**です——そして `str` の添字読み取りはコードポイント単位です。したがって ③ は「1 コードポイントで 1 スロットに書き込む」
> ASCII の場面（uuid にハイフンを入れる、time に数字を入れる、hex 表を引く）にのみ適しています。**バイト**単位で内容を組み立てるには
> （`>= 0x80` のバイトや、非 ASCII の可能性があるソース文字列を含む場合）、① の `[]byte` を使う必要があります。
> 実測では `f = with-len(8)` の後に place-match で 224..231 を順に書き込むと、最初の 4 スロットしか保存されず、
> 残りはゲートによって暗黙にスキップされました。`path.split` の「非 ASCII のファイル名」が切り詰められるのもまさにこの仕組みです。

> **長さの切り詰め**：素の `s.len = n` はもはやサポートされません。代わりにスライスを使ってください——`s.slice(0, n)` は**コードポイント**スライスであり、
> `s.slice-bytes(0, n)` がバイトスライスです（`[]byte` バッファ上の `b.slice(0, k)` は当然バイトスライスです）。
>
> **`with-cap(n)` で str を作った後に `push` で伸長する**：`s str = with-cap(256)` は len=0 ですが容量を持つバッファで、
> 最初の `push` はそのまま書き込まれ、拡張をトリガしません（`push-str` は `len + 追加長` が
> `cap` を超えたときだけ realloc し、倍増で成長します）。バイト単位の `buf[i] = b` は str に対して引き続き禁止されています。

### 伸長：`push` ファミリー（2026-11-12）

直接書き込みが禁止された後、**可変長には明示的な 1 回の呼び出しが必要**です：

| メソッド | 意味 |
|---|---|
| `s.push(c char)` | 1 つのコードポイントを追加し、UTF-8 エンコードします（内部で `push-str` に委譲） |
| `s.push-str(t str)` | 文字列を追加します。**バイト単位**でコピーし、その場で拡張します |

```no
s = 'ab'
s.push("中");      'ab中'，len-bytes 5、len 3
s.push-str('de');  'ab中de'，len-bytes 7

t = 'zz'
t.push-str(t);     'zzzz'（自我追加安全：先 retain 源、再用 memmove 拷貝）

u = ''
u.push-str('');    ''（空源不改變任何東西，也不分配）
```

> `push-str` はコンパイラ組み込みです（`#{buildin}`。MIR では「その場での拡張 + memmove + 長さの変更」に展開されます）。
> std のループではありません。1 回の追加は O(追加長) で、繰り返し追加ならならし O(1) です（倍増）。
> `push` は UTF-8 エンコードを経由するため、`len-bytes` の増分はそのコードポイントのエンコード長に等しく、`len` は常に 1 増えます。

> **`txt` への書き込みも同様に禁止済み（2026-11-12）**：`t[i] = c` は**コードポイント単位の再エンコード書き戻し**であり、長さは
> 書き込みに応じて暗黙に変化します——`i` がコードポイント数に等しい場合は追加と等価で、合計バイト長が 255 を超える部分は暗黙に破棄されます。
> 「1 回の添字書き込みでこっそり長さが変わる」こそが禁令で消したいものであり、txt も str と同じ扱いです。txt の可変長の
> 入口は `t.push(c)` / `t.push-str(s)` / `t.push-txt(u)` です。その場で値を変えるには place-match を使います。
> 読み取り `t[i]` は引き続きコードポイント `char` を返し、この点は変わりません。
>
> バイト単位の生の書き込み関数 `str._set-byte` / `txt._set-byte` は 2026-11-11 以降 **std 専用**です
> （std 内部の `str.fill` / `txt.push` などだけが呼び出します）。ユーザーコードからは使えません。
> バイト単位で `txt` を組み立てる必要がある場合は、まず `[]byte` に溜めてから `txt.from-bytes(b)` で一度にコピーしてください
> （255 バイトを超える分は自動的に切り詰められ、長さは実際のバイト数に設定されます）。

## 事前割り当て（組み込み構文）

`with-cap`、`with-len`、`with-cap-len` という 3 つの組み込み構文でヒープメモリを事前に割り当て、その後の `push` による繰り返しの拡張を回避できます：

```no
; with-cap(cap)：配置 cap 容量，len=0（需 push 後才能索引）
s = with-cap(256); str，len=0, cap=256

; with-len(len)：配置 len 容量，len=cap（可直接索引讀）
s = with-len(128); str，len=128, cap=128

; with-cap-len(cap, len)：同時指定容量與長度，適合「預留成長空間」場景
s = with-cap-len(512, 64); str，len=64, cap=512
```

| 組み込み構文 | 引数 | len | cap | 適用場面 |
|---|---|---|---|---|
| `with-cap(cap)` | 1 | 0 | cap | 上限のみが分かっており、長さは push で伸長させる |
| `with-len(len)` | 1 | len | len | 長さが固定で、添字で直接読み取れる |
| `with-cap-len(cap, len)` | 2 | len | cap | 初期長が分かっており、拡張用の余裕も確保したい |

> 引数と `s.cap()` / `s.len-bytes()` の戻り値はいずれも **`i64`** です（対外 API は不変）。ただし記述子内部では len / cap を
> **`u32`** で保持しています。呼び出し側が見るのは引き続き 64 ビットの数値で、変換はコンパイラが記述子の境界で行います。
> 詳細は〈内部レイアウトと対外 API〉を参照してください。`s.len = n` / `s.cap = n` のようなフィールドへの代入も同じ境界を通るため、
> 隣接する header フィールドを上書きすることはありません。

> ⚠️ **`str` のバッファには添字による直接書き込みは一切許可されません**（2026-11-11 以降、`with-cap` 基底も例外ではなくなりました）。
> `idxwrite` の with-cap 例外は現在 **`[]byte` / `[]T` / 固定配列** のみを対象とします。これらは len=0 の
> バッファを `buf[i] = b` で伸長させ続けており、等価な代替書き方がありません。`str` では `[]byte` バッファ +
> `to-str()` に切り替えてください（〈添字書き込みが禁止されています〉の節を参照）。
> `with-len(n)` / `with-cap-len(cap, len)` は len がすでに確保されているため、**書き込みには place-match
> `buf[i]: { ok -> it = v / -> _ }` または `buf[i] ?= v` が必要**です。他のどのコンテナと同じく、直接書き込みは
> コンパイルエラー `idxwrite` です。（2026-11-10 以降 `with-len` も例外ではなくなりました。）

> **型推論**：3 つの組み込み構文の結果型は代入の左辺から推論され、`str` や `[]T` スライスに使えます。
