# メモリ管理

Nolang は**GC なし**の言語であり、メモリ安全はコンパイラが自動的に `free` を挿入することで保証されます。本記事では、実装済みのメモリ設計と所有権のセマンティクスについて説明します。

## 中心的な原則

### 単一所有権
各ヒープの `data` バッファには**所有者が 1 つだけ**います。所有権は move によって転移でき、転移後は元の所有者が free の責任を放棄します。ローカル変数間の `=` は、深い clone によって 2 つの変数がそれぞれ独立して data を所有するようにします。

### 代入のセマンティクス
`b = a` は文脈に応じて、以下のセマンティクスのいずれかを選択します：

| セマンティクス | 発動条件 | 動作 |
|------|---------|------|
| **値コピー** | 基本型（i64/f64/bool など）で can_slot_rebind を満たさない | 値を直接コピーし、ヒープデータなし |
| **スタックスロット再バインド** | ローカル変数間の `b = a` で、a がスタック型（i64/u64/i128/u128/txt）かつ can_slot_rebind を満たす | `g.varAlias[b] = a` とし、b と a が同じスタックスロットを共有、0 コピー（値コピーより優位）；そうでなければ値コピーに格下げ |
| **深い clone** | ローカル変数間の `b = a` で、a がヒープ所有型（vec/arr/str/clone 可能な構造体/**`?str`、`?[]T`**）かつ代入後も**参照されている** | 新しい data を malloc + memcpy + 要素を再帰的に clone；a と b がそれぞれ独立して data を所有し、関数終了時にそれぞれ free |
| **move（ソースは死亡済み）** | ローカル変数間の `b = a` で、a がヒープ所有型だが代入後**参照されない** | ゼロコピーで所有権を転移；ソースは free をスキップ。深い clone と**観測的に等価**で、コピー 1 回分だけを削減 |
| **move** | 出力引数 `out = x` | 構造体を浅くコピー + ソースを moved とマーク；ソースは free をスキップ |
| **深い clone** | `vec.push(x)`（x がヒープ所有型） | 新しい data を malloc + memcpy + 要素を再帰的に clone；ソースは独立した data を所有し続け、関数終了時にそれぞれ free |

> **値から値への代入は常に深いコピーであり、ゼロコピーのエイリアスを禁止します。** `b = a`（RHS が名前付き変数全体）には 2 種類の lowering しかありません——
> **ソースが生存中 ⇒ 深い clone**、**ソースが死亡済み ⇒ move**；「2 つの名前が 1 つの buffer を共有し、free を 1 つだけ残す」ことは**許可されません**
> （そのような lowering は読み取り専用の前方最適化にかつて存在しましたが、削除されました）。**要素／フィールドの読み取り**（`b = a[i]`、`b = a.f`）は
> **ビューエイリアス**のセマンティクスを維持し、この制限を受けません。

## スタック型の move（スタックスロット再バインド / slot-rebind）

`i64/u64/i128/u128/txt` はいずれも**スタック型**（値が alloca のスタックスロットに直接格納され、ヒープ data は存在しない）ですが、`b = a` はセマンティクス上、引き続き既定で「値コピー」（a のスタック値を b のスタックスロットへ memcpy する）を実行します。不要なコピーを減らすため、コンパイラは **can_slot_rebind** 制約を満たすスタック型の `b = a` に対して**スタックスロット再バインド**を実行します：`g.varAlias[b] = a` とし、b と a に同じスタックスロットを共有させます（0 コピーで、値コピーより優位です）。

### can_slot_rebind 制約（保守的な正しさ）
再バインド後、b と a は同じスタックスロットを指すため、a がその後 b に対して行う読み取りはすべて「a のストレージ」を読み取ることになります。セマンティクス上の誤りを避けるため、再バインドはソース a が**今後「まったく参照されない（読み取りも書き込みもない）」**場合にのみ許可され、それ以外では**完全な値コピーに格下げ**されます（セマンティクスは不変で、memcpy が 1 回増えるだけです）。

- 安全性は `computeSlotRebindSafety`（main 関数）/`computeMoveEligibility`（ユーザー関数）が `stmtContainsVarRefAny` / `exprContainsVarRefAny` を用いて静的に求解します：move 以降のすべての文（分岐／ループのバックエッジを含む）を走査し、ソース変数が何らかの形で参照されていれば `slotRebindSafe[stmt] = false` となり、コピーへ進みます。
- 参照の走査では**変数を参照しうるすべての AST ノード**を網羅する必要があります。網羅されていない書き込み参照があると、安全でない再バインドが発生します（エイリアス先のスロットが汚染され → 誤った出力や無限ループに至ることもあります）。カバー済み：文レベルでは `LetStatement` / `ExpressionStatement` / `ForStatement`（`Init`/`Update`/`Condition`/`CountExpr`/`Body` と **`IterRange` による反復集合**を含む）/ `ReturnStatement` / `MultiAssignStatement` / **`UnwrapAssignStatement`（`?=` によるアンラップ代入）** / **`BlockStatement`（ベアブロック）**；式レベルでは `Identifier` / `AssignExpression` / `Infix` / `Prefix` / `Call` / `Dot` / `Index` / `IfExpression`（分岐本体を含む）/ `Slice` / `Conditional` / `Grouped` / **`CoExpression`（`co <call>` によるコルーチン spawn。防御的なもので、関数全体の無効化は引き続き `curHasUnsafeConstruct` が担当）** / **`CastExpression`** / **`RangeExpression`**。新たに変数参照を導入する構造を追加した場合は、必ずこれら 2 つの走査関数にも追加してください。
- `match` は `IfExpression` に desugar されるため、その分岐本体内の参照は上記の解析の走査にカバーされ、したがって **match は無効化をトリガーしません**（`tests/match.no` / `tests/option.no` によりベースラインと一致することが検証済みです）。

### 無効化シナリオ（常に値コピーへ格下げ）
| 無効化条件 | 理由 |
|---------|------|
| ターゲットが出力引数 / グローバル変数 / ヒープ型変数 | 出力引数はポインタで渡され、グローバルは関数をまたいで可視であり、ヒープ型は深い free が必要なため、再バインドは所有権を破壊する |
| ソースが引数 / グローバル変数 | 引数は参照で渡されるため、再バインドは呼び出し元のスタックフレームを破壊する |
| **stdlib 関数**（`curIsStdLib`、`SetStdModules` が判定） | stdlib 内部の alias バインド（fmt の `it` がローカルの `n` に別名化されるなど）は参照解析で完全にモデル化することが困難 |
| **ユーザー関数本体がクロージャ（`FunctionLiteral`）またはコルーチン spawn（`RunExpression`）を含む**（`curHasUnsafeConstruct`、`bodyHasUnsafeConstruct` が再帰的に走査） | クロージャが捕捉した変数は「独立した関数コンテキスト」で評価され、コルーチンはスレッドをまたいで実行されるため、いずれも変数のライフタイムが現在の関数の `g.varAlias` 単一関数エイリアススコープを超え、再バインドは共有スタックスロットを破壊する |

> 設計上の取捨：クロージャ／コルーチンには「変数ごとの精算」ではなく「関数単位の無効化」を採用しています。単一関数のエイリアス解析では関数間／スレッド間のストレージ共有を本質的にモデル化できないためです。関数単位の無効化は最適化を失うだけ（コピーへ格下げ）で、誤りを一切導入せず、「保守的な正しさ」の原則に適合します。

### エイリアスの無効化（alias invalidation）
- ターゲットが再代入された際、まず `delete(g.varAlias, name)` で残った古いエイリアスを消去します。そうしないと汎用の代入パス `varAddr(name)` が古いソースのスタックスロットを指したままになり、古いソースを汚染します。
- 再バインドは推移的な解決を実行します：`g.varAlias` のチェーンをたどって最終的なソースのスタックスロット（`a → c → …`）を見つけ、複数ホップのエイリアスによる位置ずれを避けます。また `g.varTypes[name]` も同期させ、以降の型問い合わせを整合させます。

### ヒープ型の move との直交性
スタックスロット再バインドはスタック型の `b = a` における**値コピー**のセマンティクスにのみ作用し、ヒープ所有型の「深い clone / move（出力引数）」とは完全に直交します。ヒープ型のパスは `slotRebindSafe` の影響を受けません。

### テストの参考
- `tests/slot-rebind.no`：i64/u64 の再バインド、i128/u128 の `==` による比較、txt の `.len-bytes()` による比較、コピーへの格下げ（`da` の再利用 → `db`/`dc` はコピー）、再代入後（`ra`=10）、引数の move（`pm_fn` のソースが引数 → コピー）、再バインド後の再代入（`rr_fn` → `rr`=99）、消費（`consume(m)` → `cm`=84）。期待出力は `42 7 1 1 17 5 5 10 100 99 84`。
- `tests/slot-rebind-unsafe.no`：コルーチン（`awy { co ... }`）がスタック変数を capture するケースで、`curHasUnsafeConstruct` による再バインド無効化後も出力がベースラインと一致することを検証します。

### コンパイラによる free の挿入
- 関数終了時：moved になっていないすべてのローカルヒープ変数を解放
- 再代入前：古い値を解放
- 構造体のフィールド：ヒープデータを含むフィールドを再帰的に解放

## 型のレイアウト

| Nolang の型 | メモリ構造 | フィールド | 割り当て戦略 |
|------------|-----------|------|---------|
| `[]T`（スライス） | **16 バイト** | **u32 len, u32 cap, i64 data（ptrtoint）** | malloc（ヒープ） |
| `[N]T`（固定長配列） | N × sizeof(T) | 要素はインライン、**len/cap ディスクリプタなし** | alloca（スタック）または malloc |
| `str`（長い文字列） | **16 バイト** | **u32 len, u32 cap, i8\* data** | malloc（ヒープ） |
| `txt`（固定文字列） | 256 バイト | `[255 x i8]` data, i8 len | alloca（スタック） |
| `?T`（nullable） | **ペイロードに応じて決定**：`{ i8 tag, [K x i64] }` | 1 バイトのタグ + 7 バイトのパディング + ペイロード（8 の倍数） | alloca（スタック）；ペイロードが閾値を超える場合はヒープポインタを格納 |
| タグ付き列挙型 | `{ iN tag, [K x i64] }` | tag の幅はバリアント数に依存（`i8` から開始）、ペイロードは最も広いバリアントの union | alloca（スタック） |
| 構造体 | 各フィールドの合計 | 各フィールド | alloca（スタック） |

**`?T` のサイズは固定ではなく、計算によって求められます**：`?i64` = 16 バイト、`?str` = 24、`?txt` = 264 であり、
`option-inline-threshold`（既定値 264 = 1 + 7 + 256、最小 16）を超えるペイロードはヒープにボックス化され、option 全体は
16 バイトに戻ります。ペイロード型ごとに専用の `%option_<key>` 型があるため（`src/mir/layout.go`）、
「型が同じ ⇔ レイアウトが同じ」となります。`err` のペイロードは常にボックス化され、ペイロード予算を消費しません。詳細は
`docs/docs/lang/syntax.md` の〈nullable 型（option）・メモリレイアウト〉を参照してください。

**タグ付き列挙型**の tag 幅はバリアント数に応じて変化し（`<=256` → `i8`、`<=65536` → `i16`、`<2^32` → `i32`、
それ以外は `i64`）、ペイロード union の幅は「最も広いバリアント 1 つ」であり、すべてを合計した値ではありません。フィールドは自然アラインメントで配置され、
**バイトオフセット**でアドレス指定されます。すべてのバリアントがペイロードを持たない場合、レイアウトは `{ iN }`（1 バイトから開始）に退化します。

**`str` の u32 ヘッダ**：`%str-long = type { i32, i32, i8* }`（64 ビットプラットフォームで 16 バイト）。
`len` / `cap` は内部的には `u32`（LLVM `i32`）ですが、**対外 API はすべて `i64` のまま**です：読み取り時に `zext i32 -> i64`、
書き込み時に `trunc i64 -> i32` を行います。`s.len-bytes()`、`s.len()`、`s.cap()`、`s._len()` / `s._cap()` /
`s._set-len()` / `s._set-cap()`、`len(s)` のシグネチャは変更されていません。この境界は codegen の
`strLenI64` / `strCapI64` / `strHeaderLoadI64` / `strHeaderStoreI64` / `strLongFromParts` が一括して処理します：
descriptor の第 0 / 1 フィールドに対して `load i64` / `store i64` を直接発行しては**いけません**。opaque pointer では
LLVM verifier が検出しないため、8 バイトを一度に読み書きして隣接する header フィールドまで変更してしまいます（実測で
`s.len-bytes()` が `len | cap<<32` を返したことがあります）。

関連するサイズ定数も 16 バイトに追従する必要があります：`[]str` の element stride、`os.args()` の argv backing
store、そしてグローバル文字列定数の `{ i32 len, i32 cap, i8* data }` リテラルです。`?str` のペイロードはちょうど 16
バイト（2 つの i64 word で、最初の word に len と cap がパックされている）なので、`?str` は 24 バイトのインライン option です；
タグ付き列挙型の `str` バリアントのペイロードも同様に 2 つの word です。`txt` は従来どおりで、`str` に合わせて u32 には変更しません。

**`[]T` の u32 ヘッダ**：`%vec = type { i32, i32, i64 }`（16 バイト）。`len` / `cap` は `str` と
同型で、内部的には `u32`、対外 API は `i64` のままです。違いは **data フィールドが `i64` のまま**（`i8*` ではなく
`ptrtoint` でエンコードされたポインタ）である点で、`inttoptr` / `ptrtoint` の既存の呼び出し箇所を変えないためです。この境界は
`vecLenI64` / `vecCapI64` / `vecHeaderLoadI64` / `vecHeaderStoreI64` / `vecFromParts`
（および汎用の `hdrFieldI64` / `hdrTrunc` / `hdrWiden`）が一括して処理し、`emitLenCap` / `emitGetField` /
`emitSetField` / `ensureVecBuffer` はすべてこれらを経由します。`str` と同じ禁止事項が適用されます：**`%vec` の
第 0 / 1 フィールドに対して `load i64` / `store i64` を直接発行してはいけません**。

`cap == 0` は `%vec` にとって**借用ビュー**の印です（`s.bytes()`、`[N]T` → `[]T` の借用、str → `[]byte` の
強制変換）：ヒープを所有せず、`@vec_free` / `@vec_retain` はスキップされます。`cap > 0` の場合のみ `data` が指すブロックを所有します。

`[N]T` には実行時のディスクリプタがまったくありません：LLVM レベルではむき出しの集約 `[N x T]` であり、`.len` はコンパイラが
コンパイル時定数 `N` に直接置き換えます。`cap` は存在しません。

## 浅い free と深い free

### 浅い free
コンテナの data バッファのみを解放し、要素を走査しません。以下に適用されます：
- `%str-long`（文字列 data は文字バッファであり、入れ子になったヒープ所有要素はない）
- 要素が基本型（i64、double など）の vec/arr

### 深い free
まず各要素を走査してそのヒープデータを再帰的に解放し、その後コンテナの data バッファを free します。要素がヒープ所有型の vec/arr に適用されます：
- `[]str`（要素が %str-long）
- `[][]i64`（要素が %vec）
- `[]MyType`（要素がユーザー構造体で、フィールドを再帰的に解放）

### NULL チェック
すべての free の前に `icmp eq i8* %ptr, null` をチェックし、free(NULL) や未初期化ポインタの free を回避します。

## 所有権の転移（move）

### 単一戻り値の move
```no
get-slice = () (out []i64) {
    local = [1, 2, 3]
    out = local; local 標記為 moved，函數結束不 free；out 由呼叫者管理
}

v = get-slice(); v 擁有 data，函數結束時 free
```

### 複数の戻り値の move（引数の位置順）
```no
get-pair = () (a []i64, b []i64) {
    x = [1, 2]
    y = [3, 4]
    a = x; 第一個輸出參數，x 標記為 moved
    b = y; 第二個輸出參數，y 標記為 moved
}

a, b = get-pair(); a 擁有 x 的 data，b 擁有 y 的 data
```

**処理順序**：出力引数を関数シグネチャでの**宣言順**に従って順に処理します。各 `out = src` 代入はソース変数を個別に moved とマークします。

**同じソース変数への複数代入**：`a` と `b` が同じソース変数を参照する場合（例：`a = x; b = x`）、コンパイラは **Liveness 事前解析**（`moveEligible`）によって clone か move かを自動的に決定します：

- `a = x`：x が後続の `b = x` で参照される → **深い clone**、a が独立して data を所有
- `b = x`：x が後続で参照されない → **move**、b が x の data を引き継ぎ、x は moved とマークされて free をスキップ

これにより double-free を回避できます。規則：**最後の参照は move、それより前の参照は clone**。

条件分岐のシナリオ（例：`if cond { out = x }`）では、実行時のビットマップで moved 状態を追跡します。次節を参照してください。

### vec.push の深い clone
```no
inner = [1, 2, 3]
outer.push(inner)
; inner 的 data 被深層 clone 到 outer 新元素位置
; inner 仍擁有獨立 data，函數結束時 inner 與 outer 各自 free
```

push はヒープ所有要素型（`%str-long`/`%vec`/`%arr`/ユーザー構造体）に対して深い clone を実行します：新しい data を malloc + memcpy + 要素を再帰的に clone します。ソース変数と外側の vec はそれぞれ独立した data を所有し、**move のマークは不要**で、double-free を回避します。基本型の要素（i64/f64 など）は値を直接 store します。

### 実行時の move 追跡（ヒープ変数の添字で索引付けたビットマップ）

条件分岐下の move には課題があります：ある move が実際に発生したかどうかをコンパイル時に確定できません。

```no
cond-move = (flag i64) (out []i64) {
    x = [1, 2, 3]
    if flag == 1 {
        out = x; move 僅在 flag==1 時發生
    }
    ; flag==0 時 x 仍擁有 data，函數結束需 free
    ; flag==1 時 x 所有權已轉移，函數結束需跳過 free
}
```

Nolang は**ヒープ変数の添字で索引付けたビットマップ**を採用してこの問題を解決します。コンパイル時に各ローカルヒープ変数へ一意の `varIdx` を割り当て、実行時のビットマップの各 bit が 1 つのヒープ変数（出力引数ではなく）に対応します。

#### コンパイラの状態

| フィールド | 型 | 用途 |
|------|------|------|
| `heapVarIndex` | `map[string]int` | ヒープ変数名 → `varIdx`（ローカルヒープ変数のみ） |
| `outBindState` | `[]int` | 各出力引数が現在バインドしているヒープ変数の添字（-1=バインドなし、-2=不確定） |
| `movedVarBitset` | `[]uint64` | コンパイル時の moved ビットマップ（実行時ビットマップがない場合に使用） |
| `movedBitmapBase` | `string` | 実行時ビットマップ変数名の接頭辞（例：`%__mb`、空=未割り当て） |
| `bitmapCount` | `int` | u64 ビットマップブロック数（= maxVarIdx/64 + 1） |

#### 添字のマッピング規則

1 つの `u64` ブロックに 64 個のフラグビットを格納します。ヒープ変数の添字 `varIdx` については：

- ブロック番号 = `varIdx / 64`
- ブロック内オフセット = `varIdx % 64`
- マスク = `1u64 << 偏移`

コンパイル時に定数として直接計算されるため、実行時の計算オーバーヘッドはありません。複数の `u64` ブロックで任意の数のヒープ変数をサポートでき、**引数／戻り値の数に上限はありません**。

#### move 代入の処理（上書き時に古い bit をクリア）

ヒープ変数を出力引数へ move するたびに、以下を行います：

1. その出力引数が以前に別の変数へバインドされていた場合（`outBindState[outIdx] >= 0`）、まず古い変数に対応する bit をクリア
2. 次に現在の変数に対応する bit を 1 に設定
3. その出力引数がバインドする変数の添字を更新（`outBindState[outIdx] = srcVarIdx`）

#### 関数末尾での解放

すべてのヒープ変数を走査し、平坦な独立した `if` を生成します：対応する bit が 0 なら free、bit が 1 なら所有権が移転済みを表し、解放をスキップします。

#### ビットマップのオンデマンド割り当て

ビットマップ変数は**必要な場合にのみ**割り当てられ、分岐のないシナリオでのパフォーマンスオーバーヘッドを回避します：

| シナリオ | ビットマップ割り当て | free の動作 |
|------|---------|----------|
| move なし | 割り当てなし | すべて free |
| move が分岐内にない（決定的な move） | 割り当てなし | コンパイル時の `movedVarBitset` が直接 free をスキップ |
| move が分岐内にある（条件付き move） | 割り当てあり | 実行時のビットマップ検査：bit=1 ならスキップ、bit=0 なら free |

コンパイラは関数本体を生成する前に AST を事前走査し（`detectBranchMoveToOut`）、`IfExpression`/`ForStatement`/`ConditionalExpression` の分岐内で出力引数への move 代入が存在するかを検出します。そのようなパターンが存在する場合にのみ実行時ビットマップ変数を割り当てます。ビットマップの `alloca` は関数本体の生成後に挿入され（この時点で `nextHeapVarIdx` は最終値になっています）、entry block に書き込まれます。

この機構はすべてのヒープ型（`vec`/`str-long`/`arr`/ユーザー構造体）に適用されます。

## 深い clone（ローカル変数間の代入）

```no
a []i64 = [10, 20, 30]
b = a; 深層 clone：malloc 新 data + memcpy + 遞迴 clone 元素
b[0] = 99
; a[0] == 10（a 不受影響）
; b[0] == 99（b 獨立修改）
```

### 深い clone の流れ
1. ターゲット変数の古い値を解放（すでにヒープデータがある場合）
2. 新しい data バッファを `malloc` し、ソース data を新しい data へ `memcpy`
3. 各ヒープ所有要素を再帰的に clone：
   - `%str-long` 要素：malloc + memcpy で文字列 data を複製
   - ユーザー構造体要素：構造体を memcpy + ヒープデータを含むフィールドを再帰的に clone
4. 新しい data ポインタ、len、cap をターゲット変数へ書き込み
5. ターゲットをヒープ変数として追跡（関数終了時に free）

### clone 可能な型
| 型 | 深い clone 可能 | 説明 |
|------|-------------|------|
| `%vec` / `%arr`（要素が基本型） | ✅ | data を memcpy するだけ |
| `%vec` / `%arr`（要素が %str-long） | ✅ | 要素ごとに malloc+memcpy で文字列 data を複製 |
| `%vec` / `%arr`（要素が clone 可能な構造体） | ✅ | 要素ごとに構造体フィールドを再帰的に clone |
| `%vec` / `%arr`（要素が %vec / %arr） | ✅ | `elemElemType` 機構によって内側コンテナの要素を再帰的に clone |
| `%str-long` | ✅ | malloc + memcpy で文字列 data を複製 |
| ユーザー構造体（入れ子コンテナのフィールドなし） | ✅ | 構造体を memcpy + ヒープフィールドを再帰的に clone |
| ユーザー構造体（入れ子コンテナのフィールドあり） | ✅ | 構造体を memcpy + 入れ子コンテナを含むフィールドを再帰的に clone（`elemElemType` 経由） |
| `?str` | ✅ | inline payload の option：option 自身とその文字列 data を clone |
| `?[]T` | ✅ | inline payload の option：option 自身と内側スライスの data を clone（要素ごとに clone、`?[]str` など要素がヒープを所有する場合は再帰） |

> **`?str` / `?[]T` は inline payload ですが、ヒープを所有します。** これらの payload は option 自身の
> `%option_<key>` に直接格納されます（`?str` の構造は `{ i8 tag, [2 x i64] }` で、16 バイトのペイロードに
> `{ u32 len, u32 cap, i8* data }` が入ります）が、その中の `str` data／slice の backing store はヒープ上に確保されます
> ⇒ **clone 時は payload ごと深いコピーし、free 時も payload ごと解放する**必要があり、両側は対になる必要があります。
> `?[]T` の解放は `[]T` と同じ深い free helper を通るため（要素型に応じて再帰するかどうかを決定）、
> 「深い clone には深い free を対応させる」という対偶はここでも成り立ちます。
> ⚠️ 一般の（`?str`/`?[]T` 以外の）option では、payload は借用または純粋な値であり、ヒープを**所有しません**。clone／free ともこれに触れません。
> ペイロードが `option-inline-threshold` を超える大きさになると、option はヒープポインタを格納するようになり、その際は free でボックスごと解放します
> （`Boxed` が決定します。`src/mir/layout.go` を参照）。

### move との違い
- **深い clone**：ソースとターゲットがそれぞれ独立して data を所有し、関数終了時にそれぞれ free
- **move**：ソースが所有権を放棄し（moved とマーク）、ターゲットが data を引き継ぎ、ソースは free をスキップ

`b = a` の判定規則：
1. a が出力引数のソースである場合 → move
2. そうでなく、a がヒープ所有型だが**代入後に参照されない**場合 → move（ゼロコピー、深い clone と観測的に等価）
3. そうでなく、a がヒープ所有型で深い clone が可能な場合 → 深い clone
4. それ以外は値コピー

`vec.push(x)` はこの判定規則の対象外です：push はメソッド呼び出しであり、x がヒープ所有型かどうかに関係なく、ヒープ所有要素に対して深い clone を実行します（前節を参照）。

## スタック型の move（スタックスロット再バインド / slot-rebind）

`i64`/`u64`/`i128`/`u128`/`txt` はスタック型（ヒープ所有ではない）ですが、ソース `a` が後続で参照されない場合、`b = a`（RHS が変数）は値コピーを行わず、**スタックスロット再バインド**（stack-slot rebind）を実行します：`g.varAlias[b] = a` とし、`b` と `a` に同じスタックスロットを共有させます（0 コピー）。これは値コピー（値コピーでは load+store を emit する必要がある）より優れており、大きなスタック型（256 バイトの `%txt` など）では特に効果が顕著です。

### can_slot_rebind 制約（保守的な正しさ）

スタックスロット再バインドは、ヒープ move の `moveEligible` よりも**厳格**です：

- `moveEligible`：ソース `a` が後続で**読み取られなければ** move を許可（ヒープ型に適用。move 後はソースが free をスキップし、ターゲットに影響しない）。
- `can_slot_rebind`（`slotRebindSafe`）：ソース `a` が後続で**まったく参照されない（読み取りも書き込みもない）**場合にのみ再バインドを許可。再バインド後は `b` と `a` が同じスタックスロットを共有するため、`a` が後続で書き込まれると `b` の値が破壊されるためです。

計算：`generateFunctionDefinition` は `computeMoveEligibility` を呼び出し（`moveEligible` と `slotRebindSafe` の両方を埋める）、`generateMainFunction` は `computeSlotRebindSafety` を呼び出します（**`slotRebindSafe` のみ**を埋め、`moveEligible` には触れません——HEAD の main 関数ではヒープ move を有効にしておらず、SEGFAULT を避けるため閉じたままにしています）。いずれも `stmtContainsVarRefAny` を通じて分岐／ループを考慮した参照走査を行います（`AssignExpression` の左辺値、ループのバックエッジを含む）。

`can_slot_rebind` が満たされない場合（ソースが後続でも参照されている場合）→ **完全な値コピーへ格下げ**され、安全でない動作に退化することは絶対にありません。

### 無効化シナリオ（通常の代入パスを通る必要がある）

| シナリオ | 理由 |
|------|------|
| stdlib 関数（`curIsStdLib`） | stdlib には match/closure/coroutine など参照解析で完全にモデル化できない構造が含まれ、再バインドは共有スタックスロットを破壊する（例：fmt 内部で `it` がローカルの `n` へ別名バインドされる）。検出は `g.stdModules`（`transpiler.go` の `SetStdModules` が `checker.KnownStdModules()` から注入）、フォールバックは `g.funcOwner[fd.Name]` |
| ターゲットが出力引数 | 出力引数は呼び出し元からポインタで渡されるため、再バインドするとローカルソースのスタックスロットを指し、呼び出し元が読み取れない |
| ターゲットがグローバル変数 | 再バインドするとグローバル名がローカルソースのスタックスロットへ解決され、グローバルのセマンティクスが破壊される |
| ターゲットがヒープ型変数 | スタックスロット再バインドはスタック型にのみ適用される |
| ソースが引数 | 引数は参照で渡されるため、再バインドは呼び出し元のスタックフレームを破壊する |
| ソースがグローバル変数 | グローバルアドレスがローカルソースへ別名化され、セマンティクスが誤る |

### 再代入後のエイリアス無効化

変数が再代入される際（`b = ...`）、まず `delete(g.varAlias, name)` で残っている可能性のある古いエイリアスを消去し、汎用の代入パスが `varAddr(name)` を経由して古いソースのスタックスロットを指したまま古いソースを汚染するのを防ぎます。新しいエイリアスを設定する際は別名チェーンに沿って**推移的な解決**を行い（`src := ident.Value; for { if n2,ok := g.varAlias[src]; ok { src = n2 } else break }`）、最終的なソースのスタックスロットを見つけて、複数ホップのエイリアスによる位置ずれを回避します。

### ヒープ move との直交性

スタックスロット再バインドはスタック型にのみ作用し、所有権の転移や `free` には関与せず、ヒープ型の clone/move 機構とは完全に独立しています。

**テスト**：`tests/slot-rebind.no`（i64/u64/i128/u128/txt の再バインド、copy への格下げ、ターゲット再代入後のエイリアス無効化、引数 move の格下げ、consume への引数渡しをカバーし、期待出力は `42 7 1 1 17 5 5 10 100 99 84`）。

## FFI extern str の戻り値

FFI extern 関数（`#{c}` でマーク）が返す C 文字列ポインタ（`i8*`）は、静的メモリ（例：`getenv`、`strerror`）や外部バッファ（例：`strchr` が返すポインタは引数の内部を指す）を指す場合があります。これを直接 `%str-long` にラップすると、`emitHeapFree` 時にヒープではないメモリを `free()` することになり → UB となります。

コンパイラは FFI extern の `str` 戻り値パスに安全な複製を挿入します：

1. **NULL チェック**：C が NULL を返した場合、空の `%str-long`（data=0、len=0）を構築します。なお `str` は option ではないため、**`s == nil` はコンパイルエラー**です（`q4nilcmp`）。NULL と空文字列を区別するには、extern を `?str` を返す宣言にする（NULL ⇒ `nil`）か、`s.len == 0` で判定してください
2. **NULL 以外**：`strlen` + `malloc` + `memcpy` + null 終端で、独立したヒープバッファへ複製
3. **PHI マージ**：2 つのパスを合流させ、`%str-long` を構築して返す

```no
#{c}
strchr = (s str, c i64) (r str)

find = () (r str) {
    r = strchr('hello', 108); C 返回指向 'hello' 內部的指標
    ; 編譯器自動 malloc+memcpy 複製，r 獨立擁有 data
    ; 函數結束時 emitHeapFree 安全釋放 r.data
}
```

この機構は clib の `RetCStrToStr` パス（`get-env`、`get-wd` などの組み込み関数で使用）と論理的に同一であり、すべての C 文字列戻り値が独立した所有権を持つことを保証します。

## モジュールレベル変数の解放

モジュールレベルのヒープ変数（`vec`/`str`/`arr`/構造体）は LLVM global（`@name`）にコンパイルされ、その `data` バッファは `main` エントリの top-level 文で malloc により初期化されます。

コンパイラは C エントリ `main` の `ret i32 0` の前に以下を呼び出します：
1. `emitHeapFree` — top-level のローカルヒープ変数を解放（globalVars 以外）
2. `emitGlobalHeapFree` — `moduleVarTypes` を走査し、`globalVars` 内のヒープ所有型をすべて解放

```no
GLOBAL-STR = 'hello'; LLVM @GLOBAL-STR = global %str-long zeroinitializer
GLOBAL-VEC = [1, 2, 3]; LLVM @GLOBAL-VEC = global %vec zeroinitializer
; top-level 語句 malloc data 並存入 global
; main ret 前 emitGlobalHeapFree 釋放 data
```

これにより、長期実行サービス（ループを含むデーモンなど）でのメモリの累積リークを回避できます。使い捨ての CLI ツールには影響しません（プロセス終了時に OS が回収するため）。

## スライスビュー

スライス式 `arr[1..3]` はビュー（ゼロコピー）を生成し、元の配列 data を共有します。ビューの 3 つの行き先：

| ターゲット | 動作 | 所有権 |
|------|------|--------|
| ローカル変数 `v = arr[1..3]` | ゼロコピービュー | 元の配列 data を共有 |
| 出力引数 `out = arr[1..3]` | clone（malloc+memcpy） | 独立所有 |
| 明示的な `[]T` 型 `v []i64 = arr[1..3]` | clone | 独立所有 |

**理由**：出力引数は呼び出し元へ escape するため、元の配列が関数終了前に free される可能性があり、ビューは独立した data へ clone する必要があります。

## 再代入と古い値の解放

```no
s = 'hello'; malloc data 緩衝區
s = 'world'; 釋放 'hello' 的 data，malloc 新 data
```

ヒープ所有型を再代入する際、コンパイラは代入前に古い値の data を自動的に解放し、リークを回避します。

## 構造体フィールドの解放

```no
Node {
    name str
    items []i64
}

n = Node {
    name: 'hello'
    items: [1, 2, 3]
}
; 函數結束時遞迴釋放：
;   - n.name.data（%str-long 欄位）
;   - n.items.data（%vec 欄位）
```

構造体の解放時はすべてのフィールドを走査し、ヒープ所有型のフィールドについてはその data を再帰的に解放します。

## 固定長配列のスライスへの再代入

```no
local [4]i64 = [100, 200, 300, 400]; local 是固定陣列（16 字節）
local = [100, 200, 300]; 重新賦值為切片（16 字節）
```

固定長配列（`%arr`、2 フィールド）とスライス（`%vec`、3 フィールド）はメモリレイアウトが異なります。再代入時にコンパイラは自動的に新しい `%vec` 変数を割り当て、以降のすべてのアクセスをリダイレクトし、バッファの境界越えを回避します。

## 既知の制限

### map コンテナ
hashmap は key/value の深い free を実装しておらず、map コンテナのヒープデータがリークします。

```no
#{fmt-skip}
loop {
    s = 'temp'   ; 每次迭代 malloc 新 data，舊 data 未釋放
}
```

```no
view = arr[1..3]; view 共享 arr.data
```

### async のデータ共有（2026-09-30 修正済み）

`awy { r = co f(x) }` の spawn 境界では現在、ヒープを所有する引数を**深いコピー**し、タスクは呼び出し元とバッファを共有しなくなりました。

コルーチンは協調的かつシングルスレッドであるため、「コルーチン間で可変ヒープデータを共有する」ことは言語レベルでは成り立ちません。唯一共有されうるのは
**呼び出し元が spawn 後も保持している**値です。修正前は argbuf が引数記述子の**ビットコピー**にすぎず、
`data` を呼び出し元と共有しており、タスクは待機点まで実行されなかったため —— 呼び出し元がそれより前に再代入するかスコープを抜けると
バッファが解放され、タスクは解放済みのメモリを読み取っていました（実測：str が 40 個の NUL を出力、`[]i64` が 0 を出力、
いずれも rc は 0 で診断なし）。

現在は spawn 時点で深いコピーを行い、wrapper が呼び出し終了後にコピーを解放します：

| 引数の型 | spawn 境界 | wrapper の解放 |
|---|---|---|
| `str` | `@str_clone` | `@str_free` |
| `[]T`（T に deep-clone helper がある場合） | `vecDeepClone` | `@vec_free` |
| ヒープを所有する struct（インラインの `str` リーフ／ポインタフィールド） | その場でのリーフ clone ＋ pointee の複製 | 再帰的な構造体デストラクタ |
| その他（純粋な値型） | ビットコピー（正しい） | コンテナのみ解放 |

回帰テスト：`tests/async-ownership.no`。

### struct の再代入によるリーク（2026-09-30 修正済み）

```no
holder {
    s str
}
h holder = holder {
    s: 'first'
}
h = holder {
    s: 'second'
}
; 舊的 'first' buffer 曾洩漏
```

ローカル変数を再バインドする際、古い値はその型が `Type.Owned`（`str`/`vec`/`[]T`/`map`/`?owned`）である場合にのみ
解放されます。struct は**意図的に** `Type.Owned` に**含められていません**（このマーカーは lowerer が「バインドがエイリアスかどうか」を判定する
根拠でもあるため）。そのため `h = holder { … }` は構造体全体を直接上書きし、古い `s` バッファは永久に解放されません。
しかし drop 機構自体は struct を認識しており（`dropOwnsHeap` → `typeOwnsHeap`、さらに `emitDrop` が再帰的
デストラクタで解放する）、lowerer のゲートが狭すぎただけでした。修正後は再バインド前に古いフィールドを解放します。

実測では 2,000,000 回の再代入で、ピーク RSS が 66.1 MB → 33.8 MB に改善し、出力はバイト単位で同一でした。

### struct リテラルの最初のフィールド値がメソッド呼び出し（2026-09-30 修正済み）

```no
holder {
    s str
}
h = holder {
    s: n.to-str()
}
; 修復前：'holder' is not defined
```

`{ … }` の分類は、先読みした数個の token によって決定されます。match の**アーム区切りも `:`** であるため、
`s: n.to-str()` は「pattern が `s` の match アーム」と「struct リテラルのフィールド」の両方に見えます。
両者を識別する唯一の手がかりは `ident.ident` **の後**の token です —— メソッド呼び出しはフィールド値にしかなりえません。
古い分岐では `(` を見落としていたため、ブロック全体が match と判定され、struct 名が match の文脈で見つからず未定義エラーとなりました
（フィールド値が通常の関数呼び出しの場合は正常でした）。

修正後は `h = holder { s: recv.method(args) }` が正常に解析されます。nolang の match アームは
`name : X(` で始まることはありません（アーム区切りは `->` であり、`:` で始まるアームは必ず wildcard/default で、本体に括弧付き呼び出しは入らない）ため、
`(` を許可しても正当な match を struct リテラルへ誤判定することはありません。回帰テスト：
`src/parser/struct_literal_field_value_test.go`。

### spawn 引数の移動：ソースが死亡済みならゼロコピー（2026-10-01）

`co f(x)` はヒープを**所有する**引数ごとに spawn 境界で 1 回深いコピーを行います。タスクがグループ末尾まで実行されない可能性があり、
呼び出し側がそれより前に再代入したりスコープを抜けたりできるためです。x が spawn 後にもう使われないことが**確定している**場合、
そのコピーは冗長です：所有権をタスクへ直接**転移**します。

```no
s str = 'hello'
awy {
    v = co echo(s)      ; s 之後不再被讀 -> 零拷貝轉移
}
print(v)                ; hello

s str = 'hello'
awy {
    v = co echo(s)
}
print(s)                ; s 仍被讀 -> 維持深拷貝（兩邊各自擁有）
print(v)                ; hello
```

判定基準は 3 つで、すべて必要です：

1. 呼び出し側が**もともと** x を解放する —— 借用（スライスビュー、borrow read）と引数は呼び出し側で解放されない；
2. x が spawn 後に死亡している（**後続の読み取りがまったくない**）；
3. 呼び出される側のその位置の引数が `str` / `[]T` / ヒープを所有する `struct` である —— wrapper がその payload を解放する。

これら 3 類について、タスク wrapper の解放と呼び出し側本来の drop は**同じ 1 つの helper に統合**されるため、転移とは
**同じ 1 回の解放**を呼び出し側からタスクへ移すだけであり、解放が過剰にも不足にもなりません。

**不変のユーザーセマンティクス**：待機されなかったタスクの引数バッファは、もともと wrapper が待機時に初めて解放するものであり、
移動でもコピーでもこの点はまったく同じです。

実装：`insertDrops` が `Module.spawnArgMoves` に記録し、`emitAsyncRun` がそれに基づいて深いコピーをスキップします。
回帰テスト：`tests/async-arg-move.no`、`src/mir/spawn_arg_move_test.go`。

### コルーチンの待機者テーブルのエイリアス（2026-09-30 修正済み）

スケジューラは当初 `@nolang_waiters = global [256 x i8*]` を用い、`ptrtoint(task) & 255` を索引としていました。
task は `@malloc` で確保され、**16 バイトアライン**であるため、ポインタの下位ビットで有効なのは 4 ビットだけ —— 256 スロットは実際には
16 個に崩壊し（実測では 8 個しか使われなかった）、並行して待機する 2 つのタスクが互いの待機者を上書きし、誤ったタスクを起床させることが極めて起こりやすかったです。

`@nolang_async_done` がそのフィールドを読み、非空ならキューに入れてからクリアします。これにより検索は正確になり、アドレスのエイリアスはなくなりました。

> この項目は現在**潜在的な**欠陥であり、観測可能な故障ではありません。回帰テスト：

### 文の位置にあるベアの `{ ... }` が宣言として扱われる（2026-09-30 修正済み）

`parseStatement` の `LBRACE` 分岐は `classifyBlockAtCurrent()` を呼び出します（この時点で `currentToken` はすでに
`{` であり、消費できる名前はありません）。その戻り値の `blockEnum` / `blockIface` / `blockTaggedEnum` は**文の位置**では
まったく意味がありません —— 本物の列挙型／インターフェース／タグ付き列挙型の宣言には前置する名前が必要で、より前の
`classifyBlock()` 分岐を通るためです。しかし文のディスパッチは `blockUnknown` しか文ブロックへ導かなかったため：

- `{ x = 2 }` は `blockEnum`、`{ print(2) }` は `blockIface` に分類され；
- 両者とも `parseExpressionStatement` へ送られ、`expr.go` の `LBRACE` 分岐は
  `blockStruct` / `blockMatch` しか認めず、それ以外は `p.nextToken(); return nil` を実行し；
- `{` が消費され、ブロック内の文が外側の本体の**兄弟**となり、ブロック自身の `}` が逆に**外側**のブロックを閉じていました。

結果は「飲み込まれる」ではなく**文が 1 層外へ漏れる**ことでした：`f = () { print(1); { print(2) }; print(3) }` は
`3,1,2` を出力し；`f = () { x = 1; { x = 2 }; print(x) }` は何も出力しません。いずれも `rc=0` で診断なしです。

修正は、文のディスパッチで `blockEnum` / `blockIface` / `blockTaggedEnum` も一緒に文ブロックへ導くことです
（`blockStruct` は**式のパスに残す必要があります** —— `{ field: value }` は正当な匿名構造体リテラルの文です）。
⚠️ この問題を「修正」するために `classifyBlockAtCurrent` の `ASSIGN` 分岐を変更してはいけません：それは 3 種類の誤分類のうち
1 種類しかカバーせず、しかも判断を「自分が文の位置にいる」ことを唯一知っている場所から移動させてしまいます。

⚠️ **連鎖影響**：この修正により、文の位置にある `{ ... }` が初めて `*parser.BlockStatement` として実際に生存するようになり、
`programUsesPrint`（`src/build/transpiler.go` にあり、`fmt`/`io`/`str`/`byte` を読み込むかどうかを決める
手書きの AST walker）のホワイトリストに `BlockStatement` がなかったため ⇒ `print` をベアブロック内に書いただけのプログラムが検出されなくなりました。
**文の層に変更を加えたら `go test ./build/ -run TestProgramUsesPrint` を再実行し**、新しいコンテナ型を
`walkStmt` に追加してください。回帰テスト：`src/parser/stmt_boundary_block_test.go`、`tests/stmt-boundary.no`。

### グローバル変数の初回代入における free スキップ判定が不十分に正確

コンパイラはコンパイル時の map `globalFirstAssigned` を用いて、グローバル変数が初回代入済みかどうかを追跡します：初回代入では古い値の解放をスキップし（古い値は `zeroinitializer` でありヒープデータではない）、後続の再代入でのみ古いヒープ値を解放します。

この map はコンパイルプロセス全体で 1 回だけ初期化され、関数単位でのリセットも、条件分岐のパスの区別も行いません。グローバル変数が条件分岐内で初回代入される場合、コンパイラは AST 順に処理します：1 番目の代入文を「初回」としてマークし（free をスキップ）、2 番目の代入文（別分岐であっても）は再代入パスへ進み（古い値の free を試みる）。実行時に 2 番目の分岐が先に実行されると、グローバルはまだ `zeroinitializer`（data=NULL, len=0）であるため、未初期化の古い値を free しようとします。

**現在の緩和策（有効）**：
- 浅いコンテナ（`%str-long`）：`emitNullCheckFree` が実行時の `icmp eq i8* dataPtr, null` チェックを生成し、NULL なら `call @free` をスキップ
- 深いコンテナ（`%vec/%arr`）：`emitDeepContainerFree` に追加の `len == 0` 短絡チェックがあり、zeroinitializer の len は 0 なので解放ループ全体を直接スキップ

この 2 層の実行時防御により、コンパイル時の判定が不十分に正確でも実際にはクラッシュしません。ただし論理的には、コンパイル時の精確な判定ではなく、実行時の NULL チェックを安全網として依存しています。

**潜在的な改善方向**：`globalFirstAssigned` をコンパイル時の map から実行時の追跡機構（`movedVarBitset` のようなビットマップ）へ変更する方法がありますが、実行時オーバーヘッドが増加し、現在の緩和策で十分に効果があるため見送っています。

## 設計上の取捨

1. **深い clone のコスト。** `b = a` は data を 1 つ確保して複製し、`vec.push(x)` もヒープ所有要素に対して深い clone を 1 回行います。
   これは意図的です：**1 回のコピーでエイリアス解析のカテゴリ全体を置き換える**ためです —— 値と値の間には「所有」と「移動」だけを残し、共有は残しません。
   その結果、「誰が所有し、誰が解放し、書き込みが観測可能か」について、エイリアスのケースごとに別々の規則を書く必要がなくなります。
2. **spawn 境界での深いコピー（＝スナップショット）。** `co f(x)` はヒープを所有する引数を spawn 時点で 1 回深いコピーするため、タスクが見るのは
   **spawn 時点の値**であり、呼び出し元がその後に書き込んだ内容には関係ありません。**ソースが死亡済みの場合はゼロコピーの move に切り替わります**。
   ⚠️ このコピーを節約するために「同じバッファを共有 ＋ 参照カウント」へ変更しないでください：それはタスクに、spawn からグループ末尾の待機までの間に呼び出し元が行った
   **その場での書き込み**（共有）を見せてしまい、第 4 条に違反します。コピーを節約する正しい方法は「**書き込み時にコピーする**」（copy-on-write）です。
3. **タスクの参照カウントは環を作らない。** 内部の `%task` が唯一の参照カウント対象であり、新しい `awy { ... }` はハンドルを露出せず、
   各 `co` はグループ末尾でちょうど 1 回だけ待機するため、「タスクが互いにハンドルを保持し合う」環は形成されません。
4. **コルーチン間で可変ヒープデータを共有しない。** コルーチンは**協調的・シングルスレッド**でスケジューリングされるため、コルーチンをまたいで可変ヒープデータを共有することは言語レベルで成り立ちません。
   共有を許可してもデータ競合とダングリングポインタをもたらすだけです。したがって spawn 境界では常に**独立したコピー**を渡す（または所有権を転移する）ことにします。
