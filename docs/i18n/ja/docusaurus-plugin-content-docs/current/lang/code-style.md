# コーディング規約

## ファイル末尾の改行（Trailing Newline / EOF）

すべての**空でない** `.no` ソースファイルは、**ちょうど一つの末尾改行文字で終わらなければなりません**（つまり、ファイルの最後に空行が一つある状態）。

- ファイルに末尾改行が**ない** → 一つ追加する。
- ファイル末尾に**複数の**空行がある → 単一の末尾改行に統合する。
- **空ファイル**（0 バイト）→ そのままにする。

除外ディレクトリ：`dist/`、`vscode-nolang/`、`node_modules/`。

理由：EOF の単一改行を統一すると、`git diff` に "no newline at end of file" が表示されるのを防ぎ、差分がきれいになり、ツールの連携や連結の挙動が予測可能になります。

### 自動実行（ツールチェーンに内蔵）

この規約はツールチェーンによって**自動実行**され、独立したスクリプトはありません。

- **`no fmt`**：`src/cmd/no/main.go` の `fmt` サブコマンドがファイルをその場で整形し、`fmt.FormatFile` を呼び出して、ちょうど一つの末尾改行を保証します。
- **LSP の保存時整形 / `textDocument/formatting`**：`src/lsp/server.go` の `formatNolangCode` → `fmt.FormatFile` が、エディタでの保存時や `.no` ファイルの手動整形時に、EOF の改行を自動的に追加・統合します。

実装は `src/fmt/formatter.go` にあります。

- `FormatFile(code)` はファイル全体を整形し、`ensureTrailingNewline` を呼び出します。末尾のすべての `\r` / `\n` を除去し（CRLF や複数の末尾空行に対応）、その後に `\n` を一つ追加します。空ファイルや解析できない内容はそのまま返され、ファイルを壊さないようにします。
- `Format(code)` は純粋な断片用の整形関数（末尾改行を追加しない）で、主に単体テスト向けです。実際のソースファイルへ書き込む際は `FormatFile` を使ってください。

## インポート文の自動整理（重複排除 / 別名なし std インポートの削除 / ソート）

`no fmt`（および LSP の保存時整形）は**ファイル先頭の連続したインポート区間**（`# path[.fn] [alias]`）を自動整理します。実装は `src/fmt/imports.go` にあります。

1. **重複排除**：完全に同じ（パス、関数名、別名が文字単位で同一）インポートは最初の一条だけを残します。
2. **別名なし std モジュールインポートの自動削除**：標準ライブラリモジュールは暗黙的に読み込み可能なので（[モジュール間呼び出しのプレフィックス](./module) を参照）、`# std/noml` / `# std/math` / `# std/database/sql` のような「別名なし・`.関数` なし」の純モジュールインポートは名前を束縛せず冗長であり、formatter に削除されます。ただし三つの例外は保持されます。
   - **別名**（`# std/noml n`）や**関数インポート**（`# std/fmt.sprintf fm`）が書かれている場合。これは意図的な名前の束縛です。
   - インポート行に**コメント**や `#{...}` の付着アノテーションがある場合。ユーザーが書いた内容を黙って捨ててはいけません。
3. **自動ソート**：パス → 関数名 → 別名 の辞書順で安定ソートします。

保守的な境界：区間内のいずれかのインポートにコメント（独立した行でも同じ行の行末でも可）や `#{...}` の付着アノテーション（例 `#{bind=ffi}` のネイティブ束縛戦略）があれば、区間全体で**元の順序を保持し、削除も行いません**。ソートはコメントと文の対応関係を壊し、削除はコメントごと消してしまうからです。この場合でも「付着内容がまったくない完全重複項目」は削除されます。

ファイル先頭以外（コードの後）に現れるインポート区間はすべてそのまま保持されます。

```no
#{fmt-skip}
; 整形前                            ; 整形後
# std/vec                           # aaa/lib
# std/noml                          # std/io
# std/io                            # std/vec
# std/noml n
# aaa/lib        ;→  別名なし std インポート（# std/noml、# std/vec、# std/io）を削除；
                    ;   別名付きの # std/noml n は保持；残りは辞書順にソート
```

## コメントマーカー（Comment Markers）

Nolang は二種類の**単行コメント**マーカーと一種類の**複数行（ブロック）コメント**マーカーをサポートします。セマンティクスは次のとおりです。

- `//` —— 従来の単行マーカー（行末までがコメント）
- `;` —— 別の単行マーカー（2026-07-17 に実装、行末までがコメント）
- `;; ... ;;` —— 複数行（ブロック）コメント（2026-07-18 に実装、対称なデリミタ、閉じられなければファイル末尾までがコメント）

```no
#{fmt-skip}
// 這是註釋
; 這也是註釋，語義相同
x = 1 ; 行內註釋，註釋到行尾

;;
   這是多行（塊）註釋
   可以跨多行
   以 ;; 結尾 ;;
y = 2 ;; 行內塊註釋 ;;
```

**ブロックコメントのデリミタ**：`;;` で開始し `;;` で終了し、その間（改行を含む）はすべてコメント内容です。内容内の単一の `;` はブロックを終わらせず、`;;` だけが終わらせます。終了の `;;` が見つからない場合は、`;;` の開始からファイル末尾までコメントし続けます。開始デリミタ `;;` の後は**改行まで空白だけ**の場合にのみ複数行モードに入ります。同じ行の `;;` の後に文字が続く場合は、普通の単行コメントです（例：`;; 説明文字` はその行だけをコメントし、次の行は相変わらずコードです）。終了デリミタも同様で、`;;` の後は空白だけの場合にのみ閉じたと見なされます。

**整形では元のマーカーを保持**：`no fmt` はコメントのマーカーを一切変更しません。`;` は `;` のまま、`//` は `//` のまま、`;; ... ;;` は `;; ... ;;` のままです。formatter は `Comment.Marker` を通じて元のマーカーを記憶しそのまま出力し、ブロックコメントの内容（内部の改行を含む）も文字単位で保持するため、整形は冪等です。

**安全な範囲**：`;` / `;;` が文字列リテラル（例 `'text/plain; charset=utf-8'`、`index-from(';', pos)`）や `//` コメントの内部に現れる場合、lexer の文字列スキャナとコメントスキャナが先に消費するため、コメントマーカーとしては扱われません。

**`cond -> X; Y` に注意**：`;` は現在コメントなので、`cond -> X; Y` は「`cond -> X` を実行（X を評価して破棄）」と行内コメント `; Y` に解析されます。`X` には**代入されません**。正しい書き方は `cond -> X = Y` です（stdlib の既存の慣例。`arr.no`、`uuid.no`、`path.no`、`err.no`、`assert.no` を参照）。ソースコードに `cond -> X; Y` を見つけたら、優先的に `cond -> X = Y` に変更してください。

**一行に複数の文を書くのは禁止**：`;` は単なるコメントマーカーであり、同じ行で複数の文を繋ぐのに使えません。カンマ `,` も文を繋げません。ブロック `{ ... }` 内の各文はそれぞれ独立した一行を占めなければなりません。ブロックを一行に圧縮するのは最も危険な誤りです。

```no
#{fmt-skip}
; ❌ 錯誤：`; return }` 整段變成註釋，塊的 `}` 隨之消失
cond -> { print('X'); return }
```

```no
; ✅ 正確：每條語句獨佔一行
cond -> {
    print('X')
    return
}
```

`cond -> { print('X'); return }` は実際には `cond -> { print('X')` だけが残ります。ブロックが閉じることがなく、`}` 以降の文（多くの場合、その関数の残りの関数本体全体、さらには後続のモジュール級関数まで）がまとめて飲み込まれます。コンパイラが必ずしもエラーを出すとは限らず、エラー位置も大きくずれる可能性があり、極めて特定が困難です。

## 真偽値リテラルと `== true` / `== false` の簡略化（2026-09-24 実装）

`true` / `false` キーワードのほか、Nolang は二種類の**真偽値リテラルの略記**を受け付けます。

- `!!` —— `true` と等価な独立したリテラル。
- `!` —— `false` と等価な独立したリテラル（`!` の後が演算子の起点になりうる記号でない場合のみ。後ろが `換行` / `;` / ファイル末尾 / `)` / `}` / `]` / `->` なら `false` として解析されます）。

> 注意：ここで述べているのは**式の位置**の `!!` / `!` で、ループの位置の `!! { }`（常に実行）や `! { }`（実行しない）とは異なります。

これら二つの略記は**解析時に**普通の `BooleanLiteral` へ変換されるため、`f == true`、`f == !!`、`f == false`、`f == !` の四つは構文的に完全に等価で、同じ処理ロジックを通ります。

`no fmt` の真偽値に対する処理ルール（実装は `src/fmt/expr.go`）：

- **独立したリテラルはキーワード表記に統一**：`c = !!` → `c = true`、`c = !` → `c = false`。
- **既知のものだけ簡略化し、未知のものは簡略化しない**：`==` / `!=` のいずれか一方が真偽値リテラルで、もう一方のオペランドが**bool 値であると確証できる**場合に、最も簡潔な形を出力します。四つの経路は同じ署名**収集基準**（`collectModuleSignatures`：std の埋め込み表、`use` / `#` が指すローカルモジュール、EnumVariants）と同じ `SemRebuildConfig.Apply` 注入契約を共有しています。違いは表を供給する側だけで、`no fmt` / LSP は `build.FmtSigLoader` が表を供給し、`no build` / `no vet` は相変わらず `preloadModuleSignatures` + `astParseConfig` を通ります（両者はまだ単一の loader に統合されていません）。`no fmt` は fresh な `SkipLowering` parse の前に注入し、LSP は `ParseDocument` が注入した後に `parseSnapshot` を発行し、format-on-save は同じ糖 AST の深いコピー（`fmt.CloneProgramForFormat`）を再利用して、デフォルト設定では追加の parse を行いません。確証できる出所は三種類あります。

  1. 明示的な型注釈：`b bool = true`、引数 `(b bool)`。
  2. 真偽値リテラルの代入：`flag = true` / `flag = false`。
  3. `bool` を返すと宣言された関数の呼び出し：**当該ファイル内で定義**（例 `bytes-eq = ... (eq bool)`）、または署名表で検索できる std / ローカルモジュールの関数（例 `args.has-flag`、ローカルモジュールの `helper.is-ok`）。変数レシーバのメソッド呼び出し（`s.starts-with('a')`）は、Sem が推論済みのレシーバ型（`s: str`）で `str.starts-with` を調べます。型が推論できていない場合や、同名の変数が異なるスコープで異なる型に推論された場合は未知と見なします（意図的に「メソッド名がグローバルに一意」という推測はしません。`?bool` を純粋な bool と誤認しないためです）。署名表で結果型が見つからない場合も未知と見なします。

  | 元の書き方（下表の `b` は上記の「既知」の変数） | 整形後 |
  | ------------------------------------------ | -------- |
  | `b == true` / `b == !!`                    | `b`      |
  | `b == false` / `b == !`                    | `! b`    |
  | `b != true` / `b != !!`                    | `! b`    |
  | `b != false` / `b != !`                    | `b`      |
  | `true == b`（リテラルが左側）              | `b`      |

  `!=` は極性を反転させるだけです。`true == false`（両側がリテラル）はそのまま変更しません。
  `f == true` のような**bool の根拠がない**裸の名前はそのまま保持します。
- **`?T` とすべての未知オペランドは元の比較を保持**：option（`?T`）、署名表で結果型が見つからない跨モジュール呼び出し、代入のない裸の名前、型が推論できていないドットアクセス、呼び出し式、演算結果は、一律 `== true` / `== false` を保持します。これを裸の `x` / `! x` に折りたたんで制御フローの条件にすると、MIR が「option-as-i1」の codegen crash にぶつかります。v0.3.3 はまさにそのためルール全体を revert し（`8a8ecb59`）、2026-11-15 に「正向で確証できた場合のみ簡略化」へ変更して復活させました。「`?T` が見つからなければ値とみなす」という逆向きの推論はもう使いません。同日から `no fmt` / LSP も跨モジュール署名を注入するようになり、`fs.write-str(...)`（`?bool`）のような option 戻り値が**見える**ようになり、option のハードゲートがブロックします。「型が見えないこと」に頼るのではありません。option は**独立したハードゲート**（`boolOperandIsOptionTyped`）であり、bool 値の証拠判定より先行するため、型注釈がソースファイルに残っているかどうかに関わらず簡略化しません。`ok ?bool = fs.write-str(...)` と `ok = fs.write-str(...)` のどちらの書き方でも比較を保持します。`no fmt` が既存規約（`fixRedundantTypeSource`）に従って冗長な型注釈を削除するのは**正しい動作**であり、option 判定を保つためにこの削除を止めないでください。回帰テスト：`src/fmt/bool_comparison_test.go`、`src/fmt/signatures_test.go`、`src/lsp/fmt_gate_test.go`。
- **`->` 分岐 / 独立した if-then 条件でも同様に有効**（既知の変数に対して）：
  `b == ! -> return` → `! b -> return`。
- **演算子の優先順位の安全性**：否定は `! `（空白一つ付き）と書き、前置演算子の既存の慣例に合わせて `no fmt` の冪等性を保証します。現在確証できるオペランドはすべて識別子で、`!` が再結合することはありません。ただし実装は将来的に判定を緩和する可能性に備え、非原子のオペランドには括弧による保護を残しています（`! a + b` ではなく `! (a + b)`）。

## 戻り値変数の遅延ゼロ初期化（Deferred Zero-Init for Return Values）

Nolang の関数における名前付き結果引数（out 引数）は**遅延ゼロ初期化**戦略を採用しています。関数の prologue は out 引数に対して一切ゼロ初期化を行いません。代わりにコンパイラはビットマップ `%__ret_init_bitmap` を使い、各 out 引数が関数本体内で明示的に代入されたかどうかを追跡します。関数が返るとき、**明示的に代入されていない** out 引数には対応する型のゼロ値 store が自動的に補われます（整数 → `0`、str-long → `zeroinitializer`、struct → `zeroinitializer`、option → `nil`）。この仕組みは既存の `%__move_bitmap` による遅延解放機構と対称です。

### この設計の理由

- **性能**：prologue がすべての out 引数に対して `store zeroinitializer` を一度ずつ行い、その後関数本体の代入で上書きされるという、純粋に冗長な store を避けます。遅延戦略では「本当に代入されていない」場合にだけ一度ゼロを補います。
- **可読性**：関数の先頭に `found = false` / `result = nil` のような定型の早期ゼロ代入コードを書く必要がなく、読み手は「成功パスでのみ代入する」という意図を直接見て取れます。
- **一貫性**：`%__move_bitmap` の遅延解放機構と同じビットマップ追跡パターンを採用しており、コンパイラ内部の実装は対称です。

### 推奨される書き方

関数の先頭で out 引数に早期のゼロ代入を行わないでください。コンパイラが返るときに自動的にゼロを補います。「成功パス」の代入だけを書けば十分です。

```no
; Good：不寫提前賦零值，編譯器自動處理
hashmap-str-tmpl.contains = (key str) (found bool) {
    val ?v = .get(key)
    val: {
        ok -> found = true

        err -> {
        }

        nil -> {
        }
    }
}
```

### アンチパターン（避けるべきもの）

冗長な早期ゼロ代入を書かないでください。これは後続の代入で上書きされるだけの無効な store です。

```no
#{fmt-skip}
; Bad：冗餘的提前賦零值
hashmap-str-tmpl.contains = (key str) (found bool) {
    found = false              ; 冗餘——編譯器會在返回時自動補零
    val ?v = .get(key)
    val: {
        ok -> found = true
        err -> {}
        nil -> {}
    }
}
```

### Option のデフォルトは nil

`?T` の option 型の out 引数について、コンパイラはゼロを補う際に直接 `nil`（tag=1, data=0）を書き込みます。これは `result = nil` と等価です。したがって「見つからない / 空集合 / EOF」のようなパスは裸の `return` だけで十分で、ソースコードに `result = nil` を書く必要はありません。

```no
#{fmt-skip}
; Good：未命中路徑用裸 return，編譯器自動補 result = nil
hashmap-str-tmpl.get = (key str) (result ?v) {
    .size == 0 -> return        ; 編譯器補 result = nil
    ...
    ; fall-through：編譯器補 result = nil
}
```

### デバッグのヒント

関数が予期しないゼロ値を返した場合（たとえば `found` が `true` であるべきなのに `false` になった、あるいは `result` が値を持つべきなのに `nil` になった）、関数本体の**非ゼロ値を返すべきすべてのパス**で out 引数に対して明示的な代入が行われているかを確認してください。コンパイラは意図を推測しません。代入されていない out 引数にゼロを補うだけです。詳細は `.agents/skills/nolang-debug/SKILL.md` のデバッグヒントを参照してください。

## 出力スロットを既存の変数へ直接束縛する（中継変数を避ける）

**推奨される書き方**：新しいコードを書く際、呼び出し結果が単に既存の変数を更新するためだけなら、出力スロットを**その変数へ直接束縛**し、一度きりの中継変数を追加しないでください。これは複数の出力があり、かつレシーバ自体が更新対象の状態である場合に特によく見られます。

```no
; ✅ 推薦：餘數直接寫回 r（r 同時是方法接收者）
qsq, r = r.div-mod(modulus)
```

```no
; ❌ 避免：msq 只被寫回一次，沒有其它用途
qsq, msq = r.div-mod(modulus)
r = msq
```

- 使わない出力は `_` でプレースホルダーにします：`_, r = r.div-mod(modulus)` なら新しい変数を一つも導入しません。
- 読み取り専用の入力参照と出力スロットが同じオブジェクトを指すのは〈エイリアス規則〉で合法です。`src/std/bigint.no` の `r = r._mul(r)` も同じ種類のインプレース更新で、単一出力にも適用されます。
- これは**新しいコード**に対する推奨であり、リファクタリング命令ではありません。既存の合法なコードをスタイルのために書き換える必要はありません（〈黄金律〉を参照）。
- 完全なセマンティクス、実測結果、適用範囲は[言語リファレンス：関数定義](./syntax)を参照してください。

## Markdown のコードブロック（`no fmt -md`）

`no fmt -md` は ```` ```no ```` / ```` ```nolang ```` のフェンス**内部**の内容だけを整形し、フェンスの行とその他の Markdown は文字単位で保持します。ブロックの内容は Nolang のソースコードとして解析されます。解析できない場合はブロック全体をそのまま残して行番号を報告し、壊すことはありません（`-md` と `-fix` は排他関係で、整形のみを扱います）。

### 正しい例と誤った例はそれぞれ独立したブロックにする

同じブロックに「正しい書き方」と「誤った書き方」の両方を書くと、両者が一つのプログラムとして扱われます。正しい方は `no fmt` の検証を失い、誤った方は整形によって「ついでに修正」され、問題が見えなくなる可能性があります。そのため：

- **正しい例**は単独のブロックとし、アノテーションを付けず、`no fmt` による整形と検証に任せます。
- **誤った例**は単独のブロックとし、先頭行に `#{fmt-skip}` を書きます。検証も変更もされません。

```no
; ✅ 正確：每條語句獨佔一行
cond -> {
    print('X')
    return
}
```

```no
#{fmt-skip}
; ❌ 錯誤：`;` 之後整行都是註釋，塊的 `}` 隨之消失
cond -> { print('X'); return }
```

### `#{fmt-skip}` の三種類の用途

1. **誤った例 / 反例**：そもそも合法なプログラムではないため、整形するとかえって邪魔になります。
2. **疑似コードと署名の早見表**：形だけがあり実装のない断片（例 `f = (a i64) (r i64) { ... }` の署名スケルトン）。
3. **コメント列を揃えた早見表**：`no fmt` は `code      ; 説明` を `code; 説明` に圧縮しますが、列の整列こそがこの種の表の可読性の源なので、フィルタリングが必要です。

### 「展開を防ぐため」にアノテーションを付けない

`no fmt` は空のブロック `{ }` や単行のアーム `-> { x() }` を複数行へ展開します。

```no
ok = (b bool) (yes bool) {
}

dispatch = (cmd str) {
    cmd == 'a' -> {
        fa()
    }
}
```

これは**受け入れるべき**規約形です。展開されて初めてブロック内に独立した行ができ、後続の文を挿入できます。そうでなければ一行追加するたびに手動でブロックを分解する必要があります。同様に、`true -> {}` が `true -> {\n}` になっても元に戻す必要はありません。本当に `#{fmt-skip}` が必要なのは上記の三種類（反例、疑似コード、整列表）だけです。

### コメントだけのブロックにはアノテーションは不要

ブロック全体がコメントだけ（正しい書き方を「コメントアウト」したもの）の場合、解析結果は**零個の文**となり、`no fmt` は「整形するものがない」と見なしてそのまま残し、報告もしません。そもそも構文エラーではないため、`#{fmt-skip}` を付けるのは事実を隠すだけです。

### 順序：まずアノテーションを付け、その後整形する

`no fmt -md -w` はフィルタリングされていないすべてのブロックをその場で書き換えます。誤った例が整形ツールによって「修正」されると反例として成立しなくなり、元の書き方を復元できなくなります。**先に `#{fmt-skip}` を補い、その後で `-w` を実行してください。**
