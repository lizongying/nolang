# エクスポート

Nolang は `@` キーワードを使い、パッケージのルートディレクトリにある `lib.no` ファイルでエクスポート項目を宣言します。外部パッケージが `#` でインポートする際にアクセスできるのは、エクスポートされたこれらのシンボルだけです。

> **注意**：`@` は Nolang パッケージ間のシンボルエクスポートのみを担当し、C ABI シンボルは生成しません。C / C++ / Rust / Go / Java / Python / C# から Nolang を呼び出したい場合は、代わりに `#{cabi='symbol'}` アノテーションを `no build --shared` と組み合わせてください。[ホスト言語から Nolang を呼び出す](./host-interop) を参照してください。

## 構文

```no
@ path.func
[alias]
```

- `path` — モジュールパス（パッケージルートディレクトリからの相対、`/` で始まり、`.no` 拡張子は付けない）
- `func` — エクスポートする関数/定数/列挙型の名前
- `alias` — 任意の別名。外部からのインポート時に使う名前

## ルール

- エクスポート文は**パッケージルートディレクトリの `lib.no` ファイルにしか書けません**（唯一の例外は下節「グローバル callable 別名」を参照）。
- 一行に一つのエクスポート項目。
- エクスポートできるのは関数、定数、列挙型などの最終的なシンボルだけです。
- **シンボル名を指定しなければなりません**：`@ std/txt`（パスだけで、`func` も `alias` もない）はエラーです（`lgxbfk9a`）。この書き方は何も宣言しません。すべての利用側が「シンボル名がある」ことを前提としているため、黙って無視することはもうありません。また、「型をあるモジュールに束縛する」目的にも使えません。型にはグローバル名という層がなく、`@` の別名は callable なシンボルに対してのみ意味を持ちます。
- エクスポートされた関数が参照する構造体や列挙型などの型は**自動的にエクスポート**され、手動で宣言する必要はありません。
- エクスポートされた関数がモジュール内に存在しない場合、LSP がエラーを表示します。

## 例

```no
; lib.no - 包根目錄導出文件
@ /src/utils.greet a
@ /src/utils.hello b
@ /src/math.pi
```

```no
; src/utils.no
; 定義被導出的函數
greet = (name str) {
    print('Hello, ' - name)
}

hello = () {
    print('Hi')
}
```

## グローバル callable 別名

同じ構文を **`std/global.no`**（あるパッケージの `lib.no` ではなく）に書くと、意味が異なります。エクスポート項目をふるいにかけるのではなく、**グローバルに呼び出し可能な第二の名前**を宣言します。裸の名前 `<alias>` がそのまま `path` モジュールの `func` となり、`<path>.<func>(...)` を完全に書いた場合と同じ効果です。

```no
; std/global.no —— 兩種寫法，語義相同
@ std/err.new err; 導出式
err = err.new; 賦值式
```

```no
e = err('disk full', code.io); 等同 e = err.new('disk full', code.io)
m = e.msg(); 'disk full'
```

ルール：

- この意味を持つのは `std/global.no` だけです。`lib.no` 内の `@` は相変わらずエクスポートのフィルタリングです。
- 二つの書き方は**等価**で、コンパイラはこれらを同じ宣言へ正規化します。両方を同時に書いても衝突しません。
- 代入形式は**`global.no` 内でのみ有効**です。通常のプログラムにおける `x = mod.fn` は関数値を保持する変数（間接呼び出しに使える）であり、グローバル別名とは見なされません。
- 代入形式の右辺は裸の `<モジュール>.<関数>` 参照でなければなりません。呼び出しでもリテラルでもフィールド読み取りでも型付きの束縛でもいけません。対象が関数でない場合、宣言は自動的に無効になります（`PI = math.PI` のような定数宣言は影響を受けません）。
- 別名が有効なのは**裸の名前による呼び出し**の位置だけです。限定呼び出しは影響を受けません。`io.err(...)` は相変わらず `io` モジュールの stderr ライタであり、`err` 別名に乗っ取られることはありません。
- モジュール内で自分と同名の関数を呼び出す場合も影響を受けません（自モジュールは免除）。
- 別名の**引数表**は対象関数から取り、**戻り値の型**は呼び出し地点で対象関数によって決まります。
- 別名は組み込み option の `err` バリアントと衝突しません。期待される型が `?T` である位置（`x ?i64` の後の `x = err('m')`、`err ->` のマッチアーム、`?T` を返す関数）では、`err(...)` は相変わらず option の err バリアントのコンストラクタ（tag 2）です。

## エクスポート済みシンボルのインポート

外部パッケージが `#` でインポートする際にアクセスできるのは、`lib.no` で宣言されたエクスポート項目だけです。

```no
; 导入別名 a（對應 package-name.utils.greet）
# package-name.utils.greet a
; 或者直接使用函數名
# package-name.utils.greet
```

## LSP サポート

- **定義へジャンプ**：`lib.no` 内でエクスポートされた関数名や別名をクリックすると、対応するモジュールファイルの定義位置へジャンプします。
- **自動補完**：`@` とパスを入力すると、選択可能なファイルパスと関数名を自動で提案します。
- **エラー表示**：エクスポートされた関数がモジュール内に存在しない場合、エラー診断を表示します。
