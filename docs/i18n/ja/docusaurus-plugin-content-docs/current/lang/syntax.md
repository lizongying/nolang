# 構文


## コメント

Nolang は**単行コメント**と**複数行（ブロック）コメント**の記法をサポートします：

- `;` —— 単行記法（行末までがコメント）
- `;; <內容>` —— 単行記法（`;;` の**同じ行**に内容が続く場合、行末までがコメント。意味は `;` と同じ）
- `;;\n` —— 複数行（ブロック）コメント：`;;` の**直後に改行**（空白のみ許可）が続くと複数行モードが起動し、同じく改行/EOF が続く `;;` に達するまで続きます

```no
; 這是註釋
; 這也是註釋，語義相同
;; 這還是單行註釋（;; 後沒有換行）
x = 1; 行內註釋，註釋到行尾
x = 2;; 行內單行註釋，語義相同

;;
這是多行（塊）註釋
可以跨多行
直到遇到單獨的 ';;'
;;

y = 3
;;
結束 ;; 後必須換行或文件尾
才會被視為結束定界符
;;
```

> **複数行開始ルール：** `;;` の後は改行または EOF まで**空白（スペース／タブ）のみ**でなければ、複数行モードに入りません。`;;` の後に同じ行で空白以外の文字が1つでもあれば、単行コメント（行末までコメント）として扱われます。
>
> **複数行終了ルール：** 終了の `;;` も同様に、改行または EOF が続かなければなりません（途中は空白のみ許可）。閉じられていない複数行コメントはファイル末尾までコメントし続けます。

> **ルール：1行に1つの文。同じ行に複数の文を書くことは禁止です。**
> セミコロン `;` は**コメント記号**であり、文の区切りではありません。カンマ `,` でも複数の文をつなぐことはできません。同じブロック `{ ... }` 内の各文は、それぞれ独立した1行を占有しなければなりません。
> このルールはコメント内のコード例にも適用されます。コメント内であっても、読者を誤解させないよう `;` や `,` で複数の文を同じ行に書かないでください。

```no
#{fmt-skip}
; ❌ 錯誤：用 `;` 分隔多條語句 —— `;` 之後整行都是註釋，
; 連塊的 `}` 也被一起註釋掉，塊無法閉合，後續程式碼被靜默丟棄
; cond -> { print('X'); return }

; ❌ 錯誤：用逗號連接多條語句
; h0 = 1732584193, h1 = 4023233417
; out = from-i64(v), out = from-u64(v)
; debug(msg), info(msg), warn(msg)
```

```no
; ✅ 正確：每條語句獨佔一行
cond -> {
    print('X')
    return
}

; ✅ 正確：每條語句獨佔一行
; h0 = 1732584193
; h1 = 4023233417
; out = from-i64(v)
; out = from-u64(v)
; debug(msg)
; info(msg)
; warn(msg)
```

> **なぜ `;` が特に危険か：** `cond -> { print('X'); return }` では `; return }` 全体がコメントとみなされ、実際のコードは `cond -> { print('X')` だけになります。ブロックが永久に閉じられないため、`}` 以降のすべての文（多くの場合、その関数の残りの本体全体）が飲み込まれ、エラー位置も大きくずれて極めて見つけにくくなります。

## データ型

基本型

- byte
- bool ; 小文字のみ許可
- char ; 文字型：単一の Unicode スカラー値（rune）。内部表現は i32。ダブルクォートで1文字を囲みます（例: "中"）
- str ; 文字列型。シングルクォートで 'hello'、またはバッククォートによる生文字列 `多行內容`
- txt ; 固定長テキスト型。内部は固定 256 バイト（データは最大 255 バイト）。明示的な型注釈が必要（例: t txt = 'abc'）
- i8
- i16
- i32
- i64 ; 数値のデフォルト型。アーキテクチャに依存しない
- i128 ; 128ビット符号付き整数
- u8
- u16
- u32
- u64
- u128 ; 128ビット符号なし整数
- f32
- f64

### char 型（Unicode コードポイント）

`char` は**単一の Unicode スカラー値**（scalar value）を表します。内部の記憶型は **`i32`** であり、`i64` ではありません：

- **有効範囲**：`0 ..= 0x10FFFF`（つまり `0 ..= 1114111`）。コードポイントの最大値は 21 bit で足りるため、`i32` に十分収まります。
- **範囲外エラー**：リテラルがこの範囲を超えると、コンパイル時（`no vet` を含む）に**直接エラー**になります。例：`c char = 0x110000` ✗、`c char = 1114112` ✗；`c char = 1114111` ✓。
- **数値演算が可能**：`char` は**整数演算に直接参加できます**。たとえば `z = a + 25` や `u = ch - 32`（`ch` は `for ch <- s` のイテレーション変数）は**通常の書き方**で、コードポイント値に対して加減算します。演算は常に **i32 の幅**で行われ、結果は普通の整数値として扱われます。そのため `char` の `+ - * /` は**整数ファミリのようにデフォルトで `option<int>` を返すことはなく**、「未処理の整数オーバーフロー」というコンパイルエラーも発生しません。注意すべきは範囲だけです：コードポイントの最大は `0x10FFFF` で、`i32`／コードポイントの意味を超える場面（オフセットや累計カウントなど）では、意図を明確にするため事前に `i32`／`i64` へ明示的に変換してから計算することをおすすめします。
- **`str` との関係**：`s[i]` は `char` を返します。`char` は `str` へ暗黙的に変換できます（UTF-8 エンコード）。詳細は [文字列 — 暗黙変換](str.md) を参照してください。

> **「内部型」と「呼び出し時変換」は別の話です。** `char` 自身は `i32` です。組み込み関数 `str_from_cp(cp char) -> ?str` の**ソース上のシグネチャ**では引数が `char` ですが、**外部ランタイムを呼び出すときだけ**、コンパイラがこの i32 引数を**ゼロ拡張**（`zext i32 → i64`）して `@str_from_cp` の IR 引数に合わせます。これは引数準備段階の一時的な変換にすぎず、`char` の型は**変わりません**。C の `char c='a'; f((long)c);` と同じで、`c` 自体は1バイトで、呼び出し時に一時的に昇格されます。

コンテナ型

- obj ; オブジェクト
- map ; マップ
- arr ; 固定長配列
- vec ; 可変長配列
- slice ; スライス（ビュー）は独立したデータ構造を持たず、arr/vec/str/txt に依存する必要があります

- \* ; ポインタ。FFI の `#{c}` 宣言と標準ライブラリのみ
- usize ; FFI のみで使用
- any ; 任意の型。標準ライブラリのみ

高度な型

- bigint
- err

## 型エイリアスとユニオン型

型エイリアスは既存の型に新しい名前を付けます。等号構文 `name = type` を用い、単一の型エイリアスと複数型のユニオンをサポートします。

### 構文

```no
; 聯合類型：多個類型用 | 分隔
int = i8 | i16 | i32 | i64 | i128 | u8 | u16 | u32 | u64 | u128
float = f32 | f64
num = int | float
string = str | txt

; 單一類型別名
bytes = []byte
buf = [16]u8
```

> `int`、`float`、`num` は `std/number` で、`string` は `std/str` で定義されています。これらはコンパイラ組み込みのキーワードではなく、標準ライブラリが同じエイリアス構文で記述したユニオン型です。

### ユニオン型のチェーン参照

ユニオン型は他のユニオン型を参照でき、階層構造を形成します。

```no
int = i8 | i16 | i32 | i64 | i128 | u8 | u16 | u32 | u64 | u128
float = f32 | f64
num = int | float; num 是 int 和 float 的聯合
string = str | txt; string 直接聯合兩個具體字符串類型
```

### 関数での使用

ユニオン型は関数の引数と戻り値に使用できます。コンパイラは自動的に単相化（monomorphization）を行い、各メンバ型に対して独立した関数バージョンを生成します。

```no
; 參數類型為 num 聯合
max = (a ..num) (r num) {
    r = a[0]
    n = len(a)
    i <- [1..n): {
        a[i] > r -> r = a[i]
    }
}

; 方法定義在聯合類型上
num.sign = () (r num) {
    {
        . > 0 -> r = 1

        . < 0 -> r = -1

        -> r = 0
    }
}
```

`string`（= `str | txt`）も引数と戻り値に使用できます：

```no
; str 與 txt 實參都能傳入，各自單態化一份具體函數
take = (s string) (n i64) {
    n = len(s)
}

a str = 'hello'
b txt = 'hi'
n1 = take(a); take__str
n2 = take(b); take__txt
```

> ユニオン型の関数本体に関する既存の制限（`num` と `string` で同じ）：関数本体内で union 引数に対してメンバメソッドを呼び出すこと（例 `s.len()`）はまだサポートされていません。グローバルな組み込み関数（`len(s)`、バイト数）を使うか、具象型ごとの関数に分割してください。ユニオン型の変数宣言（`s string = 'x'`）もまだサポートされていません。また、メンバメソッドと同名のエイリアスメソッド（例 `string.len`）を定義しないでください。`s.len()` の呼び出しを乗っ取り、メソッド本体内で自分自身へ再帰的にディスパッチされます。

### 検出規則

等号構文は、次のような場合に型エイリアスとして認識されます（変数代入ではなく）：

- `name = type | type | ...`：ユニオン型（`|` を含む）
- `name = []type`：スライス型
- `name = [N]type`：配列型
- `name = ?type`：オプション型
- `name = known-type`：単一の型エイリアス。`known-type` は組み込み型名（`i64`、`f64`、`bool`、`str` など）、または既に定義済みの型エイリアス名です

## 生文字列（Raw String）

一対のバッククォート `` ` `` ` ` `` ` `` で生文字列を宣言します。型は `str` です。

### 構文

```
sql = `
SELECT id,name
FROM user
WHERE id > 100
`
```

### 厳格な書式制約

1. **先頭**の `` ` `` の後は**直ちにソースの改行**が続かなければなりません（LF。Windows ファイルの CRLF も受け付けます）；
2. **末尾**の `` ` `` は**単独で1行を占め**、その行には空白と終了バッククォートのみが許可されます；
3. **先頭と末尾のバッククォートがある行は文字列の内容に含めず**、区切り記号としてのみ扱います；
4. **エスケープ規則**：内部の `\`、`\n`、`\t`、`\'`、`\"` はすべて**そのまま保持**し、エスケープ解析は一切行いません；
5. **ソース内の改行とインデント空白を完全に保持**して文字列のバイトに含めます；CR（`\r`）例外——**常に破棄**，そのため CRLF ファイル與 LF ファイルバイト単位で同一の値が得られます；
6. **バッククォート文字を直接埋め込むことはできません**。含めたい場合は `` ` `` を通常のシングルクォート文字列との連結で表現してください。

### 例

```
; 內容為 "SELECT id,name\nFROM user\nWHERE id > 100\n"
; 轉義字符 \n \t 原樣保留，不解釋
raw = `
line1\nline2
\ttabbed
`
```

## 正規表現リテラル（Regex Literal）

Nolang は JavaScript 形式の正規表現リテラル構文 `/pattern/flags` をサポートし、コンパイル済みの `regexp` インスタンスを作成します。

### 構文

```no
; 基本正則字面量
re = /\d+/

; 帶旗標（flags）
re = /hello/gi

; 字符類、錨點、量詞
re = /[a-z]+/
re = /^hello.*world$/

; 轉義斜線
re = /a\/b/
```

### フラグ

| フラグ | 意味        |
| --- | --------- |
| `g` | グローバルマッチ      |
| `i` | 大文字・小文字を区別しない    |
| `m` | 複数行モード      |
| `s` | `.` が改行文字にマッチ |

フラグは省略可能で、終了の `/` の後に続き、ASCII 文字で構成されます。

### 文脈依存の字句解析

`/` は除算演算子であると同時に正規表現リテラルの開始記号でもあります。Nolang は JavaScript と同じ**文脈依存**の字句解析によってこれを区別します：

- **式の開始位置**（文の先頭、`=` / `(` / `[` / `{` / `,` / `:` / `;` などの後）→ `/` は正規表現リテラルの開始
- **値が生成される位置**（識別子、リテラル、`)` / `]` / `}` などの後）→ `/` は除算演算子
- `//` は常に行コメントです（最優先）

```no
; 正則字面量（= 後是表達式起始位置）
re = /\d+/
result = match-text(/[a-z]+/, text)

; 除法運算符（標識符後是值產生位置）
ratio = 100 / 4
x = a / b
```

### 脱糖

正規表現リテラルはコード生成段階で、標準ライブラリの `regexp-compile` 関数の呼び出しへ脱糖されます：

```no
; 源碼
re = /\d+/

; 脫糖後等價於
re = regexp-compile('\\d+')
```

`regexp-compile` は `std/regexp.no` で定義され、`regexp` 構造体を作成して `.compile()` を呼び出しパターンをコンパイルします。

### 使用例

```no
; 創建正則並匹配
re = /\d+/
matched = re.matches('hello 123 world')
print(matched); true

; 查找匹配
re = /[a-z]+/g
result = re.find('hello 42 world')
print(result); "hello"

; 作為函數參數
result = match-text(/\d+/, text)
```

> **注意：** 空の pattern `//` は行コメントと衝突します（JavaScript の動作と同じ）。空にマッチさせたい場合は `/(?:)/` を使用してください。

## 命名規則

変数名、関数名、構造体名などはアンダースコアで始めることができ、その後はハイフン、字母、数字で構成できます。数字で始めることはできず、ハイフンで終わることも、複数のハイフンが連続することもできません。

**大文字・小文字の規則（厳守）：**

- **グローバル定数・グローバル変数**：**必ず**大文字で始めます（例 `NOLANG`、`MAX-SIZE`、`HEX-CHARS`）。プライベートなグローバル変数はアンダースコアで始まり、その後はやはり大文字にします（例 `_NOLANG`、`_PRIVATE-CONST`）。
- **ローカル変数・関数引数**：小文字を使用します（例 `hex-chars`、`data-len`）。`_` 接頭辞は**使わないでください**。ローカル変数はそもそもスコープ内でプライベートであり、可視性の印は不要です。`_` 接頭辞はプライベートなグローバル変数と FFI のプライベート宣言にのみ使用します。
- **関数名・構造体名**：小文字を使用します（例 `sha1-block`、`db-mysql`）

**関数名の慣例（強く推奨）：**

- **関数名にモジュール名の接頭辞を付けない**。モジュール内の関数は短く直感的な名前で十分で、モジュール接頭辞は他モジュールからの呼び出し時に `ShortName.` として自動的に付きます。たとえば `tail.no` ではエントリ関数を `tail` ではなく `tail-run`、補助関数を `atoi` ではなく `tail-atoi` と定義します。コードが簡潔になり、他モジュールからの呼び出しも `tail.tail()` の形で直感的になります。
- **エントリ関数**にはモジュール名そのものを使うことを推奨します（例 `ping.no` → `ping`、`cat.no` → `cat`）。他モジュールからのインポートは `# /src/tail.tail` の形になります。
- **キーワードは避ける**：`awy`（コルーチングループのキーワード）、`match`（条件マッチのキーワード）などは関数名に使用できません。`run` は削除されたため、通常の識別子として使えます。
- **`main` は予約名であり関数名に使用できません**：Nolang のプログラム入口は**トップレベル文から自動合成**されるため（`hir2mir.synthesizeMainForTopLevel` を参照）、明示的に `main` を定義する必要はなく、**許可もされません**。`main = (...) { }` が現れた瞬間——メソッド `recv.main` や、他の関数内にネストされた `main` も含む——コンパイラは直ちにエラーを報告します（`'main' is a reserved name and cannot be used as a function name`）。エントリにしたい場合は、文をトップレベルに直接記述してください。

> **グローバル変数は大文字で始めなければなりません**。これは慣例ではなく強制規則です。小文字で始まるトップレベル変数はコンパイラにローカル変数として扱われ、未定義参照などのエラーを招く可能性があります。

```no
; ✅ 正確：全局數據使用大寫字母
NOLANG = 'nolang'
MAX-SIZE = 1024
HEX-CHARS = '0123456789abcdef'

; ✅ 私有全局變量：下劃線開頭，其後仍需大寫
_NOLANG = 'nolang'
_PRIVATE-CONST = 42
```

```no
#{fmt-skip}
; ❌ 錯誤：全局變量不能使用小寫字母開頭
; x1 = 10
; x = 10
; foo-bar = 42
; hello-world = 'Hello World'
```
```

```no
#{fmt-skip}
; ✅ 局部變量（函數內）使用小寫字母，不加 _ 前綴
; fn-example = () {
;     x1 = 10
;     x = 10
;     foo-bar = 42
;     hello-world = 'Hello World'
;     ; ❌ 錯誤：局部變量不需要 _ 前綴
;     ; _x = 10
; }
```
```

### モジュール内ではグローバル変数を避ける

**強く推奨：必要でなければモジュール（`.no` ファイル）内でグローバル変数を使用しないでください。** グローバル変数は次の問題を引き起こします：

- **コンパイラのバグリスク**：Nolang コンパイラはグローバルな構造体変数の関数間のメモリアドレス処理に既知の制限があり、異なる関数が異なるアドレスを参照して状態が矛盾する可能性があります。
- **並行安全性**：グローバルな可変状態は fork や非同期の場面で追跡が難しく、競合状態を引き起こしやすいです。
- **テスト容易性**：グローバルな状態は関数に暗黙の依存を生じさせ、テストを分離することが困難になります。
- **コードの可読性**：グローバル変数はデータの流れを分かりにくくし、読者はモジュール全体を追わないと関数の動作を理解できません。

**推奨される方法：**

1. **ローカル変数を優先**：状態は関数内のローカル変数に保持し、引数と戻り値で受け渡します。
2. **構造体で状態をカプセル化**：関連する状態を構造体にまとめ、メソッドで操作します（メソッドのレシーバはローカル変数で、アドレスが一致します）。
3. **必要な場合のみグローバル変数を使う**：モジュールレベルの定数（不変）、シングルトン資源（全体のログバッファなど）といった場面です。
4. **グローバル変数は大文字にする**：これは強制規則です（上記参照）。小文字で始まるトップレベル変数はコンパイラにローカル変数として扱われます。

```no
#{fmt-skip}
; ❌ 避免：在模組中使用全局可變變量
; g-conn = tls.conn {}
; g-buf = ' '
;
; fn-a = () {
;     g-conn.send(g-buf)   ; 全局變量跨函式可能位址不一致
; }
```
```

```no
; ✅ 推薦：使用局部變量，狀態透過參數/返回值傳遞
fn-a = () {
    conn = tls.conn {}; 局部變量，位址一致
    buf = ' '
    conn.send(buf)
}

; ✅ 推薦：將完整流程封裝在單一函式中，避免狀態跨函式傳遞
serve-once = (listen-fd fd, body str) (ok bool) {
    ok = false
    client-fd = net.net-accept(listen-fd)
    conn = tls.server-init(client-fd); 局部變量
    conn: {
        ok -> {
            c = it
            c.handshake()
            c.send(body)
            c.close()
            ok = true
        }

        -> fs.close(client-fd)
    }
}
```

> **実例**：`std/net/tls.no` の `https-serve-once` 関数は HTTPS のリクエスト・レスポンス周期全体（accept + handshake + recv + send + close）を単一の関数にカプセル化し、すべての TLS 状態をローカル変数に保持することで、グローバル変数の関数間アドレス不一致というコンパイラのバグを回避しています。

## API ドキュメントの規則

関数のドキュメントコメントには、すべての引数名と型、および戻り値パラメータの名前と型を含めるべきです。

**ルール：**

- 関数定義の上のドキュメントコメントには、各引数の名前と型、および戻り値パラメータの名前と型を記載しなければなりません
- モジュール先頭の API 概要も完全なシグネチャ（引数名、型、戻り値名、型を含む）を使用し、省略形を使わないでください

```no
#{fmt-skip}
; ❌ 錯誤：缺少型別，缺少返回參數名
; sha1(data) (hash)
; sha1-block(s, h0..h4)
```
```

```no
; ✅ 正確：包含參數名、型別、返回參數名、型別
; sha1(data []byte) (hash [20]byte) — 完整雜湊
; sha1-block(s []u32, h0 u32, h1 u32, h2 u32, h3 u32, h4 u32) — 處理單一區塊

; 函數定義上方的文檔註釋也應遵守同樣規範：
; sha1: 計算 SHA-1 雜湊
; data []byte: 輸入位元組陣列
; 返回 hash [20]byte: 20 位元組雜湊值
sha1 = (data []byte) (hash [20]byte) {
    ...
}

### 翻訳可能なドキュメント注釈（Markdown リンク）

ドキュメント注釈は**独立した Markdown リンク**で終わらせることができ、注釈全体を翻訳カタログの1つのエントリに対応させます：

```no
; get: 獲取第 i 個參數
; 委派至 os.arg(i) builtin（讀取 main 的 argv[i]）；越界回傳 nil
; [get](#args.get)
get = (i i64) (val ?str) {
    val = os.arg(i)
}
```

**ルール：**

- リンクは注釈グループの**最終行**でなければならず、単独の1行を占めます。その上のすべての行が一つのまとまりを構成し、1つのメッセージとしてまとめて翻訳されます
- 対象は `#` で始まるアンカー（同じカタログ内のエントリ）でなければなりません。`[說明](https://example.com)` のような外部リンクは人間向けの通常のリンクであり、**翻訳マーカーとしては扱われません**
- アンカーがそのままキーです（`args.get`）。著者が指定し、翻訳者はカタログ内でそれを目にします。文字列から導出されるものではないため、表現を書き換えても既存の翻訳は無効になりません。アンカーに使用できるのはアルファベット、数字、`.`、`_`、`-` で、グローバルです。モジュール接頭辞を付けることを推奨します
- 前綴用**打平後的模組名**，不是目錄名。編譯器把 std 檔案打平成它的檔名：`std/collection/linked-hash-map.no` 的模組就是 `linked-hash-map`，`use std/collection` 也不會給符號加 `collection.` 前綴。所以 `linked-hash-map.clear` 的錨點是 `linked-hash-map.linked-hash-map.clear`（模組名 + 原樣的名字），**不是** `collection.linked-hash-map.linked-hash-map.clear`。`collection`／`net`／`crypto`／`archive`／`encoding`／`database` 這些目錄段不屬於任何符號，不該出現在錨點裡
- 角括弧内の文字（`[get]`）はソースを読む人へのヒントにすぎず、表示時には行全体が取り除かれます。`[](#args.get)` も有効です
- リンクを持てるのは `;` の単行コメントだけです（`;;` と `;;block` は対象外）

訳文は `locales/<語言>-doc.noml` に置き、アンカーをキーとします。訳文がない場合は注釈原文にフォールバックし、空白にはなりません。ファイル名は `.no` の命名規則（小文字、数字、単一のハイフン）に従い、タグ自体がその形式です。`--lang=zh-tw` は `zh-tw-doc.noml` を読み込みます。

標準ライブラリの注釈付き関数とメソッドにはすべてアンカーが付いているため（約 2000 件）、どの訳文でも1つ追加すればすぐに LSP から利用できます。`make i18n` は**翻訳済み**のエントリだけをカタログに書き出し、原文を訳文として流し込むことはありません（そうすると英語のカタログにまた中国語が現れてしまいます）。`go run ./i18n/cmd/genen -doc-missing` は未翻訳のアンカーを一覧表示します。

**LSP のヒント：** 関数名にマウスをホバーすると翻訳済みの説明全体が表示されます。リンクのある行にホバーすると、アンカー自体が指す内容（同じく現在の言語）が表示され、その場で訳文を照合できます。

str-to-bytes = (s str) (out []byte) {

- `str.to-bytes()` — 文字列をバイト配列に変換（手書きの `str-to-bytes` の代わり）
- `[]byte.to-str()` — バイト配列を文字列に変換（手書きの `bytes-to-str` の代わり）

### TOML 設定ファイル（`toml`）

標準ライブラリの `toml` は TOML 1.0 設定ファイルの解析とシリアライズを提供します。パーサはコメント、bare/quoted/dotted keys、`[table]`、`[[array-of-tables]]`、basic/literal/multiline strings、整数（10進／16進／8進／2進）、浮動小数点数、真偽値、日付時刻、配列、inline table をサポートします。値は TOML の生のリテラル値として保持されるため、配列や日付時刻などの情報が失われません。

```no
cfg = toml.parse('title = "Nolang"\n[server]\nport = 8080\n[[server.backends]]\nname = "local"')

doc = toml.new()
doc.put('name', '"nolang"')
doc.put('server.port', '8080')
doc.put('enabled', 'true')
text = toml.stringify(doc)
```

よく使われる API：

- `toml.new()` — 空の `toml` を作成
- `toml.parse(text)` — TOML を解析し `?toml` を返す
- `doc.put(key, raw-value)` — 生の TOML 値を追加または更新。不正な値は拒否され、重複キーはパーサがエラーを報告します
- `toml.get(doc, key)` — 生の値を取得（`?str`）
- `toml.get-str(doc, key)`、`toml.get-i64(doc, key)`、`toml.get-f64(doc, key)`、`toml.get-bool(doc, key)` — 変換済みの scalar を取得
- `toml.stringify(doc)` — TOML を出力。array-of-tables は `[[...]]` ヘッダを出力します

現在のドキュメントモデルでは、1つのドキュメントに最大 4 個のキー、2 個の通常テーブル、2 個の array-of-tables までという制限があります。1 キーは最大 32 バイト、1 値は最大 128 バイトで、これを超える場合は設定ファイルを分割するか呼び出し側で処理してください。

### YAML ドキュメント（`yaml`）

標準ライブラリの `yaml` は YAML 1.2 core schema のドキュメントを解析・生成します。ブロックマッピング、ブロックシーケンス、フロー形式のコレクション、3 種類のクォート付きスカラ、ブロックスカラ `|` / `>`、コメント、複数ドキュメント、アンカーとエイリアス、マージキー `<<`、明示キー、さらに型推論（null / bool / int / float / `.inf` / `.nan`）をサポートします。

```no
doc ?yaml = yaml.parse('name: Alice\nserver:\n  port: 8080\ntags:\n  - a\n  - b\n')
doc: {
    nil -> print('nil')

    err -> print(it.msg())

    -> {
        doc = it
        name = doc.find-str('name'); ?str
        port = doc.find-i64('server.port'); ?i64
        name: {
            ok -> print(it)

            -> print('')
        }
        print(doc.to-json())
    }
}
```

よく使われる API：

- `yaml.parse(text)` / `yaml.parse-all(text)` — 解析し `?yaml` を返す
- `yaml.valid-of(text)` / `yaml.error-of(text)` — 検証のみ
- `it.find(path)` / `it.get(key)` — 子ノードを取得し `?yaml` を返す
- `it.find-str(path)`、`find-i64`、`find-f64`、`find-bool` — 値を簡便に取得し `?值` を返す
- `it.to-json()` / `it.to-yaml()` — シリアライズ

> 注意：子ノードは `?yaml`、値取得の補助関数は `?值` を返します。match でアンラップしてください（`child = it.find(path)` の `ok` アームで `it` に子ノードをバインドし、デフォルトアームで空値を処理します。各アームは独立した1行にします）。

## ファイル名の命名規則

`.no` のファイル名（フォルダ名を含む）は必ずハイフン `-` で単語を連結し、**アンダースコア `_` は使用しません**。これは変数名、関数名、構造体名など Nolang 識別子の命名スタイルと一致しています。

コンパイラは `run` / `build` / `test` / `vet` / `fmt` / `ast` コマンドでこの規則を**強制チェック**し、パスのどの部分（フォルダ名またはファイル名本体。`.no` 拡張子は除く）でも違反があれば**直接エラー**になります：

- 許可される文字：小文字の `a-z`、数字 `0-9`、ハイフン `-`。
- 禁止される文字：アンダースコア `_`、大文字、その他の特殊記号。
- ハイフンはセグメントの先頭・末尾に置けず、連続させることもできません（`--`）。

たとえば `tmp/zz_stridx/r_index.no` は `zz_stridx` と `r_index` にアンダースコアが含まれるため拒否されます。`tmp/zz-stridx/r-index.no` に変更すれば準拠します。絶対 OS パス（例 `/Users/me/proj/a.no`）では現在の作業ディレクトリ配下の部分のみを検証し、ホスト側のディレクトリ名（例 `Users`）で誤検知することはありません。

```shell
✅ 推薦：
utils/
├── string-helper.no
├── hash-table.no
└── http-client.no
```

```shell
❌ 避免：
utils/
├── string_helper.no
├── hash_table.no
└── http_client.no
```

## 関数の定義

関数は**名前付き結果パラメータ（named result parameters）**によって結果を出力できます。本質的には  
**出力パラメータ（out-parameter）の構文糖**です。`return`（およびその省略形 `***`、現時点では非推奨）は早期終了にのみ使われ、結果を伴うことはできません。

Nolang の関数定義の形式は `name = (in-params) (out-params) { body }` です。第2の  
括弧組 `(out-params)` が名前付き結果パラメータを宣言します（構文糖）。関数本体内でそれらに値を代入します  
（通常の入力引数と同様に参照型です）。**結果を実際に受け取る変数は呼び出し側で定義する必要があります**——  
定義側の結果パラメータ名は単なるプレースホルダであり、呼び出し側の LHS（または末尾引数）が結果の格納先を決めます  
変数：

```no
parse-line = (s str, max-fields ?i64) (fields []str) {
    ...; 函數體內對 fields 賦值
}

; 調用處定義接收變數（LHS 綁定，型別由簽名推斷）
fields = parse-line(line, nil)

; 多結果按順序綁定
a, b = swap(x, y)

; 或尾隨引數形式：res 作為額外的輸出引數傳入
add1(5, 3, res)
```

Nolang の関数には次の特徴があります：

- **名前付き結果パラメータは構文糖**：実装は入力引数（out-parameter）によるもので、  
  新しい戻り値オブジェクトは生成されないため、内部は安全です。
- **入力引数は読み取り専用**：スカラは値渡し、複合型は読み取り専用参照で渡されます。関数本体内で入力引数とそのサブフィールドへ書き込むことは禁止されています。
- **出力引数は書き込み可能**：呼び出し側は既存の変数を出力スロットにバインドでき、関数はそのメモリを直接変更します。バインドしない場合は、関数が新しい値を生成して渡します。
- 関数内の変数は関数終了時に自動的に破棄されます。
- 呼び出し側は受け取り変数（LHS または末尾引数）を提供しなければなりません。「関数に戻り値がない」という言い方は正確ではありません——  
  正確には、結果は名前付き結果パラメータ（out-parameter の構文糖）を通じて渡され、呼び出し側がバインドします。
- **別名規則**：入力の読み取り専用参照と出力スロットが同じオブジェクトを指すことを許可します。書き込みが出力領域のみで、入力が読み取りのみであれば合法です。コンパイラは静的な別名チェックを行いません。

### 出力スロットを既存の変数へ直接バインドする（中継変数を避ける）

呼び出し側の出力スロットは**既に存在する変数へ直接バインド**でき、関数はそのメモリをその場で書き換えます（上の「出力引数は書き込み可能」を参照）。
したがって、ある出力が既存の状態を引き続き更新するだけの場合、一度きりの中継変数に受け取ってから書き戻す必要はありません：

```no
; ✅ 推薦：餘數直接寫回 r（r 同時是方法的接收者）
qsq, r = r.div-mod(modulus)
```

```no
; ❌ 避免：msq 只被用一次，純粹是轉存
qsq, msq = r.div-mod(modulus)
r = msq
```

- **レシーバを出力先にできる**：`r.div-mod(modulus)` のレシーバ `r` は読み取り専用入力（暗黙の `self`）であり、
  `r` は第2の出力スロット `r bigint` にもバインドされます。〈別名規則〉により、入力は読み取りのみ、出力は書き込みのみなら合法です。
  実測では（`no build` / `no vet` / `no fmt`）、`q, a = a.div-mod(bigint.from-i64(7))` は
  `a = bigint.from-i64(100)` の後に `q = 14`、`a = 2` となり、「いったん `msq` を受けてから `r = msq`」と完全に一致します；
  `r` が外側の関数の結果パラメータでも同じです（`src/std/bigint.no` の `mod-pow` がまさにこの形です）。
- **使わない出力は `_` で捨てる**：商をまったく使わない場合、`_, r = r.div-mod(modulus)` なら新しい変数を1つ導入する必要もなく、
  最も簡潔な書き方です（後述の〈多重代入〉の `_` プレースホルダを参照）。
- **単一出力でも同じ**：`r = r._mul(r)`、`s = s.trim()`、`out = out.replace-str(...)` はいずれも stdlib に既存のその場更新です。
- **既に合法なコードをこのために書き換える必要はありません**：これは新しいコードに対する推奨であり、リファクタリング命令ではありません。〈黄金律：合法なコードを変更しない〉に従い、
  スタイルのために正しく動いているプログラムに手を入れないでください。

### 引数のデフォルト値

**未サポート**。引数リスト内の `name type = expr`（例 `foo = (a i64, b ?i64 = 10)`）は**構文エラー**です（`E_DEFAULT_PARAM`）。コンパイラはデフォルト式を解析せず、呼び出し時にデフォルト値を補うこともありません。これにより「1つの宣言に対して複数の合法な arity がある」という曖昧さが解消され、すべての呼び出し点でデフォルト式を再帰的に低減することによる単相化の膨張も回避されます。

オプションの意味が必要な場合は、引数を option 型 `?T` として宣言し、呼び出し側から**明示的に** `nil` / `ok(...)` を渡し、関数本体で `match` によって処理します：

```no
parse-line = (s str, max-fields ?i64) (fields []str) {
    limit = 1024
    max-fields: {
        ok(v) -> limit = v

        nil ->

        err ->
    }
    ...; limit 即上限
}

; 調用端必須顯式傳參
fields = csv.parse-line(line, nil); 回退 1024

## 制御フロー

> **非推奨構文（n バージョン以降で削除）**：`for { }` / `for cond { }` / `for init, cond, update { }` / `for i in [..) { }` / `match x { }` / `if/elif/else { }` は依然として解析できますが、deprecation warning が出力されます。下記の「**新式構文**」に切り替えてください。

### 新旧の対照

| 旧式 / 後置形式（suffix）           | 前置形式（prefix、format のデフォルト）                   |
| -------------------------- | --------------------------------------- |
| `{ } (true)` 無限ループ          | `!! { }` または `true { }`                   |
| `{ } (cond)` 条件ループ          | `(cond) { }`（空の `()` は false とみなされ、実行されません）       |
| `{ } ()` 実行しない               | `! { }` または `false { }` または `() { }`        |
| `{ } * n` 固定回数             | `n * { }`（N ≤ 0 のときループ本体は実行されません）                |
| `for i=0, i<n, i++ { }` カウント | `n * { }`（固定回数）または `i <- [0..n): { }`（変数） |
| `for i <- [a..b] { }` 範囲   | `i <- [a..b]: { }`                      |
| `for i in [a..b) { }` 範囲   | `i <- [a..b): { }`                      |
| `match x { ... }` マッチ       | `x: { ... }`                            |
| `if/elif/else { }` 分岐      | `{ cond -> body }`（短絡評価。`{}` で囲む必要があります）      |
| `continue`                 | `*` （省略形は現時点では非推奨）                        |
| `break`                    | `**`（省略形は現時点では非推奨）                       |
| `return`                   | `***`（省略形は現時点では非推奨）                      |

> ⚠️ `return`（およびその省略形 `***`、省略形は現時点では非推奨）は**単独でしか使えず、戻り値を伴うことはできません。**  
> Nolang の関数には「戻り値」の仕組みがありません。結果は必ず**名前付き結果パラメータ（out-param）**によって関数本体内で値が代入されて渡されます（「関数の定義」を参照）。  
> そのため `return <值>`、`return(expr)`、`*** <值>` はすべて**禁止**され、コンパイラ / formatter / LSP がいずれもエラーを報告します：
>
> - コンパイラ（`no build`）：`Error: compilation error: parser errors: line L, column C: 'return' 後不能跟返回值；… [E_GENERAL]`
> - `no vet`：`<file>:L:C: [ERROR] nolang-compile: 'return' 後不能跟返回值；… [E_GENERAL]`（他の診断と同じ形式で、1 件につき 1 行）
> - `no fmt`：`format error: …` を出力し、非零の終了ステータスで終了します
> - LSP：該当行に赤いエラー診断を表示します
>
> 誤った書き方：
>
> ```no
> has = (n i64) (r i64) {
>     n == 0 -> return 0        ; ❌ 編譯 / formatter / LSP 均報錯
>     r = n
> }
> ```
>
> 正しい書き方（まず結果パラメータに値を代入し、その後で素の `return` によって早期終了します。アーム本体に複数の文がある場合はそれぞれ 1 行を占めなければなりません）：
>
> ```no
> has = (n i64) (r i64) {
>     n == 0 -> {
>         r = 0
>         return
>     }
>     r = n
> }
> ```
>
> ⚠️ `n == 0 -> { r = 0; return }` のように1行に圧縮するのは省略形ではありません。`; return }` 全体がコメントになり、
> ブロックがそのため永久に閉じられず、後続のすべての文（多くの場合、関数本体の残り全体）がそのアームへ静かに飲み込まれます ——
> 実測では `no vet` はエラーを報告せず、その関数は一度も呼び出されません。

## チャネル（`chan[T]`）

チャネルは**有界で、拡張可能で、送信はブロックせず、受信は待機する**値のキューです。受信側は三状態の `?T` で1つずつ値を取り出します。
構文記号は `<-` の1種類だけです（他の使い方は「制御フロー」の `i <- range:` による走査を参照）。

```no
ch chan[i64] = with-cap(8)   ; 顯式初始容量
buf chan[i64]                 ; 裸宣告：等價於 with-cap(0)，發送時按需增長

ch <- 1                       ; 發送（左側型別是 chan[T] 才算發送）
n = ch.len()                  ; 當前積壓數
c = ch.cap()                  ; 初始容量
ch.close()                    ; 關閉：不再接受發送，既有值仍可取
```

### 受信：三状態ループ

`v <- ch: { ... }` は**ループ**で、各周回で三状態の `?T` を `v` にバインドします。`break` で早期に抜けられます。
`ok` は値を取得できたこと、`nil` はチャネルが閉じられて空になったこと、`err` は**真のエラー**（初期化されていない
ゼロ値ハンドル——待つものがない）——**後ろの2つはいずれもループを終了します**（同じ周回のアームは通常どおり実行されます）。

`ok` 以外で最も重要なのは、**空読みは「値を待つ」のであって「値がない」のではない**ということです。チャネルが開いているのに空の場合、読み手は
一時停止し、誰かが `send` または `close` するまで待ちます：

- コルーチン内（`co` から作られた `-async` クローン）では本当に park します。状態番号はヒープ上のフレームに書き込まれ、タスクは
  チャネルの待ちチェーンに登録されたうえでスケジューラへ戻ります（「コルーチン」の節を参照）。
- 通常の関数では park できないため、**ブロック**します。準備済みキューを繰り返し回して、取り出せる値が出るまで待ちます。

したがって「空になるまで取り出す」には `close()` でループを終了させる必要があり、形は Go の channel に対する `range` と同じです。

```no
ch chan[i64] = with-cap(2)
ch <- 10
ch.close()

<- ch: {
    ok -> print('got {it}')      ; it 是本輪的元素
    nil -> print('closed')       ; 取空後落到這裡
    err -> print('bad channel')  ; 只有零值句柄才會落到這裡
}
```

ループ変数を捨てる場合は `<- ch: { ... }` と書きます。body の最初の文が `v` に対する match でない場合、
`v` は**要素そのもの**（`T` であって `?T` ではない）に直接バインドされ、`ok` の周回だけが body を実行します：

```no
i <- ch: {
    print(i)                     ; i 是 i64，不是 ?i64
}
```

自分で三状態を判別しつつループ変数も残したい場合は、body の先頭でそれを match すればよいです。アームだけを書く（`v:` を省く）のは
同義の省略形で、判定は**アーム名**に行われ、`ok` / `nil` / `err` の3つの名前が現れたときに三状態とみなされます：

```no
i <- ch: {
    ok -> print('got {it}')      ; it 是本輪元素，i 是本輪的 ?i64
    nil -> print('closed')
    err -> print('empty')
}
```

判定は構文に基づくもので、型に基づくものではありません（下の「形態の判定」を参照）。`no fmt` は上記の省略形を
明示的な主語 `i: { ... }` へ補完します。どちらの書き方も再解析でき、フォーマットは冪等です。

### 形態の判定

| body の先頭 | 形態 | `v` の型 |
|---|---|---|
| `co bar(i)`、`print(i)` などの通常の文 | 要素 | `T` |
| `v: { ... }` | 三状態 | `?T` |
| `ok -> ...` / `nil -> ...` / `err -> ...` | 三状態（省略形） | `?T` |
| その他の素の match（例 `i > 5 -> ...`） | 要素 | `T` |

判定は **body を解析する前**に行わなければなりません。ブロックの先頭が match の場合、パーサは直ちにそれを
`if` チェーンへ脱糖し、後から元の意味を認識できなくなります。この判定はかつて完全に機能せず、`i <- ch:` が常に要素形態として扱われ、
三状態アームは互いに無関係な独立ガード（毎周回すべて実行）へ退化し、`it` には空値がバインドされていました。

### 意味

| 観点 | 規則 |
|---|---|
| 容量 | `with-cap(n)` の `n` は**初期**容量です。満杯になると倍増し、`send` は**決してブロックせず、値を失いません** |
| 空読み | **待機**：コルーチンは park し、通常の関数は準備済みキューを回してブロックします。`err` はゼロ値ハンドルという真のエラーにだけ使われます |
| 終了 | `close()` の後に `send` するとプロセスを中止します。すでにキューにある値は順序どおりに取り出せ、取り切ると `nil` になります。終了時は待っている全員を同時に起床させます |
| ペイロード | 送信時に**ディープコピー**され（`str` / `%vec` は clone を経由）、受信側は独立した1つのコピーを取得します。元の変数が書き換えられたり早期に解放されたりする心配は不要です |
| 並行 | チャネル自体はロックしません（シングルスレッドの協調的スケジューリング）。待機者は制御ブロックの `waiters` チェーンにぶら下がり、`send` / `close` がチェーン全体を外して1つずつ再登録します。**起床されたことが値の取得を意味するわけではなく**、再開後は読み取り可能性を再判定する必要があるため、コルーチンの再開点は park ブロックそのものです |
| デッドロック | 準備済みキューが空で対象タスクが未完了の場合、これ以上進めません。実行時に `nolang: deadlock: …` を stderr に出力して abort します。誰も送信していない値を返したり、空回りしたりはしません |

> 空読みでの一時停止の直接的な帰結：**排出ループは `close()` で終了させる必要があります**。初期バージョンでは「開いているが空」を
> `err` として報告してループを自然に終了させていたため、`for` の形ではチャネルを閉じる必要がありませんでした。現在その経路は待機であり、
> `close()` を忘れたプログラムは最後の周回で止まります（コルーチンでは一時停止し、通常の関数ではデッドロックと判定されます）。

### 制限

- **LLVM バックエンドのみで実装されています。** `no build --js` / `--wasm` はチャネルノードに遭遇すると明確なエラー
  （`[chbkn001]`）を出力します。不完全なコードを黙って生成することはありません。
- チャネルは**値型**（1マシンワード幅のハンドル）で、引数・結果・要素として渡せます。
  `chan[chan[T]]` や `?chan[T]` も宣言できます（まだ `tests/chan.no` のカバレッジには含まれていません）。

## プレースホルダ文（`...`）

`...` は言語の**プレースホルダ文**で、構文上は合法ですが、意味的に**何もしません**。主にドキュメントの実演、
コードの骨格、`TODO` の予約位置に使われます。コンパイル時には AST→HIR 段階で文全体が破棄され、成果物は「その行を一度も書かなかった」
場合と完全に同じです（同じソースで `...` を追加・削除してもコンパイルされたバイナリの `sha256` が同じことを確認済み）。

```no
parse-line = (s str) (fields []str) {

    ; TODO: 這裡還要處理跳脫字元
    ...

    fields = csv.parse-line(s)
}

add = (a i64, b i64) (result i64) {
    result = a + b
    ...
}
```

ルール：

- **単独の1行に限る**（行末に `;` コメントを付けるのは可）。`fail -> ...`、`x = ...`、`[0...n)` のような書き方は
  すべて構文エラーになります。`...` には値がなく、式の位置や文の他の部分に現れることができません。
- **`return` の別名ではありません**。また**範囲演算子でもありません**。範囲は `..`（2点）で、早期リターンは `return` と書きます。
- `no fmt` はそのまま保持し、削除も移動もしません。

次の書き方はすべて不正です：

```no
#{fmt-skip}
add = (a i64, b i64) (result i64) {
    result = a + b
    ...          ; ✅ 唯一合法形式：獨佔一行
}

ok -> ...        ; ❌ 語法錯誤：`...` 不能出現在表達式位置
x = ...          ; ❌ 語法錯誤：同上
i <- [0...n): {  ; ❌ 語法錯誤：`...` 不是範圍運算子，應寫 [0..self.n)
}
```

x: {
    err(e) -> log(e.msg())

    nil -> log('nil')

    ok(v) -> do-right-thing(v)
}

; 註：struct 模式匹配（`user: { User{id=1} -> ... }`）與欄位綁定尚未支援，故不示範

score: {
    [0..59] -> print('不及格')

    [60..89] -> print('良好')

    [90..100] -> print('優秀')

    -> print('分數非法')
}

; 區間語法共 16 種組合，規律：'[' 表示包含左端點，'(' 表示不包含；
;                     ']' 表示包含右端點，')' 表示不包含。
;
; 【有界區間】（4 種）— 兩端都有具體值
;   [a..b]  → x >= a && x <= b   兩端都包含
;   [a..b)  → x >= a && x <  b   左包含右不包含
;   (a..b]  → x >  a && x <= b   左不包含右包含
;   (a..b)  → x >  a && x <  b   兩端都不包含
;
; 【無上限區間】（4 種）— 省略右端點（End=nil），僅檢查下界
;   [a..)   → x >= a              左包含，無上限
;   [a..]   → x >= a              左包含，無上限
;   (a..)   → x >  a              左不包含，無上限
;   (a..]   → x >  a              左不包含，無上限
;
; 【無下限區間】（4 種）— 省略左端點（Start=nil），僅檢查上界
;   [..b]   → x <= b              無下限，右包含
;   [..b)   → x <  b              無下限，右不包含
;   (..b]   → x <= b              無下限，右包含
;   (..b)   → x <  b              無下限，右不包含
;
; 【完全無界區間】（4 種）— 兩端都省略，基於類型最小值/最大值
;   [..]    → true                類型最小值 ≤ x ≤ 類型最大值（兩端都包含）
;   [..)    → true                類型最小值 ≤ x < 類型最大值
;   (..]    → true                類型最小值 < x ≤ 類型最大值
;   (..)    → true                類型最小值 < x < 類型最大值
;
; 在 match 中，完全無界區間基於被匹配變量的類型值域（必然為真，等同 catch-all）。
; 在 range-for 中，基於迭代變量的類型範圍（如 i64 的 [..] 從 i64.MIN 到 i64.MAX）。
;
; 範例：使用無界區間做完整分類
v = 85
result = v: {
    [..0) -> 'negative'

    [0..60) -> 'fail'

    [60..80) -> 'pass'

    [80..90) -> 'good'

    [90..100] -> 'excellent'

    (100..) -> 'extraordinary'
}
print(result)

num: {
    1 || 3 || 5 || 7 -> print('奇數小數')

    2 || 4 || 6 -> print('偶數小數')

    -> print('更大數字')
}

; 有返回值，最後一個語句/值
result = x: {
    1 -> 1

    2 -> 2 + 1

    -> a + b
}

; 多行 arm body 必須使用大括號 -> { ... }
x: {
    nil -> {
        log('nil')
        do-cleanup()
        return
    }

    err -> {
        log(it.msg())
        do-cleanup()
        return
    }

    ok -> print(it)
}
```

> **マルチ行 arm body のルール**：arm body に複数の文が含まれる場合は、波括弧 `-> { ... }` で囲む必要があります。単行の body は `->` の直後に直接書けます。これは、複数行の body を波括弧で囲まないと option match の `it` バインディングを正しく挿入できず、コンパイルエラーになるためです。

> **for-in 体内の match 意味**：`i <- (a..b]: { 1 -> ... 2 -> ... }` は各反復変数 `i` ごとに match 本体を一度実行します（`1 ->` は `i == 1 ->` と等価で、以下同様です）。これは各反復で一度 match を実行する構文糖です。

#### Match 主語の三つの形態

match 主語には**値**、**式**、**ブロック**の三種類があります：

| 形態 | 書き方 | 評価方法 |
| --- | --- | --- |
| 値 | `x: { ... }` | `x` に直接マッチ |
| 式 | `x + 1: { ... }` | 式の値を先に計算してからマッチ |
| ブロック | `{ ... }: { ... }` | 一連の文の本体を実行し、その間の `?=` の結果にマッチ |

最初の二つは**式**です：文としても使え、値コンテキストで値を取得することもできます（`v = x: { ok -> it, -> 0 }`）。
三つ目は**文のみ**です——式ではなく、代入できず、ブロック末尾の値も持たず、`-> _` が結果を破棄するために使われます。
`no fmt` は `}: {` をそのまま往復させ、アーム間の空行ルールは通常の match と同じです。

##### 式主語（`expr: { ... }`）

`expr: { ... }` の `: {` は優先順位が `=` より**高い**です：代入右側ではそれは RHS 全体であり、
「まず `r = <expr>` を完了させ、その後に独立した match が続く」ではありません。そのため option 算術を一段階でアンパックできます：

```no
#{overflow=wrap}
rem = seconds % 3600: {
    ok -> it

    -> 0
}

#{overflow=wrap}
sec = rem % 60: {
    ok -> it

    -> 0
}
```

これは以前は三段階に分割する必要があった `rem-opt = seconds % 3600` / `rem = 0` /
`rem = rem-opt: { ok -> it  -> 0 }` と等価です。最初の代入には明示的な型を付けられ
（`rem i64 = seconds % 3600: { ... }`）、二回目の代入は `rem = ...: { ... }` と直接書けます；
どちらも単一の値位置 match であり、結果の型はアーム末尾の式で決まります。

意味と制約：

- 主語が D6 option 算術（`+ - * / %`）の場合、結果は `?T` です。match はそれを
  `__match_subj_L_C ?T` という合成一時変数に正規化します：主語は**ちょうど一度だけ評価**され、
  `ok -> it` が payload にバインドされ、条件は option タグ比較を通り、`-> 0` が `nil` / `err` を
  フォールバックします。合成名は診断や `no fmt` の出力には現れません。
- match の結果は **plain T** で、セマンティック副表に登録されます。したがって後続で
  `sec = rem % 60: { ... }` と書き続けることができ、連続する複数の値位置 match でも payload が失われません。
- 値位置 match は**値コンテキスト**（代入／`?=`／複合代入の右側）にのみ付加され、`: { ... }` は
  実際に match ブロックでなければなりません。`cond: { body }` のような文レベルの条件ループや
  struct リテラルは、従来の解析パスを通り、影響を受けません。
- **フィールド目標への代入も値コンテキストです**（2026-11-09 以降）：`d.month = mp - 9: { ... }`、
  `b.n ?= b.n + 1: { ... }` の `: {` は**右辺値**にバインドされ、代入全体にはバインドされません。
  以前はこれら二つの分岐が右辺値の解析時に `CTX_EXPR` の推論を漏らしており
  （識別子目標は `let` を通すと推論されるが、`obj.f =` / `a[i] =` では推論されなかった）、
  結果として `: {` が文レベルで拾われ、代入全体の外側に適用され、
  `match(主語 = (d.month = mp - 9))` と解析されていました：代入は従来どおり実行され `?T` が
  暗黙にアンパックされてフィールドに書き込まれ、`ok -> it` / `-> 0` の二つのアームは
  事実上デッドコードになっていました。現在ではアームの値が実際にフィールドへ戻ります。
- インデックス目標（`a[i] = …: { ... }`）も形状は同じですが、D9 は元々添字の直接書き込みを
  禁止しているため、この書き方は checker に `idxwrite` として拒否されます。place-match
  （`a[i]: { ok -> it = v }`）または `?=` に書き換える必要があります。
- `no fmt` は `expr: { ... }` をそのまま往復させ、代入＋独立 match の二つの文に分割しません。
- **型の可視性境界**：option 算術の主語を `?T` に正規化するには、二つのオペランドの
  宣言型が parser から静的に見える必要があります。オペランドが深いメソッドチェーンから
  来ている場合（レシーバ型が AST 再生でも推論できない場合）は、その宣言に明示的な型を
  補ってください（例：`e i64 = flr.to-i64()`）。そうしないと正規化が保守的にスキップされ、
  `ok -> it` にバインディングがなくなり、MIR がゼロ埋めして観測値は常に 0 になります。
  `src/std/number.no` の `f64.to-str-general` がまさにそうです：この注釈がないと、
  `fmt.fmt-f64(2.5, '')` が
  `'2.5'` から `'3'` に退化します。回帰テストは
  `src/parser/value_match_expr_subject_test.go::TestValueMatchExprSubjectASTAnnotatedOperand`
  （注釈を外すと即座に失敗）。

`src/std` は 2026-11-09 に **122 箇所 / 22 モジュール**の option アンパックをこの一段階の
書き方に変更しました：最初の三段式（`x-opt = expr` / `x = 0` / `x = x-opt: { ... }`）のほか、
二段式（ゼロ値初期化なし）、明示的な型による最初の代入（`x i64 = expr: { ... }`）、および
中間変数が同じ関数内で複数回ペアで宣言される書き方も含みます。畳み込み後の主語は
メソッド呼び出し、インデックス、option 算術のいずれにもなれます；
`ok -> it`／`ok(v) -> v`／定数アーム／`-> _` はすべて実測で等価であり、`no fmt` は
これらのサイトに対して冪等です。コンパイラの型推論は「セマンティック副表では `?T` が見つかるが
宣言は実際には `i64` である」といった全域的な同名の残骸も考慮し、`ok -> it` が
バインディングを失うことはありません。

保持された（9 箇所の）ケース：① 内側の match が `-opt` 変数自体に書き戻す（その変数は
後続の値位置 match の主語）；② 二段の連鎖 option match；③ 値による分派を行う
値位置 match（errno → メッセージなど、option アンパックではない）；④ 宣言と match の間に
他の文がある、または中間変数が分岐をまたいで累積された結果（畳み込むと評価タイミングが変わる）。

##### ブロック主語（`}: {`）

ブロック主語は一連の文を包み込み、**`?T` 結果パラメータを持たない関数**でもその場で
`?=` の上位伝播を処理できるようにします：

```no
; d i64: 除數，0 時 6/d 得 err
f = (d i64) {
    {
        v ?= 6 / d; 失敗不再要求函式有 ?T 結果參數
        print(v.to-str()); 失敗時不會執行
    }: {
        err -> print(it.msg())

        nil -> print('nil')

        -> _; 丟棄結果
    }
    print('之後照常執行'); arms 跑完後流程繼續
}
```

意味：

- 本体内の `?=` は**最も近い**ブロック match に捕捉されます（入れ子の場合は最内層が優先し、
  所在する関数が `?T` 結果パラメータを持っていてもブロック match が優先されます）。
  捕捉は再帰的で、裸のブロック、if 本体、ループ本体、match アーム内の `?=` がすべて対象です；
  関数定義は境界ですが、関数リテラルは境界ではありません。
- マッチされるのは三 state の `?T` で、標準の option match と同じ**網羅性チェック**が
  適用されます：フォールバック・アームがない場合、`ok ->` が実行時に到達不能でも、
  `nil` / `err` / `ok` の三つのアームを揃える必要があります。
- 本体が正常に最後まで進んだ（`?=` が零個、またはすべて成功）⇒ `nil` にマッチ；
  ある `?=` が失敗 ⇒ その時の `nil` または `err` にマッチします（`err` アームの `it` は
  完全な `err.err` です。〈`it` の型〉を参照）。
- **一度失敗すると本体全体が停止します**：後続の文や後続のループ反復は実行されず、
  アームは一度だけ実行されます。これは「停止ブロック」であり、関数 `return` ではありません。
  ユーザー自身の `return` / `break` / `continue` の束縛は影響を受けません。
- 展開は既存のコア AST のみで構成され（合成 `?T` ローカル変数 + `if` ガードチェーン +
  一般 match）、新しい HIR / MIR ノードはありません。合成変数名は診断や `no fmt` の出力には現れません。

> `=` によるその場捕捉との役割分担：`=` は失敗を**目標変数に保存**して処理を続けます；
> `}: {` は失敗を**一つの match に収束させ**、本体の残りを停止します。「失敗後も続行」
> が必要な場合は `=` + 後続 match を使い、「失敗したらクリーンアップ・アームへ飛ぶ」
> が必要な場合は `}: {` を使います。

##### ブロック match と値位置 match の取捨選択

同じこと——option 算術の結果を plain 変数に戻す——に二つの書き方があります。
**ブロック本体にこの一文しかない場合は両者は等価ですが、本体に他の文がある場合や
右辺値が別の箇所で失敗しうる場合、意味は分岐します。**

```no
; A：塊 match + `?=`（區塊級「try」）
{
    #{overflow=wrap}
    np ?= np + 1
}: {
    err -> _

    -> _
}

; B：值位 match 直接綁目標（陳述級）
#{overflow=wrap}
np = np + 1: {
    ok -> it

    -> _
}
```

`#{overflow=wrap}` の下では `np + 1` の結果は**常に `ok`（折り返し値）**で、両者とも
裸の `add i64` を一つだけ生成し、オーバーフロー検査分岐はありません。失敗アームは
「加算自体」に対してはデッドコードです——これが多くのサイトで両者が「完全に等価」に
見える理由です。本当の違いは**作用範囲**と**失敗パス**にあります：

| 観点 | A：ブロック match + `?=` | B：値位置 match |
| --- | --- | --- |
| 構文位置 | **文**：末尾値なし、代入不可 | **式**：代入右側、フィールド目標、`?=` 右側に置ける |
| 失敗時の目標書き込み | **ゼロ値**（`i64` → `0`、`str` → `''`） | フォールバック・アーム次第：`-> _` は**書き込まない**（元の値を保持）、`-> 0` は 0 を書く、`-> sum` は古い値を書き戻す |
| 本体の残りの文 | **すべてスキップ**（後続のループ反復を含む） | 通常どおり実行 |
| 一つの `err` アームがカバーする範囲 | ブロック内の**すべて**の `?=` | この一文のみ |
| 目標に型宣言が付く | ❌ `q i64 ?= …` は解析エラー（`yh8904fm`） | ✅ `q i64 = …: { … }` |
| 右辺値が定数折りたたみ | ❌ `s8gh6opt`（`4 / 2` が plain に折りたたまれ、option でなくなる） | ✅ 主語は依然として `?T` に正規化される |
| 使用可能な前提 | 関数が `?T` 結果パラメータを持つ、または自身がブロック match 内にある（そうでないと `l86f91me`） | なし |
| 成功時のアーム | 一度はアームに入る（本体が最後まで進み `nil` にマッチ）、アームには破棄または純粋な処理のみ置くべき | `ok` アームのみ実行 |

選択の順序：

1. **単一文で、失敗したら 0 とみなし、後ろに実行するものがない** → 両者は等価。B を優先：
   インデントが一段少なく、ゼロ値 store も一回少なく、`no fmt` はどちらの形態にも冪等です。
2. **一連の失敗しうる文で一つのエラー処理を共有したい**（ファイル読み込み → 解析 → 書き戻し）
   → A：`?=` を一行ずつ書き、同じ `err ->` アームを共有し、最初の失敗でクリーンアップ・
   アームに停止します。
3. **失敗時に元の値を保持したい／具体的なフォールバック値にしたい／後続の文を通常どおり
   実行させたい** → B（`-> sum`、`-> 0`、`-> it`）。
4. **この値がさらに演算に参加する**（代入右側、フィールド目標、`?=` 右側）→ B：A は文であり値がありません。
5. **要素ごとに処理し、単一の失敗でバッチ全体を壊したくない** → B；**バッチ全体が失敗したら
   中止したい** → A（ループ反復まで停止）。

陥りやすい二点：

- 🔴 **注釈の位置**：`#{overflow=wrap}` は**ブロック内**に、`?=` の行のすぐ上に書く必要が
  あります。ブロック match の外側（`{` の上）に書くと**効果がありません**——実測では
  オーバーフローは相変わらず `err` を返し、`np` は `?=` でゼロにされます。
- 🔴 **アキュムレータに A をそのまま使わない**：`sum ?= 1 / (i - 1)` は失敗した反復で
  **累積済みの `sum` もまとめて `0` に抹消します**（`?=` によるゼロ値書き込み）。
  累積値を保持するには B の `-> sum` を使ってください。

```no
#{fmt-skip}
; ❌ 避免重複分支體
w = tls-c.send(req)
w: {
    nil -> {
        tls-c.close()
        return
    }

        tls-c.close()

```
```

```no
; ✅ 公共邏輯放 -> catch-all
w = tls-c.send(req)
w: {
    ok -> n = it

    -> {
        tls-c.close()
        return
    }
}

; ✅ 反之亦然：簡單分支命名，複雜邏輯放 ->
val: {
    nil -> return

    err -> log(it.msg())

    -> {
        n = it
        total = total + n

```

```no
; 單語句 — 不加大括號
val: {
    ok -> print(it)

    -> print('empty or error')
}

; 多語句 — 必須加大括號
val: {
    ok -> {
        n = it
        total = total + n
    }

    -> {
        log('failed')
        return
    }
}
```

```no
; it 隱式綁定
val: {
    ok -> process(it); it = 解包後的值

    err -> log(it.msg()); it = 結構化錯誤 err.err（非 str）

    -> log('empty'); catch-all，此處為 nil
}
```

```no
#{fmt-skip}
; it 的作用域：巢狀 match 按層還原
; （佔位函數名寫 keep —— `use` 是導入關鍵字，不能當函數名；
;   且裸 `->` 臂在 nil/err 未同時認領時讀 it 是編譯錯誤，故各層都寫 ok ->）
outer: {
    ok -> {
        keep(it)            ; 外層 it
        inner ?T = f(it)
        inner: {
            ok -> keep(it)  ; 內層 it = inner 的解包值
        }
        keep(it)            ; ✅ 內層臂結束後 it 已還原成外層值
    }
}
```

> **注意**：復元は**入れ子の** match でのみ行われます。最外層の match が終了した後も `it` は  
> 最後のアームの値を保持しているため、match の外で `it` を使わないでください。  
> 層をまたいで使う必要がある場合は具名変数（`doc = it`）に保存するか、分解バインディング  
> `ok(v) -> ...` でペイロードを自分の名前にバインドしてください。

> **ベストプラクティス（option アンパックでは `it` を優先）**：マッチされる値が **option `?t`** の場合は、  
> `ok(v) -> ...(v)...` ではなく `ok -> ...(it)...` を優先してください——余分なバインド名を導入しないため、  
> 「異なるアームで同名の変数が codegen の型を混同する」落とし穴を自然に回避できます。  
> **具名バインド** `ok(v) ->` を残さなければならないのは二つの場合だけです：(1) マッチされる値が  
> **ユーザー定義の列挙型バリアント**の場合（例：
> `res { ok(v str) }`、`shape { rect(w, h) }`）——この場合の `it` は**列挙型全体**であり、ペイロードではありません。  
> (2) **入れ子の match の後も**その値を使い続ける場合——内側の match が `it` を再バインドするため、  
> 具名バインドを使うか、先に具名ローカルへコピーしてください。

### 添字書き込みには明示的なアンパックが必要

インデックス読み取りの戻り値は option です（範囲外は `err`、`code.index-out`）。
**添字に直接代入すると範囲外が未チェックの範囲外書き込みになってしまう**ため、これは許可されず、
次の二選一が必要です：

```no
#{fmt-skip}
; ❌ 不允許：a[1] = 2
```
```

```no
; ✅ place-match：自行處理越界臂（it = 元素位置，可讀可寫）
a[1]: {
    ok -> it = 2

    -> _
}

; ✅ 錯誤上拋：所在函式有 option 結果參數時（越界 → 上拋）
a[1] ?= 2
```

- コンパイラが添字の範囲外でないことを証明できる場合（固定長配列 + 定数添字、ループ変数が
  範囲内と証明できる場合など）は**内部で検査を除去して直接代入し、実行時オーバーヘッドはありません**。
  ただし構文上はアンパック形式で書く必要があり、ユーザー側に免除はありません。
- map（`[str]i64` など）は**この規則の対象外です**：`m['b'] = c` と直接書けます。
  place-match も `?=` も不要です。map の添字は**位置ではなくキー**であり、書き込みは
  put/insert（キーがなければ挿入、あれば上書き）で常に定義され、「範囲外書き込み」は存在しません；
  構造体フィールドを基底とする場合（`self.keys[i] = v`）も現時点では対象外です。
- map の**読み取り**側は引き続き option の扱いです（配列/vec/slice の `a[i]` とまったく同じ規則）：
  関数内の `x = m[k]` は `?V` となり、キーが存在しない場合は `nil` です。`m[k]` と `m.get(k)` は同義で、
  `m[k] = v` と `m.put(k, v)` は同義であり、両方の書き方を自由に混ぜられます。
- `m[k] ?= v` は**コンパイルエラー**です（単なる冗長ではありません）：`?=` の ok アームは
  「要素を読み出して**位置**に書き戻す」ですが、map が読み出す `?V` は `get` のコピーにすぎず、
  それに書き戻しても map には反映されません。`m[k] = v` と直接書いてください。
  `m[k]: { ok -> it = v }` のような place-match は引き続き使えます（put と等価）。

### 反復変数も要素の「位置」である

`x <- a`（`a` が `arr` / `vec` / `slice` / 固定長配列）がバインドする `x` は
**要素そのものの位置**であり、各反復で読み込まれるコピーではありません：

- **`x` を読む**と `a[__i]` が再読み込みされます —— 同じ反復内で先に書き込んでから読めば
  新しい値が見え、`x = x + 1` は読み-変更-書き込みです；
- **`x = v` と書く**と `a[__i]` に反映されます；
- match アーム内の `it` は同じ位置の**別名**であり（そのアーム内でのみ有効）、したがって
  `x: { ok -> it = v }` と `a[i]: { ok -> it = v }` は完全に等価です。

```no
; 以下兩段結果相同：a 的每個元素都變成 5
a []i64 = [0, 0, 0]
i <- [0..3): {
    a[i]: {
        ok -> it = 5

        -> _
    }
}

b []i64 = [0, 0, 0]
x <- b: {
    x: {
        ok -> it = 5

        -> _
    }
}
```

- 要素自体が option（`[]?T`）の場合、`it` は**ペイロード**であり、書き戻す際は自動的に `ok` で包み直されます。
- アーム終了後は別名が無効になります。match の後に `it = v` と書いてもコンテナには反映されません。

**位置ではない場合**（書き込みはローカルに留まる）：

- `c <- s`（`str`）の場合、要素はデコードされた**コードポイント**であり、文字列には対応する記憶スロットがありません。
- `k <- m`（map）の場合、添字は**キー**であって位置ではないため、書き込みは表に反映されません。

### `it` は「単一のケースと証明できる」アームでのみ使える

catch-all の `->` アームは、先行する明示アームが引き受けなかったすべてのケースを受け取ります。
残りのケースが**ちょうど一つ**の場合にのみ `it` は単一の明確な意味を持ちます：

```no
; ✅ -> 就是 ok（nil / err 都已被認領）
v: {
    nil -> log('empty')

    err -> log(it.msg())

    -> process(it)
}

; ✅ -> 就是 err（ok / nil 都已被認領）
v: {
    ok -> process(it)

    nil -> log('empty')

    -> log(it.msg())
}
```

```no
#{fmt-skip}
; ❌ -> 可能是 nil 也可能是 err —— 編譯錯誤
v: {
    ok -> process(it)

    -> log(it)
}
```
```

補上 `nil ->` / `err ->`，或改用 `ok ->`，即可通過。enum 與裸 match（`{ cond -> ... }`）  
不在此限：`it` 指的是被匹配的值本身，沒有 nil / err 的可能。

> `err ->` 臂的 `it` **永遠是錯誤值（`err.err`）**，與 option 的元素型別無關——  
> `option { ok(v t), nil, err(e err.err) }`。所以就算匹配的是 `?i64` / `?bool` 這類  
> 純量 option，`err ->` 臂裡的 `it` 也是結構化錯誤：讀訊息用 `msg = it.msg()`，  
> 比對錯誤碼用 `it.is(code.io)`，發生位置在 `it.file` / `it.line` / `it.col`  
> （由編譯器在 `err(...)` 的構造點自動注入）。

```no
; ✅ 組合 option 模式：nil || err -> body
; 當 option 為 nil 或 err 時共用同一個分支
val: {
    nil || err -> {
        cleanup()
        return
    }

    ok -> process(it)
}

; ✅ 也可與 -> catch-all 混用
val: {
    nil || err -> log('failed')

    ok -> process(it)
}
```

### 短絡パイプライン（`->`）

`->` は**左結合の短絡パイプライン演算子**であり、意味は固定で、**外側が代入であるか、match アーム内であるかに影響されません**。
裸文、match アームの単行 body、代入右側の三箇所が同じ lowering を共有します。

パイプライン内のノードは三種類に分かれます：

| ノード                                | パイプライン state への影響                             |
| --------------------------------- | ----------------------------------------- |
| 副作用呼び出し（戻り値なし、`print('A')` など）         | 実行され、**state を変えない**；それまで Ok なら次のノードへ進む        |
| `?T` を返す呼び出し（失敗しうる、`might-fail()` など） | 実行され、**state を上書き**；nil/err になると**後続ノードはすべてスキップ** |
| 末尾の普通の値式                          | state がまだ Ok の場合のみ評価される                        |

**`?T` を返すノードだけがパイプラインを失敗状態に切り替えられます**；`print` のような副作用は決してできません。
そのため「チェーン全体が `print`」の場合は短絡がないように見えますが、実際は失敗を生成できるノードが
ないだけです。

```no
; 沒有可失敗節點 → 全部執行
ok -> print('A') -> print('B')

; might-fail() 回傳 ?T → 失敗時 print('B') 不執行
ok -> print('A') -> might-fail(x) -> print('B')

; 賦值右側：同一套語義
r = print('E') -> might-fail(x) -> 42
```

**境界の明確化：**

1. `->` の意味は一つだけで、裸文と代入式は同じパイプライン lowering を共有し、外側に代入があるかどうかでモードが切り替わることはありません。
2. match アームの**単行 body 内の `->` はパイプラインの継続であり、新しいアームではありません**。
   アームとアームは**改行**で区切られます：

```no
; ✅ 一個臂，body 是管道 → 兩行都印
ok -> print('A') -> print('B')

; ✅ 兩個臂（換行分隔）→ 命中 ok 就不會印 'miss'
v: {
    ok -> print('hit')

    -> print('miss')
}
```

> ⚠️ アームは改行で区切られるため、同じ行に書いた `pat -> A -> B` は**一つのアームのパイプライン**であり、
> 「if A else B」ではありません。if/else が必要な場合はアームを別行に書くか、`{}` で包んだ短絡グループを使ってください。

1. **パイプラインは値を生成できる**：代入右側に書いた場合、パイプラインの結果は**末尾の値ノード**になります（state がまだ Ok の場合のみ評価）。

```no
n = 7
x = 1 > 2 -> 42; 條件不成立 → x 保持原值 7
y = 2 > 1 -> 42; y == 42
s str = 'old'
s = 1 > 2 -> 'new'; 短路 → s 仍是 'old'
r = print('E') -> might-fail(bad) -> 99; 中段失敗 → r 保持原值
```

失敗（条件が成立しない、または `?T` ノードで短絡した）場合、**代入は行われません**：
変数は元の値を保持し、初回宣言の場合はその型のゼロ値になります。これは叙述形式と同じです —— 
`{ 1 > 2 -> x = 42 }` も `x` を変更しません。

値の型はアームの末尾式から推論され（`str` / `i64` / `?T` のいずれも可）、
既存の match による値取得形式 `x = subject: { arms }` と同じ推論を共有します。

### If / Else

if-else グループ（短絡）は**必ず** `{}` で包んでください。最初に一致した条件が勝ち、後続の条件は検査されません。

```no
; 多分支（推薦新式）— 短路 if-else 鏈
{
    a == 1 -> {
        a = 1
        b = 2
    }

    a == 2 || a == 3 -> do-something()

    -> {
        c = 0
    }
}

; 單 if（保留）— 獨立 if，不短路
x == 1 -> do-something()

; 三元表達式 condition ? true-value : false-value
c = flag ? 1 : 2
max = sum > 10 ? sum : 10
```

**重要な規則：**

1. **短絡グループ** — 複数の `cond -> body` を `{}` で包むと if-elif-else チェーンを形成し、最初に一致した分岐だけが実行されます。
2. **独立 if** — 関数本体／ループ本体の中に `cond -> body` を直接書く（`{}` で包まない）のは独立 if であり、隣接する if-then と短絡しません。
   **else が現れたら必ずグループ化が必要** — 改行した `->` フォールバック・アームを `{}` の外に書くのは**コンパイルエラー**です。
   孤立した `cond ->` に `->` を組むと `k3r7mbqd`、その上に兄弟の `cond ->` アームがある場合は
   `m7vq3xrt` が報告されます（メッセージには失われたアーム数が示されます）。
   パーサは改行した `->` を**直近の**裸 if にだけ畳み込み、残りのアームは黙って無効になります——
   字面の読み方と実際にコンパイルされる結果がまったく異なるため、規則として定められています。
   すべてのアームを `{ ... }` の中に入れてください；**else のない孤立した `cond -> body` は裸書きのまま許可されます**。
3. **混在禁止** — `{}` 短絡グループの直接の子ノードはすべて `cond -> body` 分岐でなければならず、普通の文を混ぜることはできません。

```no
#{fmt-skip}
; ❌ 不會短路 — 這些是獨立 if，所有條件都會被檢查
git-dispatch = (cmd str) {
    cmd == 'a' -> {
        fa()
    }
    cmd == 'b' -> {
        fb()
    }
}
```
```

```no
; ✅ 短路 — 用 {} 包裹，第一個匹配勝出
git-dispatch = (cmd str) {
    {
        cmd == 'a' -> {
            fa()
        }

        cmd == 'b' -> {
            fb()
        }

        true -> {
        }
    }
}
```

```no
#{fmt-skip}
; ❌ if/else 寫在短路組外面 — 編譯錯誤
; 換行的 `-> break` 只掛在 `c == 43` 上，命中 `c == 45` 之後仍會被 break 掐斷
;   c == 45 -> {
;       exp-sign = -1
;       i = i + 1
;   }
;   c == 43 -> i = i + 1
;   -> break
```
```

```no
; ✅ 同一份代碼寫成 if 組 — 臂間互斥，`->` 才是真正的兜底臂
{
    c == 45 -> {
        exp-sign = -1
        i = i + 1
    }

    c == 43 -> i = i + 1

    -> break
}
```

```no
#{fmt-skip}
; ❌ match-block 混雜普通語句 → 編譯報錯
{
    cmd == 'a' -> {
        fa()
    }
    print(cmd)
    cmd == 'b' -> {
        fb()
    }
}
```
```

```no
; ✅ 普通語句放到分支 body 內部
{
    cmd == 'a' -> {
        print(cmd)
        fa()
    }

    cmd == 'b' -> {
        fb()
    }

    true -> {
    }
}
```

### 非同期プログラミング：`awy { ... }` コルーチン・グループ + `co`

Nolang に表層の並行構文は一種類だけです：`awy { ... }` コルーチン・グループであり、
グループ内で `co` によってタスクを生成します。`run` キーワードは削除されました
（`run` は現在は普通の識別子です）；`awy <handle>` の待機接頭辞と、文位置の裸ブロックに
よるコルーチン・グループも廃止されました。**グループ外で `co` を書くのはコンパイルエラー**です
（`E_CO_OUTSIDE_GROUP`）。

`co` には二つの形態があり、どちらも**手続き**を開始するだけで、値は生成しません：

```no
; 過程：只寫通道，沒有宣告回傳值
produce = (ch chan[i64], v i64) {
    ch <- v
    ch.close()
}

ch chan[i64] = with-cap(2)
awy {
    co produce(ch, 1)          ; ① 過程 spawn：co f(args)
    co {                       ; ② 閉包 spawn：co { ... }
        ch <- 2
        ch.close()
    }
}
sum = 0
i <- ch: {
    sum = sum + i
}
print(sum.to-str())            ; => 3
```

#### ① 手続き spawn：`co f(args)`

`f` は**戻り値を宣言してはいけません**。spawn の結果には行き先がありません（`co` は値ではないため）、
したがって戻り値を持つ関数が `co` で呼び出されると `c0retval` が報告されます：

```no
worker = (n i64) (r i64) { r = n }   ; 有宣告回傳值
awy { co worker(1) }                  ; ✗ c0retval
```

メソッドが暗黙に返す `self` は戻り値に**含まれません**——これは全メソッドが持つレシーバの出力引数であり、
呼び出しを連鎖させるために存在します。そのため `co obj.flush()` のような書き方は問題ありません：

```no
queue {
    n i64
}
queue.flush = () {          ; 隱式 (self queue)，沒有其它回傳值
    self.n = 0
}
awy { co q.flush() }        ; ✓
```

結果が必要ならチャネルを書きます：手続きが値をチャネルに送って `close()` し、
呼び出し側がグループの外で受け取ります。これはスタイルの提案ではなく一つの規則です——
spawn された呼び出しの結果は、グループが join された後にしか読めず、読む場所は join 地点では
ありません。これが `chan` が存在するまさにその場面です。

#### ② クロージャ spawn：`co { ... }`

`co { ... }` は一連の手続きをその場でコルーチンに渡して実行します。ブロック内の
**自由変数は値で捕捉**されます（spawn 時点のスナップショットであり、通常の spawn における
実引数の深いコピーと同じ意味です）：

```no
seed = 33
ch chan[i64] = with-cap(1)
awy {
    co {
        ch <- seed
        ch.close()
    }
}
r = 0
<- ch: { ok -> r = it }
print(r.to-str())          ; => 33
```

#### `co` は値ではない：単独の文にしかなれない

`co` は void を生成するため、一つの文を丸ごと占める必要があります。代入右側、実引数位置、
戻り値位置はいずれも `E_CO_NOT_STATEMENT`（`c0nostmt`）となります：

```no
r = co produce(ch, 1)      ; ✗ c0nostmt
print(co produce(ch, 1))   ; ✗ c0nostmt
```

さらに `co` の後ろに置けるのは「呼び出し」か「ブロック」だけで、それ以外の形は
`E_CO_NOT_CALL`（`c0notcal`）となります。

#### 無色 async：自動単態化

`co` は無色（colorless）の構文です：色付けされていない関数名 `produce` を書くと、
コンパイラが自動的に `produce-async` バリアントを単態化し、内部では色付けされたスタックレス
コルーチンとして実行します。アプリケーションコードで `-async` 接尾辞を手書きしないでください。

規則：

- **単態化**：`co produce(ch, 1)` は自動的に `produce-async` を生成します（`produce` の本体を
  コピーして改名）。`produce` が同期呼び出しもされる場合は、両者が共存します。
- **伝播性**：ある手続きの内部にも `awy { co child(n) }` がある場合、その手続き自体も `-async` に
  単態化され、非同期の色付けが呼び出しチェーンを上へ伝播します。
- **バリア**：グループ内の `co` でない文（普通の代入、`print`、ループ、`if`、**チャネル読み取り**…）は、
  まず飛行中のすべてのタスクを待ちます。グループ内のデータ依存は「先にチャネルを読み、その値を
  使って spawn する」と書きます——チャネル読み取り自体がバリアであり、暗黙の変数依存より読みやすいからです。
- **関数本体はコルーチン・グループではない**：グループを導入するのは `awy { ... }` だけです。
  関数本体、`if` 分岐、ループ本体内の `co` はすべて拒否されます。
- **結果を捨てても待つ**：`awy { co side(5) }` でも spawn + await が行われ、未待機のタスクは残りません。

#### スケジューリング・モデル：真のサスペンド

`-async` クローンは「最後まで一気に走ってから報告する」ものではなく、
**再開可能なステートマシン**です：ローカル変数は `%task.frame` にぶら下がるヒープ・フレームへ
移され、各サスペンド点はそのブロックの終端記号になります（状態番号をフレームに書いて return し、
関数入口は状態比較のチェーン `__state == k` ⇒ 第 k 復帰点へ直接ジャンプ、となります）。

したがって三箇所で**ブロックではなくサスペンド**します：

| サスペンド点 | 復帰条件 |
|---|---|
| `async-yield()` | 自分自身をキューの末尾に再投入し、先頭に回ってくるのを待つ |
| 未完了の子タスクに対する `awy` | 子タスク完了時に起床（ `%task.waiters` チェーンに登録され、一度の起床でチェーン全体を起床） |
| 空のチャネル受信（`v <- ch:` / `<- ch:`） | `send` / `close` が待機チェーン全体を外して順に再投入する |

スケジューリングは単一スレッドの協調型で、準備キューは FIFO です。したがって**順序は完全に
アサート可能**で、sleep は不要です：二つのタスクが各一回ずつ譲れば必ず `a1 b1 a2 b2` となり
（`tests/coro-yield.no` がイベント・コードを固定しています）。起床した待機者が**値を手に入れた
ことにはなりません**——一回の `send` は要素を一つ追加するだけですが、複数の待機者を起床させる
ことがあるため、チャネルの復帰点は park ブロック自体であり、そこで読み取り可能性を再判定して
取るか待ち続けるかを決めます。

> デッドロックは検出可能です：準備キューが空なのに目標タスクが未完了の場合 ⇒ 実行時に
> `nolang: deadlock: …` を stderr に印字して abort します。これは「誰も送っていないゼロ値を返す」
> より遥かに誠実です。

> **低レベル lowering**（ユーザー構文ではありません）：各 `co` は `OpRun` になり、グループ末尾に
> 各タスクの `OpAwait` が挿入されます；`KRun` / `KAwait` / `OpRun` / `OpAwait` は HIR/MIR にのみ
> 存在します。コルーチン変換は `Analyze` の後に MIR の `PlanCoroutines` が行います
> （`src/mir/coro.go`）。

キャンセル：`cancelled()` はコルーチン関数内で協調的な自己検査に使えます；`cancel(h)` は
低レベルのハンドル操作であり、新しい構文は task ハンドルを公開しないため、
アプリケーションコードでは使いません。

### 多重代入

関数は複数の値を返せ、呼び出し時に多重代入で受け取ります：

```no
; 函數定義返回多個結果參數
swap = (a i64, b i64) (x i64, y i64) {
    x = b
    y = a
}

; 多重賦值
a, b = swap(5, 3)

; 使用 _ 忽略不需要的返回值（占位變數）
_, b = swap(5, 3); 只取第二個值，忽略第一個
a, _ = swap(5, 3); 只取第一個值，忽略第二個
_, _ = swap(5, 3); 忽略全部返回值（呼叫僅為副作用）

; 也支援作為 match arm 的 body
val: {
    ok -> {
        a, b = parse-pair(it)
    }

    -> return
}
```

## 演算子オーバーロード

左オペランドの静的型が特定の `_op` メソッドを定義している場合、コンパイラは lowering 段階で
中置演算 `a op b` をメソッド呼び出し `a._op(b)` へ自動書き換えします。オーバーロード集合は
閉じた五つの対称二項算術演算子です：

| 演算子 | オーバーロード・メソッド |
|--------|----------|
| `+` | `_add` |
| `-` | `_sub` |
| `*` | `_mul` |
| `/` | `_div` |
| `%` | `_mod` |

```no
big {
    v i64
}

; 回傳型別書寫 ?big，編譯器視作純 payload big
big._add = (b big) (c ?big) {
    c = big {
        v: .v + b.v
    }
}

f = (a big, b big) (out big) {
    r big = a + b; 編譯器改寫為 a._add(b)
    out = r
}
```

**型の約束**：演算子オーバーロード・メソッドの結果引数は**`?T` と書きますが、実効型は純粋な
ペイロード `T`** です——コンパイラは option の包装／アンパックを行わず、メソッド本体では `c` に
直接 `T` 値を代入し、呼び出し側も `T` を受け取ります。ゼロ除算などのエラーは組み込み数値型と
同様に実行時に直接トラップし、option は生成されません。

**意味の要点**：

- 左オペランドの静的型が対応する `_op` メソッドを定義している場合にのみ書き換えられます；
  組み込み数値型（i64、f64 など）は引き続き組み込み算術を使います。
- 明示的なメソッド呼び出し `a._add(b)` と `a + b` は完全に等価です。
- 左側に入れ子になった連鎖演算は層ごとに書き換えられます：`a + b + c` → `(a._add(b))._add(c)`；
  中間結果の型は依然として `T` であり、演算やメソッド呼び出しに引き続き参加できます。
- 標準ライブラリの `bigint` はこの機構で `+ - * / %` をサポートしています
  （「標準ライブラリ > その他のモジュール」の bigint 節を参照）。

## 配列とスライス

コンテナはデータのコピーを格納し、元の変数とコンテナは独立しているため、
垂れ下がり参照（dangling reference）を排除します。

**固定長配列 arr：**

```no
; 使用定長数组
a [3] = [1, 2, 3]; 長さ 3 の固定長配列 i64
a [3]u16 = [1, 2, 3]; 型を明示した固定長配列

a[nil]
u16 = [1, 2, 3]; 自動推斷長度（指定類型）
a[nil] = [1, 2, 3]; 自動推斷長度（i64）
```

**可変長配列 vec：**

```no
v = [1, 2, 3]; 變長數組 i64
bs = [0x11, 0x22, 0x33]
v []u8 = [1, 2, 3]; 型を明示した可変長配列

; 預分配（避免反覆擴容）
v = with-cap(100); len=0, cap=100（需 push 後索引）
v = with-len(100); len=100, cap=100（可直接索引）
v = with-cap-len(200, 100); len=100, cap=200（預留擴容空間）
```

**スライス slice（ビュー、独立型ではない）：**

スライスは元データに対する**ビュー（view）**であり、データをコピーせず、新しい独立型も生成しません。
スライスの内部は元バッファへのポインタ、長さ、容量だけを記録するため：

- スライスを通じて要素を変更すると元データに影響し、その逆も同様です
- スライスはデータを所有せず、元変数が解放されるとスライスは無効になります
- スライスの型は元の型で決まり、メソッドがそのまま使えるため、「継承」機構は不要です

```no
; 支持arr/vec/str
; 支持範圍 和for <- 的表示一致
nums [5]u8 = [0, 1, 2, 3, 4]

nums[..]; [0 1 2 3 4]   完全無界，等同整個切片
nums[1..]; [1 2 3 4]     無上限，從索引 1 到末尾
nums[..4]; [0 1 2 3 4]   無下限，從開頭到索引 4
nums[2..3]; [2 3]        有界，兩端都包含
nums[1..3]; [1 2 3]      有界，兩端都包含
nums[1..3); [1 2]        左閉右開
nums(1..3); [2]          兩端開區間

; 字符串（切片結果型別為 str 視圖，共享底層記憶體；下標為碼點位置，與 s[i] 一致）
s = 'abc'
s[1..]; 'bc'
s[1..s.len()); 'bc'
b str = s[0..1]; 切片結果已是 str，可直接賦值給 str 變數
```

> スライス構文は match/range-for と同じ 16 種類の範囲の組み合わせをサポートします。
> スライス文脈では、無界範囲はスライスの長さを基準にします：`[..]` はスライス全体、`[a..]` は
> インデックス a から末尾、`[..b]` は先頭からインデックス b までを表します。

**スライスの型とメソッド：**

スライスは新しい独立型を生成せず、元の型のビュー（開始ポインタと長さを調整したもの）にすぎません。
したがって元の型のメソッドがそのまま使えます：

| 元の型           | スライス・ビュー型       | 使えるメソッド                                                                             |
| -------------- | ------------ | -------------------------------------------------------------------------------- |
| `arr` (`[n]t`) | `[]t<range>` | `[]t` のすべてのメソッド（`len`、`push`、`pop`、`contains`、`reverse`、`clone`、`fill`、`to-arr` など） |
| `vec` (`[]t`)  | `[]<range>`  | 同上                                                                               |
| `str`          | `str<range>` | `str` のすべてのメソッド（`to-upper`、`to-lower`、`index`、`contains`、`slice`、`copy`、`fill` など）  |

```no
; arr 切片 → vec 視圖，共享 arr 的底層記憶體
a [5]u8 = [0, 1, 2, 3, 4]
s = a[1..4]; s 是 []u8 視圖，指向 a 的記憶體
n = s.len(); slice.len()

; vec 切片 → vec 視圖，共享 vec 的底層記憶體
v = [10, 20, 30, 40, 50]
s = v[2..]; s 是 []i64 視圖
s.reverse(s.len()); slice.reverse

; str 切片 → str 視圖，共享 str 的底層記憶體
s = 'Hello World'
sub = s[6..]; sub 是 'World' 視圖
upper = sub.to-upper(); str.to-upper

; 通過切片修改元素會影響原始資料
data = [10, 20, 30, 40, 50]
view = data[1..4]; view = [20, 30, 40]
view[0] = 99; 修改 view 的元素
; data[1] 現在也是 99，因為 view 共享 data 的記憶體
```

### インデックス

```no
; 字符串索引 → 回傳 ?char（Unicode 碼點，不是字節）
c char = s[i]; 顯式 plain 型別把結果拉回 char（見〈安全索引〉）

; arr、vec獲取元素
arr[i]; → ?elem
vec[i]; → ?elem

; map 獲取 value
map[str]
```

> **インデックス読み取りの結果は常に `?T` です**：`arr[i]` / `vec[i]` / 固定長配列 / `slice` → `?elem`、  
> `str` / `txt` のインデックス `s[i]` → `?char`（D6、整数算術と同じ統一規則）。  
> したがって `str[i]` の**推論型は `?char`** です。plain `char` を取り戻すには二通りあります：  
> バインディングに明示的な plain 型を書く（`c char = s[i]`、lower 時に短絡合成されて plain 値を読み戻す）、  
> または match / `?=` でアンパックする。  
> `str[a..b]` のスライスは引き続き `str` を返します（コードポイント意味のビュー、基盤となるメモリを共有）。  
> `char` は**`str` へ暗黙変換できます**（単一文字列として符号化される）ため、次の書き方はすべて合法で、  
> `char.to-str()` を手動で呼ぶ必要はありません：

```no
s = 'héllo'
c char = s[1]; 'é'（char，其碼點為 233）
a str = s[1]; 'é'（char → str 隱式轉換）
b str = s[0..1]; 'hé'（切片結果本身已是 str）
msg = 'first: ' - s[0]; char 參與拼接（-）時隱式轉為 str
ok = s[0] == 'h'; char 與 str 比較時隱式轉為 str
```

### 安全なインデックス（Safe Indexing）

`arr` / `vec` / `slice`（`[]T`）/ 固定長配列 / `str` / `txt` に対するインデックス `v[i]` の**結果は常に `?T`** です：
範囲外の場合は `err` を返し（`err('index out of range', code.index-out)`、添字のあるソース位置を付与）、
範囲内なら `ok(値)` を返し、決して abort しません（runtime error: index out of bounds）。
これは整数 `+ - * / %` の注釈なしオーバーフローと同じ規則です（〈整数演算のオーバーフロー〉を参照）。

`?T` を使う方法は三通りだけです（**`#{index-out=DEF}` 注釈は D11 で廃止・削除されました**。
残存注釈はコンパイルエラーです；また「明示的な plain 型で plain に戻す」近道もなく、
`v i64 = a[i]` も明示的に消費する必要があります）：

**1. 読み取り —— match によるアンパック**

値 match で直接値を取り、または文 match で `ok` アーム内で代入します。`-> _` は「破棄」アームであり、
値コンテキストでは**要素型のゼロ値**を生成します（i64→0、str→''、byte→0、コンテナ→空コンテナ）。

```no
; 值 match
x = state[5]: {
    ok -> it

    -> _
}

; 陳述 match
state[5]: {
    ok -> x = it

    -> _
}
```

**2. 書き込み —— place-match**

`it` は `ok` アーム内で**要素の位置**であり（読み書き可能）、値のコピーではありません。

```no
state[5]: {
    ok -> it = x

    -> _
}
```

> **map の例外：** `m['k'] = 1` への書き込みは**アンパック不要**です——map の添字はキーであり、
> 書き込みは put/insert で、キーがなければ挿入、あれば上書きされ、常に定義され、「範囲外書き込み」を
> 守る必要がありません。ただし **map の読み取り `m['k']` は依然として `?V` を返すため、アンパックが必要**です。
> `m[k] ?= v` は**コンパイルエラー**です（`get` が読み出した `?V` はコピーにすぎず、それに書き戻しても
> map には戻りません）。`m[k] = v` と直接書いてください。

**3. 省略形 `?=` —— エラーの上位伝播**

`x ?= state[5]`（読み）、`state[5] ?= x`（書き）は上記二種類の match の省略形であり、
失敗時に option 全体を上位へ伝播させます。これは**次の二つの情形のいずれか**で合法です：

- 所在する関数が `?T` 結果パラメータを持つ —— 失敗時に結果パラメータへ書き込んで早期 `return` する；
- 文が**文レベルのブロック match** `{ ... }: { ... }` の本体内にある —— 最も近いブロック match が捕捉し、
  本体が停止して arms が一度だけ実行され、関数に `?T` 結果パラメータは**不要**です。

どちらでもない場合はコンパイルエラーです。したがって「戻り値が option でないが省略形を使いたい」場合の
標準的なフォールバックは、関数本体をブロック match で包むことです：

```no
handle = (x i64) {
    {
        y ?= x + 1
        print(1)
    }: {
        err -> _

        -> _
    }
}
```

**入れ子の読み取り**：内側の match は `it` を再バインドするため、内側では具名バインド
`ok(it1) -> it1` を使います。ユーザーが与えた正確な形（値 match を place-match の `it = ...` 右側に
直接書く形）は 2026-11-06 以降**正しくコンテナへ書き戻されます**：コンパイラは lowering 時にその
値 match を合成一時変数へ昇格させてから `it` を再バインドします。回帰は `tests/match.no` の
`place-write-value-match` 節を参照。**推奨の直接書き方**は、値 match の結果を最終的に使うその名前へ
直接バインドし、一度きりの一時変数に入れてからコピーしないことです。

```no
#{fmt-skip}
; ✅ 直接綁定目標變數
at = argt[i]: {
    ok -> it

    -> _
}
s.farg.push(at)

; ❌ 不要為單次使用引入一次性暫存
arg-at = argt[i]: { ok -> it  -> _ }
at = arg-at
s.farg.push(at)
```

「値 match をアーム外の具名一時変数へ引き上げ、アーム内で `it = arg-at` する」のは
**直接書き方と等価ではありません**。自由に交換できる整形の選択肢ではないのです：評価タイミングが
異なります（アーム外へ引き上げると、外側の `nil` / `err` / catch-all も先に一度読みます）；
`it` はアーム内でのみ有効で要素位置を指すため、コピー戻しはアーム内に留める必要があります；
具名一時変数は新たなバインディングであり、独自の move／所有権とスコープ退出時の破棄を持ちます；
さらに入れ子では内側が具名バインド `ok(it1) -> it1` を使わなければならず、外側の
`ok -> it` をそのまま使えません。同じ値を複数の箇所で本当に再利用する場合にだけ引き上げ、
値の用途が分かる変数名を使ってください。

#### `?=` とブロック match で残りの一度きり一時変数を片付ける

上記は「単一回使用なら直接バインド」でした。さらに一歩進めて：安全なインデックスは `?T` を返すため、
**関数の結果パラメータ自体が `?T` なら、値 match すら書く必要がなく、`?=` 一行で直接上位伝播できます**：

```no
#{fmt-skip}
; ✅ 函式有 ?T 結果參數：無暫存、無 match
at ?= argt[i]
s.farg.push(at)
```

**関数の結果が option でない場合**（最も一般的：戻り値のない補助関数、またはコンテナへ書き戻すだけの場合）は、
この「try に似た」書き方でその文を包みます：

```no
#{fmt-skip}
handle = (x i64) {
    {
        y ?= x + 1
        print(y)
    }: {
        err -> _

        -> _
    }
    print('continues afterwards')
}
```

⚠️ **これは新しい `try` 構文ではなく、言語に `try` キーワードもありません。**
これは単なる**文レベルのブロック match**（`{ ... }: { ... }`）であり、主語は三 state の `?T` です；
`?=` は失敗を**最も近い**ブロック match へ伝播させます
（詳細は〈`?=` によるエラー上位伝播〉と〈Match 主語の三つの形態〉を参照）。
失敗時はブロック本体の残りの文——後続ループ反復を含む——がすべてスキップされ、アームは一度だけ実行され、
その後**ブロックの次のコードへ処理が進みます**。関数 `return` ではありません。
`err -> _` はエラーを破棄し、`-> _` は成功結果をフォールバック破棄します；
エラーを処理するには `err -> print(it.msg())` と書けます。

⚠️ **意味の差異をはっきりさせておきます**（実測、直感に頼らない）：`?=` が失敗すると**目標にもゼロ値が
書き込まれます**——`i64` は `0`、`str` は `''`、`out[1]` は `0` です。一方、値位置 match の
フォールバック・アーム `-> _` は**目標に書き込みません**：目標が**新規宣言**なら元々ゼロ初期化なので
見た目は同じですが、目標が**すでに値を持つ**場合は両者が分岐します（`?=` はゼロにし、`-> _` は元の値を
保持し、ゼロにするには `-> 0` と書く必要があります）。もう一つの差異は制御フローです：`?=` は
**ブロック本体の中でそれ以降の文をスキップします**（`?T` 関数では早期 `return`、ブロック match では
直接アームへ飛びます）。

つまり：**ブロック本体にこの一文しかなく、失敗前の古い値に意味がない場合**は、フォールバック・アームを
`-> 0` と書くだけで完全に等価です（これはまさに本リポジトリのバッチ書き換えの形であり、
一時変数の多くは新規宣言でした）；しかし本体の `?=` の後ろに別の文（ループカウンタ、
後続の代入）がある場合や、目標の古い値に意味がある場合は分岐するため、それらのサイトを機械的に
置き換えることはできません。完全な取捨表は〈ブロック match と値位置 match の取捨選択〉を参照。

もう一つ陥りやすい点：**成功時にもアームが一度実行される**ことです。catch-all が成功値を受け取り
（`-> print('x')` は印字します）。したがってアームには破棄か純粋な処理だけを置くべきです；
`err -> _` / `-> _` のような形には副作用がありません。

ここから一度きり一時変数を片付ける順序が得られます：

1. 値が同じ箇所で一度だけ使われる → 最終的な目標名へ直接バインド（上記参照）。
2. 関数が `?T` 結果パラメータを持つ → `TARGET ?= EXPR`、一時変数不要。
3. そうでない → その文をブロック match に入れて `TARGET ?= EXPR` と書く；place-match による
   書き戻し（`SUBJ: { ok -> it = temp  -> _ }`）も `SUBJ ?= EXPR` へ直接縮められます。
4. 同じ値を複数の箇所で本当に再利用する場合にだけ具名一時変数を残し、意味のある変数名を使う。

二つの境界：`?=` は `?T` 結果パラメータもブロック match 本体もない場合はコンパイルエラーであり
（`l86f91me`）、**型宣言付きの LHS に `?=` は組めません**（`ai i64 ?= a[i]` は解析エラー
`yh8904fm`、`expected assignment operator`）。`byte → i64` のような明示的な昇格が必要なら、
型宣言付きの直接値 match に書き換えます：

```no
#{fmt-skip}
ai i64 = a[i]: {
    ok -> it

    -> _
}
```

> **適用範囲：** `arr` / `vec` / `slice` / 固定長配列 / `str` / `txt` はすべて有効です；
> **直接変数を基底とする**インデックス（`v[i]`）だけが安全な形式へ書き換えられ、
> `receiver.field[i]` は従来の bounds-check パスを通ります。
> 比較オペランド内のインデックス読み取りは payload を比較します（`a[i] == 5`）。
> `{tag, payload}` 全体ではありません。

> ⛔ **ハードエラー：** `?T` を普通の値として使う（例：`crc = crc ^ s[i]`、`f(s[i])`、
> `v i64 = a[i]`）と `no build` がブロックされ、コンパイラが match または `?=` の使用を提案します
> （`?T` 結果パラメータがない場合はブロック match で包みます）。
> 既存コーパスは `no fmt --fix=index-out` で一度に移行済みで、このツールは D11 とともに退役しました。

> **中核の保証：** 範囲外で黙ってクラッシュすることは決してありません——match で処理されるか、
> `?=` で上位伝播されるかのいずれかです。

> **比較オペランド内のインデックス読み取り**にも安全なインデックスが適用されます：
> `a[i] == 5` は payload を比較します（`?T == 5` と同じ規則）、
> `{tag, payload}` 全体を比較するのではありません。範囲外では `err`（`code.index-out`）が読み出され、
> どんな値と比較しても**偽**となり（`a[i] == 0` も `a[i] == 5` も偽）、範囲外メモリを読むことは**ありません**。
> `s[0] == 'a'` も同様です：コードポイントと単一文字列を比較する際は `char → str` 暗黙変換を通ります。

> **入れ子の添字** `a[i][j]`：**二層とも安全なインデックス**です。外側の `a[i]` が先に境界検査と
> 存在判定を行い、存在する場合に限って `[j]` を取ります；どちらかの層で範囲外なら、式全体が `err` です。
> したがって `a[oob][0] == 'c'` は偽となり、abort しません。

> **コンテナ比較** `[]T == []T`（および `[N]T == [N]T`）は**構造比較**です：まず長さを比べ、次に
> 要素ごとに比べます。要素自体がコンテナ（`[][]i64`）なら層ごとに再帰し、要素が `str` なら
> data ポインタではなく**内容**を比べます。順序比較（`<` / `<=` / `>` / `>=`）はコンテナに対して
> 定義されておらず、`==` / `!=` のみをサポートします。

> **`nil` と比較できるのは option だけです**：`?T == nil` / `?T != nil` は合法ですが、
> option でない `T == nil`（`str`、`[]i64`、`[N]T`、`txt`、`i64`、構造体…）は**コンパイルエラー**です
> （`q4nilcmp`）。理由は潔癖さではありません：`str == nil` は常に false で（ `%str-long` 構造体と 0 を比較）、
> `[]i64 == nil` は整数比較パスに落ちて不正な LLVM（`icmp eq i64 %vec, i64`）を生成し、
> どちらも黙って間違った答えを出します。「値がないかもしれない」を表すには、型を `?T` と宣言してから
> `nil` と比較してください。

## メソッド

メソッドは型に対して定義され、`.` を使ってレシーバ（receiver）を参照します。

### 構文

```no
#{fmt-skip}
type.method-name = (params) (results) {
    ; . 是接收者
}
```

### 規則

1. メソッド名は `type.method` 形式を使い、type は定義済みの型でなければなりません。
2. レシーバは明示的に宣言する必要はなく、メソッド体内で `.` を使って参照します。
3. 呼び出しには `receiver.method(args)` 構文を使います。
4. 戻り値は普通の関数と同様に第二組の括弧に置きます。
5. **構文糖の脱糖**：`type.method = (inputs) (rest-outputs...) {}` は普通の関数  
   `method = (inputs) (self type, rest-outputs...) {}` と等価です。`instance.method(args)` を  
   呼び出すと、instance が出力リストの第一引数 `self` にバインドされ、関数体内の `.` は出力領域の `self` を指し、  
   関数が `self` に書き込むと元のインスタンスが直接変更されます。出力リストの `self` 以外の残りの出力は、  
   オプションの分解代入で受け取るか、そのまま破棄できます。

### 例

```no
; str 方法
str.to-upper = () (out str) {
    n = .len-bytes()
    b []byte = with-cap-len(n, n)
    i <- [0..n): {
        c ?byte = .byte(i)
        v = c: {
            ok -> it

            nil -> 0

            err -> 0
        }
        {
            v >= 97 && v <= 122 -> b[i] = v - 32

            -> b[i] = v
        }
    }
    out = b.to-bytes-str()
}

; char 方法
char.is-digit = () (result bool) {
    result = false
    . >= 48 && . <= 57 -> result = true
}

; struct 方法
user {
    name str
    age i64
}

user.greet = () {
    print('Hello, ' - .name)
}

; 調用
s = 'hello'
u = s.to-upper(); receiver.method()
c char = 5
d = c.is-digit(); receiver.method()
u = user {
    name: 'Alice'
    age: 30
}
u.greet()
```

### インターフェースの合併

インターフェースは他のインターフェースのメソッドを「合併」できます。親インターフェース名はインターフェース本体内に**1行に1つ**ずつ記述し（モジュール接頭辞を付けてもよい）、カンマも括弧も付けません：

```no
json {
    to-json()
}
noml {
    to-noml()
}

serialize {
    json
    noml
}

; 傳遞合併：roundtrip 同時獲得 serialize、json、noml 的全部方法
roundtrip {
    serialize
    roundtrip-json()
}
```

規則：

- **再帰的な合併**：合併は推移的です——`roundtrip` が `serialize` を合併し、`serialize` がさらに `json` / `noml` を合併する場合、`roundtrip` は3つすべてのインターフェースのメソッドを持ちます。
- **1行に1つ、カンマは不可**：`serialize { json, noml }` は C スタイルの列挙型（`color { red, green }`）と同形なので、引き続き列挙型として解析され、インターフェースの合併とは見なされません。
- **同名のメソッド**：シグネチャが同じ（引数と戻り値の型が一致し、レシーバー名は異なってもよい）⇒ 重複を除いて1つだけ保持；シグネチャが異なる ⇒ 診断エラー。
- **実装側**：型は実装宣言を書くだけでよく（前置リスト `user serialize { name str }`）、親インターフェースのメソッドも実装済みと見なされ、シグネチャ検査は親インターフェースを通して行われます。
- **`no fmt`**：古い「前置リスト」の書き方（`serialize json, noml { }`）も引き続き解析できますが、`no fmt` は本体形式に書き換え、`no vet` はこれに対して WARNING を出します。

診断（`no vet` とエディターの診断は同一ソース、TraceID `ifmrg001`）：

| 状況 | メッセージ |
| --- | --- |
| 親インターフェースが未宣言 | `interface 'serialize': unknown parent interface 'noml'` |
| 循環合併 | `interface 'a': merge cycle a -> b -> a` |
| 同名でシグネチャが異なる | `interface 'serialize': merged method 'to-str' has conflicting signatures ('json.to-str', 'noml.to-str')` |

> `serialize = json \| noml` のような書き方は**共用体型**（union type）の構文であり、インターフェースの合併とは無関係です。インターフェースの合併は「型がどのメソッドを持たなければならないか」にだけ影響します。

### タグ付き列挙型（ペイロード付き）

バリアントは名前付きのペイロード・フィールドを持てます。括弧形式 `變體(欄位 型別)` で記述し、ペイロードのないバリアントは裸の名前で記述します。  
1つのバリアントは**複数の**フィールドを持てます（複数フィールドのペイロードはヒープ上で合成 struct として表現されます）：

```no
#{fmt-skip}
; 標籤列舉：變體可帶載荷，tag 依聲明順序為 0,1,2...
result {
    ok(v t),
    nil,
    err(e str),
}

; 有值：載荷欄位 v，型別 t
; 空值：無載荷
; 錯誤：載荷欄位 e，型別 str（用戶自定義枚舉，與內建 option 無關）

shape {
    circle(r f64),
    rect(w f64, h f64),
    dot,
}
; 單欄位
; 多欄位
; 無載荷
```
```

マッチ時はバリアント名をアームのパターンとして使用します。ペイロード付きのバリアントはペイロードを分解して束縛できます（複数フィールドは位置順に1対1で束縛されます）：

```no
r result = ok(42)
r: {
    ok(v) -> print(v); 把 ok 的載荷綁定到 v

    nil -> print('empty')

    err(e) -> print(e)
}

s shape = rect(3.0, 4.0)
s: {
    circle(r) -> print(r); 綁定單欄位

    rect(w, h) -> print(w * h); 按位置綁定多欄位

    dot -> print('dot')
}
```

バリアントは**式の位置**で直接構築でき、関数の引数や他のバリアントのペイロードとして使えます：

```no
x f64 = perimeter(rect(3.0, 4.0)); 內聯建構並傳參
o outer = wrap(a(5)); 枚舉載荷本身是另一個枚舉
```

> **名前空間と裸名の解決**：コンパイラは内部でバリアントを「完全修飾名」として登録します（`模組.枚舉.變體`、  
> 例：`option.option.ok`、`some-mod.my-result.ok`）。異なる列挙型の同名バリアントは互いに衝突しません。  
> ユーザーは裸名（`ok`、`rect`）だけを書き、コンパイラが**マッチ／構築される変数の静的型に基づいて**  
> 完全な名前を自動補完します。そのため、2つの列挙型がともに `ok` バリアントを持ち、tag の順序が異なっていても正しく区別できます。
>
> 旧形式の空白区切り型 `ok t` も書けます。これは `ok(v t)` と等価です（フィールド名を省略）。  
> タグ付き列挙型のバリアント名はコンパイラの列挙バリアント表に登録され、マッチと網羅性チェックに使用されます。

### 組み込みタグ付き列挙型（`#{#buildin}`）

タグ付き列挙型の前に `#{buildin}` を付けると、それが**組み込み列挙型**であることを示します。バリアント（名前、順序、ペイロード型）は  
マッチと網羅性チェックに使用されますが、基盤となる表現と構築は runtime/builtin が提供し、**ユーザーから見える  
struct/union は生成されません**。`?t` option もこの方法で宣言されています：

```no
; src/std/global.no
#{buildin}
option {
    ok(v t),
    nil,
    err(e err.err),
}
```

`option` の tag は順に `0=ok`、`1=nil`、`2=err` で、組み込み option の表現と一致します。ユーザーは  
option を自分で宣言する必要はありません。ここでの `#{buildin}` により、組み込み option のバリアントの出所が1つに統一されます（「NULL 許容型（option）」を参照）。

### 列挙型のアノテーションとメモリレイアウト

列挙型は `#{...}` アノテーションをサポートします。位置は他の対象と同じです（〈アノテーションの位置〉を参照）：**上**（独立した行）または  
**後**（同じ行の末尾に続けて）。対象の**前方の同じ行**に書くのはコンパイルエラーです。

アノテーションは**2か所**に置けます：

1. **enum 全体の上方** —— enum 定義自体に作用します（`#{buildin}`、`#{inline=true}` など）。
2. **個々のメンバーの上方または同行末尾** —— そのメンバーに作用します（C スタイル列挙型の「値」とタグ付き列挙型の「バリアント」のどちらも可）。

```no
; ① 整個 enum：獨立成行置於 enum 上方
#{inline=true}
box {
    full(v i64) #{doc='有值'},
    empty #{doc='空值'},
}

; ② 單個變體：獨立成行置於變體上方

; ② 單個變體：同一行尾隨

; `#{inline=false}`：明確寫出「不用 inline 佈局」
#{inline=false}
plain {
    a,
    b,
}

color {
    red #{deprecated},
    green #{deprecated},
    blue,
}
; C 風格枚舉的單個值同樣支援這兩種寫法
```

**アノテーションは enum の構造を変更しません**：バリアント名、宣言順序（tag）、ペイロードのフィールドと型はアノテーションの影響を受けず、  
マッチと網羅性チェックも完全に変わりません。アノテーションは定義に付加される**メタデータ**にすぎません。

#### メモリレイアウト（スタック形式）

タグ付き列挙型はメモリ上で**スタック形式のレイアウト**（inline stack form）を採用します——値で格納される小さなオブジェクトで、ペイロードはヒープに散らばりません：

```llvm
%tenum_<name> = type { iN tag, [K x i64] payload }   ; 一般情形
%tenum_<name> = type { iN tag }                      ; 所有變體皆無載荷
```

- `tag` の幅は**バリアントの個数**に応じて変化し、完全な `u8/u16/u32/u64` のいずれかです：
  `<= 256` → `i8`、`<= 65536` → `i16`、`< 2^32` → `i32`、それ以外は `i64`。判別値は宣言順に `0, 1, 2...` を取ります。
- `payload` は**すべてのバリアントが共有する** union です（各バリアントが自分のフィールドを同じ記憶領域に書き込みます）。`K` は**最も幅の広いバリアント**が  
  必要とする8バイト語の数で、**すべてのバリアントの合計ではありません**。最小値は1です。
- バリアント内部ではフィールドが**自然アラインメント**で配置されるため、フィールドのオフセットが8の倍数とは限りません（`(a char, b char, c char)`  
  のオフセットは 0 / 4 / 8）。読み書きは常に**バイトオフセット**でアドレス指定され（`bitcast` で `i8*` にしてから `getelementptr`）、  
  そのため「書き込んだオフセット」と「読み出したオフセット」は同じレイアウト表によって決定されます。

サイズは `8 + 8K` です（`tag` は配列の8バイトアラインメントに合わせて完全な語にパディングされます）。ペイロードのない列挙型だけが純粋なタグサイズになります：

| 情形 | `K` | サイズ |
| ---------------------------------------------- | ----------------- | ---------- |
| すべてのバリアントがペイロードなし | —（payload フィールドなし） | **1バイト**（`{ i8 }`；バリアント > 256 の場合は 2 / 4 / 8） |
| 最も幅の広いバリアントが `i64` / `i32` / `f64` / ポインタ | 1 | 16バイト |
| 最も幅の広いバリアントが `char`（4バイト）/ `bool`（1バイト） | 1 | 16バイト |
| 最も幅の広いバリアントが `(a char, b char, c char)`（12バイト） | 2 | 24バイト |
| 最も幅の広いバリアントが `str` / `vec` / `[]T`（16バイトのデスクリプタ） | 2 | 24バイト |
| 最も幅の広いバリアントが構造体 `T` | `ceil(sizeof(T) / 8)` | `8 + 8K` |

つまり、**デフォルトは16バイトから始まり**、あるバリアントのペイロードが実際にそれより広い場合だけ大きくなります——
「デフォルト固定16バイト」と「サイズがバリアントに応じて変化する」は同じことの表裏です。`char` / `bool` のような小さなペイロードは
アラインメントを決めるだけで union を広げません。`payload` の幅は「最も幅の広い1つのバリアント」であり、すべての合計ではありません。

> レイアウトの唯一の情報源は `src/mir/layout.go` です。`tagWidth` が `iN` を決定し、`enumVariantLayout` が各
> バリアントのフィールドオフセットと自身のサイズを決定し、`enumUnionLayout` が最大値を取って `K` を得ます。`hir2mir.fillEnumLayout`
> はテーブル構築時にこれらの数値を `TaggedEnumInfo` に記録し、emitter は読み取るだけで計算しません——両者が異なる答えを出すことはあり得ません。

#### `#{inline}` の3つの書き方

`inline` は**真偽値**のアノテーションで、3つの書き方があり、**値が実際に尊重されます**：

| 書き方 | 意味 |
| ----------------- | --------------------------- |
| `#{inline}` | 省略形、`inline=true` と等価（単独のキーは真を意味します） |
| `#{inline=true}` | 明示的に真（`#{inline=1}` も可） |
| `#{inline=false}` | 明示的に偽（`#{inline=0}` も可） |

真偽値以外は**コンパイルエラー**です（`#{inline=foo}`、`#{inline='true'}`）。暗黙に真として扱われることはありません：  
`ValidateFieldTags`（TraceID `fieldtag1`）は構造体フィールドと enum 定義の両方に対してエラーを報告します。

enum 全体の上方に `#{inline=true}` を書くのはスタック形式レイアウトの**明示的な印**で、「この列挙型はスタック形式レイアウトを使う」ことを示します。  
コンパイラはこれを `TaggedEnumInfo.Inline` に記録します。**現在のデフォルトレイアウトは元々スタック形式**なので、  
アノテーションを付けるかどうか、`true` と書くか `false` と書くかに関わらずレイアウトは完全に同じです——印の役割は意図を明確にし、将来的にデフォルト  
レイアウトが変更された際に安定した選択スイッチとして機能することです。

> `#{inline}` を**enum 全体の上方**に書くと「この列挙型はスタック形式レイアウトを使う」ことを示します。**個々のバリアント**に書いた場合は現在  
> レイアウトを変更せず、そのバリアントのメタデータとして保持されるだけです（構造体フィールドとは異なるので、次の節を参照）。

#### 構造体フィールド上の `#{inline}`

enum とは異なり、**構造体フィールド**上の `#{inline}` は**実際の効果を持ちます**。それはそのフィールドが  
ホスト構造体内に**値でインライン展開**されるか（`%pt`）、**ポインタ**として格納されるか（`ptr`）を直接決定します。

```no
pt {
    x i64
    y i64
}

holder {
    inl pt #{inline=true}; 按值：結構體直接長在 holder 裡
    out pt #{inline=false}; 指標：欄位存的是指向 pt 的指標
    bare pt #{inline}; 簡寫，等於 inline=true
}
```

| 書き方 | フィールドのレイアウト |
| ---------------------------------------------- | --------------------------- |
| `#{inline}` / `#{inline=true}` / `#{inline=1}` | ホスト内に**値で**インライン展開（`%pt`） |
| `#{inline=false}` / `#{inline=0}` | **ポインタ**（`ptr`） |
| 書かない | `NOLANG_FIELD_PTR` に依存（下表を参照） |
| `#{inline=foo}` / `#{inline='true'}` | **コンパイルエラー**——真偽値ではない |

**アノテーションがない場合のデフォルトレイアウトは `NOLANG_FIELD_PTR` が決定します。** `mir.FieldPtrLayout` は  
`os.Getenv("NOLANG_FIELD_PTR") != ""` と等しく、**デフォルトはオフ**です。これをオンにすると「Phase 1 レイアウト反転」が起動し、  
構造体フィールドのデフォルトが値渡しからポインタに変わります。

| フィールド | フラグ オフ（デフォルト） | フラグ オン（`NOLANG_FIELD_PTR=1`） |
| ------------------------------ | --------- | ------------------------- |
| アノテーションなし | `%pt`（値） | `ptr`（ポインタ） |
| `#{inline}` / `#{inline=true}` | `%pt` | `%pt` |
| `#{inline=false}` | `ptr` | `ptr` |

つまり、**アノテーションは常に有効で、この環境変数の影響を受けません**。フラグが変更するのは「アノテーションを書かなかった場合」のデフォルトだけです。そのため  
デフォルト構成では、`#{inline=false}` は「積極的にポインタを要求する」ことを意味し、`#{inline=true}` は元からそうなっている  
レイアウトを明示的に書き直すだけです。反転が有効になると、両者の役割は入れ替わります。

チェッカーには2つの規則があります（TraceID `fieldtag1`、`ValidateFieldTags`）：

1. **構造体型のフィールドに対してのみ意味を持ちます。** スカラー / `str` / `vec` / 配列 / スライス / map / option /  
   ポインタのフィールドは元々すべて値で格納されるため、`#{inline}` を書いても何も述べていないのと同じで、エラーになります。  
   `#{inline=false}` も同様にエラーです。コンパイラの動作と逆のレイアウトを宣言することになるからです。
2. **値によるインライン展開で循環してはなりません。** インライン展開される構造体はホストの**内部**に格納されるため、  
   `a { #{inline} b b }` と `b { #{inline} a a }` が併存するとサイズが無限大になり、エラーとしなければなりません（直接の自己  
   参照は退化したケースです）。値の辺が作られるのは `=true` の場合だけなので、相互に再帰する構造体は**両側に  
   `#{inline=false}` を書いた**場合に限り合法です。
   > ⚠️ **「アノテーションを書かない」は「inline を使わない」を意味しません。** デフォルト構成ではアノテーションを書かないことは値でのインライン展開を意味するため、  
   > `a { x b }` と `b { y a }`（どちらもアノテーションなし）は**デフォルト構成では不正**で、  
   > `opt: error: identified structure type 'b' is recursive` というエラーで失敗します——しかもこのエラーは現在  
   > チェッカーからは**報告されず**、LLVM の検証段階になって初めて発生します。デフォルト構成で再帰型を書くには、**明示的に**  
   > `#{inline=false}` を書く**必要があります**。`NOLANG_FIELD_PTR=1` の場合だけ、「書かない」ことがポインタを意味します。

#### 再帰型：なぜ `inline=false` が必要か

自分自身を値でインライン展開する構造体はサイズが無限大になるため、**自己参照**は値で格納できません。デフォルト構成  
（`NOLANG_FIELD_PTR` オフ）では構造体フィールドはデフォルトで値渡しなので、`node` が自分自身を参照できるようにする  
唯一の書き方は、明示的にポインタを要求することです：

```no
node {
    v i64
    next node #{inline=false}; 指標：這樣 node 才有有限大小
}

n node
n.v = 1
n.next.v = 2
print(n.next.v); 2
```

上の `#{inline=false}` を取り除く（または `#{inline=true}` と書く）と、LLVM はこの型を  
即座に拒否します：`identified structure type 'node' is recursive`。

ポインタフィールドは参照先（pointee）を**所有**し、ライフタイムはコンパイラが処理します：

- pointee は**最初の書き込み時に遅延確保**されます（`@__nolang_get_<T>`、`malloc` + ゼロクリアを含みます）。  
  ホスト構築時に一括で確保されるわけではありません。
- ホストがスコープを抜けると、`@__nolang_drop_<T>` が**ヌルポインタチェックの後で**それを**解放**します。
- 値によるコピー（`b = a`、引数としての受け渡し、コンテナへの書き込み）は pointee を**ディープコピー**します。そのため2つのホストは  
  同じメモリ領域を共有せず、二重に解放されることもありません。

エンドツーエンドのテストは `tests/field-inline-annotation.no` を参照してください。

### 列挙値の参照

**規則：列挙値は `枚舉類型.值` という修飾形式で参照しなければならず、裸の値を直接使うことはできません。**  
これにより名前の衝突を防ぎ、外部パッケージが個々の値を直接使用できないようにします。

```no
#{fmt-skip}
; ❌ 錯誤：直接使用裸值
kind = null
yes = e.is(io)
```
```

```no
; ✅ 正確：使用限定方式
kind = json-kind.null
yes = e.is(code.io)
```

> 列挙型は構造体のフィールド型、関数の引数型、戻り値型に使用できます。  
> 列挙型を定義したモジュールの内外を問わず、列挙値は `枚舉類型.值` の形式で参照してください。

## enter/leave

`enter` / `leave` インターフェースを実装した型は、スコープへの侵入時と退出時に自動的に呼び出されます：

```no
file enter, leave {
    path str
}

file.enter = () {
    .open()
}

file.leave = () {
    .close()
}

read-file = () {

    ; 自動 f.enter()
    f = file {
        path: 'data.txt'
    }

    ; 使用 f
    ; 自動 f.leave()
    read(f)
}
```

### NULL 許容型（option）

型の前に `?` を付けると NULL 許容型を表します：

NULL 許容型の変数は空値／エラー値を合法的に保持でき、コンパイラがそれに応じた NULL チェックを行います。

`?t` は組み込みのタグ付き列挙型で、そのバリアントは `src/std/global.no` で定義されています：

```no
#{buildin}
option {
    ok(v t),
    nil,
    err(e err.err),
}
; tag 0：有值
; tag 1：空值
; tag 2：錯誤（std 結構化錯誤 err.err）
```

`err` バリアントのペイロードは**`str` ではなく**、`std/err` の `err` 構造体（`code` / `msg` / `file` / `line` / `col`）です。
`err('msg', code)` は `err.new('msg', code)` の別名コンストラクタです——エラーコード `code` は**必須**パラメータです
（パラメータのデフォルト値は言語から削除されました）。具体的なエラーコードがない場合は明示的に `code.unknown` を渡します。
位置フィールドはコンパイラが構築箇所で自動的に注入します。引数を1つだけ書いた `err('msg')` はこの別名ではなく、
option の `err` バリアントのコンストラクタです（後述）。

`#{buildin}` は基盤となる表現と構築が組み込みランタイムによって提供されることを示します（`%option` 型、`ok(...)`/`nil`/`err(...)`  
コンストラクタ）。`option` の列挙宣言はマッチと網羅性チェックにのみ使用されます。詳細は「タグ付き列挙型」と「組み込みタグ付き列挙型」を参照してください。

#### メモリレイアウト

`?T` は**ペイロード型ごとに型が決まります**：各ペイロード型に対応する LLVM 型が1つずつあり、名前はペイロード型から導出されます（単射）。
そのため「ペイロード型が同じ ⇒ レイアウトも同じ」であり、`?i32` / `?i64` / `?bool` は同じ型を共有します：

```llvm
%option_<key> = type { i8 tag, [K x i64] payload }   ; 內聯
%option_<key> = type { i8 tag, [1 x i64] payload }   ; 裝箱（payload 存 i8* 指標）
```

- `tag` は常に**1バイト**です。`option` は3つのバリアント（`0=ok`、`1=nil`、`2=err`）しかなく、
  「`<= 256` 個のバリアント → `i8`」の区分に入ります。列挙型の tag 幅の規則は〈メモリレイアウト（スタック形式）〉を参照してください。
- タグの後には**アラインメント用のパディング**があり（1バイトのタグ → 7バイトのパディング）、その後にペイロードが続きます。
- ペイロードサイズ `K` は `T` の実際のサイズで決まり、8の倍数に切り上げられます。**固定スロットではありません**。  
  `?i64` は16バイト（8 + 8）、`?str` は24バイト（8 + 16）、`?txt` は264バイト（8 + 256）です。
- 閾値を超えるペイロードは**ヒープへのボックス化**に切り替わります。`payload` には8バイトのポインタ1つだけが格納され、option 全体は16バイトになります。

閾値 `option-payload-inline-threshold` は**option 構造体全体**のバイト数で計算されます（デフォルトは **264** = 1バイトのタグ +
7バイトのパディング + 256バイトのペイロード、最小 **16**）。ペイロードがインライン展開される条件は
`8 + roundUp8(sizeof(T)) <= 門檻` です。そのためデフォルトでは「ペイロードが256バイト以下ならインライン展開」となり、`?txt`
（256バイトのインラインバッファ）はぎりぎり境界内に収まります。

| `?T` の `T` | インライン？ | `%option_<key>` のサイズ |
| --- | --- | --- |
| `i64` / `i32` / `bool` / `char` / `f64` / ポインタ | はい | 16バイト |
| `str` / `[]T` / `vec`（16バイトのデスクリプタ） | はい | 24バイト |
| `txt`（256バイトのインラインバッファ） | はい | 264バイト（ちょうどデフォルト上限） |
| サイズが256バイトを超える構造体 / 配列 | いいえ | 16バイト（ペイロードはヒープ上） |
| 自己参照するペイロード（`node { next ?node }`） | いいえ | 16バイト（自己参照はポインタで断つしかない） |

> **`err` のペイロードは常にボックス化されます**：`err` バリアントが格納するのは `std/err` の `err` 構造体へのポインタで、上記の  
> ペイロード予算を消費しません。そのため `?str` は `ok` のとき24バイトのインライン文字列であり、`err` のときも同じ24バイトの  
> 構造体です——違うのは `payload` の語にエラーオブジェクトへのポインタが入っている点だけです。この規則により、「同じ `?T` 型で、  
> 2つのバリアント、2種類のペイロード」でも追加の領域は不要です。

> **インライン展開とボックス化は「どこに置くか」を変えるだけで、所有権は変えません**：どちらの経路も**コピー**が発生したときに構造体ペイロードの  
> ヒープ部分を別途確保します（ポインタフィールドは再帰的に、インライン所有の `str` / `[]T` バッファはクローンされます）。そのため `?T` の値セマンティクスは  
> インライン展開の有無と無関係です——同じプログラムはどんな `option-payload-inline-threshold` でも出力が完全に一致しなければなりません。  
> 閾値を1つずらすだけで挙動が変わるなら、それはコンパイラのバグであって機能ではありません。（純粋な移動の代入ではクローンせず、option が  
> 元のヒープを受け取ります。）

> レイアウトの唯一の情報源は `src/mir/layout.go` です。`optLayoutOfPayload` が `K` とボックス化の有無を決定し、  
> `optionPayloadOffset`（8）がペイロードの固定バイトオフセットです。`hir2mir` がモジュールレベルの `?T` 定数を畳み込み、  
> codegen が読み書きを出力するときも、同じ関数に問い合わせます。

#### `?=` による異なるペイロード間の上拋（伝播）

`?=` はまず「右辺の連鎖の**根**にある option」を option 結果パラメータにコピーし、`nil` / `err` をそのまま上拋させ、  
成功パスは `ok` アームで上書きします：

```no
pick = (p pool) (out ?i64) {
    out ?= p.nodes[0].kind; 根是 ?node，結果槽是 ?i64
}
```

したがって両側のペイロード型は**異なっていてもかまいません**。これは実際の ABI 境界であり（`?node` は112バイト、`?i64` は16バイト）、
同じレイアウトの2つの表記ではありません。型をまたいで運べるものは2つだけです：

- `tag`——各 option の第0バイト。
- `err`——`err` バリアントは option の属性でありペイロードとは無関係で、常にボックス化されます。そのため両側ともペイロード領域の
  先頭の語は8バイトのボックスへのポインタです（ボックス本体は**コピー**され、共有されません。両側が drop するためです）。

`ok` のペイロードは**型をまたいで運ばれません**：目標のペイロード領域はまずゼロクリアされ、成功値は常に `ok` アームが書き直します。
実装は `@__nolang_opt_prop_<dst>__<src>`（`src/mir/codegen.go` の `optPropagateState`）にあり、
`?=` のようなコンパイラ生成の上拋代入にだけ現れます。

```no
o ?i64
o = nil; 設為空
o = 42; 設為有值
o = err('msg'); 設為錯誤

nullableValue ?[]str
nullableString ?str

; 修改可空類型
nullableString = 'test'

; 設置錯誤
nullableString = err('some error')

; 可通過match判斷
x: {
    err -> log(it.msg()); it 是 err.err，訊息靠 .msg()

    nil -> log('nil')

    -> do-right-thing(it)
}

; 強制解包
; 取消實現
; !x.say()
```

### スタイルガイド：(val, ok) の代わりに ?t option を使う

関数が失敗する可能性や空値を返す可能性がある場合、`(val t, ok bool)` の2値返しパターンではなく、**`?t` option 型を優先して使用してください**。

`?t` はタグ付き列挙型で、3つの状態を持ちます：`ok`（値あり）、`nil`（空値）、`err`（エラー）。正常値は暗黙に束縛され、値が見つからなかっただけの場合は `nil` を、実際のエラーが発生した場合は `err(...)` を使います。

```no
#{fmt-skip}
; ❌ 不推薦：雙返回值模式
stack.pop = () (val i64, ok bool) {
    .n == 0 -> return
    val = .data[.n]
    ok = true
}
```
```

```no
; ✅ 推薦：option 類型（nil 表示空，err 表示錯誤）
stack.pop = () (val ?i64) {
    .n == 0 -> {
        val = nil
        return
    }
    val = .data[.n]
}

; ✅ 返回錯誤
file.read = () (data ?str) {
    .fd < 0 -> {
        data = err('file not open')
        return
    }

    ; ... 讀取資料
    data = buf
}
```

match で option をアンパックします：

```no
val = s.pop()
val: {
    nil -> print('empty')

    err -> print(it.msg()); it = 結構化錯誤 err.err

    -> print(it); it = 彈出的值
}
```

## 整数演算のオーバーフロー（`#{overflow}` アノテーション）

Nolang は panic をサポートしません。オーバーフローする可能性のある操作はすべて `option` または明示的なアノテーションで処理する必要があり、実行時に整数オーバーフロー例外が投げられることは決してありません。以下の**整数の四則演算**のオーバーフロー動作は `#{overflow = ...}` アノテーションで制御されます：

- 符号付き・符号なしの **`+` `-` `*`**：左右のオペランドが整数（`int` リテラルを含む）の場合に適用されます。
- 符号付き **`/`**：`INT_MIN / -1` の場合だけオーバーフローします（符号なし除算 `a/b ≤ a` はオーバーフローしないため対象外です）。

> 符号なし整数（`u8`/`u16`/`u32`/`u64`/`u128`）の `+ - *` は符号付き整数と**まったく同じ規則**に従います。アノテーションがない場合もデフォルトで `option<int>` を返し、オーバーフロー時は `err` になります。これは設計上の意図的な選択です——「コンパイル時にオーバーフロー不可能と証明できない限り、同じ規則で扱う」。

### 特例：`byte` と `char` の算術

`byte` と `char` はオーバーフローセマンティクスの**特例**です。これらの算術は **option を生成せず**、`#{overflow}` アノテーションの対象外です。

- **`byte`（u8）**：`+ - *` がオーバーフローすると**暗黙に2's補数でラップアラウンド**します（`250 + 10` → `4`、`0 - 1` → `255`）。`byte` はバイトバッファや hex のエンコード／デコードなど「自然にラップアラウンドを許容する」場面向けで、ハッシュやカウンタの `#{overflow = wrap}` と同じセマンティクスを持ちます。ただし組み込みであり、アノテーションは不要です。
- **`char`（Unicode コードポイント）**：`+ -` は**コードポイント算術**です。結果が正当なコードポイントの範囲（`< 0` または `> 0x10FFFF`）を超えると **`-1`**（無効なコードポイントの番兵）になります。`err` にはならず、ラップアラウンドもしません。

**設計上の理由**：`i8`–`i128` / `u8`–`u128` は一般に**実際の業務上の数値**（金額、個数、容量）に使われ、暗黙のラップアラウンドはオーバーフローのバグを隠してしまうため、デフォルトは `err` とし、明示的な選択を強制します。一方 `byte` / `char` の典型的な用途（バイトストリーム、コードポイントの走査）はセマンティクス上ラップアラウンドを自然に許容し（むしろ期待し）るため、option にすると解包のノイズが増えるだけです。`byte` / `char` の演算でオーバーフローを検出したい場合は、まずより広い型（例：`b.to-i64()`）に変換してから計算してください。

| モード | アノテーション | オーバーフロー時 | 結果の型 | 適用場面 |
| ----------- | ------------------------ | --------------------------- | ------ | ------------------ |
| **デフォルト（アノテーションなし）** | — | オーバーフロー → `err`、正常 → `ok(value)` | `?int` | オーバーフローを検出する演算 |
| **ラップアラウンド** | `#{overflow = wrap}` | 暗黙に2's補数でラップアラウンド | `?int` | ハッシュ、暗号、カウンタなどセマンティクス上ラップアラウンドを許容する場合 |
| **ゼロにする** | `#{overflow = clamp0}` | オーバーフロー（上溢または下溢）で `0` | `?int` | 差が負になってはならないセマンティクス（残量など） |
| **最小値にクランプ** | `#{overflow = min}` | オーバーフロー時に型の最小値にクランプ | `?int` | カウンタの下限、添字の保護 |
| **最大値にクランプ** | `#{overflow = max}` | オーバーフロー時に型の最大値にクランプ | `?int` | 容量の上限、飽和加算 |
| **飽和** | `#{overflow = saturate}` | 上溢→最大値、下溢→最小値 | `?int` | 信号／色の飽和など |

> ⚠️ **アノテーションは解包しません**（D1）：`#{overflow = …}` は**「失敗時にどう値を取得するか」だけを決定します**。
> 結果の型は常に `?T` です。結果を plain に戻すには match または `?=` で消費するしかありません。2つの消費形態
> （`?=` + ブロック match／値位置 match）の違いと選択については〈ブロック match と値位置 match の取捨〉を参照してください。
> 明示的に plain 型として書く（`w i64 = a - b  #{overflow=wrap}`）**抜け道ではありません** ——
> 実測では依然として `15w45dqk`（cannot assign `?i8` value to `i8` variable）が報告されます。

さらに、すべてのモードで**型接頭辞形式**をサポートします。これは特定の狭い型の飽和境界を正確に指定するもので、例：`#{overflow = u8-max}`、`#{overflow = i8-min}`、`#{overflow = u16-saturate}`。

> **アノテーションの粒度**：`#{overflow = ...}` は**行アノテーション**です——**直後の次の一文**にだけ作用します。
> これは**設計上唯一許可される**形式です（乱用を防ぐため）。実行セマンティクス（codegen）と `ovfhndld` ハードエラーの両方がこれだけを認識します。
> さらにこれは「オーバーフロー時の値の取得方法」だけを変え、型は変えません。ブロック級や関数級に緩めると、広い範囲の演算のセマンティクスが遠く離れた1行のアノテーションによって決まってしまいます。
> 理由は [〈アノテーションと注釈のスコープ〉](annotation-scope.md) §4.1 を参照してください。
>
> ⛔ **関数定義の上、ブロックの先頭、ファイルの先頭に置くのは不正です**。現在の唯一の抜け穴は、関数級アノテーションを付けると
> `ovf-int-default` lint が関数全体をスキップし（一覧は「きれい」に見えます）、関数本体のアノテーションなしの演算は相変わらず
> `ovfhndld` を発生させます。ブロック級アノテーションは lint が下方に継承して沈黙しますが、codegen は一切認識しません。一文ずつアノテーションを付けてください。
> `no fmt --fix=overflow` が生成するのも、この一文単位の形式です。
>
> 完全なモデル（L0 モジュール / L1 宣言 / L2 ブロック / L3 単行、およびどのキーがどの階層をサポートするか）は
> [〈アノテーションと注釈のスコープ〉](annotation-scope.md) を参照してください。同ページ §7 に既存品と抜け穴、§8 に締め付けの順序があります。

> **LSP クイックフィックス**：エディター（nolang-lsp）はアノテーションなしの整数演算に対して**ヒント**（`nolang-overflow`、trace id `ovfhndld`）を報告し、5つの quickfix——**Add `#{overflow = wrap}`** / **`clamp0`** / **`min`** / **`max`** / **`saturate`**——を提供します。該当演算のある文の上に、その行と同じインデントで対応するアノテーションを自動挿入し、オーバーフロー動作を指定します（結果は依然として `?T` で、別途 match / `?=` での消費が必要です）。コマンドライン版は `no fmt --fix=overflow` です（後述）。

### デフォルト：`option<int>` を返す

アノテーションがない場合、`a - b` の結果型は `option<int>` です。受け取り側は `?T`（NULL 許容型）でなければならず、match で `err` / `nil` / `ok` の3分岐を分解します：

```nolang
main = () {
    x i64 = 100
    d ?i64 = x - 1; 默認：返回 option<i64>
    d: {
        err -> print(-1); 溢出（如 x - 2^63 下溢）

        nil -> print(0)

        -> print(1); ok(value)：正常結果
    }
}
main()
```

> `%option` の `data` フィールドは `i64` です。狭い型（`i8`/`i16`/`i32`）の結果はまず符号拡張（sext）されてから格納され、アンパック時に元の幅に切り詰められます。

### wrap：暗黙のラップアラウンド

```nolang
#{overflow=wrap}
sub-wrap = (a i64, b i64) (r i64) {
    r = a - b; 溢出時靜默 2's 補數回繞；r 是 plain i64（顯式型別）
}
```

文レベル：

```nolang
x i64 = -9223372036854775807

#{overflow=wrap}
w i64 = x - 2; 下溢回繞 → 9223372036854775807
print(w)
```

### clamp0：オーバーフロー時にゼロにする

```nolang
x i64 = -9223372036854775807

#{overflow=clamp0}
c i64 = x - 2; 下溢 → 0（上溢同樣歸零）
print(c)
```

### min / max / saturate：飽和クランプ

3つのモードはオーバーフロー結果を型が表現できる区間内に「挟み込み」ます。ラップアラウンドやゼロ化ではありません：

```nolang
#{overflow=min}
floor = (a i64, b i64) (r i64) {
    r = a - b; 下溢 → i64 最小值；上溢 → i64 最大值
}

#{overflow=max}
cap = (a i64, b i64) (r i64) {
    r = a * b; 上溢 → i64 最大值；下溢 → i64 最小值
}

#{overflow=saturate}
sat = (a i64, b i64) (r i64) {
    r = a + b; 上溢→max、下溢→min
}
```

型接頭辞形式を使うと狭い型の飽和境界を正確に制御できます（関数級アノテーションは本体内の対応するすべての型の演算に適用されます）：

```nolang
#{overflow=max}
inc = (x u8) (r u8) {
    r = x + 1; x = 255 時上溢 → 255（而非回繞成 0）
}

#{overflow=min}
dec = (x i8) (r i8) {
    r = x - 1; x = -128 時下溢 → -128（而非回繞成 127）
}
```

### コンパイラによる強制

アノテーションなしの整数演算はデフォルトで `option<int>` を返すため、「未処理」は強制的に検出されます。**未処理と見なすかどうかは並列判定**です——以下のいずれかを満たせばエラーになりません：

- **`?=` による上拋**（関数に option 結果パラメータが必要です）。
- **その場での捕獲**：`=` で**新しい**変数に束縛する（変数は自動的に `?T` と推論されます）、または明示的に `?T` を宣言する（例：`x ?i64 = a + b`）。
- **`_ = expr` による明示的な破棄**（評価自体は安全な経路を通り、エラーも一緒に無視されます）。
- **アノテーションを付ける** `#{overflow = wrap}` / `clamp0` / `min` / `max` / `saturate`（または `u8-max`、`i8-min` のような型接頭辞形式）。ラップアラウンド／飽和セマンティクスを受け入れることを宣言します。

4つすべてが欠けている場合だけエラーになります（`ovfhndld`）。

> **純粋な算術はエラー源ではない**：`+ - * <<` と単項マイナス自体は捕獲を発生させません（そうするとすべての算術が option になり、標準ライブラリが爆発します）。そのため `d = x - 1`（`/` `%` を含まず、安全な添字アクセスや option オペランドも含まない）は依然としてエラーです——アノテーションを付けるか、`d ?i64 = x - 1` と書いてください。
>
> **既存の変数は型を変えません**：捕獲は「この文で初めて宣言される」対象にだけ効きます。変数がすでに存在する場合（例：先に `d = 0` としてから `d = x - 1` とする、あるいは先に `v i64 = 0` としてから `v = arr[i]` とする）、コンパイラはその場で option に変更せず、セマンティクスを明示的に選択するようエラーを出します。

上記の豁免の影響を受けない硬性エラーが別に2つあります。

- アノテーションなしの整数演算を**明示的な plain `int`** 変数に代入すると、コンパイラはエラーを報告します（`cannot assign ?i64 value to i64 variable`）。`#{overflow = wrap}` / `#{overflow = clamp0}` / `#{overflow = min}` / `#{overflow = max}` / `#{overflow = saturate}`（または型接頭辞形式）を付けるか、名前付きの `?T` を使うことを強制します。
- アノテーションなしの整数演算を**すでに存在する**変数で、かつ型が option でないもの（`d = 0` の後の `d = x - 1`）に代入すると、コンパイラはエラーを報告し、アノテーションを付けるか `?i64` を宣言するよう促します。不正な IR が生成されるのを防ぐためです。

その他の規則：

- 符号なし整数演算（`u8`/`u16`/`u32`/`u64`/`u128`）にも**同じ機構が適用されます**。アノテーションなしの `+ - *` はデフォルトで `option<int>` を返し、オーバーフロー時は `err` です。符号付き整数と同じ規則です。
- `i128` 演算は `option` 経路をサポートしません（data フィールドが `i64` のみ）。正確性を保つため、すべて暗黙のラップアラウンドに退化します。

> **なぜデフォルトは wrap ではなく option なのか？** 暗黙のラップアラウンドはオーバーフローのバグを隠してしまいます。デフォルトで `option` を返すことで、呼び出し側にオーバーフローの明示的な処理を強制します（あるいは自ら `wrap` を付けて「ラップアラウンドセマンティクスを受け入れる」と表明させます）。これにより「オーバーフローを許容するかどうか」が可視的な設計判断になります。

### ゼロ除算（division by zero）

整数の `/` と `%` の除数が `0` になるのは**未定義動作（UB）**であり、オーバーフローとは**別の2つの事柄**です——どんなアノテーションもこれを免除できません：

- **コンパイル時に判定可能**：除数が**リテラル定数 0**（`10 / 0`、`a % 0`、`x / 0`）⇒ **ハードエラー**（trace id `div-by-zero`）。`#{overflow = wrap}` もこれを免除しません（このアノテーションが扱うのはオーバーフローであってゼロ除算ではありません）。
- **実行時になって初めて分かる**：除数が変数や外部入力から来る場合 ⇒ コンパイラは**両方の経路に**ゼロチェックを挿入します。違いは「どう報告するか」だけです：

| 結果の型 | 発動条件 | 除数が 0 のとき |
| ----------- | ----------------------- | ------------------------------------------------------------------------------ |
| `?int`（デフォルト） | 文にアノテーションなし | option tag = `err`。`?=` / match で処理します |
| plain `int` | 文に `#{overflow = ...}` がある | 結果が強制的に `0` になり、**stderr** に `nolang: integer division or remainder by zero ...` を出力します |

```nolang
safe = (a i64, b i64) (r ?i64) {
    r = a / b; b == 0 → err（呼叫方必須處理）
}

#{overflow=wrap}
fast = (a i64, b i64) (r i64) {
    r = a / b; b == 0 → 0 並印一行 stderr 診斷（不再是裸 sdiv 的 UB）
}
```

> **なぜ `#{overflow = wrap}` でゼロ除算ガードを免除できないのか**：これは**オーバーフロー動作**（結果型は常に `?int`）を変えるものであり、除数の安全性を変えるものではありません。もし免除すると、コンパイラは裸の `sdiv` を出力し、オプティマイザーは除数が常に非0であると仮定する権利を持ちます（`a / 0` を任意の値に畳み込む）。一方 x86-64 の `idiv` は #DE でクラッシュします——UB でありながら診断もありません。そのため zero-divisor ガードは**アノテーションとは独立して**存在します。plain 経路で stderr に1行多く出力するのは、その経路には呼び出し側がチェックできる option がないからです。
>
> **同じガードは `sdiv (INT_MIN, -1)` もカバーします**（結果は表現できず、同じく UB です。x86-64 では SIGFPE になります）。option 経路はこれを `err` に含めます。plain 経路は2の補数のラップアラウンド値を取ります（`INT_MIN / -1 → INT_MIN`、`INT_MIN % -1 → 0`）。

浮動小数点の除算は対象外です。`1.0 / 0.0` は IEEE-754 により `inf` / `nan` と定義されており、UB ではありません。

### アノテーションなしの演算をエラーにする（`ovf-int-default`）

`no vet` は**アノテーションなし**の整数演算を**ヒント**として報告します（trace id `ovfhndld`、HINT）。理由：デフォルトの `?T` はユーザーから見えないため、そのことを認識させる必要があるからです。`#{overflow = ...}` を付けてオーバーフロー動作を指定するか、`?T` + `?=` / match / 明示的な plain 型で消費します。本当にビルドをブロックすべきは `optunuse`（option が上拋も解包もされていない場合）です。

### 自動修復：`no fmt --fix=overflow`

アノテーションを一括で補うのに手書きは不要です。`no fmt` の修復カテゴリ引数を使います：

```bash
no fmt --fix=overflow -w src/std          # 就地修復整個目錄
no fmt --fix=overflow -d src/std/str.no   # 只印 diff，不寫檔
no fmt --fix=overflow src/std/str.no      # 印出修復後的內容
```

修復は**正確で、他の部分を汚しません**。lint が実際に報告した演算のある文の上にだけ `#{overflow=wrap}` を挿入し、他の文は変更せず、再整形もせず、既存のアノテーションも触りません。再実行しても冪等です（すでにアノテーション済みのものは変化しません）。これは `no fmt -w` を直接実行するのとは異なります——後者は完全な再フォーマットです。

> 修復後にもう一度 `no vet` を実行してゼロになったことを確認してください。ほとんどの場合1回でクリアされます（`src/std` は 4728 件から 0 になりました）。既知の唯一の例外形：報告が match arm の**条件**にあり、その arm 本体にアノテーション可能な文が一切ない場合です。行アノテーションは直後の最初の文にだけ作用するため、arm 自身の条件演算には届きません。このとき `no vet` が再び報告します。その場合はまずその演算を独立した文に抽出してからアノテーションを付けてください。

### 自動修復：冗長な型アノテーション

変数宣言の**型アノテーションが右辺の値から推論される型とまったく同じ**場合、そのアノテーションは冗長です（`no vet` がヒント `tcpoxtfd`、`type annotation '<T>' can be omitted (inferred from value)` を報告します）。

- **デフォルトの `no fmt` が自動削除します**：`no fmt -w` はフォーマット時に冗長なアノテーションも削除します（同時に通常の再フォーマットも行います）。`no fmt -d` はこの変更を含むプレビュー、`-w` は書き込みです。

```bash
no fmt -w main.no          # 格式化並去掉冗餘標註
no fmt -d main.no          # 只印 diff（含標註移除）
no fmt -w src/             # 整個目錄
```

- **`--fix=redundant`（外科的、アノテーションのみを変更）**：冗長なアノテーションだけを削除し、完全な再フォーマットはしたくない場合（例：`src/std` では `no fmt` が `#{index-out}` を失ってしまう）、このカテゴリを使います。アノテーションだけを削除し、再整形はしません。

```bash
no fmt --fix=redundant -w src/std          # 就地移除整個目錄的冗餘標註（不重排版）
no fmt --fix=redundant -d src/std/str.no   # 只印 diff，不寫檔
no fmt --fix=redundant src/std/str.no      # 印出修復後的內容
```

```nolang
; 修復前
x str = ''
b i64 = 5
m [str]i64 = make-map()

; 修復後（標註 == 推斷型別，去掉）
x = ''
b = 5
m = make-map()
```

規則の要点：

- **アノテーション型 == 推論型**の場合だけ削除します（`str`/`i64`/`[str]i64` が推論値と一致する場合など）。
- **暗黙変換は可能だが等しくない**場合は**削除しません**。変換セマンティクスを保つためにアノテーションを残します。例：`c i16 = 5`（`5` は `i64` と推論され、`i16` とは異なる）、`p ?i64 = nil`、`last txt = ''`（`txt` と `str` は暗黙に相互変換できますが型は異なる）。
- **型アノテーションがない**書き方（例：`d = 'x'`）は元々報告されないので、変更もされません。
- **固定長配列アノテーション `[N]T` / `[?]T` は常に保持します**（冗長とは見なされません）。`[N]` は単なる型ヒントではなく、**表現形式を決めるスイッチ**です。これを書くと右辺の `[...]` リテラルが固定長のスタック配列として解析され、書いた結果として推論型がアノテーションに「ちょうど等しく」なります——これはアノテーション自身が作り出した循環論法です。削除すると同じ行が再解析されてヒープ上で伸長可能なスライス `[]T` になり、セマンティクスが変わります。`fixed [3]char = ["x", "y", "z"]` では `.push()` が無効で（`.len()` は常に3）、`fixed = ["x", "y", "z"]` に退化させると `.push()` で `.len()` が4になります。スライスアノテーション `[]T` は対象外です——削除してもスライスのままなので、真の冗長です。
- **16進リテラルを含む値は常にアノテーションを保持します**（保守的な例外）。`no vet` の型推論は `0xNN` に対して「`byte` と推論する」ヒューリスティックを使いますが、コンパイラの「アノテーションなしの整数字面量はデフォルトで `i64`」という実際のセマンティクスとは異なります。そのため `IP-TBL [64]byte = [0x3a, ...]`、`s []byte = [0x50, 0x4b]` は冗長と誤判定され、削除するとリテラルが `i64` 要素に退化して `expected '[]byte', got '[]i64'` のような型エラーが発生します。したがって値の式のテキストに `0x` / `0X` が出現する場合、ヒントも削除も行われません。
- **右辺がフィールド読み出しの場合は常にアノテーションを保持します**（保守的な例外）。`i i64 = .pos` のような書き方のアノテーションは単なる型ヒントではなく、後続の整数演算が `?T` を生成するかどうかのスイッチです。フィールドから型を推論させると `i + N` が「符号付き演算」ではなくなり `?i64` を返さなくなるため、2段階の解包の `ok` アームが永久にヒットせず、ループカウンタがその場で止まります。`src/std/yaml.no` の `parser.looks-like-map-entry` が実例で、`i64` を削除すると `yaml.parse('abc')` が無限ループに陥ります。そのため `x = .field`、`x = obj.field`（括弧や接頭辞で包まれたものを含む）のアノテーションは `tcpoxtfd` を報告せず、デフォルトの `no fmt` や `--fix=redundant` でも削除されません。

デフォルトの `no fmt` であれ `--fix=redundant` であれ、削除は報告されたその型アノテーションとその前の空白だけを削除し、再実行しても冪等です（削除済みのものは変化しません）。修復後はもう一度 `no vet` を実行して `tcpoxtfd` がゼロになったことを確認することをお勧めします。

### 自動修復：option の消費（`--fix=unwrap`）

統一ルールの下では「option を生成したが一度も消費していない」ことがビルドをブロックすべき唯一の診断です（trace `optunuse`）。これを明示的な消費形式に一括で書き換えるには `--fix=unwrap` を使います：

```bash
no fmt --fix=unwrap -w src/std            # 就地修復整個目錄
no fmt --fix=unwrap -d src/std/str.no     # 只印 diff，不寫檔
no fmt --fix=unwrap src/std/str.no        # 印出修復後的內容
```

修復の形態（〈安全な添字アクセス〉を参照）：**所在関数にすでに `?T` 結果パラメータがある** → 上拋（`x ?= <expr>`）。それ以外 → 名前を変更して match で解包：

```nolang
; 修復前
x = a + b

; 修復後（所在函式有 ?T 結果參數）
x ?= a + b

; 修復後（否則，4 行標準形；空兜底臂 = 零值）
x-opt = a + b
x = x-opt: {
    ok -> it

    ->
}
```

他の fix カテゴリと同様です。外科的なテキスト置換で、整形は変更せず、文の上の `#{overflow=…}` / `#{index-out=…}` アノテーションも触りません（これらは引き続き「失敗時にどう値を取得するか」を担当します）。再実行しても冪等です。修復後はもう一度 `no vet` を実行して `optunuse` がゼロになったことを確認してください。

### アノテーションのバインドと単行への統合

`#{...}` アノテーションは**ノードにバインドされる**ため、1つの文に複数のキーを同時に持たせることができます。複数のアノテーションは常に**1行に統合**されます：

```nolang
#{fmt-skip}
i <- [0..16): {

    #{index-out=0, overflow=wrap}
    buf[base + i] = data[i]
}
```

上の一文は「範囲外のときデフォルト値を取る」（`index-out`）と「オーバーフロー時にラップアラウンドする」（`overflow`）という2つのセマンティクスを同時に必要とします。2行に分けて書いても解析結果は同じですが、`no fmt --fix=overflow` は統合後の単行形式を出力します。

> **行アノテーションの作用範囲**：`#{overflow = ...}` は**直後の次の一文**にだけ作用します。途中に関係のないアノテーションが挟まっていても、その文に正しく適用されます。安全な添字への書き込み（`arr[base + i] = v`、`.buf[.pos + i] = v`）は match 形式に desugar され、`#{overflow = wrap}` も desugar 後のノードに引き継がれるため、添字の算式もアノテーションの対象になり、アノテーションなしと誤報告されることはありません。

### エラーの上拋（`?=` 演算子）

`?=` は option の解包とエラーの上方への伝播をまとめた**便利な書き方**です。**関数が option を返すことは必須条件ではありません**。以下の2つのうちどちらかを満たせばよいため、
戻り値が option でない関数でも本体をブロック match で包めば `y ?= x + 1` と書けます。

**構文：**

```no
v ?= expr
```

**セマンティクス：**

- `expr` が `ok(value)` を返した場合、`v` には解包された内部値が代入されます（自動解包）。
- `expr` が `nil` または `err` を返した場合：
  - 関数に `?T` 結果パラメータがある場合 → その option を結果パラメータに書き込んで早期 `return` します（自動上拋）。
  - 文が**文レベルのブロック match** `{ ... }: { ... }` の本体内にある場合 → **最も近い**ブロック match が捕捉し、
    **本体全体が停止**し、arms は1回だけ実行されます（`return` ではありません）。関数に `?T` 結果パラメータは不要です。

**使用条件（どちらか一方で可）：**

1. 所在関数が option 型の結果パラメータを持つこと。
2. 文が文レベルのブロック match `{ ... }: { ... }` の本体内にあること（〈Match 主語の3つの形態〉を参照）。

どちらでもない場合、コンパイラはエラーを報告します。`err -> _` / `-> _` の2つの arm で上拋されたエラーをその場で飲み込めます。これは「`?T` 結果パラメータなしで
簡記法を使いたい」場合の標準的なフォールバックです：

```no
handle = (x i64) {
    {
        y ?= x + 1
        print(1)
    }: {
        err -> _

        -> _
    }
}
```

**結果パラメータは事前の代入が不要です**：関数プロローグはゼロ初期化を行いませんが、return 時に明示的に代入されていない出力パラメータは自動的にゼロで埋められます（整数 → `0`、`str` / 構造体 → ゼロ値、option → `nil`）。そのため例では `result = nil` という定型文を書かず、成功経路の代入だけを書けば十分です。

**例：**

```no
; 逐行讀取檔案並處理 — 使用 ?= 簡化錯誤傳播
process-file = (path str) (result ?str) {
    f ?= open(path); 失敗時自動 result = f; return
    line ?= f.read-line(); EOF 或錯誤時自動上拋
    result = line
}
```

等価な展開形式（コンパイラが自動生成する match の連鎖）：

```no
#{fmt-skip}
process-file = (path str) (result ?str) {
    result = nil
    __tmp = open(path)
    __tmp: {
        nil || err -> {
            result = __tmp
            return
        }
        -> f = it
    }
    __tmp2 = f.read-line()
    __tmp2: {
        nil || err -> {
            result = __tmp2
            return
        }
        -> line = it
    }
    result = line
}
```

**チェーン使用：** 複数の `?=` を連結して使うことで、パイプライン状のエラー伝播を実現できます：

```no
pipeline = (input str) (result ?str) {
    a ?= step1(input); 失敗則上拋
    b ?= step2(a); 失敗則上拋
    result = b
}
```

**裸の算術演算：** `?=` の右辺は関数呼び出しに限られません。`option` を返す整数演算（アノテーションなしの `a - b`、`a + b`、`a * b` など）ならば、直接 `?=` でオーバーフローエラーを上拋でき、途中変数に束縛する必要はありません：

```no
; 溢出時自動 result = err; return，正常時 v 解包為內部值
sub-safe = (a i64, b i64) (result ?i64) {
    v ?= a - b; 下溢/上溢 → err 自動上拋；否則 v = 內部 i64
    result = v
}

add-safe = (a i64, b i64) (result ?i64) {
    v ?= a + b; 同上，適用於 + * 與有號 /
    result = v
}
```

等価な展開（コンパイラが自動生成）：

```no
#{fmt-skip}
sub-safe = (a i64, b i64) (result ?i64) {
    result = nil
    __unwrap = a - b            ; option<i64>
    __unwrap: {
        nil -> {
            result = __unwrap
            return
        }
        err -> {
            result = __unwrap
            return
        }
        -> v = it               ; ok(value)：解包內部值
    }
    result = v
}
```

**複合右辺（compound RHS）：** `?=` の右辺は、複数の option オペランドを含む複合式にできます。各 option オペランドは自動的に解包され、伝播ガードが注入されます。いずれかのオペランドが `nil` / `err` になると、現在の関数の option 結果パラメータにその値が設定されて `return` します（上方へ伝播します）。すべて成功した場合だけ内部値が左辺に代入されます：

```no
sum3 = () (result ?i64) {
    a ?i64 = ok(10)
    b ?i64 = ok(20)
    c ?i64 = ok(30)
    total ?= a + b + c; 每個 option 運算元自動解包並傳播
    result = total
}

comp = () (result ?i64) {
    a ?i64 = ok(4)
    b ?i64 = ok(6)
    v ?= dbl(a + b); a + b 可能是 option，同樣自動解包並傳播
    result = v
}
```

> 「オペランド位置」にある option のみが自動的にアンラップされます（`a + b + c`、`f(b + c)` など）。関数の引数として直接渡される option 変数は対象外です——これは `?=` の既存の「素の option 引数」例外（`a ?= f(v)`。ここで `v` は `?i64`、`f` はプレーンな `i64` を受け取る）を通ります。

**非 option の右辺はエラー：** `=` を `?=` と広範囲に誤記するのを防ぐため、右辺がコンパイル時に「明確に非 option」と判定できる場合、コンパイラはエラーを報告し、`=` の使用を提案します：

- リテラル：`v ?= 42`
- 定数折りたたみ可能な整数演算：`v ?= 10 + 20`
- 型が既知で非 option のローカル変数：`v ?= x`（ここで `x i64 = 5`）

エラーメッセージは次の形式です：`` `?=` RHS `42` is not an option — use `=` instead ``。

> 算術演算は、いずれかのオペランドが option（または型が未知／関数呼び出しで option を返す可能性がある）であれば「option の可能性あり」として通し、誤検出しません——例えば `v ?= a + b + c`（a/b/c が `?i64`）や `v ?= b + c`（b/c が未知の型）も正常にコンパイルできます。

**適用シナリオ：**

- `pop` / `peek` など空になりうるコンテナ操作 → `?t`（`nil` = 空）
- `read-line` / `read-byte` など I/O 操作 → `?str` / `?i64`（`nil` = EOF、`err` = エラー）
- `lookup` / `get` など検索操作 → `?t`（`nil` = 見つからない）
- `parse` / `from-str` など解析操作 → `?t`（`nil` = 空、`err` = 無効な入力）
- `accept` / `dial` などネットワーク接続 → `?conn`（`nil` = 接続なし、`err` = エラー）

**nil と err：** 欠損が正常／予期された結果（空のスタック、キーが存在しない、EOF）の場合は `nil` を使い、欠損が実際のエラー状態（I/O 失敗、入力が無効、接続拒否）を表す場合は `err('msg')` を使います。

**例外：** 関数が複数の独立した値を返す必要がある場合（例：`(name str, value str, ok bool)`）は、複数戻り値のパターンを維持できます。

**複数戻り値で `?T` は最大 1 つ（ハードエラー）：** 関数宣言の戻りパラメータでは、`?T` は最大 1 つです。`?T` は**単一**のエラーチャネルであり——関数本体内の `?=` による早期リターンでは、失敗をその唯一の option 戻りパラメータにしか格納できません。2 つの `?T` を同時に宣言すると、コンパイラは最初の 1 つしか埋められず、呼び出し側は半分だけ埋まったタプル（`(err, nil)`）を受け取り、どの値が失敗を表すか判断できません：

```no
#{fmt-skip}
pair = () (a ?i64, b ?i64) {; 錯誤：兩個 ?T 返回參數
    a = ok(1)
    v ?= boom(); boom() 回 err('boom')
    a = v
    b = ok(2); 永不執行 —— 呼叫方看到 (err, nil)
}
```
```

正しい書き方は、独立した値をプレーンな型として宣言し、`?T` をエラーチャネルとして 1 つだけ残すことです：

```no
lookup = (k str) (value str, found bool, err ?str) {
    value = ''
    found = false
    err = nil
}
```

エラーメッセージは次の形式です：`` function 'pair' declares 2 option (?T) results ('a', 'b'); only one result may be ?T … [moptres1] ``。メソッド定義における暗黙の `self` レシーバーは呼び出し側の別名による出力パラメータであり、この枠には含まれません。`#{c}` による extern 宣言も同様に制限されます。

### エラー捕捉代入（`=` によるその場での捕捉）

`?=` のセマンティクスは「エラーを上位に投げる」ことです——これには所在する関数が option の結果パラメータを持つことが必要で、失敗時は早期 `return` します。早期リターンではなくその場でエラーを処理したい場合は、通常の `=` を使います。右辺に**エラー発生源**が含まれる限り、対象変数は自動的に `?T` と推論され、`nil` / `err` が**その場でその変数に格納され**、処理が続行されます。

```no
handle = (b i64, c i64, d i64) (r i64) {
    a = b + c / d; a 推斷為 ?i64；除零 → a = err
    a: {
        err -> {
            r = -1; 就地處理錯誤
        }

        nil -> {
            r = -1
        }

        -> {
            r = it; 成功：r = b + c/d
        }
    }
}
```

**エラー発生源（捕捉のトリガー）：**

| 発生源                   | 例                                   | 捕捉結果                          |
| --------------------- | ----------------------------------- | ----------------------------- |
| 整数除法 / 剰余             | `a = b + c / d`、`a = b % c`         | ゼロ除算、`MIN / -1` → `err`         |
| 安全なインデックス              | `a = v[i]`（`arr` / `vec` / `slice`） | 範囲外 → `err`（`code.index-out`）  |
| option 型のオペランド         | `a = x + 1`（`x ?i64`）               | `x` が `nil` / `err` の場合、そのまま `a` に格納 |
| option を返す呼び出し（算術オペランドとして） | `a = f(x) + 1`（`f` は `?i64` を返す）       | 同上                            |

> 関数の引数として**直接**渡される option は対象外です——それは呼び出された側が処理します（`?=` の素の option 引数例外と同じ）。

**純粋な算術はエラー発生源ではない**：`+ - * <<` と符号反転自体は捕捉をトリガーしません（そうでなければすべての算術が option になってしまいます）。しかし、option の経路に乗った場合（例えば右辺に別途 `/` がある、または対象が明示的に `?T` と宣言されている）、これらの演算は**実行時のオーバーフロー検査**を伴い、オーバーフロー → `err` となります：

```no
ovf = (x i64) (r i64) {
    a ?i64 = x + 1; 顯式 ?T → 走 option 包裝路徑
    a: {
        err -> {
            r = 0; x = i64-max 時溢出 → err
        }

        nil -> {
            r = 0
        }

        -> {
            r = it
        }
    }
}
```

**捕捉 vs 上位へのスロー：**

| 書き方            | 失敗時                                 | option 結果パラメータが必要 | その後の値の取得方法             |
| ------------- | ----------------------------------- | -------------- | ------------------ |
| `a ?= expr`   | 結果パラメータに `nil`/`err` を設定して `return`（早期リターン） | はい              | 該当なし（既にリターン済み）           |
| `a = expr`    | `a` にその場で `nil`/`err` を格納し、処理は続行            | いいえ              | `a: { ok -> ... }` |
| `a ?T = expr` | `=` と同じ（明示的な注釈、内部にエラー発生源の部分式を含む）               | いいえ              | 同上                 |
| `_ = expr`    | 評価はするが結果とエラーを破棄（エラーにならず、unused lint も発動しない）     | いいえ              | 該当なし                |

**適用範囲：** 安全なインデックスの捕捉は `?=` と同様、**`?T` 結果を返す関数内でのみ有効**です（〈安全なインデックス〉の第 3 の書き方を参照）。`/` `%` と option オペランドの捕捉はすべての関数に適用されます。

**既存変数の型は変更しない：** 捕捉は「この文で初めて宣言された」対象にのみ適用されます。対象がすでに存在する場合（`v i64 = 0` の後の `v = arr[i]`、または `d = 0` の後の `d = x - 1`）、コンパイラはその場で型を変更せず、セマンティクスの明示的な選択を求めるエラーを報告します（`#{overflow=...}` / `#{index-out=...}` 注釈を付ける、`?=` を使う、または `?T` と宣言する）。

### ジェネリクス

```no
arr_to_vec = (arr [n]t) (out []t) {
    i <- [0..n): {
        out[i] = arr[i]
    }
}
```

### 整数代入の型チェック

コンパイラは整数代入に対して型チェックを行い、安全でない狭小化（narrowing）によるデータ損失を防ぎます。以下が規則です：

#### 暗黙の拡大（安全、自動的に許可）

狭い整数型の値は、より広い型に自動的に代入できます。目標型の範囲が元の型の範囲を完全に含むためです：

```no
b byte = 200
i i64 = b; ✓ byte 範圍 [0,255] ⊆ i64 範圍
u u32 = b; ✓ byte 範圍 ⊆ u32 範圍
```

#### 整数リテラルの代入

整数リテラル（デフォルトでは `i64` と推論される）は、その値を含む範囲を持つ任意の整数型に代入できます：

```no
#{fmt-skip}
n u8 = 200; ✓ 200 ∈ [0,255]
m u8 = 300; ✗ 300 > 255，編譯錯誤
big u64 = 18446744073709551615; ✓ 2^64-1，u64 最大值
```
```

#### 安全でない狭小化（コンパイルエラー）

広い型の変数を狭い型に直接代入するとコンパイルエラーになります。データ損失の可能性があるためです。エラーメッセージには**実行可能な修正ヒント**が付き、ビット演算で安全に狭小化する方法が提案されます：

```no
#{fmt-skip}
d u64 = 42
h u32 = d; ✗ cannot assign u64 value to u32 variable 'h'; hint: narrow safely with a bitwise mask (e.g. `& 4294967295`) or right shift (e.g. `>> 32`)
h u16 = d; ✗ cannot assign u64 value to u16 variable 'h'; hint: narrow safely with a bitwise mask (e.g. `& 65535`) or right shift (e.g. `>> 48`)
h u8 = d; ✗ cannot assign u64 value to u8 variable 'h'; hint: narrow safely with a bitwise mask (e.g. `& 255`) or right shift (e.g. `>> 56`)
x u32 = d + 1; ✗ 加法結果仍為 u64，不安全
y u32 = foo(); ✗ 函式呼叫結果型別不匹配
```
```

> **修正ヒント**：コンパイラは目標型に基づいて正確な mask 値とシフト量を自動的に計算します。ヒントに従って mask またはシフトを適用すれば、安全に狭小化できます（次の節を参照）。
>
> **符号付き目標型**：`i8`/`i16`/`i32`/`i64` などの符号付き整数では、ヒントはビット狭小化が適用できないこと（符号ビットの切り捨てのセマンティクスが不明確）を説明し、代わりに明示的な範囲チェックの使用を提案します。

#### ビット演算による安全な狭小化（自動的に許可）

代入の右辺が**ビット演算式**（`&`、`|`、`^`、`<<`、`>>`）で、目標型が**符号なし整数**（`u8`/`u16`/`u32`/`u64`/`byte`）の場合、コンパイラは暗黙の狭小化を許可します——上位ビットの切り捨てはビット操作の標準的なセマンティクスであり、予期しないデータ損失を招かないためです：

```no
d u64 = 42

; ✓ mask 運算：結果必 ≤ mask 值，安全落入 u32
h u32 = d & 67108863; mask = 2^26-1 < 2^32
h u32 = d & 4294967295; mask = 2^32-1，正好 u32 範圍

; ✓ 位移運算：右移後高位為 0，安全
hi u32 = d >> 32; u64 >> 32 留 32 bits

; ✓ XOR / OR 組合
c u32 = a ^ b; 位元運算結果
b byte = v & 255; mask 到 byte 範圍

; ✓ 複合位元運算（常見於密碼學/編解碼）
s u32 = (key[0] & 255) | ((key[1] & 255) << 8) | ((key[2] & 255) << 16) | ((key[3] & 255) << 24)
```

> **なぜ許可されるのか？** ビット演算（mask、シフト、XOR、OR）のセマンティクスは、ビットパターンを構築することです。狭い符号なし型に代入する際に上位ビットを切り捨てるのは意図的な操作です——開発者は mask やシフトによって結果の範囲を保証するか、意図的に上位ビットを破棄しています。これは暗号学（ChaCha20、Poly1305、Blake2 など）やコーデック処理のコードにおける標準的なパターンです。

> **符号なし目標型に限ります。** 符号付き整数の目標（`i8`/`i16`/`i32`/`i64`）では、右辺がビット演算であってもエラーになります。符号ビットの切り捨てのセマンティクスが不明確なためです：
>
> ```no
> d u64 = 42
> h i32 = d & 4294967295   ; ✗ 仍報錯：有號目標不適用安全窄化
> ```

> **最上位はビット演算である必要があります。** 式の最上位の演算子が `&`/`|`/`^`/`<<`/`>>` の場合のみ許可されます。加法、減法、関数呼び出し、直接の変数参照などは対象外です：
>
> ```no
> d u64 = 42
> h u32 = d              ; ✗ 頂層是 Identifier，不是位元運算
> h u32 = d + 1          ; ✗ 頂層是 +，不是位元運算
> ```

#### `.noml` 設定ファイルの直接読み込み

`.noml` ファイルは `#` で直接読み込めます。解決順はまず同名の `.no` を探し、見つからなければ `.noml` を探します。読み込み後、
**構造体名はデフォルトでファイル名**（拡張子を除く。ファイル先頭の `#{name = '...'}` 注釈で書き換え可能）となり、各メンバーはその構造体のフィールドになります。同時に
同名のグローバル値が生成されてファイル内容を保持するため、
`server.port` で設定を読み取れます。

```noml
; cfg/server.noml
{
  host: 'localhost'
  port: 8080
  tags: [] #{type = '[]str'}
  compiler: {
    version: 'v0.1.0'
  }
}
```

```no
# /cfg/server

print(server.port); 8080
print(server.compiler.version); v0.1.0
```

- フィールド型は、まずメンバーの `#{type = '...'}` 注釈を優先します（値は完全な nolang 型式、例：
  `'[]str'`、`'[]i64'`、`'?i64'`）。注釈がない場合は値から推論されます：文字列 → `str`、整数 → `i64`、
  小数 → `f64`、真偽値 → `bool`、オブジェクト → 自動生成される入れ子構造体（`server-compiler`）、
  配列 → `[]要素型`。
- 空のコンテナ（`[]`、`{}`）には `#{type = '...'}` の記述が**必須**です。noml の値自体には型がなく、空のコンテナは
  推論できません。オブジェクトのメンバーに `#{type = 'x'}` が注釈されている場合は `x` をそのまま使用し（定義は別途必要）、
  入れ子構造体は自動生成されません。
- 入れ子オブジェクトの構造体名はファイル名を接頭辞とします（`server-compiler`）。定義順は入れ子が先、宿主が後です。
- **先頭（ファイル級）の注釈で構造体名を書き換えられます**：`#{name = '...'}`（等価な書き方 `#{type = '...'}` もあり、
  `name` が優先）を最上位の `{` の上の独立した行（または最上位の値と同じ行の末尾）に記述します。書き換え後は値のバインド名と
  入れ子構造体の接頭辞もこれに追随しますが、**インポートパスは引き続きファイル名で解決されます**：

```noml
; cfg/db.noml
#{name = 'db-options'}
{
  host: 'localhost'
}
```

```no
# /cfg/db
# /cfg/db as db2

print(db-options.host); localhost
print(db2.host); localhost
```

- 異なる 2 つのファイルが同じ型名を生成する場合（例えば異なるディレクトリ配下の同名ファイル）はエラーになります。先頭の
  `#{name = '...'}` で区別すれば回避できます。同じファイルが複数回インポートされた場合（例えば `as` エイリアスを追加した場合）は、型定義は 1 つだけマージされます。
- キー名は nolang の規則に従って小文字のハイフン区切り（`anonymous-fn-type`）に変換されます。数字で始まる場合は `f-` を付け、
  キーワードと同名の場合は `x-` を付けます。
- `as` エイリアスで値のバインド名を書き換えられますが、構造体名は変わりません：`# /cfg/server as cfg`。
- `.noml` の型はモジュール接頭辞に関与しません。ファイル名が標準ライブラリのモジュールと同名（例：`server`）でも、型は裸の名前のままです。
- `package.noml` / `workspace.noml` にも `#{...}` 注釈（例：`#{type = '[]str'}`）を記述できます。
  解析時は無視され、外部ツールが強く型付けされた構造を再構築するためのものです。構文は nolang の `#{...}` と完全一致します。

### FFI（`#{c}` 注釈）

`#{c}` 注釈によって外部 C 関数を宣言し、FFI（Foreign Function Interface）を実現します。

**構文**：`#{c}` は独立した行に記述し、次の行を FFI 宣言としてマークします。`#{c}` は注釈システムにおける FFI の言語キーであり、`#{cpp}`、`#{rust}` などの他言語もサポートします。旧構文 `#c` も引き続き後方互換です。

**非公開宣言**：名前が `_` で始まるものは非公開（エクスポートされない）を表し、C ABI シンボルは接頭辞 `_` が自動的に除去され、ハイフンがアンダースコアに変換されます。

**別ファイルは不要**：FFI 宣言と通常のコードを同じ `.no` ファイルに記述できます。

**ポインタ型の構文**：FFI では C スタイルの `*T`、`**T`、`***T` でポインタを表します。具象型 `T` が必要です。通常のコードではこの構文は使用できません。

| 構文        | 意味          | LLVM IR | 用途                  |
| --------- | ----------- | ------- | ------------------- |
| `*byte`   | byte へのポインタ | `i8*`   | 不透明ポインタ（例：db handle）  |
| `**byte`  | 二重ポインタ        | `i8**`  | 出力パラメータ（例：`sqlite3**`） |
| `***byte` | 三重ポインタ        | `i8***` | 極めてまれな三重間接            |

```no
; sqlite.no — FFI 綁定與安全包裝在同一檔案
; 編譯器自動將連字號 (-) 轉為底線 (_) 以匹配 C ABI 符號
; 以 _ 開頭的名稱為私有，C ABI 符號自動去除前綴 _

; 基本型別參數
#{c}
c-strlen = (s str) (n i64)

; 指針參數（*byte = 不透明指標），私有宣告
#{c}
_sqlite3-close = (db *byte) (rc i32)

; 雙重指針（**byte = 輸出參數，呼叫後值自動存回變數），私有宣告
#{c}
_sqlite3-open = (filename str, db **byte) (rc i32)

; 多個指針參數，私有宣告
#{c}
_sqlite3-exec = (db *byte, sql str, callback *byte, arg *byte, errmsg *byte) (rc i32)
```

```no
; 同一檔案中的安全包裝

open = (dsn str) (d db-sqlite) {
    handle i64 = 0
    rc i32 = _sqlite3-open(dsn, handle)
    rc != SQLITE-OK -> {
        return
    }
    d.handle = handle
}
```

**規則：**

1. `#{c}` は独立した行に記述し、次の行を FFI 宣言としてマークします（旧構文 `#c` も後方互換）
2. FFI は宣言のみで、関数本体は持たない
3. ポインタには具象型が必要（例：`*byte`）。裸の `ptr` は不可
4. `**byte` は出力パラメータに使用：呼び出し後、C 関数が書き込んだポインタ値が自動的に `i64` に変換されて呼び出し側の変数に保存される
5. すべてのポインタは Nolang 側で `i64` として保存される（`ptrtoint`）
6. `str` 型のパラメータは自動的に null 終端の `i8*` に変換される
7. 名前が `_` で始まるものは非公開（エクスポートされない）を表し、C ABI シンボルから接頭辞 `_` が除去される
8. FFI 宣言と通常のコードを同じ `.no` ファイルに記述できる

> 逆方向（C / C++ / Rust / Go / Java / Python / C# から Nolang を呼び出す）には `#{cabi='symbol'}` と `no build --shared` を使います。[ホスト言語から Nolang を呼び出す](./host-interop)を参照してください。

### 注釈システム（`#{...}`）

`#{...}` は汎用の注釈システムで、カンマ区切りのキーと値のペアのリストです。以下の値の型をサポートします：

| 構文  | 型  | 例                                   |
| --- | --- | ------------------------------------ |
| 単独キー | 真偽値  | `#{debug}`                           |
| 真偽値 | 真偽値  | `#{inline=true}` / `#{inline=false}` |
| 数値  | 整数  | `#{max=100}`                         |
| テキスト  | 文字列  | `#{name='hello'}`                    |
| 識別子 | 識別子 | `#{mode=fast}`                       |
| 配列  | 配列  | `#{derive=[Serialize, Deserialize]}` |
| 範囲  | 範囲  | `#{range=[0..256)}`                  |

複数のキーと値のペアはカンマで区切ります：

```no
#{derive=[Serialize, Deserialize], range=[0..256), max=100, debug}
```

#### 注釈の位置

`#{...}` は次の 2 つの書き方のみが許可されます：

- **上**：独立した行として、対象（文、構造体フィールド、列挙型のメンバー、宣言、match アーム）の上に置く；
- **後ろ**：対象と同じ行の末尾に記述（`res = arr[i] #{index-out=zero}`、`a pt #{inline}`、  
  `green #{deprecated}`）。

対象の**手前の同じ行**（接頭辞、例：`#{index-out=zero} res = arr[i]`）に書くのは**コンパイルエラー**で、コンパイラと  
LSP は同じ診断を報告します。判定方法：注釈グループの `}` の後、同じ行にコードがあってはなりません（改行、  
`;` 行コメント、または直後に続く別の注釈グループはコードとはみなされません）。

```no
; ✓ 上方：獨立成行
#{overflow=wrap}
x i8 = a + 100

; ✓ 後方：同一行尾隨
x i8 = a + 100 #{overflow=wrap}
```

```no
#{fmt-skip}
; ✗ 前方：同一行前綴 → 報錯
#{overflow = wrap} x i8 = a + 100
```

構造体フィールドと列挙型のメンバー（C スタイル列挙型の値、タグ付き列挙型のバリアント）の注釈も、上または後ろのみが許可されます  
（`a pt #{inline}`、`a pt #{inline=true}`、`green #{deprecated}`、`ok(v i64) #{inline}`）。  
なお `#{inline}` の**値**も同様にサポートされます。`#{inline=false}` は有効です（下文の  
〈構造体フィールドの `#{inline}`〉を参照）。

`if <cond> { ... }` の書き方で、注釈が条件と `{` の間に挟まれている場合（`if x > 0 #{overflow=wrap} {`）も  
「手前」の位置であり、同様にエラーになります。この箇所のスキャンは寛容で、以前は注釈グループ全体を飲み込んでしまい——効果もエラーも出ず、  
最も気づきにくい失效の 1 つでした。

範囲構文は 16 種類の括弧の組み合わせをサポートします（規則：`[` は左端点を含み、`(` は含まない。`]` は右端点を含み、`)` は含まない）：

**有界区間（4 種類）** — 両端に値がある：

- `[a..b]` — 両端が閉区間（`x >= a && x <= b`）
- `[a..b)` — 左閉右開（`x >= a && x < b`）
- `(a..b]` — 左開右閉（`x > a && x <= b`）
- `(a..b)` — 両端が開区間（`x > a && x < b`）

**上限なし区間（4 種類）** — 右端点を省略：

- `[a..]`、`[a..)` — 左を含み、上限なし（`x >= a`）
- `(a..]`、`(a..)` — 左を含まず、上限なし（`x > a`）

**下限なし区間（4 種類）** — 左端点を省略：

- `[..b]`、`(..b]` — 下限なし、右を含む（`x <= b`）
- `[..b)`、`(..b)` — 下限なし、右を含まない（`x < b`）

**完全無界区間（4 種類）** — 両端とも省略し、型の最小値／最大値に基づく：

- `[..]` — 型の最小値 ≤ x ≤ 型の最大値（両端とも含む）
- `[..)` — 型の最小値 ≤ x < 型の最大値
- `(..]` — 型の最小値 < x ≤ 型の最大値
- `(..)` — 型の最小値 < x < 型の最大値

#### 注釈のスコープ

注釈の**位置**が宿主を決定し、宿主の**種類**がその適用範囲を決定します。全部で 4 層あり、外側から内側へ向かって適用され、
近いものが優先的に上書きします。関数本体は継承における硬い境界です：

| 階層 | ホスト | 適用範囲 |
| --- | --- | --- |
| **L0 モジュール級** | ファイル先頭 | このファイルのすべての宣言と文（ファイル先頭の注釈 + 1 行の空行） |
| **L1 宣言級** | 定数／グローバル変数、構造体、インターフェース、タグ付き列挙型、関数、メソッド | その宣言の定義全体（関数は関数本体とすべての入れ子ブロックを含む） |
| **L2 ブロック級** | コルーチングループ、if グループ、`cond -> body`、match、`for`／カウント／範囲ループ | そのブロック内のすべての文（入れ子ブロックを含み、内側の L1 境界で止まる） |
| **L3 単行級** | 単一文（`let`、代入、`?=`、`return`、呼び出し、`cond ->` アーム） | その文自身とその式 |

```no
; L1：整個函式
#{overflow=wrap}
sum = (xs []i64) (total i64) {
    ; L3：只管下一條陳述
    #{overflow=wrap}
    total = xs.len() - 1
    ; L2：整個循環體
    #{overflow=wrap}
    i <- [0..xs.len()): {
        total = total + xs[i]
    }
}
```

完全な判定規則、キー × 階層のマトリクス、および現行実装との差分については、
[〈注釈とコメントのスコープ〉](annotation-scope.md)を参照してください。

FFI 注釈 `#{c}` は注釈システムの特殊な形式です。注釈に FFI 言語キー（`c`、`cpp`、`rust` など）が含まれ、その後に関数宣言が続く場合、コンパイラはこれを FFI バインディングとして認識します：

```no
; #{c} 帶額外註解
#{c, debug}
_sqlite3-open = (filename str, db **byte) (rc i32)
```

#### 注釈の宣言への付加

非 FFI の注釈は直後に続く宣言（変数宣言、構造体定義）に自動的に付加されます。`num`、`i64` などの数値型に対して範囲制限などのメタデータを付与するために使えます：

```no
; 變數宣告帶 range 註解
#{range=[0..256)}
x num = 42

; 結構體定義帶註解
#{derive=[Serialize, Deserialize]}
point {
    x i64
    y i64
}

; 結構體欄位帶 range 註解（可用於 num 等數值型別）
person {
    age num #{range=[0..150]}
    score i64 #{range=[0..256)}
    name str
}
```

`range` 注釈は特に `num` 型（`num = int | float`）に適しており、数値の有効範囲を表すために使います。範囲の値は整数または識別子にできます：

```no
; 使用常量識別字作為範圍邊界
#{range=['i8.MIN'..'i8.MAX']}
val i8 = 100
```

#### ファイル埋め込み（`#{embed=...}`）

`#{embed=...}` 注釈はコンパイル時に外部ファイルの内容を `[]byte` の読み取り専用定数として埋め込みます。Go の `//go:embed` に似ています。埋め込まれたデータは直接実行ファイルにコンパイルされ、実行時にファイルを読むことなく単一バイナリ配布を実現します。

**構文**：

```no
#{embed='path/to/file'}
ICON []byte

; 或使用裸路徑（無引號）
#{embed='assets/icon.ico'}
ICON []byte
```

`embed` 注釈は直後に続く `[]byte` 変数宣言に付加されます。変数宣言に明示的な初期値を付けることは**できません**——値は埋め込まれたファイルの内容から提供されます。

**パス解決**：

- 相対パスはパッケージルートディレクトリ（`package.noml` のあるディレクトリ）を基準に解決されます
- 絶対パスをサポートします
- パスには `/`、`.`、`-` の文字を含められます

**例**：

```no
; 嵌入 Windows 圖標
#{embed='assets/win-icon.ico'}
WIN-ICON []byte

; 嵌入 SSL 證書
#{embed='certs/server.pem'}
SERVER-CERT []byte

; 嵌入配置文件
#{embed='config/default.json'}
CONFIG []byte

; 使用嵌入數據
print('icon size: ', len(WIN-ICON))
print('first byte: ', WIN-ICON[0])
```

**注意事項**：

1. 埋め込みデータは**読み取り専用**の定数で、読み取り専用のメモリ領域を指します。埋め込みデータへの書き込み動作は未定義です（Go の `//go:embed` と同じセマンティクス）
2. 埋め込み変数はヒープ解放に関与しません——プログラム終了時に埋め込みデータのポインタが free されることはありません
3. `[]byte` 型の宣言のみをサポートします（`[N]byte` の固定長配列も可）
4. ファイルはコンパイル時に存在する必要があり、存在しない場合はエラーになります
5. 明示的な初期値と共存できません（例：`ICON []byte = [1, 2, 3]` はエラー）

#### ディレクトリ埋め込み（`#{embed='dir'}`）

`#{embed=...}` はディレクトリ全体の埋め込みもサポートします。パスがディレクトリを指す場合、コンパイラはそのディレクトリ配下のすべてのファイルを再帰的に読み取り、`fs.embed` 型の読み取り専用ファイルシステムとして埋め込みます。実行時に `read()`、`exists()` メソッドでパスを指定して埋め込みファイルにアクセスでき、C 関数は不要です——検索ロジックは完全に Nolang で実装されています。

**構文**：

```no
; 嵌入整個前端目錄
#{embed='../frontend/dist'}
DIST fs.embed

; 從嵌入的文件系統讀取文件
data = DIST.read('index.html')

; 檢查文件是否存在
ok = DIST.exists('css/style.css')
```

**`fs.embed` 型**：

`fs.embed` は Nolang 標準ライブラリの `fs` モジュールで定義された構造体で、埋め込みファイルのメタデータ（パス、オフセット、長さ）を保持します。コンパイラはコンパイル時にディレクトリを読み取り、すべてのファイル内容を連結して定数のグローバル変数とします。実行時は純粋な Nolang で実装された `read` メソッドが走査して検索します。

| メソッド       | シグネチャ                                  | 説明                |
| -------- | ----------------------------------- | ----------------- |
| `read`   | `(path str) (data ?[]byte)`           | 埋め込みファイルを読み取り、内容を返す（見つからない場合は nil） |
| `exists` | `(path str) (yes bool)`             | 埋め込みファイルが存在するか確認する       |

**例**：

```no
; HTTP 靜態文件伺服器：將前端文件嵌入單一二進制
#{embed='../frontend/dist'}
DIST fs.embed

serve = (conn server-conn) {
    conn.parse()
    path = conn.path
    path == '/' -> path = '/index.html'

    ; 去掉前導 / 得到相對路徑
    rel = path.slice(1, path.len-bytes())

    ; 從嵌入的文件系統讀取
    data []byte = DIST.read(rel)
    {
        ok -> it

        -> {
            conn.write-html(404, 'Not Found')
            conn.close()
            return
        }
    }
    conn.write-status(200)
    conn.write-header('Content-Type', get-content-type(path))
    conn.write-body(data)
    conn.close()
}
```

**注意事項**：

1. ディレクトリ内のすべてのファイル（サブディレクトリを含む）が再帰的に埋め込まれます。パスは埋め込みディレクトリからの相対パスで保存されます（例：`css/style.css`）
2. パスの区切り文字はスラッシュ `/` に統一されます（クロスプラットフォームで一貫）
3. `fs.embed` 型の変数は読み取り専用で、ヒープ解放には関与しません
4. 単一バイナリ配布のシナリオに適しています（HTTP 静的ファイルサーバー、CLI ツールのリソース埋め込みなど）

#### プラットフォーム注釈

プラットフォーム注釈はコンパイル時のフィルタで、対象プラットフォームに基づいてコードを含めるかどうかを決定します。**フラット化キー**（例：`#{mac-arm64}`）を使って OS とアーキテクチャを同時に指定するため、曖昧さがなく、直後に続く宣言に付加されます。一致しないコードはコンパイルに完全に関与しません——LLVM IR は生成されず、型チェックも行われません。

**サポートされるプラットフォームキー（6 種類のフラットな組み合わせ）：**

| キー                | 一致する対象                         |
| ---------------- | -------------------------- |
| `#{linux-amd64}` | Linux x86_64               |
| `#{linux-arm64}` | Linux ARM64                |
| `#{win-amd64}`   | Windows x86_64             |
| `#{win-arm64}`   | Windows ARM64              |
| `#{mac-amd64}`   | macOS x86_64（Intel）        |
| `#{mac-arm64}`   | macOS ARM64（Apple Silicon） |

```no
#{mac-arm64}
print('running on macOS ARM64')

#{linux-amd64}
print('running on Linux x86_64')

#{win-amd64}
print('running on Windows x86_64')

; 平台特定的變數
#{mac-amd64, mac-arm64}
sep = '/'

#{win-amd64, win-arm64}
sep = '\\'

; 平台特定的函數
#{mac-arm64, mac-amd64}
greet = () {
    print('hello from mac')
}

#{linux-amd64, linux-arm64}
greet = () {
    print('hello from linux')
}

greet()
```

同じ宣言上の複数のキーは **OR** 関係です——いずれかが一致すれば含まれます。各キーが OS とアーキテクチャを同時に指定しているため、AND ロジックは不要です。

| 注釈                          | 意味                                |
| --------------------------- | --------------------------------- |
| `#{mac-arm64}`              | macOS ARM64 のみ                     |
| `#{mac-amd64, mac-arm64}`   | macOS の任意のアーキテクチャ                        |
| `#{linux-amd64, win-amd64}` | Linux x86_64 **または** Windows x86_64 |
| `#{mac-arm64, linux-arm64}` | macOS ARM64 **または** Linux ARM64     |

```no
; macOS 和 Linux（所有架構）都執行
#{mac-amd64, mac-arm64, linux-amd64, linux-arm64}
shared = () {
    print('unix-like')
}

; 僅 Windows x86_64
#{win-amd64}
reg-key = () {
    print('reading registry on win/x64')
}

; 僅 macOS ARM64（Apple Silicon）
#{mac-arm64}
neural = () {
    print('Apple Neural Engine available')
}
```

`os.get-arch()` を使うと実行時に現在のアーキテクチャを取得でき、プラットフォーム注釈を使うとコンパイル時にコードを含めたり除外したりできます。

## package.noml コンパイラ設定

`package.noml` の `compiler` ブロックはコンパイラの動作を制御します。`version` の値は先頭に `v` を付ける慣例です（例：`"v0.1.0"`）。コンパイラ内部の解析では接頭辞を区別せず、`"v0.1.0"` と `"0.1.0"` は同じバージョンとして扱われます。

```noml
{
  compiler: {
    version: 'v0.1.0'
    emit: 'js'
  }
}
```

### `emit`

出力先のバックエンドを制御します：

| 値           | 説明                                      |
| ----------- | --------------------------------------- |
| `""`（空、既定値） | LLVM バックエンドを使用してネイティブ実行ファイルを生成                      |
| `"js"`      | JS バックエンドを使用して JavaScript を生成（型消去）、LLVM ツールチェーン不要 |

`"js"` に設定すると、`no build` は自動的に JS バックエンドを使い、コマンドラインの `--js` と同等になります。コマンドラインフラグは設定ファイルより優先されます。

```noml
; 自動生成 JavaScript
compiler: {
  emit: 'js'
}
```

### `anonymous-fn-type`

匿名関数型の構文（例：`cb ()()`）を許可するかどうかを制御します。デフォルトは `false`（無効）で、名前付きの関数型エイリアスを使用する必要があります。

### `link-libs`

リンクする C ライブラリのリストを指定します：

```noml
compiler: {
  link-libs: ['crypto', 'ssl']
}
```

## コンパイル時の変数注入（-ld）

`no build`、`no run`、`no test` は `-ld-KEY=VALUE` フラグによってコンパイル時にグローバル定数を注入できます。注入された変数はソースコードの先頭で `KEY = VALUE` を宣言したのと同等で、プログラム内で直接使えます。

### 構文

```bash
no build -ld-KEY=VALUE [更多 -ld...] <file>
```

- `-ld` 接頭辞の直後に変数名と値を続け、`=` で区切ります
- 複数の `-ld` フラグを同時に使用できます
- 真偽値の省略形：`-ld-DEBUG`（`=VALUE` を含まない）は `-ld-DEBUG=true` と同等です

### 値の型推論

| 値の形式             | 推論される型            | 例                  |
| ---------------- | --------------- | ------------------- |
| 整数               | `i64`           | `-ld-COUNT=42`      |
| 浮動小数点数              | `f64`           | `-ld-PI=3.14`       |
| `true` / `false` | `bool`          | `-ld-DEBUG=true`    |
| その他               | `str`（単一引用符の文字列リテラル） | `-ld-VERSION=0.1.2` |

### 例

```no
; 假設使用 -ld-VERSION=0.1.2 -ld-COUNT=42 -ld-DEBUG=true 編譯
print('VERSION:', VERSION); 輸出: VERSION: 0.1.2
print('COUNT:', COUNT); 輸出: COUNT: 42
print('DEBUG:', DEBUG); 輸出: DEBUG: 1 (bool 在原生後端印為 1)
```

```bash
; 注入多個變數
no build -ld-VERSION=0.1.2 -ld-COUNT=42 -ld-DEBUG=true main.no

; 布林簡寫
no run -ld-RELEASE main.no

; JS 後端也支援
no build --js -ld-VERSION=0.1.2 main.no
```

### ソースコードの宣言との関係

`-ld` で注入された変数とソースコードの宣言の相互作用の規則：

- **ソースコードに同名の宣言がある場合**：注入された値がソースコード内のその変数の値を**その場で置き換えます**。よく使われるパターンは、ソースコードでプレースホルダ変数（例：`VERSION = ''`）を宣言し、ビルド時に `-ld-VERSION=0.1.2` で値を代入することです。
- **ソースコードに存在しない場合**：注入された変数は AST の先頭に前置され、新しいグローバル定数宣言としてすべての後続のコンパイルパス（型推論、検証、モジュール結合、codegen）に参与します。
- **注入しない場合**：ソースコード内の宣言はそのまま保持され、影響を受けません。

```no
; 源碼聲明占位變數
VERSION = ''
COUNT = 0

print('VERSION:', VERSION)
print('COUNT:', COUNT)

; no build -ld-VERSION=0.1.2 main.no
; 輸出: VERSION: 0.1.2  （注入值覆蓋了源碼的 ''）
;       COUNT: 0        （未注入，保持源碼值）
```
