# アノテーションとコメントのスコープ

`#{...}` アノテーション自体は「どこまで範囲を持つか」という情報を持ちません。範囲は**どのノードに付着しているか**によって決まります。
このページではそのルールを固定します。すなわち、一つの位置、一つの判定ルール、四つのレベル、そして「あるキーはそのうちのいくつかのレベルしかサポートしないことがある」という条項（`overflow` が L3 のみを認める例、§4.1 参照）です。これにより、作者、`no fmt`、`no vet`、codegen、LSP が同じ行のアノテーションに対して同じ答えを出せるようにします。

> なぜ固定が必要か：同じ `#{overflow=wrap}` について、`no vet` は関数全体を管すると判断し、codegen は次の一行だけを管すると判断した場合、「vet はすべて緑なのに、実行時には相変わらず `err` が返る」という静かなセマンティクスの逸脱が発生します。
> スコープはアノテーションの属性ではなく、**読み手間の共通認識**です。共通認識を文書化しないと、それぞれが勝手に逸脱していきます。

---

## 1. 一つの原則：スコープはホストが決める

アノテーションが置ける場所は二通りだけです（位置ルール自体は [`syntax.md`](syntax.md) の〈アノテーションの位置〉を参照）：

```no
; ① 上方：獨佔一行，置於目標之上
#{overflow=wrap}
x i8 = a + b

; ② 尾隨：寫在目標同一行的後方
x i8 = a + b #{overflow=wrap}

; 多行目標（函式、區塊）的尾隨寫在收尾 `}` 之後
greet = () {
    print('hi')
} #{mac-arm64}
```

**両者は完全に等価**です。同じキー、同じホスト、同じスコープであり、`no fmt` が一方を他方に書き換えることもありません（行末に置いたものは行末に、直上に置いたものは直上に残ります）。どちらを選ぶかは可読性だけを見て決めます。短い文では行末に置く方が一行節約でき、式全体に注釈を付けたい場合や文が長い場合は直上に置きます。

**対象の直前の同じ行に書くのはコンパイルエラー**です。「前置したものが後ろに作用する」という道は存在しません。

```no
#{overflow = wrap} x i8 = a + b   ; ✗ 前綴 → 報錯
```

判定は三段階で、それぞれ答えは一つだけです：

| 手順 | 問い | 答えの出所 |
| --- | --- | --- |
| 1 | ホストは誰か？ | 位置：直上にあるアノテーションでも注釈でもない最初の行の文、または同じ行の直前の文 |
| 2 | ホストはどのレベルに属するか？そのキーはこのレベルをサポートするか？ | §2 の表 + §4 のマトリクス（非サポートならコンパイルエラー） |
| 3 | どこまで及ぶか？ | ホストの部分木から内側のハード境界を引いたもの（§3） |

## 2. 四つのレベル

| レベル | ホスト | 有効範囲 | 記述例 |
| --- | --- | --- | --- |
| **L0 モジュール級** | ファイル先頭 | 当該ファイルの全宣言と文 | ファイルの最上位に置き、後続の内容との間に一行空ける |
| **L1 宣言級** | 定数/グローバル変数、構造体、インターフェース、タグ付き列挙型、関数、メソッド | その宣言の定義全体（関数は関数本体とすべてのネストしたブロックを含む） | 宣言の直上に密着させるか、宣言行の行末に置く |
| **L2 ブロック級** | コルーチングループ、if グループ、`cond -> body`、match、`for`/カウント/範囲ループ、裸ブロック | そのブロック本体内の全ての文（ネストしたブロックを含み、内側の L1 境界で止まる） | ブロック頭の文の直上に密着させるか、ブロック末尾の `}` の後に書く |
| **L3 単行級** | 単一文（`let`、代入、`?=`、`return`、呼び出し、`cond ->` アーム） | その文自身とその式 | 文の直上に密着させるか、同じ行の行末に置く |

### L0 モジュール級

位置は**ファイルの先頭**（前に文や import が一切ないこと）で、かつアノテーションのグループと最初の文の間に**少なくとも一行の空行**が必要です。ここでの空行は「スコープの終端記号」であり、このアノテーション群が次の文ではなくファイル全体に属することを示します。

```no
#{win-amd64}

; ↑ 空行 → 模組級：本檔只在 Windows x86_64 編譯
; 以下所有宣告與語句都在管轄內
helper = () {
    print('windows only')
}

label = 'win'
```

空行がなければ通常の L1（最初の宣言に付着）となります。この境界により、既存のコードを移行する必要がありません。

```no
#{buildin}
bool.to-str = () (out str) {
}
```

モジュール級は「ファイル全体に対して意味を持つ」キーにのみ有用です（現時点ではプラットフォームキーのみ）。宣言キー（`buildin`、`generic`、`embed`…）が L0 に現れるのはエラーであり、「範囲を拡大する」ことではありません。`overflow` も L0 を受け付けません。L3 のみを認めます。

ファイルをまたぐ設定はアノテーションの対象外で、`package.noml` に記述します。

### L1 宣言級

```no
; 整個結構體：欄位佈局由型別標記決定
#{inline}
holder {
    inl point
    out point
}

; 整個函式：進出日誌自動帶呼叫者
#{track-caller}
log.write = (msg str) {
    ...
}

; 整個常量宣告：嵌入目錄（路徑相對 package.noml）
#{embed='assets'}
ASSETS fs.embed

; 編譯期剔除整棵子樹（含函式體）
#{mac-arm64, linux-arm64}
greet = () {
    print('hello from unix')
}
```

L1 の内部にはさらに**メンバー単位の粒度**があります。構造体のフィールド、タグ付き列挙型のバリアント、C 形式列挙型のメンバーに付けたアノテーション（`a pt #{inline}`、`ok(v i64) #{inline}`）は、型全体ではなくそのメンバーを管します。メンバーのアノテーションも配置は二通りだけで、メンバーの直上一行に密着させるか、そのメンバーと同じ行の後ろに書きます（慣例として行末が使われます）。

### L2 ブロック級

ホストが「ブロック頭の文」である場合、スコープはブロック本体全体です。

```no
; 整塊被排除（不生成 IR，也不做型別檢查）
#{win-amd64}
2 * {
    print('windows only')
}

; if 組同樣以整組為單位
x = 1
#{win-amd64}
{
    x == 1 -> print('arm-1')
    -> print('arm-other')
}
```

四種類のブロック頭すべてに適用されます。コルーチングループ（`awy { ... }`）、if グループ（`{ cond -> … }`）、単一条件文（`cond -> body`）、match、`for` / カウント / 範囲ループです。

`cond -> body` の body が単一文だけなら、L2 と L3 の結果は同じです。ブロックとして書いた場合にだけ違いが生じます。

**すべてのキーが四つのレベルを全部使うわけではありません。** あるキーはそのうちのいくつかのレベルしかサポートしないことがあり、サポートしないレベルに書くのは**コンパイルエラー**です。「一行多く書くだけの無害な冗長性」ではありません。現時点で唯一の制限付きキーは `overflow` で、L3 のみを認めます。理由は §4.1 を参照してください。

### L3 単行級

```no
a i8 = 100
b i8 = 100
; 只管緊跟的下一條陳述（尾隨寫法 `c = a + b #{overflow=wrap}` 等價）
#{overflow=wrap}
c = a + b
c: {
    ok -> print('wrap:' - (it == -56).to-str())
    nil -> print('nil')
    err -> print('err')
}
```

ブロック内で独立した一行になっているアノテーションは、「直後に続くあの一文」だけを認めます。間に無関係な注釈行が挟まっていても（たとえば `#{overflow=wrap}` の後に別の `#{...}` が続く場合でも）途切れず、最初の実際の文を探し当てます。ただし、次のアノテーション自身も同じキーを持つ場合は、前者はいかなる文も管しません（後者が優先されます）。

⚠️ **ブロック match `{ … }: { … }` は「一文」であり、透過されません**：アノテーションをその `{` の直上に書いた場合、ホストはそのブロック文自体であり、ブロック内の `?=` の式へ**沈み込むことはありません**（実測：`#{overflow=wrap}` をブロック外に置くと、ブロック内の `np ?= np + 1` は相変わらずオーバーフロー → `err` となり、対象はゼロクリアされます）。`overflow` をブロック内の式に適用するには、ブロック内その `?=` の真上に書いてください。二つの消費形態の違いは [syntax.md](syntax.md) の〈ブロック match と値位置 match の取捨〉を参照してください。

## 3. 継承、上書き、ハード境界

**外側から内側へ継承し、近いものが優先されます。** 複数レベルをサポートするキー（プラットフォームキー）では、L0 → L1 → L2 → L3 と段階的に有効になります。同じノード上に同名のキーが現れた場合、後者が前者を上書きします（`#{mac-arm64} #{mac-arm64, win-amd64}` では後者が優先されます）。

**関数本体はハード境界です。** L2 ブロックのスコープは**構文上の部分木**で止まります。呼び出し関係に沿って拡散することも、いかなる関数 / メソッド / 匿名関数の定義本体に入り込むこともありません。関数本体内部でどのモードを使うかは、その関数自身の L1 アノテーションか内部の L3 アノテーションだけで決まり、それを呼び出しているブロック上のアノテーションとは無関係です。

```no
; L1：整個函式連同函式體一起被剔除（macOS 上不生成 IR）
#{win-amd64}
windows-only = () {
    print('never compiled on mac')
}

; 沒有自己的 L1 註解 → 任何平台都編譯，也不會因為被誰呼叫而改變
always = () {
    print('always compiled')
}
```

理由：外側のアノテーションが関数本体まで透過できると、呼び出し側の一行が呼び出される関数のセマンティクスを静かに変更してしまい、デバッグ時にまったく見抜けなくなります。L1 アノテーションは逆です。その関数頭に直接書かれており、宣言の一部だからです。

**ハード境界の一覧**（継承はここで止まる）：関数本体、メソッド本体、匿名関数/lambda 本体、`#{c}` による外部宣言。
**非境界**（通常どおり継承）：`{}` 裸ブロック、if グループ、match アーム、ループ本体。

## 4. キー × レベル マトリクス

`✓` 有効 ／ `✗` 不正（コンパイルエラーにすべき）／ `—` そのレベルでは無意味（同様にエラーにすべきで、黙って捨ててはならない）

| キー | L0 モジュール | L1 宣言 | L2 ブロック | L3 単行 |
| --- | --- | --- | --- | --- |
| `overflow` | ✗ | ✗ | ✗ | ✓ |
| プラットフォームキー（`mac-arm64` など） | ✓ | ✓ | ✓ | ✓ |
| `buildin` | ✗ | ✓ 関数 / タグ付き列挙型 / レイアウト構造体 | ✗ | ✗ |
| `inline` | ✗ | ✓ 構造体 / フィールド / バリアント / 関数 | ✗ | ✓ メンバーの行末 |
| `generic` | ✗ | ✓ 関数 / 構造体 | ✗ | ✗ |
| `track-caller` | ✗ | ✓ 関数 | ✗ | ✗ |
| `embed` | ✗ | ✓ トップレベルの `let` | ✗ | ✗ |
| `bind` | ✗ | ✓ import 行 | ✗ | ✗ |
| `c` / `cpp` / `rust` | ✗ | ✓ 直後の関数宣言 | ✗ | ✗ |
| `fmt-skip` | ✗ | ✗ | ✓ markdown のフェンスブロック | ✗ |
| メタデータ（`derive` / `range` / `max` / `debug`…） | ✗ | ✓ 宣言 / メンバー | ✗ | ✗ |
| `index-out` | — | — | — | — D11 で削除済み、出現即エラー |

「不正」も「無意味」も**エラーにしなければならず**、黙って無効化してはいけません。for ループの直上に書かれた `#{buildin}` がこっそり無視されると、作者は組み込み宣言が有効だと思い込んでしまいます。

### 4.0 `#{buildin}` の三つの担い手、および「レイアウト構造体」の特異性

`#{buildin}` は宣言に付けられますが、三つの担い手に対するセマンティクスはまったく異なります。

| 担い手 | セマンティクス | 例 |
| --- | --- | --- |
| 関数 | 空本体のスタブ：コンパイラ / FFI が実装を提供し、Nolang 側では関数本体を生成しない | `#{buildin}`<br/>`fs.remove = (p str) (ok bool) { }` |
| タグ付き列挙型 | バリアントはマッチングと網羅性チェックに用い、背後の表現と構築は組み込み runtime が提供 | `#{buildin}`<br/>`option { ok(v t), nil, err(e err.err), }` |
| **レイアウト構造体** | **単なるレイアウトの文書**：この `struct` はセマンティクス上存在せず、唯一の産出はフィールドの型（`t.len` は `u8`） | `#{buildin}`<br/>`txt { data [255]byte; len u8 }` |

三つ目は個別に説明する必要があります。前の二つと方向が逆だからです。関数のスタブとタグ付き列挙型は「コンパイラが実際にこの宣言を使う」のに対し、レイアウト構造体は「コンパイラはこの宣言を**使わず**、単にフィールド型の供給元と読みやすいレイアウトの説明にすぎない」ものです。真のレイアウトとドキュメントのリンク先は別の場所にあります。

| 型 | 真のレイアウトの出所 | ドキュメント / リンクの出所 |
| --- | --- | --- |
| `str` | MIR の手書きディスクリプタ `%str-long = { i32 len, i32 cap, i8* data }` | `parser.BuiltinTypes()` |
| `vec` | MIR の手書きディスクリプタ `%vec = { i32 len, i32 cap, i64 data }` | `parser.BuiltinTypes()` |
| `txt` | MIR の手書きディスクリプタ `%txt = { [255 x i8] data, i8 len }` | `parser.BuiltinTypes()` |
| `arr` | ディスクリプタなし：`[n]t` そのものが裸の集約 `[N x T]` であり、`.len` はコンパイル時定数 `n` | `parser.BuiltinTypes()` |

`parser.BuiltinTypes()`（`src/parser/builtintype.go`）は「名前 → std モジュール → モジュールのドキュメントアンカー → レイアウト」の唯一の登録表であり、LSP の hover / 定義へジャンプ / 補完と `IsBuiltinLayoutStructName` はすべてこれを読みます。だからこそレイアウト構造体は**もはやリンクを担いません**。それを削除しても hover と F12 は相変わらず動作します。ただし checker が `t.len` のフィールド型を失うため、現時点では残されています。

ここから二つの厳格なルールが導かれます。どちらかが破られても、真のレイアウトと矛盾する「影の構造体」が即座に生じます。

1. **`#{buildin}` を付けた struct は組み込みレイアウト名を使わなければなりません**（`str` / `vec` / `txt` / `arr`）。別の struct に付けるのはエラーです。その宣言は MIR によって「レイアウトはコンパイラが保持する」と見なされてスキップされ、フィールドがすべて無効になり、作者には `unknown field` の山が残されます。
2. **組み込みレイアウト名で struct を宣言するには `#{buildin}` が必要です**。ユーザーが裸の `str { … }` を書くと、それは当該モジュールの通常の型として扱われプレフィックスが付き（`m.str`）、codegen は `%str-long` と衝突する `%m_str` を生成します。

どちらも `checker.ValidateBuiltinStructDecls` がエラーを報告し（`1a8m445h` / `3lu6n4np`）、`no build` と `no vet` の両方が検出します。逆に、**`#{buildin}` + レイアウト名という組み合わせだけ**が、モジュールのプレフィックス処理段階と MIR の `collectStructFields` によってスキップされます（`src/build/module_prefix.go` の Phase 1 と `src/mir/hir2mir.go` の `isBuiltinLayoutStruct` を参照）。判定基準は名前そのものではなく、「アノテーション + 名前」という組み合わせです。

### 4.1 なぜ `overflow` は L3 のみなのか

`#{overflow}` は**演算ごと**のセマンティクス切替であり、宣言のメタデータではありません。これを関数やブロックに書けるようにすると、「ある演算が実際にどのモードを使うか」は、アノテーションからどれだけ離れているか、間に別のアノテーションが挟まっているか、ブロックが何層重なっているかによって決まってしまいます。一行のコードを読むのに上へ遡って調べる必要があり、`no fmt` / `no vet` / codegen の三者が同じ答えを維持するのは極めて困難です（実測ですでに逸脱しています。§7 参照）。

さらに、これは**型を変えません**。結果は常に `?T` です。ブロック級や関数級の `wrap` は `?T` を `T` に変えることはなく、「オーバーフローなら `err`」を「黙って折り返す」に静かに入れ替えるだけです。エラーが「明示的な失敗」から「成功に見える誤った値」へと変わるのであり、一行離れたアノテーションに決めさせるべきことではありません。

そのため、一行につき一つのアノテーションと定めました。

- 直後に続くあの一文だけを認めます。行末に書く形式（`x = a + b #{overflow=wrap}`）も等価です。
- 広い範囲に適用したい場合は一文ずつ書きます。`no fmt --fix=overflow` と LSP の quickfix が生成するのもこの形式です。
- 関数頭、ブロック頭、ファイル先頭に書くと**コンパイルエラー**です。「無効だが無害」ではありません。

副次的な利点として、アノテーションは常にそれが管する文と同じ画面にあり、コードを移動しても互いに離れません。また、`wrap` がインデントの調整だけで隣の演算に意図せず及ぶこともありません。

## 5. コメント（`;` / `//` / `;;`）のスコープ

コメントはコンパイルのセマンティクスには関与しません。帰属は `no fmt` の整形と API ドキュメントへの関連付けにだけ影響します。マーカーの構文は [`code-style.md`](code-style.md) の〈コメントマーカー〉を参照してください。

| コメント | 帰属 |
| --- | --- |
| 行内（`x = 1 ; 説明`） | その行 |
| 行上の連続したコメント行 | 直後に続く次の文/宣言（L1 または L3、アノテーションのホスト判定と同じ） |
| 対象との間に空行がある | どのノードにも帰属せず、ブロック/ファイルの区切り説明となる（ファイル先頭は例外、L0 を参照） |
| `;; … ;;` ブロックコメント | 自身の終了デリミタまでで、スコープをまたがない |
| アノテーションと対象の間のコメント | 対象に追随し、出力順は「ドキュメントコメント → アノテーション → 文」で固定 |

`;` と `//` はセマンティクスが同じです。`no fmt` は元のマーカーを保持し書き換えません。ドキュメントコメントの翻訳アンカー（`[get](#args.get)`）はコメントグループの**最終行**でなければならず、同じホストに属し、ノードをまたいではいけません。

## 6. 四つの読み手は一致しなければならない

同じ一つのアノテーションについて、四つの読み手は同じスコープを得なければなりません。

| 読み手 | 知っておくべきこと |
| --- | --- |
| parser / codegen | このノードとその部分木がどのモードを使うか |
| checker / `no vet` | 「アノテーション済み」と判定する範囲 |
| `no fmt` | アノテーションを元の位置へ書き出し、ホストをまたいで移動してはならない |
| LSP | hover/quickfix の挿入位置が実際に有効になる位置と一致すること |

ここから四つの不変条件が導かれます。

1. **アノテーション判定の一致**：codegen が「アノテーション済み」と見なす範囲は、必然的に `no vet` が処理済みと見なす範囲でもあり、その逆も同じです。
2. **fmt は移動しない**：`no fmt` が位置を調整できるのは同じホスト内だけです（直上 ↔ 行末）。ホストをまたぐ移動はセマンティクスの変更に等しいです。
3. **無効なら必ずエラー**：アノテーションが対応するセマンティクスのないレベルに置かれた場合（§4 の `✗` / `—` を参照）、エラーを報告し、黙って無視してはいけません。
4. **レベルの制限**：キーはマトリクスが許可するレベルでのみ有効です。`overflow` が L0/L1/L2 に書かれた場合、四つの読み手はすべてそれを**エラー**として扱わなければなりません。「vet は認める、codegen は認めない」といった分岐が生じてはなりません（現状は §7 を参照）。

## 7. 現状とギャップ（2026-11-11 実測）

`bin/no` で項目ごとに検証しました。形は「二つの `i8 = 100` を足し、結果が `err` か `-56`（wrap）かを見る」で統一しています。プラットフォームキーは `#{win-amd64}` を使い、macOS で除外されるかを検証しました。

| レベル | `overflow`（設計：L3 のみ） | プラットフォームキー | 宣言キー |
| --- | --- | --- | --- |
| L0 モジュール | ✗ 設計上禁止。現在は最初の文に付着する（L1 と同じ） | 未実装 | 未実装 |
| L1 宣言 | ✗ 設計上禁止。**現状はバグ**：`no vet` は認める（関数全体をスキップ）、codegen は認めない（相変わらず `err`） | ✓ 部分木全体を除外 | ✓ |
| L2 ブロック | ✗ 設計上禁止。codegen は認めない。`for` / if グループ / match アーム頭なら `no vet` をブロックに沿って黙らせられる。**文位置の裸ブロック `{` は黙らせることすらできない**（下記参照） | ✗ ブロック内は依然コンパイルに参加 | — |
| L3 単行 | ✓ | ✓ | — |

実測の証拠：

```text
a-none.no    (無註解)                     → err
b-line.no    (陳述上方 #{overflow=wrap})   → result:true  (-56，生效)
c-fn.no      (函式上方 #{overflow=wrap})   → err           (vet: No issues found)
d-block.no   (for 上方 #{overflow=wrap})   → err ×2        (vet: 2 hints)

p1-block.no  (#{win-amd64} + 2 * {…})      → 塊體仍執行    (未過濾)
p2-stmt.no   (#{win-amd64} + 單條 print)   → 該行被排除    (生效)
p4-fn.no     (#{win-amd64} + 函式宣告)     → 函式被排除    (生效)
p6-ifgroup.no(#{win-amd64} + if 組)        → 臂仍執行      (未過濾)

; 編譯期對照：`for` 頭加註解 vs 不加，15w45dqk 逐字相同
k2.no (for 頭 #{overflow=wrap} + 體內 `x i8 = a + a`) → cannot assign ?i8 to i8
k3.no (刪掉那一行，其餘逐字相同)                       → cannot assign ?i8 to i8
```

裸ブロックが黙らせることすらできない理由：`parseAnnotationStatement` の付着可能な対象は IDENT / USE / IN / RARROW / 配列型のメソッドだけで、`{` は含まれていません。そのため、次のような書き方のアノテーションはブロックにもブロック内の文にも付着せず、独立した `AnnotationStatement` へ退化します。parser、codegen、`no vet` の三者にとって死に行です。

```no
#{overflow=wrap}
{
    ...
}
```

`for` / if グループ / match アームの頭は識別子か `in` で始まるため、たまたま付着可能な対象に該当します。

引き締めるべき三つの穴（`overflow` の「L3 のみ」はまだ強制されていません）：

1. **`no vet` は関数級の `overflow` を見つけると関数全体をスキップする**（`walkStmtForOverflow` の `fn.OverflowMode == ""` による短絡）→ チェックはすべて緑なのに、実行時は相変わらず `err`。
2. **`no vet` がブロックに沿って下へ継承する**（`enclosingOverflow`）→ ブロック頭の一行のアノテーションでブロック全体が黙り、codegen がまったく認めない場合でも同様です。
3. **parser / codegen が L1/L2 の `overflow` を黙って無視し**、エラーを報告しない → 作者はそれが有効でないことを知る由もありません。

既存コードの棚卸しと対処（`src/std` に対し `no fmt --fix=overflow` を三回の下ろし込みで実施）：

| 区分 | 移行前 | 第1輪後 | 第2輪後 | 第3輪後 |
| --- | --- | --- | --- | --- |
| `overflow` アノテーション行の合計 | 4580 | 4083 | 3861 | 4080 |
| そのうち「どのノードにも付着しない」死に行 | 330（形態別に計上） | 87 | **0** | **0** |
| `no vet` が報告するがアノテーションを付けられないもの | — | 約270 | 270 | **51** |

第1輪（2026-11-11）の純変化：スコープ級アノテーションを816行削除し、文ごとのアノテーションを325行挿入しました。A/B に分けて見ると、325行のうち約218行は元からアノテーションが欠けており下ろし込みとは無関係な箇所で（挿入だけ行い遮蔽を外さない場合も同じ場所が補われます）、約97行がブロックレベルの意図が文ごとの形に具体化されたものです。

第2輪（2026-11-12）は**純粋な清掃**でした。原因は `findFixTargetNode` がアーム本体へ下りず、「挿入後の自己チェック」もなかったためです。381行削除、159行追加で、**すべて `#{...}` アノテーション行であり、コード行は0行**（`diff` で行ごとに照合）。そのうち159行は「ブロック頭/アーム頭から文の直上へ移す」変位で、残る222行は死に行と余分なスコープ級アノテーションを直接削除したものです。これらの位置は元から有効でなく、削除してもコンパイル/チェック結果は変わりません。

第2輪で併せて修正した三つのツールの欠陥：

1. **`checker` が報告する行番号がコンテナに潰れる**：`walkExprForIntOverflow` の `emit` がコンテナの `stmt.Pos().Line` と演算子の column を混用していたため、`{ ... }` / if グループ / match アーム内のあらゆる報告の行番号がヘッダ行になっていました。診断が位置を誤るのは表面現象で、真の問題は `--fix` の `findFixTargetNode` が「その行を含む最も内側の文」を取得しようとしてコンテナしか返せず、アノテーションがブロック頭に挿し戻されることでした。現在は**演算子自身の行**（`x.Token.Line`）を取得するよう改め、token の行番号が欠けている場合はコンテナ行にフォールバックします。
2. **アーム本体へ下りない**：`findFixTargetNode` は元々、意図的に match 文全体の直上で停止していました。現在は**ブロック形式のアーム本体**（`cond -> {` の `{ ... }`、`{ ... }: { ... }` の `BlockMatchStatement.Body` を含む）へ下ります。行内のアーム本体は相変わらず下りません（`w i64 -> w + 1` の文とアームパターンは同じ行にあり、その直上へ挿すのは match の中へ挿すことと同義で、アームパターンの行より前になってしまいます）。
3. **付着できない位置にも挿してしまう**：`#{overflow}` は現在、挿入後に**もう一度解析して自己チェック**を行い、「挿入したが独立した `AnnotationStatement` に退化した」アノテーションを取り消します（死に行を残しません）。取り消した後、二回目の `--fix` が受け取るソースは変化せず、冪等性が保たれます。

第3輪（2026-11-12）で変更したのは parser です。`parseAnnotationStatement` の付着対象に **DOT** が追加されました。`.n = .n + 1` / `.cnt == 0 -> …` のようなレシーバで始まる文は `x = …` と同じ種類（単一文、L3）なのに、従来は付着対象に含まれていませんでした。そのためアノテーションが独立した `AnnotationStatement`（死に行）へ退化し、箇所は永久に報告され続け、`--fix` が挿入しても自己チェックで取り消されていました。緩和後、219箇所が L3 アノテーションを取得し（アノテーション行 3861 → 4080）、付けられない箇所が270から51へ減少しました。これにより AST の形が変わり（AnnotationStatement が一つ減り、対象文に side-table の記録と `OverflowMode` が一つ増える）、`parser.ASTVersion` が `2026-11-12.1` に bump され、変更後は必ず `make gen no` が必要です。

**`{` と `(` は意図的に緩和していません**：`{`（文位置の裸ブロック / 括弧付き match）と `(`（`(cond) { }` のループ頭）は L2 ブロックのホストであり、`overflow` の設計は L3 のみを認めます。これらを許可すると `overflowAnnotatedNode` がブロック全体に対して早期リターンし、L2 セマンティクスを合法化することと同じになり、§8 の「まず引き締め、次に緩和」という順序と衝突します。残る51箇所の大部分はこの二種類で、§8 の手順 4b に該当します。

受入基準（分離ツリー A/B、同一ソース・同一コンパイラで `src/std` のみ差異、ファイルごとに `no vet`）：影響を受けた73ファイルは**すべてエラー0**（コンパイル破壊なし）で、25ファイルで診断が減り、19ファイルで増えました。増えた分はすべて、遮蔽を外したことで露呈した `ovfhndld`「`?T` に束縛されているがオーバーフロー値の取得が宣言されていない」であり、§8 手順1の予期される結果で、新しい欠陥ではありません。さらに9件の `nolang-overflow-ineffective` 警告は、ツール本来の「欠けを補う」動作が bigint / 文字列の演算子オーバーロードに及んだ古い問題で、下ろし込みとは無関係です。第2輪の後、`bin/no run test/std/*.no` を全面再実行（zstd / tls / str / json / set / base32 …）し、**すべて PASSED** でした。

第3輪の再実行基準：`parser` テストの3件の赤（`TestAnnotationsLiveOnAST` / `TestCachedASTLowersToIdenticalHIR` / `TestBuildSemViewsMatchesFreshParse`）は**緩和の前後で文字単位で同一**でした。`only 288 files parsed cleanly` は両回とも同じで、緩和によって新たな解析失敗は生じていません。これらは並行作業中の parser/annotation リファクタリングの進行中の状態です。`no fmt -d src/std` の出力も緩和の前後で**バイト単位で同一**であり、formatter が `.` 上のアノテーションをそのまま元の位置へ書き出し、フォーマットの逸脱がないことを示しています。`test/std` の heap / zstd / tls / json / set / map / regexp はすべて緑です。

**残る76箇所のアーム頭アノテーション**（`#{overflow=wrap}` が `cond -> {` の直上に密着）について：これらは**死に行ではありません**。parser がアーム級のアノテーションをアーム本体内のあらゆる文へ複製するため、アーム本体に対して有効です（実測：アーム頭の一行のアノテーションでアーム本体の `r = i * 2` が黙り、残るのはヘッダ条件の一文だけが報告されます）。ただし**アーム条件**自体には無効です（条件は文ではないため）。この76箇所は現状のまま維持します。文ごとの挿入では取得できず（アーム本体の箇所はすでに黙っていて報告されなくなっている）、これらを外して付け直すのはヘッダ行での無駄な往復になるだけだからです。

**いまだ `no vet` に報告され、かつ現在の言語ではアノテーションを付けられない51箇所**（第2輪では270箇所、第3輪で DOT を緩和した後に残ったもの）：対象文の先頭が `{`（文位置の裸ブロック / 括弧付き match）または `(`（`(cond) { }` のループ頭）であるものと、ごく少数のアームヘッダ条件です。これらは今日**同じく**報告されています（元のアノテーションが元から有効でなかったため）、したがって取り消しても回帰にはなりません。ゼロにするにはまず §8 手順1–2（L2 の `overflow` をエラーと判定する）を行い、その上で L2 を実際にサポートするかどうかを判断する必要があります。§8 手順 4b を参照してください。

`archive/bzip2.no:315` のような箇所を抜き取り調査すると、ブロック頭とブロック内の**両方**に `#{overflow=wrap}` があります。ブロック頭の層は現在有効ではなく、実際に機能しているのはブロック内の文ごとの層（`--fix=overflow` が補済み）です。したがってブロック級の層を削除してもセマンティクスは変わりません。ただし削除した後に `no vet` を走らせると、「外側のアノテーションだけに頼って黙っていた」箇所が露呈します。これはまさに引き締めの目的であり、副作用ではありません。実測では `crypto/rsa.no` の `ovfhndld` hint が19件から22件に増え、すべて「`?T` に束縛されているがオーバーフロー値の取得が宣言されていない」文に該当し、セマンティクスは変わっていません。

L0 の既存コードへの影響：`src/**/*.no` のうち、アノテーションがファイルの最初の有効行になっているファイルは21個で、そのうち17個が `#{js}`、残りは宣言に密接する `#{buildin}` などです。いずれも空行が**なく**、§2 の L0 判定基準によれば相変わらず L1 であり、`no fmt` とコンパイルの挙動は変わりません。`str.no` には「アノテーション + 空行 + cond アーム」が2箇所ありますが、関数本体内にあり、L0 判定基準には該当しません。

## 8. 引き締めの順序

1. **まず `no vet` が L1/L2 の `overflow` を認めないようにする**：「関数級の全体スキップ」の短絡を削除し、`enclosingOverflow` を同じ文の部分木内に制限します（ブロックをまたいで下へ伝えない）。
2. **次に parser をエラーにする**：`#{overflow}` が L0/L1/L2 に置かれたらコンパイルエラーとし、メッセージで「文ごとにアノテーションを付けるか、`no fmt --fix=overflow` を実行してください」を指します。この手順で既存コードが一挙に露呈します。
3. **既存コードを清理する**：`no fmt --fix=overflow` はすでに下ろし込み能力を備えています（スコープ級の層を外し、checker の報告に従って文ごとに L3 を補う）。`src/std` は三回実施済みです（§7 の既存コード表を参照）。変更後は必ず `make gen no` が必要で（blob と StdSigKey を焼き直す）、`src/std` に対して `no fmt -w` を実行してはなりません。移行はアノテーション行だけを変更し、ファイルごとに `no fmt -fix=overflow -w <f>` で完了させ、`diff` で他の変更がないことを保証します。
4. **parser の付着対象を緩和する**（第3輪で半分完了）：
   - **4a 完了**：`parseAnnotationStatement` が **DOT** で始まる文を受け付けるようにしました。`.n = .n + 1` / `.cnt == 0 -> …` は `x = …` と同じ単一文（L3）なのに、従来アノテーションを付けられず、`src/std` の219箇所の `#{overflow=wrap}` が一度も有効になっていませんでした。緩和後、付けられない箇所が270から51へ減少し、`parser.ASTVersion` が `2026-11-12.1` に bump されました。
   - **4b 未決定**：`{`（文位置の裸ブロック / 括弧付き match）と `(`（`(cond) { }` のループ頭）は **L2 ブロックのホスト**です。これらを緩和するのは `overflow` に L2 セマンティクスを合法化することと同じで（`overflowAnnotatedNode` がブロック全体に対して早期リターンする）、手順1–2の引き締め方向と逆です。正しい順序は、まず手順1–2（L2 の `overflow` をエラー判定）を行い、その上で残る51箇所を「ブロックを持たない文への書き換え」か「arm body の文ごと補完」で解決するかを判断することであり、`{` / `(` を無条件に解放することではありません。
5. **残るキーを段階的に引き締める**：宣言キー（`buildin` / `generic` / `embed`…）が L2/L3 に書かれた場合を「無効」から「エラー」に変更する。
6. 各手順で `no fmt` の冪等性を保ち、四つの読み手が同じ入力に対して同じ結論に達するようにします（§6）。
