# パス解決の規約：ワークスペースルート基準（Workspace-Root-Relative）

## 規約（Adopted Convention）

すべての **embed パス** と **インポートパス**（`use` / `#` ディレクティブ、embed リソース）は、
**ワークスペースルート（workspace root）を基準とした正規化された絶対パス**として解決され、
**「現在のソースファイルがあるディレクトリ」を相対基準にはしません**。

- 「ワークスペースルート」= `workspace.noml` のあるディレクトリ、つまり `pkg.WorkspaceRoot()`。
  注意：`package.noml` のあるディレクトリは**パッケージルート**（`pkg.RootDir`）であり、両者は同じ階層ではありません——ワークスペースルートは上位にあり（`workspace.noml` を含み、複数のパッケージを含むことができます）、パッケージルートは個々の**パッケージ**のディレクトリ（`package.noml` を含む）で、パッケージ内には若干の**モジュール**（`.no` ソースファイル）が含まれます。混同しないでください。
- 解決後は正規化（`filepath.Clean`、`.` / `..` の除去、区切り文字の統一）を行い、**グローバルに一意**な正規パスを得ます。
  これをモジュール読み込み、キャッシュキー、AST／セマンティクスの帰属に対する唯一の識別子として使います。
- この正規パスは `lexer.tokenCache` と `checker.parseProgramFileCache` のキャッシュキーの**パス成分**です。
  キャッシュキーは実際には複合キー `(正規パス, コンテンツハッシュ)`（`cache.Key`、`src/cache/lru.go` を参照）です：
  同じパスの内容が変わると → ハッシュが変わり → 自動的に無効化され、古い token/AST を取得しなくなります。またキャッシュは容量上限のある
  LRU なので、常駐プロセス（LSP / fmt）でメモリリークが起きません（元の 2 パス構成レビューの第③項）。

## 理由

1. **キャッシュの名前衝突を根本から解消**。旧い token/AST のキャッシュキーは「パス文字列」だったため、異なるソースファイルが同じ
   相対文字列（例：`utils/no` や embed 名 `data.json`）でインポート／埋め込みされると、同じキャッシュエントリに命中 →
   内容が混ざり、誤った token/AST を取得していました。ワークスペースルート基準の正規絶対パスに変更後は、**論理ファイルごとに一意のキーを持ち、
   同じファイルは常に同じキー**となるため、衝突は構造的に消滅します（元の 2 パス構成レビューの第④項）。
2. **コンパイラのロジックが大幅に簡素化され、より堅牢に**。パス解決は「parser / transpiler / checker の各所に散在していた
   現在のファイルディレクトリからの相対解決」から**単一の正規化ステップ**に集約されました。前方参照、モジュール読み込み、キャッシュキー、診断情報内の
   パスはすべて同じ基準に基づき、インポート元ファイルの位置に依存しなくなりました。
3. **ファイル間／並列ビルドのキャッシュへの道を開く**。正規絶対パスによりキャッシュキーが安定しグローバルに比較可能になるため、今後の
   deep-clone による再利用（`ParseProgram` の重複を避ける）や遅延解析の最適化が容易になります。

## 適用範囲

- **絶対パス**（`/` で始まるローカルモジュール）：すでにワークスペースルートを基準に解決されており、そのまま維持。
- **`std/` モジュール**：組み込みの `StdFS` 由来で、キーは `std/<rel>.no`。そのまま維持し、ローカルパスと混同しません。
- **embed リソース**：どのような相対名で参照されても、内部ではワークスペースルート基準の正規 embed キーに一律に正規化されます。

## 実装済み（Implemented, 2026-08-02）

共通の helper は `src/package/paths.go` に実装済みです（パッケージ `pkg`、標準ライブラリのみ、循環依存なし）：

- `FindWorkspaceRoot(start)`：`start` から上方向へ `workspace.noml` のあるディレクトリを探します。
- `FindPackageRoot(start)`：`start` から上方向へ `package.noml` のあるディレクトリを探します（workspace がない場合のフォールバック）。
- `ResolveToWorkspaceRoot(wsRoot, rel)`：任意のインポート／embed の生パスをワークスペースルート基準の
  絶対パスに正規化します（先頭の `/` を除去、絶対パスはそのまま返す、`wsRoot` が空の場合はカレントディレクトリにフォールバック）。
- `ResolveEmbedBase(sourcePath)`：相対 embed パスの解決基準——ワークスペースルートを優先し、パッケージルート／ソースファイルディレクトリにフォールバック。

集約済みのエントリポイント：

- `src/build/transpiler.go` の `resolveUse`：分岐 A（`/` 接頭辞）と分岐 E（alias）を統一して
  `pkg.ResolveToWorkspaceRoot(t.workspaceRoot(), path)` に変更し、`t.workspaceRoot()` メソッドを
  新設しました（`pkg.WorkspaceRoot()` を優先し、なければ `sourcePath` から上方向へ `workspace.noml` を探す）。
  旧い `if t.pkg != nil { baseDir = pkg.RootDir; if wsRoot... }` という重複ロジックは削除され、cwd 相対の
  フォールバックは `FindWorkspaceRoot` を通るように変更されました。
- `src/build/transpiler.go` の `processEmbeds`：相対 embed パスは `pkg.ResolveEmbedBase(sourcePath)` を通るように変更
  （ワークスペースルート優先）。
- `src/checker/checker.go` の `ValidateEmbedAnnotations`：embed 検証パスも同様に `pkg.ResolveEmbedBase` を通ります。

キャッシュキー（`tokenCache` / `parseProgramFileCache`）は `resolveFile(filePath)` を経由してワークスペースルート基準の
正規絶対パスをパス成分として取得します。さらにソースファイルの内容ハッシュと組み合わされて複合キー（`cache.Key`）となり、衝突は構造的に消滅します。
また同じパスを編集すると自動的に無効化され、LRU に上限があるためリークも防がれます。

`std/` と `js/` の組み込みモジュールは引き続き `StdFS` / `JsFS` を使い（キーは `std/<rel>.no` / `js/<rel>.no`）、影響を
受けません。`processEmbeds` はメインプログラム（ユーザーソース）にのみ適用され、std モジュール自身の embed は引き続きその自身の位置を基準に解決されます。

> 状態：**実装済み（2026-08-02）**。新しいコードでは `pkg.ResolveToWorkspaceRoot` /
> `pkg.ResolveEmbedBase` を直接使ってください。`filepath.Dir(t.sourcePath)` のような「現在のファイルディレクトリ」を
> 基準にした相対解決は行わないでください。

## 用語対照（統一，2026-08-02）

- **workspace ワークスペース** —— 一般的には 1 つの repo です。ルートに `workspace.noml` を置き、複数のパッケージを含むことができます。ワークスペースルートは
  すべての embed／インポートパス解決の唯一の基準です。
- **package パッケージ** —— 大きなコンパイル単位です。1 つのライブラリまたは 1 つの実行ファイル。ルートに `package.noml` を置きます（つまり**パッケージルート**）。
  依存関係や emit バックエンドなどを宣言します。1 つのパッケージは若干のモジュールを含みます。
- **module モジュール** —— 一般的には 1 つのソースファイル（`.no`）です。現在の規約では **1 ファイル = 1 モジュール**。1 つのモジュールを読み込むことは
  = 1 つの `.no` ファイルを読み込むことです。

3 者の階層：**ワークスペース ⊃ パッケージ（1 つ以上） ⊃ モジュール（1 つ以上）**。「module」を「パッケージ」
（コンパイル単位）の意味で使わないでください——それは「package」の役割です。
