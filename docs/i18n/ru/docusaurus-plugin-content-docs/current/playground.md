# Playground

Nolang Playground — это онлайн-среда, в которой можно редактировать, компилировать и запускать программы Nolang прямо в браузере. Компилятор Nolang (`no.wasm`) и языковой сервер (`lsp.wasm`) скомпилированы в WebAssembly, а пользовательский код выполняется через WASI в песочнице браузера — без установки какого-либо локального инструментария.

Переходите сразу: [**/playground**](/playground)

## Использование

Страница Playground разделена на две области:

- **Редактор слева**: редактор кода на базе [CodeMirror 6](https://codemirror.net/) с подсветкой синтаксиса Nolang, автоматическим отступом и историей.
- **Output / stderr / Diagnostics справа**: результаты выполнения, стандартный поток ошибок и диагностические сообщения.

Интерфейс следует за локалью Docusaurus и автоматически переключается между упрощённым китайским и английским; область вывода поддерживает и светлую, и тёмную темы.

### Панель инструментов

| Кнопка        | Функция                                                            |
| ------------- | ------------------------------------------------------------------ |
| **▶ Run**     | Скомпилировать текущий код в WASM и выполнить через WASI; stdout показывается в правой области Output. |
| **Format**    | Вызвать `no fmt` через LSP для форматирования текущего кода.       |
| **Examples**  | Загрузить встроенный пример по категории, заменив содержимое редактора. |

В правой части панели инструментов отображается текущее состояние (простой / компиляция / выполнение / завершено / ошибка), а под выпадающим списком — двуязычное описание выбранного примера. Последний выбранный пример сохраняется в локальном хранилище браузера.

### Примеры

В выпадающем списке Examples предустановлено **24 примера**, сгруппированных по темам; все они проверяются в CI через тот же путь компиляции `--wasm-direct`, что и в браузере:

| Категория | Количество | Содержание |
| --------- | ---------- | ---------- |
| Основы | 7 | Hello World, вывод типов, функции и рекурсия, Фибоначчи, арифметика и побитовые операции, форматированный вывод, строки |
| Управление потоком | 6 | короткие замыкания-стражы, сопоставление с образцом, FizzBuzz, четыре вида циклов по диапазону, условный цикл while, break / continue |
| Структуры данных | 4 | массивы фиксированной длины, динамические срезы, структуры, методы |
| Скалярные типы | 4 | char, bool, f64, byte |
| Стандартная библиотека | 2 | math.max / math.min / sqrt, rand.rand |
| Обработка ошибок | 1 | option и nil в match с тремя ветвями |

Каждый пример снабжён стабильной ожидаемой подстрокой вывода; CI компилирует каждый пример, выполняет его через `wasmtime` и проверяет, что эта подстрока присутствует в stdout. Благодаря этому примеры не могут незаметно устареть после развития языка или Direct-WASM-бэкенда.

После выбора любого примера Playground очищает текущие Output, stderr и Diagnostics и заменяет содержимое редактора содержимым примера.

### Диагностика

Когда LSP обнаруживает синтаксическую ошибку или ошибку типа, она появляется в области Diagnostics в правом нижнем углу. Щелчок по любому элементу диагностики ведёт к соответствующей строке и столбцу. Сообщения `file:line:col` в stderr компилятора дополнительно разбираются в маркеры **Run Errors**, при этом завершающие TraceID и локализованные префиксы серьёзности автоматически удаляются.

### Ошибки и тайм-ауты

Раньше ошибки загрузки WASM попадали только в `console.warn`, и пользователь видел кнопку Run, которая ничего не делала. Сейчас поведение следующее:

- Если `no.wasm` или `lsp.wasm` не удалось скачать или скомпилировать, вверху страницы появляется закрываемый баннер ошибки с указанием ресурса и причины.
- Ошибка инициализации языкового сервера также показывает баннер; редактор продолжает работать, но автодополнение, подсказки при наведении и форматирование недоступны.
- Каждый запуск контролируется сторожевым таймером в главном потоке (по умолчанию 8 секунд). `wasi.start()` — синхронный вызов внутри worker, поэтому бесконечный цикл не даёт сработать ни одному таймеру внутри этого worker; единственный способ действительно остановить его — завершить worker из главного потока. После тайм-аута worker завершается, при следующем запуске создаётся заново, и предварительный прогрев WASM немедленно начинается снова.
- Повторные нажатия Run отсекаются защитой от параллельного запуска, а отложенные таймеры необработанных правок отменяются при смене примера или форматировании, чтобы устаревший ввод не перезаписал новое содержимое.

`no.wasm` и `lsp.wasm` скачиваются и компилируются потоково в свободное время браузера, поэтому при первом нажатии Run больше не нужно ждать полной загрузки и компиляции 27 МБ.

## Ограничения

Поскольку Playground выполняется в песочнице WASM браузера, некоторые возможности Nolang недоступны:

### FFI не поддерживается

Браузер не может компоноваться с нативными C-библиотеками, поэтому FFI-объявления `#{c}`, `#{cpp}`, `#{rust}` и т. п. в Playground не работают. Код, содержащий FFI (например, драйверы `sqlite`, `mysql`), не может быть выполнен.

### fork / exec / pipe не поддерживаются

WASI preview1 не предоставляет API управления процессами, поэтому стандартная библиотека `process` (`process.start`, `process.wait` и др.) в Playground недоступна.

### Сетевые сокеты недоступны

WASI preview1 не предоставляет API сокетов, поэтому следующие стандартные библиотеки в Playground не работают:

- `net` (TCP listener / conn)
- `http` / `http2` / `http3` (HTTP client)
- `ws` (WebSocket)
- `tls` (TLS-соединения)
- `quic`, `sse`, `dns`

**Ограничения для самого `no` / `lsp` (строже, чем для стандартной библиотеки):** wasm-артефакты не могут даже «импортировать» функции сокетов.
На стороне браузера инстанцирование выполняется через `@wasmer/wasi`, в котором не реализованы `sock_accept` / `sock_shutdown`,
поэтому как только артефакт из-за `net` / `net/http` получает эти два импорта `wasi_snapshot_preview1`,
`WebAssembly.Instance` сразу выбрасывает:

```
Failed to instantiate WASI: RuntimeError: JsValue(LinkError: WebAssembly.Instance():
Import #28 "wasi_snapshot_preview1" "sock_accept": function import requires a callable)
```

Следствие: вся программа не доходит даже до `_start` — языковой сервер сообщает «ошибка инициализации» (автодополнение, подсказки и форматирование полностью не работают),
кнопка выполнения тоже. Поэтому весь сетевой код, который имеет смысл только в нативной среде, вынесен в файлы с `!wasip1`,
а на стороне wasip1 остались только заглушки с сообщением об ошибке: `cmd/lsp/pprof_wasip1.go`, `cmd/no/serve_esm_wasip1.go`,
`package/download_net_wasip1.go`, `package/release_net_wasip1.go`.
`bun scripts/wasm_imports_check.ts` (`make wasm-imports-check`) охраняет эту границу, проверяя таблицу импортов собственными средствами движка.

### `poll_oneoff` восполняется фронтендом

Чистая таблица импортов означает лишь «функция существует», но не «функция не упадёт». Тело `poll_oneoff` в `@wasmer/wasi` — это
Rust `unimplemented!()`: стоит его вызвать (даже с нулём подписок), как выполняется `unreachable` и весь экземпляр
завершается trap'ом, ошибка выглядит так:

```
Error while running start function: RuntimeError: JsValue(RuntimeError: unreachable)
```

Среда выполнения Go превращает и `time.Sleep`, и `netpoll(delay)` в одну подписку на монотонные часы,
поэтому **это случается с каждой Go-программой** — `no fmt` / `no vet` / `no build` все умрут при первом же «засыпании»,
а проверка таблицы импортов этого вообще не увидит.

Исправление находится в `docs/src/playground/wasm-loader.ts`: `instantiateWasi()` сам формирует объект импортов через `wasi.getImports()`
и подменяет `poll_oneoff` JS-реализацией (подписка на часы → спим до ближайшего срока, затем сообщаем о событии clock;
только подписка на fd → сразу сообщаем о готовности, чтобы не блокироваться навсегда). Обратите внимание, что **нельзя** передавать переопределение в
`wasi.instantiate(module, overrides)`: собственные функции glue имеют приоритет, переопределение молча игнорируется, и программа всё равно завершается trap'ом.
Кроме того, из-за перехода к собственному объекту импортов `wasi.start(instance)` необходимо явно передавать экземпляр.

### Время компиляции при первом запуске

Run использует `no build --wasm-direct` для генерации wasm. Замеры показывают, что hello world в wasm занимает около **0,5 секунды**
(нативная `no` с той же командой — около 0,6 секунды; оба значения — после предварительной индексации std в ноябре 2026, ранее было
примерно 55 и 11 секунд соответственно).

Раньше узким местом был не codegen, а **повторный разбор всего std дважды при каждом холодном запуске**: `validateProgram`
в `ValidateUndefinedVars`, чтобы распознавать модульно-квалифицированные вызовы вроде `math.max(...)`, собирает экспортируемые символы
для всех 119 модулей std; `CollectStdUnionAliases` отдельно разбирает ту же партию модулей в поисках псевдонимов union.
Теперь `genstdsig` запекает «экспортируемые символы каждого модуля» и «какие модули имеют псевдонимы union» вместе в
`stdsig_gen.go`, а во время выполнения идёт прямой поиск по таблице; есть ещё две проверки (`hir.TestModuleExportsMatchChecker`
сравнивает HIR по модулям и полям, `TestUnionAliasNarrowingMatchesFullScan` сравнивает узкий и полный обход), чтобы устаревшая таблица
вызывала провал теста, а не молча меняла семантику.

Сторожевой таймер по-прежнему держит двухступенчатый бюджет «загрузка + компиляция 180 секунд / пользовательская программа 5 секунд»: у первого сейчас огромный запас,
он оставлен, чтобы поглотить холодный запуск, большие программы и длинный хвост медленных устройств.

### Виртуальная файловая система

WASI preview1 предоставляет только три файловых дескриптора — stdin / stdout / stderr, — настоящей файловой системы нет. Поэтому `fs`, `path`, `os.get-env`, `os.set-env` и другие стандартные библиотеки, связанные с файлами или окружением, могут работать в Playground не так, как ожидалось.

### Ограничение памяти

Браузерный WASM обычно ограничен 32-битным адресным пространством, доступная память — примерно **2 ГБ ~ 4 ГБ** (в зависимости от браузера и ОС). Программы, требующие много памяти (глубокая рекурсия, большие массивы), могут завершиться из-за нехватки памяти.

## Совместимость с браузерами

Playground требует современного браузера с поддержкой WebAssembly. Рекомендуются следующие версии или новее:

| Браузер   | Минимальная версия |
| --------- | ------------------ |
| Chrome    | 100+               |
| Firefox   | 100+               |
| Safari    | 16+                |
| Edge      | 100+               |

Если браузер не поддерживает WebAssembly или в нём не включён JavaScript, Playground не сможет загрузить редактор или выполнить код.

## Разработка и проверка

После изменения Playground на чистом дереве сборки можно выполнить следующие проверки:

```bash
make playground-demos                       # компиляция + запуск всех примеров в процессе через собственный WASI-загрузчик playground
make playground-demos DEMO_RUN=wasmtime     # запуск через внешний wasmtime вместо него (перекрёстная проверка)
make playground-demos DEMO_RUN=none         # только компиляция, вывод не проверяется (не может быть порогом выпуска)
make wasm-imports-check                     # пересобрать оба wasm и проверить, что в таблице импорта нет socket-функций
make wasm-runtime-smoke                     # прогнать version/fmt/vet через тот же путь загрузки worker
RUN_WASM_LSP=1 RUN_WASM_BUILD=1 make wasm-runtime-smoke   # добавить языковой сервис и полную компиляцию + запуск
bun scripts/playground_ui_check.ts          # диагностика разбора, watchdog, восстановление worker, i18n
make playground-smoke                       # dev server и HTTP 200 для WASM-маршрута
cd docs && bun run typecheck                # проверка TypeScript-типов
```

Компилятор `playground-demos` — **нативная** `no`, но артефакты идут по браузерному пути `--wasm-direct -target wasm32-wasi`,
а выполнение использует `instantiateWasi()` из `wasi-glue` + `wasm-loader` — полностью тот же код, что и в `runner.worker`,
поэтому устанавливать wasmtime не нужно, CI запускает это напрямую. Он проверяет сразу три вещи: сниппет компилируется, артефакт проходит
верификацию WebAssembly (такие ошибки пустого стека, как в case-match по полю значения, проявляются здесь) и выведенный текст соответствует `expect`
(такие расхождения бэкенда, как молчаливое получение 0 от `?=`, тоже проявляются здесь).

Единственное, что он не ловит, — это таблица импортов самих `no.wasm` / `lsp.wasm` (эти два артефакта не создаются из сниппета);
это восполняет `wasm-imports-check`: если в `@wasmer/wasi` нет `sock_*`, `WebAssembly.Instance` сразу даёт `LinkError`,
и весь playground (включая языковой сервер) не может даже запуститься. На стороне worker есть ещё один слой защиты: `instantiateWasi()`
в `wasm-loader.ts` подменяет WASI-функции, которых нет в `@wasmer/wasi`, заглушками, возвращающими `ENOSYS` / `NOTSUP`,
благодаря чему неожиданный импорт вырождается в неудавшийся системный вызов, а не в падение всей службы.

`wasm-imports-check` тоже не ловит случай «функция есть, но её тело завершается trap'ом» (как `poll_oneoff` выше),
поэтому `make wasm-runtime-smoke` закрывает последний пробел: он проходит по настоящему пути `instantiateWasi()` и реально выполняет
`no version` / `no fmt` / `no vet`, а также может дополнительно проверить языковой сервер и полный цикл компиляции + выполнения.

`docs/static/wasm/*.wasm` исключены через `.gitignore`, локальные артефакты никогда не должны коммититься. `no.wasm` и `lsp.wasm` пересобираются CI
из одного и того же исходного кода и одного и того же `StdSigKey`, что гарантирует: компилятор в браузере, встроенный blob std AST и Direct-WASM-бэкенд
происходят из одной сборки; рассогласование версий этих трёх компонентов было частой причиной прошлых `unreachable` и ошибок верификации.

CI (`.github/workflows/build.yml` — `pr-verify`, сборка сайта в `static.yml`) выполняет по порядку Go-тесты, проверку типов, UI-проверки и проверку примеров,
и только после этого пересобирает WASM с чистого дерева и разворачивает сайт.
