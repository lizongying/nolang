# Область действия аннотаций и комментариев

Аннотация `#{...}` сама по себе не несёт информации о «насколько велика область её действия» — область определяется **узлом, к которому она прикреплена**.
Эта страница фиксирует это: одна позиция, один набор критериев, четыре уровня плюс одно уточнение («ключ может поддерживать лишь некоторые из этих уровней»
(`overflow` — как раз тот, что поддерживает только L3, см. §4.1), чтобы автор, `no fmt`, `no vet`, codegen и LSP
давали один и тот же ответ для одной и той же строки аннотации.

> Почему это нужно зафиксировать: если для одной и той же аннотации `#{overflow=wrap}` `no vet` считает, что она охватывает всю функцию, а codegen
> считает, что она охватывает только следующую строку, возникает скрытый семантический дрейф — «vet весь зелёный, а во время выполнения всё равно возвращается `err`».
> Область действия — это не свойство аннотации, а **общее понимание читателей**; если это понимание не записано, каждый дрейфует в свою сторону.

## 1. Один принцип: область действия определяется хостом

Аннотация имеет ровно две допустимые позиции (сами правила позиции см. в [`syntax.md`](syntax.md)〈Позиции аннотаций〉):

```no
; ① сверху: занимает отдельную строку, размещается над целью
#{overflow=wrap}
x i8 = a + b

; ② сзади (trailing): пишется на той же строке после цели
x i8 = a + b #{overflow=wrap}

; для многострочных целей (функции, блоки) trailing-форма пишется после закрывающей `}`
greet = () {
    print('hi')
} #{mac-arm64}
```

**Обе формы полностью эквивалентны** — один и тот же ключ, один и тот же хост, одна и та же область действия, и `no fmt` никогда не переписывает одну форму в
другую (trailing остаётся trailing, сверху остаётся сверху). Выбор зависит только от читаемости: для коротких инструкций trailing-форма экономит одну строку,
а когда нужно аннотировать целое выражение или инструкция длинная, используют форму сверху.

**Написание аннотации на той же строке перед целью является ошибкой компиляции** — пути «префикс действует на последующее» не существует:

```no
#{overflow = wrap} x i8 = a + b   ; ✗ префикс → ошибка
```

Определение проходит в три шага, и на каждом шаге ровно один ответ:

| Шаг | Вопрос | Источник ответа |
| --- | --- | --- |
| 1 | Кто хост? | Позиция: первое выражение сверху, не являющееся аннотацией/комментарием, или предыдущее выражение на той же строке |
| 2 | К какому уровню относится хост? Поддерживает ли ключ этот уровень? | таблица в §2 + матрица в §4 (неподдержка = ошибка компиляции) |
| 3 | Насколько далеко простирается? | поддерево хоста за вычетом внутренних жёстких границ (§3) |

## 2. Четыре уровня

| Уровень | Хост | Область действия | Пример записи |
| --- | --- | --- | --- |
| **L0 — уровень модуля** | заголовок файла | все объявления и инструкции этого файла | самый верх файла, при этом между аннотацией и последующим содержимым одна пустая строка |
| **L1 — уровень объявления** | константы/глобальные переменные, структуры, интерфейсы, помеченные перечисления, функции, методы | всё определение этого объявления (функция — вместе с телом и всеми вложенными блоками) | вплотную над объявлением или trailing на строке объявления |
| **L2 — уровень блока** | группы корутин, группы if, `cond -> body`, match, циклы `for`/со счётчиком/по диапазону, голые блоки | все инструкции внутри тела блока (включая вложенные блоки, до внутренней границы L1) | вплотную над инструкцией, открывающей блок, или после закрывающей `}` блока |
| **L3 — уровень одной строки** | одиночная инструкция (`let`, присваивание, `?=`, `return`, вызов, ветка `cond ->`) | сама инструкция и её выражения | вплотную над инструкцией или trailing на той же строке |

### L0 — уровень модуля

Позиция — **самое начало файла** (перед ним нет ни одной инструкции или import), при этом между группой аннотаций и первой инструкцией
**как минимум одна пустая строка** — здесь пустая строка служит «терминатором области действия», означая, что эта группа аннотаций не относится к следующей инструкции,
а относится ко всему файлу.

```no
#{win-amd64}

; ↑ пустая строка → уровень модуля: этот файл компилируется только под Windows x86_64
; все объявления и инструкции ниже находятся под действием этой аннотации
helper = () {
    print('windows only')
}

label = 'win'
```

Без пустой строки это обычный L1 (прикреплён к первому объявлению); эта граница позволяет существующему коду не требовать миграции:

```no
#{buildin}
bool.to-str = () (out str) {
}
```

Уровень модуля полезен только для ключей, «имеющих смысл для всего файла» (сейчас это только ключи платформ); ключи объявлений (`buildin`, `generic`,
 `embed`…), появляясь на L0, являются ошибкой, а не «расширением области действия». `overflow` тоже не работает на L0 — он поддерживает только L3.

Конфигурация, общая для нескольких файлов, не является аннотацией и записывается в `package.noml`.

### L1 — уровень объявления

```no
; вся структура: размещение полей определяется меткой типа
#{inline}
holder {
    inl point
    out point
}

; вся функция: журнал входа/выхода автоматически включает вызывающего
#{track-caller}
log.write = (msg str) {
    ...
}

; всё объявление константы: встраиваемая директория (путь относительно package.noml)
#{embed='assets'}
ASSETS fs.embed

; на этапе компиляции исключается всё поддерево (включая тело функции)
#{mac-arm64, linux-arm64}
greet = () {
    print('hello from unix')
}
```

Внутри L1 есть также **уровень членов**: аннотации на полях структур, вариантах помеченных перечислений и членах C-подобных перечислений
(`a pt #{inline}`, `ok(v i64) #{inline}`) управляют этим членом, а не всем типом. Аннотации членов
также имеют только две позиции: вплотную строкой над членом или после члена на той же строке (обычно trailing-форма).

### L2 — уровень блока

Когда хостом является «инструкция, открывающая блок», область действия — всё тело блока:

```no
; весь блок исключается (IR не генерируется, проверка типов не выполняется)
#{win-amd64}
2 * {
    print('windows only')
}

; группа if тоже обрабатывается целиком
x = 1
#{win-amd64}
{
    x == 1 -> print('arm-1')
    -> print('arm-other')
}
```

Применимы все четыре вида заголовков блока: группы корутин (`awy { ... }`), группы if (`{ cond -> … }`), одиночные условные инструкции
(`cond -> body`), match, циклы `for` / со счётчиком / по диапазону.

Если body у `cond -> body` — всего лишь одиночная инструкция, результаты L2 и L3 совпадают; разница появляется, когда оно записано как блок.

**Не каждый ключ поддерживает все четыре уровня.** Ключ может поддерживать лишь некоторые из них; запись на неподдерживаемом уровне — **ошибка компиляции**,
а не «безвредная лишняя строка». Пока единственный ограниченный ключ — `overflow`: он поддерживает только L3, причина — в §4.1.

### L3 — уровень одной строки

```no
a i8 = 100
b i8 = 100
; действует только на следующую инструкцию (trailing-форма `c = a + b #{overflow=wrap}` эквивалентна)
#{overflow=wrap}
c = a + b
c: {
    ok -> print('wrap:' - (it == -56).to-str())
    nil -> print('nil')
    err -> print('err')
}
```

Внутри блока аннотация, занимающая отдельную строку, действует только на «непосредственно следующую за ней инструкцию». Находящиеся между ними посторонние строки аннотаций
(например, после `#{overflow=wrap}` идёт ещё одна `#{...}`) не прерывают поиск — первая настоящая инструкция всё равно находится;
но если следующая аннотация сама содержит ключ с тем же именем, то предыдущая не управляет ни одной инструкцией (побеждает последующая).

⚠️ **Блочный match `{ … }: { … }` — это «одна инструкция» и не просматривается насквозь**: когда аннотация написана над его `{`,
хостом является сама эта инструкция блока, и аннотация **не** опускается в выражения `?=` внутри блока (проверено: `#{overflow=wrap}` снаружи блока,
а `np ?= np + 1` внутри блока всё равно переполняется → `err`, цель обнуляется). Чтобы применить `overflow` к выражению внутри блока, пишите его
вплотную над той инструкцией `?=` внутри блока. Различие двух способов обработки см. в [syntax.md](syntax.md),
〈Выбор между блочным match и match по значению〉.

## 3. Наследование, переопределение и жёсткие границы

**Наследование извне внутрь, переопределение по ближайшему.** Для ключей, поддерживающих несколько уровней (ключи платформ), L0 → L1 → L2 → L3 действуют последовательно;
если на одном узле встречаются ключи с одинаковым именем, последующий переопределяет предыдущий (`#{mac-arm64} #{mac-arm64, win-amd64}`
действует последний).

**Тело функции — жёсткая граница.** Область действия блока L2 ограничивается **синтаксическим поддеревом**: она не распространяется по связям вызовов и не входит ни в одно
определение функции / метода / анонимной функции. То, какой режим используется внутри тела функции, определяется только её собственной аннотацией L1 или внутренней
аннотацией L3 и не зависит от аннотации на блоке, который её вызывает.

```no
; L1: вся функция вместе с телом исключается (под macOS IR не генерируется)
#{win-amd64}
windows-only = () {
    print('never compiled on mac')
}

; нет собственной аннотации L1 → компилируется под любой платформой и не меняется в зависимости от того, кто её вызывает
always = () {
    print('always compiled')
}
```

Причина: если бы внешняя аннотация могла проникать в тело функции, одна строка в точке вызова молча меняла бы семантику вызываемой функции — при отладке
это было бы совершенно незаметно. Аннотация L1, напротив, пишется прямо на заголовке этой функции и является частью объявления.

**Список жёстких границ** (наследование останавливается): тело функции, тело метода, тело анонимной функции/lambda, внешнее объявление `#{c}`.
**Не границы** (наследование продолжается): голый блок `{}`, группа if, ветка match, тело цикла.

## 4. Матрица «ключ × уровень»

`✓` действует / `✗` недопустимо (должна быть ошибка компиляции) / `—` не имеет смысла для этого уровня (тоже должна быть ошибка, а не молчаливое игнорирование)

| Ключ | L0 модуль | L1 объявление | L2 блок | L3 одна строка |
| --- | --- | --- | --- | --- |
| `overflow` | ✗ | ✗ | ✗ | ✓ |
| Ключи платформ (`mac-arm64` и др.) | ✓ | ✓ | ✓ | ✓ |
| `buildin` | ✗ | ✓ функция / помеченное перечисление / структура размещения | ✗ | ✗ |
| `inline` | ✗ | ✓ структура / поле / вариант / функция | ✗ | ✓ trailing члена |
| `generic` | ✗ | ✓ функция / структура | ✗ | ✗ |
| `track-caller` | ✗ | ✓ функция | ✗ | ✗ |
| `embed` | ✗ | ✓ `let` верхнего уровня | ✗ | ✗ |
| `bind` | ✗ | ✓ строка import | ✗ | ✗ |
| `c` / `cpp` / `rust` | ✗ | ✓ следующее за ним объявление функции | ✗ | ✗ |
| `fmt-skip` | ✗ | ✗ | ✓ блок в markdown-ограждении | ✗ |
| Метаданные (`derive` / `range` / `max` / `debug`…) | ✗ | ✓ объявление / член | ✗ | ✗ |
| `index-out` | — | — | — | — удалено в D11, появление — ошибка |

И «недопустимо», и «не имеет смысла» должны **вызывать ошибку**, а не молча игнорироваться: аннотация, написанная над циклом for,
`#{buildin}`, если её тихо проигнорировать, заставит автора думать, что встроенное объявление подействовало.

### 4.0 Три носителя `#{buildin}` и особенность «структуры размещения»

`#{buildin}` ставится на объявлении, но для трёх носителей его семантика полностью различна:

| Носитель | Семантика | Пример |
| --- | --- | --- |
| Функция | Заглушка с пустым телом: реализацию предоставляет компилятор / FFI, на стороне Nolang тело функции не генерируется | `#{buildin}`<br/>`fs.remove = (p str) (ok bool) { }` |
| Помеченное перечисление | Варианты используются для сопоставления и проверки исчерпываемости, базовое представление и конструкторы предоставляет встроенный runtime | `#{buildin}`<br/>`option { ok(v t), nil, err(e err.err), }` |
| **Структура размещения** | **Это лишь документация по размещению**: данный `struct` семантически не существует, единственный результат — типы полей (`t.len` имеет тип `u8`) | `#{buildin}`<br/>`txt { data [255]byte; len u8 }` |

Третий случай нужно объяснить отдельно, потому что он направлен противоположно первым двум: заглушка функции и помеченное перечисление — это «компилятор действительно
использует это объявление», а структура размещения — это «компилятор **не использует** это объявление, оно лишь источник типов полей и
читаемое описание размещения». Настоящее размещение и ссылки на документацию находятся в другом месте:

| Тип | Источник реального размещения | Источник документации / ссылок |
| --- | --- | --- |
| `str` | Ручной дескриптор MIR `%str-long = { i32 len, i32 cap, i8* data }` | `parser.BuiltinTypes()` |
| `vec` | Ручной дескриптор MIR `%vec = { i32 len, i32 cap, i64 data }` | `parser.BuiltinTypes()` |
| `txt` | Ручной дескриптор MIR `%txt = { [255 x i8] data, i8 len }` | `parser.BuiltinTypes()` |
| `arr` | Дескриптора нет: `[n]t` — это просто агрегат `[N x T]`, а `.len` — константа времени компиляции `n` | `parser.BuiltinTypes()` |

`parser.BuiltinTypes()` (`src/parser/builtintype.go`) — это единственная таблица регистрации «имя → модуль std →
якорь документации модуля → размещение»; hover / переход к определению / автодополнение LSP и `IsBuiltinLayoutStructName`
читают её. Именно поэтому структура размещения **больше не отвечает за ссылки**: удалите её — hover и F12 по-прежнему работают;
только checker потеряет тип поля `t.len`, поэтому она пока сохраняется.

Отсюда два жёстких правила; нарушение любого из них немедленно создаёт «теневую структуру», противоречащую реальному размещению:

1. **Структура с `#{buildin}` должна использовать встроенное имя размещения** (`str` / `vec` / `txt` / `arr`).
   Прикрепление к другой структуре — ошибка: MIR сочтёт такое объявление «размещением, которым управляет компилятор», и пропустит его,
   все поля не подействуют, а автор получит кучу `unknown field`.
2. **Объявление структуры с встроенным именем размещения обязательно должно иметь `#{buildin}`**. Если пользователь напишет просто
   `str { … }`, оно будет сочтено обычным типом этого модуля с префиксом (`m.str`), и codegen сгенерирует
   `%m_str`, который конфликтует с `%str-long`.

Оба правила проверяются `checker.ValidateBuiltinStructDecls` (`1a8m445h` / `3lu6n4np`),
и `no build`, и `no vet` их поймают. Напротив, **только** сочетание `#{buildin}` + имя размещения пропускается
на этапе добавления префиксов модуля и в MIR `collectStructFields` (см. `src/build/module_prefix.go`
фазу 1 и `src/mir/hir2mir.go`, функцию `isBuiltinLayoutStruct`) — критерий здесь «аннотация +
имя», а не просто имя.

### 4.1 Почему `overflow` предоставляется только на L3

`#{overflow}` — это семантический переключатель **для каждой операции**, а не метаданные объявления. Стоит разрешить его на функции или блоке, как
«какой режим фактически использует та или иная операция» начнёт зависеть от того, насколько далеко она от аннотации, есть ли между ними другие аннотации и сколько слоёв блоков —
чтобы ответить, придётся прослеживать код вверх по строкам, а трём сторонам — `no fmt` / `no vet` / codegen — поддерживать один и тот же ответ
крайне трудно (проверка уже показала дрейф, см. §7).

Более того, он **не меняет тип**: результатом всегда остаётся `?T`. `wrap` на уровне блока или функции не превратит `?T` в `T`, а лишь молча заменит
«переполнение ⇒ `err`» на «тихое зацикливание» — ошибка из «явного сбоя» превращается в «неверное значение, выглядящее как успех»,
и именно это меньше всего должно определяться строкой далёкой аннотации.

Поэтому жёстко определено: одна аннотация на одну строку:

- действует только на непосредственно следующую инструкцию; trailing-форма (`x = a + b #{overflow=wrap}`) эквивалентна.
- чтобы охватить весь фрагмент, пишите аннотацию для каждой инструкции — именно такую форму создают `no fmt --fix=overflow` и LSP quickfix.
- написание на заголовке функции, заголовке блока или в начале файла → **ошибка компиляции**, а не «неэффективно, но безвредно».

Дополнительное преимущество: аннотация всегда находится на одном экране с инструкцией, которой управляет, и они не разделяются при перемещении кода; `wrap` также не
охватит случайно соседнюю операцию из-за однократной правки отступов.

## 5. Область действия комментариев (`;` / `//` / `;;`)

Комментарии не участвуют в семантике компиляции; их принадлежность влияет только на форматирование `no fmt` и привязку документации API. Синтаксис меток см. в
[`code-style.md`](code-style.md)〈Метки комментариев〉.

| Комментарий | Принадлежность |
| --- | --- |
| Строчный (`x = 1 ; пояснение`) | Эта строка |
| Непрерывные строки комментариев над строкой | Следующая за ними инструкция/объявление (L1 или L3, по тем же правилам определения хоста, что и для аннотаций) |
| Пустая строка между комментарием и целью | Не принадлежит ни одному узлу, служит разделительным пояснением блока/файла (кроме начала файла, см. L0) |
| Блочный комментарий `;; … ;;` | Действует только до собственного закрывающего разделителя, не выходит за пределы области действия |
| Комментарий между аннотацией и целью | Следует за целью; порядок вывода фиксирован: «документирующий комментарий → аннотация → инструкция» |

`;` и `//` имеют одинаковую семантику; `no fmt` сохраняет исходную метку и не переписывает её. Якорь перевода документирующего комментария
(`[get](#args.get)`) должен быть **последней строкой** группы комментариев, принадлежать тому же хосту и не переходить на другой узел.

## 6. Четыре читателя должны быть согласованы

Для одной и той же аннотации четыре читателя должны получить одну и ту же область действия:

| Читатель | Что нужно знать |
| --- | --- |
| parser / codegen | Какой режим используется для этого узла и его поддерева |
| checker / `no vet` | Область, считающаяся «уже аннотированной» |
| `no fmt` | Аннотация выводится на прежнее место и не переносится через границу хоста |
| LSP | Место вставки hover/quickfix совпадает с местом, где аннотация реально действует |

Отсюда четыре инварианта:

1. **Согласованность определения аннотированности**: область, которую codegen считает «аннотированной», обязательно совпадает с областью, которую `no vet` считает обработанной, и наоборот.
2. **fmt не переносит**: `no fmt` может менять положение только внутри одного хоста (сверху ↔ trailing); перенос через границу хоста равносилен изменению семантики.
3. **Недействительность ⇒ ошибка**: если аннотация попала на уровень, для которого у неё нет соответствующей семантики (см. `✗` / `—` в §4), должна быть ошибка, а не молчаливое игнорирование.
4. **Ограничение по уровням**: ключ действует только на уровнях, разрешённых матрицей. Когда `overflow` написан на L0/L1/L2, все четыре читателя должны
   считать это **ошибкой** — недопустимо расхождение типа «vet признаёт, codegen не признаёт» (текущее состояние — в §7).

## 7. Текущее состояние и расхождения (проверка 2026-11-11)

Проверка точка за точкой с помощью `bin/no`; форма единообразна: «сложить два `i8 = 100` и посмотреть, будет ли результат `err` или `-56`
(wrap)»; ключи платформ проверялись на macOS с помощью `#{win-amd64}` на предмет исключения.

| Уровень | `overflow` (по замыслу: только L3) | Ключи платформ | Ключи объявлений |
| --- | --- | --- | --- |
| L0 модуль | ✗ запрещено по замыслу; сейчас прикрепляется к первой инструкции (то есть как L1) | Не реализовано | Не реализовано |
| L1 объявление | ✗ запрещено по замыслу; **в текущей версии — уязвимость**: `no vet` признаёт (пропускает всю функцию), codegen не признаёт (по-прежнему `err`) | ✓ исключается всё поддерево | ✓ |
| L2 блок | ✗ запрещено по замыслу; codegen не признаёт. Заголовки `for` / групп if / ветвей match могут заставить `no vet` замолчать на весь блок; **голый блок `{` в позиции инструкции не может добиться даже этого** (см. ниже) | ✗ внутри блока всё равно участвует в компиляции | — |
| L3 одна строка | ✓ | ✓ | — |

Свидетельства проверки:

```text
a-none.no    (без аннотации)                     → err
b-line.no    (над инструкцией #{overflow=wrap})   → result:true  (-56, действует)
c-fn.no      (над функцией #{overflow=wrap})   → err           (vet: No issues found)
d-block.no   (над for #{overflow=wrap})   → err ×2        (vet: 2 hints)

p1-block.no  (#{win-amd64} + 2 * {…})      → тело блока всё равно выполняется    (не отфильтровано)
p2-stmt.no   (#{win-amd64} + одиночный print)   → строка исключена    (действует)
p4-fn.no     (#{win-amd64} + объявление функции)     → функция исключена    (действует)
p6-ifgroup.no(#{win-amd64} + группа if)        → ветка всё равно выполняется      (не отфильтровано)

; Сравнение на этапе компиляции: аннотация на заголовке `for` vs её отсутствие — 15w45dqk дословно одинаковы
k2.no (на заголовке for #{overflow=wrap} + в теле `x i8 = a + a`) → cannot assign ?i8 to i8
k3.no (удалена эта строка, остальное дословно одинаково)                       → cannot assign ?i8 to i8
```

Почему голый блок не может добиться даже этого: у `parseAnnotationStatement` список целей, к которым можно прикрепить аннотацию, включает только IDENT / USE /
IN / RARROW / методы типов массивов; `{` в него не входит. Поэтому в записи ниже аннотация не прикрепляется ни к блоку, ни
к инструкции внутри блока — она вырождается в отдельную `AnnotationStatement` и для parser, codegen и
`no vet` — это мёртвая строка:

```no
#{overflow=wrap}
{
    ...
}
```

Заголовки `for` / групп if / ветвей match начинаются с идентификатора или `in`, поэтому как раз попадают в список целей, к которым можно прикрепить аннотацию.

Три «дыры», которые нужно закрыть (требование «только L3» для `overflow` пока не обеспечивается):

1. **`no vet`, увидев `overflow` на уровне функции, пропускает всю функцию** (короткое замыкание
   `fn.OverflowMode == ""` в `walkStmtForOverflow`) → проверка целиком зелёная, во время выполнения по-прежнему `err`.
2. **`no vet` наследует вниз по блоку** (`enclosingOverflow`) → одна строка аннотации на заголовке блока заставляет весь блок замолчать,
   даже если codegen её вообще не признаёт.
3. **parser / codegen молча игнорируют `overflow` на L1/L2**, не сообщая об ошибке → автор не может узнать, что аннотация не подействовала.

Инвентаризация и обработка уже существующего кода (`src/std`; `no fmt --fix=overflow` запускалось три раза для проталкивания вниз):

| Категория | До миграции | После 1-го прохода | После 2-го прохода | После 3-го прохода |
| --- | --- | --- | --- | --- |
| Всего строк с аннотацией `overflow` | 4580 | 4083 | 3861 | 4080 |
| Из них мёртвые строки, которые «не прикрепляются ни к какому узлу» | 330 (по формам) | 87 | **0** | **0** |
| Сообщаются `no vet`, но не могут быть аннотированы | — | ~270 | 270 | **51** |

Первый проход (2026-11-11), чистое изменение: удалено 816 строк аннотаций уровня области действия, добавлено 325 постраочных аннотаций. Если разнести по A/B,
то из 325 строк примерно 218 приходятся на места, где метки изначально отсутствовали и что не связано с проталкиванием вниз (они были бы добавлены и при одной только вставке без удаления перекрывающих аннотаций),
примерно 97 строк — это намерение уровня блока, воплощённое в постраочной форме.

Второй проход (2026-11-12) — это **чистая уборка**; причина в том, что `findFixTargetNode` не спускается в тело ветки и не выполняет «самопроверку после вставки»:
381 строка удалена, 159 добавлено — **все это строки аннотаций `#{...}`, ноль строк кода** (проверено построчно через `diff`). Из них
159 — это перемещения «с заголовка блока/ветки на строку над инструкцией», а остальные 222 — простое удаление мёртвых строк и лишних аннотаций уровня области действия;
эти позиции изначально не действовали, поэтому удаление не меняет результаты компиляции/проверки.

Три недостатка инструмента, исправленные заодно во втором проходе:

1. **`checker` сообщает номер строки, «схлопнутый» до контейнера**: `emit` в `walkExprForIntOverflow` смешивает `stmt.Pos().Line` контейнера
   и column оператора, поэтому для `{ ... }` / групп if / ветвей match каждое сообщение содержит
   номер строки заголовка. Неправильное указание места в диагностике — лишь симптом; настоящая проблема в том, что `findFixTargetNode` у `--fix`
   берёт «внутреннюю инструкцию, содержащую эту строку», и получает только контейнер, поэтому аннотация вставляется обратно в заголовок блока. Теперь берётся **строка самого оператора**
   (`x.Token.Line`), а при отсутствии номера строки у токена используется строка контейнера.
2. **Спуск в тело ветки**: `findFixTargetNode` раньше намеренно останавливался над всей инструкцией match. Теперь он спускается
   **в тело ветки в блочной форме** (`{ ... }` у `cond -> {`, включая `BlockMatchStatement.Body` у `{ ... }: { ... }`),
   в строчное тело ветки по-прежнему не спускается (инструкция `w i64 -> w + 1` находится на одной строке с шаблоном ветки, а вставка над ней означала бы вставку внутрь match —
   перед строкой шаблона ветки).
3. **Вставка даже в позицию, где аннотация не прикрепляется**: теперь после вставки `#{overflow}` выполняется **повторный разбор с самопроверкой**, и аннотация, «вставленная, но
   выродившаяся в отдельную `AnnotationStatement`», отзывается (мёртвые строки больше не остаются). После отзыва второй проход `--fix`
   получает неизменный исходный код, идемпотентность сохраняется.

Третий проход (2026-11-12) затронул parser: в список целей `parseAnnotationStatement` добавлен **DOT**.
`.n = .n + 1` / `.cnt == 0 -> …` — такие инструкции, начинающиеся с получателя, относятся к тому же классу, что и `x = …` (одиночная инструкция, L3),
но раньше не входили в список целей ⇒ аннотация вырождалась в отдельную `AnnotationStatement` (мёртвая строка), место постоянно сообщалось,
а вставка `--fix` отзывалась самопроверкой. После расширения 219 мест получили аннотацию L3 (строк аннотаций 3861 → 4080),
неподдающихся аннотированию стало 51 вместо 270. Форма AST поэтому изменилась (на одну `AnnotationStatement` меньше, у целевой инструкции на одну запись
в side-table и `OverflowMode`), `parser.ASTVersion` повышен до `2026-11-12.1`; после изменений обязательно
 `make gen no`.

**`{` и `(` намеренно не расширены**: `{` (голый блок в позиции инструкции / match в скобках) и `(` (заголовок цикла `(cond) { }`)
— это хосты блока L2, а `overflow` по замыслу работает только на L3. Их добавление заставило бы `overflowAnnotatedNode`
вернуться раньше времени для всего блока, что равносильно узакониванию семантики L2 и противоречит порядку «сначала ужесточить, потом расширить» из §8. Оставшиеся 51 мест
по большей части относятся к этим двум категориям и попадают под шаг 4b из §8.

Критерий приёмки (изолированные деревья A/B, один и тот же исходный код и компилятор, разница только в `src/std`, `no vet` для каждого файла): 73 затронутых файла —
**все 0 error** (без нарушений компиляции), в 25 файлах диагностики стало меньше, в 19 — больше; все случаи увеличения — это выявленные после снятия перекрытий
`ovfhndld` («привязано к `?T`, но не объявлено получение значения при переполнении»), что является ожидаемым результатом шага 1 из §8, а не новым недостатком.
Кроме того, 9 предупреждений `nolang-overflow-ineffective` — это старая проблема инструмента: его поведение «заполнение пропусков» срабатывает на bigint /
перегруженных операциях строк и не связано с проталкиванием вниз. После второго прохода полный повторный прогон `bin/no run test-std/src/*.no`
(zstd / tls / str / json / set / base32 …) — **всё PASSED**.

Критерий повторного прогона после третьего прохода: 3 «красных» теста `parser` (`TestAnnotationsLiveOnAST` /
`TestCachedASTLowersToIdenticalHIR` / `TestBuildSemViewsMatchesFreshParse`) **до и после расширения
дословно одинаковы** — `only 288 files parsed cleanly` в оба раза одинаково, то есть расширение не вызвало новых ошибок разбора;
это «в полёте» состояние рефакторинга parser/annotation в параллельной работе. Вывод `no fmt -d src/std` до и после расширения
**побайтно одинаков**, то есть formatter выводит аннотации на `.` без изменений на те же места, без дрейфа форматирования. `test-std/src`
по heap / zstd / tls / json / set / map / regexp — весь зелёный.

**Осталось 76 аннотаций на заголовках ветвей** (`#{overflow=wrap}` непосредственно над `cond -> {`): они **не мёртвые строки** —
parser копирует аннотацию уровня ветки на каждую инструкцию в теле ветки, поэтому она действует на тело (проверено: одна строка аннотации на заголовке ветки заставляет тело
`r = i * 2` замолчать, и только условие в заголовке продолжает сообщаться). Но на **условии ветки** она не действует (условие — не инструкция).
Эти 76 мест остаются без изменений: постраочная вставка их не затрагивает (места в теле ветки уже замолчали и больше не сообщаются), а их удаление с последующим
повторным добавлением лишь вызвало бы топтание на месте в строке заголовка.

**51 место, которые по-прежнему сообщаются `no vet` и не могут быть аннотированы в текущем языке** (после второго прохода было 270, после расширения DOT в третьем проходе
осталось только это): целевая инструкция начинается с `{` (голый блок в позиции инструкции / match в скобках) или `(` (заголовок цикла `(cond) { }`),
а также несколько условий в заголовках ветвей. Сегодня они **тоже** сообщаются (исходная аннотация изначально не действовала), поэтому отзыв не является
регрессией; чтобы свести их к нулю, нужно сначала выполнить шаги 1–2 из §8 (объявить `overflow` на L2 ошибкой), а затем решить, нужно ли действительно поддерживать
L2 — см. шаг 4b из §8.

Проверка таких мест, как `archive/bzip2.no:315`, где `#{overflow=wrap}` есть **одновременно** на заголовке блока и внутри блока:
уровень на заголовке блока сейчас не действует, а работает постраочный уровень внутри блока (`--fix=overflow` его уже добавил). Поэтому удаление
уровня блока не меняет семантику; но после удаления повторный запуск `no vet` выявит места, которые замолчали только благодаря внешней аннотации, — это как раз
и есть цель ужесточения, а не побочный эффект. Проверено: количество подсказок `ovfhndld` в `crypto/rsa.no` выросло с 19 до 22,
все они приходятся на инструкции «привязано к `?T`, но не объявлено получение значения при переполнении»; семантика не изменилась.

Влияние на существующий код уровня L0: в `src/**/*.no` 21 файл имеет аннотацию в качестве первой значимой строки файла; 17 из них —
`#{js}`, остальные — `#{buildin}` и т.п. перед объявлением; у всех **нет** пустой строки, и по критерию L0 из §2
они по-прежнему относятся к L1, поэтому `no fmt` и компиляция работают как раньше. В `str.no` есть 2 случая «аннотация + пустая строка + ветка cond»,
находящихся внутри тела функции, так что критерий L0 не срабатывает.

## 8. Порядок ужесточения

1. **Сначала сделать так, чтобы `no vet` больше не признавал `overflow` на L1/L2**: удалить короткое замыкание «пропуск всей функции на уровне функции»,
   и ограничить `enclosingOverflow` поддеревом одной инструкции (не передавать вниз через блоки).
2. **Затем заставить parser сообщать об ошибке**: `#{overflow}` на L0/L1/L2 → ошибка компиляции, сообщение указывает «пожалуйста, аннотируйте каждую инструкцию
   либо запустите `no fmt --fix=overflow`». Этот шаг разом выявит весь существующий код.
3. **Очистка существующего кода**: `no fmt --fix=overflow` уже умеет проталкивать вниз (снимает уровень области действия, затем по сообщениям checker
   добавляет L3 для каждой инструкции); `src/std` прошёл три прохода (см. таблицу в §7). После изменений обязательно `make gen no` (перепечь
   blob и StdSigKey), при этом нельзя запускать `no fmt -w` на `src/std` — миграция затрагивает только строки аннотаций и выполняется покажно
   с помощью `no fmt -fix=overflow -w <f>`; `diff` гарантирует отсутствие других изменений.
4. **Расширить список целей в parser** (третий проход выполнил это наполовину):
   - **4a выполнено**: `parseAnnotationStatement` принимает инструкции, начинающиеся с **DOT**. `.n = .n + 1` /
     `.cnt == 0 -> …` и `x = …` относятся к одиночным инструкциям (L3), но раньше не принимали аннотации ⇒ в `src/std` было 219 мест,
     где `#{overflow=wrap}` никогда не действовала. После расширения неподдающихся аннотированию стало 51 вместо 270, `parser.ASTVersion` повышен до
     `2026-11-12.1`.
   - **4b ожидает решения**: `{` (голый блок в позиции инструкции / match в скобках) и `(` (заголовок цикла `(cond) { }`) — это **хосты
     блока L2**. Их расширение равносильно узакониванию семантики L2 для `overflow` (`overflowAnnotatedNode` вернётся раньше времени для всего
     блока), что противоречит направлению ужесточения в шагах 1–2. Правильный порядок — сначала шаги 1–2 (`overflow` на L2
     объявляется ошибкой), затем решить, нужно ли оставшиеся 51 мест решать путём «переписывания в инструкцию без блока» или «постраочного добавления в arm body»,
