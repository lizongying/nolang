# Синтаксис


## Комментарии

Nolang поддерживает маркеры **однострочных комментариев** и **многострочных (блочных) комментариев**:

- `;` — однострочный маркер (комментарий до конца строки)
- `;; <содержимое>` — однострочный маркер (если после `;;` **на той же строке** есть содержимое, комментарий идёт до конца строки, семантика совпадает с `;`)
- `;;\n` — многострочный (блочный) комментарий: если после `;;` **сразу следует перевод строки** (допускаются только пробелы), включается многострочный режим до встречи `;;`, за которым также следует перевод строки или EOF

```no
; это комментарий
; это тоже комментарий, семантика та же
;; это всё ещё однострочный комментарий (после ;; нет перевода строки)
x = 1; встроенный комментарий, до конца строки
x = 2;; встроенный однострочный комментарий, семантика та же

;;
Это многострочный (блочный) комментарий
Может занимать несколько строк
До встречи одиночного ';;'
;;

y = 3
;;
После закрывающего ;; должен быть перевод строки или конец файла
Только тогда он считается закрывающим разделителем
;;
```

> **Правило начала многострочного комментария:** после `;;` **могут быть только пробелы** (пробелы/табуляции) до перевода строки или EOF — только тогда включается многострочный режим. Если после `;;` на той же строке есть любой непробельный символ, это однострочный комментарий (до конца строки).
>
> **Правило окончания многострочного комментария:** закрывающий `;;` также должен сопровождаться переводом строки или EOF (между ними допустимы только пробелы). Незакрытый многострочный комментарий продолжается до конца файла.

> **Правило: одна инструкция на строку, несколько инструкций в одной строке запрещены.**
> Точка с запятой `;` — это **маркер комментария**, а не разделитель инструкций; запятая `,` тоже не может соединять инструкции. Каждая инструкция внутри блока `{ ... }` должна занимать отдельную строку.
> Это правило относится и к примерам кода внутри комментариев: даже в комментариях не пишите несколько инструкций в одной строке через `;` или `,`, чтобы не вводить читателя в заблуждение.

```no
#{fmt-skip}
; ❌ ошибка: разделение нескольких инструкций через `;` — после `;` вся строка становится комментарием,
; даже закрывающая `}` блока оказывается закомментированной, блок не закрывается, последующий код молча отбрасывается
; cond -> { print('X'); return }

; ❌ ошибка: соединение нескольких инструкций запятой
; h0 = 1732584193, h1 = 4023233417
; out = from-i64(v), out = from-u64(v)
; debug(msg), info(msg), warn(msg)
```

```no
; ✅ верно: каждая инструкция занимает отдельную строку
cond -> {
    print('X')
    return
}

; ✅ верно: каждая инструкция занимает отдельную строку
; h0 = 1732584193
; h1 = 4023233417
; out = from-i64(v)
; out = from-u64(v)
; debug(msg)
; info(msg)
; warn(msg)
```

> **Почему `;` особенно опасен:** в `cond -> { print('X'); return }` фрагмент `; return }` целиком считается комментарием, и реальный код сводится к `cond -> { print('X')`. Блок никогда не закрывается, и все инструкции после `}` (часто — остаток всего тела функции) поглощаются; место ошибки может сильно сместиться, и находить его очень трудно.

### Тип char (кодовая точка Unicode)

`char` представляет **одну скалярную кодовую точку Unicode** (scalar value). Его базовый тип хранения — **`i32`**, а не `i64`:

- **Допустимый диапазон**: `0 ..= 0x10FFFF` (то есть `0 ..= 1114111`). Для максимальной кодовой точки достаточно 21 бита, `i32` полностью вмещает её.
- **Ошибка при выходе за границы**: если литерал выходит за этот диапазон, компилятор (включая `no vet`) **немедленно сообщает об ошибке**. Например, `c char = 0x110000` ✗, `c char = 1114112` ✗; `c char = 1114111` ✓.
- **Разрешены арифметические операции**: `char` **может напрямую участвовать в целочисленных операциях**, например `z = a + 25`, `u = ch - 32` (где `ch` — переменная цикла `for ch <- s`) — это **нормальная практика**, сложение и вычитание по значению кодовой точки. Операции всегда выполняются в **ширине i32**, а результат считается обычным целым; поэтому `+ - * /` у `char` **не возвращают по умолчанию `option<int>`**, как это делает семейство целых типов, и не вызывают ошибки «необработанное целочисленное переполнение». Следить нужно лишь за диапазоном: максимум кодовой точки — `0x10FFFF`; в контекстах, выходящих за семантику `i32`/кодовой точки (например, смещения или накапливающие счётчики), рекомендуется сначала явно преобразовать в `i32`/`i64`, чтобы намерение было яснее.
- **Связь со `str`**: `s[i]` возвращает `char`; `char` неявно преобразуется в `str` (кодировка UTF-8), подробнее см. [Строки — неявное преобразование](str.md).

> **«Базовый тип» и «преобразование при вызове» — разные вещи.** Сам `char` — это `i32`. У встроенной функции `str_from_cp(cp char) -> ?str` **параметр в исходной сигнатуре** имеет тип `char`; только при **вызове внешнего runtime** компилятор **расширяет с нулём** (`zext i32 → i64`) этот параметр i32, чтобы соответствовать входным аргументам `@str_from_cp` в IR — это лишь временное преобразование при подготовке аргумента, **оно не меняет тип `char`**. Подобно C: `char c='a'; f((long)c);` — `c` сам по себе занимает 1 байт, а при вызове временно расширяется.

## Псевдонимы типов и типы-объединения

Псевдоним типа создаёт новое имя для существующего типа. Используется синтаксис с равно `name = type`; поддерживаются как одиночные псевдонимы, так и объединения нескольких типов.

### Синтаксис

```no
; тип-объединение: несколько типов разделяются |
int = i8 | i16 | i32 | i64 | i128 | u8 | u16 | u32 | u64 | u128
float = f32 | f64
num = int | float
string = str | txt

; одиночный псевдоним типа
bytes = []byte
buf = [16]u8
```

> `int`, `float`, `num` определены в `std/number`, `string` — в `std/str`; это не встроенные ключевые слова компилятора, а типы-объединения, записанные стандартной библиотекой с помощью того же синтаксиса псевдонимов.

### Цепочки ссылок в типах-объединениях

Тип-объединение может ссылаться на другие объединения, образуя иерархию:

```no
int = i8 | i16 | i32 | i64 | i128 | u8 | u16 | u32 | u64 | u128
float = f32 | f64
num = int | float; num — объединение int и float
string = str | txt; string напрямую объединяет два конкретных строковых типа
```

### Использование в функциях

Типы-объединения можно использовать в параметрах и возвращаемых значениях функций; компилятор автоматически выполняет мономорфизацию (monomorphization), создавая отдельную версию функции для каждого типа-члена:

```no
; тип параметра — объединение num
max = (a ..num) (r num) {
    r = a[0]
    n = len(a)
    i <- [1..n): {
        a[i] > r -> r = a[i]
    }
}

; метод определён на типе-объединении
num.sign = () (r num) {
    {
        . > 0 -> r = 1

        . < 0 -> r = -1

        -> r = 0
    }
}
```

`string` (= `str | txt`) также можно использовать в параметрах и возвращаемых значениях:

```no
; аргументы str и txt принимаются оба, для каждого создаётся своя конкретная функция
take = (s string) (n i64) {
    n = len(s)
}

a str = 'hello'
b txt = 'hi'
n1 = take(a); take__str
n2 = take(b); take__txt
```

> Существующие ограничения на тела функций с объединениями (одинаковы для `num` и `string`): вызов методов-членов на параметре union внутри тела (например, `s.len()`) пока не поддерживается; используйте глобальную встроенную функцию (`len(s)`, число байт) или разбейте на функции конкретных типов. Объявления переменных с типом-объединением (`s string = 'x'`) тоже пока не поддерживаются. Также не определяйте псевдоним-метод с тем же именем, что и метод-член (например, `string.len`) — он перехватит вызов `s.len()` и рекурсивно направит его сам в себя в теле метода.

### Правила распознавания

Синтаксис с равно распознаётся как псевдоним типа (а не присваивание переменной) в следующих случаях:

- `name = type | type | ...`: тип-объединение (с `|`)
- `name = []type`: тип среза
- `name = [N]type`: тип массива
- `name = ?type`: необязательный (nullable) тип
- `name = known-type`: одиночный псевдоним, где `known-type` — имя встроенного типа (например, `i64`, `f64`, `bool`, `str` и др.) или имя ранее определённого псевдонима типа

## Raw-строки (Raw String)

Raw-строку объявляют парой обратных кавычек `` ` `` ` ` `` ` ``; её тип — `str`.

### Синтаксис

```
sql = `
SELECT id,name
FROM user
WHERE id > 100
`
```

### Обязательные ограничения формата

1. **Открывающая** `` ` `` должна **немедленно сопровождаться переводом строки в исходном коде** (LF; CRLF в файлах Windows тоже принимается);
2. **Закрывающая** `` ` `` должна **занимать отдельную строку**, и на этой строке допустимы только пробелы + закрывающая обратная кавычка;
3. **Строки с открывающей и закрывающей кавычками не входят в содержимое строки**, они служат лишь разделителями;
4. **Правила экранирования**: все внутренние `\`, `\n`, `\t`, `\'`, `\"` сохраняются **как есть**, без какой-либо обработки экранирования;
5. **Переводы строк и пробелы отступа в исходном коде полностью сохраняются** в байтах строки; исключение — CR (`\r`): он **всегда отбрасывается**, поэтому CRLF-файлы и LF-файлы дают побайтно одинаковое значение;
6. **Нельзя напрямую вставить символ обратной кавычки**; если она нужна, используйте конкатенацию с обычной строкой в одиночных кавычках.

### Пример

```
; содержимое: "SELECT id,name\nFROM user\nWHERE id > 100\n"
; escape-последовательности \n \t сохраняются как есть, не интерпретируются
raw = `
line1\nline2
\ttabbed
`
```

## Регулярные литералы (Regex Literal)

Nolang поддерживает синтаксис регулярных литералов в стиле JavaScript `/pattern/flags` для создания уже скомпилированного экземпляра `regexp`.

### Синтаксис

```no
; базовый регулярный литерал
re = /\d+/

; с флагами (flags)
re = /hello/gi

; классы символов, якоря, квантификаторы
re = /[a-z]+/
re = /^hello.*world$/

; экранированная косая черта
re = /a\/b/
```

### Флаги

| Флаг  | Значение        |
| --- | --------- |
| `g` | глобальный поиск      |
| `i` | без учёта регистра    |
| `m` | многострочный режим      |
| `s` | `.` совпадает с переводом строки |

Флаги необязательны, идут после закрывающего `/` и состоят из ASCII-букв.

### Контекстно-зависимый лексический анализ

`/` — и оператор деления, и начало регулярного литерала; Nolang использует тот же **контекстно-зависимый** лексический анализ, что и JavaScript, чтобы их различать:

- **Позиция начала выражения** (начало инструкции, после `=` / `(` / `[` / `{` / `,` / `:` / `;` и т. д.) → `/` начинает регулярный литерал
- **Позиция получения значения** (после идентификатора, литерала, `)` / `]` / `}` и т. д.) → `/` — оператор деления
- `//` всегда однострочный комментарий (наивысший приоритет)

```no
; регулярный литерал (= — позиция начала выражения)
re = /\d+/
result = match-text(/[a-z]+/, text)

; оператор деления (после идентификатора — позиция получения значения)
ratio = 100 / 4
x = a / b
```

### Развёртывание (desugar)

На этапе генерации кода регулярный литерал разворачивается (desugar) в вызов функции стандартной библиотеки `regexp-compile`:

```no
; исходный код
re = /\d+/

; после развёртывания эквивалентно
re = regexp-compile('\\d+')
```

`regexp-compile` определён в `std/regexp.no`; он создаёт структуру `regexp` и вызывает `.compile()` для компиляции шаблона.

### Примеры использования

```no
; создать регулярное выражение и проверить совпадение
re = /\d+/
matched = re.matches('hello 123 world')
print(matched); true

; найти совпадение
re = /[a-z]+/g
result = re.find('hello 42 world')
print(result); "hello"

; в качестве параметра функции
result = match-text(/\d+/, text)
```

> **Внимание:** пустой pattern `//` конфликтует с однострочным комментарием (как и в JavaScript). Для пустого совпадения используйте `/(?:)/`.

## Правила имён

Имена переменных, функций, структур и т. д. могут начинаться с подчёркивания, дальше состоять из дефисов, букв и цифр; не могут начинаться с цифры, заканчиваться дефисом или содержать несколько дефисов подряд.

**Правила регистра (обязательные):**

- **Глобальные константы, глобальные переменные**: **должны** начинаться с заглавной буквы (например, `NOLANG`, `MAX-SIZE`, `HEX-CHARS`). Приватные глобальные переменные начинаются с подчёркивания, после которого всё равно нужна заглавная (например, `_NOLANG`, `_PRIVATE-CONST`).
- **Локальные переменные, параметры функций**: строчные буквы (например, `hex-chars`, `data-len`). **Не** используйте префикс `_` — локальные переменные и так приватны в своей области видимости, маркер видимости не нужен. Префикс `_` используется только для приватных глобальных и приватных FFI-объявлений.
- **Имена функций, имена структур**: строчные буквы (например, `sha1-block`, `db-mysql`)

**Соглашения об именовании функций (настоятельно рекомендуется):**

- **Не добавляйте префикс имени модуля к имени функции.** Функции внутри модуля достаточно коротких и понятных имён; префикс модуля автоматически подставляется как `ShortName.` при межмодульном вызове. Например, в `tail.no` определите входную функцию `tail`, а не `tail-run`, а вспомогательную — `atoi`, а не `tail-atoi`. Так код короче, а межмодульный вызов вроде `tail.tail()` понятнее.
- **Входная функция** рекомендуется называть самим именем модуля (например, `ping.no` → `ping`, `cat.no` → `cat`). Межмодульный импорт выглядит как `# /src/tail.tail`.
- **Избегайте ключевых слов**: `awy` (ключевое слово группы корутин), `match` (ключевое слово условного сопоставления) и др. нельзя использовать как имена функций. `run` удалён и может быть обычным идентификатором.
- **`main` — зарезервированное имя, его нельзя использовать как имя функции**: точка входа программы в Nolang **синтезируется автоматически из инструкций верхнего уровня** (см. `hir2mir.synthesizeMainForTopLevel`), поэтому явное определение `main` не нужно и **не допускается**. Как только появляется `main = (...) { }` — включая метод `recv.main` и `main`, вложенный в другую функцию, — компилятор сразу выдаёт ошибку (`'main' is a reserved name and cannot be used as a function name`). Чтобы служить точкой входа, просто пишите инструкции на верхнем уровне.

> **Глобальные переменные должны начинаться с заглавной буквы** — это обязательное правило, а не соглашение. Топ-level переменная со строчной буквы будет сочтена компилятором локальной, что может привести к ошибкам неопределённой ссылки.

```no
; ✅ верно: глобальные данные пишутся с заглавной буквы
NOLANG = 'nolang'
MAX-SIZE = 1024
HEX-CHARS = '0123456789abcdef'

; ✅ приватная глобальная переменная: подчёркивание, затем заглавная
_NOLANG = 'nolang'
_PRIVATE-CONST = 42
```

```no
#{fmt-skip}
; ❌ ошибка: глобальные переменные не mogą начинаться со строчной буквы
; x1 = 10
; x = 10
; foo-bar = 42
; hello-world = 'Hello World'
```
```

```no
#{fmt-skip}
; ✅ локальные переменные (внутри функции) со строчной буквы, без префикса _
; fn-example = () {
;     x1 = 10
;     x = 10
;     foo-bar = 42
;     hello-world = 'Hello World'
;     ; ❌ ошибка: локальным переменным не нужен префикс _
;     ; _x = 10
; }
```
```

### Избегайте глобальных переменных в модулях

**Настоятельно рекомендуется:если нет крайней необходимости, не используйте глобальные переменные в модулях (`.no`-файлах).** Глобальные переменные создают следующие проблемы:

- **Риск багов компилятора**: у компилятора Nolang есть известные ограничения в обработке адресов памяти глобальных структурированных переменных между функциями; разные функции могут видеть разные адреса, что ведёт к несогласованности состояния.
- **Безопасность конкурентности**: глобальное изменяемое состояние трудно отслеживать при fork или в асинхронных сценариях, легко возникают состояния гонки.
- **Тестируемость**: глобальное состояние создаёт неявные зависимости функций, что затрудняет изолированное тестирование.
- **Читаемость кода**: глобальные переменные делают поток данных неявным; читателю приходится отслеживать весь модуль, чтобы понять поведение функции.

**Рекомендуемый подход:**

1. **Предпочитайте локальные переменные**: удерживайте состояние в локальных переменных внутри функций, передавайте его через параметры и возвращаемые значения.
2. **Инкапсулируйте состояние в структуре**: организуйте связанное состояние в структуре и работайте с ним через методы (получатель метода — локальная переменная, адрес согласован).
3. **Используйте глобальные переменные только при необходимости**: например, константы уровня модуля (неизменяемые), одиночные ресурсы (например, глобальный буфер логирования).
4. **Глобальные переменные должны быть с заглавной**: это обязательное правило (см. выше); топ-level переменная со строчной буквы будет сочтена компилятором локальной.

```no
#{fmt-skip}
; ❌ избегайте: глобальные изменяемые переменные в модуле
; g-conn = tls.conn {}
; g-buf = ' '
;
; fn-a = () {
;     g-conn.send(g-buf)   ; адрес глобальной переменной между функциями может различаться
; }
```
```

```no
; ✅ рекомендуется: локальные переменные, состояние передаётся через параметры/возвраты
fn-a = () {
    conn = tls.conn {}; локальная переменная, адрес согласован
    buf = ' '
    conn.send(buf)
}

; ✅ рекомендуется: инкапсулировать весь поток в одну функцию, не передавая состояние между функциями
serve-once = (listen-fd fd, body str) (ok bool) {
    ok = false
    client-fd = net.net-accept(listen-fd)
    conn = tls.server-init(client-fd); локальная переменная
    conn: {
        ok -> {
            c = it
            c.handshake()
            c.send(body)
            c.close()
            ok = true
        }

        -> fs.close(client-fd)
    }
}
```

> **Практический пример**: функция `https-serve-once` из `std/net/tls.no` инкапсулирует полный цикл HTTPS-запрос-ответ (accept + handshake + recv + send + close) в одной функции, всё состояние TLS удерживается в локальных переменных, что позволяет успешно обойти баг компилятора с несогласованностью адресов глобальных переменных между функциями.

## Спецификация документации API

Документирующие комментарии функции должны содержать полные имена и типы параметров, а также имена и типы возвращаемых значений.

**Правила:**

- Документирующий комментарий над определением функции должен перечислять имя и тип каждого параметра, а также имя и тип возвращаемого значения
- Сводка API в верхней части модуля тоже должна использовать полные сигнатуры (с именами параметров, типами, именами и типами возврата), без сокращений

```no
#{fmt-skip}
; ❌ ошибка: нет типов, нет имени возвращаемого параметра
; sha1(data) (hash)
; sha1-block(s, h0..h4)
```
```

```no
; ✅ верно: есть имена параметров, типы, имена и типы возврата
; sha1(data []byte) (hash [20]byte) — полный хеш
; sha1-block(s []u32, h0 u32, h1 u32, h2 u32, h3 u32, h4 u32) — обработка одного блока

; документирующие комментарии над определением функции также должны соблюдать ту же норму:
; sha1: вычислить хеш SHA-1
; data []byte: входной массив байт
; возврат hash [20]byte: 20-байтовое значение хеша
sha1 = (data []byte) (hash [20]byte) {
    ...
}
```

### Переводимые документирующие комментарии (Markdown-ссылка)

Документирующий комментарий может заканчиваться **отдельной Markdown-ссылкой**, указывающей весь комментарий на запись в каталоге переводов:

```no
; get: получить i-й аргумент
; делегирует встроенной функции os.arg(i) (читает argv[i] из main); при выходе за границы — nil
; [get](#args.get)
get = (i i64) (val ?str) {
    val = os.arg(i)
}
```

**Правила:**

- Ссылка должна быть **последней строкой** группы комментариев и занимать отдельную строку; все строки над ней образуют единое целое и переводятся целиком как одно сообщение
- Цель должна быть якорём, начинающимся с `#` (запись внутри того же каталога). Внешние ссылки вроде `[пояснение](https://example.com)` — это обычные ссылки для людей и **не** считаются маркерами перевода
- Якорь — это ключ (`args.get`). Его задаёт автор, переводчик видит его в каталоге; он не выводится из текста, поэтому переформулировка не обесценивает существующий перевод. В якоре допустимы буквы, цифры, `.`, `_`, `-`; он глобален, рекомендуется добавлять префикс модуля
- Префикс — это **выровненное (flattened) имя модуля**, а не имя каталога. Компилятор выравнивает std-файл в его имя файла: модуль `std/collection/linked-hash-map.no` — это просто `linked-hash-map`, а `use std/collection` не добавляет символам префикс `collection.`. Поэтому якорь для `linked-hash-map.clear` — `linked-hash-map.linked-hash-map.clear` (имя модуля + имя как есть), а **не** `collection.linked-hash-map.linked-hash-map.clear`. Сегменты каталогов `collection`/`net`/`crypto`/`archive`/`encoding`/`database` не принадлежат ни одному символу и не должны появляться в якорях
- Текст в квадратных скобках (`[get]`) — это лишь подсказка для читающего исходный код; при отображении вся строка удаляется; `[](#args.get)` тоже допустимо
- Только однострочные комментарии `;` могут содержать ссылку (`;;` и `;;block` не учитываются)

Переводы лежат в `locales/<язык>-doc.noml`, ключ — якорь. Если перевода нет, используется исходный текст комментария, а не пустота. Имя файла следует правилам имён `.no` (строчные буквы, цифры, одиночный дефис); сама метка имеет этот вид: `--lang=zh-tw` читает `zh-tw-doc.noml`.

У каждой функции и метода со комментарием в стандартной библиотеке уже есть якорь (около 2000), поэтому любой новый перевод сразу доступен LSP. `make i18n` записывает в каталог только **переведённые** записи и не подставляет исходный текст как перевод — иначе в английском каталоге снова появился бы китайский. `go run ./i18n/cmd/genen -doc-missing` выводит якоря, у которых ещё нет перевода.

**Подсказка LSP:** при наведении курсора на имя функции показывается весь переведённый текст; при наведении на строку со ссылкой показывается содержимое, на которое указывает сам якорь (тоже на текущем языке), чтобы сверить перевод на месте.

## Предпочитайте стандартную библиотеку

Стандартная библиотека Nolang предоставляет множество часто используемых возможностей: операции со строками, преобразование байт, вычисление хешей, сетевое взаимодействие и др.

**Правило: если соответствующая функция уже есть в стандартной библиотеке, не рекомендуется реализовывать её заново.** Разработчику следует внимательно изучить документацию стандартной библиотеки (`docs/docs/std/overview.md`), чтобы не изобретать велосипед.

```no
#{fmt-skip}
; ❌ ошибка: самостоятельная реализация преобразования str → []byte
str-to-bytes = (s str) (out []byte) {
    n = s.len-bytes()
    i = 0
    (i < n) {
        out[i] = s[i]
        i = i + 1
    }
}
```
```

```no
; ✅ верно: использовать метод стандартной библиотеки str.to-bytes()
data []byte = s.to-bytes()
```

Частые замены из стандартной библиотеки:

- `str.to-bytes()` — строка в массив байт (вместо самописного `str-to-bytes`)
- `[]byte.to-str()` — массив байт в строку (вместо самописного `bytes-to-str`)
- `[n]t.to-vec()` — массив фиксированной длины в срез (`[20]byte` → `[]byte`)
- `[]byte.to-hex()` / `[]byte.to-hex-lower()` — массив байт в шестнадцатеричную строку
- `str.to-i64()` / `str.to-f64()` — разбор строки в число
- `int.to-str()` / `float.to-str()` — число в строку
- `std/crypto/sha1`, `std/crypto/sha256`, `std/crypto/sha512` — вычисление хешей

### Конфигурационные файлы TOML (`toml`)

Стандартная библиотека `toml` обеспечивает разбор и сериализацию конфигурационных файлов TOML 1.0. Парсер поддерживает комментарии, ключи bare/quoted/dotted, `[table]`, `[[array-of-tables]]`, строки basic/literal/multiline, целые (десятичные/шестнадцатеричные/восьмеричные/двоичные), числа с плавающей точкой, логические значения, даты и время, массивы и inline table. Значения сохраняются как исходные литералы TOML, поэтому информация о массивах, датах и времени не теряется.

```no
cfg = toml.parse('title = "Nolang"\n[server]\nport = 8080\n[[server.backends]]\nname = "local"')

doc = toml.new()
doc.put('name', '"nolang"')
doc.put('server.port', '8080')
doc.put('enabled', 'true')
text = toml.stringify(doc)
```

Частые API:

- `toml.new()` — создать пустой `toml`
- `toml.parse(text)` — разобрать TOML, вернуть `?toml`
- `doc.put(key, raw-value)` — добавить или обновить исходное значение TOML; некорректные значения отклоняются, дублирующиеся ключи выявляются парсером
- `toml.get(doc, key)` — получить исходное значение (`?str`)
- `toml.get-str(doc, key)`, `toml.get-i64(doc, key)`, `toml.get-f64(doc, key)`, `toml.get-bool(doc, key)` — получить преобразованное скалярное значение
- `toml.stringify(doc)` — вывести TOML; array-of-tables выводятся с заголовками `[[...]]`

Текущая модель документа ограничивает один документ 4 ключами, 2 обычными таблицами и 2 array-of-tables; один ключ — не более 32 байт, одно значение — не более 128 байт; при превышении следует разделить конфигурационный файл или обработать это в вызывающем коде.

### YAML-документы (`yaml`)

Стандартная библиотека `yaml` разбирает и порождает документы YAML 1.2 core schema; поддерживает блочные отображения, блочные последовательности, потоковые коллекции, три вида кавычных скаляров, блочные скаляры `|` / `>`, комментарии, несколько документов, якоря и псевдонимы, ключ слияния `<<`, явные ключи, а также вывод типов (null / bool / int / float / `.inf` / `.nan`).

```no
doc ?yaml = yaml.parse('name: Alice\nserver:\n  port: 8080\ntags:\n  - a\n  - b\n')
doc: {
    nil -> print('nil')

    err -> print(it.msg())

    -> {
        doc = it
        name = doc.find-str('name'); ?str
        port = doc.find-i64('server.port'); ?i64
        name: {
            ok -> print(it)

            -> print('')
        }
        print(doc.to-json())
    }
}
```

Частые API:

- `yaml.parse(text)` / `yaml.parse-all(text)` — разбор, возвращает `?yaml`
- `yaml.valid-of(text)` / `yaml.error-of(text)` — только проверка
- `it.find(path)` / `it.get(key)` — получить дочерний узел, возвращает `?yaml`
- `it.find-str(path)`, `find-i64`, `find-f64`, `find-bool` — удобные методы получения значений, возвращают `?значение`
- `it.to-json()` / `it.to-yaml()` — сериализация

> Внимание: дочерние узлы возвращаются как `?yaml`, а вспомогательные функции получения значений — как `?значение`; распаковывайте через match (`child = it.find(path)`, его ветка `ok` связывает дочерний узел через `it`, ветка по умолчанию обрабатывает пустое значение; каждая ветка — на отдельной строке).

## Имена файлов

Имена `.no`-файлов (включая имена папок) всегда соединяют слова дефисом `-`, а **не подчёркиванием `_`**. Это согласуется со стилем имён других идентификаторов Nolang — переменных, функций, структур.

Компилятор **принудительно проверяет** это правило в командах `run` / `build` / `test` / `vet` / `fmt` / `ast`; любой сегмент пути (имя папки или основная часть имени файла, расширение `.no` не учитывается), нарушающий правило, **сразу вызывает ошибку**:

- Допустимые символы: строчные буквы `a-z`, цифры `0-9`, дефис `-`.
- Запрещённые символы: подчёркивание `_`, заглавные буквы и другие специальные символы.
- Дефис не может стоять в начале или конце сегмента и не может идти подряд (`--`).

Например, `tmp/zz_stridx/r_index.no` отклоняется из-за подчёркиваний в `zz_stridx` и `r_index`; замена на `tmp/zz-stridx/r-index.no` делает имя корректным. Абсолютные пути ОС (например, `/Users/me/proj/a.no`) проверяются только в части, лежащей внутри текущего рабочего каталога; имена каталогов хоста (например, `Users`) ошибочно не сообщаются.

```shell
✅ рекомендуется:
utils/
├── string-helper.no
├── hash-table.no
└── http-client.no
```

```shell
❌ избегайте:
utils/
├── string_helper.no
├── hash_table.no
└── http_client.no
```

## Определение функций

Функция может **возвращать результат через именованные параметры результата (named result parameters)** — по сути, это  
**синтаксический сахар выходных параметров (out-parameter)**; `return` (и его сокращение `***`, пока не рекомендуется) служит только для досрочного завершения и не может сопровождаться результатом.

Форма определения функции в Nolang: `name = (in-params) (out-params) { body }`; вторая  
группа скобок `(out-params)` объявляет именованные параметры результата (синтаксический сахар). Присваивание им значений внутри тела  
(как и обычным входным параметрам — это ссылочные типы); **переменная, действительно получающая результат, должна быть определена в точке вызова** —  
имя параметра результата в определении — лишь заполнитель; LHS вызывающей стороны (или concluding аргумент) определяет, в какую  
переменную попадёт результат:

```no
parse-line = (s str, max-fields ?i64) (fields []str) {
    ...; присваивание fields внутри тела функции
}

; в точке вызова определить переменную-получатель (связывание LHS, тип выводится из сигнатуры)
fields = parse-line(line, nil)

; несколько результатов связываются по порядку
a, b = swap(x, y)

; или форма с concluding аргументом: res передаётся как дополнительный выходной аргумент
add1(5, 3, res)
```

Функции в Nolang имеют следующие особенности:

- **Именованные параметры результата — синтаксический сахар**: на нижнем уровне всё делается через входные параметры (out-parameter), новый объект возвращаемого значения не создаётся, поэтому внутри безопасно.
- **Входные параметры доступны только для чтения**: скаляры передаются по значению, составные типы — по ссылке только для чтения; запись во входные параметры и их вложенные поля в теле функции запрещена.
- **Выходные параметры доступны для записи**: вызывающая сторона может связать уже существующую переменную с выходным слотом, и функция изменит её память напрямую; можно также не связывать — тогда функция создаёт новое значение и передаёт его.
- **Переменные внутри функции уничтожаются при её выходе.**
- **В точке вызова должна быть переменная-получатель** (LHS или concluding аргумент); утверждение «функция не возвращает значение» неточно —  
точное утверждение: результат передаётся через именованные параметры результата (синтаксический сахар out-parameter) и связывается в точке вызова.
- **Правило псевдонимов**: входная ссылка только для чтения и выходной слот могут указывать на один объект. Если запись происходит только в области вывода, а ввод только читается, это корректно; компилятор не выполняет статическую проверку псевдонимов.
- **Правило псевдонимов**: входная ссылка только для чтения и выходной слот могут указывать на один и тот же объект. Это допустимо, пока операции записи происходят только в выходной области, а вход только читается; компилятор не выполняет статическую проверку псевдонимов.

### Выходной слот напрямую связывается с существующей переменной (без промежуточных переменных)

Выходной слот на стороне вызова может **связываться напрямую с уже существующей переменной**, и функция изменит её память на месте (см. выше «Выходные параметры доступны для записи»).
Поэтому, если выходное значение нужно лишь для продолжения обновления уже существующего состояния, не нужно сначала принимать его в одноразовую промежуточную переменную, а затем записывать обратно:

```no
; ✅ рекомендуется: остаток записывается прямо в r (r одновременно — получатель метода)
qsq, r = r.div-mod(modulus)
```

```no
; ❌ избегайте: msq используется только один раз, просто перевалочная переменная
qsq, msq = r.div-mod(modulus)
r = msq
```

- **Получатель может одновременно быть целью вывода**: у `r.div-mod(modulus)` получатель `r` — это вход только для чтения (неявный `self`),
  и он же связан со вторым выходным слотом `r bigint`; по〈Правилу псевдонимов〉ввод только читается, вывод только пишется — это корректно.
  Проверено (`no build` / `no vet` / `no fmt`): `q, a = a.div-mod(bigint.from-i64(7))` после
  `a = bigint.from-i64(100)` даёт `q = 14`, `a = 2`, полностью совпадая с вариантом «сначала в `msq`, затем `r = msq`»;
  то же верно, даже если `r` — параметр результата внешней функции (именно такую форму имеет `mod-pow` в `src/std/bigint.no`).
- **Неиспользуемый вывод отбрасывается через `_`**: если частное вообще не используется, `_, r = r.div-mod(modulus)` не требует введения даже одной новой переменной —
  это самая компактная запись (см. ниже〈Множественное присваивание〉, заполнитель `_`).
- **Для одного вывода тоже верно**: `r = r._mul(r)`, `s = s.trim()`, `out = out.replace-str(...)` — это существующие в stdlib обновления на месте.
- **Уже корректный код не нужно переписывать**: это рекомендация для нового кода, а не указание к рефакторингу; следуйте〈Золотому правилу: не изменяйте корректный код〉,
  не трогайте уже правильные программы ради стиля.

### Значения параметров по умолчанию

**Не поддерживаются.** Конструкция `name type = expr` в списке параметров (например, `foo = (a i64, b ?i64 = 10)`) — это **синтаксическая ошибка** (`E_DEFAULT_PARAM`): компилятор не разбирает выражение по умолчанию и не подставляет значения по умолчанию ни в одной точке вызова. Это устраняет неоднозначность «одно объявление — несколько допустимых arity» и избегает раздувания мономорфов из-за повторного понижения выражения по умолчанию в каждой точке вызова.

Если нужна необязательная семантика, объявите параметр с типом option `?T`, а вызывающая сторона **явно** передаёт `nil` / `ok(...)`, и тело функции обрабатывает это через `match`:

```no
parse-line = (s str, max-fields ?i64) (fields []str) {
    limit = 1024
    max-fields: {
        ok(v) -> limit = v

        nil ->

        err ->
    }
    ...; limit — это верхняя граница
}

; вызывающая сторона должна явно передавать аргументы
fields = csv.parse-line(line, nil); откат 1024
fields = csv.parse-line(line, ok(256)); предел 256
```

```no
add = (a i64, b i64) (result i64) {
    result = a + b; вернуть результат через параметр
    ...; инструкция-заполнитель: ничего не делает, при build удаляется целиком (см.〈Инструкция-заполнитель〉)
}

; переменное число аргументов
add3 = (a ..i64) {
}

; вызов функции
sum = add(1, 2); sum == 3

; анонимная функция и for? с передачей аргументов?
(a i64) {
    print(a)
}(10)

; вызов функции
add(a, b)

; также может быть несколько возвращаемых значений
a, b = swap(5, 3)
```

## Управление потоком выполнения

> **Устаревший синтаксис (будет удалён после версии n)**: `for { }` / `for cond { }` / `for init, cond, update { }` / `for i in [..) { }` / `match x { }` / `if/elif/else { }` всё ещё разбираются, но выдают предупреждение об устаревании. Используйте «**новый синтаксис**» ниже.

### Сравнение старого и нового

| Старый / суффиксный (suffix)        | Префиксный (prefix, по умолчанию в format)          |
| -------------------------- | --------------------------------------- |
| `{ } (true)` бесконечный цикл          | `!! { }` или `true { }`                   |
| `{ } (cond)` условный цикл          | `(cond) { }` (пустое `()` считается false, не выполняется)       |
| `{ } ()` не выполняется               | `! { }` или `false { }` или `() { }`        |
| `{ } * n` константный счётчик             | `n * { }` (при N ≤ 0 тело цикла не выполняется)                |
| `for i=0, i<n, i++ { }` счётчик | `n * { }` (константный счётчик) или `i <- [0..n): { }` (переменная) |
| `for i <- [a..b] { }` диапазон   | `i <- [a..b]: { }`                      |
| `for i in [a..b) { }` диапазон   | `i <- [a..b): { }`                      |
| `match x { ... }` сопоставление       | `x: { ... }`                            |
| `if/elif/else { }` ветвление      | `{ cond -> body }` (сокращённая форма, нужно оборачивать в `{}`)      |
| `continue`                 | `*` (сокращение пока не рекомендуется)                        |
| `break`                    | `**` (сокращение пока не рекомендуется)                       |
| `return`                   | `***` (сокращение пока не рекомендуется)                      |

### Loop / While / for-in

> **Две эквивалентные формы записи**: один и тот же цикл поддерживает «префиксную форму `(cond) { }`» и «суффиксную форму `{ } (cond)`»;  
> семантика полностью одинакова, различается только порядок условия и тела. `no fmt` по умолчанию выводит **префиксную форму**;  
> `no fmt -loop-style=suffix` переключает обратно на суффиксную (обе формы гарантируют идемпотентность форматирования).

```no

### Выход / пропуск / досрочный возврат

> ⚠️ **`*` (пропустить текущую итерацию) / `**` (выйти из цикла) / `***` (вернуть-завершить) — эта группа сокращений пока не рекомендуется** — пишите
> английские ключевые слова `continue` / `break` / `return`; `no fmt` приведёт все поддерживаемые сокращения к ключевым словам.

```no
i <- [0..10): {

    ; continue (пропустить текущую итерацию, пока не рекомендуется)
    continue

    ; break (выйти из цикла, пока не рекомендуется)
    break

    ; return/terminate (досрочный возврат, только завершает функцию; планируется, пока не рекомендуется)
    break
    continue
}

; рекомендуется использовать английские ключевые слова (как в C/Rust, удобно портировать, корректно компилируется и выполняется):
i <- [0..10): {

    ; эквивалент * (пока не рекомендуется)
    continue

    ; эквивалент ** (пока не рекомендуется)
    break

    ; эквивалент *** (пока не рекомендуется), только досрочно завершает функцию
    return
}

; псевдонимы ключевых слов (лексер поддерживает полностью, полностью эквивалентны исходным ключевым словам):
;   ctn ≡ continue, brk ≡ break, rtn ≡ return; `no fmt` сохраняет исходное написание псевдонима
i <- [0..10): {

    ; эквивалент continue
    ctn

    ; эквивалент break
    brk
}

; эквивалент return, только досрочно завершает функцию
rtn
```

> ⚠️ **`return` (и его сокращённая форма `***`, пока не рекомендуется) можно использовать только отдельно, без возвращаемого значения.**
> У функций Nolang нет механизма «возвращаемого значения» — результат всегда передаётся через **именованные параметры результата (out-param)** и присваивается внутри тела функции (см. «Определение функций»).
> Поэтому `return <значение>`, `return(expr)`, `*** <значение>` **запрещены**; компилятор / formatter / LSP сообщат об ошибке:
>
> - компилятор (`no build`): `Error: compilation error: parser errors: line L, column C: после 'return' не может следовать возвращаемое значение; … [E_GENERAL]`
> - `no vet`: `<file>:L:C: [ERROR] nolang-compile: после 'return' не может следовать возвращаемое значение; … [E_GENERAL]` (тот же формат, что и у других диагностик, по одной на строку)
> - `no fmt`: `format error: …` и выход с ненулевым статусом
> - LSP: показывает красную диагностику ошибки на соответствующей строке
>
> Неправильная запись:
>
> ```no
> has = (n i64) (r i64) {
>     n == 0 -> return 0        ; ❌ компилятор / formatter / LSP сообщают об ошибке
>     r = n
> }
> ```
>
> Правильная запись (сначала присвоить параметру результата, затем отдельно `return` для досрочного завершения; несколько инструкций в теле ветки должны занимать по одной строке):
>
> ```no
> has = (n i64) (r i64) {
>     n == 0 -> {
>         r = 0
>         return
>     }
>     r = n
> }
> ```
>
> ⚠️ сжатие в одну строку `n == 0 -> { r = 0; return }` — это не сокращение: фрагмент `; return }` целиком — комментарий,
> поэтому блок никогда не закрывается, и все последующие инструкции (часто — остаток всего тела функции) молча поглощаются этой веткой —
> проверено: `no vet` не сообщает об ошибке, а функция никогда не вызывается.

## Каналы (`chan[T]`)

Канал — это **ограниченная, расширяемая очередь значений с неблокирующей отправкой и ожидающей приёмом**, получатель берёт значения по одному через трёхсостояние `?T`.
Он сохраняет только один синтаксический символ: `<-` (остальные применения см. в «Управлении потоком», обход `i <- range:`).

```no
ch chan[i64] = with-cap(8)   ; явная начальная ёмкость
buf chan[i64]                 ; голое объявление: эквивалентно with-cap(0), растёт по мере отправки

ch <- 1                       ; отправить (тип слева должен быть chan[T], чтобы это была отправка)
n = ch.len()                  ; текущее число накопленных значений
c = ch.cap()                  ; начальная ёмкость
ch.close()                    ; закрыть: больше не принимает отправки, существующие значения ещё можно взять
```

### Приём: цикл с тремя состояниями

`v <- ch: { ... }` — это **цикл**, на каждой итерации связывающий трёхсостояние `?T` с `v`; `break` может досрочно выйти.
`ok` означает полученное значение, `nil` — канал закрыт и опустошён, `err` — **настоящая ошибка** (неинициализированный
нулевой дескриптор — нечего ожидать); **последние два также завершают цикл** (ветки той же итерации выполняются как обычно).

Главное правило, кроме `ok`: **пустое чтение — это «ожидание значения», а не «отсутствие значения»**. Пока канал открыт, но пуст, читатель
приостанавливается, пока кто-то не вызовет `send` или `close`:

- в корутине (`-async`-клон, полученный через `co`) он действительно park: номер состояния записывается во фрейм в куче, задача
  регистрируется в цепочке ожидания канала и возвращается планировщику (см. раздел «Корутины»);
- в обычной функции нельзя park, поэтому происходит **блокировка**: планировщик многократно прогоняет очередь готовых задач, пока не появится значение.

Поэтому «истощение» должно завершаться через `close()`, форма совпадает с `range` по channel в Go.

```no
ch chan[i64] = with-cap(2)
ch <- 10
ch.close()

<- ch: {
    ok -> print('got {it}')      ; it — элемент текущей итерации
    nil -> print('closed')       ; сюда попадаем после истощения
    err -> print('bad channel')  ; сюда попадаем только с нулевым дескриптором
}
```

Чтобы отбросить переменную цикла, пишите `<- ch: { ... }`; если первая инструкция body — не match для `v`,
то `v` связывается **непосредственно с самим элементом** (`T`, а не `?T`), и body выполняется только на итерациях `ok`:

```no
i <- ch: {
    print(i)                     ; i — это i64, не ?i64
}
```

Чтобы различать три состояния самому и одновременно сохранить переменную цикла, достаточно начать body с match её; записать только ветви (опустив `v:`)
— это синонимичное сокращение — признак лежит в **именах ветвей**: три состояния считаются, только если присутствуют имена `ok` / `nil` / `err`:

```no
i <- ch: {
    ok -> print('got {it}')      ; it — элемент текущей итерации, i — её ?i64
    nil -> print('closed')
    err -> print('empty')
}
```

Признак синтаксический, а не типовой (см. ниже «Определение формы»). `no fmt` дополнит указанное сокращение до
явного подлежащего `i: { ... }`; обе формы разбираются снова, форматирование идемпотентно.

### Определение формы

| Начало body | Форма | Тип `v` |
|---|---|---|
| `co bar(i)`, `print(i)` и другие обычные инструкции | Элемент | `T` |
| `v: { ... }` | Три состояния | `?T` |
| `ok -> ...` / `nil -> ...` / `err -> ...` | Три состояния (сокращение) | `?T` |
| Другой голый match (например, `i > 5 -> ...`) | Элемент | `T` |

Определение должно выполняться **до разбора body**: если блок начинается с match, парсер сразу разворачивает его в
цепочку `if`, и afterwards исходный смысл уже не распознать. Однажды эта ячейка полностью вышла из строя — `i <- ch:` всегда считался формой элемента,
ветви трёх состояний вырождались в независимые guard (выполнявшиеся на каждой итерации), а `it` связывался с пустым значением.

### Семантика

| Аспект | Правило |
|---|---|
| Ёмкость | `n` в `with-cap(n)` — **начальная** ёмкость; при заполнении удваивается, `send` **никогда не блокируется и не теряет значения** |
| Пустое чтение | **Ожидание**: корутина park, обычная функция блокирующе прогоняет очередь готовых задач; `err` остаётся только для настоящей ошибки — нулевого дескриптора |
| Закрытие | После `close()` вызов `send` завершает процесс; уже поставленные в очередь значения всё ещё можно взять по порядку, после истощения — `nil`; закрытие одновременно будит всех ожидающих |
| Полезная нагрузка | При отправке **глубокое копирование** (`str` / `%vec` идут через clone), получатель берёт независимую копию; не нужно беспокоиться, что исходная переменная будет перезаписана или освобождена заранее |
| Параллелизм | Сам канал не блокируется (однопоточная кооперативная планировка): ожидающие висят в цепочке `waiters` блока управления, `send` / `close` снимают всю цепочку и по одному возвращают в очередь; **быть разбуженным — не значит получить значение**, после возобновления нужно заново проверить доступность, поэтому точка возобновления корутины — сам блок park |
| Взаимоблокировка | Очередь готова пуста, целевая задача ещё не завершена ⇒ дальше двигаться нельзя: во время выполнения печатается `nolang: deadlock: …` в stderr и выполняется abort, а не возврат значения, которое никто не отправлял, или холостой цикл |

> Прямое следствие приостановки при пустом чтении: **цикл опустошения должен завершаться через `close()`**. В ранних версиях «открыт, но пуст» сообщалось как `err`, чтобы цикл естественно завершался, и форма `for` не требовала закрывать канал; теперь этот путь — ожидание,
> и программа, забывшая `close()`, остановится на последней итерации (в корутине — приостановится, в обычной функции — будет признана взаимоблокировкой).
> Программа, забывшая `close()`, остановится на последней итерации (в корутине — зависнет, в обычной функции — будет распознана как взаимоблокировка).

### Ограничения

- **Реализовано только в LLVM-бэкенде.** `no build --js` / `--wasm` при встрече любого узла канала выдают явную ошибку
  (`[chbkn001]`), а не молча порождают неполный код.
- Канал — **тип-значение** (дескриптор шириной в одно машинное слово), его можно передавать как параметр, результат или элемент;
  `chan[chan[T]]`, `?chan[T]` тоже можно объявлять (пока не покрыто `tests/chan.no`).

## Инструкция-заполнитель (`...`)

`...` — это **инструкция-заполнитель** языка: синтаксически корректная, семантически **ничего не делает**. Используется главным образом для демонстрации в документации,
каркасов кода и мест под `TODO`. При компиляции инструкция целиком отбрасывается на стадии AST→HIR, и результат
полностью совпадает со случаем «этой строки никогда не было» (проверено: бинарники, собранные из одного и того же исходника с `...` и без него, имеют одинаковый `sha256`).

```no
parse-line = (s str) (fields []str) {

    ; TODO: здесь ещё нужно обработать escape-символы
    ...

    fields = csv.parse-line(s)
}

add = (a i64, b i64) (result i64) {
    result = a + b
    ...
}
```

Правила:

- **Может занимать только отдельную строку** (в конце строки может идти `;`-комментарий). Записи вроде `fail -> ...`, `x = ...`, `[0...n)`
   — это синтаксическая ошибка: у `...` нет значения, она не может стоять в позиции выражения или в остальной части инструкции.
- **Не псевдоним `return`** и **не оператор диапазона**: диапазон — это `..` (две точки), досрочный возврат пишется `return`.
- `no fmt` сохраняет её как есть, не удаляя и не перемещая.

Следующие записи полностью некорректны:

```no
#{fmt-skip}
add = (a i64, b i64) (result i64) {
    result = a + b
    ...          ; ✅ единственная корректная форма: отдельная строка
}

ok -> ...        ; ❌ синтаксическая ошибка: `...` не может стоять в позиции выражения
x = ...          ; ❌ синтаксическая ошибка: то же
i <- [0...n): {  ; ❌ синтаксическая ошибка: `...` не оператор диапазона, нужно писать [0..self.n)
}
```

### Match

```no
; простая форма, it используется для получения параметра
x: {
    err -> log(it.msg()); it — структурированная ошибка err.err

    nil -> log('nil')

    -> do-right-thing(it)
}

; форма с деструктуризацией
x: {
    err(e) -> log(e.msg())

    nil -> log('nil')

    ok(v) -> do-right-thing(v)
}

; примечание: сопоставление с образцом struct (`user: { User{id=1} -> ... }`) и связывание полей пока не поддерживаются, поэтому пример не приводится

score: {
    [0..59] -> print('неудовлетворительно')

    [60..89] -> print('хорошо')

    [90..100] -> print('отлично')

    -> print('оценка некорректна')
}

; синтаксис диапазонов имеет 16 комбинаций, правило: '[' означает включить левую границу, '(' — не включать;
;                     ']' означает включить правую границу, ')' — не включать.
;
; 【Ограниченный диапазон】(4 вида) — обе границы имеют конкретные значения
;   [a..b]  → x >= a && x <= b   обе границы включены
;   [a..b)  → x >= a && x <  b   левая включена, правая нет
;   (a..b]  → x >  a && x <= b   левая не включена, правая да
;   (a..b)  → x >  a && x <  b   обе границы не включены
;
; 【Диапазон без верхней границы】(4 вида) — правая граница опущена (End=nil), проверяется только нижняя
;   [a..)   → x >= a              левая включена, без верхней границы
;   [a..]   → x >= a              левая включена, без верхней границы
;   (a..)   → x >  a              левая не включена, без верхней границы
;   (a..]   → x >  a              левая не включена, без верхней границы
;
; 【Диапазон без нижней границы】(4 вида) — левая граница опущена (Start=nil), проверяется только верхняя
;   [..b]   → x <= b              без нижней границы, правая включена
;   [..b)   → x <  b              без нижней границы, правая не включена
;   (..b]   → x <= b              без нижней границы, правая включена
;   (..b)   → x <  b              без нижней границы, правая не включена
;
; 【Полностью неограниченный диапазон】(4 вида) — обе границы опущены, на основе минимума/максимума типа
;   [..]    → true                минимум типа ≤ x ≤ максимум типа (обе границы включены)
;   [..)    → true                минимум типа ≤ x < максимум типа
;   (..]    → true                минимум типа < x ≤ максимум типа
;   (..)    → true                минимум типа < x < максимум типа
;
; В match полностью неограниченный диапазон основан на диапазоне значений типа сопоставляемой переменной (всегда истина, аналог catch-all).
; В range-for — на диапазоне типа переменной цикла (например, [..] для i64 от i64.MIN до i64.MAX).
;
; Пример: полная классификация с помощью неограниченных диапазонов
v = 85
result = v: {
    [..0) -> 'negative'

    [0..60) -> 'fail'

    [60..80) -> 'pass'

    [80..90) -> 'good'

    [90..100] -> 'excellent'

    (100..) -> 'extraordinary'
}
print(result)

num: {
    1 || 3 || 5 || 7 -> print('нечётное малое число')

    2 || 4 || 6 -> print('чётное малое число')

    -> print('большее число')
}

; есть возвращаемое значение — последняя инструкция/значение
result = x: {
    1 -> 1

    2 -> 2 + 1

    -> a + b
}

; многострочное тело arm должно использовать фигурные скобки -> { ... }
x: {
    nil -> {
        log('nil')
        do-cleanup()
        return
    }

    err -> {
        log(it.msg())
        do-cleanup()
        return
    }

    ok -> print(it)
}
```

> **Правило многострочного тела arm**: когда тело arm содержит несколько инструкций, его нужно обернуть в фигурные скобки `-> { ... }`. Однострочное тело можно писать сразу после `->`. Это потому, что без фигурных скобок привязка `it` в option match не сможет быть корректно вставлена, что приведёт к ошибке компиляции.

> **Семантика match внутри for-in**: `i <- (a..b]: { 1 -> ... 2 -> ... }` выполняет тело match один раз для каждой переменной цикла `i` (`1 ->` эквивалентно `i == 1 ->` и т. д.). Это синтаксический сахар для выполнения match на каждой итерации.

#### Три формы подлежащего match

Подлежащее match может быть **значением**, **выражением** или **блоком**:

| Форма | Запись | Способ вычисления |
| --- | --- | --- |
| Значение | `x: { ... }` | непосредственно сопоставляется `x` |
| Выражение | `x + 1: { ... }` | сначала вычисляется значение выражения, затем сопоставление |
| Блок | `{ ... }: { ... }` | выполняется тело инструкций, сопоставляется результат `?=` внутри него |

Первые две — **выражения**: их можно использовать и как инструкцию, и для получения значения в контексте значения (`v = x: { ok -> it, -> 0 }`).
Третья — **только инструкция**: не выражение, не может быть присвоена, не имеет END-значения блока; `-> _` служит для отбрасывания результата.
`no fmt` возвращает `}: {` как есть; правило пустых строк между ветвями такое же, как у обычного match.

##### Выражение-подлежащее (`expr: { ... }`)

У `expr: { ... }` приоритет `: {` **выше**, чем у `=`: в правой части присваивания это вся RHS, а не
«сначала выполнить `r = <expr>`, а потом идёт отдельный match». Поэтому арифметику option можно распаковать за один приём:

```no
#{overflow=wrap}
rem = seconds % 3600: {
    ok -> it

    -> 0
}

#{overflow=wrap}
sec = rem % 60: {
    ok -> it

    -> 0
}
```

Это эквивалентно прежней трёхчастной форме, которую нужно было разбивать: `rem-opt = seconds % 3600` / `rem = 0` /
`rem = rem-opt: { ok -> it  -> 0 }`. Первое присваивание может иметь явный тип
(`rem i64 = seconds % 3600: { ... }`), а повторное пишется просто `rem = ...: { ... }`;
оба — одиночный value-position match, тип результата определяется выражением в конце ветви.

Семантика и ограничения:

- Когда подлежащее — арифметика D6 option (`+ - * / %`), результат — `?T`. match нормализует его в
  синтетическую временную переменную `__match_subj_L_C ?T`: подлежащее **вычисляется ровно один раз**, `ok -> it` связывает payload,
  условие идёт через сравнение тега option, `-> 0` подстраховывает `nil` / `err`. Синтетическое имя не появляется в диагностике или
  в выводе `no fmt`.
- Результат match — **простой T**, и он регистрируется в семантической побочной таблице; поэтому дальше можно продолжать писать
  `sec = rem % 60: { ... }`, последовательные value-position match не теряют payload.
- Value-position match присоединяется только в **контексте значения** (справа от присваивания／`?=`／составного присваивания), и `: { ... }`
  должен быть действительно блоком match. Условные циклы уровня инструкции вроде `cond: { body }` и литералы struct
  идут по прежнему пути разбора и не затрагиваются.
- **Присваивание с целевым полем также является контекстом значения** (с 2026-11-09): `d.month = mp - 9: { ... }`,
  `b.n ?= b.n + 1: { ... }` — их `: {` привязывается к **правой части**, а не ко всему присваиванию. Раньше эти две
  ветви при разборе правой части не передавали `CTX_EXPR` (для идентификатора-цели через `let` передавался, а для `obj.f =` / `a[i] =`
  нет), поэтому `: {` подхватывается уровнем инструкции, надевается поверх всего присваивания и разбирается как
  `match(подлежащее = (d.month = mp - 9))`: присваивание выполняется как раньше и неявно распаковывает `?T`, записывая в поле,
  а обе ветви `ok -> it` / `-> 0` становятся мёртвым кодом. Теперь значение ветви действительно попадает обратно в поле.
- Индексная цель (`a[i] = …: { ... }`) имеет ту же форму, но D9 изначально запрещает прямую запись по индексу, поэтому такая запись
  всё равно отклоняется checker как `idxwrite`; нужно переписать в place-match (`a[i]: { ok -> it = v }`)
  или `?=`.
- `no fmt` возвращает `expr: { ... }` как есть, не разбивая его на две инструкции — присваивание и отдельный match.
- **Граница видимости типов**: чтобы нормализовать option-арифметику подлежащего в `?T`, объявленные типы обоих операндов должны
  быть статически видимы парсеру. Если операнд происходит из глубокой цепочки методов (тип получателя не выводится даже при воспроизведении AST),
  добавьте к его объявлению явный тип, например `e i64 = flr.to-i64()`; иначе нормализация консервативно
  пропускается, `ok -> it` не получает привязки, MIR заполняет нулями, и наблюдаемое значение всегда 0. У `src/std/number.no`
  функция `f64.to-str-general` именно такая: без этой аннотации `fmt.fmt-f64(2.5, '')` деградирует с
  `'2.5'` до `'3'`. Регрессия закреплена в
  `src/parser/value_match_expr_subject_test.go::TestValueMatchExprSubjectASTAnnotatedOperand`
  (без аннотации тест красный).

`src/std` 2026-11-09 перевёл **122 места в 22 модулях** option-распаковку на эту односоставную форму:
помимо исходной трёхчастной (`x-opt = expr` / `x = 0` / `x = x-opt: { ... }`), охвачены и двухчастная
(без нулевой инициализации), первое присваивание с явным типом (`x i64 = expr: { ... }`), а также случаи, когда промежуточная переменная
объявляется парами несколько раз внутри одной функции. После свёртки подлежащим может быть вызов метода, индекс или option-арифметика;
`ok -> it` / `ok(v) -> v` / ветви-константы / `-> _` — все проверены на эквивалентность, `no fmt` идемпотентен на этих сайтах.
Вывод типов компилятора также учитывает случай «в семантической побочной таблице найдено `?T`, а объявление на самом деле `i64`» —
такой глобальный тёзка-остаток; `ok -> it` из-за этого не теряет привязку.

Сохранённые случаи (9 мест): ① внутренний match записывает обратно в саму переменную `-opt` (она — подлежащее последующего value-position match);
② двухуровневые цепочки option match; ③ value-position match с Dispatch по значению (например, errno → сообщение, а не
распаковка option); ④ между объявлением и match есть другие инструкции или промежуточная переменная — результат, накапливаемый через ветви
(свёртка изменила бы момент вычисления).

##### Блочное подлежащее (`}: {`)

Блочное подлежащее оборачивает группу инструкций, позволяя **функциям без результат-параметра `?T`** обрабатывать всплывающее `?=` на месте:

```no
; d i64: делитель, при делителе 0 операция 6/d даёт err
f = (d i64) {
    {
        v ?= 6 / d; при ошибке больше не требуется результат-параметр ?T у функции
        print(v.to-str()); при ошибке не выполнится
    }: {
        err -> print(it.msg())

        nil -> print('nil')

        -> _; отбросить результат
    }
    print('дальше выполняется как обычно'); после завершения arms поток продолжается
}
```

Семантика:

- `?=` внутри тела перехватывается **ближайшим** блочным match (при вложенности приоритет у внутреннего; даже если функция содержит
  результат-параметр `?T`, приоритет всё равно у блочного match). Перехват рекурсивен: `?=` в голом блоке, в теле if, в теле цикла,
  в ветви match — всё считается; определение функции — граница, литерал функции — нет.
- Сопоставляется трёхсостояние `?T`, сохраняется **проверка исчерпываемости** обычного option match: если нет ветви-ловушки,
  то даже если `ok ->` недостижима во время выполнения, нужно дописать все три ветви `nil` / `err` / `ok`.
- Тело Completed успешно (ноль `?=` или все успешны) ⇒ сопоставляется `nil`; какой-то `?=` дал сбой ⇒ сопоставляется
  его `nil` или `err` (у ветви `err` значение `it` — полный `err.err`, см.〈Тип `it`〉).
- **Один сбой останавливает всё тело**: последующие инструкции и последующие итерации цикла не выполняются, arms запускаются один раз.
  Это «стоп-блок», а не `return` функции; пользовательские `return` / `break` / `continue`
  не затрагиваются.
- Развёртывание полностью состоит из существующих узлов ядра AST (синтетическая локальная `?T` + цепочка `if`-guard + обычный match),
  новых узлов HIR / MIR нет. Синтетические имена переменных не появляются в диагностике или в выводе `no fmt`.

> Разделение обязанностей с `=` на месте: `=` **сохраняет ошибку в целевую переменную** и поток продолжается; `}: {` 
> **сводит ошибку к одной ветви match** и останавливает остаток тела. Если нужно «после ошибки продолжить» — используйте `=` +
> последующий match; если нужно «при ошибке перейти в ветвь очистки» — используйте `}: {`.

##### Выбор между блочным match и value-position match

Одно и то же дело — вернуть результат option-арифметики в обычную переменную — имеет две формы записи. **Когда тело блока состоит только из этой
инструкции, они эквивалентны; но если в теле есть другие инструкции или правая часть может дать сбой в другом месте, семантика расходится.**

```no
; A: блочный match + `?=` (блочный «try»)
{
    #{overflow=wrap}
    np ?= np + 1
}: {
    err -> _

    -> _
}

; B: value-position match напрямую связывает цель (уровень инструкции)
#{overflow=wrap}
np = np + 1: {
    ok -> it

    -> _
}
```

Под `#{overflow=wrap}` результат `np + 1` **всегда `ok`** (обёрнутое значение); обе формы порождают только одну голую
`add i64` без ветви проверки переполнения, а ветвь ошибки для «самой операции сложения» — мёртвый код — именно поэтому на большинстве сайтов они
кажутся «полностью эквивалентными». Настоящая разница — в **области действия** и **пути ошибки**:

| Измерение | A: блочный match + `?=` | B: value-position match |
| --- | --- | --- |
| Синтаксическая позиция | **Инструкция**: без END-значения, нельзя присвоить | **Выражение**: можно в правую часть присваивания, в поле, в правую часть `?=` |
| Запись в цель при ошибке | **Нулевое значение** (`i64` → `0`, `str` → `''`) | Определяется ветвью-ловушкой: `-> _` **не пишет** (сохраняет старое значение), `-> 0` пишет 0, `-> sum` пишет обратно старое значение |
| Остаток инструкций тела | **Все пропускаются** (включая последующие итерации цикла) | Выполняются как обычно |
| Один `err`--arm покрывает | **Все** `?=` внутри блока | Только эту одну инструкцию |
| Цель с объявленным типом | ❌ `q i64 ?= …` — ошибка разбора (`yh8904fm`) | ✅ `q i64 = …: { … }` |
| Правая часть — константное свёртывание | ❌ `s8gh6opt` (`4 / 2` свёртывается в plain, уже не option) | ✅ подлежащее всё равно нормализуется в `?T` |
| Предпосылка применения | Функция имеет результат-параметр `?T` или сама находится внутри блочного match (иначе `l86f91me`) | Нет |
| Ветвь при успехе | Тоже заходит в ветвь один раз (тело доходит до `nil`), в ветви следует только отбрасывать или чисто обрабатывать | Работает только ветвь `ok` |

Порядок выбора:

1. **Одна инструкция, ошибка — как 0, после неё нечего выполнять** → формы эквивалентны, предпочтительна B: один уровень отступа меньше, одна запись нуля меньше,
   `no fmt` идемпотентно возвращает обе формы.
2. **Цепочка fallible-инструкций должна делить одну обработку ошибок** (чтение файла → разбор → запись) → A: `?=` по одной на строку,
   общая ветвь `err ->`, первый сбой останавливается в ветви очистки.
3. **При ошибке нужно сохранить старое значение／подставить конкретное резервное／позволить последующим инструкциям идти дальше** → B (`-> sum`, `-> 0`, `-> it`).
4. **Это значение ещё участвует в вычислении** (правая часть присваивания, цель-поле, правая часть `?=`) → B: A — инструкция, у неё нет значения.
5. **Обработка по элементам, одиночный сбой не должен губить всю партию** → B; **вся партия падает вместе — остановить** → A (останавливаются даже итерации цикла).

Две частые ловушки:

- 🔴 **Позиция аннотации**: `#{overflow=wrap}` должен быть написан **внутри блока**, вплотную над строкой `?=`. Написанный снаружи блочного
  match (над `{`) **не подействует** — проверено: переполнение всё равно даёт `err`, `np` обнуляется через `?=`.
- 🔴 **Не копируйте A для аккумулятора**: `sum ?= 1 / (i - 1)` на итерации сбоя **стёрт накопленный `sum` в
  `0`** (нулевая запись у `?=`). Чтобы сохранить накопленное, используйте B с `-> sum`.

#### Рекомендации по стилю Match

```no
#{fmt-skip}
; ❌ избегайте дублирования тела ветви
w = tls-c.send(req)
w: {
    nil -> {
        tls-c.close()
        return
    }

    err -> {
        tls-c.close()
        return
    }

    ok -> n = it
}
```
```

```no
; ✅ общую логику выносите в -> catch-all
w = tls-c.send(req)
w: {
    ok -> n = it

    -> {
        tls-c.close()
        return
    }
}

; ✅ и наоборот: простые ветви именуйте, сложную логику выносите в ->
val: {
    nil -> return

    err -> log(it.msg())

    -> {
        n = it
        total = total + n
        process(n)
    }
}
```

```no
; одно инструкция — без фигурных скобок
val: {
    ok -> print(it)

    -> print('empty or error')
}

; несколько инструкций — фигурные скобки обязательны
val: {
    ok -> {
        n = it
        total = total + n
    }

    -> {
        log('failed')
        return
    }
}
```

```no
; неявное связывание it
val: {
    ok -> process(it); it = распакованное значение

    err -> log(it.msg()); it = структурированная ошибка err.err (не str)

    -> log('empty'); catch-all, здесь nil
}
```

```no
#{fmt-skip}
; область видимости it: вложенный match восстанавливает по уровням
; (заполнитель имени функции — keep: `use` — ключевое слово импорта, нельзя использовать как имя функции;
;   а голая ветвь `->` при несовпадении nil/err одновременно читать it — ошибка компиляции, поэтому на каждом уровне пишем ok ->)
outer: {
    ok -> {
        keep(it)            ; внешний it
        inner ?T = f(it)
        inner: {
            ok -> keep(it)  ; внутренний it = распакованное значение inner
        }
        keep(it)            ; ✅ после завершения внутренней ветви it снова внешнее значение
    }
}
```

> **Внимание**: восстановление происходит только в **вложенном** match. После завершения самого внешнего match `it` сохраняет значение последней ветви,
> не используйте `it` вне match. Если нужно использовать его значение на разных уровнях, сохраните в именованную переменную (`doc = it`) или используйте деструктурирующее связывание
> `ok(v) -> ...`, чтобы привязать полезную нагрузку к собственному имени.

> **Лучшая практика (для распаковки option предпочитайте `it`)**: когда сопоставляемое значение — **option `?t`**, предпочитайте `ok -> ...(it)...`
> вместо `ok(v) -> ...(v)...`: не вводится лишнее имя привязки, и тем самым естественно избегается ловушка «одинаковые имена переменных в разных ветвях приводят к коллизии в codegen».
> Только в двух случаях нужно сохранять **именованную привязку** `ok(v) ->`: (1) сопоставляемое значение — **вариант пользовательского перечисления** (например,
> `res { ok(v str) }`, `shape { rect(w, h) }`) — там `it` — это **всё перечисление**, а не полезная нагрузка, и получить нагрузку можно только по имени;
> (2) нужно продолжить использовать значение **после вложенного match** — внутренний match перепривязывает `it`, поэтому используйте именованную привязку или сначала скопируйте в именованную локальную.

### Запись по индексу требует явной распаковки

Чтение по индексу возвращает option (при выходе за границы — `err`, `code.index-out`), поэтому **прямое присваивание по индексу превратило бы выход за границы в непроверенную запись вне границ**; это запрещено, нужно выбрать одно из двух:

```no
#{fmt-skip}
; ❌ не разрешено: a[1] = 2
```
```

```no
; ✅ place-match: обработать ветвь выхода за границы самостоятельно (it = позиция элемента, доступна чтению и записи)
a[1]: {
    ok -> it = 2

    -> _
}

; ✅ всплытие ошибки: когда функция содержит параметр результата option (выход за границы → всплытие)
a[1] ?= 2
```

- Когда компилятор может доказать, что индекс в границах (массив фиксированной длины + константный индекс, переменная цикла с доказуемо допустимым значением и т. п.), **проверка внутренне удаляется, присваивание прямое, без накладных расходов во время выполнения**; но синтаксически всё равно нужно писать форму распаковки — для пользователя никаких исключений нет.
- map (`[str]i64` и др.) **полностью не подчиняется этому правилу**: `m['b'] = c` пишется напрямую, не нужно ни place-match, ни `?=` — индекс map — это **ключ**, а не позиция, запись — put/insert (при отсутствии ключа вставка, при наличии перезапись), всегда определена, «записи вне границ» не существует; база — поле структуры (`self.keys[i] = v`) пока тоже не подчиняется правилу.
- **Чтение** у map по-прежнему идёт через option (полностью то же правило, что у `a[i]` для массивов/vec/slice): внутри функции `x = m[k]` даёт `?V`, если ключа нет — `nil`. `m[k]` и `m.get(k)` синонимичны, `m[k] = v` и `m.put(k, v)` синонимичны, обе формы можно свободно смешивать.
- `m[k] ?= v` — **ошибка компиляции** (не просто избыточность): ветвь `ok` у `?=` — это «прочитать элемент и записать обратно в **позицию**», а `?V`, прочитанное из map, — это всего лишь копия из `get`; запись в неё не вернётся в map. Пишите прямо `m[k] = v`. Place-match вида `m[k]: { ok -> it = v }` по-прежнему допустим (эквивалентен put).

### Переменная цикла — это тоже «позиция» элемента

`x <- a` (где `a` — `arr` / `vec` / `slice` / массив фиксированной длины) связывает `x` с **непосредственно позицией элемента**, а не с копией, загружаемой на каждой итерации:

- **Чтение** `x` заново читает `a[__i]` — в одной итерации запись перед чтением видна, `x = x + 1` — это read-modify-write;
- **Запись** `x = v` попадает обратно в `a[__i]`;
- `it` в ветви match — это **псевдоним** той же позиции (действует только внутри этой ветви), поэтому `x: { ok -> it = v }` и `a[i]: { ok -> it = v }` полностью эквивалентны.

```no
; следующие два фрагмента дают одинаковый результат: каждый элемент a становится равным 5
a []i64 = [0, 0, 0]
i <- [0..3): {
    a[i]: {
        ok -> it = 5

        -> _
    }
}

b []i64 = [0, 0, 0]
x <- b: {
    x: {
        ok -> it = 5

        -> _
    }
}
```

- Когда сам элемент — option (`[]?T`), `it` — это **полезная нагрузка**, при записи она автоматически упаковывается обратно в `ok`.
- После завершения ветви псевдоним перестаёт действовать: запись `it = v` после match не вернётся в контейнер.

**Случаи, когда это не позиция** (запись остаётся локальной):

- `c <- s` (`str`): элемент — декодированная **кодовая точка**, в строке нет соответствующей ячейки хранения.
- `k <- m` (map): индекс — это **ключ**, а не позиция, запись не попадает обратно в таблицу.

### `it` можно использовать только в ветви, где «доказуемо единственный случай»

Ветвь catch-all `->` перехватывает все случаи, которые не были явно обработаны предыдущими ветвями. Только когда остаётся **ровно один** случай,  
`it` имеет единственный однозначный смысл:

```no
; ✅ -> — это ok (nil / err уже обработаны)
v: {
    nil -> log('empty')

    err -> log(it.msg())

    -> process(it)
}

; ✅ -> — это err (ok / nil уже обработаны)
v: {
    ok -> process(it)

    nil -> log('empty')

    -> log(it.msg())
}
```

```no
#{fmt-skip}
; ❌ -> может быть и nil, и err — ошибка компиляции
v: {
    ok -> process(it)

    -> log(it)
}
```
```

Добавьте `nil ->` / `err ->` либо переходите на `ok ->` — и ошибки не будет. Перечисления и голый match (`{ cond -> ... }`)  
не подпадают под это ограничение: `it` означает само сопоставляемое значение, в котором не может быть nil / err.

> `it` в ветви `err ->` **всегда является значением ошибки (`err.err`)**, независимо от типа элемента option —  
> `option { ok(v t), nil, err(e err.err) }`. Так что даже если сопоставляется скалярный option вроде `?i64` / `?bool`,  
> `it` в ветви `err ->` всё равно структурированная ошибка: сообщение читается как `msg = it.msg()`,  
> код ошибки сравнивается через `it.is(code.io)`, а место возникновения — в `it.file` / `it.line` / `it.col`  
> (компилятор автоматически добавляет их в точке создания `err(...)`).

```no
; ✅ комбинированный option-шаблон: nil || err -> body
; когда option равен nil или err, используется общая ветвь
val: {
    nil || err -> {
        cleanup()
        return
    }

    ok -> process(it)
}

; ✅ можно сочетать и с -> catch-all
val: {
    nil || err -> log('failed')

    ok -> process(it)
}
```

### Короткозамыкающий конвейер (`->`)

`->` — это **левоассоциативный короткозамыкающий оператор конвейера**, его семантика фиксирована и **не зависит от того, есть ли внешнее присваивание и находимся ли мы внутри ветви match**. Голые инструкции, однострочные body ветвей match и правая часть присваивания используют один и тот же lowering.

Узлы внутри конвейера делятся на три типа:

| Узел                                | Влияние на состояние конвейера                             |
| --------------------------------- | ----------------------------------------- |
| Вызов с побочным эффектом (без возврата, например `print('A')`)         | выполняется, **не меняет состояние**; пока состояние было Ok, идём к следующему узлу        |
| Вызов, возвращающий `?T` (может завершиться неудачей, например `might-fail()`) | выполняется, **перезаписывает состояние**; как только оно стало nil/err, **все последующие узлы пропускаются** |
| Конечное обычное выражение                          | вычисляется, только если состояние всё ещё Ok                        |

**Только узлы, возвращающие `?T`, способны переключить конвейер в состояние неудачи**; такие побочные эффекты, как `print`, никогда не могут. Поэтому «вся цепочка состоит из `print`» выглядит как отсутствие короткого замыкания — на самом деле просто нет ни одного узла, который мог бы создать неудачу.

```no
; нет узла, который может завершиться неудачей → выполняются все
ok -> print('A') -> print('B')

; might-fail() возвращает ?T → при неудаче print('B') не выполняется
ok -> print('A') -> might-fail(x) -> print('B')

; правая часть присваивания: та же семантика
r = print('E') -> might-fail(x) -> 42
```

**Уточнение границ:**

1. У `->` единственная семантика: голые инструкции и выражения присваивания используют один и тот же конвейерный lowering и не переключают режим в зависимости от наличия внешнего присваивания.
2. **`->` в однострочном body ветви match — это продолжение конвейера, а не новая ветвь**; ветви отделяются друг от друга **переводом строки**:

```no
; ✅ одна ветвь, body — конвейер → печатаются обе строки
ok -> print('A') -> print('B')

; ✅ две ветви (разделены переводом строки) → при совпадении ok 'miss' не печатается
v: {
    ok -> print('hit')

    -> print('miss')
}
```

> ⚠️ Ветви разделяются переводами строк, поэтому записанные в одной строке `pat -> A -> B` — это **конвейер внутри одной ветви**, а не «if A else B». Если нужен if/else, записывайте ветви на отдельных строках либо используйте короткозамыкающую группу в `{}`.

1. **Конвейер может выдавать значение**: при записи справа от присваивания результатом конвейера является **конечный узел значения** (вычисляется, только если state всё ещё Ok).

```no
n = 7
x = 1 > 2 -> 42; условие не выполнено → x сохраняет исходное значение 7
y = 2 > 1 -> 42; y == 42
s str = 'old'
s = 1 > 2 -> 'new'; короткое замыкание → s остаётся 'old'
r = print('E') -> might-fail(bad) -> 99; сбой в середине → r сохраняет исходное значение
```

При неудаче (условие не выполнено или конвейер короткозамкнулся на узле `?T`) **присваивание не выполняется**: переменная сохраняет исходное значение, а при первом объявлении принимает нулевое значение своего типа. Это согласуется с линейной формой — `{ 1 > 2 -> x = 42 }` тоже не изменяет `x`.

Тип значения выводится из конечного выражения ветви (может быть `str`, `i64` или `?T`) и использует ту же систему вывода, что и существующая форма получения значения match `x = subject: { arms }`.

### If / Else

Группа if-else (короткозамыкающая) **должна** быть обёрнута в `{}`. Побеждает первое совпавшее условие, последующие условия не проверяются.

```no
; несколько ветвей (рекомендуемый новый стиль) — короткозамыкающая цепочка if-else
{
    a == 1 -> {
        a = 1
        b = 2
    }

    a == 2 || a == 3 -> do-something()

    -> {
        c = 0
    }
}

; одиночный if (сохранён) — изолированный if, без короткого замыкания
x == 1 -> do-something()

; тернарное выражение condition ? true-value : false-value
c = flag ? 1 : 2
max = sum > 10 ? sum : 10
```

**Важные правила:**

1. **Короткозамыкающая группа** — когда несколько `cond -> body` обёрнуты в `{}`, образуется цепочка if-elif-else, и выполняется только первая совпавшая ветвь.
2. **Изолированный if** — запись `cond -> body` непосредственно в теле функции/цикла (без обёртки в `{}`) является изолированным if и не короткозамыкается с соседними if-then.
   **Появление else обязательно требует группы** — запись завершающей ветви `->` на новой строке вне `{}` является **ошибкой компиляции**: изолированный `cond ->` с `->` даёт `k3r7mbqd`, а если выше есть соседние ветви `cond ->` — `m7vq3xrt` (сообщение указывает число отброшенных ветвей). Парсер сводит `->` на новой строке только к **ближайшему** голому if, остальные ветви молча игнорируются — буквальный смысл прочтения полностью расходится с реально скомпилированным результатом, поэтому это правило, а не предупреждение. Обёртывайте все ветви в `{ ... }`; **изолированный `cond -> body` без else по-прежнему можно писать без обёртки**.
3. **Запрещено смешивать** — прямые дочерние узлы короткозамыкающей группы `{}` должны быть исключительно ветвями `cond -> body`; обычные инструкции недопустимы.

```no
#{fmt-skip}
; ❌ нет короткого замыкания — это изолированные if, проверяются все условия
git-dispatch = (cmd str) {
    cmd == 'a' -> {
        fa()
    }
    cmd == 'b' -> {
        fb()
    }
}
```
```

```no
; ✅ короткое замыкание — обёрнуто в {}, побеждает первое совпадение
git-dispatch = (cmd str) {
    {
        cmd == 'a' -> {
            fa()
        }

        cmd == 'b' -> {
            fb()
        }

        true -> {
        }
    }
}
```

```no
#{fmt-skip}
; ❌ if/else записан вне короткозамыкающей группы — ошибка компиляции
; `-> break` на новой строке относится только к `c == 43`; при совпадении `c == 45` выполнение всё равно прерывается break
;   c == 45 -> {
;       exp-sign = -1
;       i = i + 1
;   }
;   c == 43 -> i = i + 1
;   -> break
```
```

```no
; ✅ тот же код, записанный как группа if — ветви взаимно исключают друг друга, `->` становится настоящей завершающей ветвью
{
    c == 45 -> {
        exp-sign = -1
        i = i + 1
    }

    c == 43 -> i = i + 1

    -> break
}
```

```no
#{fmt-skip}
; ❌ match-block с примесью обычных инструкций → ошибка компиляции
{
    cmd == 'a' -> {
        fa()
    }
    print(cmd)
    cmd == 'b' -> {
        fb()
    }
}
```
```

```no
; ✅ обычные инструкции помещены внутрь тела ветви
{
    cmd == 'a' -> {
        print(cmd)
        fa()
    }

    cmd == 'b' -> {
        fb()
    }

    true -> {
    }
}
```

### Асинхронное программирование: группа корутин `awy { ... }` + `co`

В Nolang существует только один синтаксис поверхностной конкуренции: группа корутин `awy { ... }`, внутри которой задачи порождаются через `co`.
Ключевое слово `run` удалено (`run` теперь обычный идентификатор); префикс ожидания `awy <handle>` и голые блоки в позиции инструкции
для групп корутин упразднены. **Запись `co` вне группы — ошибка компиляции** (`E_CO_OUTSIDE_GROUP`).

У `co` две формы, и обе запускают только **процедуру** и не возвращают значение:

```no
; процедура: только запись в канал, возвращаемое значение не объявлено
produce = (ch chan[i64], v i64) {
    ch <- v
    ch.close()
}

ch chan[i64] = with-cap(2)
awy {
    co produce(ch, 1)          ; ① spawn процедуры: co f(args)
    co {                       ; ② spawn замыкания: co { ... }
        ch <- 2
        ch.close()
    }
}
sum = 0
i <- ch: {
    sum = sum + i
}
print(sum.to-str())            ; => 3
```

#### ① spawn процедуры: `co f(args)`

`f` **не должен объявлять возвращаемое значение**. Результат spawn некуда поместить (`co` не является значением), поэтому функция с возвращаемым значением,
вызванная через `co`, даёт ошибку `c0retval`:

```no
worker = (n i64) (r i64) { r = n }   ; объявлено возвращаемое значение
awy { co worker(1) }                  ; ✗ c0retval
```

Неявно возвращаемое методом `self` **не считается** возвращаемым значением — это выходной параметр-получатель, присутствующий в каждом методе; его назначение —
позволить выстраивать вызовы в цепочку, поэтому запись вроде `co obj.flush()` полностью нормальна:

```no
queue {
    n i64
}
queue.flush = () {          ; неявный (self queue), других возвращаемых значений нет
    self.n = 0
}
awy { co q.flush() }        ; ✓
```

Когда нужен результат, используйте канал: процедура отправляет значение в канал, затем `close()`, а вызывающая сторона опустошает его вне группы. Это не рекомендация по стилю,
а правило — результат spawn-вызова читается только после join группы, причём чтение происходит не в точке join,
а в другом месте; именно для такого сценария и существует `chan`.

#### ② spawn замыкания: `co { ... }`

`co { ... }` передаёт фрагмент процедуры корутине для выполнения на месте. **Свободные переменные в блоке захватываются по значению**
(снимок на момент spawn, та же семантика, что и глубокое копирование аргументов при обычном spawn):

```no
seed = 33
ch chan[i64] = with-cap(1)
awy {
    co {
        ch <- seed
        ch.close()
    }
}
r = 0
<- ch: { ok -> r = it }
print(r.to-str())          ; => 33
```

#### `co` не является значением: только отдельная инструкция

`co` возвращает void, поэтому он должен занимать целую инструкцию. Справа от присваивания, в позиции аргумента или возвращаемого значения —
всегда `E_CO_NOT_STATEMENT` (`c0nostmt`):

```no
r = co produce(ch, 1)      ; ✗ c0nostmt
print(co produce(ch, 1))   ; ✗ c0nostmt
```

Кроме того, после `co` может следовать только «вызов» или «блок»; другие формы дают `E_CO_NOT_CALL` (`c0notcal`).

#### Бесцветный async: автоматическая мономорфизация

`co` — бесцветный (colorless) синтаксис: вы пишете неокрашенное имя функции `produce`, а компилятор автоматически мономорфизирует
вариант `produce-async` и выполняет его как окрашенную безстековую корутину на нижнем уровне. Не пишите суффикс `-async` вручную в прикладном коде.

Правила:

- **Мономорфизация**: `co produce(ch, 1)` автоматически создаёт `produce-async` (копирует тело `produce` и переименовывает его). Если `produce` одновременно вызывается и синхронно, оба варианта сосуществуют.
- **Транзитивность**: если внутри процедуры тоже есть `awy { co child(n) }`, сама процедура также мономорфизируется в `-async`, и асинхронная окраска передаётся вверх по цепочке вызовов.
- **Барьер**: инструкции внутри группы, не являющиеся `co` (обычное присваивание, `print`, циклы, `if`, **чтение канала**…), сначала ожидают все задачи в полёте. Поэтому временна́я зависимость внутри группы записывается как «сначала прочитать канал, затем использовать прочитанное значение для spawn» — чтение канала само является барьером и читается лучше, чем неявная зависимость по переменным.
- **Тело функции не является группой корутин**: группу вводит только `awy { ... }`. `co` в теле функции, ветви `if` или теле цикла всегда отклоняется.
- **Отброшенный результат тоже ожидается**: `awy { co side(5) }` всё равно выполняет spawn + await, не оставляя неожидаемых задач.

#### Модель планирования: настоящее приостановление

Клон `-async` — это не «пробежать всё за один раз и затем сообщить», а **восстанавливаемая машина состояний**: локальные переменные переносятся в
кучевую рамку, прикреплённую к `%task.frame`; каждая точка приостановления становится терминатором текущего блока (записать номер состояния в рамку и вернуться),
а вход в функцию превращается в цепочку сравнений состояния (`__state == k` ⇒ переход к k-й точке восстановления).

Поэтому в трёх местах происходит **приостановление**, а не блокировка:

| Точка приостановления | Условие восстановления |
|---|---|
| `async-yield()` | повторно поставить себя в конец очереди и ждать, пока не окажешься в её голове |
| `awy` незавершённой дочерней задачи | пробуждение при завершении задачи (регистрация в цепочке `%task.waiters`, одно пробуждение будит всю цепочку) |
| пустое чтение канала (`v <- ch:` / `<- ch:`) | `send` / `close` снимает всю цепочку ожидания и по очереди переставляет её в очередь |

Планирование однопоточное, кооперативное, с FIFO-очередью готовности, поэтому **порядок полностью предсказуем**, sleep не нужен:
две задачи, каждая из которых уступает по разу, неизменно дают `a1 b1 a2 b2` (`tests/coro-yield.no` закрепляет коды событий).
Разбуженный ожидатель **не означает получивший значение** — один `send` добавляет лишь один элемент, но может разбудить нескольких ожидателей,
поэтому точка восстановления канала — это сам park-блок: он заново проверяет читаемость и решает, забрать значение или продолжить ожидание.

> Взаимоблокировка обнаруживается: очередь готовности пуста, а целевая задача всё ещё не завершена ⇒ среда выполнения выводит
> `nolang: deadlock: …` в stderr и выполняет abort. Это гораздо честнее, чем «вернуть нулевое значение, которое никто не отправлял».

> **Нижний lowering** (не синтаксис пользователя): каждая `co` превращается в `OpRun`, а в конце группы для каждой задачи вставляется `OpAwait`;
> `KRun` / `KAwait` / `OpRun` / `OpAwait` существуют только в HIR/MIR. Преобразование корутин выполняется в MIR,
> в `PlanCoroutines`, после `Analyze` (`src/mir/coro.go`).

Отмена: `cancelled()` позволяет корутине выполнить кооперативную самопроверку; `cancel(h)` — низкоуровневая операция с дескриптором,
новый синтаксис не предоставляет дескриптор task, и прикладной код его не использует.

### Множественное присваивание

Функция может возвращать несколько значений; при вызове их принимают через множественное присваивание:

```no
; функция объявляет несколько выходных параметров
swap = (a i64, b i64) (x i64, y i64) {
    x = b
    y = a
}

; множественное присваивание
a, b = swap(5, 3)

; использовать _ для игнорирования ненужных возвращаемых значений (заполнитель)
_, b = swap(5, 3); взять только второе значение, первое игнорировать
a, _ = swap(5, 3); взять только первое значение, второе игнорировать
_, _ = swap(5, 3); игнорировать все возвращаемые значения (вызов только ради побочного эффекта)

; также поддерживается как тело ветви match
val: {
    ok -> {
        a, b = parse-pair(it)
    }

    -> return
}
```

## Перегрузка операторов

Когда статический тип левого операнда определяет соответствующий метод `_op`, компилятор на этапе lowering автоматически переписывает инфиксную операцию `a op b` в вызов метода `a._op(b)`. Множество перегружаемых операторов замкнуто и состоит из 5 симметричных бинарных арифметических операторов:

| Оператор | Метод перегрузки |
|--------|----------|
| `+` | `_add` |
| `-` | `_sub` |
| `*` | `_mul` |
| `/` | `_div` |
| `%` | `_mod` |

```no
big {
    v i64
}

; возвращаемый тип записан как ?big, компилятор считает его чистым payload big
big._add = (b big) (c ?big) {
    c = big {
        v: .v + b.v
    }
}

f = (a big, b big) (out big) {
    r big = a + b; компилятор переписывает в a._add(b)
    out = r
}
```

**Соглашение о типах**: выходной параметр метода перегрузки оператора **записывается как `?T`, а действующий тип — чистый payload `T`** — компилятор не выполняет упаковку/распаковку option: в теле метода `c` сразу присваивается значение `T`, и вызывающая сторона тоже получает `T`. Ошибки вроде деления на ноль, как и у встроенных числовых типов, напрямую вызывают trap во время выполнения, option не создаётся.

**Ключевые моменты семантики**:

- переписывание происходит только когда статический тип левого операнда определяет соответствующий метод `_op`; встроенные числовые типы (i64, f64 и др.) по-прежнему используют встроенную арифметику.
- явный вызов метода `a._add(b)` полностью эквивалентен `a + b`.
- левоассоциативные цепочки переписываются по уровням: `a + b + c` → `(a._add(b))._add(c)`; тип промежуточного результата остаётся `T` и может дальше участвовать в операциях и вызовах методов.
- по этому механизму стандартная библиотека `bigint` поддерживает `+ - * / %` (см. раздел bigint в «Стандартная библиотека > Другие модули»).

## Массивы и срезы

Контейнеры хранят копии данных; исходная переменная и контейнер независимы, что исключает висячие ссылки.

**Массив фиксированной длины arr:**

```no
; использование массива фиксированной длины
a [3] = [1, 2, 3]; массив i64 фиксированной длины 3
a [3]u16 = [1, 2, 3]; массив фиксированной длины с указанным типом

a[nil]
u16 = [1, 2, 3]; длина выводится автоматически (тип указан)
a[nil] = [1, 2, 3]; длина выводится автоматически (i64)
```

**Массив переменной длины vec:**

```no
v = [1, 2, 3]; массив переменной длины i64
bs = [0x11, 0x22, 0x33]
v []u8 = [1, 2, 3]; массив переменной длины с указанным типом

; предварительное выделение (чтобы избежать повторного расширения)
v = with-cap(100); len=0, cap=100 (индексация после push)
v = with-len(100); len=100, cap=100 (можно индексировать сразу)
v = with-cap-len(200, 100); len=100, cap=200 (зарезервировано место для расширения)
```

**Срез slice (представление, не отдельный тип):**

Срез — это **представление (view)** исходных данных: он не копирует данные и не создаёт новый отдельный тип.  
Внутри срез хранит лишь указатель на исходный буфер, длину и ёмкость, поэтому:

- изменение элементов через срез влияет на исходные данные и наоборот
- срез не владеет данными; после освобождения исходной переменной срез становится недействительным
- тип среза определяется исходным типом, методы естественным образом применимы без механизма «наследования»

```no
; поддерживаются arr/vec/str
; поддерживаемые диапазоны совпадают с обозначениями for <-
nums [5]u8 = [0, 1, 2, 3, 4]

nums[..]; [0 1 2 3 4]    полностью неограничен, равен всему срезу
nums[1..]; [1 2 3 4]      без верхней границы, от индекса 1 до конца
nums[..4]; [0 1 2 3 4]    без нижней границы, от начала до индекса 4
nums[2..3]; [2 3]         с обеими границами, обе включены
nums[1..3]; [1 2 3]       с обеими границами, обе включены
nums[1..3); [1 2]         слева закрыт, справа открыт
nums(1..3); [2]           интервал открыт с обеих сторон

; строка (результат среза имеет тип str-представления, память общая; индекс — позиция кодовой точки, как и в s[i])
s = 'abc'
s[1..]; 'bc'
s[1..s.len()); 'bc'
b str = s[0..1]; результат среза уже str, можно сразу присвоить переменной str
```

> Синтаксис срезов поддерживает те же 16 сочетаний интервалов, что и match/range-for. В контексте среза неограниченные интервалы основаны на длине среза: `[..]` означает весь срез, `[a..]` — от индекса a до конца, `[..b]` — от начала до индекса b.

**Тип и методы среза:**

Срез не порождает новый отдельный тип, он лишь представление исходного типа (со смещённым начальным указателем и длиной).  
Поэтому методы исходного типа доступны напрямую:

| Исходный тип        | Тип представления среза | Доступные методы                                                              |
| -------------- | ------------ | -------------------------------------------------------------------------------- |
| `arr` (`[n]t`) | `[]t<range>` | все методы `[]t` (`len`, `push`, `pop`, `contains`, `reverse`, `clone`, `fill`, `to-arr` и др.) |
| `vec` (`[]t`)  | `[]<range>`  | те же                                                                              |
| `str`          | `str<range>` | все методы `str` (`to-upper`, `to-lower`, `index`, `contains`, `slice`, `copy`, `fill` и др.)   |

```no
; срез arr → представление vec, общая базовая память arr
a [5]u8 = [0, 1, 2, 3, 4]
s = a[1..4]; s — представление []u8, указывает на память a
n = s.len(); slice.len()

; срез vec → представление vec, общая базовая память vec
v = [10, 20, 30, 40, 50]
s = v[2..]; s — представление []i64
s.reverse(s.len()); slice.reverse

; срез str → представление str, общая базовая память str
s = 'Hello World'
sub = s[6..]; sub — представление 'World'
upper = sub.to-upper(); str.to-upper

; изменение элементов через срез влияет на исходные данные
data = [10, 20, 30, 40, 50]
view = data[1..4]; view = [20, 30, 40]
view[0] = 99; изменение элемента view
; data[1] теперь тоже 99, потому что view использует общую память data
```

### Индексация

```no
; индексация строки → возвращает ?char (Unicode-кодовая точка, не байт)
c char = s[i]; явный plain-тип возвращает результат к char (см. «Безопасная индексация»)

; получение элемента arr, vec
arr[i]; → ?elem
vec[i]; → ?elem

; получение значения map
map[str]
```

> **Результат индексного чтения всегда `?T`**: `arr[i]` / `vec[i]` / массив фиксированной длины / `slice` → `?elem`,  
> `str` / `txt`: индекс `s[i]` → `?char` (D6, единое правило с целочисленной арифметикой).  
> Поэтому **выводимый тип `str[i]` — `?char`**; чтобы получить обычный `char`, есть два пути:  
> указать явный обычный тип при связывании (`c char = s[i]` — на этапе lower выполняется короткозамыкающий синтез, и читается обычное значение),  
> либо распаковать через match / `?=`.  
> Срез `str[a..b]` по-прежнему возвращает `str` (представление с семантикой кодовых точек, общая базовая память).  
> `char` может **неявно преобразовываться в `str`** (кодируется как строка из одного символа), поэтому все записи ниже допустимы без ручного вызова `char.to-str()`:

```no
s = 'héllo'
c char = s[1]; 'é' (char, его кодовая точка — 233)
a str = s[1]; 'é' (неявное преобразование char → str)
b str = s[0..1]; 'hé' (результат среза уже является str)
msg = 'first: ' - s[0]; char при конкатенации (-) неявно превращается в str
ok = s[0] == 'h'; char при сравнении со str неявно превращается в str
```

### Безопасная индексация (Safe Indexing)

Для индекса `v[i]` у `arr` / `vec` / `slice` (`[]T`) / массива фиксированной длины / `str` / `txt` **результат всегда `?T`**: при выходе за границы возвращается `err` (`err('index out of range', code.index-out)` с указанием исходной позиции индекса), в пределах границ — `ok(значение)`; abort никогда не происходит (runtime error: index out of bounds). Это то же правило, что и неотмеченное переполнение при целочисленных `+ - * / %` (см. «Переполнение целочисленных операций»).

Использовать `?T` можно тремя способами (**аннотация `#{index-out=DEF}` упразднена и удалена в D11**, оставшаяся аннотация — ошибка компиляции;
и никакого сокращения «явный обычный тип возвращает обычное значение» не существует — `v i64 = a[i]` также требует явного потребления):

**1. Чтение — распаковка через match**

Value- match напрямую извлекает значение, а statement- match присваивает его внутри ветви `ok`. `-> _` — ветвь «отбросить»,
в контексте значения она выдаёт **нулевое значение типа элемента** (i64→0, str→'', byte→0, контейнер→пустой контейнер).

```no
; value- match
x = state[5]: {
    ok -> it

    -> _
}

; statement- match
state[5]: {
    ok -> x = it

    -> _
}
```

**2. Запись — place-match**

В ветви `ok` `it` — это **позиция элемента** (читаемая и записываемая), а не копия значения.

```no
state[5]: {
    ok -> it = x

    -> _
}
```

> **Исключение для map:** запись `m['k'] = 1` **не требует распаковки** — индекс map — это ключ, а запись — put/insert,
> отсутствующий ключ вставляется, существующий перезаписывается; значение всегда определено, и «запись вне границ» здесь нечего защищать. Но **чтение map `m['k']` по-прежнему возвращает `?V` и требует распаковки**.
> `m[k] ?= v` — **ошибка компиляции** (`?V`, прочитанное через `get`, — лишь копия, и запись в неё не вернётся в map); пишите сразу `m[k] = v`.

**3. Сокращение `?=` — всплытие ошибки**

`x ?= state[5]` (чтение) и `state[5] ?= x` (запись) — сокращения для двух видов match выше: при неудаче весь option
всплывает вверх. Это допустимо в **одном из двух случаев**:

- функция, в которой это записано, имеет выходной параметр `?T` — при неудаче в него записывается значение и выполняется досрочный `return`;
- инструкция находится в теле **statement-level блочного match** `{ ... }: { ... }` — её перехватывает ближайший блочный match,
  тело останавливается, ветви выполняются один раз, и функция **не нуждается** в выходном параметре `?T`.

Если не выполняется ни одно из условий — ошибка компиляции. Поэтому стандартный приём, когда «возвращаемое значение не option, но хочется использовать сокращение», — обернуть тело функции в блочный match:

```no
handle = (x i64) {
    {
        y ?= x + 1
        print(1)
    }: {
        err -> _

        -> _
    }
}
```

**Вложенное чтение**: внутренний match заново связывает `it`, поэтому внутри используется именованное связывание `ok(it1) -> it1`. Точная форма, которую дал пользователь
(value- match, записанный прямо справа от `it = ...` в place-match), начиная с 2026-11-06, **корректно записывает обратно в контейнер**: компилятор при
lowering поднимает этот value- match в синтетический временный и заново связывает `it`; регрессионный тест — в `tests/match.no`,
раздел `place-write-value-match`. **Предпочтительная прямая запись**: результат value- match сразу связывается с тем именем, которое в итоге используется,
а не помещается сначала в одноразовый временный, а затем копируется ещё раз.

```no
#{fmt-skip}
; ✅ прямое связывание целевой переменной
at = argt[i]: {
    ok -> it

    -> _
}
s.farg.push(at)

; ❌ не вводить одноразовый временный для однократного использования
arg-at = argt[i]: { ok -> it  -> _ }
at = arg-at
s.farg.push(at)
```

«Поднять value- match в именованную переменную вне ветви, а внутри ветви написать `it = arg-at`» **не эквивалентно прямому написанию** — это не свободно
заменяемый вариант оформления: моменты вычисления различаются (после подъёма вне ветви внешние `nil` / `err` / catch-all тоже читают один раз);
`it` действует только внутри ветви и указывает на позицию элемента, поэтому копирование обратно должно оставаться внутри ветви; именованная переменная — новое связывание со своим move/
правом собственности и уничтожением при выходе из области видимости; а при вложенности внутренний уровень обязан использовать именованное связывание `ok(it1) -> it1`, нельзя копировать внешнее
`ok -> it`. Подъём оправдан только когда одно и то же значение действительно используется в нескольких местах, и с осмысленным именем, описывающим значение.

#### Уборка оставшихся одноразовых временных через `?=` и блочный match

Выше речь шла о «при однократном использовании связывай напрямую». Следующий шаг: безопасная индексация возвращает `?T`, **поэтому когда выходной параметр функции
сам является `?T`, не нужно писать даже value- match — `?=` одной строкой сразу всплывает**:

```no
#{fmt-skip}
; ✅ функция с выходным параметром ?T: ни временных, ни match
at ?= argt[i]
s.farg.push(at)
```

**Когда результат функции не option** (чаще всего: вспомогательная функция без возвращаемого значения или просто запись обратно в контейнер), используйте такой
«похожий на try» приём, чтобы обернуть эту инструкцию:

```no
#{fmt-skip}
handle = (x i64) {
    {
        y ?= x + 1
        print(y)
    }: {
        err -> _

        -> _
    }
    print('continues afterwards')
}
```

⚠️ **Это не новый синтаксис `try` — в языке нет ключевого слова `try`.** Это просто **statement-level блочный
match** (`{ ... }: { ... }`) с подлежащим `?T`, имеющим три состояния; `?=` всплывает при неудаче к **ближайшему** блочному match
(подробнее см. «Всплытие ошибки через `?=`» и «Три формы подлежащего match»). При неудаче оставшиеся инструкции тела блока — включая
последующие итерации цикла — всё пропускается, ветви выполняются один раз, после чего **выполнение продолжается с кода после блока**, а не
производит `return` из функции. `err -> _` отбрасывает ошибку, `-> _` в качестве запасной ветви отбрасывает успешный результат; чтобы обработать ошибку, можно написать
err -> print(it.msg())`.

⚠️ **Семантическую разницу нужно проговорить явно** (проверено на практике, не по интуиции): при неудаче `?=` **целевая переменная всё равно записывается нулевым значением** — `i64` получает
`0`, `str` получает `''`, `out[1]` получает `0`. Но запасная ветвь `-> _` value- match **не записывает в цель**: если цель
**впервые объявлена**, она изначально инициализирована нулём — кажется одинаково; если цель **уже имеет значение**, пути расходятся (`?=` обнуляет, `-> _`
сохраняет исходное, чтобы обнулить — пишите `-> 0`). Другое различие — управление потоком: `?=` **пропускает инструкции после себя в теле блока**
(в функции с `?T` это досрочный `return`, в блочном match — прямой переход к ветвям).

Поэтому: **если в теле блока только эта одна инструкция и старое значение до неудачи не несёт смысла**, запасная ветвь `-> 0` полностью
эквивалентна (именно в такой форме этот репозиторий переписывался пакетно — временные переменные чаще всего были новыми объявлениями); но если после `?=` в теле есть
другие инструкции (счётчики цикла, последующие присваивания) или старое значение цели содержательно, пути расходятся — такие места нельзя заменять механически. Полную
таблицу соображений см. в «Блочный match против value- match: что выбрать».

Ещё одна частая ловушка: **при успехе ветви тоже выполняются один раз**, catch-all получает успешное значение (`-> print('x')` напечатает его).
Поэтому в ветвях следует только отбрасывать или чисто обрабатывать значение; формы `err -> _` / `-> _` не имеют побочных эффектов.

Отсюда порядок уборки одноразовых временных:

1. Значение используется только в одном месте → связать напрямую с итоговым именем (см. выше).
2. Функция имеет выходной параметр `?T` → `TARGET ?= EXPR`, временная не нужна.
3. Иначе → поместить инструкцию в блочный match и написать `TARGET ?= EXPR`; запись через place-match
   (`SUBJ: { ok -> it = temp  -> _ }`) также сразу сокращается до `SUBJ ?= EXPR`.
4. Именованную переменную оставляйте только когда одно значение действительно переиспользуется в нескольких местах, и с осмысленным именем.

Два ограничения: `?=` — ошибка компиляции, если ни выходного параметра `?T`, ни нахождения в теле блочного match нет
(`l86f91me`); **LHS с объявлением типа нельзя сочетать с `?=`** (`ai i64 ?= a[i]` — ошибка разбора
`yh8904fm`, `expected assignment operator`). Когда нужно явное расширение вроде `byte → i64`, используйте прямой value- match с объявлением типа:

```no
#{fmt-skip}
ai i64 = a[i]: {
    ok -> it

    -> _
}
```

> **Область применения:** `arr` / `vec` / `slice` / массив фиксированной длины / `str` / `txt` — всё допустимо; безопасной форме подвергается только индекс с **непосредственной переменной в основе**
> (`v[i]`); `receiver.field[i]` идёт по прежнему пути проверки границ (bounds-check).
> Чтение по индексу в операндах сравнения сравнивает payload (`a[i] == 5`), а не всю структуру `{tag, payload}`.

> ⛔ **Твёрдая ошибка:** использование `?T` как обычного значения (например, `crc = crc ^ s[i]`, `f(s[i])`, `v i64 = a[i]`) блокирует
> `no build`; компилятор подсказывает использовать match или `?=` (при отсутствии выходного параметра `?T` — обернуть в блочный match).
> Существующий корпус уже единократно мигрирован с помощью `no fmt --fix=index-out`; этот инструмент упразднён вместе с D11.

> **Ключевая гарантия:** выход за границы никогда не приводит к тихому сбою — ошибка либо обрабатывается match, либо всплывает через `?=`.

> **Чтение по индексу в операндах сравнения** подчиняется тому же правилу безопасной индексации: `a[i] == 5` сравнивает payload (то же правило, что и для `?T == 5`),
> а не всю структуру `{tag, payload}`. При выходе за границы читается `err` (`code.index-out`), и сравнение с любым значением даёт **ложь**
> (`a[i] == 0` и `a[i] == 5` — оба ложны), при этом чтение за границами **не происходит**.
> То же для `s[0] == 'a'`: при сравнении кодовой точки со строкой из одного символа используется неявное преобразование `char → str`.

> **Вложенные индексы** `a[i][j]`: **оба уровня являются безопасной индексацией**. Внешний `a[i]` сначала проверяет границы и наличие элемента,
> и только если он существует, к нему применяется `[j]`; если любой уровень выходит за границы, всё выражение — `err`.
> Поэтому `a[oob][0] == 'c'` даёт ложь, а не abort.

> **Сравнение контейнеров** `[]T == []T` (а также `[N]T == [N]T`) — это **структурное сравнение**: сначала сравнивается длина, затем элементы по очереди.
> Если элементы сами являются контейнерами (`[][]i64`), сравнение рекурсивно по уровням; если элемент — `str`, сравнивается **содержимое**, а не указатель data.
> Операторы упорядочивания (`<` / `<=` / `>` / `>=`) для контейнеров не определены; поддерживаются только `==` / `!=`.

> **`nil` можно сравнивать только с option**: `?T == nil` / `?T != nil` допустимы; сравнение не-option
> `T == nil` (`str`, `[]i64`, `[N]T`, `txt`, `i64`, структуры…) — **ошибка компиляции** (`q4nilcmp`).
> Причина не в педантизме: `str == nil` всегда false (структура `%str-long` сравнивается с нулём),
> `[]i64 == nil` попадает в путь целочисленного сравнения и порождает некорректный LLVM (`icmp eq i64 %vec, i64`),
> в обоих случаях молча выдаётся неверный ответ. Чтобы выразить «значения может не быть», объявите тип как `?T` и сравнивайте с `nil`.

## Структуры

Определения структур и литералы должны использовать многострочную форму: каждое поле занимает отдельную строку, поля не разделяются запятыми, и запятой нет в конце.

```no
user {
    name str
    age i64
}

u = user {
    name: 'Alice'
    age: 30
}
u.name = 'Bob'
u.age = 25
print(u.name)
```

### Реализация интерфейсов структурой

Структура может реализовывать один или несколько интерфейсов; имена интерфейсов пишутся после имени структуры через запятую.

```no
; реализация одного интерфейса
user json {
    name str
    age i64
}

; реализация нескольких интерфейсов
file enter, leave {
    path str
    fd i64
}
```

#### Межмодульная реализация интерфейсов

При реализации интерфейса, определённого **в другом модуле**, имя интерфейса должно содержать префикс модуля (`ShortName.`). См. [префиксы при межмодульных вызовах](module.md).

```no
#{fmt-skip}
; ❌ ошибка: db, rows, stmt — интерфейсы, определённые в модуле sql, префикс нельзя опускать
db-mysql db {
    fd i64
}
```
```

```no
; ✅ верно: использовать sql.db, sql.rows, sql.stmt
db-mysql sql.db {
    fd i64
}

rows-mysql sql.rows {
    fd i64
}

stmt-mysql sql.stmt {
    fd i64
}
```

> Встроенные интерфейсы (`enter`, `leave`) и интерфейсы, определённые в том же файле, не требуют префикса модуля.

## Методы

Методы определяются на типе; для обращения к получателю (receiver) используется `.`.

### Синтаксис

```no
#{fmt-skip}
type.method-name = (params) (results) {
    ; . — это получатель
}
```

### Правила

1. Имя метода использует формат `type.method`, где type должен быть уже определённым типом
2. Получатель не нужно объявлять явно как параметр; внутри тела метода он доступен через `.`
3. Вызов осуществляется по синтаксису `receiver.method(args)`
4. Возвращаемые значения помещаются во вторую пару скобок, как и у обычных функций
5. **Сахар разворачивается**: `type.method = (inputs) (rest-outputs...) {}` эквивалентно обычной функции  
   `method = (inputs) (self type, rest-outputs...) {}`. При вызове `instance.method(args)`  
   instance связывается с первым параметром списка выходов `self`; внутри тела метода `.` обозначает выходную область `self`;  
   запись функции в `self` напрямую изменяет исходный экземпляр. Остальные выходы списка, кроме `self`,  
   поддерживают необязательное декомпозиционное связывание или простое отбрасывание.

### Пример

```no
; метод str
str.to-upper = () (out str) {
    n = .len-bytes()
    b []byte = with-cap-len(n, n)
    i <- [0..n): {
        c ?byte = .byte(i)
        v = c: {
            ok -> it

            nil -> 0

            err -> 0
        }
        {
            v >= 97 && v <= 122 -> b[i] = v - 32

            -> b[i] = v
        }
    }
    out = b.to-bytes-str()
}

; метод char
char.is-digit = () (result bool) {
    result = false
    . >= 48 && . <= 57 -> result = true
}

; метод struct
user {
    name str
    age i64
}

user.greet = () {
    print('Hello, ' - .name)
}

; вызов
s = 'hello'

### Объединение интерфейсов

Интерфейс может «объединять» методы других интерфейсов: имена родительских интерфейсов пишутся внутри тела интерфейса, **по одному на строку** (с префиксом модуля или без), без запятых и без скобок:

```no
json {
    to-json()
}
noml {
    to-noml()
}

serialize {
    json
    noml
}

; транзитивное объединение: roundtrip получает все методы serialize, json и noml
roundtrip {
    serialize
    roundtrip-json()
}
```

Правила:

- **Рекурсивное объединение**: объединение транзитивно — `roundtrip` объединяет `serialize`, а `serialize`, в свою очередь, объединяет `json` / `noml`, значит `roundtrip` обладает методами всех трёх интерфейсов.
- **По одному на строку, без запятых**: `serialize { json, noml }` имеет тот же вид, что и перечисление в стиле C (`color { red, green }`), поэтому разбирается как перечисление, а не как объединение интерфейсов.
- **Одинаковые имена методов**: если сигнатуры совпадают (типы параметров и возвращаемого значения одинаковы, имя получателя может отличаться) ⇒ дубликат удаляется, остаётся один; если сигнатуры различаются ⇒ диагностика ошибки.
- **Сторона реализации**: типу достаточно записать объявление реализации (префиксный список `user serialize { name str }`); методы родительских интерфейсов также считаются реализованными, и проверка сигнатур проходит через родительские интерфейсы.
- **`no fmt`**: старая форма «префиксного списка» (`serialize json, noml { }`) всё ещё разбирается, но `no fmt` переписывает её во внутрителесную форму, а `no vet` выдаёт по этому поводу WARNING.

Диагностика (`no vet` и редактор используют общий источник диагностики, TraceID `ifmrg001`):

| Ситуация | Сообщение |
| --- | --- |
| Родительский интерфейс не объявлен | `interface 'serialize': unknown parent interface 'noml'` |
| Циклическое объединение | `interface 'a': merge cycle a -> b -> a` |
| Одинаковое имя, разные сигнатуры | `interface 'serialize': merged method 'to-str' has conflicting signatures ('json.to-str', 'noml.to-str')` |

> `serialize = json \| noml` — это синтаксис **объединённого типа** (union type), не имеющий отношения к объединению интерфейсов; объединение интерфейсов влияет лишь на то, «какие методы должен иметь тип».

### Тегированное перечисление (с нагрузкой)

Вариант может нести именованные поля нагрузки, записываемые в форме `вариант(поле тип)`; вариант без нагрузки записывается просто голым именем.  
Один вариант может нести **несколько** полей (многополевая нагрузка представляется на куче как синтетический struct):

```no
#{fmt-skip}
; тегированное перечисление: варианты могут нести нагрузку, tag присваивается по порядку объявления — 0, 1, 2...
result {
    ok(v t),
    nil,
    err(e str),
}

; со значением: поле нагрузки v, тип t
; пустое значение: без нагрузки
; ошибка: поле нагрузки e, тип str (пользовательское перечисление, не связано со встроенным option)

shape {
    circle(r f64),
    rect(w f64, h f64),
    dot,
}
; одно поле
; несколько полей
; без нагрузки
```
```

При сопоставлении имя варианта используется как образец ветви; вариант с нагрузкой позволяет деконструировать и связать нагрузку (несколько полей связываются по позициям):

```no
r result = ok(42)
r: {
    ok(v) -> print(v); связать нагрузку ok с v

    nil -> print('empty')

    err(e) -> print(e)
}

s shape = rect(3.0, 4.0)
s: {
    circle(r) -> print(r); связать одно поле

    rect(w, h) -> print(w * h); связать несколько полей по позициям

    dot -> print('dot')
}
```

Вариант можно создавать непосредственно в **позиции выражения** — в качестве аргумента функции или нагрузки другого варианта:

```no
x f64 = perimeter(rect(3.0, 4.0)); встроенное создание и передача аргументом
o outer = wrap(a(5)); нагрузка перечисления сама является другим перечислением
```

> **Пространство имён и разрешение голых имён**: внутри компилятор регистрирует варианты по «полному квалифицированному имени» (`модуль.перечисление.вариант`,  
> например `option.option.ok`, `some-mod.my-result.ok`); одноимённые варианты разных перечислений не конфликтуют.  
> пользователь пишет только голое имя (`ok`, `rect`), а компилятор автоматически дополняет его **на основе статического типа сопоставляемой/создаваемой переменной**  
> до полного имени. Поэтому даже если два перечисления содержат вариант `ok` с разным порядком tag, они корректно различаются.
>
> Допустима также старая форма с разделением типа пробелом — `ok t`, эквивалентная `ok(v t)` (имя поля опущено).  
> Имена вариантов тегированного перечисления заносятся в таблицу вариантов компилятора для сопоставления и проверки исчерпываемости.

### Встроенные тегированные перечисления (`#{buildin}`)

Аннотация `#{buildin}` перед тегированным перечислением означает, что это **встроенное перечисление**: варианты (имена, порядок, типы нагрузки) используются  
для сопоставления и проверки исчерпываемости, но базовое представление и создание обеспечиваются runtime/builtin; **пользовательские видимые  
struct/union не создаются**. `?t` option объявляется именно так:

```no
; src/std/global.no
#{buildin}
option {
    ok(v t),
    nil,
    err(e err.err),
}
```

Теги `option` в порядке: `0=ok`, `1=nil`, `2=err`, что совпадает с представлением встроенного option. Пользователю не нужно  
объявлять option самостоятельно; здесь `#{buildin}` делает источник вариантов встроенного option единым (см. «Nullable-тип (option)»).

### Аннотации перечислений и размещение в памяти

Перечисления поддерживают аннотации `#{...}` в тех же позициях, что и другие цели (см. «Позиции аннотаций»): **сверху** (отдельной строкой) или  
**сзади** (в конце той же строки); запись **перед целью на той же строке** — ошибка компиляции.

Аннотации можно размещать в **двух местах**:

1. **Над всем enum** — действует на определение enum целиком (например, `#{buildin}`, `#{inline=true}`);
2. **Над отдельным членом или в конце его строки** — действует на этот член (и «значения» C-подобных перечислений, и «варианты» тегированных).

```no
; ① весь enum: отдельной строкой над enum
#{inline=true}
box {
    full(v i64) #{doc='со значением'},
    empty #{doc='пусто'},
}

; ② отдельный вариант: отдельной строкой над вариантом

; ② отдельный вариант: в конце той же строки

; `#{inline=false}`: явно указать «не использовать inline-размещение»
#{inline=false}
plain {
    a,
    b,
}

color {
    red #{deprecated},
    green #{deprecated},
    blue,
}
; отдельные значения C-подобного перечисления также поддерживают обе формы записи
```

**Аннотации не изменяют структуру enum**: имена вариантов, порядок объявления (tag), поля и типы нагрузки не зависят от аннотаций,  
сопоставление и проверка исчерпываемости тоже полностью неизменны. Аннотации — лишь **метаданные**, присоединённые к определению.

#### Размещение в памяти (стековое)

Тегированное перечисление использует в памяти **стековое размещение** (inline stack form) — небольшой объект, хранящийся по значению, при этом нагрузка не разбросана по куче:

```llvm
%tenum_<name> = type { iN tag, [K x i64] payload }   ; общий случай
%tenum_<name> = type { iN tag }                      ; все варианты без нагрузки
```

- Ширина `tag` зависит от **числа вариантов** и является полной `u8/u16/u32/u64`:
  `<= 256` → `i8`, `<= 65536` → `i16`, `< 2^32` → `i32`, иначе `i64`. Дискриминант принимает значения по порядку объявления: `0, 1, 2...`.
- `payload` — это union, **общий для всех вариантов** (каждый вариант записывает свои поля в одну и ту же область); `K` — это **ширина самого широкого варианта**,
  выраженная в 8-байтовых словах, **не сумма всех вариантов**, минимум 1.
- Внутри варианта поля размещаются с **естественным выравниванием**, поэтому смещения полей не обязательно кратны 8 (для `(a char, b char, c char)` смещения равны 0 / 4 / 8).
  чтение и запись всегда адресуются по **байтовому смещению** (`bitcast` к `i8*`, затем `getelementptr`),
  поэтому «смещение записи» и «смещение чтения» определяются одной и той же таблицей размещения.

Размер составляет `8 + 8K` (`tag` заполняется до целого слова выравниванием массива на 8 байт); только перечисления без нагрузки имеют размер чистого тега:

| Ситуация | `K` | Размер |
| ---------------------------------------------- | ----------------- | ---------- |
| Все варианты без нагрузки | — (нет поля payload) | **1 байт** (`{ i8 }`; при вариантах > 256 — 2 / 4 / 8) |
| Самый широкий вариант — `i64` / `i32` / `f64` / указатель | 1 | 16 байт |
| Самый широкий вариант — `char` (4 байта) / `bool` (1 байт) | 1 | 16 байт |
| Самый широкий вариант — `(a char, b char, c char)` (12 байт) | 2 | 24 байта |
| Самый широкий вариант — `str` / `vec` / `[]T` (16-байтовый дескриптор) | 2 | 24 байта |
| Самый широкий вариант — структура `T` | `ceil(sizeof(T) / 8)` | `8 + 8K` |

Иными словами: **по умолчанию размер начинается с 16 байт**, и растёт только когда нагрузка какого-то варианта действительно шире —
«по умолчанию фиксированные 16 байт» и «размер зависит от варианта» — две стороны одного и того же. Малая нагрузка вроде `char` / `bool`
определяет лишь выравнивание и не расширяет union: ширина `payload` — это «самый широкий вариант», а не сумма всех.

> Единственный источник размещения — `src/mir/layout.go`: `tagWidth` определяет `iN`, `enumVariantLayout` определяет для каждого
> варианта смещения полей и его размер, а `enumUnionLayout` берёт максимум и получает `K`. `hir2mir.fillEnumLayout`
> при построении таблицы записывает эти числа в `TaggedEnumInfo`; emitter только читает, не вычисляет — две стороны не могут получить разные ответы.

#### Три формы записи `#{inline}`

`inline` — это **логическая** аннотация с тремя формами записи, и **её значение действительно учитывается**:

| Форма записи        | Значение                      |
| ----------------- | --------------------------- |
| `#{inline}`       | сокращение, равно `inline=true` (одиночный ключ означает true) |
| `#{inline=true}`  | явно true (также `#{inline=1}`)      |
| `#{inline=false}` | явно false (также `#{inline=0}`)      |

Нелогические значения — **ошибка компиляции** (`#{inline=foo}`, `#{inline='true'}`); они не молча считаются true:  
`ValidateFieldTags` (TraceID `fieldtag1`) сообщает об этом и для полей структур, и для определений enum.

Запись `#{inline=true}` над всем enum — это **явная метка** стекового размещения, означающая «это перечисление использует стековое размещение»;  
компилятор запоминает её в `TaggedEnumInfo.Inline`. **Текущее размещение по умолчанию уже стековое**, поэтому есть аннотация или нет,  
записано `true` или `false` — размещение одинаково. Метка нужна, чтобы сделать намерение явным и служить стабильным  
переключателем на случай изменения размещения по умолчанию в будущем.

> `#{inline}` над **всем enum** означает «это перечисление использует стековое размещение»; на **отдельном варианте** пока  
> размещение не изменяет и сохраняется лишь как метаданные этого варианта (в отличие от полей структур, см. следующий раздел).

#### `#{inline}` на полях структур

В отличие от enum, `#{inline}` **на полях структур** имеет **реальный эффект**: он напрямую определяет, хранится ли поле  
**по значению внутри** структуры-владельца (`%pt`) или в виде **указателя** (`ptr`).

```no
pt {
    x i64
    y i64
}

holder {
    inl pt #{inline=true}; по значению: структура растёт прямо внутри holder
    out pt #{inline=false}; указатель: поле хранит указатель на pt
    bare pt #{inline}; сокращение, равно inline=true
}
```

| Форма записи                                     | Размещение поля                 |
| ---------------------------------------------- | --------------------------- |
| `#{inline}` / `#{inline=true}` / `#{inline=1}` | **по значению** внутри владельца (`%pt`)      |
| `#{inline=false}` / `#{inline=0}`              | **указатель** (`ptr`)               |
| не указано                                       | зависит от `NOLANG_FIELD_PTR` (см. таблицу ниже) |
| `#{inline=foo}` / `#{inline='true'}`           | **ошибка компиляции** — не логическое значение     |

**Размещение по умолчанию без аннотации определяется `NOLANG_FIELD_PTR`.** `mir.FieldPtrLayout` равен  
`os.Getenv("NOLANG_FIELD_PTR") != ""`, **по умолчанию выключен**; включение запускает «Phase 1 переворота размещения»,  
меняя размещение полей структур по умолчанию с «по значению» на «указатель».

| Поле                            | Флаг выключен (по умолчанию) | Флаг включён (`NOLANG_FIELD_PTR=1`) |
| ------------------------------ | --------- | ------------------------- |
| без аннотации                    | `%pt` (по значению) | `ptr` (указатель)                 |
| `#{inline}` / `#{inline=true}` | `%pt`     | `%pt`                     |
| `#{inline=false}`              | `ptr`     | `ptr`                     |

Иными словами: **аннотации всегда действуют и не зависят от этой переменной окружения**, флаг меняет только значение по умолчанию «без аннотации». Поэтому при  
настройках по умолчанию `#{inline=false}` — это «явное требование указателя», а `#{inline=true}` лишь ещё раз записывает  
уже принятое размещение; после включения переворота их роли меняются на противоположные.

У проверяющего две правила (TraceID `fieldtag1`, `ValidateFieldTags`):

1. **Имеет смысл только для полей типа-структуры.** Скаляры / `str` / `vec` / массивы / срезы / map / option /  
   указательные поля изначально всегда хранятся по значению; `#{inline}` ничего не говорит — поэтому ошибка; запись  
   `#{inline=false}` тоже даёт ошибку, поскольку это утверждает размещение, противоположное поведению компилятора.
2. **Объединение по значению не должно образовывать цикл.** Встраиваемая структура хранится **внутри** владельца, поэтому  
   сосуществование `a { #{inline} b b }` и `b { #{inline} a a }` даёт бесконечный размер — нужно сообщить об ошибке (прямая  
   ссылка на себя — вырожденный случай). Только `=true` создаёт ребро по значению, поэтому взаимно рекурсивные структуры при **записи с обеих сторон  
   `#{inline=false}`** допустимы.
   > ⚠️ **«Не написать аннотацию» — не то же, что «не использовать inline».** В настройках по умолчанию отсутствие аннотации означает встраивание по значению, поэтому  
   > `a { x b }` вместе с `b { y a }` (без аннотаций) при **настройках по умолчанию недопустимо** — завершится  
   > ошибкой `opt: error: identified structure type 'b' is recursive` — и сейчас эта ошибка  
   > **не** выдаётся проверяющим, а взрывается только на этапе проверки LLVM. Чтобы записать рекурсивный тип при настройках по умолчанию, **необходимо**  
   > явно написать `#{inline=false}`. И только при `NOLANG_FIELD_PTR=1` «не написать» означает указатель.

#### Рекурсивные типы: зачем нужен `inline=false`

Структура, встраивающая саму себя по значению, имеет бесконечный размер, поэтому **само-ссылка** не может храниться по значению. При настройках по умолчанию  
(`NOLANG_FIELD_PTR` выключен) поля структур по умолчанию хранятся по значению, поэтому чтобы `node` мог ссылаться на себя,  
единственный способ — явно запросить указатель:

```no
node {
    v i64
    next node #{inline=false}; указатель: только так node имеет конечный размер
}

n node
n.v = 1
n.next.v = 2
print(n.next.v); 2
```

Если убрать `#{inline=false}` из примера выше (или записать `#{inline=true}`), LLVM напрямую отвергнет этот  
тип: `identified structure type 'node' is recursive`.

Поле-указатель **владеет** своим объектом (pointee), а время жизни обрабатывает компилятор:

- pointee выделяется **лениво при первой записи** (`@__nolang_get_<T>`, внутри `malloc` + обнуление),  
  а не один раз при создании владельца;
- при выходе владельца из области видимости `@__nolang_drop_<T>` **проверяет указатель на null и освобождает** его;
- копирование по значению (`b = a`, передача аргументом, запись в контейнер) **глубоко копирует** pointee, поэтому два владельца  
  не используют одну и ту же память и не освобождают её дважды.

Сквозной тест — в `tests/field-inline-annotation.no`.

### Ссылки на значения перечисления

**Правило: значения перечисления следует использовать только в квалифицированной форме `тип_перечисления.значение`, голые значения недопустимы.**  
Это предотвращает конфликты имён и не позволяет внешним пакетам напрямую использовать конкретные значения.

```no
#{fmt-skip}
; ❌ ошибка: использовать голое значение напрямую
kind = null
yes = e.is(io)
```
```

```no
; ✅ верно: использовать квалифицированную форму
kind = json-kind.null
yes = e.is(code.io)
```

> Тип перечисления может использоваться как тип поля структуры, тип параметра функции и тип возвращаемого значения.  
> Как внутри модуля, определяющего перечисление, так и вне его значения следует использовать в форме `тип_перечисления.значение`.

## enter/leave

Типы, реализующие интерфейсы `enter` / `leave`, автоматически вызываются при входе в область видимости и выходе из неё:

```no
file enter, leave {
    path str
}

file.enter = () {
    .open()
}

file.leave = () {
    .close()
}

read-file = () {

    ; автоматически f.enter()
    f = file {
        path: 'data.txt'
    }

    ; использовать f
    ; автоматически f.leave()
    read(f)
}
```

### Nullable-тип (option)

Знак `?` перед типом обозначает nullable-тип:

Переменная nullable-типа может законно содержать пустое значение/значение ошибки; компилятор выполняет соответствующую проверку на null.

`?t` — встроенное тегированное перечисление, его варианты определены в `src/std/global.no`:

```no
#{buildin}
option {
    ok(v t),
    nil,
    err(e err.err),
}
; tag 0: со значением
; tag 1: пустое значение
; tag 2: ошибка (структурированная ошибка std — err.err)
```

Нагрузка варианта `err` — **не `str`**, а структура `err` из `std/err` (`code` / `msg` / `file` / `line` / `col`).
`err('msg', code)` — это псевдоним-конструктор для `err.new('msg', code)`; код ошибки `code` — **обязательный** параметр
(значения параметров по умолчанию удалены из языка); если конкретного кода нет, явно передавайте `code.unknown`;
Поля позиции компилятор добавляет автоматически в точке создания. `err('msg')` с одним аргументом — не этот псевдоним,
а конструктор варианта `err` у option (см. ниже).

`#{buildin}` означает, что базовое представление и создание обеспечивает встроенный runtime (тип `%option`, конструкторы `ok(...)`/`nil`/`err(...)`)  
); объявление перечисления `option` используется только для сопоставления и проверки исчерпываемости. Подробнее см. «Тегированное перечисление» и «Встроенные тегированные перечисления».

#### Размещение в памяти

`?T` **определяется по нагрузке**: для каждого типа нагрузки существует свой LLVM-тип, имя выводится из типа нагрузки (инъективное отображение),
поэтому «одинаковый тип нагрузки ⇒ одинаковое размещение»: `?i32` / `?i64` / `?bool` используют один и тот же тип:

```llvm
%option_<key> = type { i8 tag, [K x i64] payload }   ; встроенно
%option_<key> = type { i8 tag, [1 x i64] payload }   ; упакованно (payload хранит указатель i8*)
```

- `tag` всегда **1 байт**: у `option` всего 3 варианта (`0=ok`, `1=nil`, `2=err`), что попадает
  в категорию «`<= 256` вариантов → `i8`». Правила ширины tag перечислений см. в «Размещение в памяти (стековое)».
- После тега идёт **выравнивающее заполнение** (1-байтовый тег → 7 байт заполнения), и только затем нагрузка.
- Размер нагрузки `K` определяется фактическим размером `T` и округляется вверх до кратного 8, **не фиксированный слот**:
  `?i64` — 16 байт (8 + 8), `?str` — 24 байта (8 + 16), `?txt` — 264 байта (8 + 256).
- Нагрузка, превышающая порог, **упаковывается в кучу**: `payload` хранит только 8-байтовый указатель, и весь option занимает 16 байт.

Порог `option-payload-inline-threshold` измеряется в байтах **всей структуры option** (по умолчанию **264** = 1-байтовый тег +
7 байт заполнения + 256 байт нагрузки, минимум **16**); условие встраивания нагрузки:
`8 + roundUp8(sizeof(T)) <= порог`. Поэтому по умолчанию «нагрузка до 256 байт встраивается», а `?txt`
(256-байтовый встроенный буфер) как раз попадает в границу.

| `T` в `?T` | Встраивается? | Размер `%option_<key>` |
| --- | --- | --- |
| `i64` / `i32` / `bool` / `char` / `f64` / указатель | да | 16 байт |
| `str` / `[]T` / `vec` (16-байтовый дескриптор) | да | 24 байта |
| `txt` (256-байтовый встроенный буфер) | да | 264 байта (ровно до значения по умолчанию) |
| структуры / массивы размером > 256 байт | нет | 16 байт (нагрузка в куче) |
| само-ссылочная нагрузка (`node { next ?node }`) | нет | 16 байт (само-ссылка разрывается только указателем) |

> **Нагрузка `err` всегда упакована**: вариант `err` хранит указатель на структуру `err` из `std/err` и не занимает вышеуказанный
> бюджет нагрузки. Поэтому `?str` в варианте `ok` — 24-байтовая встроенная строка, а в варианте `err` — та же 24-байтовая
> структура — только word `payload` хранит указатель на объект ошибки. Это правило позволяет «одному и тому же типу `?T`,
> двум вариантам и двум нагрузкам» обойтись без дополнительного места.

> **Встраивание и упаковка меняют только «где лежит», но не владение**: оба пути при **копировании** создают новую копию кучевой части нагрузки структуры
> (рекурсивно для полей-указателей, клонируются встроенные owned-буферы `str` / `[]T`), поэтому семантика значения `?T` не зависит
> от того, встроена ли нагрузка, — одна и та же программа при любом `option-payload-inline-threshold` должна выдавать полностью одинаковый результат.
> Если из-за порога меняется поведение — это дефект компилятора, а не особенность. (Чисто перемещающее присваивание не клонирует: option
> забирает кучу источника.)

> Единственный источник размещения — `src/mir/layout.go`: `optLayoutOfPayload` определяет `K` и факт упаковки,
> `optionPayloadOffset` (8) — фиксированное байтовое смещение нагрузки. `hir2mir` свёртывает константы `?T` уровня модуля,
> а codegen генерирует чтение и запись — все обращаются к одной и той же функции.

#### Межнагрузочное всплытие через `?=`

`?=` сначала копирует «option в **корне** цепочки правого выражения» в выходной параметр option, чтобы `nil` / `err` сразу всплыли,
а успешный путь затем перезаписывается ветвью `ok`:

```no
pick = (p pool) (out ?i64) {
    out ?= p.nodes[0].kind; корень — ?node, слот результата — ?i64
}
```

Поэтому типы нагрузки с обеих сторон **могут различаться**, и это настоящая ABI-граница (`?node` — 112 байт, `?i64` — 16 байт),
а не два написания одного и того же размещения. Через границу типов переносятся только две вещи:

- `tag` — нулевой байт каждого option;
- `err` — вариант `err` является свойством option, не зависит от нагрузки и всегда упакован, поэтому с обеих сторон нулевое слово области нагрузки
  содержит 8-байтовый указатель на boxing (сам бокс **копируется**, не разделяется, поскольку обе стороны выполняют drop).

Нагрузка `ok` **не переносится между типами**: область нагрузки цели сначала обнуляется, а успешное значение всегда заново записывается ветвью `ok`.
Реализовано в `@__nolang_opt_prop_<dst>__<src>` (`optPropagateState` в `src/mir/codegen.go`),
появляется только на таких генерируемых компилятором всплывающих присваиваниях, как `?=`.

```no
o ?i64
o = nil; установить пустым
o = 42; установить со значением
o = err('msg'); установить ошибкой

nullableValue ?[]str
nullableString ?str

; изменение nullable-типа
nullableString = 'test'

; установка ошибки
nullableString = err('some error')

; можно проверить через match
x: {
    err -> log(it.msg()); it — err.err, сообщение через .msg()

    nil -> log('nil')

    -> do-right-thing(it)
}

; принудительная распаковка
; отмена реализации
; !x.say()
```

### Рекомендации по стилю: использовать ?t option вместо (val, ok)

Когда функция может завершиться неудачей или вернуть пустое значение, **следует предпочитать тип `?t` option**, а не шаблон с двумя возвращаемыми значениями `(val t, ok bool)`.

`?t` — это тегированное перечисление с тремя состояниями: `ok` (есть значение), `nil` (пустое значение), `err` (ошибка). Обычное значение связывается неявно; `nil` используется, когда операция просто не нашла значение, а `err(...)` — когда операция столкнулась с реальной ошибкой.

```no
#{fmt-skip}
; ❌ не рекомендуется: шаблон с двумя возвращаемыми значениями
stack.pop = () (val i64, ok bool) {
    .n == 0 -> return
    val = .data[.n]
    ok = true
}
```
```

```no
; ✅ рекомендуется: тип option (nil — пусто, err — ошибка)
stack.pop = () (val ?i64) {
    .n == 0 -> {
        val = nil
        return
    }
    val = .data[.n]
}

; ✅ возврат ошибки
file.read = () (data ?str) {
    .fd < 0 -> {
        data = err('file not open')
        return
    }

    ; ... чтение данных
    data = buf
}
```

Распаковка option через match:

```no
val = s.pop()
val: {
    nil -> print('empty')

    err -> print(it.msg()); it = структурированная ошибка err.err

    -> print(it); it = извлечённое значение
}
```

## Переполнение целочисленных операций (аннотация `#{overflow}`)

Nolang не поддерживает panic — любая операция, которая может переполниться, должна обрабатываться через `option` или явную аннотацию; во время выполнения целочисленное переполнение никогда не выбрасывает исключение. Поведение при переполнении следующих **целочисленных арифметических операций** управляется аннотацией `#{overflow = ...}`:

- **Знаковые и беззнаковые** `+` `-` `*`: применяются, когда оба операнда целые (включая литералы `int`);
- **Знаковое** `/`: переполнение происходит только в случае `INT_MIN / -1` (беззнаковое деление `a/b ≤ a` никогда не переполняется и не подпадает под правило).

> Беззнаковые целые (`u8`/`u16`/`u32`/`u64`/`u128`) при `+ - *` **подчиняются в точности тем же правилам**, что и знаковые: без аннотации по умолчанию возвращается `option<int>`, переполнение → `err`. Это сознательный выбор дизайна: «если нельзя доказать на этапе компиляции, что переполнения не может быть, действуют те же правила».

### Особый случай: арифметика `byte` и `char`

`byte` и `char` — **исключение** в семантике переполнения: их арифметика **не создаёт option** и не регулируется аннотацией `#{overflow}`.

- **`byte` (u8)**: при переполнении `+ - *` **тихо переполняется по модулю 2 (в дополнительном коде)** (`250 + 10` → `4`, `0 - 1` → `255`). `byte` ориентирован на сценарии, где переполнение естественно допустимо: байтовые буферы, hex-кодирование; это та же семантика, что и `#{overflow = wrap}` для хэшей/счётчиков, только встроенная и не требующая аннотации.
- **`char` (Unicode-кодовая точка)**: `+ -` — это **арифметика кодовых точек**; если результат выходит за допустимый диапазон (`< 0` или `> 0x10FFFF`), он равен **`-1`** (признак недействительной кодовой точки) — ни `err`, ни переполнения по модулю не происходит.

**Обоснование дизайна**: `i8`–`i128` / `u8`–`u128` обычно используются для **реальных бизнес-значений** (суммы, счётчики, ёмкости), где тихое переполнение по модулю скрывало бы ошибки, поэтому по умолчанию `err` и требуется явный выбор; а типичное применение `byte` / `char` (потоки байтов, обход кодовых точек) семантически естественно допускает (и даже ожидает) переполнение по модулю, и option лишь добавил бы шума при распаковке. Если нужно обнаружить переполнение в операциях с `byte` / `char`, сначала расширьте тип (например, `b.to-i64()`), затем вычисляйте.

| Режим         | Аннотация                  | При переполнении               | Тип результата | Сценарий применения        |
| ----------- | ------------------------ | --------------------------- | ------ | ------------------ |
| **По умолчанию (без аннотации)** | —                        | переполнение → `err`, норма → `ok(value)` | `?int` | операции, где нужно обнаруживать переполнение          |
| **Переполнение по модулю**      | `#{overflow = wrap}`     | тихое переполнение по модулю 2 (дополнительный код)                 | `?int` | хэширование, криптография, счётчики и другие сценарии, где допустимо переполнение по модулю |
| **Обнуление**      | `#{overflow = clamp0}`   | при переполнении (вверх или вниз) берётся `0`              | `?int` | семантика, где разность не должна быть отрицательной (например, остаток)    |
| **Ограничение минимумом**   | `#{overflow = min}`      | переполнение ограничивается минимальным значением типа                  | `?int` | нижняя граница счётчика, защита индекса         |
| **Ограничение максимумом**   | `#{overflow = max}`      | переполнение ограничивается максимальным значением типа                  | `?int` | верхняя граница ёмкости, насыщающее суммирование          |
| **Насыщение**      | `#{overflow = saturate}` | переполнение вверх → максимум, вниз → минимум               | `?int` | насыщение сигнала/цвета и т.п.           |

> ⚠️ **Аннотация не распаковывает** (D1): `#{overflow = …}` **определяет только «как получить значение при неудаче»**,
> тип результата всегда `?T`. Чтобы привести результат к обычному типу, его можно только потребить через match или `?=`; две формы потребления
> (`?=` + блочный match / value- match), их различия и выбор см. в «Блочный match против value- match: что выбрать».
> Явная аннотация обычного типа (`w i64 = a - b  #{overflow=wrap}`) **не является** лазейкой —
> на практике всё равно выдаётся `15w45dqk` (cannot assign `?i8` value to `i8` variable).

Кроме того, все режимы поддерживают **форму с префиксом типа**, позволяющую точно задать границы насыщения для конкретного узкого типа, например `#{overflow = u8-max}`, `#{overflow = i8-min}`, `#{overflow = u16-saturate}`.

> **Гранулярность аннотации**: `#{overflow = ...}` — это **строчная аннотация** — действует только на **непосредственно следующую инструкцию**.
> Это **единственная допускаемая дизайном** форма (защита от злоупотреблений): исполняемая семантика (codegen) и твёрдая ошибка `ovfhndld` признают только её,
> и она меняет только «получение значения при переполнении», не тип; расширение до уровня блока или функции означало бы, что семантика целого блока операций определяется одной далёкой строкой
> аннотации. Подробнее см. [«Область действия аннотаций и комментариев»](annotation-scope.md) §4.1.
>
> ⛔ **Нельзя размещать над определением функции, в начале блока или в начале файла**. Единственная текущая лазейка: аннотация уровня функции заставляет
> lint `ovf-int-default` пропустить всю функцию (список выглядит «чистым»), а неотмеченные операции внутри тела функции по-прежнему
> вызывают `ovfhndld`; аннотация уровня блока заставляет lint унаследовать её и замолчать, но codegen её не признаёт вообще. Аннотируйте каждую инструкцию;
> именно такую поинструкционную форму и создаёт `no fmt --fix=overflow`.
>
> Полную модель (L0 модуль / L1 объявление / L2 блок / L3 одна строка, и какие ключи поддерживают какие уровни) см. в
> [«Область действия аннотаций и комментариев»](annotation-scope.md); §7 этой страницы перечисляет текущее состояние и лазейки, §8 — порядок ужесточения.

> **Быстрое исправление в LSP**: редактор (nolang-lsp) выдаёт для неотмеченных целочисленных операций **подсказку** (`nolang-overflow`, trace id `ovfhndld`) и предлагает пять quickfix — **Add `#{overflow = wrap}`** / **`clamp0`** / **`min`** / **`max`** / **`saturate`** — которые автоматически вставляют соответствующую аннотацию над инструкцией с этой операцией с тем же отступом, что и у строки, задавая поведение при переполнении (результат по-прежнему `?T`, его нужно потребить через match / `?=`). Эквивалент в командной строке — `no fmt --fix=overflow` (см. ниже).

### По умолчанию: возврат `option<int>`

Без аннотации результатом `a - b` является `option<int>`. Принимающая сторона должна быть `?T` (nullable-тип), и нужно разобрать три ветви `err` / `nil` / `ok` через match:

```nolang
main = () {
    x i64 = 100
    d ?i64 = x - 1; по умолчанию: возврат option<i64>
    d: {
        err -> print(-1); переполнение (например, x - 2^63 — отрицательное переполнение)

        nil -> print(0)

        -> print(1); ok(value): нормальный результат
    }
}
main()
```

> Поле `data` у `%option` имеет тип `i64`; результаты узких типов (`i8`/`i16`/`i32`) сначала расширяются со знаком (sext), затем сохраняются, а при распаковке снова усекаются до исходной ширины.

### wrap: тихое переполнение по модулю

```nolang
#{overflow=wrap}
sub-wrap = (a i64, b i64) (r i64) {
    r = a - b; при переполнении тихо переполняется по модулю 2 (дополнительный код); r — обычный i64 (явный тип)
}
```

На уровне инструкции:

```nolang
x i64 = -9223372036854775807

#{overflow=wrap}
w i64 = x - 2; отрицательное переполнение по модулю → 9223372036854775807
print(w)
```

### clamp0: обнуление при переполнении

```nolang
x i64 = -9223372036854775807

#{overflow=clamp0}
c i64 = x - 2; отрицательное переполнение → 0 (положительное переполнение тоже обнуляется)
print(c)
```

### min / max / saturate: насыщающее ограничение

Три режима «зажимают» результат переполнения в диапазоне, представимом типом, а не переполняют по модулю и не обнуляют:

```nolang
#{overflow=min}
floor = (a i64, b i64) (r i64) {
    r = a - b; отрицательное переполнение → минимальное i64; положительное → максимальное i64
}

#{overflow=max}
cap = (a i64, b i64) (r i64) {
    r = a * b; положительное переполнение → максимальное i64; отрицательное → минимальное i64
}

#{overflow=saturate}
sat = (a i64, b i64) (r i64) {
    r = a + b; вверх → max, вниз → min
}
```

Форма с префиксом типа позволяет точно управлять границами насыщения для узких типов (аннотация уровня функции применяется ко всем операциям соответствующего типа в теле):

```nolang
#{overflow=max}
inc = (x u8) (r u8) {
    r = x + 1; при x = 255 положительное переполнение → 255 (а не 0 по модулю)
}

#{overflow=min}
dec = (x i8) (r i8) {
    r = x - 1; при x = -128 отрицательное переполнение → -128 (а не 127 по модулю)
}
```

### Принудительная проверка компилятора

Неотмеченная целочисленная операция по умолчанию возвращает `option<int>`, поэтому «необработанная» будет принудительно перехвачена. Считается ли она необработанной, определяется по параллельным условиям — ошибок нет, если выполняется любое из них:

- **Всплытие через `?=`** (требует, чтобы функция имела выходной параметр option);
- **Перехват на месте**: привязка через `=` к **новой** переменной (тип выводится как `?T`) либо явное объявление `?T` (например, `x ?i64 = a + b`);
- **Явное отбрасывание `_ = expr`** (само вычисление идёт по безопасному пути, ошибка тоже игнорируется);
- **Аннотация** `#{overflow = wrap}` / `clamp0` / `min` / `max` / `saturate` (или форма с префиксом типа вроде `u8-max`, `i8-min`), заявляющая о принятии семантики переполнения по модулю/насыщения.

Ошибка возникает, только если не выполняется ни одно из четырёх условий (`ovfhndld`).

> **Чистая арифметика не является источником ошибок**: `+ - * <<` и унарное отрицание сами по себе не вызывают перехвата (иначе вся арифметика стала бы option, и стандартная библиотека раздулась бы). Поэтому `d = x - 1` (без `/` `%`, без безопасной индексации, без операндов option) по-прежнему даёт ошибку — добавьте аннотацию или напишите `d ?i64 = x - 1`.
>
> **Существующие переменные не меняют тип**: перехват действует только на цель, **впервые объявляемую в этой инструкции**. Если переменная уже существует (например, сначала `d = 0`, затем `d = x - 1`, или сначала `v i64 = 0`, затем `v = arr[i]`), компилятор не превращает её в option на месте, а требует от вас явно выбрать семантику.

Есть ещё две жёсткие ошибки, на которые не действуют перечисленные исключения:

- Если неотмеченная целочисленная операция присваивается переменной с **явным обычным `int`**, компилятор сообщает об ошибке (`cannot assign ?i64 value to i64 variable`), заставляя вас добавить `#{overflow = wrap}` / `#{overflow = clamp0}` / `#{overflow = min}` / `#{overflow = max}` / `#{overflow = saturate}` (или форму с префиксом типа) либо использовать именованный `?T`.
- Если неотмеченная целочисленная операция присваивается **уже существующей** переменной не-option типа (`d = x - 1` после `d = 0`), компилятор сообщает об ошибке и предлагает добавить аннотацию или объявить `?i64`, чтобы не допустить некорректный IR.

Остальные правила:

- Операции с беззнаковыми целыми (`u8`/`u16`/`u32`/`u64`/`u128`) **подчиняются этому же механизму**: без аннотации `+ - *` по умолчанию возвращают `option<int>`, переполнение → `err`, как и для знаковых целых.
- Операции с `i128` не поддерживают путь `option` (поле data имеет только `i64`) и единообразно деградируют до тихого переполнения по модулю ради сохранения корректности.

> **Почему по умолчанию option, а не wrap?** Тихое переполнение по модулю скрывает ошибки; возврат `option` по умолчанию заставляет вызывающую сторону явно обработать переполнение (или сознательно аннотировав `wrap`, заявив «я принимаю семантику переполнения по модулю»), превращая «допустимо ли переполнение» в видимое проектное решение.

### Деление на ноль (division by zero)

Делитель `0` при целочисленных `/` и `%` — это **неопределённое поведение (UB)**, и это **две независимые вещи** с переполнением — никакая аннотация не может его отменить:

- **Определимо на этапе компиляции**: делитель — **литеральная константа 0** (`10 / 0`, `a % 0`, `x / 0`) ⇒ **жёсткая ошибка** (trace id `div-by-zero`). `#{overflow = wrap}` не отменяет её (эта аннотация управляет переполнением, а не делением на ноль).
- **Известно только во время выполнения**: делитель приходит из переменной/внешнего ввода ⇒ компилятор **вставляет проверку на ноль в обе ветви**; разница лишь в «как сообщается»:

| Тип результата        | Условие срабатывания                    | При делителе 0                                                                        |
| ----------- | ----------------------- | ------------------------------------------------------------------------------ |
| `?int` (по умолчанию)  | инструкция без аннотации                   | option tag = `err`, обрабатывается через `?=` / match                                           |
| обычный `int` | инструкция с `#{overflow = ...}` | результат принудительно `0`, а в **stderr** выводится `nolang: integer division or remainder by zero ...` |

```nolang
safe = (a i64, b i64) (r ?i64) {
    r = a / b; b == 0 → err (вызывающая сторона должна обработать)
}

#{overflow=wrap}
fast = (a i64, b i64) (r i64) {
    r = a / b; b == 0 → 0 и вывод строки диагностики в stderr (больше не голый sdiv с UB)
}
```

> **Почему `#{overflow = wrap}` не отменяет защиту от деления на ноль**: он меняет **поведение при переполнении** (тип результата по-прежнему всегда `?int`), а не безопасность делителя. Если бы он её отменял, компилятор выпустил бы голый `sdiv`, и оптимизатор получил бы право предполагать, что делитель никогда не равен 0 (сворачивая `a / 0` в произвольное значение), а `idiv` на x86-64 сразу же аварийно завершился бы с #DE — и UB, и никакой диагностики. Поэтому защита zero-divisor существует **независимо от аннотации**; то, что обычный путь дополнительно печатает строку в stderr, как раз и объясняется тем, что у этого пути нет option, который мог бы проверить вызывающий.
>
> **Та же защита покрывает и `sdiv (INT_MIN, -1)`** (результат непредставим, тоже UB; на x86-64 вызывает SIGFPE). option-путь относит это к `err`; обычный путь берёт значение по модулю 2 (`INT_MIN / -1 → INT_MIN`, `INT_MIN % -1 → 0`).

Деление с плавающей точкой не регулируется: `1.0 / 0.0` определено стандартом IEEE-754 как `inf` / `nan`, это не UB.

### Неотмеченные операции считаются ошибкой (`ovf-int-default`)

`no vet` сообщает о **неотмеченных** целочисленных операциях как о **подсказке** (trace id `ovfhndld`, HINT). Причина: используемое по умолчанию `?T` не видно пользователю, и его нужно уведомить — можно добавить `#{overflow = ...}`, задав поведение при переполнении, либо потребить `?T` + `?=` / match / явный обычный тип. Что действительно должно блокировать сборку — так это `optunuse` (option ни всплыл, ни был распакован).

### Автоматическое исправление: `no fmt --fix=overflow`

Массово добавлять аннотации вручную не обязательно — используйте параметр категории исправлений у `no fmt`:

```bash
no fmt --fix=overflow -w src/std          # исправить весь каталог на месте
no fmt --fix=overflow -d src/std/str.no   # только вывести diff, не записывать
no fmt --fix=overflow src/std/str.no      # вывести исправленное содержимое
```

Исправление **точное и не загрязняющее**: `#{overflow=wrap}` вставляется только над той инструкцией, где lint реально сообщил об ошибке; другие инструкции не изменяются, переформатирования нет, существующие аннотации не трогаются, и повторный запуск идемпотентен (уже отмеченные не меняются). Это отличается от простого `no fmt -w` — последнее выполняет полное переформатирование.

> После исправления запустите `no vet` ещё раз, чтобы убедиться в нуле. В подавляющем большинстве случаев всё очищается за один проход (`src/std`: с 4728 до 0). Единственная известная исключительная форма: сообщение относится к **условию** ветви match, а в теле этой ветви нет инструкции, которую можно было бы аннотировать, — строчная аннотация действует только на первую следующую инструкцию и не покрывает операцию в условии самой ветви, поэтому `no vet` сообщит снова. В таком случае сначала выделите эту операцию в отдельную инструкцию и только затем аннотируйте.

### Автоматическое исправление: избыточные аннотации типов

Когда **аннотация типа в объявлении переменной полностью совпадает с типом, выведенным из значения справа**, такая аннотация избыточна (`no vet` сообщает подсказкой `tcpoxtfd`, `type annotation '<T>' can be omitted (inferred from value)`).

- **Обычный `no fmt` удаляет их автоматически**: `no fmt -w` при форматировании одновременно убирает избыточные аннотации (и выполняет нормальное переформатирование), `no fmt -d` показывает это изменение в предпросмотре, `-w` записывает.

```bash
no fmt -w main.no          # отформатировать и убрать избыточные аннотации
no fmt -d main.no          # только вывести diff (включая удаление аннотаций)
no fmt -w src/             # весь каталог
```

- **`--fix=redundant` (хирургический, только аннотации)**: если нужно удалить только избыточные аннотации без полного переформатирования (например, для `src/std`, поскольку `no fmt` теряет `#{index-out}`), используйте эту категорию — она только удаляет аннотации, не переформатируя:

```bash
no fmt --fix=redundant -w src/std          # удалить избыточные аннотации во всём каталоге на месте (без переформатирования)
no fmt --fix=redundant -d src/std/str.no   # только вывести diff, не записывать
no fmt --fix=redundant src/std/str.no      # вывести исправленное содержимое
```

```nolang
; до исправления
x str = ''
b i64 = 5
m [str]i64 = make-map()

; после исправления (аннотация == выведенный тип, удалена)
x = ''
b = 5
m = make-map()
```

Основные правила:

- Удаляется только когда **тип аннотации == выведенному типу** (например, `str`/`i64`/`[str]i64` совпадают с выведенными значениями).
- Случаи, когда **типы неявно преобразуются, но не равны**, **не удаляются** — аннотация сохраняет семантику преобразования. Например, `c i16 = 5` (`5` выводится как `i64`, не равно `i16`), `p ?i64 = nil`, `last txt = ''` (`txt` и `str` неявно преобразуются друг в друга, но типы различны).
- Записи **без аннотации типа** (например, `d = 'x'`) изначально не сообщаются и, естественно, не изменяются.
- **Аннотации массивов фиксированной длины `[N]T` / `[?]T` сохраняются всегда** (никогда не считаются избыточными). `[N]` — это не простая подсказка о типе, а переключатель, определяющий **представление**: только с ним литерал `[...]` справа разбирается как стековый массив фиксированной длины; только с ним выведенный результат «оказывается в точности равным» аннотации — это порочный круг, созданный самой аннотацией. После удаления та же строка при повторном разборе превращается в расширяемый срез в куче `[]T`, и семантика меняется: у `fixed [3]char = ["x", "y", "z"]` метод `.push()` недействителен (`.len()` всегда 3), а после вырождения в `fixed = ["x", "y", "z"]` вызов `.push()` делает `.len()` равным 4. Аннотация среза `[]T` в их число не входит — после удаления он остаётся срезом, то есть действительно избыточен.
- **Значения с шестнадцатеричными литералами всегда сохраняют аннотацию** (консервативное исключение). Вывод типов в `no vet` для `0xNN` использует эвристику «вывести как `byte`», отличную от реальной семантики компилятора «без аннотации целочисленный литерал по умолчанию `i64`», поэтому `IP-TBL [64]byte = [0x3a, ...]` и `s []byte = [0x50, 0x4b]` ошибочно принимаются за избыточные; после удаления литералы вырождаются в элементы `i64` и возникают ошибки типов вроде `expected '[]byte', got '[]i64'`. Поэтому если в тексте выражения значения встречается `0x`/`0X`, подсказка и удаление не производятся.
- **Когда справа стоит чтение поля, аннотация сохраняется всегда** (консервативное исключение). Аннотация в записи вроде `i i64 = .pos` — это не простая подсказка о типе, а переключатель, определяющий, будет ли последующая целочисленная арифметика порождать `?T`: если тип выводится из поля, `i + N` перестаёт быть «знаковой операцией» и не возвращает `?i64`, ветвь `ok` двухэтапной распаковки никогда не срабатывает, а счётчик цикла остаётся на месте. Пример из `src/std/yaml.no`, `parser.looks-like-map-entry`: удаление `i64` заставляет `yaml.parse('abc')` зациклиться. Поэтому аннотации на `x = .field`, `x = obj.field` (включая скобки или префиксную обёртку) не порождают `tcpoxtfd` и не удаляются ни обычным `no fmt`, ни `--fix=redundant`.

Независимо от того, используется обычный `no fmt` или `--fix=redundant`, удаление убирает только ту аннотацию типа, о которой сообщено, и предшествующие ей пробелы; повторный запуск идемпотентен (удалённые больше не меняются). После исправления рекомендуется ещё раз запустить `no vet` и убедиться, что `tcpoxtfd` равен нулю.

### Автоматическое исправление: потребление option (`--fix=unwrap`)

При единой модели «option создан, но никогда не потреблён» — это единственная диагностика, которая действительно должна блокировать сборку (trace `optunuse`). Чтобы массово переписать её в форму явного потребления, используйте `--fix=unwrap`:

```bash
no fmt --fix=unwrap -w src/std            # исправить весь каталог на месте
no fmt --fix=unwrap -d src/std/str.no     # только вывести diff, не записывать
no fmt --fix=unwrap src/std/str.no        # вывести исправленное содержимое
```

Формы исправления (см. «Безопасная индексация»): **если функция уже имеет выходной параметр `?T`** → всплытие (`x ?= <expr>`); иначе → переименование + распаковка через match:

```nolang
; до исправления
x = a + b

; после исправления (функция имеет выходной параметр ?T)
x ?= a + b

; после исправления (иначе, стандартная форма из 4 строк; пустая запасная ветвь = нулевое значение)
x-opt = a + b
x = x-opt: {
    ok -> it

    ->
}
```

Как и у других категорий исправлений: хирургическая текстовая замена, без изменения форматирования, без затрагивания аннотаций `#{overflow=…}` / `#{index-out=…}` над инструкцией (они по-прежнему отвечают за «как получить значение при неудаче»), повторный запуск идемпотентен. После исправления запустите `no vet` ещё раз и убедитесь, что `optunuse` равен нулю.

### Привязка аннотаций и объединение в одну строку

Аннотации `#{...}` **привязываются к узлу**, поэтому одна инструкция может нести несколько ключей сразу; несколько аннотаций всегда **объединяются в одну строку**:

```nolang
#{fmt-skip}
i <- [0..16): {

    #{index-out=0, overflow=wrap}
    buf[base + i] = data[i]
}
```

У приведённой выше инструкции одновременно нужны две семантики: «значение по умолчанию при выходе за границы» (`index-out`) и «переполнение по модулю» (`overflow`). Запись в две строки даёт тот же результат разбора, но `no fmt --fix=overflow` создаёт объединённую однострочную форму.

> **Область действия строчной аннотации**: `#{overflow = ...}` действует только на **непосредственно следующую инструкцию**. Если между ними оказалась посторонняя аннотация, она всё равно корректно применяется к нужной инструкции. Запись с безопасной индексацией (`arr[base + i] = v`, `.buf[.pos + i] = v`) при дешугаринге превращается в форму match, и `#{overflow = wrap}` переносится на узлы после дешугаринга, поэтому выражение индекса тоже регулируется аннотацией и не будет ошибочно принято за неотмеченное.

### Всплытие ошибки (оператор `?=`)

`?=` — это **сокращённая запись** распаковки option + всплытия ошибки вверх. **Возврат option из функции не является обязательным условием**: достаточно одного из двух следующих случаев,
поэтому функция, чьё возвращаемое значение не option, тоже может писать `y ?= x + 1`, если обернуть тело в блочный match.

**Синтаксис:**

```no
v ?= expr
```

**Семантика:**

- Если `expr` возвращает `ok(value)`, то `v` присваивается распакованное внутреннее значение (автоматическая распаковка)
- Если `expr` возвращает `nil` или `err`:
  - если функция имеет выходной параметр `?T` → записать этот option в выходной параметр и досрочно `return` (автоматическое всплытие);
  - если инструкция находится в теле **statement-level блочного match** `{ ... }: { ... }` → её перехватывает **ближайший** блочный match,
    **всё тело останавливается**, ветви выполняются один раз (**не** `return`), и функция не нуждается в выходном параметре `?T`.

**Условия применимости (достаточно одного из двух):**

1. функция, в которой это записано, имеет выходной параметр типа option;
2. инструкция находится в теле statement-level блочного match `{ ... }: { ... }` (см. «Три формы подлежащего match»).

Если не выполняется ни одно из условий, компилятор сообщает об ошибке. Две ветви `err -> _` / `-> _` могут проглотить всплывшую ошибку на месте — это стандартный приём, когда «нет выходного параметра `?T`,
но хочется использовать сокращение»:

```no
handle = (x i64) {
    {
        y ?= x + 1
        print(1)
    }: {
        err -> _

        -> _
    }
}
```

**Выходной параметр не нужно инициализировать заранее**: пролог функции не выполняет обнуление, но при return неявно присвоенные выходные параметры автоматически заполняются нулями (целые → `0`, `str` / структуры → нулевое значение, option → `nil`), поэтому в примере не пишется шаблон `result = nil`, а записывается только присваивание на успешном пути.

**Пример:**

```no
; построчное чтение файла и обработка — ?= упрощает распространение ошибок
process-file = (path str) (result ?str) {
    f ?= open(path); при неудаче автоматически result = f; return
    line ?= f.read-line(); при EOF или ошибке автоматически всплывает
    result = line
}
```

Эквивалентная развёрнутая форма (цепочка match, автоматически генерируемая компилятором):

```no
#{fmt-skip}
process-file = (path str) (result ?str) {
    result = nil
    __tmp = open(path)
    __tmp: {
        nil || err -> {
            result = __tmp
            return
        }
        -> f = it
    }
    __tmp2 = f.read-line()
    __tmp2: {
        nil || err -> {
            result = __tmp2
            return
        }
        -> line = it
    }
    result = line
}
```

**Цепочечное использование:** несколько `?=` можно объединять в цепочку, реализуя конвейерную передачу ошибок:

```no
pipeline = (input str) (result ?str) {
    a ?= step1(input); при неудаче всплывает
    b ?= step2(a); при неудаче всплывает
    result = b
}
```

**Голые арифметические операции:** справа от `?=` не обязательно должен быть вызов функции — любая целочисленная операция, возвращающая `option` (например, неотмеченные `a - b`, `a + b`, `a * b`), может напрямую всплыть через `?=` без предварительной привязки к промежуточной переменной:

```no
; при переполнении автоматически result = err; return, при норме v распаковывается во внутреннее значение
sub-safe = (a i64, b i64) (result ?i64) {
    v ?= a - b; отрицательное/положительное переполнение → err автоматически всплывает; иначе v = внутреннее i64
    result = v
}

add-safe = (a i64, b i64) (result ?i64) {
    v ?= a + b; то же, применимо к + * и знаковому /
    result = v
}
```

Эквивалентное развёртывание (генерируется компилятором автоматически):

```no
#{fmt-skip}
sub-safe = (a i64, b i64) (result ?i64) {
    result = nil
    __unwrap = a - b            ; option<i64>
    __unwrap: {
        nil -> {
            result = __unwrap
            return
        }
        err -> {
            result = __unwrap
            return
        }
        -> v = it               ; ok(value): распаковать внутреннее значение
    }
    result = v
}
```

**Составное справа (compound RHS):** справа от `?=` может стоять составное выражение с несколькими операндами-option. Каждый операнд-option автоматически распаковывается, и вставляется guard распространения — как только какой-то операнд оказывается `nil` / `err`, выходной параметр option текущей функции получает это значение и выполняется `return` (всплытие вверх); только при полном успехе внутреннее значение присваивается левой стороне:

```no
sum3 = () (result ?i64) {
    a ?i64 = ok(10)
    b ?i64 = ok(20)
    c ?i64 = ok(30)
    total ?= a + b + c; каждый операнд-option автоматически распаковывается и распространяется
    result = total
}

comp = () (result ?i64) {
    a ?i64 = ok(4)
    b ?i64 = ok(6)
    v ?= dbl(a + b); a + b может быть option, тоже автоматически распаковывается и распространяется
    result = v
}
```

> Автоматически распаковываются только option в **позиции операнда** (например, `a + b + c`, `f(b + c)`); переменная option, переданная напрямую как аргумент функции, в их число не входит — для неё действует существующее исключение `?=` для голого аргумента-option (`a ?= f(v)`, где `v` имеет тип `?i64`, а `f` принимает обычный `i64`).

**Ошибка для не-option справа:** чтобы избежать массового написания `=` вместо `?=`, когда правое выражение на этапе компиляции можно определить как «заведомо не option», компилятор сообщает об ошибке и рекомендует использовать `=`:

- Литерал: `v ?= 42`
- Сворачиваемая константами целочисленная операция: `v ?= 10 + 20`
- Локальная переменная с известным не-option типом: `v ?= x` (где `x i64 = 5`)

Сообщение об ошибке имеет вид: `` `?=` RHS `42` is not an option — use `=` instead ``.

> Арифметическая операция считается «возможно option» и пропускается, если любой её операнд является option (или имеет неизвестный тип / является вызовом функции, который может вернуть option), — ложных срабатываний нет: например, `v ?= a + b + c` (a/b/c имеют тип `?i64`) или `v ?= b + c` (b/c неизвестного типа) компилируются нормально.

**Сценарии применения:**

- `pop` / `peek` и другие операции с контейнером, которые могут быть пустыми → `?t` (`nil` = пусто)
- `read-line` / `read-byte` и другие операции ввода-вывода → `?str` / `?i64` (`nil` = EOF, `err` = ошибка)
- `lookup` / `get` и другие операции поиска → `?t` (`nil` = не найдено)
- `parse` / `from-str` и другие операции разбора → `?t` (`nil` = пусто, `err` = неверный ввод)
- `accept` / `dial` и другие сетевые соединения → `?conn` (`nil` = нет соединения, `err` = ошибка)

**nil против err:** используйте `nil`, когда отсутствие — нормальный/ожидаемый результат (пустой стек, ключ не найден, EOF); используйте `err('msg')`, когда отсутствие означает реальное состояние ошибки (сбой ввода-вывода, неверный ввод, соединение отклонено).

**Исключение:** когда функции нужно вернуть несколько независимых значений (например, `(name str, value str, ok bool)`), шаблон с несколькими возвращаемыми значениями можно оставить.

**Не более одного `?T` среди нескольких возвращаемых значений (жёсткая ошибка):** среди выходных параметров, объявленных функцией, `?T` может быть не более одного. `?T` — это **единый** канал ошибок: когда `?=` в теле функции возвращает досрочно, ошибку можно поместить только в этот единственный параметр option; если объявить два `?T`, компилятор сможет заполнить только первый, и вызывающая сторона получит наполовину заполненный кортеж (`(err, nil)`), при этом невозможно определить, какое значение означает неудачу:

```no
#{fmt-skip}
pair = () (a ?i64, b ?i64) {; ошибка: два выходных параметра ?T
    a = ok(1)
    v ?= boom(); boom() возвращает err('boom')
    a = v
    b = ok(2); никогда не выполняется — вызывающая сторона видит (err, nil)
}
```
```

Правильный способ — объявить независимые значения обычными типами, оставив один `?T` в качестве канала ошибок:

```no
lookup = (k str) (value str, found bool, err ?str) {
    value = ''
    found = false
    err = nil
}
```

Сообщение об ошибке имеет вид: `` function 'pair' declares 2 option (?T) results ('a', 'b'); only one result may be ?T … [moptres1] ``. Неявный получатель `self` в определении метода — это выходной параметр-псевдоним вызывающей стороны, и он не занимает это место; `#{c}` extern-объявления подчиняются тому же ограничению.

### Перехват ошибок присваиванием (`=` перехват на месте)

Семантика `?=` — «всплытие ошибки вверх»: она требует, чтобы функция имела выходной параметр option, и при неудаче выполняет досрочный `return`. Когда вы не хотите возвращаться досрочно, а хотите обработать ошибку на месте, используйте обычное `=`: если справа есть **источник ошибок**, целевая переменная автоматически выводится как `?T`, а `nil` / `err` **сохраняются прямо в этой переменной**, и выполнение продолжается.

```no
handle = (b i64, c i64, d i64) (r i64) {
    a = b + c / d; a выводится как ?i64; деление на ноль → a = err
    a: {
        err -> {
            r = -1; обработать ошибку на месте
        }

        nil -> {
            r = -1
        }

        -> {
            r = it; успех: r = b + c/d
        }
    }
}
```

**Источники ошибок (триггеры перехвата):**

| Источник                | Пример                                   | Результат перехвата                          |
| --------------------- | ----------------------------------- | ----------------------------- |
| Целочисленное деление / остаток             | `a = b + c / d`, `a = b % c`         | деление на ноль, `MIN / -1` → `err`         |
| Безопасная индексация                  | `a = v[i]` (`arr` / `vec` / `slice`) | выход за границы → `err` (`code.index-out`)  |
| Операнд типа option           | `a = x + 1` (`x ?i64`)               | если `x` — `nil` / `err`, значение как есть сохраняется в `a` |
| Вызов, возвращающий option (как арифметический операнд) | `a = f(x) + 1` (`f` возвращает `?i64`)       | то же                            |

> Option, переданный **напрямую** как аргумент функции, в их число не входит — его оставляют вызываемой стороне (в соответствии с исключением `?=` для голого аргумента-option).

**Чистая арифметика не является источником ошибок**: `+ - * <<` и унарное отрицание сами по себе не вызывают перехвата (иначе вся арифметика стала бы option). Но как только вычисление оказывается на пути option (например, справа есть `/` или цель явно объявлена как `?T`), эти операции получают **проверку переполнения во время выполнения**, переполнение → `err`:

```no
ovf = (x i64) (r i64) {
    a ?i64 = x + 1; явный ?T → путь упаковки option
    a: {
        err -> {
            r = 0; при x = i64-max переполнение → err
        }

        nil -> {
            r = 0
        }

        -> {
            r = it
        }
    }
}
```

**Перехват против всплытия:**

| Запись            | При неудаче                                 | Нужен выходной параметр option | Как получить значение после             |
| ------------- | ----------------------------------- | -------------- | ------------------ |
| `a ?= expr`   | установить выходной параметр в `nil`/`err` и `return` (досрочный возврат) | да              | не применяется (уже возвращено)           |
| `a = expr`    | `a` сохраняет `nil`/`err` на месте, выполнение продолжается            | нет              | `a: { ok -> ... }` |
| `a ?T = expr` | то же, что `=` (явная аннотация, включая внутренние источники ошибок)               | нет              | то же                 |
| `_ = expr`    | вычислить, но отбросить результат и ошибку (нет ошибки, не вызывает unused lint)     | нет              | не применяется                |

**Область применения:** перехват при безопасной индексации, как и у `?=`, **действует только внутри функций, возвращающих `?T`** (см. «Безопасная индексация», третий способ). Перехват `/` `%` и операндов-option действует во всех функциях.

**Существующие переменные не меняют тип:** перехват действует только на цель, **впервые объявляемую в этой инструкции**. Если цель уже существует (`v = arr[i]` после `v i64 = 0` или `d = x - 1` после `d = 0`), компилятор не меняет её тип на месте, а требует явно выбрать семантику (добавить аннотацию `#{overflow=...}` / `#{index-out=...}`, использовать `?=` или объявить `?T`).

### Проверка типов при целочисленном присваивании

Компилятор проверяет типы при целочисленном присваивании, чтобы предотвратить опасное сужение (narrowing), ведущее к потере данных. Правила ниже:

#### Неявное расширение (безопасно, разрешается автоматически)

Значение узкого целочисленного типа можно автоматически присвоить более широкому типу, поскольку диапазон целевого типа полностью содержит диапазон исходного:

```no
b byte = 200
i i64 = b; ✓ диапазон byte [0,255] ⊆ диапазон i64
u u32 = b; ✓ диапазон byte ⊆ диапазон u32
```

#### Присваивание целочисленных литералов

Целочисленный литерал (по умолчанию выводится как `i64`) можно присвоить любому целочисленному типу, диапазон которого содержит это значение:

```no
#{fmt-skip}
n u8 = 200; ✓ 200 ∈ [0,255]
m u8 = 300; ✗ 300 > 255, ошибка компиляции
big u64 = 18446744073709551615; ✓ 2^64-1, максимальное значение u64
```
```

#### Небезопасное сужение (ошибка компиляции)

Непосредственное присваивание переменной широкого типа переменной узкого типа приводит к ошибке компиляции, так как возможна потеря данных. Сообщение об ошибке содержит **практическую подсказку по исправлению**, рекомендующую, как безопасно сузить значение с помощью побитовых операций:

```no
#{fmt-skip}
d u64 = 42
h u32 = d; ✗ cannot assign u64 value to u32 variable 'h'; hint: narrow safely with a bitwise mask (e.g. `& 4294967295`) or right shift (e.g. `>> 32`)
h u16 = d; ✗ cannot assign u64 value to u16 variable 'h'; hint: narrow safely with a bitwise mask (e.g. `& 65535`) or right shift (e.g. `>> 48`)
h u8 = d; ✗ cannot assign u64 value to u8 variable 'h'; hint: narrow safely with a bitwise mask (e.g. `& 255`) or right shift (e.g. `>> 56`)
x u32 = d + 1; ✗ результат сложения по-прежнему u64, небезопасно
y u32 = foo(); ✗ тип результата вызова функции не совпадает
```
```

> **Подсказка по исправлению**: компилятор автоматически вычисляет точное значение маски и величину сдвига для целевого типа. Применив подсказанную маску или сдвиг, можно безопасно сузить значение (см. следующий раздел).
>
> **Знаковый целевой тип**: для знаковых целых `i8`/`i16`/`i32`/`i64` подсказка указывает, что побитовое сужение неприменимо (семантика усечения знакового бита неоднозначна), и рекомендует вместо этого явную проверку диапазона.

#### Безопасное сужение побитовыми операциями (разрешается автоматически)

Когда справа от присваивания стоит **побитовое выражение** (`&`, `|`, `^`, `<<`, `>>`), а целевой тип — **беззнаковое целое** (`u8`/`u16`/`u32`/`u64`/`byte`), компилятор разрешает неявное сужение — ведь усечение старших разрядов является стандартной семантикой побитовых операций и не приводит к неожиданной потере данных:

```no
d u64 = 42

; ✓ операция mask: результат всегда ≤ значения маски, безопасно попадает в u32
h u32 = d & 67108863; mask = 2^26-1 < 2^32
h u32 = d & 4294967295; mask = 2^32-1, ровно диапазон u32

; ✓ операция сдвига: после сдвига вправо старшие разряды равны 0, безопасно
hi u32 = d >> 32; u64 >> 32 оставляет 32 бита

; ✓ комбинации XOR / OR
c u32 = a ^ b; результат побитовой операции
b byte = v & 255; маска в диапазон byte

; ✓ составные побитовые операции (часто в криптографии/кодировании)
s u32 = (key[0] & 255) | ((key[1] & 255) << 8) | ((key[2] & 255) << 16) | ((key[3] & 255) << 24)
```

> **Почему разрешено?** Семантика побитовых операций (mask, сдвиг, XOR, OR) как раз и состоит в построении битового шаблона. При присваивании узкому беззнаковому типу усечение старших разрядов — намеренная операция: разработчик уже гарантировал диапазон результата с помощью маски или сдвига либо намеренно отбросил старшие разряды. Это стандартный приём в криптографии (например, ChaCha20, Poly1305, Blake2) и в коде кодирования/декодирования.

> **Только беззнаковые целевые типы.** Для знаковых целевых целых (`i8`/`i16`/`i32`/`i64`) даже побитовое справа даёт ошибку, поскольку семантика усечения знакового бита неоднозначна:
>
> ```no
> d u64 = 42
> h i32 = d & 4294967295   ; ✗ всё равно ошибка: знаковый целевой тип не поддерживает безопасное сужение
> ```

> **Верхний уровень должен быть побитовой операцией.** Пропуск происходит только когда операция верхнего уровня выражения — `&`/`|`/`^`/`<<`/`>>`. Сложение, вычитание, вызовы функций, прямые ссылки на переменные в их число не входят:
>
> ```no
> d u64 = 42
> h u32 = d              ; ✗ верхний уровень — Identifier, не побитовая операция
> h u32 = d + 1          ; ✗ верхний уровень — +, не побитовая операция
> ```

; локальный модуль, должен начинаться с /
# /utils/math.add
; псевдоним
# std/math.add a

; ── ниже старый синтаксис (deprecated, работает, но не рекомендуется) ──
; use std/math.add
; use github.com/utils/math.add
; use /utils/math.add
; use std/math.add a
```

#### Прямой импорт конфигурационного файла `.noml`

Файл `.noml` можно импортировать напрямую через `#`: порядок разбора сначала ищет `.no` с тем же именем, а если не находит — `.noml`. После импорта
**имя структуры по умолчанию совпадает с именем файла** (без расширения; его можно переопределить аннотацией `#{name = '...'}` в начале файла),
а каждый член становится полем этой структуры; одновременно создаётся глобальное значение с тем же именем, несущее содержимое файла, поэтому работает
чтение `server.port`.

```noml
; cfg/server.noml
{
  host: 'localhost'
  port: 8080
  tags: [] #{type = '[]str'}
  compiler: {
    version: 'v0.1.0'
  }
}
```

```no
# /cfg/server

print(server.port); 8080
print(server.compiler.version); v0.1.0
```

- Тип поля берётся из аннотации члена `#{type = '...'}` (значение — полное выражение типа nolang, например
  `'[]str'`, `'[]i64'`, `'?i64'`); без аннотации тип выводится из значения: строка → `str`, целое → `i64`,
  дробное → `f64`, логическое → `bool`, объект → автоматически создаваемая вложенная структура (`server-compiler`),
  массив → `[]тип-элемента`.
- Пустые контейнеры (`[]`, `{}`) **обязательно** требуют `#{type = '...'}`: у значения noml нет типа, пустой контейнер
  нельзя вывести. Если член объект аннотирован `#{type = 'x'}`, используется `x` (должен быть определён пользователем), и вложенная структура
  не создаётся автоматически.
- Имя структуры вложенного объекта использует имя файла как префикс (`server-compiler`); порядок определения: сначала вложенные, затем вмещающая.
- **Аннотация сверху (уровня документа) может переопределить имя структуры**: `#{name = '...'}` (эквивалентная запись `#{type = '...'}`,
  `name` имеет приоритет) пишется отдельной строкой над верхним `{` (или в конце строки верхнего значения). После переопределения имя привязки значения и
  префикс вложенной структуры меняются вместе с ним, но **путь импорта по-прежнему определяется именем файла**:

```noml
; cfg/db.noml
#{name = 'db-options'}
{
  host: 'localhost'
}
```

```no
# /cfg/db
# /cfg/db as db2

print(db-options.host); localhost
print(db2.host); localhost
```

- Когда два разных файла создают одно и то же имя типа (например, одноимённые файлы в разных каталогах), возникает ошибка; используйте верхнюю
  аннотацию `#{name = '...'}` для различения; повторный импорт одного файла (например, с дополнительным `as`) объединяет только одно определение типа.
- Имена ключей по правилам nolang преобразуются в дефисный нижний регистр (`anonymous-fn-type`): если начинается с цифры, добавляется `f-`, если
  совпадает с ключевым словом — добавляется `x-`.
- Разрешается псевдоним `as`, меняющий имя привязки значения; имя структуры не меняется: `# /cfg/server as cfg`.
- Типы `.noml` не участвуют в префиксе модуля: даже если имя файла совпадает с именем модуля стандартной библиотеки (например, `server`), тип остаётся голым именем.
- `package.noml` / `workspace.noml` также могут содержать аннотации `#{...}` (например, `#{type = '[]str'}`):
  при разборе они игнорируются и нужны только внешним инструментам для восстановления строго типизированной структуры; синтаксис полностью совпадает с nolang `#{...}`.

### FFI (аннотация `#{c}`)

Через аннотацию `#{c}` объявляются внешние C-функции, реализующие FFI (Foreign Function Interface).

**Синтаксис**: `#{c}` на отдельной строке помечает следующую строку как FFI-объявление. `#{c}` — это FFI-ключ системы аннотаций; поддерживаются и другие языки: `#{cpp}`, `#{rust}` и т.д. Старый синтаксис `#c` сохраняет обратную совместимость.

**Приватные объявления**: имя, начинающееся с `_`, означает приватное (не экспортируемое); C ABI-символ автоматически теряет префикс `_`, а дефисы превращаются в подчёркивания.

**Отдельные файлы больше не нужны**: FFI-объявления и обычный код можно писать в одном `.no`-файле.

**Синтаксис типов указателей**: в FFI для указателей используются C-стилевые `*T`, `**T`, `***T`, при этом тип `T` должен быть конкретным. В обычном коде этот синтаксис недопустим.

| Синтаксис        | Значение          | LLVM IR | Применение                  |
| --------- | ----------- | ------- | ------------------- |
| `*byte`   | указатель на byte | `i8*`   | непрозрачный указатель (например, db handle)  |
| `**byte`  | двойной указатель        | `i8**`  | выходной параметр (например, `sqlite3**`) |
| `***byte` | тройной указатель        | `i8***` | редкое тройное косвенное обращение            |

```no
; sqlite.no — FFI-привязка и безопасная обёртка в одном файле
; компилятор автоматически превращает дефис (-) в подчёркивание (_) для соответствия C ABI-символам
; имена, начинающиеся с _, приватны; C ABI-символ автоматически теряет префикс _

; параметры базовых типов
#{c}
c-strlen = (s str) (n i64)

; параметр-указатель (*byte = непрозрачный указатель), приватное объявление
#{c}
_sqlite3-close = (db *byte) (rc i32)

; двойной указатель (**byte = выходной параметр, после вызова значение автоматически сохраняется в переменной), приватное объявление
#{c}
_sqlite3-open = (filename str, db **byte) (rc i32)

; несколько параметров-указателей, приватное объявление
#{c}
_sqlite3-exec = (db *byte, sql str, callback *byte, arg *byte, errmsg *byte) (rc i32)
```

```no
; безопасная обёртка в том же файле

open = (dsn str) (d db-sqlite) {
    handle i64 = 0
    rc i32 = _sqlite3-open(dsn, handle)
    rc != SQLITE-OK -> {
        return
    }
    d.handle = handle
}
```

**Правила:**

1. `#{c}` на отдельной строке помечает следующую строку как FFI-объявление (старый синтаксис `#c` сохраняет обратную совместимость)
2. FFI — только объявление, без тела функции
3. Указатель должен иметь конкретный тип (например, `*byte`), голый `ptr` не допускается
4. `**byte` используется для выходного параметра: после вызова указатель, записанный C-функцией, автоматически преобразуется в `i64` и сохраняется в переменной вызывающей стороны
5. Все указатели на стороне Nolang хранятся как `i64` (`ptrtoint`)
6. Параметр типа `str` автоматически преобразуется в null-terminated `i8*`
7. Имя с префиксом `_` означает приватное (не экспортируемое); C ABI-символ теряет префикс `_`
8. FFI-объявления и обычный код можно писать в одном `.no`-файле

> Обратное направление (пусть C / C++ / Rust / Go / Java / Python / C# вызывают Nolang) — через `#{cabi='symbol'}` и `no build --shared`, см. [Вызов Nolang из host-языков](./host-interop).

### Система аннотаций (`#{...}`)

`#{...}` — это универсальная система аннотаций, список пар «ключ-значение», разделённых запятыми. Поддерживаются следующие типы значений:

| Синтаксис  | Тип  | Пример                                   |
| --- | --- | ------------------------------------ |
| Одиночный ключ | логическое  | `#{debug}`                           |
| Логическое значение | логическое  | `#{inline=true}` / `#{inline=false}` |
| Число  | целое  | `#{max=100}`                         |
| Текст  | строка  | `#{name='hello'}`                    |
| Идентификатор | идентификатор | `#{mode=fast}`                       |
| Массив  | массив  | `#{derive=[Serialize, Deserialize]}` |
| Диапазон  | диапазон  | `#{range=[0..256)}`                  |

Несколько пар «ключ-значение» разделяются запятыми:

```no
#{derive=[Serialize, Deserialize], range=[0..256), max=100, debug}
```

#### Позиции аннотаций

`#{...}` допускается писать только двумя способами:

- **Сверху**: отдельной строкой над целью (инструкция, поле структуры, член перечисления, объявление, ветвь match);
- **Сзади**: в конце той же строки, что и цель (`res = arr[i] #{index-out=zero}`, `a pt #{inline}`,  
  `green #{deprecated}`）。

Запись **перед целью на той же строке** (префикс, например `#{index-out=zero} res = arr[i]`) — **ошибка компиляции**, компилятор и  
LSP выдают одну и ту же диагностику. Правило: после `}` группы аннотаций на той же строке не должно быть кода (перевод строки,  
`;` однострочный комментарий или сразу следующая группа аннотаций кодом не считаются).

```no
; ✓ сверху: отдельной строкой
#{overflow=wrap}
x i8 = a + 100

; ✓ сзади: в конце той же строки
x i8 = a + 100 #{overflow=wrap}
```

```no
#{fmt-skip}
; ✗ спереди: префикс на той же строке → ошибка
#{overflow = wrap} x i8 = a + 100
```

Аннотации полей структур и членов перечислений (значения C-подобных перечислений, варианты тегированных) тоже допускаются только сверху или сзади  
（`a pt #{inline}`、`a pt #{inline=true}`、`green #{deprecated}`、`ok(v i64) #{inline}`）。  
Обратите внимание: **значение** `#{inline}` тоже поддерживается: `#{inline=false}` допустимо (см. ниже  
«`#{inline}` на полях структур»).

В записи `if <cond> { ... }` аннотация между условием и `{` (`if x > 0 #{overflow=wrap} {`) тоже считается  
«передней» позицией и тоже даёт ошибку. Сканирование в этом месте было мягким, и раньше всю группу аннотаций просто проглатывало — ни эффекта, ни ошибки,  
самый незаметный вид отказа.

Синтаксис диапазонов поддерживает 16 сочетаний скобок (правило: `[` включает левую границу, `(` не включает; `]` включает правую, `)` не включает):

**Ограниченные интервалы (4 вида)** — обе границы заданы:

- `[a..b]` — интервал, закрытый с обоих концов (`x >= a && x <= b`)
- `[a..b)` — слева закрыт, справа открыт (`x >= a && x < b`)
- `(a..b]` — слева открыт, справа закрыт (`x > a && x <= b`)
- `(a..b)` — интервал, открытый с обоих концов (`x > a && x < b`)

**Интервалы без верхней границы (4 вида)** — правая граница опущена:

- `[a..]`, `[a..)` — левая включена, без верхней границы (`x >= a`)
- `(a..]`, `(a..)` — левая не включена, без верхней границы (`x > a`)

**Интервалы без нижней границы (4 вида)** — левая граница опущена:

- `[..b]`, `(..b]` — без нижней границы, правая включена (`x <= b`)
- `[..b)`, `(..b)` — без нижней границы, правая не включена (`x < b`)

**Совершенно неограниченные интервалы (4 вида)** — обе границы опущены, на основе минимального/максимального значения типа:

- `[..]` — минимальное значение типа ≤ x ≤ максимальное значение типа (обе границы включены)
- `[..)` — минимальное значение типа ≤ x < максимальное значение типа
- `(..]` — минимальное значение типа < x ≤ максимальное значение типа
- `(..)` — минимальное значение типа < x < максимальное значение типа

#### Область действия аннотаций

**Позиция** аннотации определяет носителя, а **вид** носителя определяет, как велика область её действия. Всего четыре уровня, они действуют снаружи внутрь,
ближайший перекрывает, а тело функции — жёсткая граница наследования:

| Уровень | Хост | Область действия |
| --- | --- | --- |
| **L0 уровень модуля** | заголовок файла | все объявления и инструкции этого файла (аннотация в заголовке + одна пустая строка) |
| **L1 уровень объявления** | константы/глобальные переменные, структуры, интерфейсы, тегированные перечисления, функции, методы | всё определение этого объявления (функция включает тело и все вложенные блоки) |
| **L2 уровень блока** | группа корутин, группа if, `cond -> body`, match, циклы `for`/счётчика/диапазона | все инструкции внутри тела блока (включая вложенные блоки, до внутренней границы L1) |
| **L3 уровень строки** | одна инструкция (`let`, присваивание, `?=`, `return`, вызов, ветвь `cond ->`) | сама инструкция и её выражения |

```no
; L1: вся функция
#{overflow=wrap}
sum = (xs []i64) (total i64) {
    ; L3: только следующая инструкция
    #{overflow=wrap}
    total = xs.len() - 1
    ; L2: всё тело цикла
    #{overflow=wrap}
    i <- [0..xs.len()): {
        total = total + xs[i]
    }
}
```

Полные правила определения, матрицу «ключ × уровень» и расхождения с текущей реализацией см. в
[«Область действия аннотаций и комментариев»](annotation-scope.md).

FFI-аннотация `#{c}` — особая форма системы аннотаций: когда аннотация содержит FFI-ключ языка (`c`, `cpp`, `rust` и др.) и за ней следует объявление функции, компилятор распознаёт её как FFI-привязку:

```no
; #{c} с дополнительной аннотацией
#{c, debug}
_sqlite3-open = (filename str, db **byte) (rc i32)
```

#### Присоединение аннотаций к объявлениям

Не-FFI аннотации автоматически присоединяются к следующему за ними объявлению (объявление переменной, определение структуры) и могут использоваться для маркировки метаданных, таких как ограничения диапазона для числовых типов (например, `num`, `i64`):

```no
; объявление переменной с аннотацией range
#{range=[0..256)}
x num = 42

; определение структуры с аннотацией
#{derive=[Serialize, Deserialize]}
point {
    x i64
    y i64
}

; поле структуры с аннотацией range (применимо к числовым типам вроде num)
person {
    age num #{range=[0..150]}
    score i64 #{range=[0..256)}
    name str
}
```

Аннотация `range` особенно применима к типу `num` (`num = int | float`) для маркировки допустимого диапазона значения. Значение диапазона может быть целым числом или идентификатором:

```no
; использовать идентификатор-константу как границу диапазона
#{range=['i8.MIN'..'i8.MAX']}
val i8 = 100
```

#### Встраивание файлов (`#{embed=...}`)

Аннотация `#{embed=...}` встраивает содержимое внешнего файла на этапе компиляции как константу `[]byte` только для чтения, подобно `//go:embed` в Go. Встроенные данные компилируются прямо в исполнимый файл, обеспечивая распространение одним бинарником без чтения файлов во время выполнения.

**Синтаксис**:

```no
#{embed='path/to/file'}
ICON []byte

; или использовать голый путь (без кавычек)
#{embed='assets/icon.ico'}
ICON []byte
```

Аннотация `embed` присоединяется к следующему за ней объявлению переменной `[]byte`. Объявление переменной **не может** иметь явное начальное значение — значение предоставляется содержимым встроенного файла.

**Разрешение путей**:

- Относительные пути разрешаются относительно корня пакета (каталога, где находится `package.noml`)
- Поддерживаются абсолютные пути
- Путь может содержать символы `/`, `.`, `-`

**Пример**:

```no
; встроить иконку Windows
#{embed='assets/win-icon.ico'}
WIN-ICON []byte

; встроить SSL-сертификат
#{embed='certs/server.pem'}
SERVER-CERT []byte

; встроить конфигурационный файл
#{embed='config/default.json'}
CONFIG []byte

; использовать встроенные данные
print('icon size: ', len(WIN-ICON))
print('first byte: ', WIN-ICON[0])
```

**Примечания**:

1. Встроенные данные — константы **только для чтения**, указывающие на область памяти только для чтения. Запись во встроенные данные — неопределённое поведение (в соответствии с семантикой `//go:embed` в Go)
2. Встроенные переменные не участвуют в освобождении кучи — при выходе программы указатель встроенных данных не освобождается
3. Поддерживаются только объявления типа `[]byte` (также допустимы фиксированные массивы `[N]byte`)
4. Файл должен существовать на этапе компиляции, иначе ошибка
5. Нельзя сочетать с явным начальным значением (например, `ICON []byte = [1, 2, 3]` даст ошибку)

#### Встраивание каталога (`#{embed='dir'}`)

`#{embed=...}` также поддерживает встраивание целого каталога. Когда путь указывает на каталог, компилятор рекурсивно читает все файлы в нём и встраивает их как файловую систему только для чтения типа `fs.embed`. Во время выполнения через методы `read()` и `exists()` обращаются к встроенным файлам по пути — без каких-либо C-функций: логика поиска полностью реализована на Nolang.

**Синтаксис**:

```no
; встроить весь каталог фронтенда
#{embed='../frontend/dist'}
DIST fs.embed

; прочитать файл из встроенной файловой системы
data = DIST.read('index.html')

; проверить существование файла
ok = DIST.exists('css/style.css')
```

**Тип `fs.embed`**:

`fs.embed` — это структура, определённая в модуле `fs` стандартной библиотеки Nolang; она содержит метаданные встроенных файлов (путь, смещение, длина). Компилятор читает каталог на этапе компиляции и объединяет содержимое всех файлов в глобальные константы, а во время выполнения метод `read`, реализованный на чистом Nolang, выполняет поиск.

| Метод       | Сигнатура                                  | Описание                |
| -------- | ----------------------------------- | ----------------- |
| `read`   | `(path str) (data ?[]byte)`           | прочитать встроенный файл, вернуть содержимое (nil, если не найден) |
| `exists` | `(path str) (yes bool)`             | проверить, существует ли встроенный файл       |

**Пример**:

```no
; HTTP-сервер статических файлов: встроить фронтенд в один бинарник
#{embed='../frontend/dist'}
DIST fs.embed

serve = (conn server-conn) {
    conn.parse()
    path = conn.path
    path == '/' -> path = '/index.html'

    ; убрать ведущий /, чтобы получить относительный путь
    rel = path.slice(1, path.len-bytes())

    ; прочитать из встроенной файловой системы
    data []byte = DIST.read(rel)
    {
        ok -> it

        -> {
            conn.write-html(404, 'Not Found')
            conn.close()
            return
        }
    }
    conn.write-status(200)
    conn.write-header('Content-Type', get-content-type(path))
    conn.write-body(data)
    conn.close()
}
```

**Примечания**:

1. Все файлы каталога (включая подкаталоги) встраиваются рекурсивно; пути сохраняются относительно встроенного каталога (например, `css/style.css`)
2. Разделитель путей унифицирован в прямую косую черту `/` (одинаково на всех платформах)
3. Переменные типа `fs.embed` доступны только для чтения и не участвуют в освобождении кучи
4. Применимо для распространения одним бинарником (например, HTTP-сервер статических файлов, CLI-инструменты со встроенными ресурсами)

#### Платформенные аннотации

Платформенные аннотации — это фильтры на этапе компиляции, которые определяют, включать ли код, в зависимости от целевой платформы. Используются **плоские ключи** (например, `#{mac-arm64}`), одновременно задающие ОС и архитектуру, без двусмысленности; присоединяются к следующему за ними объявлению. Неподходящий код вообще не участвует в компиляции — LLVM IR не генерируется, проверка типов не выполняется.

**Поддерживаемые платформенные ключи (6 плоских сочетаний):**

| Ключ                | Соответствие                         |
| ---------------- | -------------------------- |
| `#{linux-amd64}` | Linux x86_64               |
| `#{linux-arm64}` | Linux ARM64                |
| `#{win-amd64}`   | Windows x86_64             |
| `#{win-arm64}`   | Windows ARM64              |
| `#{mac-amd64}`   | macOS x86_64 (Intel)        |
| `#{mac-arm64}`   | macOS ARM64 (Apple Silicon) |

```no
#{mac-arm64}
print('running on macOS ARM64')

#{linux-amd64}
print('running on Linux x86_64')

#{win-amd64}
print('running on Windows x86_64')

; переменные для конкретной платформы
#{mac-amd64, mac-arm64}
sep = '/'

#{win-amd64, win-arm64}
sep = '\\'

; функции для конкретной платформы
#{mac-arm64, mac-amd64}
greet = () {
    print('hello from mac')
}

#{linux-amd64, linux-arm64}
greet = () {
    print('hello from linux')
}

greet()
```

Несколько ключей на одном объявлении находятся в отношении **OR** — достаточно совпадения любого. Поскольку каждый ключ уже задаёт и ОС, и архитектуру, логика AND не нужна.

| Аннотация                          | Значение                                |
| --------------------------- | --------------------------------- |
| `#{mac-arm64}`              | только macOS ARM64                     |
| `#{mac-amd64, mac-arm64}`   | macOS любой архитектуры                        |
| `#{linux-amd64, win-amd64}` | Linux x86_64 **или** Windows x86_64 |
| `#{mac-arm64, linux-arm64}` | macOS ARM64 **или** Linux ARM64     |

```no
; выполняется и на macOS, и на Linux (все архитектуры)
#{mac-amd64, mac-arm64, linux-amd64, linux-arm64}
shared = () {
    print('unix-like')
}

; только Windows x86_64
#{win-amd64}
reg-key = () {
    print('reading registry on win/x64')
}

; только macOS ARM64 (Apple Silicon)
#{mac-arm64}
neural = () {
    print('Apple Neural Engine available')
}
```

Используя `os.get-arch()`, можно получить текущую архитектуру во время выполнения, а платформенные аннотации включают или исключают код на этапе компиляции.

## Конфигурация компилятора package.noml

Блок `compiler` в `package.noml` управляет поведением компилятора. Значение `version` по соглашению имеет ведущую `v` (например, `"v0.1.0"`); при внутреннем разборе компилятор нечувствителен к префиксу: `"v0.1.0"` и `"0.1.0"` считаются одной и той же версией.

```noml
{
  compiler: {
    version: 'v0.1.0'
    emit: 'js'
  }
}
```

### `emit`

Управляет целевым бэкендом вывода:

| Значение           | Описание                                      |
| ----------- | --------------------------------------- |
| `""` (пустое, по умолчанию) | использовать LLVM-бэкенд для создания нативного исполнимого файла                      |
| `"js"`      | использовать JS-бэкенд для создания JavaScript (стирание типов), LLVM-инструменты не нужны |

После установки `"js"` команда `no build` автоматически использует JS-бэкенд, что эквивалентно `--js` в командной строке. Флаги командной строки имеют более высокий приоритет, чем файл конфигурации.

```noml
; автоматическая генерация JavaScript
compiler: {
  emit: 'js'
}
```

### `anonymous-fn-type`

Управляет, разрешён ли синтаксис анонимных типов функций (например, `cb ()()`). По умолчанию `false` (запрещено), нужно использовать именованный псевдоним типа функции.

### `link-libs`

Задаёт список C-библиотек для компоновки:

```noml
compiler: {
  link-libs: ['crypto', 'ssl']
}
```

## Внедрение переменных на этапе компиляции (-ld)

`no build`, `no run`, `no test` поддерживают внедрение глобальных констант на этапе компиляции через флаги `-ld-KEY=VALUE`. Внедрённые переменные эквиваленты объявлению `KEY = VALUE` в начале исходного кода и могут использоваться в программе напрямую.

### Синтаксис

```bash
no build -ld-KEY=VALUE [ещё -ld...] <file>
```

- После префикса `-ld` сразу следуют имя переменной и значение, разделённые `=`
- Несколько флагов `-ld` можно использовать одновременно
- Сокращение для логических значений: `-ld-DEBUG` (без `=VALUE`) эквивалентно `-ld-DEBUG=true`

### Вывод типа значения

| Форма значения             | Выводимый тип            | Пример                  |
| ---------------- | --------------- | ------------------- |
| Целое               | `i64`           | `-ld-COUNT=42`      |
| Число с плавающей точкой              | `f64`           | `-ld-PI=3.14`       |
| `true` / `false` | `bool`          | `-ld-DEBUG=true`    |
| Другое               | `str` (строковый литерал в одиночных кавычках) | `-ld-VERSION=0.1.2` |

### Пример

```no
; предположим компиляцию с -ld-VERSION=0.1.2 -ld-COUNT=42 -ld-DEBUG=true
print('VERSION:', VERSION); вывод: VERSION: 0.1.2
print('COUNT:', COUNT); вывод: COUNT: 42
print('DEBUG:', DEBUG); вывод: DEBUG: 1 (bool в нативном бэкенде печатается как 1)
```

```bash
; внедрить несколько переменных
no build -ld-VERSION=0.1.2 -ld-COUNT=42 -ld-DEBUG=true main.no

; сокращение для логического значения
no run -ld-RELEASE main.no

; JS-бэкенд тоже поддерживает
no build --js -ld-VERSION=0.1.2 main.no
```

### Связь с объявлениями в исходном коде

Правила взаимодействия переменных, внедрённых через `-ld`, с объявлениями в исходном коде:

- **В исходном коде уже есть объявление с таким именем**: внедрённое значение **замещает на месте** значение этой переменной в исходном коде. Частый шаблон — объявить в исходном коде переменную-заполнитель (например, `VERSION = ''`), а при сборке присвоить ей значение через `-ld-VERSION=0.1.2`.
- **В исходном коде переменной нет**: внедрённая переменная добавляется в самое начало AST как новое объявление глобальной константы и участвует во всех последующих проходах компиляции (вывод типов, проверка, объединение модулей, codegen).
- **Когда внедрения нет**: объявления в исходном коде остаются без изменений.

```no
; объявить переменную-заполнитель в исходном коде
VERSION = ''
COUNT = 0

print('VERSION:', VERSION)
print('COUNT:', COUNT)

; no build -ld-VERSION=0.1.2 main.no
; вывод: VERSION: 0.1.2  (внедрённое значение перекрыло '' из исходного кода)
;       COUNT: 0        (не внедрено, сохранено значение из исходного кода)
```
