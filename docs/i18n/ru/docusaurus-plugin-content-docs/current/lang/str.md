# Строки

Строки Nolang (`str`) — это выделенная в куче последовательность байт, поддерживающая различные операторы и методы.

## Внутреннее представление и публичный API

Дескриптор `str` (`%str-long`) на 64-битных платформах занимает **16 байт**:

```llvm
%str-long = type { i32, i32, i8* }   ; u32 len, u32 cap, data
```

| Поле | Внутренний тип | Публичный тип | Описание |
|---|---|---|---|
| `len` | `u32` (LLVM `i32`) | `i64` | логическая длина в байтах; `s.len-bytes()`, `len(s)`, `s._len()` |
| `cap` | `u32` (LLVM `i32`) | `i64` | физическая ёмкость (только для str-long); `s.cap()`, `s._cap()` |
| `data` | `i8*` | `[]byte` / `*byte` | указатель на буфер в куче |

Внутреннее сужение `len` / `cap` до `u32` сделано, чтобы уменьшить дескриптор с 24 до 16 байт (`i32` + `i32` + 8-байтовый выровненный указатель). **Публичный API по-прежнему полностью основан на `i64`**: при чтении на границе выполняется `zext i32 -> i64`, при записи — `trunc i64 -> i32`. Стандартной библиотеке и пользовательскому коду не нужно (и не следует) трогать этот слой преобразования; сигнатуры `s.len-bytes()`, `s.len()`, `s.cap()`, `s._len()` / `s._cap()` / `s._set-len()` / `s._set-cap()` остаются `i64`.

> ⚠️ Внутренние счётчики имеют тип `u32`, поэтому максимальная длина/ёмкость одной `str` составляет 4 ГиБ (`4294967295`). Переданное значение `i64`, превышающее его, будет усечено на границе; обычная обработка строк не затрагивается, но перед предварительным выделением огромного буфера следует проверить это самостоятельно.
>
> `txt` **не затрагивает это изменение**: он по-прежнему представляет собой фиксированные 256 байт `{ [255 x i8] data, i8 len }`, поля `cap` нет, длина занимает 1 байт.

## Операторы строк

### Конкатенация (`-`)

Для конкатенации строк используется оператор `-`:

```no
; конкатенация литералов
s = 'Hello' - ' ' - 'World'

; конкатенация с переменной
greeting = 'Hello, ' - name
```

### Повторение (`*`)

Для повторения строки используется оператор `*`:

```no
s = 'Hello' * 3
```

### Сравнение (`==` / `!=` / `str.compare`)

`str` **реализует только сравнение на равенство**: `==` / `!=` идут через runtime-функцию `@str_eq`, многосимвольные строки полностью допустимы.

Операторы отношения (<code>&lt;</code> `>` <code>&lt;=</code> `>=`) **не имеют семантики лексикографического сравнения строк**, их использование со строками — ошибка компиляции:

- **Допустимо**: **односимвольный** строковый литерал `'a'`, неявно рассматриваемый как `char` (кодовая точка); можно сравнивать с другим односимвольным литералом или с `char` (`"a"`).
- **Ошибка**: многосимвольные строки — `'ab'`, переменная `str`, вызов, возвращающий `str` (раньше **молча возвращали false**).

Когда нужна лексикографическая сортировка, используйте `str.compare(b)`:

```no
s = 'abc'
b = 'abd'
c = s.compare(b); -1 (s < b) / 0 (равны) / 1 (s > b)

'a' <= 'z'; true — односимвольная строка неявно char
ch >= 'a'; ch — char, допустимо
s < b; ошибка компиляции: многосимвольная строка
s.compare(b) < 0; правильная запись
```

## Индексация и срезы

**Индексация**: выводимый тип `s[i]` — **`?char`** (кодовая точка Unicode), а не `byte` — при выходе за границы возвращается `err` (`code.index-out`), в пределах — `ok(кодовая точка)` (единый набор правил, как у целочисленных `+ - * / %`). Для строк с многобайтовыми символами `s[i]` декодирует UTF-8 от начала строки вперёд, отсчитывая i-ю кодовую точку (см. замечание о производительности ниже).

```no
#{fmt-skip}
s = 'Hello World'
c = s[0]: { ok -> it  -> _ }   ; кодовая точка 'H' (?char нужно явно распаковать, пустая ветка даёт '\0')
```

> Есть три способа «потратить» `?char` (**`#{index-out=DEF}` упразднён и удалён в D11**, оставшиеся упоминания — ошибка компиляции;
> нет и краткого пути «явно привести plain обратно к plain», `c char = s[i]` тоже требует явного потребления):
> **распаковка через match** (`x = s[i]: { ok -> it, -> _ }`, пустая ветка даёт нулевое значение `char` — `'\0'`),
> **запись через place-match** (`s[i]: { ok -> it = x, -> _ }`) или **сокращённая передача вверх `?=`** (у функции есть результирующий параметр `?T`
> или оператор находится внутри тела блочного match). Подробности и примеры — в разделе syntax · «Безопасная индексация».

**Срезы**: `s[a..b]` возвращает **представление** (view) базовой строки, тип по-прежнему **`str`** (память разделяется, копирования нет). Индексы срезов — **позиции кодовых точек**, как и у `s[i]`:

```no
sub = s[6..]; 'World'
sub = s[6..11]; 'World'
sub = s[0..5); 'Hello' (левая граница включительная, правая — исключительная)
```

> Индексы срезов — **позиции кодовых точек**, а не байтовые смещения. Если нужен срез по байтовым смещениям (например, для обхода вместе с `s.byte(i)`), используйте `s.slice-bytes(start, end)`.

```no
; длина
n = s.len(); число кодовых точек (число символов Unicode)
n = s.count(); то же (старое имя метода, ещё работает)
n = s.len-bytes(); длина в байтах (число байт UTF-8)
; внимание: голое s.len (поле структуры) больше не поддерживается, чтение и запись дают ошибку; используйте s.len() / s.len-bytes()
```

### Неявное преобразование (char → str)

`char` можно **неявно преобразовать** в `str`: кодовая точка кодируется в UTF-8 и получается новая строка. Поэтому все следующие записи допустимы, **вызывать `char.to-str()` вручную не нужно**:

```no
s = 'héllo'; 'h' 'é' 'l' 'l' 'o' (é — многобайтовый)

; 1) char из s[i] напрямую присваивается переменной str → неявно превращается в односимвольную строку
a str = s[0]; 'h'

; 2) результат среза уже имеет тип str, можно присваивать напрямую
b str = s[0..1]; 'hé' (индексы 0..1, обе границы включительные)

; 3) char в конкатенации строк (-) неявно превращается в str
msg = 'first: ' - s[0]; 'first: h'

; 4) char при сравнении со str неявно превращается в str
ok = s[0] == 'h'; true
```

> **`'...'` — это литерал `str`, а `"..."` — литерал `char`** — даже если `'x'` содержит всего одну кодовую точку, это всё равно `str`. Поэтому когда **обе стороны** `+` / `-` — литералы (`'...'` с `"..."`), срабатывает описанное выше неявное преобразование, и результат — **конкатенация**, а не целочисленная операция:
>
> ```no
> 'x' - "a"                ; "xa" (конкатенация, а не 120-97 = 23)
> "a" + 'x'                ; "ax"
> 'xy' + "a"               ; "xya"
> ```
>
> Стоит только одной стороне **не быть литералом** (переменная char, `s[i]`, целое число) — односимвольный `'...'` участвует в целочисленной операции **как байт** — это намеренное поведение, благодаря которому работает идиома получения значения цифрового символа:
>
> ```no
> c char = "5"
> n = c - '0'              ; 5 (вычитание байтов, а не "50")
> m = 'A' + 1              ; 66
> "z" - "a"                ; 25 (обе стороны — литералы char, вычитание char)
> 'x' - c                  ; 23 (c — переменная → байтовая операция)
> ```
>
> И наоборот, вырождение в байт происходит **только когда на другой стороне целое или символ**. Если на другой стороне значение типа `bool`, `f64`, структура — то есть **не имеющее байтовой семантики** — `'...'` остаётся строкой, и всё выражение — **конкатенация**, а другая сторона визуализируется через `to-str`:
>
> ```no
> b = true
> 'x' - b                  ; "xtrue" (не 120 - 1 = 119)
> 'x' - 1.5                ; "x1.5"
> 'x' - 'y'                ; "xy" (обе стороны — строковые литералы)
> ```
>
> Поэтому `'x' - b` можно присвоить в `str`: `s str = 'x' - b` даёт `"xtrue"`; а `s str = 'x' - 1` по-прежнему будет отклонено, потому что это байтовая операция (результат — число).

> Неявное преобразование кодирует в `str` только **одну кодовую точку**. Если нужно числовое значение, используйте сам `char` (например, `print(c)` выведет десятичное значение кодовой точки); если нужно явное преобразование, можно использовать `c.to-str()` (эквивалентно неявному).
>
> `char` представляет одну скалярную кодовую точку Unicode, базовый тип хранения — **`i32`** (допустимый диапазон `0 ..= 0x10FFFF`).
>
> `char` **может нормально участвовать в целочисленных операциях** (например, `z = a + 25`, `u = ch - 32`), вычисления идут по значению кодовой точки в ширине i32; в отличие от целочисленного семейства, он не возвращает по умолчанию `option<int>`, поэтому не вызывает ошибки компиляции «необработанное целочисленное переполнение».
>
> **Способ визуализации**: при преобразовании `char` в текст всегда выводится **десятичное значение кодовой точки** (`"A"` → `65`, `"é"` → `233`),
> и результаты `print(c)` и интерполяции строкой `print('{c}')` **должны совпадать**. Арифметика char считается как **знаковый i32**,
> поэтому `"x" - "y"` даёт `-1`, и оба пути выводят `-1` (ни одна из сторон не выведет `4294967295`).
> Допустимая кодовая точка всегда лежит в `0 ..= 0x10FFFF` (31-й бит равен 0), знаковое и беззнаковое расширение там эквивалентны,
> поэтому это правило влияет только на отрицательные значения, полученные при выходе char-арифметики за границы. Если нужен **сам символ**, а не число, используйте
> `c.to-str()` (`"A".to-str()` → `"A"`) — это другая операция.

## Оптимизация ASCII и советы по производительности

Индекс `s[i]` у `str`/`txt` берёт **i-ю кодовую точку (символ Unicode)**, а не i-й байт. Поэтому для строк, которые могут содержать многобайтовые символы UTF-8 (например, китайский, emoji, `é`), каждый `s[i]` должен проходить вперёд по UTF-8 от начала строки, пока не будет сосчитана i-я кодовая точка, — сложность **O(n)**.

Когда компилятор может **доказать**, что строка состоит исключительно из ASCII-символов (кодовые точки 0–127), каждый байт в точности равен одному символу, и `s[i]` напрямую адресует байт в буфере, вырождаясь в **O(1)**. Компилятор доказывает чистый ASCII по следующим правилам:

- явная аннотация: аннотация `#{ascii}` при объявлении или присваивании;
- присваивание ASCII-строкового литерала (например, `'hello'`);
- распространение через идентификатор: `b = a`, если `a` уже доказано как ASCII, то и `b` таков же;
- обе стороны конкатенации (`-`) доказаны как ASCII.

```no
; ASCII-литерал → компилятор доказывает чистый ASCII, s[i] — O(1)
name = 'hello'
c = name[1]; O(1), берём байт 'e'

; есть многобайтовый символ → доказать ASCII нельзя, s[i] — O(n) обход кодовых точек
s = 'héllo'
c = s[1]; O(n), берём 1-ю кодовую точку 'é' (а не байт)
```

### Предупреждение о производительности (LSP / `no vet`)

Когда вы **в цикле вручную перебираете по индексу кодовых точек** строку `str`/`txt`, для которой не доказано, что она ASCII (то есть записи вроде `for i <- [0..s.count()): { s[i] }`, где символы берутся по индексу кодовой точки один за другим), `no vet` и LSP редактора выдают **статическое предупреждение уровня WARNING** (синтаксис не запрещается, это лишь подсказка). Такая запись заставляет каждый `s[i]` проходить вперёд по UTF-8 от начала строки ради i-й кодовой точки, и весь цикл вырождается в **O(n²)**.

Одиночный `s[i]` (например, `s[5]`, всего O(n) один раз) **не** вызывает предупреждения; прямой обход `for c <- s` по символам тоже **не** вызывает предупреждения (см. ниже).

Рекомендуется вместо этого использовать более быстрые способы:

- если нужно перебрать каждый символ, используйте прямой проход вперёд `for c <- s` — это предпочтительная однопроходная запись O(n), избегающая O(n²) от повторных `s[i]`. Компилятор продвигается по **кодовым точкам UTF-8 (символам Unicode)**, каждый раз помещая декодированное значение кодовой точки в переменную цикла `c`; семантика эквивалентна `for c <- s.to-chars()`:
  ```no
  c <- s: {
      ; c — текущая кодовая точка, тип char (уже декодирована из UTF-8, не байт)
  }
  ```
- если нужен доступ именно к байтам (например, кодирование/декодирование, хэширование, memcmp), используйте «аварийный люк» `s.byte(i)` — он всегда напрямую адресует i-й байт, **всегда O(1)**, и не заходит в тело std-функции:
  ```no
  b = s.byte(0); берём 0-й байт, тип ?byte, O(1)
  out = 0
  b: {
      ok -> {
          out = it; в пределах: ok(byte)
      }

      -> {
          out = 0; вне пределов: nil (пустая ветка синтезирует нулевое значение)
      }
  }
  ```
  > Результат `s.byte(i)` — **`?byte`** (с 2026-10-21): раньше чтение голого байта не проверяло границы,
  > выход за границы был неопределённым поведением. Теперь вне границ возвращается `nil` — обратите внимание, что это **отличается** от индексации контейнеров `arr[i]` / `s[i]`, где вне границ возвращается `err`
  > (`code.index-out`): `s.byte(i)` — это побайтовый «аварийный люк», и выход за границы здесь означает лишь «такого байта нет», а не ошибку.
  > (см. design/option-unified.md §3.1, пункт 5). Поэтому `b i64 = s.byte(0)` даёт
  > `15w45dqk` — явная аннотация plain вкупе с option-вызовом является молчаливой распаковкой и считается жёсткой ошибкой компиляции;
  > используйте `?=`, двухступенчатый match (`b = s.byte(0): { ok -> it, -> _ }`) или `_ =`.
  > У `txt.byte(i)` та же семантика (поле `byte` у `txt` — это длина в байтах).

> Внутри стандартной библиотеки (src/std) весь побайтовый доступ уже переведён на `s.byte(i)`: это кодирование/декодирование UTF-8 (`decode-cp`), сравнение (`compare`/`starts-with`/`ends-with`) в `str.no`/`txt.no`, хэширование, копирование срезов (`slice`/`repeat`/`trim`/`copy`), `to-bytes`/`to-upper`/`to-lower`/`reverse`/`replace-char`/`count`/`index` и др. Поэтому `no vet` больше не нужно пропускать файлы стандартной библиотеки; остальной доступ к элементам `[]byte`/срезов/массивов `x[i]` изначально идёт по элементу (байту), семантика не изменилась и предупреждений не вызывает.

| Запись | Семантика | Сложность | Описание |
|---|---|---|---|
| `s[i]` (ASCII доказано) | i-й байт = i-й символ | O(1) | доказывается автоматически, менять ничего не нужно |
| `s[i]` (ASCII не доказано, в цикле) | i-я кодовая точка | O(n²) — антипаттерн | вызывает предупреждение LSP |
| `s[i]` (ASCII не доказано, вне цикла) | i-я кодовая точка | O(n) один раз | предупреждения нет |
| `s.byte(i)` | i-й байт (`?byte`, вне границ `nil`) | O(1) | побайтовый «аварийный люк» |
| `for c <- s` | по одной кодовой точке | O(n), однопроходный | предпочтительный обход, предупреждения нет |

## Методы строк

```no
#{fmt-skip}
; сравнение
ok = a.eq(b, n)               ; сравнение на равенство (метод)
c = s.compare(b)              ; лексикографическое сравнение

; поиск (index/rindex возвращают «позицию кодовой точки (символа)», как и s[i])
pos = s.index(sub)             ; индекс кодовой точки первого вхождения, -1 если не найдено
pos = s.index-from(sub, k)     ; поиск начиная с k-й кодовой точки
pos = s.rindex(sub)            ; индекс кодовой точки последнего вхождения
pos = s.rindex-from(sub, k)    ; поиск в обратном направлении от k-й кодовой точки
pos = s.last-index(sub)        ; псевдоним rindex
ok  = s.contains(sub)          ; содержит ли
ok  = s.starts-with(sub)       ; проверка префикса
ok  = s.ends-with(sub)         ; проверка суффикса
ok  = s.empty()                ; пуста ли

; обратите внимание: семейство index возвращает «позицию кодовой точки», поэтому s[s.index(sub)] даёт первый символ sub,
;       что согласовано с семантикой индекса по кодовым точкам у s[i]. Например, '日本語'.index('語') == 2, а s[s.index('語')] == кодовая точка '語'.
;       если нужен срез по «позициям кодовых точек», s.slice(start, end) — это семантика кодовых точек (как у s[i]);
;       если нужен срез по «байтовым смещениям» (например, для обхода с s.byte), используйте s.slice-bytes(start, end).
;       внутри str есть побайтовый поиск str.find-byte-from (используется повторно, например, в split).
;       обратите внимание: у типа txt slice/at по-прежнему имеют байтовую семантику (txt — «голый» байтовый буфер), семантика разошлась со str.

; преобразование
out = s.to-upper()             ; upper case
out = s.to-lower()             ; lower case
out = s.trim()                 ; удалить начальные и конечные пробелы
out = s.trim-char(c)           ; удалить указанный символ
out = s.repeat(n)              ; повторить
out = s.reverse()              ; обратить
out = s.slice(start, end)      ; срез (индексы — позиции кодовых точек, как у s[i])
out = s.slice-bytes(b, e)      ; срез (индексы — байтовые смещения, внутреннее использование)
val = s.replace-char(old, new) ; замена символа

; преобразование в другие типы
b = s.to-bytes()               ; в []byte
v = s.to-i64()                 ; в ?i64
v = s.to-f64()                 ; в ?f64
v = s.to-bool()                ; в ?bool

; разделение и соединение
parts = s.split(sep)           ; разделить (возвращает []str)
out = ss.join(sep)             ; соединить []str

; копирование и заполнение
dst = s.copy()                 ; копирование строки
s.fill(val byte)               ; заполнение значением byte
```

## Преобразование строк и чисел

```no
; число в строку (методы)
s = i64.to-str(); i64 в строку
s = f64.to-str(); f64 в строку
s = bool.to-str(); bool в "true"/"false"
s = byte.to-str(); byte в строку
s = char.to-str(); char в строку

; строка в число (возвращает option)
v = s.to-i64(); возвращает ?i64
v = s.to-i32(); возвращает ?i32
v = s.to-u64(); возвращает ?u64
v = s.to-f64(); возвращает ?f64
```

## Запись по индексу запрещена (`str` — 2026-11-11 / `txt` — 2026-11-12)

> **`s[i] = v` — ошибка компиляции `idxwrite`**; bases `with-cap` / `with-len` / `with-cap-len`
> не являются исключениями. **`t[i] = c` у `txt` тоже запрещена** (причины ниже).
>
> Причина для `str`: это единственный источник «записи за пределами уже выделенного буфера» — буфер с len=0 растёт за счёт прямой записи,
> и запись при `i >= cap` выходит за пределы выделенной области. Защита роста `ensureStrLongBuffer` в codegen изначально
> создавалась именно для этого; после запрета прямой записи эта защита стала недостижимой для пользовательского кода и осталась только как защитный код.
>
> Причина для `txt` другая, но «преступление» то же: `t[i] = c` — это **перекодировочная запись по кодовой точке**, длина неявно меняется при записи
> (`i`, равное числу кодовых точек, эквивалентно добавлению в конец, а всё, что выше 255, молча отбрасывается). У txt нет кучи и расширения,
> но «одна запись по индексу украдкой изменила длину» — та же опасность.

Четыре по-прежнему допустимых способа записи:

```no
; ① побайтовое «конструирование»: буфер []byte, в конце весь буфер обратно в str
b []byte = with-cap-len(n, n)
b[0] = 48
b[i] = src.byte(i): {
    ok -> it

    -> 0
}
s = b.slice(0, k).to-str(); можно и b.to-str() (весь буфер)

; ② перезапись «на месте» существующего содержимого: str.fill заполняет все len байт одним значением, длина не меняется
s = 'hello'
s.fill(72); 'HHHHH'

; ③ запись по индексу осталась только как place-match (затвор — «чтение»: при i >= len молча пропускается, без роста и выхода за границы)
s[i]: {
    ok -> it = v
    -> _
}

; ④ чтобы изменить длину: семейство push (явный, аудируемый один вызов)
s.push("中");      добавить по кодовой точке (UTF-8)
s.push-str('de');  добавить по байтам (расширение на месте)
```

> ⚠️ **place-match — это затвор по «кодовой точке», а не по байту.** Его затвор приходит от чтения `s[i]`,
> а чтение по индексу у `str` считает кодовые точки. Поэтому ③ годится только для сценария «одна кодовая точка — одна ячейка»
> в ASCII (uuid ставит дефисы, time пишет цифры, hex-таблица). Чтобы собрать содержимое **побайтно**
> (включая байты `>= 0x80` или любые потенциально не-ASCII исходные строки), нужно ① с `[]byte`:
> на практике после `f = with-len(8)` и последовательной записи place-match значений 224..231 на диск попадают только первые 4 ячейки,
> остальные затвор молча пропускает; именно так обрезаются «не-ASCII имена файлов» в `path.split`.

> **Усечение длины**: голое `s.len = n` больше не поддерживается, используйте срез — `s.slice(0, n)` — это срез по **кодовым точкам**,
> а `s.slice-bytes(0, n)` — срез по байтам. (`b.slice(0, k)` на буфере `[]byte`, разумеется, — байтовый срез.)
>
> **`with-cap(n)` создать str, а затем расти через `push`**: `s str = with-cap(256)` — это буфер с len=0, но уже с ёмкостью,
> первый `push` пишет прямо туда, не вызывая расширения (`push-str` делает realloc только когда `len + длина добавления`
> превышает `cap`, и растёт удвоением). Побайтовое `buf[i] = b` для str по-прежнему запрещено.

### Рост: семейство `push` (2026-11-12)

После запрета прямой записи **изменение длины должно быть явным одним вызовом**:

| Метод | Семантика |
|---|---|
| `s.push(c char)` | добавить одну кодовую точку в кодировке UTF-8 (внутри делегирует `push-str`) |
| `s.push-str(t str)` | добавить строку, копируя **побайтно**, с расширением на месте |

```no
s = 'ab'
s.push("中");      'ab中', len-bytes 5, len 3
s.push-str('de');  'ab中de', len-bytes 7

t = 'zz'
t.push-str(t);     'zzzz'  (самодобавление безопасно: сначала retain источник, затем копировать memmove)

u = ''
u.push-str('');    '' (пустой источник ничего не меняет и не выделяет память)
```

> `push-str` — встроенная функция компилятора (`#{buildin}`, в MIR разворачивается в «расширение на месте + memmove + изменение длины»),
> а не цикл std: одно добавление — O(длина добавления), повторные добавления — амортизированно O(1) (удвоение).
> `push` идёт через кодирование UTF-8, поэтому приращение `len-bytes` равно длине кодировки кодовой точки, а `len` всегда увеличивается на 1.

> **Запись в `txt` тоже запрещена (2026-11-12)**: `t[i] = c` — это **перекодировочная запись на уровне кодовой точки**, длина неявно меняется
> при записи — `i`, равное числу кодовых точек, эквивалентно добавлению в конец, а всё, что превышает 255 байт, молча отбрасывается.
> «Одна запись по индексу украдкой изменила длину» — именно это и должен был устранить запрет; к txt применён тот же подход, что к str. Точки роста длины txt —
> `t.push(c)` / `t.push-str(s)` / `t.push-txt(u)`; изменение значения на месте — через place-match.
> Чтение `t[i]` по-прежнему возвращает кодовую точку `char`, это не изменилось.
>
> Побайтовые «сырые» писатели `str._set-byte` / `txt._set-byte` с 2026-11-11 являются **приватными для std**
> (их вызывают только внутренние `str.fill` / `txt.push` и т. п.), пользовательскому коду они недоступны.
> Когда нужно собрать `txt` по байтам, сначала накопьте `[]byte`, затем скопируйте всё разом через `txt.from-bytes(b)`
> (всё, что превышает 255 байт, автоматически усекается, длина устанавливается по фактическому числу байт).

## Предварительное выделение (встроенный синтаксис)

Три встроенные конструкции `with-cap`, `with-len`, `with-cap-len` позволяют заранее выделить память в куче, чтобы последующие `push` не вызывали повторного расширения:

```no
; with-cap(cap): выделить ёмкость cap, len=0 (индексировать можно после push)
s = with-cap(256); str, len=0, cap=256

; with-len(len): выделить ёмкость len, len=cap (можно сразу читать по индексу)
s = with-len(128); str, len=128, cap=128

; with-cap-len(cap, len): одновременно задать ёмкость и длину, подходит для сценария «зарезервировать место для роста»
s = with-cap-len(512, 64); str, len=64, cap=512
```

| Встроенная конструкция | Параметры | len | cap | Сценарий применения |
|---|---|---|---|---|
| `with-cap(cap)` | 1 | 0 | cap | известен только предел, длина растёт через push |
| `with-len(len)` | 1 | len | len | фиксированная длина, можно сразу читать по индексу |
| `with-cap-len(cap, len)` | 2 | len | cap | известна начальная длина и нужно зарезервировать место для расширения |

> Параметры и возвращаемые значения `s.cap()` / `s.len-bytes()` — все **`i64`** (публичный API не изменился), но внутри дескриптора len / cap хранятся как
> **`u32`**. Вызывающая сторона по-прежнему видит 64-битные значения, преобразование выполняется компилятором на границе дескриптора;
> подробнее — в разделе «Внутреннее представление и публичный API». Такие записи полей, как `s.len = n` / `s.cap = n`, тоже проходят через этот слой,
> поэтому они не перезаписывают соседние поля заголовка.

> ⚠️ **Буфер `str` никогда не допускает прямой записи по индексу** (с 2026-11-11, база `with-cap` больше не является исключением).
> Исключение `idxwrite` для with-cap теперь относится только к **`[]byte` / `[]T` / массивам фиксированной длины**: их буферы с len=0
> по-прежнему растут за счёт `buf[i] = b`, эквивалентной замены у них нет. Для `str` используйте буфер `[]byte` +
> `to-str()` (см. раздел «Запись по индексу запрещена»).
> У `with-len(n)` / `with-cap-len(cap, len)` длина уже установлена, **запись должна идти через place-match
> `buf[i]: { ok -> it = v / -> _ }` или `buf[i] ?= v`** — как и у любого другого контейнера, прямая запись есть
> ошибка компиляции `idxwrite`. (С 2026-11-10 `with-len` больше не является исключением.)

> **Вывод типа**: результат всех трёх встроенных конструкций выводится из левой части присваивания; они применимы к `str` или срезам `[]T`.
