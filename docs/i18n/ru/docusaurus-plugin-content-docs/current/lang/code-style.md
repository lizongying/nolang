# Стиль кода

## Завершающий перевод строки в конце файла (Trailing Newline / EOF)

Каждый **непустой** исходный файл `.no` **должен заканчиваться ровно одним завершающим переводом строки** (то есть в конце файла должен быть один перевод строки).

- У файла **нет** завершающего перевода строки → добавьте его.
- В конце файла **несколько** пустых строк → слейте их в один завершающий перевод строки.
- **Пустой файл** (0 байт) → оставить без изменений.

Исключённые каталоги: `dist/`, `vscode-nolang/`, `node_modules/`.

Обоснование: единообразный завершающий перевод строки в конце файла не даёт `git diff` показывать «no newline at end of file», делает различия чище, а цепочки инструментов и конкатенацию предсказуемыми.

### Автоматическое применение (встроено в инструментарий)

Это правило применяется **автоматически** самим инструментарием — отдельного скрипта нет:

- **`no fmt`**: подкоманда `fmt` (`src/cmd/no/main.go`) форматирует файлы на месте и вызывает `fmt.FormatFile`, что гарантирует ровно один завершающий перевод строки.
- **Форматирование при сохранении в LSP / `textDocument/formatting`**: `formatNolangCode` → `fmt.FormatFile` в `src/lsp/server.go` автоматически добавляет или объединяет перевод строки в конце EOF при сохранении или форматировании файла `.no` в редакторе.

Реализация находится в `src/fmt/formatter.go`:

- `FormatFile(code)` форматирует весь файл и вызывает `ensureTrailingNewline`, который удаляет все завершающие `\r` / `\n` (совместимо с CRLF и несколькими пустыми строками), затем добавляет один `\n`. Пустой или неразбираемый ввод возвращается без изменений, чтобы форматтер никогда не испортил файл, который он не понимает.
- `Format(code)` — чистая функция форматирования фрагмента (без завершающего перевода строки), используется главным образом в модульных тестах; при записи реального исходного файла используйте `FormatFile`.

## Автоматическая упорядочка операторов импорта (дедупликация / удаление std-импортов без псевдонима / сортировка)

`no fmt` (и форматирование при сохранении в LSP) автоматически нормализует **непрерывный блок импортов в начале файла** (`# path[.fn] [alias]`); реализация находится в `src/fmt/imports.go`:

1. **Дедупликация**: полностью совпадающие (путь, имя функции и псевдоним совпадают побайтово) импорты сводятся к первому вхождению.
2. **Автоматическое удаление всех чистых std-импортов модулей без псевдонима**: модули стандартной библиотеки могут загружаться неявно (см. [Префиксы при вызове между модулями](./module)) — `# std/<module>` без псевдонима и без `.функции` (например, `# std/noml`, `# std/math`, `# std/database/sql`) не связывает имя и избыточен; форматтер его удаляет. Три исключения сохраняют его:
   - написан **псевдоним** (`# std/noml n`) или **импорт функции** (`# std/fmt.sprintf fm`) — это намеренное связывание имени;
   - строка импорта несёт **комментарий** или прикреплённую аннотацию `#{...}` — написанное пользователем содержимое не удаляется молча.
3. **Автоматическая сортировка**: импорты стабильно сортируются лексикографически по пути → имени функции → псевдониму.

Консервативная граница: если любой импорт в блоке несёт комментарий (отдельной строкой выше или в конце той же строки) или прикреплённую аннотацию `#{...}` (например, политику нативной привязки `#{bind=ffi}`), весь блок **сохраняет исходный порядок и ничего не удаляется** — сортировка разрушила бы соответствие между комментариями и операторами, а удаление унесло бы комментарий вместе с ними. В этом случае полностью идентичные записи без прикреплённого содержимого всё равно дедуплицируются.

Блоки импортов, встречающиеся где-либо ещё, а не в начале файла (после кода), остаются без изменений.

```no
#{fmt-skip}
; до форматирования                  ; после форматирования
# std/vec                            # aaa/lib
# std/noml                           # std/io
# std/io                             # std/vec
# std/noml n
# aaa/lib        ;→  std-импорты без псевдонима (# std/noml, # std/vec, # std/io) удалены;
                    ;   # std/noml n с псевдонимом сохранён; остальное отсортировано по алфавиту
```

## Маркеры комментариев

Nolang поддерживает два маркера **однострочных комментариев** и один маркер **многострочного (блочного) комментария** со следующей семантикой:

- `//` — традиционный однострочный маркер (комментарий до конца строки)
- `;` — альтернативный однострочный маркер (реализован 2026-07-17, комментарий до конца строки)
- `;; ... ;;` — многострочный (блочный) комментарий (реализован 2026-07-18, симметричные разделители; если не закрыт, комментарий идёт до конца файла)

```no
#{fmt-skip}
// это комментарий
; это тоже комментарий, та же семантика
x = 1 ; встроенный комментарий, до конца строки

;;
   это многострочный (блочный) комментарий
   он может занимать несколько строк
   заканчивается ;; ;;
y = 2 ;; встроенный блочный комментарий ;;
```

**Границы блока**: `;;` открывает и `;;` закрывает; всё между ними (включая переводы строк) является содержимым комментария. Одиночный `;` внутри не закрывает блок — это делает только `;;`. Если закрывающий `;;` не найден, комментарий идёт от открывающего `;;` до самого конца файла. Открывающий `;;` переключает в многострочный режим только тогда, когда **после него на этой строке не остаётся ничего, кроме пробелов**, — если после `;;` на той же строке есть текст, это обычный однострочный комментарий (например, `;; пояснение` комментирует только эту строку, следующая строка всё ещё код). Закрывающий разделитель работает так же: после `;;` могут быть только пробелы.

**Форматтер сохраняет исходный маркер**: `no fmt` никогда не меняет маркеры комментариев — `;` остаётся `;`, `//` остаётся `//`, `;; ... ;;` остаётся `;; ... ;;`. Форматтер запоминает исходный маркер через `Comment.Marker` и выводит его дословно; содержимое блочного комментария (включая внутренние переводы строк) также сохраняется как есть, поэтому форматирование идемпотентно.

**Безопасная область**: когда `;` / `;;` встречаются внутри строковых литералов (например, `'text/plain; charset=utf-8'`, `index-from(';', pos)`) или внутри комментариев `//`, сканеры строк и комментариев лексера поглощают их первыми, поэтому они никогда не воспринимаются как маркеры комментария.

**Замечание о `cond -> X; Y`**: теперь, когда `;` — это комментарий, `cond -> X; Y` разбирается как «выполнить `cond -> X` (вычислить X и отбросить)» плюс встроенный комментарий `; Y` — **X не получает значения**. Правильная запись: `cond -> X = Y` (устоявшийся шаблон в stdlib, см. `arr.no`, `uuid.no`, `path.no`, `err.no`, `assert.no`). Если в исходном коде встречается `cond -> X; Y`, в первую очередь исправьте его на `cond -> X = Y`.

**Запрещена запись нескольких операторов в одной строке**: `;` — лишь маркер комментария и не может соединять несколько операторов в одной строке; запятая `,` тоже не соединяет операторы. Каждый оператор внутри блока `{ ... }` должен занимать собственную строку. Сжатие блока в одну строку — самая опасная ошибка:

```no
#{fmt-skip}
; ❌ Неправильно: `; return }` целиком становится комментарием, и `}` блока исчезает
cond -> { print('X'); return }
```

```no
; ✅ Правильно: каждый оператор занимает отдельную строку
cond -> {
    print('X')
    return
}
```

`cond -> { print('X'); return }` фактически оставляет только `cond -> { print('X')`: блок никогда не закрывается, и все операторы после « осиротевшей» `}` (обычно весь остаток тела функции, а иногда и последующие функции уровня модуля) поглощаются. Компилятор может даже не сообщить об ошибке, а диагностика может указывать далеко от настоящего места ошибки.

## Булевы литералы и упрощение `== true` / `== false` (реализовано 2026-09-24)

Помимо ключевых слов `true` / `false`, Nolang принимает два **сокращённых булевых литерала**:

- `!!` — самостоятельный литерал, эквивалентный `true`.
- `!` — самостоятельный литерал, эквивалентный `false` (только когда следующий за `!` токен не может начать операнд; если после `!` идёт `перевод строки` / `;` / конец файла / `)` / `}` / `]` / `->`, разбирается как `false`).

> Внимание: речь идёт о `!!` / `!` в **позиции выражения**, а не о формах в позиции цикла: `!! { }` (всегда выполняется) и `! { }` (не выполняется).

Обе сокращённые формы превращаются в обычный `BooleanLiteral` уже **на этапе разбора**, поэтому четыре формы `f == true`, `f == !!`, `f == false`, `f == !` синтаксически полностью эквивалентны и проходят через одну и ту же логику.

Правила обработки булевых значений в `no fmt` (реализовано в `src/fmt/expr.go`):

- **Самостоятельные литералы приводятся к записи ключевым словом**: `c = !!` → `c = true`, `c = !` → `c = false`.
- **Известное упрощается, неизвестное — нет**: когда одна из сторон `==` / `!=`
  является булевым литералом, а другой операнд **можно доказать как значение bool**,
  форматтер выдаёт кратчайшую форму. Все четыре конвейера используют одни и те же правила сбора сигнатур (`collectModuleSignatures`: встроенные таблицы std, локальные модули, доступные через `use` / `#`, и EnumVariants) и один и тот же контракт внедрения `SemRebuildConfig.Apply`; различается только поставщик таблиц: `no fmt` / LSP используют `build.FmtSigLoader`, а `no build` / `no vet` по-прежнему идут через `preloadModuleSignatures` + `astParseConfig` (эти два загрузчика ещё не объединены). `no fmt` внедряет таблицы перед «свежим» разбором `SkipLowering`; LSP внедряет их в `ParseDocument` и публикует `parseSnapshot`, поэтому форматирование при сохранении повторно использует глубокую копию этого «сахарного» AST (`fmt.CloneProgramForFormat`) и при настройках по умолчанию больше не выполняет повторный разбор. Доказательством служит один из трёх источников:

  1. Явная аннотация типа: `b bool = true`, параметр `(b bool)`;
  2. Присваивание булева литерала: `flag = true` / `flag = false`;
  3. Вызов функции, объявленный результат которой — `bool`: **определённой в этом же файле** (например, `bytes-eq = ... (eq bool)`) или функции std / локального модуля, найденной в таблице сигнатур (например, `args.has-flag`, локальная `helper.is-ok`). Вызов метода у переменной-получателя (`s.starts-with('a')`) разрешается через уже выведенный в Sem тип получателя (`s: str`) по `str.starts-with`; если тип не выведен или одна и та же переменная в разных областях видимости выведена как разные типы, значение остаётся неизвестным (намеренно не делается «догадка об уникальности имени метода по всему миру», чтобы не принять `?bool` за чистый bool). Если таблица сигнатур не позволяет определить тип результата, значение тоже остаётся неизвестным.

  | Исходная запись (`b` ниже — «известная» переменная) | После форматирования |
  | ------------------------------------------ | -------- |
  | `b == true` / `b == !!`                    | `b`      |
  | `b == false` / `b == !`                    | `! b`    |
  | `b != true` / `b != !!`                    | `! b`    |
  | `b != false` / `b != !`                    | `b`      |
  | `true == b` (литерал слева)                | `b`      |

  `!=` просто инвертирует полярность; `true == false` (обе стороны — литералы) остаётся без изменений. Голое имя без признаков bool, такое как `f == true`, также остаётся без изменений.
- **`?T` и любой неизвестный операнд сохраняют сравнение**: option (`?T`), межмодульные вызовы, тип результата которых не найден в таблице сигнатур, голые имена без присваивания, обращения через точку с невыведенным типом получателя, вызовы и результаты вычислений — все они сохраняют `== true` / `== false`. Свёртка такого выражения в голое `x` / `! x` в качестве условия управления вызывает аварийный сбой кодогенерации MIR «option-as-i1» — именно по этой причине v0.3.3 целиком откатила это правило (`8a8ecb59`). 2026-11-15 правило восстановили в варианте «упрощаем только при положительном доказательстве», а не старой логикой «раз `?T` не видно, значит это значение». В тот же день `no fmt` и LSP получили межмодульные сигнатуры, поэтому option-результаты вроде `fs.write-str(...)` (`?bool`) стали **видимыми** и отсекаются жёсткой option-заслонкой, а не за счёт «невидимости» типа. Option — это **независимая жёсткая заслонка** (`boolOperandIsOptionTyped`), которая проверяется раньше доказательства булева значения, поэтому сравнение не упрощается независимо от того, сохранилась ли аннотация в исходном файле: и `ok ?bool = fs.write-str(...)`, и `ok = fs.write-str(...)` сохраняют сравнение. Удаление избыточных аннотаций типа в соответствии с существующим правилом (`fixRedundantTypeSource`) — это **правильное поведение**; не отключайте это удаление ради сохранения определения option. Регрессионные тесты: `src/fmt/bool_comparison_test.go`, `src/fmt/signatures_test.go`, `src/lsp/fmt_gate_test.go`.
- **Действует и внутри ветвей `->` / отдельными условиями if-then** (для известных переменных): `b == ! -> return` → `! b -> return`.
- **Безопасность приоритета**: отрицание записывается как `! ` (с одним пробелом) в соответствии с существующим соглашением для префиксных операторов, что обеспечивает идемпотентность `no fmt`. Сегодня все доказуемые операнды — идентификаторы, поэтому `! ` не может пересвязаться; реализация всё равно сохраняет защиту скобками для неатомарных операндов (`! (a + b)`, а не `! a + b`) на случай, если позже правила доказательства будут расширены.

## Отложенная нулевая инициализация возвращаемых значений (Deferred Zero-Init for Return Values)

Именованные результирующие параметры (out-параметры) функций Nolang используют стратегию **отложенной нулевой инициализации**: пролог функции **не** выполняет нулевую инициализацию out-параметров. Вместо этого компилятор отслеживает с помощью битовой карты `%__ret_init_bitmap`, был ли каждый out-параметр явно проинициализирован в теле функции. При возврате из функции любой out-параметр, который **не был явно проинициализирован**, автоматически получает store нулевого значения соответствующего типа (целое → `0`, str-long → `zeroinitializer`, struct → `zeroinitializer`, option → `nil`). Этот механизм симметричен существующему механизму отложенного освобождения `%__move_bitmap`.

### Почему именно такая конструкция

- **Производительность**: пролог не выдаёт `store zeroinitializer` для каждого out-параметра только для того, чтобы его тут же перезаписал последующее присваивание, — это чисто избыточный store. Отложенная стратегия записывает ноль только тогда, когда «действительно не было присваивания».
- **Читаемость**: не нужно писать в начале функции шаблонный код предварительного обнуления вроде `found = false` / `result = nil`; читатель сразу видит намерение «значение присваивается только на успешном пути».
- **Единообразие**: используется тот же шаблон отслеживания через битовую карту, что и механизм отложенного освобождения `%__move_bitmap`, — внутренняя реализация компилятора симметрична.

### Рекомендуемый стиль

Не выполняйте преждевременное обнуление out-параметров в начале функции — компилятор автоматически подставит ноль при возврате. Пишите только присваивания «успешного пути»:

```no
; Хорошо: не пишем преждевременного обнуления, компилятор справляется сам
hashmap-str-tmpl.contains = (key str) (found bool) {
    val ?v = .get(key)
    val: {
        ok -> found = true

        err -> {
        }

        nil -> {
        }
    }
}
```

### Антипаттерн (избегать)

Не пишите избыточное преждевременное обнуление — это мёртвый store, который будет перезаписан последующим присваиванием:

```no
#{fmt-skip}
; Плохо: избыточное преждевременное обнуление
hashmap-str-tmpl.contains = (key str) (found bool) {
    found = false              ; избыточно — компилятор автоматически подставит ноль при возврате
    val ?v = .get(key)
    val: {
        ok -> found = true
        err -> {}
        nil -> {}
    }
}
```

### Option по умолчанию равен nil

Для out-параметров типа `?T` (option) компилятор при подстановке нуля напрямую записывает `nil` (tag=1, data=0), что эквивалентно `result = nil`. Поэтому пути вроде «не найдено / пустое множество / EOF» требуют только голого `return`, и не нужно писать `result = nil` в исходном коде:

```no
#{fmt-skip}
; Хорошо: путь «не найдено» использует голый return, компилятор сам подставит result = nil
hashmap-str-tmpl.get = (key str) (result ?v) {
    .size == 0 -> return        ; компилятор подставит result = nil
    ...
    ; fall-through: компилятор подставит result = nil
}
```

### Подсказка для отладки

Если функция вернула неожиданное нулевое значение (например, `found` должен быть `true`, а получено `false`, или `result` должен иметь значение, а получил `nil`), проверьте, **все ли пути, которые должны вернуть ненулевое значение**, явно присваивают out-параметр в теле функции. Компилятор не догадывается о намерениях — он лишь подставляет ноль для непроинициализированных out-параметров. См. подсказку по отладке в `.agents/skills/nolang-debug/SKILL.md`.

## Прямое связывание выходного слота с уже существующей переменной (без промежуточных переменных)

**Рекомендуемый стиль**: при написании нового кода, если результат вызова нужно просто применить для обновления уже существующей переменной, свяжите выходной слот **напрямую с этой переменной**, а не создавайте одноразовую промежуточную переменную. Это особенно часто встречается при нескольких выходных значениях, когда получатель сам является обновляемым состоянием.

```no
; ✅ Рекомендуется: остаток записывается прямо в r (r одновременно — получатель метода)
qsq, r = r.div-mod(modulus)
```

```no
; ❌ Избегать: msq записывается всего один раз и больше нигде не используется
qsq, msq = r.div-mod(modulus)
r = msq
```

- Неиспользуемые выходные значения занимайте `_` : `_, r = r.div-mod(modulus)` не вводит даже новой переменной.
- Совпадение input-only ссылки и выходного слота, указывающих на один объект, допустимо (правило алиасирования); `r = r._mul(r)` в `src/std/bigint.no` — тот же случай обновления на месте, применимо и к одному выходному значению.
- Это рекомендация для **нового кода**, а не указание к рефакторингу: существующий корректный код не переписывайте ради стиля (см. «Золотое правило»).
- Полную семантику, практические результаты и область применения см. в [Справочнике по языку: определение функций](./syntax).

## Блоки кода Markdown (`no fmt -md`)

`no fmt -md` форматирует только содержимое **внутри** ограждений ```` ```no ```` / ```` ```nolang ````; строки ограждений и остальной Markdown сохраняются побайтово. Содержимое блока разбирается как исходный код Nolang; если разобрать его нельзя, блок остаётся без изменений и сообщается номер строки, так что форматирование никогда не испортит файл, который оно не понимает. (`-md` и `-fix` взаимно исключают друг друга — `-md` только форматирует.)

### Правильные и неправильные примеры — в отдельных блоках

Если в одном блоке написать и «правильный вариант», и «неправильный», парсер воспримет их как одну программу: правильная половина лишится проверки `no fmt`, а неправильную половина форматтер может «починить» так, что ошибка станет незаметной. Поэтому:

- **правильный пример** — в отдельном блоке без аннотации, чтобы `no fmt` его отформатировал и проверил;
- **неправильный пример** — в отдельном блоке, первой строкой которого стоит `#{fmt-skip}`, чтобы его не проверяли и не изменяли.

```no
; ✅ Правильно: каждый оператор занимает отдельную строку
cond -> {
    print('X')
    return
}
```

```no
#{fmt-skip}
; ❌ Неправильно: всё после `;` — комментарий, и `}` блока исчезает
cond -> { print('X'); return }
```

### Три законных применения `#{fmt-skip}`

1. **Неправильные примеры / контрпримеры** — изначально некорректные программы; форматирование только мешает.
2. **Псевдокод и краткие сводки сигнатур** — фрагменты только «формы», без реализации (например, скелет сигнатуры `f = (a i64) (r i64) { ... }`).
3. **Шпаргалки с выровненными столбцами комментариев** — `no fmt` перепишет `code      ; примечание` как `code; примечание`, а выравнивание столбцов и есть смысл такой таблицы, поэтому её нужно исключить.

### Не добавляйте аннотации только ради предотвращения раскрытия

`no fmt` раскрывает пустой блок `{ }` и однотрочечную ветку `-> { x() }` в несколько строк:

```no
ok = (b bool) (yes bool) {
}

dispatch = (cmd str) {
    cmd == 'a' -> {
        fa()
    }
}
```

Это **каноническая** форма, которую следует принять: только после раскрытия у блока появляется отдельная строка, куда можно вставить последующие операторы, иначе каждое добавление строки начиналось бы с ручного разбиения блока. Точно так же превращение `true -> {}` в `true -> {\n}` не является поводом для отката: `#{fmt-skip}` реально нужен только в трёх случаях выше (контрпримеры, псевдокод, выровненные таблицы).

### Блоки только из комментариев не требуют аннотации

Блок, содержащий только комментарии (обычный способ «закомментировать» правильный вариант), разбирается в **ноль операторов**. `no fmt` воспринимает это как «нечего форматировать», оставляет блок как есть и ничего не сообщает — это не синтаксическая ошибка, а добавление `#{fmt-skip}` лишь скрыло бы этот факт.

### Порядок: сначала аннотация, потом форматирование

`no fmt -md -w` перезаписывает каждый блок, который не исключён. Стоит форматтеру «исправить» неправильный пример — контрпример перестаёт что-либо демонстрировать, а исходная запись безвозвратно теряется. **Сначала добавьте `#{fmt-skip}`, затем запускайте `-w`.**
