# Управление памятью

Nolang — это язык **без GC**; безопасность памяти обеспечивается автоматически вставляемыми компилятором вызовами `free`. В этой статье описаны реализованная модель памяти и семантика владения.

## Основные принципы

### Единственное владение
Каждый буфер `data` в куче имеет **ровно одного владельца**. Владение можно передать через move; после передачи исходный владелец снимает с себя ответственность за free. При `=` между локальными переменными глубокий clone делает обе переменные независимыми владельцами данных.

### Семантика присваивания
`b = a` выбирает одну из следующих семантик в зависимости от контекста:

| Семантика | Условие срабатывания | Поведение |
|------|---------|------|
| **Копирование значения** | Базовые типы (i64/f64/bool и др.) и условие `can_slot_rebind` не выполнено | Прямое копирование значения, данных в куче нет |
| **Перепривязка слота стека** | `b = a` между локальными, `a` — стековый тип (i64/u64/i128/u128/txt) и выполнено `can_slot_rebind` | `g.varAlias[b] = a`: `b` и `a` используют один слот стека, 0 копирований (лучше копирования значения); иначе переход к копированию значения |
| **Глубокий clone** | `b = a` между локальными, `a` — тип, владеющий данными в куче (vec/arr/str/клонируемая структура/**`?str`, `?[]T`**), и после присваивания **всё ещё используется** | malloc новые data + memcpy + рекурсивный clone элементов; `a` и `b` независимо владеют данными, каждый освобождает их при выходе из функции |
| **move (источник мёртв)** | `b = a` между локальными, `a` владеет данными в куче, но после присваивания **больше не используется** | Передача владения без копирования; источник пропускает free. **Наблюдаемо эквивалентно** глубокому clone, экономит одно копирование |
| **move** | Выходной параметр `out = x` | Поверхностное копирование структуры + пометка источника как moved; источник пропускает free |
| **Глубокий clone** | `vec.push(x)` (`x` — тип, владеющий данными в куче) | malloc новые data + memcpy + рекурсивный clone элементов; источник по-прежнему владеет независимыми данными, каждый освобождает их при выходе из функции |

> **Присваивание значения к значению всегда глубокое; нулевое копирование с псевдонимами запрещено.** `b = a` (справа — целая именованная переменная) имеет только два варианта понижения —
> **источник жив ⇒ глубокий clone**, **источник мёртв ⇒ move**; **не допускается** «два имени делят один буфер, но free остаётся один»
> (такое понижение раньше существовало в оптимизации «read-only forward» и было удалено). **Чтение элемента/поля** (`b = a[i]`, `b = a.f`) сохраняет
> семантику **псевдонима-представления (view-alias)** и под это ограничение не попадает.

## move стековых типов (перепривязка слота стека / slot-rebind)

Хотя `i64/u64/i128/u128/txt` — **стековые типы** (значение живёт прямо в слоте alloca, без данных в куче), `b = a` по умолчанию всё равно идёт по пути «копирование значения» (memcpy стекового значения `a` в слот `b`). Чтобы избежать лишних копирований, компилятор выполняет **перепривязку слота стека** для `b = a` стековых типов, удовлетворяющих ограничению **can_slot_rebind**: он устанавливает `g.varAlias[b] = a`, так что `b` и `a` используют один слот стека (0 копирований, лучше копирования значения).

### Ограничение can_slot_rebind (консервативная корректность)
После перепривязки `b` и `a` указывают на один слот стека, поэтому любое последующее чтение `b` у `a` будет читать «хранилище `a`». Чтобы избежать семантических ошибок, перепривязка допускается только когда источник `a` **не имеет ни одной последующей ссылки (ни чтения, ни записи)**; иначе происходит **переход к полному копированию значения** (семантика не меняется, лишь одно лишнее memcpy).

- Безопасность решается статически `computeSlotRebindSafety` (главная функция) / `computeMoveEligibility` (пользовательские функции) через `stmtContainsVarRefAny` / `exprContainsVarRefAny`: сканируются все инструкции после move (включая ветки и обратные рёбра циклов); если источник всё ещё используется каким-либо образом, `slotRebindSafe[stmt] = false` → идём по пути копирования.
- Сканирование ссылок должно перечислять **все AST-узлы, которые могут ссылаться на переменную**, иначе непокрытая ссылка-запись приведёт к небезопасной перепривязке (псевдонимный слот будет испорчен → неверный результат или даже бесконечный цикл). Покрыты: на уровне инструкций `LetStatement` / `ExpressionStatement` / `ForStatement` (вкл. `Init`/`Update`/`Condition`/`CountExpr`/`Body` и **`IterRange` — коллекцию итерации**) / `ReturnStatement` / `MultiAssignStatement` / **`UnwrapAssignStatement` (`?=` распаковка)** / **`BlockStatement` (голый блок)**; на уровне выражений `Identifier` / `AssignExpression` / `Infix` / `Prefix` / `Call` / `Dot` / `Index` / `IfExpression` (вкл. тела ветвей) / `Slice` / `Conditional` / `Grouped` / **`CoExpression` (`co <call>` — spawn корутины, защитно; отключение на всю функцию по-прежнему делает `curHasUnsafeConstruct`)** / **`CastExpression`** / **`RangeExpression`**. Любая новая конструкция, ссылающаяся на переменную, должна добавляться в обе функции сканирования.
- `match` уже развёрнут (desugar) в `IfExpression`; ссылки внутри его ветвей покрываются описанным обходом, поэтому **match не вызывает отключения** (проверено на `tests/match.no` / `tests/option.no`, результат совпадает с базовым).

### Сценарии отключения (всегда переход к копированию значения)
| Условие отключения | Причина |
|---------|------|
| Цель — выходной параметр / глобальная переменная / переменная с типом в куче | Выходные параметры передаются по указателю, глобальные видны во всех функциях, для типов в куче нужен глубокий free; перепривязка нарушает владение |
| Источник — параметр / глобальная переменная | Параметры передаются по ссылке, перепривязка испортит стековый кадр вызывающего |
| **Функции stdlib** (`curIsStdLib`, определяется через `SetStdModules`) | Внутренние привязки псевдонимов в stdlib (например, `it` в fmt, алиасирующий локальную `n`) трудно полностью смоделировать в анализе ссылок |
| **Тело пользовательской функции содержит замыкание (`FunctionLiteral`) или spawn корутины (`RunExpression`)** (`curHasUnsafeConstruct`, рекурсивно сканируется `bodyHasUnsafeConstruct`) | Переменные, захваченные замыканием, вычисляются в «отдельном контексте функции», корутины выполняются в других потоках; время жизни их переменных выходит за пределы однофункциональной области псевдонимов `g.varAlias` текущей функции, и перепривязка испортит общий слот стека |

> Компромисс в дизайне: для замыканий/корутин применяется «отключение на всю функцию», а не «точный расчёт для каждой переменной», поскольку однофункциональный анализ псевдонимов принципиально не может смоделировать разделение хранилища между функциями/потоками. Отключение на всю функцию теряет только оптимизацию (переход к копированию) и никогда не вносит ошибок, что соответствует принципу «консервативной корректности».

### Аннулирование псевдонимов (alias invalidation)
- Когда цель переприсваивается, сначала `delete(g.varAlias, name)` удаляет остаточную старую привязку; иначе общий путь присваивания `varAddr(name)` по-прежнему указывает на старый слот источника и портит его.
- Перепривязка выполняет транзитивное разрешение: по цепочке `g.varAlias` ищется конечный слот-источник (`a → c → …`), чтобы избежать ошибок при нескольких переходах псевдонима; одновременно обновляется `g.varTypes[name]` для согласованности последующих запросов типа.

### Ортогональность с move типов в куче
Перепривязка слота стека действует только на семантике **копирования значения** для `b = a` стековых типов и полностью ортогональна «глубокому clone / move (выходной параметр)» для типов, владеющих данными в куче; путь типов в куче не зависит от `slotRebindSafe`.

### Ссылки на тесты
- `tests/slot-rebind.no`: перепривязка i64/u64, сравнение i128/u128 через `==`, txt через `.len-bytes()`, переход к копированию (`da` переиспользуется → `db`/`dc` копируются), после переприсваивания (`ra`=10), move параметра (`pm_fn`, источник — параметр → копирование), переприсваивание после перепривязки (`rr_fn` → `rr`=99), потребление (`consume(m)` → `cm`=84). Ожидаемый вывод `42 7 1 1 17 5 5 10 100 99 84`.
- `tests/slot-rebind-unsafe.no`: корутина (`awy { co ... }`) захватывает стековую переменную; проверяется, что после отключения перепривязки через `curHasUnsafeConstruct` вывод совпадает с базовым.

### free, вставляемый компилятором
- При выходе из функции: освободить все локальные переменные в куче, не помеченные moved
- Перед переприсваиванием: освободить старое значение
- Поля структур: рекурсивно освободить поля, содержащие данные в куче

## Компоновка типов

| Тип Nolang | Представление в памяти | Поля | Стратегия выделения |
|------------|-----------|------|---------|
| `[]T` (срез) | **16 байт** | **u32 len, u32 cap, i64 data (ptrtoint)** | malloc (куча) |
| `[N]T` (массив фиксированного размера) | N × sizeof(T) | Элементы встроены, **дескриптора len/cap нет** | alloca (стек) или malloc |
| `str` (длинная строка) | **16 байт** | **u32 len, u32 cap, i8\* data** | malloc (куча) |
| `txt` (строка фиксированного размера) | 256 байт | `[255 x i8]` data, i8 len | alloca (стек) |
| `?T` (nullable) | **Зависит от полезной нагрузки**: `{ i8 tag, [K x i64] }` | 1 байт тега + 7 байт заполнения + полезная нагрузка (кратно 8) | alloca (стек); при превышении порога нагрузки хранится указатель в кучу |
| Помеченное перечисление | `{ iN tag, [K x i64] }` | Ширина tag зависит от числа вариантов (начинается с `i8`); нагрузка — union самого широкого варианта | alloca (стек) |
| Структура | Сумма полей | Все поля | alloca (стек) |

**Размер `?T` вычисляется, а не фиксирован**: `?i64` = 16 байт, `?str` = 24, `?txt` = 264; у нагрузки, превышающей
`option-payload-inline-threshold` (по умолчанию 264 = 1 + 7 + 256, минимум 16), используется упаковка в кучу, и весь option
снова занимает 16 байт. Каждый тип нагрузки имеет собственный тип `%option_<key>` (`src/mir/layout.go`), поэтому
«одинаковый тип ⇔ одинаковая компоновка». Нагрузка `err` всегда упаковывается и не занимает место в бюджете нагрузки. Подробнее см.
`docs/docs/lang/syntax.md`〈Nullable-тип (option) и компоновка в памяти〉.

**Ширина tag у помеченного перечисления** зависит от числа вариантов (`<=256` → `i8`, `<=65536` → `i16`, `<2^32` → `i32`,
иначе `i64`); ширина union нагрузки — это «самый широкий вариант», а не сумма всех; поля размещаются с естественным выравниванием,
адресация идёт по **байтовым смещениям**. Если у всех вариантов нет нагрузки, компоновка вырождается в `{ iN }` (от 1 байта).

**Заголовок u32 у `str`**: `%str-long = type { i32, i32, i8* }` (16 байт на 64-битных платформах).
`len` / `cap` внутри имеют тип `u32` (LLVM `i32`), но **все внешние API по-прежнему `i64`**: при чтении `zext i32 -> i64`,
при записи `trunc i64 -> i32`. Сигнатуры `s.len-bytes()`, `s.len()`, `s.cap()`, `s._len()` / `s._cap()` /
`s._set-len()` / `s._set-cap()` и `len(s)` не изменились. Этот рубеж обрабатывается в codegen
единообразно через `strLenI64` / `strCapI64` / `strHeaderLoadI64` / `strHeaderStoreI64` / `strLongFromParts`:
**Нельзя** напрямую выдавать `load i64` / `store i64` для полей 0 / 1 дескриптора: при opaque pointer
верификатор LLVM это не поймает, но одна операция прочитает/запишет 8 байт и изменит заодно соседнее поле заголовка (проверено:
`s.len-bytes()` однажды вернул `len | cap<<32`).

Соответствующие константы размеров тоже должны быть 16 байт: шаг элемента `[]str`, backing-хранилище argv для `os.args()`,
а также литералы `{ i32 len, i32 cap, i8* data }` глобальных строковых констант. Нагрузка у `?str` ровно 16
байт (2 слова i64, в первом упакованы len и cap), поэтому `?str` — это inline-option размером 24 байта;
нагрузка варианта `str` в помеченном перечислении тоже занимает 2 слова. `txt` остаётся без изменений и не переходит на u32 вместе со `str`.

**Заголовок u32 у `[]T`**: `%vec = type { i32, i32, i64 }` (16 байт). `len` / `cap` устроены так же, как у `str`,
внутри `u32`, внешний API — `i64`; разница в том, что **поле data остаётся `i64`** (указатель, закодированный через `ptrtoint`,
а не `i8*`), чтобы сохранить существующие места вызова `inttoptr` / `ptrtoint`. Этот рубеж обрабатывается
`vecLenI64` / `vecCapI64` / `vecHeaderLoadI64` / `vecHeaderStoreI64` / `vecFromParts`
(а также общие `hdrFieldI64` / `hdrTrunc` / `hdrWiden`); `emitLenCap` / `emitGetField` /
`emitSetField` / `ensureVecBuffer` — все идут через них. То же ограничение, что и для `str`, действует и здесь: **нельзя** напрямую
выдавать `load i64` / `store i64` для полей 0 / 1 `%vec`.

`cap == 0` у `%vec` — это метка **заимствованного представления** (`s.bytes()`, заимствование `[N]T` → `[]T`, приведение str → `[]byte`):
не владеет кучей, `@vec_free` / `@vec_retain` её пропускают; только при `cap > 0` блок, на который указывает `data`, находится в собственности.

У `[N]T` нет никакого дескриптора времени выполнения: на уровне LLVM это просто агрегат `[N x T]`, а `.len` компилятор напрямую заменяет на
константу времени компиляции `N`; `cap` отсутствует.

## Поверхностный free и глубокий free

### Поверхностный free
Освобождает только буфер data контейнера, не обходя элементы. Применяется к:
- `%str-long` (data строки — это буфер символов, нет вложенных элементов, владеющих кучей)
- vec/arr с элементами базовых типов (i64, double и др.)

### Глубокий free
Сначала обходит каждый элемент и рекурсивно освобождает его данные в куче, затем освобождает буфер data контейнера. Применяется к vec/arr с элементами, владеющими кучей:
- `[]str` (элементы — %str-long)
- `[][]i64` (элементы — %vec)
- `[]MyType` (элементы — пользовательские структуры, поля освобождаются рекурсивно)

### Проверка NULL
Перед каждым free выполняется проверка `icmp eq i8* %ptr, null`, чтобы избежать free(NULL) или free неинициализированного указателя.

## Передача владения (move)

### move с одним возвращаемым значением
```no
get-slice = () (out []i64) {
    local = [1, 2, 3]
    out = local; local помечается как moved, при выходе из функции free не выполняется; out управляется вызывающим
}

v = get-slice(); v владеет данными, free при выходе из функции
```

### move с несколькими возвращаемыми значениями (в порядке позиций параметров)
```no
get-pair = () (a []i64, b []i64) {
    x = [1, 2]
    y = [3, 4]
    a = x; первый выходной параметр, x помечается как moved
    b = y; второй выходной параметр, y помечается как moved
}

a, b = get-pair(); a владеет данными x, b владеет данными y
```

**Порядок обработки**: выходные параметры обрабатываются по очереди в **порядке объявления** в сигнатуре функции. Каждое присваивание `out = src` независимо помечает исходную переменную как moved.

**Многократное присваивание одного и того же источника**: если `a` и `b` ссылаются на одну переменную (например, `a = x; b = x`), компилятор автоматически решает, clone или move, с помощью **предварительного анализа живучести (Liveness)** (`moveEligible`):

- `a = x`: `x` затем используется в `b = x` → **глубокий clone**, `a` независимо владеет данными
- `b = x`: `x` больше не используется → **move**, `b` перенимает данные `x`, `x` помечается moved и пропускает free

Это исключает double-free. Правило: **последняя ссылка идёт по move, предыдущие — по clone**.

Для сценариев с условными ветками (например, `if cond { out = x }`) состояние moved отслеживается через битовую карту времени выполнения, см. следующий раздел.

### Глубокий clone в vec.push
```no
inner = [1, 2, 3]
outer.push(inner)
; data inner глубоко копируется в позицию нового элемента outer
; inner по-прежнему владеет независимыми данными, при выходе из функции inner и outer освобождают их отдельно
```

push выполняет глубокий clone для типов элементов, владеющих кучей (`%str-long`/`%vec`/`%arr`/пользовательские структуры): malloc новые data + memcpy + рекурсивный clone элементов. Исходная переменная и внешний vec владеют независимыми данными, **метка move не нужна**, что исключает double-free. Элементы базовых типов (i64/f64 и др.) просто сохраняются значением.

### Отслеживание move во время выполнения (битовая карта, индексируемая по номеру переменной в куче)

move внутри условной ветки создаёт сложность: во время компиляции нельзя определить, действительно ли move произошёл.

```no
cond-move = (flag i64) (out []i64) {
    x = [1, 2, 3]
    if flag == 1 {
        out = x; move происходит только при flag==1
    }
    ; при flag==0 x по-прежнему владеет данными, при выходе из функции нужен free
    ; при flag==1 владение x передано, при выходе из функции free нужно пропустить
}
```

Nolang решает эту задачу с помощью **битовой карты, индексируемой по номеру переменной в куче**. На этапе компиляции каждой локальной переменной в куче присваивается уникальный `varIdx`, и каждый бит битовой карты соответствует одной переменной в куче (а не выходному параметру).

#### Состояние компилятора

| Поле | Тип | Назначение |
|------|------|------|
| `heapVarIndex` | `map[string]int` | Имя переменной в куче → `varIdx` (только локальные переменные в куче) |
| `outBindState` | `[]int` | Номер переменной в куче, привязанной в данный момент к каждому выходному параметру (-1 = нет привязки, -2 = неопределённо) |
| `movedVarBitset` | `[]uint64` | Битовая карта moved на этапе компиляции (используется, если нет битовой карты времени выполнения) |
| `movedBitmapBase` | `string` | Префикс имени переменной битовой карты времени выполнения (например, `%__mb`; пусто = не выделена) |
| `bitmapCount` | `int` | Число блоков u64 в битовой карте (= maxVarIdx/64 + 1) |

#### Правила отображения номеров

Один блок `u64` хранит 64 флага; номер переменной в куче `varIdx`:

- Номер блока = `varIdx / 64`
- Смещение внутри блока = `varIdx % 64`
- Маска = `1u64 << смещение`

На этапе компиляции всё вычисляется как константы, во время выполнения затрат на вычисления нет. Несколько блоков `u64` позволяют поддерживать любое число переменных в куче, **без ограничения на количество параметров/возвращаемых значений**.

#### Обработка присваивания move (перекрытие очищает старый бит)

Каждый раз, когда переменная в куче передаётся через move выходному параметру:

1. Если этот выходной параметр раньше был привязан к другой переменной (`outBindState[outIdx] >= 0`), сначала снять бит, соответствующий старой переменной
2. Затем установить в 1 бит, соответствующий текущей переменной
3. Обновить номер переменной, привязанной к этому выходному параметру (`outBindState[outIdx] = srcVarIdx`)

#### Освобождение в конце функции

Обходятся все переменные в куче и создаются независимые `if`: если соответствующий бит равен 0 — free, если бит равен 1 — владение передано, освобождение пропускается.

#### Выделение битовой карты по требованию

Переменная битовой карты выделяется только **при необходимости**, чтобы избежать накладных расходов в сценариях без ветвлений:

| Сценарий | Выделение битовой карты | Поведение free |
|------|---------|----------|
| Нет move | Не выделяется | Всё освобождается |
| move вне ветки (детерминированный move) | Не выделяется | Компилятор сразу пропускает free через `movedVarBitset` |
| move в ветке (условный move) | Выделяется | Проверка битовой карты во время выполнения: bit=1 — пропустить, bit=0 — free |

Перед генерацией тела функции компилятор предварительно сканирует AST (`detectBranchMoveToOut`), обнаруживая присваивания move выходному параметру внутри веток `IfExpression`/`ForStatement`/`ConditionalExpression`; переменная битовой карты выделяется только если такой шаблон найден. `alloca` битовой карты вставляется после генерации тела функции (когда `nextHeapVarIdx` уже имеет окончательное значение) и записывается в entry block.

Этот механизм применим ко всем типам в куче (`vec`/`str-long`/`arr`/пользовательские структуры).

## Глубокий clone (присваивание между локальными переменными)

```no
a []i64 = [10, 20, 30]
b = a; глубокий clone: malloc новые data + memcpy + рекурсивный clone элементов
b[0] = 99
; a[0] == 10 (a не изменён)
; b[0] == 99 (b изменён независимо)
```

### Процедура глубокого clone
1. Освободить старое значение целевой переменной (если уже есть данные в куче)
2. `malloc` новый буфер data, `memcpy` исходные data в новые
3. Рекурсивно клонировать каждый элемент, владеющий кучей:
   - Элементы `%str-long`: malloc + memcpy строковых data
   - Элементы пользовательской структуры: memcpy структуры + рекурсивный clone полей с данными в куче
4. Записать новые указатель data, len, cap в целевую переменную
5. Отслеживать цель как переменную в куче (free при выходе из функции)

### Клонируемые типы
| Тип | Глубокий clone | Пояснение |
|------|-------------|------|
| `%vec` / `%arr` (элементы базовых типов) | ✅ | Достаточно memcpy data |
| `%vec` / `%arr` (элементы %str-long) | ✅ | Для каждого элемента malloc+memcpy строковых data |
| `%vec` / `%arr` (элементы — клонируемые структуры) | ✅ | Для каждого элемента рекурсивный clone полей структуры |
| `%vec` / `%arr` (элементы — %vec / %arr) | ✅ | Рекурсивный clone элементов внутреннего контейнера через механизм `elemElemType` |
| `%str-long` | ✅ | malloc + memcpy строковых data |
| Пользовательская структура (без вложенных контейнерных полей) | ✅ | memcpy структуры + рекурсивный clone полей в куче |
| Пользовательская структура (с вложенными контейнерными полями) | ✅ | memcpy структуры + рекурсивный clone полей с вложенными контейнерами (через `elemElemType`) |
| `?str` | ✅ | option с inline-нагрузкой: клонируются сам option и его строковые data |
| `?[]T` | ✅ | option с inline-нагрузкой: клонируются сам option и data внутреннего среза (clone по элементам, для владеющих кучей элементов таких как `?[]str` — рекурсивно) |

> **`?str` / `?[]T` имеют inline-нагрузку, но владеют кучей.** Их нагрузка хранится непосредственно в собственном `%option_<key>` option'а
> (`?str` имеет структуру `{ i8 tag, [2 x i64] }`, 16 байт нагрузки содержат
> `{ u32 len, u32 cap, i8* data }`), но `str` data / backing store среза внутри выделяются в куче
> ⇒ **при clone нужно глубоко копировать вместе с нагрузкой, при free — освобождать вместе с нагрузкой**; обе стороны должны быть парными.
> Освобождение `?[]T` идёт через тот же helper глубокого free, что и `[]T` (рекурсия определяется типом элемента), поэтому
> и здесь сохраняется та же пара «глубокий clone — глубокий free».
> ⚠️ У обычных option (не `?str`/`?[]T`) нагрузка — заимствование или чистое значение, они **не владеют** кучей, и clone/free её не затрагивают.
> Если нагрузка слишком велика и превышает `option-payload-inline-threshold`, option хранит указатель в кучу; тогда free должен освободить и саму коробку
> (определяется `Boxed`, см. `src/mir/layout.go`).

### Отличие от move
- **Глубокий clone**: источник и цель независимо владеют данными, каждый освобождает их при выходе из функции
- **move**: источник отказывается от владения (помечается moved), цель перенимает данные, источник пропускает free

Правила выбора для `b = a`:
1. Если `a` — источник для выходного параметра → move
2. Иначе если `a` владеет данными в куче, но **после присваивания больше не используется** → move (без копирования, наблюдаемо эквивалентно глубокому clone)
3. Иначе если `a` владеет данными в куче и допускает глубокий clone → глубокий clone
4. Иначе копирование значения

`vec.push(x)` не подпадает под эти правила: push — это вызов метода, и независимо от того, владеет ли `x` кучей, он выполняет глубокий clone для элементов, владеющих кучей (см. предыдущий раздел).

## move стековых типов (перепривязка слота стека / slot-rebind)

Хотя `i64`/`u64`/`i128`/`u128`/`txt` — стековые типы (не владеют кучей), `b = a` (справа переменная), когда источник `a` больше не используется, не выполняет копирование значения, а использует **перепривязку слота стека** (stack-slot rebind): `g.varAlias[b] = a`, так что `b` и `a` делят один слот стека (0 копирований). Это лучше копирования значения (там всё равно нужно emit load+store), и особенно выгодно для больших стековых типов, таких как `%txt` на 256 байт.

### Ограничение can_slot_rebind (консервативная корректность)

Перепривязка слота стека **строже**, чем `moveEligible` у move в куче:

- `moveEligible`: move разрешён, если источник `a` **не читается** в дальнейшем (для типов в куче; после move источник пропускает free, на цели это не сказывается).
- `can_slot_rebind` (`slotRebindSafe`): перепривязка разрешается, только если у источника `a` **нет ни одной последующей ссылки (ни чтения, ни записи)**. После перепривязки `b` и `a` делят один слот, и последующая запись в `a` испортит значение `b`.

Вычисление: `generateFunctionDefinition` вызывает `computeMoveEligibility` (заполняет и `moveEligible`, и `slotRebindSafe`); `generateMainFunction` вызывает `computeSlotRebindSafety` (**только** `slotRebindSafe`, не трогая `moveEligible` — в HEAD главная функция не использует move в куче, он отключён во избежание SEGFAULT). Оба выполняют учитывающий ветвления и циклы поиск ссылок через `stmtContainsVarRefAny` (включая левые части `AssignExpression` и обратные рёбра циклов).

Если `can_slot_rebind` не выполнено (источник всё ещё используется) → **переход к полному копированию значения**, никогда к небезопасному поведению.

### Сценарии отключения (нужен обычный путь присваивания)

| Сценарий | Причина |
|------|------|
| Функции stdlib (`curIsStdLib`) | stdlib содержит конструкции (match/closure/coroutine), которые анализ ссылок не может полностью смоделировать; перепривязка испортит общий слот (например, внутри fmt `it` алиасируется с локальной `n`). Обнаружение: `g.stdModules` (внедряется `transpiler.go` через `SetStdModules` из `checker.KnownStdModules()`), откат к `g.funcOwner[fd.Name]` |
| Цель — выходной параметр | Выходной параметр передаётся вызывающим по указателю; перепривязка заставит его указывать на локальный слот источника, и вызывающий не сможет прочитать значение |
| Цель — глобальная переменная | Перепривязка приведёт к тому, что глобальное имя будет разрешаться в локальный слот источника, нарушая семантику глобальных |
| Цель — переменная с типом в куче | Перепривязка слота стека применима только к стековым типам |
| Источник — параметр | Параметры передаются по ссылке, перепривязка испортит стековый кадр вызывающего |
| Источник — глобальная переменная | Глобальный адрес будет алиасирован с локальным источником, что даст неверную семантику |

### Аннулирование псевдонима после переприсваивания

При переприсваивании переменной (`b = ...`) сначала `delete(g.varAlias, name)` удаляет возможную остаточную старую привязку, чтобы общий путь присваивания через `varAddr(name)` не указывал на старый слот источника и не портил его. При установке нового псевдонима выполняется **транзитивное разрешение** по цепочке (`src := ident.Value; for { if n2,ok := g.varAlias[src]; ok { src = n2 } else break }`), чтобы найти конечный слот-источник и избежать ошибок при нескольких переходах.

### Ортогональность с move в куче

Перепривязка слота стека действует только на стековых типах, не затрагивает передачу владения или `free` и полностью независима от механизмов clone/move для типов в куче.

**Тест**: `tests/slot-rebind.no` (покрывает перепривязку i64/u64/i128/u128/txt, переход к copy, аннулирование псевдонима после переприсваивания цели, переход к копированию при move параметра, передачу в consume; ожидаемый вывод `42 7 1 1 17 5 5 10 100 99 84`).

## Возвращаемое значение `str` у FFI extern

C-указатель на строку (`i8*`), возвращаемый функцией FFI extern (с меткой `#{c}`), может указывать на статическую память (например, `getenv`, `strerror`) или на внешний буфер (например, указатель из `strchr` указывает внутрь параметра). Непосредственная упаковка в `%str-long` приведёт к `free()` некучевой памяти в `emitHeapFree` → UB.

Компилятор вставляет безопасное копирование на пути возврата `str` из FFI extern:

1. **Проверка NULL**: если C вернул NULL, создаётся пустой `%str-long` (data=0, len=0). Обратите внимание: `str` — не option, поэтому **`s == nil` является ошибкой компиляции** (`q4nilcmp`); чтобы различить NULL и пустую строку, объявите extern как возвращающий `?str` (NULL ⇒ `nil`) или проверяйте `s.len == 0`
2. **Не NULL**: `strlen` + `malloc` + `memcpy` + null-терминатор, копирование в независимый буфер в куче
3. **PHI-объединение**: оба пути объединяются, и создаётся `%str-long` для возврата

```no
#{c}
strchr = (s str, c i64) (r str)

find = () (r str) {
    r = strchr('hello', 108); C возвращает указатель внутрь 'hello'
    ; компилятор автоматически копирует через malloc+memcpy, r независимо владеет данными
    ; при выходе из функции emitHeapFree безопасно освобождает r.data
}
```

Этот механизм логически совпадает с путём `RetCStrToStr` в clib (используется для встроенных функций `get-env`, `get-wd` и др.) и гарантирует, что все возвращаемые C-строки имеют независимое владение.

## Освобождение переменных уровня модуля

Переменные уровня модуля в куче (`vec`/`str`/`arr`/структуры) компилируются в LLVM global (`@name`); их буферы `data` инициализируются через malloc в инструкциях верхнего уровня в точке входа `main`.

Перед `ret i32 0` во входной функции C `main` компилятор вызывает:
1. `emitHeapFree` — освободить локальные переменные в куче верхнего уровня (не globalVars)
2. `emitGlobalHeapFree` — обойти `moduleVarTypes` и освободить все типы, владеющие кучей, среди `globalVars`

```no
GLOBAL-STR = 'hello'; LLVM @GLOBAL-STR = global %str-long zeroinitializer
GLOBAL-VEC = [1, 2, 3]; LLVM @GLOBAL-VEC = global %vec zeroinitializer
; инструкции верхнего уровня malloc'ят data и сохраняют в global
; перед ret в main emitGlobalHeapFree освобождает data
```

Это исключает накопление утечек памяти в долгоживущих сервисах (например, демонах с циклами). На одноразовые CLI-утилиты это не влияет (при выходе процесса память забирает ОС).

## Представления срезов (slice view)

Выражение среза `arr[1..3]` создаёт представление (без копирования), разделяющее data исходного массива. Три варианта судьбы представления:

| Цель | Поведение | Владение |
|------|------|--------|
| Локальная переменная `v = arr[1..3]` | Представление без копирования | Разделяет data исходного массива |
| Выходной параметр `out = arr[1..3]` | clone (malloc+memcpy) | Независимое владение |
| Явный тип `[]T`: `v []i64 = arr[1..3]` | clone | Независимое владение |

**Причина**: выходной параметр уходит к вызывающему, и исходный массив может быть освобождён до выхода из функции, поэтому представление должно быть склонировано в независимые data.

## Переприсваивание и освобождение старого значения

```no
s = 'hello'; malloc буфер data
s = 'world'; освободить data 'hello', malloc новые data
```

При переприсваивании типа, владеющего кучей, компилятор автоматически освобождает data старого значения перед присваиванием, чтобы избежать утечки.

## Освобождение полей структур

```no
Node {
    name str
    items []i64
}

n = Node {
    name: 'hello'
    items: [1, 2, 3]
}
; при выходе из функции рекурсивно освободить:
;   - n.name.data (поле %str-long)
;   - n.items.data (поле %vec)
```

При освобождении структуры обходятся все поля, и для полей, владеющих кучей, их data освобождаются рекурсивно.

## Переприсваивание массива фиксированного размера срезом

```no
local [4]i64 = [100, 200, 300, 400]; local — массив фиксированного размера (16 байт)
local = [100, 200, 300]; переприсваивание срезом (16 байт)
```

Массив фиксированного размера (`%arr`, 2 поля) и срез (`%vec`, 3 поля) имеют разную компоновку в памяти. При переприсваивании компилятор автоматически выделяет новую переменную `%vec` и перенаправляет все последующие обращения, чтобы избежать выхода за границы буфера.

## Известные ограничения

### Контейнер map
В hashmap не реализован глубокий free для key/value, поэтому данные в куче контейнера map утекают.

### Временные переменные в цикле
```no
#{fmt-skip}
loop {
    s = 'temp'   ; на каждой итерации malloc новые data, старые data не освобождаются
}
```

### Общие данные async (исправлено 2026-09-30)

Граница spawn у `awy { r = co f(x) }` теперь **глубоко копирует** аргументы, владеющие кучей; задача больше не делит буфер с вызывающим.

Корутины — кооперативные и однопоточные, поэтому «разделение изменяемых данных в куче между корутинами» на уровне языка невозможно; единственное, что может разделяться, —
это значение, **которое вызывающий всё ещё удерживает после spawn**. До исправления argbuf был всего лишь **побитовой копией** дескриптора аргумента,
`data` разделялся с вызывающим, а задача начинала выполняться только в точке ожидания — если вызывающий до этого переприсвоил переменную или вышел из области видимости, он
освобождал буфер, и задача читала уже освобождённую память (проверено: str выводил 40 NUL, `[]i64` выводил 0,
в обоих случаях rc=0 и никаких диагностик).

Теперь копирование выполняется глубоким сразу в момент spawn, а wrapper освобождает копию после завершения вызова:

| Тип параметра | Граница spawn | Освобождение в wrapper |
|---|---|---|
| `str` | `@str_clone` | `@str_free` |
| `[]T` (у T есть deep-clone helper) | `vecDeepClone` | `@vec_free` |
| Структура, владеющая кучей (встроенные листья `str` / поля-указатели) | Клонирование листьев на месте + копирование pointee | Рекурсивный деструктор структуры |
| Прочие (типы чистых значений) | Побитовая копия (корректно) | Освобождается только контейнер |

Регрессия: `tests/async-ownership.no`.

### Утечка при переприсваивании struct (исправлено 2026-09-30)

```no
holder {
    s str
}
h holder = holder {
    s: 'first'
}
h = holder {
    s: 'second'
}
; раньше буфер 'first' утекал
```

При перепривязке локальной переменной старое значение освобождается только в том случае, если его тип — `Type.Owned` (`str`/`vec`/`[]T`/`map`/`?owned`),
иначе — нет. struct **намеренно не считается** `Type.Owned` (этот флаг одновременно служит lowerer'у для определения «является ли привязка псевдонимом»),
поэтому `h = holder { … }` просто перезаписывает всю структуру, и старый буфер `s` никогда не освобождается.
При этом механизм drop на самом деле распознаёт struct (`dropOwnsHeap` → `typeOwnsHeap`, при этом `emitDrop` использует рекурсивный
деструктор для освобождения); слишком узкая только проверка в lowerer'е. После исправления перед перепривязкой старые поля освобождаются.

Проверка с 2 000 000 переприсваиваний: пиковое RSS 66,1 МБ → 33,8 МБ, вывод побайтно одинаков.

### Значение первого поля struct literal — вызов метода (исправлено 2026-09-30)

```no
holder {
    s str
}
h = holder {
    s: n.to-str()
}
; до исправления: 'holder' is not defined
```

Классификация `{ … }` определяется просмотром нескольких токенов вперёд. **Разделитель ветвей match тоже `:`**, поэтому
`s: n.to-str()` выглядит одновременно и как «ветка match с шаблоном `s`», и как «поле struct literal».
Единственный различающий признак — токен **после** `ident.ident`: вызов метода может быть только значением поля.
В старой ветке не хватало проверки на `(`, поэтому весь блок классифицировался как match; имя struct в контексте match не находилось и вызывало ошибку «не определено»
(если значение поля — обычный вызов функции, всё работало).

После исправления `h = holder { s: recv.method(args) }` разбирается нормально. Ветка match в nolang не может начинаться с
`name : X(` (разделитель ветвей — `->`, ветка, начинающаяся с `:`, всегда wildcard/default, а её body не содержит вызова со скобками),
поэтому разрешение `(` не приведёт к ошибочной классификации никакой допустимой ветки match как struct literal. Регрессия:
`src/parser/struct_literal_field_value_test.go`.

### Подсчёт ссылок на задачу (упрощение синтаксиса 2026-11-17)

Внутренний `%task` по-прежнему единственный объект с подсчётом ссылок: при создании spawn `rc = 1`, при завершении ожидания — `release`.
В старом синтаксисе с ручными дескрипторами пути копирования, такие как `h2 = h` / `run h`, могли пропустить retain (особенно серьёзно для задач с void-результатом,
проверено: SIGSEGV), и это перехватывал верификатор `checkRefBalance`. Новый `awy { ... }` не предоставляет дескриптор,

.no-тесты и Go-тесты на псевдонимы handle / RC были удалены вместе с `run`; на уровне MIR пары `OpTaskRetain` /
`OpAwait` по-прежнему покрываются MIR-фикстурами в `src/mir/opt_test.go`.

### Перемещение аргументов spawn: без копирования, когда источник мёртв (2026-10-01)

`co f(x)` выполняет глубокое копирование каждого аргумента, **владеющего кучей**, на границе spawn, поскольку задача может начать выполняться только в конце группы,
а вызывающая сторона до этого может переприсвоить переменную или выйти из области видимости. Когда `x` после spawn **точно больше не используется**,
это копирование избыточно: владение напрямую **передаётся** в задачу.

```no
s str = 'hello'
awy {
    v = co echo(s)      ; s больше не читается -> передача без копирования
}
print(v)                ; hello

s str = 'hello'
awy {
    v = co echo(s)
}
print(s)                ; s всё ещё читается -> сохраняется глубокое копирование (обе стороны владеют отдельно)
print(v)                ; hello
```

Три критерия, все обязательные:

1. Вызывающая сторона **всё равно освободила бы** x — заимствования (представление среза, borrow read) и параметры вызывающей стороной не освобождаются;
2. `x` после spawn мёртв (**нет ни одного последующего чтения**);
3. Параметр вызываемой функции на этой позиции — `str` / `[]T` / `struct`, владеющая кучей, — wrapper освободит его полезную нагрузку.

Для этих трёх категорий освобождение в wrapper'е задачи и изначальный drop в вызывающем **сводятся к одному и тому же helper'у**, поэтому передача лишь переносит
**одно и то же освобождение** от вызывающего к задаче, не добавляя и не убирая ни одного освобождения.

**Неизменная семантика для пользователя**: у задачи, которая так и не была ожидана, буфер параметра изначально освобождается wrapper'ом только в момент ожидания;
для этого передача и копирование ведут себя одинаково.

Реализация: `insertDrops` записывает в `Module.spawnArgMoves`, а `emitAsyncRun` на этом основании пропускает глубокое копирование.
Регрессия: `tests/async-arg-move.no`, `src/mir/spawn_arg_move_test.go`.

### Псевдонимы в таблице ожидающих корутины (исправлено 2026-09-30)

Планировщик раньше использовал `@nolang_waiters = global [256 x i8*]` с индексом `ptrtoint(task) & 255`.
Задачи выделяются через `@malloc` и **выровнены на 16 байт**, поэтому в младших битах указателя всего 4 значимых разряда — 256 слотов фактически схлопываются в

`@nolang_async_done` читает это поле и, если оно непустое, ставит в очередь и очищает. Поиск благодаря этому точен, и адресных псевдонимов больше нет.

### `awy` поглощалось, когда не было первой инструкцией блока (исправлено 2026-09-30; переписано 2026-11-17)

`skipToStatementEnd()` продвигается до токена, который может **начать** следующую инструкцию, и останавливается; при этом список разрешённых
`isStatementBoundary()` (`src/parser/stmt.go`) раньше упускал префиксные ключевые слова. В старом синтаксисе `run` / `awy t`
могли быть поглощены вместе с переводом строки, если не были первой инструкцией, что давало семантическую деградацию при `rc=0` и без диагностики.

В новом синтаксисе у `awy` есть собственный case в `parseStatement` (группа корутин), и он вместе с `co` включён в
`isStatementBoundary()`; `run` больше не ключевое слово и удалено из списка. Правило: **каждый токен, который
может быть обработан оператором `switch` в `parseStatement`, должен одновременно присутствовать в `isStatementBoundary()`**.

### Голый `{ ... }` в позиции инструкции воспринималось как объявление (исправлено 2026-09-30)

Ветка `LBRACE` в `parseStatement` вызывает `classifyBlockAtCurrent()` (при этом `currentToken` уже равен
`{`, и никакого имени для потребления нет). Возвращаемые им `blockEnum` / `blockIface` / `blockTaggedEnum` в **позиции инструкции**
не имеют смысла — настоящие объявления enum/interface/tagged enum требуют предшествующего имени и идут по более ранней
ветке `classifyBlock()`. Но диспетчеризация инструкций направляет в блок инструкций только `blockUnknown`, поэтому:

- `{ x = 2 }` классифицируется как `blockEnum`, а `{ print(2) }` — как `blockIface`;
- оба передаются в `parseExpressionStatement`, а ветка `LBRACE` в `expr.go` распознаёт только
  `blockStruct` / `blockMatch`, а для остальных выполняется `p.nextToken(); return nil`;
- `{` поглощается, инструкции внутри блока становятся братьями внешнего тела (на том же уровне), а `}` этого блока, наоборот, закрывает **внешний** блок.

Результат — не «поглощение», а **протечка инструкции на один уровень наружу**: `f = () { print(1); { print(2) }; print(3) }` выводит
`3,1,2`; `f = () { x = 1; { x = 2 }; print(x) }` не выводит ничего. Опять же `rc=0` и без диагностики.

Исправление: в диспетчеризации инструкций направлять `blockEnum` / `blockIface` / `blockTaggedEnum` в блок инструкций вместе с остальными
(`blockStruct` должен **остаться** на пути выражений — `{ field: value }` это допустимая инструкция с анонимным литералом структуры).
⚠️ **Не** пытайтесь «исправить» это, меняя ветку `ASSIGN` в `classifyBlockAtCurrent`: она покрывает лишь один из трёх случаев ошибочной классификации
и к тому же переносит проверку из единственного места, которое знает «я нахожусь в позиции инструкции».

⚠️ **Побочный эффект**: это исправление впервые заставляет `{ ... }` в позиции инструкции реально существовать как `*parser.BlockStatement`,
а в списке разрешённых обходчика `programUsesPrint` (`src/build/transpiler.go`, решающего, нужно ли загружать `fmt`/`io`/`str`/`byte`,
написанного вручную AST walker'а) нет `BlockStatement` ⇒ программы, где `print` написан только внутри голого блока, больше не обнаруживаются.
**При изменении уровня инструкций нужно перезапустить `go test ./build/ -run TestProgramUsesPrint`** и добавить новый тип контейнера в
`walkStmt`. Регрессия: `src/parser/stmt_boundary_block_test.go`, `tests/stmt-boundary.no`.

### Недостаточно точное определение пропуска free при первом присваивании глобальной переменной

Компилятор использует map времени компиляции `globalFirstAssigned`, чтобы отслеживать, было ли уже первое присваивание глобальной переменной: при первом присваивании освобождение старого значения пропускается (старое значение — `zeroinitializer`, не данные в куче), а при последующих переприсваиваниях старое значение в куче освобождается.

Этот map инициализируется один раз за всю компиляцию, не сбрасывается для каждой функции и не различает пути условных ветвлений. Если глобальная переменная впервые присваивается в условной ветке, компилятор обрабатывает её в порядке AST: первая инструкция присваивания помечается как «первая» (free пропускается), вторая (даже в другой ветке) идёт по пути переприсваивания (пытается free старое значение). Если во время выполнения вторая ветка выполнится первой, глобальная переменная всё ещё равна `zeroinitializer` (data=NULL, len=0), и произойдёт попытка free неинициализированного старого значения.

**Текущие меры смягчения (эффективные)**:
- Неглубокие контейнеры (`%str-long`): `emitNullCheckFree` генерирует проверку времени выполнения `icmp eq i8* dataPtr, null` и при NULL пропускает `call @free`
- Глубокие контейнеры (`%vec/%arr`): в `emitDeepContainerFree` есть дополнительная проверка с коротким замыканием `len == 0`; у zeroinitializer len равен 0, и весь цикл освобождения пропускается

Эти два уровня защиты во время выполнения означают, что даже при неточном решении на этапе компиляции сбой на практике не происходит. Однако логически это зависит от проверки NULL как страховки, а не от точного решения во время компиляции.

**Возможное направление улучшения**: заменить `globalFirstAssigned` — map времени компиляции — на механизм отслеживания во время выполнения (аналогичный битовой карте `movedVarBitset`), но это увеличит накладные расходы, а текущие меры смягчения уже достаточно эффективны.

## Компромиссы в дизайне

1. **Стоимость глубокого clone.** `b = a` выделяет и копирует данные; `vec.push(x)` тоже выполняет глубокий clone для элементов, владеющих кучей.
   Это сделано намеренно: **одним копированием мы избавляемся от целого класса анализа псевдонимов** — между значениями остаются только «владение» и «перенос», разделения нет,
   поэтому «кто владеет, кто освобождает, observable ли запись» не требует отдельного набора правил для каждого варианта псевдонима.
2. **Глубокое копирование на границе spawn (= снимок).** `co f(x)` делает глубокую копию аргументов, владеющих кучей, в момент spawn, поэтому задача видит
   **значение на момент spawn**, не зависящее от последующих записей вызывающего. **Если источник мёртв, используется move без копирования**.
   ⚠️ Не меняйте это на «общий буфер + подсчёт ссылок» ради экономии копирования: тогда задача увидит **записи вызывающего на месте** между spawn и ожиданием в конце группы
   (общий доступ), что нарушит пункт 4. Правильный способ сэкономить копирование — «**копирование при записи**» (copy-on-write).
3. **Подсчёт ссылок на задачи не образует циклов.** Внутренний `%task` — единственный объект с подсчётом ссылок; новый `awy { ... }` не предоставляет дескриптор,
   каждое `co` ожидается ровно один раз в конце группы, поэтому не возникает цикла «задачи держат дескрипторы друг друга».
4. **Между корутинами нет общих изменяемых данных в куче.** Корутины планируются **кооперативно и в одном потоке**, поэтому разделение изменяемых данных в куче между корутинами на уровне языка невозможно;
   разрешение общего доступа лишь создало бы гонки данных и висячие указатели. Поэтому граница spawn всегда передаёт **независимую копию** (или передаёт владение).
