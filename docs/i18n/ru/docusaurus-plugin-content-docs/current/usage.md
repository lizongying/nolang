# Установка и использование

## Установка

### Установка CLI

Скачайте исполняемый файл для своей платформы с [GitHub Releases](https://github.com/lizongying/nolang/releases/latest) или установите одним из следующих способов:

```bash
# macOS / Linux
# 1. скачать бинарный файл
# 2. поместить в PATH
sudo mv nolang /usr/local/bin/no
```

### Установка расширения VS Code

Установите расширение Nolang из [VS Code Marketplace](https://marketplace.visualstudio.com/items?itemName=lizongying.vscode-nolang): подсветка синтаксиса, диагностика LSP, переход к определению, автодополнение и др.

| Команда                                                         | Описание                    |
| ------------------------------------------------------------ | ----------------------- |
| `no version`                                                 |печать информации о версии            |

| `no new <name>`                                              | создать пакет внутри рабочей области (подкаталог + package.noml с регистрацией в workspace.noml) |

## Быстрый старт

Nolang использует архитектуру **«один репозиторий (проект) — несколько пакетов»**: корень репозитория — рабочая область (только `workspace.noml`), каждый пакет — подкаталог (со своим `package.noml`). `no init` и `no new` — две независимые операции:

- `no init` — определить рабочую область в текущем каталоге (создаётся только `workspace.noml`).
- `no new <name>` — создать новый пакет в текущей рабочей области (создаётся подкаталог `./<name>/` и его `package.noml`), и зарегистрировать пакет в `workspace.noml`.

### Инициализация рабочей области и создание пакета

```bash
# 1) определить рабочую область в корне репозитория
no init

# 2) создать пакет внутри рабочей области (автоматически регистрируется в workspace.noml)
no new foo

# 3) перейти в каталог пакета
cd foo

# запустить напрямую (автоматически собрать и выполнить main.no)
no run
```

Внутри рабочей области можно многократно использовать `no new` для добавления новых пакетов:

```bash
no new bar
no new baz
```

На этом этапе `workspace.noml` имеет следующий вид:

```noml
{
  foo: '/foo'
  bar: '/bar'
  baz: '/baz'
}
```

> **Формат путей**: значения сопоставлений в `workspace.noml` с префиксом `/` означают путь относительно рабочей области (например, `/foo` → `workspaceRoot/foo`). Также поддерживаются переходы `./`, `../` и абсолютные пути ОС (например, `/home/user/code/fork`), что позволяет ссылаться на каталоги вне рабочей области.

При запуске `no build` без аргументов в корневом каталоге все пакеты рабочей области собираются параллельно.

### Только инициализация рабочей области (без создания пакета)

```bash
# определить рабочую область в текущем каталоге
no init
```

`no init` создаёт только `workspace.noml` (изначально пустой `{}`), **не создавая `package.noml` или `main.no`**. Если `workspace.noml` уже существует, он не перезаписывается. Пакеты создаются через `no new <name>`.

### Сборка и запуск

```bash
# сборка (по умолчанию ищется main.no)
no build                    # собрать текущий каталог
no build main.no            # собрать указанный файл
no build -o output          # задать путь вывода
no build -cc zig            # использовать компилятор Zig
no build -target x86_64-linux-gnu  # кросс-компиляция (указать целевую платформу)

# запуск (сборка + выполнение)
no run                      # собрать и выполнить main.no текущего каталога
no run foo                  # запустить пакет foo в рабочей области (разбор workspace.noml)
no run ./foo                # запустить main.no каталога ./foo
no run main.no              # запустить указанный файл .no
no run -cc zig
no run -target aarch64-macos-gnu
```

> `no build -v` дополнительно записывает исходный LLVM IR рядом с путём вывода (`<путь вывода>.ll`). `no build --shared -o libdemo.dylib main.no` экспортирует функции верхнего уровня с пометкой `#{cabi='symbol'}` в стабильные символы C ABI, компонует их с `-shared -fPIC` в динамическую библиотеку и автоматически создаёт одноимённый `.h`-заголовок; путь заголовка можно переопределить через `--header`. Опции `-c` (только компиляция без компоновки) сейчас нет. Полный способ вызова Nolang из C / C++ / Rust / Go / Java / Python / C# см. в [Вызов Nolang из host-языков](./lang/host-interop).

Позиционный аргумент `no run` разрешается в следующем порядке:

1. Существующий файл `.no` → запустить его напрямую
2. Существующий каталог → запустить его `main.no`
3. Имя пакета, зарегистрированного в рабочей области (ближайший `workspace.noml`) → запустить `main.no` этого пакета

Без аргументов по умолчанию запускается `main.no` текущего каталога. Если текущий каталог — корень рабочей области (есть `workspace.noml`, но нет `main.no`), предлагается указать пакет через `no run <package>`.

### Цели кросс-компиляции

Аргумент `-target` имеет формат `<arch>-<os>-<abi>`; поддерживаются следующие цели:

| Целевой триплет           | Описание           |
| -------------------- | -------------- |
| `x86_64-linux-gnu`   | Linux x86_64   |
| `aarch64-linux-gnu`  | Linux ARM64    |
| `x86_64-macos-gnu`   | macOS x86_64   |
| `aarch64-macos-gnu`  | macOS ARM64    |
| `x86_64-windows-gnu` | Windows x86_64 |

**Автоматическое определение текущей платформы**: `no build`, `no run`, `no test` без `-target` автоматически определяют текущую host-платформу и компилируют в нативный код. В повседневной разработке target задавать вручную не нужно:

```bash
no run hello.no          # запустить напрямую на этой машине
no test                  # запустить тесты на этой машине
no build -target aarch64-linux-gnu   # явно указывать только при кросс-компиляции
```

### Выбор компилятора

Аргумент `-cc` задаёт C-компилятор бэкенда:

- `clang` (по умолчанию) — требуется установленный LLVM
- `zig` — требуется установленный Zig, подходит для кросс-компиляции

### Раскладка встроенных типов (порог инлайнинга `?T`)

Раскладка памяти `?T` **определяетсянагрузкаом**: для каждого типанагрузка T создаётся свой
`%option_<key> = { i8 tag, [K x i64] }` (1-байтовая метка,нагрузка зафиксирована по смещению 8 байт,
`K = roundUp8(sizeof(T))/8`). Еслинагрузка не помещается в порог, используется heap-боксинг, а в первом слове областинагрузка хранится указатель.

`--option-payload-inline-threshold=N` задаёт этот порог (в байтах **всей структуры option**,
то есть `1 + 7 + sizeof(T)`):

```bash
no build --option-payload-inline-threshold=1032 main.no   # разрешить инлайнинг большихнагрузка
no build --option-payload-inline-threshold=16 main.no     # минимальное настраиваемое значение
```

| Значение | Эффект |
| --- | --- |
| По умолчанию **264** (= 1 + 7 + 256) | `?i64` 16 B, `?str` 24 B, `?txt` (256 B) 264 B инлайнятся; большиенагрузка боксируются |
| Минимум **16** | инлайнится только `?i64`; начиная с `?str` (24 B) всё боксируется |
| < 16 | ошибка компиляции |

Приоритет: аргументы командной строки > переменная окружения `NOLANG_OPTION_PAYLOAD_INLINE_THRESHOLD` >
`compiler.option-payload-inline-threshold` из `package.noml` > значение по умолчанию. Единственный источник раскладки — `src/mir/layout.go`,
на уровне семантики (какие значения считаются `ok`／`nil`／`err`) **ничего не меняется**, меняется только потребление памяти и факт боксинга.

### Встроенный оптимизатор компилятора (MIR opt)

Компилятор содержит оптимизатор, работающий на **уровне MIR** (после понижения HIR, перед генерацией LLVM-кода). Это не то же самое, что LLVM `opt` бэкенда: первый меняет MIR, второй — уже сгенерированный LLVM IR.

Включается через `-opt[=N]`, **по умолчанию выключен**:

```bash
no build main.no          # по умолчанию: не включён (как в историческом поведении)
no build -opt main.no     # эквивалентно -opt=1
no build -opt=2 main.no   # свёртка констант + удаление мёртвого кода + очистка потока управления
no build -opt=0 main.no   # явно выключить
```

| Уровень | Значение |
| ---- | ---- |
| `0` / `off` / `false` / `no` / `none` | выключено (по умолчанию) |
| `1` / `on` / `true` / `yes` / `-opt` | свёртка констант + целочисленные тождества + распространение копий + удаление мёртвых скаляров |
| `2` | уровень 1 + очистка потока управления (свёртка константных ветвей, удаление недостижимых блоков, склейка переходов через пустые блоки, объединение блоков с одним предшественником) + подрезка преамбулы |

`-opt` — **глобальный** переключатель (обрабатывается в `main`, как и `-v`), поэтому поддерживается `build`, `run` и `test`.

Тот же переключатель можно задать переменной окружения `NOLANG_MIR_OPT`; флаг командной строки лишь записывает её, поэтому рассогласования не бывает. Чтобы увидеть, что сделано в этот раз:

```bash
NOLANG_MIR_OPT=2 NOLANG_MIR_OPT_STATS=1 no build -o out main.no
# [miropt] level=2 funcs=3 folded=5 (arith=2 cmp=3) ident=1 copies=4 dead=6 cfg{condbr=3 unreachable=4(5 insts) threaded=1 merged=5}
# [miropt] prelude: dropped 27 unreferenced helpers
```

| Поле | Значение |
| ---- | ---- |
| `folded` (`arith`/`cmp`) | число свёрнутых в константу арифметических／компараторных инструкций |
| `ident` | целочисленные тождества, упрощённые к одному из операндов (`x+0`, `x*1`, `x&x`, `x^0`…) |
| `copies` | скалярные копии, удалённые распространением копий |
| `dead` | удалённые мёртвые скалярные инструкции |
| `cfg{condbr, unreachable, threaded, merged}` | свёртка константных ветвей, удаление недостижимых блоков (включая число инструкций), склейка переходов через пустые блоки, объединение блоков с одним предшественником |
| `prelude: dropped N` | число runtime-хелперов в преамбуле codegen, для которых доказано, что на них никто не ссылается (см. ниже) |

### Подрезка преамбулы (уровень 2)

`emitPrelude` записывает всю runtime (`str_*`, `print_*`, `eprint_*`, `vec_*`, `nolang_*`) в **каждый** модуль, независимо от того, используется ли она, — программа с `print('hi')` порождает 60 определений функций, из которых досягаемы только 8, а **52 никогда не вызываются**.

**Это не может сделать `opt -O2`**: GlobalDCE в LLVM удаляет только определения `internal`, а преамбула испускается с external linkage (модули `no` могут компоноваться с C, и нужные компоновщику хелперы не могут быть internal). Замеры на этой программе: из 60 определений ровно 7 — `define internal`, и `opt -O2` удаляет именно эти 7, при этом `.ll` вместо уменьшения вырастает с 61 812 до 69 874 bytes (+8 062).

Поэтому уровень 2 после завершения генерации IR разово выполняет подрезку достижимости **готового текста**, оставляя только реально используемые хелперы (и рекурсивно те, которые они вызывают). Та же программа `print('hi')`: число определений 60 → **16**, `.ll` 61 812 → **14 548** bytes (**−76,5%**), исполняемый файл 36 616 → 34 648 (−5,4%). Подрезка учитывает только настоящие ссылки — **имена в комментариях не считаются**, именно поэтому удаётся убрать 44, а не 33; а при удалении функции **удаляется и её поясняющий комментарий** (`optTrailingComment`), иначе осталось бы 12 609 bytes, описывающих 44 уже несуществующие функции.

Удаление комментариев **не уменьшает исполняемый файл** — комментарии отбрасываются ещё при разборе `opt`/`llc`, и в обоих случаях исполняемый файл составляет 34 648 bytes. Выигрыш в 12 609 bytes — это экономия текста IR и объёма разбора на этапе компиляции.

Эвристики подрезки всегда смещены в сторону сохранения: блок, из которого нельзя вывести единственное имя, сохраняется; если у блока нет закрывающей фигурной скобки, подрезка останавливается на нём; `declare`／глобальные переменные／определения типов никогда не удаляются. Пропустить оптимизацию — значит получить на несколько байт больше, удалить лишнее — ошибку компоновки.

**Можно ли удалить преамбулу целиком? Нет.** В интервале преамбулы есть не только функции, но и **строковые литералы самой программы** (`@.mir.str.N`, то есть сам `"hi"`), типы `%str-long`／`%option`／`%task`, внешние объявления `@malloc`／`@write`／`@llvm.memcpy` — эта «информационная» часть занимает около 30% модуля, и без неё не проходит даже `llc` (`error: use of undefined value '@.mir.str.1'`). Удалить можно только «функциональную» половину: если заменить 48 `define` на одноимённые `declare`, компоновщик сообщит ровно о четырёх неопределённых символах — `print_nl`, `print_str`, `str_free`, `str_from_const`. Поэтому правильный вопрос — «можно ли испускать по требованию», а не «можно ли удалить».

Эта расточительность — **фиксированный налог, не зависящий от размера программы**: код и комментарии преамбулы одинаковы для каждого модуля (48 определений, код 36 043 ＋ комментарии 17 516 bytes), а в выборке из 40 файлов число сохранённых хелперов — **0–19, медиана 9**. `tests/dup.no`／`tests/q.no`／`tests/u128-types.no` сохраняют **0** — для них вся преамбула мёртва. Поэтому доля экономии полностью определяется размером модуля: для однострочной программы −76,5%, для `test-std/src/pbkdf2.no` размером 3,0 МБ — лишь −4,1%.

Можно ли удалить преамбулу целиком? Нет — в интервале есть строковые литералы программы (`@.mir.str.N`), типы и внешние объявления (1 151 bytes), без них не проходит даже `llc`. Более того, `extraFuncs`／`extraFuncsBody` в `codegen.go:75-83` изначально являются генератором по требованию (хелперы option／struct／enum／ptr идут через них), и преамбула — единственная часть, не прошедшая это преобразование; но при переводе её на генерацию по требованию почти всё дополнительно сэкономленное приходится на комментарии — в части кода брать уже нечего.

Оптимизатор сворачивает только **скаляры** (`i64`/`u64`/`i16`/`i32`/`char`/`bool`/`f32`/`f64`). `byte`/`u8`/`i8`, `i128`/`u128`, `option`, срезы, структуры и др. пропускаются: для первых в `emitConst` нет соответствующей ветви (вырождается в 0), арифметика вторых идёт через путь overflow-wrap для `option`, и свёртка изменила бы семантику. Числа с плавающей точкой тоже исключены из всех тождеств — `x * 0.0` для `inf`／`NaN` не равно 0, а `x + 0.0` для `-0.0` не равно `x`.

Главный вывод того сравнения стоит огласить здесь же: **локальная очистка (свёртка констант, удаление мёртвого кода, очистка потока управления) после прогона `opt -O2` имеет почти нулевую предельную ценность** (−0,06%), потому что LLVM делает ту же работу тщательнее. Настоящая отдача — от того, чего LLVM **не может сделать из-за linkage**, а именно от подрезки преамбулы. С подрезкой преамбулы (включая учёт комментариев) общий предельный эффект `mir+llvm_O2` → `mir_opt+llvm_O2` составляет **−19,05% инструкций / −15,83% текста**, а снижение текста при `mir` → `mir+mir_opt` меняется с −14,29% на **−17,75%** (корпус из 631 файла).

## JS-бэкенд

JS-бэкенд (`no build --js` / `no run --js`) компилирует исходный код `.no` в JavaScript (со стиранием типов),
поддерживает две цели — Node.js и браузер, платформенные аннотации `#{js}` / `#{js-browser}`, а также импорт сторонних ESM-модулей
（`# npm/<pkg>`）。

Полная документация по JS (аргументы командной строки, отображение встроенных функций, стандартная библиотека `js/*`, браузерный import map и др.)
собрана в отдельном документе [JS-бэкенд](./lang/js-backend); на этой странице она не повторяется.

## Правила входных точек

- **main.no** — входная точка программы
- **lib.no** — входная точка библиотеки, экспорт функций (подробнее см. [документ по экспорту](lang/export))
- **все файлы `.no` в каталоге tests/** — содержат проверочные утверждения

## Тесты

```bash
# протестировать все файлы .no в каталоге tests
no test

# выполнить один тестовый файл
no test my-test.no

# использовать заданный компилятор или цель
no test -cc zig
no test -target x86_64-windows-gnu
```

Пояснения к тестам:

- тестовые файлы хранятся в каталоге tests/
- каждый тестовый файл собирается отдельно
- если какой-либо тест завершается неудачей, возвращается ненулевой код выхода

## Кэш AST

`no build` / `no run` / `no test` сбрасывают AST, полученный при разборе каждого пользовательского файла, на диск
(по умолчанию `~/.cache/nolang/ast`, путь меняется через `$NOLANG_AST_CACHE_DIR`); при неизменном содержимом AST переиспользуется,
что экономит lex и parse. Стандартная библиотека использует встроенный в компилятор blob и в этом кэше не участвует.

**Вручную очищать не нужно.** Ключ кэша —

```
sha256( ASTVersion ‖ parse-time salt ‖ содержимое исходного файла )
```

причём одной из частей salt является `checker.StdSigKey` — подпись содержимого всех файлов, перечисленных в `src/hash.noml`
(стандартная библиотека + сам компилятор). Поэтому любое изменение компилятора или стандартной библиотеки меняет ключ у собранной через `make`
версии `no`, старые записи естественным образом дают miss и не переиспользуются.

| Команда | Описание |
| --- | --- |
| `no cache stat` | показать каталог кэша, число записей, общий размер и текущий `ASTVersion` |
| `no cache clear` | очистить все записи (только в крайнем случае: если есть подозрение, что записи устарели) |

Переменные окружения:

| Переменная | Действие |
| --- | --- |
| `NOLANG_AST_CACHE_OFF=1` | отключить кэш (полезно при A/B-сравнении компилятора и при поиске «исправленная ошибка вернулась») |
| `NOLANG_AST_CACHE_DIR` | задать каталог кэша. **Одновременно** действует на кэш `-ast.zip` предкомпилированных AST-зависимостей (по умолчанию `~/no/cache/ast`, см. ниже «Предкомпилированные AST-зависимости») |
| `NOLANG_AST_CACHE_MAX` | предел числа записей кэша (по умолчанию 4096) |

> Старые записи просто перестают находиться и вытесняются по мере записи новых, поэтому удалять `~/.cache/nolang/ast` **не нужно**.
> Обратите внимание: `no` нужно пересобирать через `make gen` / `make no`: бинарник, собранный самостоятельно через `cd src && go build`,
> не имеет внедрённого `StdSigKey` и сразу завершится ошибкой, а не молча переиспользует кэш.

## Установка и удаление Binary

### Установка

```bash
# установить пакет текущего каталога (локальная сборка)
no install
no install -u                                   # принудительная пересборка (обновление)

# установить предкомпилированный binary из GitHub Release (рекомендуется): <tool>[:<version>]@<host>/<owner>/<repo>
no install nogit@github.com/lizongying/notools            # последняя версия
no install nogit:v0.1.33@github.com/lizongying/notools    # заданная версия
no install nogit@lizongying/notools                       # host опущен, по умолчанию github.com
no install -u nogit@github.com/lizongying/notools         # принудительная повторная загрузка
```

При удалённой установке берётся **предкомпилированный бинарник**, а не исходный код: имя ассета — `<tool>-<os>-<arch>-<version>` (на Windows с
`.exe`), причём `<os>-<arch>` берётся от платформы, на которой работает сам `no` (например, `darwin-arm64`,
`linux-amd64`), поэтому локальный LLVM-инструментарий не нужен, и устанавливаемый инструмент не обязан быть написан на Nolang.
Если версия опущена, запрашивается `releases/latest`; задание `$GITHUB_TOKEN` (или `$GH_TOKEN`) позволяет избежать
ограничения частоты запросов GitHub API.

Процесс установки:

1. удалённо: разобрать spec → найти ассет release → скачать; локально: собрать из текущего каталога
2. записать binary в `~/no/bin/`
3. создать символическую ссылку в `/usr/local/bin/`

### Удаление

```bash
no uninstall pkg-name
```

Удаление убирает символическую ссылку в `/usr/local/bin/` и binary в `~/no/bin/`.

## Конфигурация проекта

### Формат конфигурации noml

Все конфигурационные файлы Nolang (`package.noml`, `workspace.noml`, `.workspace.noml`, `nolang.lock.noml`, `sum.noml`) используют собственный формат **noml** (Nolang Markup Language), пришедший на смену JSONC. Правила синтаксиса согласованы с самим языком Nolang:

| Правило | Описание |
| --- | --- |
| Объект верхнего уровня | это один объект: `{` и `}` занимают отдельные строки, по одному члену на строку, **без запятых-разделителей** (разделителем служит перевод строки) |
| Ключ | по умолчанию «голый» идентификатор, по тем же правилам, что имя переменной Nolang: строчные буквы/цифры/дефис (в середине)/подчёркивание в начале, не может начинаться с цифры (например, `link-libs`, `anonymous-fn-type`, `dev-dependencies`); ключи, не удовлетворяющие правилам (пути, URL, `@scope/pkg`), пишутся строкой в одиночных кавычках |
| Строковое значение | одиночные кавычки, экранирование через `\`: `\' \\ \n \t` |
| Логическое значение | `true` / `false` (в нижнем регистре, как литералы bool в Nolang) |
| Число | «голый» литерал (зарезервировано для lock-файлов и т. п.) |
| Массив | `[`, элементы, `,`, `]` могут занимать разные строки; элементы разделяются **запятыми**, **поддерживается завершающая запятая**; пустой массив пишется `[]` |
| Комментарий | `;` до конца строки (кроме строковых литералов) |
| Отступ | не имеет смысла (влияет только на читаемость, форматирование не гарантируется) |

`dependencies` / `dev-dependencies` — это **массив строк**, элементы имеют вид `'ключ:версия'` (версию можно опустить, по умолчанию `*`), например:

```noml
{
  dependencies: [
    '/example/test2',                          ; локальный пакет, любая версия по умолчанию
    'github.com/lizongying/nolang/test1:v0.1.0', ; онлайн-пакет, заданная версия,
  ]
}
```

Файл `package.noml` в корне проекта описывает информацию о проекте:

```noml
{
  name: 'my-project'
  version: 'v0.1.0'
  description: 'A new Nolang project'
  keywords: []
  author: ''
  email: ''
  organization: ''
  repository: ''
  homepage: ''
  license: 'MIT'
  dependencies: [
    'fmt',,
  ]
  compiler: {
    version: 'v0.1.0'
  }
  ignore: []
}
```

`compiler.lang` фиксирует язык сообщений этого проекта (`'zh-tw'`, `'ja'` и т. д., запись как у `--lang`): он имеет приоритет над системной локалью,
но уступает `--lang` и `NO_LANG`; если не задан, используется системная локаль.

### Управление зависимостями

```bash
# добавить зависимость: <tool>[:<version>]@<host>/<owner>/<repo>
# номер версии можно опустить (берётся последний release); ключ, записываемый в package.noml — <tool>@<host>/<owner>/<repo>
no add nogit@github.com/lizongying/notools
no add nogit:v0.1.33@github.com/lizongying/notools

# удалить зависимость
no remove pkg-name

# обновить зависимость
no update pkg-name

# обновить все зависимости
no update-all

# вывести зависимости
no list

# синхронизировать зависимости (скачать и создать lock-файл)
no sync
```

### Предкомпилированные AST-зависимости

Зависимости вида `no add <tool>@<host>/<owner>/<repo>` **содержат только AST, без исходного кода**: при компиляции из release
скачивается `<tool>-ast.zip` (zip with one .gob entry per module), декодируется и напрямую внедряется в конвейер компиляции. Использование:

```nolang
# nogit                      # псевдоним пакета; модули доступны как nogit.<module>
# nogit/remote                  # напрямую импортировать модуль remote (или nogit.remote)
# nogit.fn                      # nogit — только имя пакета; найти модуль, определяющий fn
# <host>/<owner>/<repo>/nogit/remote
```

Один zip — это один пакет, который может содержать несколько модулей (каждый как запись `<modulePath>.gob`). Входного модуля нет: `# nogit` лишь создаёт псевдоним пакета (модули доступны как `nogit.<module>`, например `nogit.remote.greet(...)`); `# nogit/remote` импортирует модуль напрямую; `# nogit.fn` ищет модуль по функции. `no fmt` удаляет неиспользуемые `# nogit` / `# nogit/remote`. Версия должна быть конкретной
(`no sync` / компиляция при `""` или `"*"` даёт ошибку). zip кэшируется в `~/no/cache/ast/`,
путь можно переопределить через `$NOLANG_AST_CACHE_DIR`.

Артефакт создаётся через `no pack` (нужны только lexer + parser, LLVM-инструментарий не требуется, подходит для CI):

```bash
no pack -o nogit-ast.zip nogit.no      # один исходный файл
no pack -o nogit-ast.zip ./nogit       # каталог пакета
```

### Типы зависимостей и правила версий

Зависимости в `package.noml` делятся на **локальные пакеты** и **онлайн-пакеты**. Компилятор автоматически определяет тип зависимости по следующим правилам и предупреждает, если локальный пакет использует версию не `"*"`.

#### Правила определения

```
ключ зависимости → поиск в workspace.noml (совпадение короткого имени или полного ключа)
  ├─ найден → локальный пакет (следует использовать "*")
  └─ не найден → проверка префикса пути (начинается с /)
      ├─ да → локальный пакет (следует использовать "*")
      └─ нет → онлайн-пакет (используется номер версии, предупреждения нет)
```

1. **Поиск в `workspace.noml`**: сначала ключ зависимости ищется в `workspace.noml` как короткое имя или полный ключ. Найденный — локальный пакет.
2. **Проверка префикса пути**: если в `workspace.noml` не найдено, но ключ начинается с `/` (путь относительно рабочей области), это тоже локальный пакет.
3. **Остальные — онлайн-пакеты**: ключи, не удовлетворяющие указанным условиям, считаются онлайн-пакетами, для них следует задавать номер версии.

> **Ограничение границы рабочей области**: локальные пути в `package.noml` могут начинаться только с `/` (относительно рабочей области); `./`, `../` и абсолютные пути ОС запрещены. Единственный вход, допускающий выход за границы рабочей области, — сопоставления в `workspace.noml` / `.workspace.noml`. Подробнее см. [Ограничение границы рабочей области](#工作區邊界約束).

#### Различные формы ссылки на локальный пакет

Локальные пакеты поддерживают следующие три формы ссылки; версия во всех случаях должна быть `"*"`:

```noml
dependencies: [
  ; 1. короткое имя: ключ, зарегистрированный в workspace.noml
  'test2',
  ; 2. путь относительно рабочей области: начинается с /, относительно корня рабочей области
  '/example/test2',
  ; 3. полный URL: если в workspace.noml есть соответствующее сопоставление — локальный пакет
  'github.com/lizongying/nolang/test2',,
]
```

> **Внимание**:
> - Третья форма является локальным пакетом только при наличии соответствующего сопоставления в `workspace.noml`. Если `workspace.noml` сопоставляет `github.com/lizongying/nolang/test2` с локальным путём, зависимость локальная (следует использовать `"*"`); иначе онлайн-пакет (следует использовать номер версии).
> - Префиксы `./` и `../` больше не допускаются в `package.noml`. Все локальные пути должны начинаться с `/` (относительно рабочей области).

#### Расширенное применение: онлайн-пакет → локальный пакет

`workspace.noml` может не только регистрировать короткие имена, но и сопоставлять имя онлайн-пакета с локальным путём, реализуя режим разработки «онлайн-пакет как локальный»:

```noml
; workspace.noml
{
  test2: '/example/test2'
  'github.com/lizongying/nolang/test2': '/example/test2'
}
```

При этом зависимость, упомянутая в `package.noml` как `github.com/lizongying/nolang/test2`, разрешается в локальный пакет `/example/test2`, а версия должна быть `"*"`. Это очень удобно при локальной разработке онлайн-пакета — достаточно добавить сопоставление в `workspace.noml`, чтобы переключить удалённую зависимость на локальный исходный код для совместной отладки.

#### Предупреждение о версии

Если при компиляции обнаруживается, что локальный пакет использует версию не `"*"` (например, `"v0.1.0"`), выводится предупреждение с предложением использовать `"*"`. Онлайн-пакеты не подпадают под это ограничение.

#### Рекурсивные сопоставления рабочей области (цепочки между пакетами)

Nolang поддерживает **рекурсивные сопоставления рабочей области**: зависимый пакет может иметь собственный `workspace.noml` с внутренними правилами сопоставления, образуя естественную цепочку разрешения между пакетами. Это ключевое отличие Nolang — `replace`/`patch` в мейнстримных Go/Cargo действуют только в текущем проекте и не передаются внутрь зависимых пакетов.

**Сценарии применения:**
- единые внутренние псевдонимы базовых библиотек
- стандартизация путей импорта
- совместимая миграция многослойных библиотек

**Как это работает:**

При разрешении ключа зависимости компилятор:
1. ищет ключ в текущем `workspace.noml`
2. если сопоставление найдено, проверяет, есть ли в целевом каталоге собственный `workspace.noml`
3. если есть, продолжает поиск по тому же ключу, спускаясь уровень за уровнем
4. пока не будут исчерпаны все глубинные сопоставления

**Пример:**

```
workspace/                  ← рабочая область верхнего уровня
├── workspace.noml         ← {"testkey": "/pkgA"}
├── pkgA/
│   ├── workspace.noml     ← {"testkey": "/pkgB"}
│   └── pkgB/
│       ├── workspace.noml ← {"testkey": "/pkgC"}
│       └── pkgC/           ← конечная цель (без workspace.noml)
```

При разрешении `testkey`:
1. сопоставление в верхнем `workspace.noml` → `/pkgA` (относительно рабочей области)
2. сопоставление в `pkgA/workspace.noml` → `/pkgB` (относительно рабочей области pkgA)
3. сопоставление в `pkgB/workspace.noml` → `/pkgC` (относительно рабочей области pkgB)
4. у `pkgC` нет `workspace.noml` → окончательное разрешение в `pkgC`

**Обнаружение циклов:**

Компилятор ведёт стек посещённых при разрешении корней рабочих областей. Как только обнаруживается циклическое сопоставление (например, A→B, B→A), сразу возникает ошибка с выводом полной цепочки:

```
Error: circular workspace mapping detected: /path/to/A → /path/to/B → /path/to/A
```

> **Внимание**: эта возможность поддерживает только естественную рекурсию между пакетами (зависимый пакет имеет собственный `workspace.noml`), а не ручные цепочки псевдонимов в одном файле.

### Настройка зеркал

В массиве `mirrors` файла `package.noml` задаются адреса зеркал для ускорения загрузки удалённых пакетов:

```noml
mirrors: [
  'https://mirror.example.com/',,
]
```

### Конфигурация рабочей области workspace.noml

`workspace.noml` находится в корне репозитория и описывает рабочую область «один репозиторий — несколько пакетов», представляя собой сопоставление «имя пакета → относительный путь». `no build` без аргументов при наличии `workspace.noml` параллельно компилирует все перечисленные пакеты; `no run` через имя пакета (например, `no run foo`) выполняет отдельный пакет рабочей области.

```noml
{
  foo: '/foo'
  bar: '/bar'
}
```

`no init` определяет рабочую область: если `workspace.noml` не существует, создаётся пустой объект `{}`, **никакие `package.noml` не создаются**; если файл существует, он остаётся без изменений и не перезаписывается. При последующем создании пакета через `no new <name>` в `workspace.noml` автоматически добавляется `"<name>": "./<name>"`.

#### Локальная приватная конфигурация .workspace.noml

Помимо общего `workspace.noml`, Nolang поддерживает локальный приватный конфигурационный файл `.workspace.noml` (обратите внимание на ведущую точку). Рекомендуется добавить его в `.gitignore`; он предназначен для временных замен зависимостей конкретного разработчика.

**Логика загрузки:**

1. сначала загружается общая конфигурация `workspace.noml`
2. затем загружается приватная конфигурация `.workspace.noml`
3. **одинаковые ключи**: приватная конфигурация перекрывает общую
4. **новые ключи**: добавляются поверх

```
workspace/
├── workspace.noml       ← общая конфигурация проекта (в системе контроля версий)
├── .workspace.noml      ← локальная приватная конфигурация (рекомендуется в .gitignore)
├── foo/
└── bar/
```

**Сценарии использования:**

- общие псевдонимы команды и правила перенаправления зависимостей пишутся в `workspace.noml` и попадают в систему контроля версий
- если разработчику нужно временно направить зависимость на локальный fork, достаточно перекрыть её в `.workspace.noml`
- временные форк-сопоставления не загрязняют общую конфигурацию проекта, что сочетает командную работу и гибкость локальной разработки

**Пример:**

```noml
; workspace.noml (общий, в системе контроля версий)
{
  foo: '/foo'
  bar: '/bar'
}

; .workspace.noml (приватный, локальная отладка)
{
  ; перекрываем общую конфигурацию: foo указывает на локальный fork (внутри рабочей области)
  foo: '/my-fork-foo'
  ; добавляем приватное сопоставление: fork вне рабочей области (абсолютный путь ОС, единственный выход)
  'github.com/lizongying/nolang/core': '/home/lzy/code/fork/core'
  ; добавляем приватное сопоставление (внутри рабочей области)
  experimental: '/experimental'
}
```

Итоговые действующие сопоставления: `foo` → `/my-fork-foo` (приватное перекрытие), `bar` → `/bar` (общее сохранено), `github.com/lizongying/nolang/core` → `/home/lzy/code/fork/core` (приватное добавление, выход за рабочую область), `experimental` → `/experimental` (приватное добавление).

### Ограничение границы рабочей области

Nolang жёстко контролирует ссылки на пути, обеспечивая переносимость и безопасность проекта.

#### Обзор правил

| Уровень конфигурации | `/` относительно рабочей области | Абсолютный путь ОС | Переходы `./` `../` |
| --- | --- | --- | --- |
| ключи зависимостей `package.noml` | ✅ разрешено | ❌ запрещено | ❌ запрещено |
| значения сопоставлений `workspace.noml` | ✅ разрешено | ✅ разрешено (выход) | ✅ разрешено (выход) |
| значения сопоставлений `.workspace.noml` | ✅ разрешено | ✅ разрешено (выход) | ✅ разрешено (выход) |
| пути импорта `#` в исходном коде | ✅ разрешено | ❌ запрещено | ❌ запрещено |

#### 1. package.noml (жёстко ограничен, выход за рабочую область запрещён)

`package.noml` — стандартная базовая конфигурация проекта для публикации, CI и командной работы; он коммитится в репозиторий.

```noml
#{fmt-skip}
dependencies: [
  ; ✅ допустимо: начинается с /, относительно корня workspace
  '/vendor/test',
  ; ❌ запрещено: абсолютный путь ОС /home/xxx/...
  ; ❌ запрещено: переходы ./ ../
]
```
```

**Ограничения:**
- локальные пути пишутся только как `/xxx`, база = корень workspace
- абсолютные пути ОС не принимаются
- `./` и `../` не поддерживаются
- нельзя напрямую ссылаться на каталоги вне рабочего репозитория

**Цель:** если разрешить внешние пути, легко получить «у меня компилируется, у других нет», а также риск случайной загрузки чужого кода.

#### 2. workspace.noml + .workspace.noml (единственный выход)

Цели сопоставления поддерживают три формы локальных путей:
- `/xxx` → каталог внутри корня workspace (та же семантика, что у package.noml)
- `./xxx`, `../xxx` → разрешаются относительно корня workspace, выход за границы допустим
- абсолютный путь ОС → можно указать каталог вне рабочей области (fork, внешние компоненты)

```noml
; .workspace.noml — приватная конфигурация для локальной разработки
{
  ; внутри рабочей области
  foo: '/vendor/foo'
  ; переход: fork вне рабочей области
  'github.com/lizongying/nolang/core': '../fork/core'
  ; абсолютный путь ОС: произвольный внешний каталог
  'github.com/lizongying/nolang/utils': '/home/lzy/code/utils'
}
```

**Ключевая логика:** `package.noml` не может напрямую ссылаться на внешний код; чтобы подключить исходный код вне репозитория, пользователь обязан явно задать сопоставление в конфигурации workspace. Это добавляет «явный и видимый переключатель» для межкаталожной загрузки, и все внешние зависимости управляются в одном месте.

#### 3. Соответствующие ограничения на уровне импорта в исходном коде

В исходном коде нельзя напрямую писать абсолютные пути ОС; все ссылки на внешний код идут только через псевдонимы workspace или идентификаторы удалённых пакетов. Переходы `./` и `../` тоже запрещены.

```no
; ✅ допустимо: путь относительно рабочей области
# /vendor/utils.helper
; ✅ допустимо: идентификатор удалённого пакета
# github.com/lizongying/nolang/core.process
; ✅ допустимо: стандартная библиотека
# std/fs
```

```no
#{fmt-skip}
; ❌ запрещено: переход
; # ./utils.helper
; # ../lib/helper.process

; ❌ запрещено: абсолютный путь ОС
; # /home/user/code/core.process
```

#### Демонстрация цепочки потока данных

Сценарий: корень workspace бизнес-проекта — `/code/project`, нужно использовать внешний `/code/fork/core`

❌ так делать нельзя (package.noml запрещает):

```noml
; package.noml
dependencies: [
  '/code/fork/core', ; некорректно: невозможно выйти за рабочую область,
]
```

✅ правильный способ (преодоление границы через сопоставление workspace):

```noml
; .workspace.noml
{
  'github.com/lizongying/nolang/core': '/code/fork/core'
}
```

```no
; обычный импорт в исходном коде
# github.com/lizongying/nolang/core
```

#### Рабочий процесс workspace

Входной каталог компиляции и выполнения всегда — **каталог рабочей области** (там, где находится `workspace.noml`). Общий процесс таков:

1. пользователь выполняет `no build` или `no run <имя пакета>` в каталоге рабочей области
2. компилятор читает `workspace.noml` и по имени пакета находит соответствующий подкаталог
3. загружается `package.noml` этого подкаталога (то есть корень пакета), и сборка/запуск идут от корня пакета
4. все пути импорта (`use /path/to/module`) **разрешаются относительно корня рабочей области** (см. [Соглашение о разрешении путей](path-resolution.md)), то есть единственной базой служит каталог с `workspace.noml`, а не пакет, из которого идёт импорт.

```
workspace/               ← каталог рабочей области (здесь находится workspace.noml)
├── workspace.noml      ← сопоставление имени пакета → путь
├── foo/                 ← пакет foo
│   ├── package.noml        ← корень пакета foo
│   ├── main.no
│   └── lib.no
└── bar/                 ← пакет bar
    ├── package.noml        ← корень пакета bar
    └── main.no
```

> **Внимание**: пути импорта считаются от **корня рабочей области** (каталога с `workspace.noml`), а не от каталога `package.noml` пакета. Если в подкаталоге пакета есть вложенный `package.noml`, `LoadPackage` ищет вверх ближайший `package.noml` и считает его корнем пакета, но разрешение импорта всегда идёт от корня рабочей области.

## Примеры применения

- [notools](https://github.com/lizongying/notools) — набор распространённых инструментов командной строки Unix, реализованных на Nolang, включая классические утилиты cat, ls, grep, wc, head, tail и другие. Демонстрирует практические возможности Nolang в области системного программирования.
