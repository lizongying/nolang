# 코딩 규칙

## 파일 끝 줄바꿈(Trailing Newline / EOF)

모든 **비어 있지 않은** `.no` 원본 파일은 **정확히 하나의 끝 줄바꿈 문자로 끝나야 합니다** (즉, 파일 마지막에 빈 줄이 하나 있어야 합니다).

- 파일에 끝 줄바꿈이 **없으면** 하나를 추가합니다.
- 파일 끝에 **여러 개**의 빈 줄이 있으면 단일 끝 줄바꿈으로 합칩니다.
- **빈 파일**(0바이트)은 그대로 둡니다.

제외 디렉터리: `dist/`, `vscode-nolang/`, `node_modules/`.

이유: EOF 에 단일 줄바꿈을 통일하면 `git diff` 에 "no newline at end of file" 이 나타나지 않아 변경 내역이 더 깔끔해지고, 도구 연결 및 이어 붙이기 동작도 예측 가능해집니다.

### 자동 실행(도구 모음 내장)

이 규칙은 도구 모음이 **자동으로 실행**하며 별도의 스크립트가 없습니다.

- **`no fmt`**: `src/cmd/no/main.go` 의 `fmt` 하위 명령이 파일을 제자리에서 포맷하고 `fmt.FormatFile` 을 호출하여 정확히 하나의 끝 줄바꿈을 보장합니다.
- **LSP 저장 시 포맷 / `textDocument/formatting`**: `src/lsp/server.go` 의 `formatNolangCode` → `fmt.FormatFile` 가 편집기에서 `.no` 파일을 저장하거나 수동으로 포맷할 때 EOF 줄바꿈을 자동으로 추가하거나 합칩니다.

구현은 `src/fmt/formatter.go` 에 있습니다.

- `FormatFile(code)` 은 전체 파일을 포맷하고 `ensureTrailingNewline` 을 호출합니다. 끝의 모든 `\r` / `\n` 을 제거하고(CRLF 및 여러 개의 끝 빈 줄 호환) `\n` 을 하나 추가합니다. 빈 파일이나 파싱할 수 없는 내용은 원본 그대로 반환하여 파일이 손상되지 않도록 합니다.
- `Format(code)` 은 순수 조각 포맷 함수이며(끝 줄바꿈을 추가하지 않음) 주로 단위 테스트에 사용됩니다. 실제 원본 파일에 기록할 때는 `FormatFile` 을 사용하세요.

## 가져오기 문장 자동 정리(중복 제거 / `# std/fmt` 제거 / 정렬)

`no fmt` (및 LSP 저장 시 포맷)은 파일 맨 위의 연속된 가져오기 구간 (`# path[.fn] [alias]`) 을 자동으로 정리하며, 구현은 `src/fmt/imports.go` 에 있습니다.

1. **중복 제거**: 완전히 동일한(경로, 함수 이름, 별칭이 글자까지 동일한) 가져오기는 첫 번째 항목만 남깁니다.
2. **`# std/fmt` 자동 제거**: `print` / `eprint` / `format` / `sprintf` 는 컴파일러 내장 함수이고 표준 라이브러리 모듈은 암시적으로 로드할 수 있으므로([모듈 간 호출 접두사](./module) 참조) `# std/fmt` 는 결코 필요하지 않으며, 작성해도 formatter 가 제거합니다. 다음 두 가지 예외는 유지됩니다.
   - **별칭**이나 **함수 가져오기**를 쓴 경우(예: `# std/fmt.sprintf fm`) — 의도적인 이름 바인딩입니다.
   - 가져오기 줄에 **주석**이나 붙어 있는 **`#{...}` 애노테이션**이 있는 경우 — 사용자가 작성한 내용을 조용히 버릴 수 없습니다.
3. **자동 정렬**: 경로 → 함수 이름 → 별칭 순으로 사전순 안정 정렬을 수행합니다.

보수적 경계: 구간 내 어느 가져오기든 주석(위쪽 독립 줄 또는 같은 줄 끝에 붙은)이나 붙어 있는 `#{...}` 애노테이션(예: `#{bind=ffi}` 네이티브 바인딩 전략)이 있으면 전체 구간의 원래 순서를 유지하고 제거하지 않습니다. 정렬하면 주석과 문장의 대응 관계가 흐트러지고, 삭제하면 주석까지 함께 사라지기 때문입니다. 이때도 "아무런 부착 내용이 없는 완전 중복 항목"은 제거됩니다.

파일 맨 위가 아닌 곳(코드 뒤)에 나타나는 가져오기 구간은 모두 원본 그대로 유지됩니다.

```no
#{fmt-skip}
; 格式化前                          ; 格式化後
# std/vec                           # std/io
# std/fmt                           # std/vec
# std/io
# std/fmt        ;→  print、format 為內建，# std/fmt 移除；其餘按字典序排序
```

## 주석 표기(Comment Markers)

Nolang은 두 가지 **단일 줄 주석** 표기와 한 가지 **여러 줄(블록) 주석** 표기를 지원하며, 의미는 다음과 같습니다.

- `//` — 기존 단일 줄 표기(줄 끝까지 주석)
- `;` — 대체 단일 줄 표기(2026-07-17 구현, 줄 끝까지 주석)
- `;; ... ;;` — 여러 줄(블록) 주석(2026-07-18 구현, 대칭 구분자이며 닫히지 않으면 파일 끝까지 주석)

```no
#{fmt-skip}
// 這是註釋
; 這也是註釋，語義相同
x = 1 ; 行內註釋，註釋到行尾

;;
   這是多行（塊）註釋
   可以跨多行
   以 ;; 結尾 ;;
y = 2 ;; 行內塊註釋 ;;
```

**블록 주석 구분**: `;;` 로 시작하고 `;;` 로 끝나며, 둘 사이(줄바꿈 포함)는 모두 주석 내용입니다. 내용 안의 단일 `;` 는 블록을 끝내지 않으며 오직 `;;` 만 끝냅니다. 닫는 `;;` 를 찾지 못하면 `;;` 부터 파일 끝까지 계속 주석 처리됩니다. 시작 구분자 `;;` 뒤에는 줄바꿈까지 공백만 있어야 여러 줄 모드로 진입한 것으로 간주합니다. 같은 줄 `;;` 뒤에 글자가 있으면 일반 단일 줄 주석입니다(예: `;; 설명 문구` 는 해당 줄만 주석 처리하며 다음 줄은 여전히 코드입니다). 끝 구분자도 마찬가지로 `;;` 뒤에 공백만 남아야 닫힌 것으로 간주합니다.

**포맷 시 원래 표기 유지**: `no fmt` 는 주석의 표기를 바꾸지 않습니다. `;` 는 그대로 `;`, `//` 는 그대로 `//`, `;; ... ;;` 는 그대로 `;; ... ;;` 입니다. formatter 는 `Comment.Marker` 를 통해 원래 표기를 기억하고 그대로 출력하며, 블록 주석 내용(내부 줄바꿈 포함)도 글자 단위로 유지되므로 포맷은 멱등합니다.

**안전 범위**: `;` / `;;` 가 문자열 리터럴(예: `'text/plain; charset=utf-8'`, `index-from(';', pos)`)과 `//` 주석 내부에 나타나면 lexer 의 문자열 스캐너와 주석 스캐너가 먼저 소비하므로 주석 표기로 취급되지 않습니다.

**`cond -> X; Y` 주의**: 이제 `;` 는 주석이므로 `cond -> X; Y` 는 "`cond -> X` 실행 (`X` 를 평가한 뒤 버림)"과 줄 끝 주석 `; Y` 로 파싱됩니다. `X` 에는 값이 할당되지 **않습니다**. 올바른 표기는 `cond -> X = Y` 입니다(stdlib 의 기존 관례. `arr.no`, `uuid.no`, `path.no`, `err.no`, `assert.no` 참조). 소스 코드에서 `cond -> X; Y` 를 보거든 우선 `cond -> X = Y` 로 고치세요.

**한 줄에 여러 문장 쓰기 금지**: `;` 는 주석 표기일 뿐이므로 같은 줄에서 여러 문장을 연결하는 데 쓸 수 없으며, 쉼표 `,` 도 문장을 연결하지 못합니다. 블록 `{ ... }` 안의 각 문장은 반드시 각자 한 줄을 점유해야 합니다. 블록을 한 줄로 압축하는 것이 가장 위험한 실수입니다.

```no
#{fmt-skip}
; ❌ 錯誤：`; return }` 整段變成註釋，塊的 `}` 隨之消失
cond -> { print('X'); return }
```

```no
; ✅ 正確：每條語句獨佔一行
cond -> {
    print('X')
    return
}
```

`cond -> { print('X'); return }` 는 실제로 `cond -> { print('X')` 만 남습니다. 블록이 닫히지 않으므로 `}` 뒤의 문장(대개 해당 함수의 남은 전체 함수체, 나아가 이후 모듈 수준 함수까지)이 통째로 삼켜집니다. 컴파일러가 반드시 오류를 내는 것은 아니며 오류 위치가 크게 어긋날 수도 있어 극히 찾기 어렵습니다.

## 불리언 리터럴과 `== true` / `== false` 단순화(2026-09-24 구현)

`true` / `false` 키워드 외에도 Nolang은 두 가지 **불리언 리터럴 축약형**을 받아들입니다.

- `!!` — `true` 와 동등한 독립 리터럴입니다.
- `!` — `false` 와 동등한 독립 리터럴입니다(`!` 뒤에 피연산자의 시작이 될 수 있는 기호가 아닐 때만 해당합니다. 뒤에 줄바꿈 / `;` / 파일 끝 / `)` / `}` / `]` / `->` 가 오면 `false` 로 파싱됩니다).

> 주의: 여기서 말하는 것은 **표현식 위치**의 `!!` / `!` 이며, 반복문 위치의 `!! { }` (항상 실행), `! { }` (실행하지 않음) 와는 다릅니다.

이 두 축약형은 **파싱 단계**에서 일반 `BooleanLiteral` 로 변환되므로 `f == true`, `f == !!`, `f == false`, `f == !` 네 가지는 문법적으로 완전히 동등하며 동일한 처리 로직을 따릅니다.

`no fmt` 의 불리언 처리 규칙(구현: `src/fmt/expr.go`):

- **독립 리터럴은 키워드 표기로 통일**: `c = !!` → `c = true`, `c = !` → `c = false`.
- **확인된 것만 단순화하고 모르는 것은 단순화하지 않음**: `==` / `!=` 의 한쪽이 불리언 리터럴이고 다른 쪽 피연산자가 bool 값임을 확증할 수 있을 때 가장 단순한 형태로 출력합니다. 네 가지 경로가 동일한 시그니처 수집 기준 (`collectModuleSignatures`: std 내장 테이블, `use` / `#` 가 가리키는 로컬 모듈, `EnumVariants`) 과 동일한 `SemRebuildConfig.Apply` 주입 계약을 공유하며, 차이는 테이블 제공자뿐입니다. `no fmt` / LSP 는 `build.FmtSigLoader` 가 테이블을 제공하고, `no build` / `no vet` 은 여전히 `preloadModuleSignatures` + `astParseConfig` 를 사용합니다(아직 단일 loader 로 합쳐지지 않았습니다). `no fmt` 는 fresh `SkipLowering` parse 전에 주입하고, LSP 는 `ParseDocument` 가 주입한 뒤 `parseSnapshot` 을 게시하며, format-on-save 는 동일한 설탕 AST 의 깊은 복사본 (`fmt.CloneProgramForFormat`) 을 재사용하므로 기본 설정에서는 추가 parse 가 없습니다. 확증할 수 있는 출처는 세 가지가 있습니다.

  1. 명시적 타입 표기: `b bool = true`, 매개변수 `(b bool)`;
  2. 불리언 리터럴 할당: `flag = true` / `flag = false`;
  3. `bool` 을 반환한다고 선언된 함수 호출: 같은 파일에 정의된 경우(예: `bytes-eq = ... (eq bool)`) 또는 시그니처 테이블에서 찾을 수 있는 std / 로컬 모듈 함수(예: `args.has-flag`, 로컬 모듈 `helper.is-ok`). 변수 receiver 의 메서드 호출(`s.starts-with('a')`)은 Sem 이 추론한 receiver 타입 (`s: str`) 에 따라 `str.starts-with` 를 조회합니다. 타입이 추론되지 않았거나 같은 이름의 변수가 서로 다른 스코프에서 다른 타입으로 추론되면 여전히 알 수 없는 것으로 봅니다("메서드 이름이 전역에서 유일하다"는 추측은 의도적으로 하지 않습니다. `?bool` 을 순수 bool 로 오해하지 않기 위해서입니다). 시그니처 테이블에서 결과 타입을 찾지 못해도 알 수 없는 것으로 봅니다.

  | 원래 표기(아래 표의 `b` 는 위의 "알려진" 변수) | 포맷 후 |
  | ------------------------------------------ | -------- |
  | `b == true` / `b == !!`                    | `b`      |
  | `b == false` / `b == !`                    | `! b`    |
  | `b != true` / `b != !!`                    | `! b`    |
  | `b != false` / `b != !`                    | `b`      |
  | `true == b` (리터럴이 왼쪽에 있음)          | `b`      |

  `!=` 는 극성만 뒤집습니다. `true == false` (양쪽 모두 리터럴) 는 원대로 두고 변경하지 않습니다.
  `f == true` 처럼 bool 근거가 없는 bare 이름은 원대로 유지됩니다.

- **  `?T` 와 모든 알 수 없는 피연산자는 원래 비교를 유지**: option (`?T`), 시그니처 테이블에서 결과 타입을 찾을 수 없는 모듈 간 호출, 값이 할당되지 않은 bare 이름, 타입이 추론되지 않은 점 표기 접근, 호출식, 연산 결과는 모두 `== true` / `== false` 를 그대로 유지합니다. 이를 bare `x` / `! x` 로 접어 제어 흐름 조건으로 쓰면 MIR 이 "option-as-i1" codegen crash 에 부딪힙니다. v0.3.3 이 바로 그 이유로 이 규칙 전체를 revert 했고 (`8a8ecb59`), 2026-11-15 에 "긍정적 확증이 있을 때만 단순화"로 바꾼 뒤 복구했습니다. "`?T` 를 찾지 못하면 값으로 간주"하는 역추론은 더 이상 쓰지 않습니다. 같은 날부터 `no fmt` / LSP 도 모듈 간 시그니처를 주입하므로 `fs.write-str(...)` (`?bool`) 같은 option 반환이 **보이게** 되었고, "타입이 안 보여서"가 아니라 option 하드 게이트가 이를 막습니다. option 은 **독립 하드 게이트** (`boolOperandIsOptionTyped`) 이며 bool 값 증거 판정보다 먼저 동작하므로 타입 표기가 원본 파일에 남아 있든 아니든 단순화하지 않습니다. `ok ?bool = fs.write-str(...)` 와 `ok = fs.write-str(...)` 두 표기 모두 비교를 유지합니다. `no fmt` 가 기존 규범 (`fixRedundantTypeSource`) 에 따라 중복 타입 표기를 제거하는 것은 **올바른 동작**이며, option 판정을 보존하려고 이 제거를 끄지 마세요. 회귀 테스트: `src/fmt/bool_comparison_test.go`, `src/fmt/signatures_test.go`, `src/lsp/fmt_gate_test.go`.
- **`->` 분기 / 독립 if-then 조건에서도 동일하게 적용** (알려진 변수에 대해): `b == ! -> return` → `! b -> return`.
- **연산 우선순위 안전**: 부정을 `! ` (공백 하나 포함) 로 써서 전위 연산자의 기존 관례에 맞추고 `no fmt` 의 멱등성을 보장합니다. 현재 확증 가능한 피연산자는 모두 식별자이므로 `!` 가 다시 결합되지 않습니다. 구현은 향후 판정을 완화할 때를 대비해 비원자 피연산자에는 괄호 보호를 유지합니다(`! a + b` 가 아니라 `! (a + b)`).

## 반환값 변수의 지연 영 초기화(Deferred Zero-Init for Return Values)

Nolang 함수의 이름 있는 결과 매개변수(out 매개변수)는 **지연 영 초기화** 전략을 사용합니다. 함수 prologue 는 out 매개변수를 영값으로 초기화하지 **않으며**, 컴파일러는 대신 bitmap `%__ret_init_bitmap` 을 사용하여 각 out 매개변수가 함수체 내에서 명시적으로 할당되었는지 추적합니다. 함수가 반환될 때 명시적으로 할당되지 않은 out 매개변수에는 해당 타입의 영값 store 가 자동으로 채워집니다(정수 → `0`, str-long → `zeroinitializer`, struct → `zeroinitializer`, option → `nil`). 이 메커니즘은 기존의 `%__move_bitmap` 지연 해제 메커니즘과 대칭입니다.

### 이렇게 설계한 이유

- **성능**: prologue 가 모든 out 매개변수에 대해 `store zeroinitializer` 를 한 번씩 수행한 뒤 함수체의 할당으로 덮어써지는 것을 피합니다. 이는 순수한 중복 store 입니다. 지연 전략은 실제로 할당되지 않았을 때만 영값을 한 번 채웁니다.
- **가독성**: 함수 시작 부분에 `found = false` / `result = nil` 처럼 미리 영값을 할당하는 상용구 코드를 작성할 필요가 없으므로, 독자는 "성공 경로에서만 값이 할당된다"는 의도를 바로 볼 수 있습니다.
- **일관성**: `%__move_bitmap` 의 지연 해제 메커니즘과 동일한 bitmap 추적 패턴을 사용하므로 컴파일러 내부 구현이 대칭입니다.

### 권장하는 방법

함수 시작에서 out 매개변수에 미리 영값을 할당하지 마세요. 컴파일러가 반환 시 자동으로 영값을 채웁니다. "성공 경로"의 할당만 작성하면 됩니다.

```no
; Good：不寫提前賦零值，編譯器自動處理
hashmap-str-tmpl.contains = (key str) (found bool) {
    val ?v = .get(key)
    val: {
        ok -> found = true

        err -> {
        }

        nil -> {
        }
    }
}
```

### 안티패턴(피할 것)

중복되는 사전 영값 할당을 작성하지 마세요. 이는 이후 할당으로 덮어써지는 무효 store 일 뿐입니다.

```no
#{fmt-skip}
; Bad：冗餘的提前賦零值
hashmap-str-tmpl.contains = (key str) (found bool) {
    found = false              ; 冗餘——編譯器會在返回時自動補零
    val ?v = .get(key)
    val: {
        ok -> found = true
        err -> {}
        nil -> {}
    }
}
```

### Option 의 기본값은 nil

`?T` option 타입의 out 매개변수에 대해 컴파일러는 영값을 채울 때 `nil` (tag=1, data=0) 을 직접 기록하며, 이는 `result = nil` 과 동일합니다. 따라서 "찾지 못함 / 빈 컬렉션 / EOF" 같은 경로는 bare `return` 만으로 충분하며 소스 코드에 `result = nil` 을 쓸 필요가 없습니다.

```no
#{fmt-skip}
; Good：未命中路徑用裸 return，編譯器自動補 result = nil
hashmap-str-tmpl.get = (key str) (result ?v) {
    .size == 0 -> return        ; 編譯器補 result = nil
    ...
    ; fall-through：編譯器補 result = nil
}
```

### 디버깅 팁

함수가 예상과 다른 영값을 반환하면(예: `found` 가 `true` 여야 하는데 `false` 가 나오거나 `result` 에 값이 있어야 하는데 `nil` 인 경우) 함수체 내에서 영값이 아닌 값을 반환해야 하는 **모든 경로**가 out 매개변수에 명시적으로 값을 할당했는지 확인하세요. 컴파일러는 의도를 추측하지 않으며, 할당되지 않은 out 매개변수에만 영값을 채웁니다. 자세한 내용은 `.agents/skills/nolang-debug/SKILL.md` 의 디버깅 팁을 참조하세요.

## 출력 슬롯을 기존 변수에 직접 바인딩하기(중간 변수 피하기)

**권장하는 방법**: 새 코드를 작성할 때 호출 결과가 기존 변수를 이어서 갱신하기만 한다면 출력 슬롯을 **그 변수에 직접 바인딩**하고, 한 번만 쓰는 임시 저장 변수를 새로 만들지 마세요. 이는 여러 출력이 있고 수신자 자체가 갱신 대상 상태일 때 특히 흔합니다.

```no
; ✅ 推薦：餘數直接寫回 r（r 同時是方法接收者）
qsq, r = r.div-mod(modulus)
```

```no
; ❌ 避免：msq 只被寫回一次，沒有其它用途
qsq, msq = r.div-mod(modulus)
r = msq
```

- 사용하지 않는 출력은 `_` 로 자리 표시: `_, r = r.div-mod(modulus)` 는 새 변수를 하나도 도입하지 않습니다.
- 읽기 전용 입력 참조와 출력 슬롯이 같은 객체를 가리키는 것은 〈별칭 규칙〉상 허용됩니다. `src/std/bigint.no` 의 `r = r._mul(r)` 도 같은 종류의 제자리 갱신이며, 단일 출력에도 적용됩니다.
- 이는 **새로 작성하는 코드**에 대한 권장 방법이며 리팩터링 명령이 아닙니다. 이미 유효한 기존 코드는 스타일을 위해 다시 작성하지 마세요(〈황금률〉 참조).
- 완전한 의미, 실제 측정 결과, 적용 범위는 [언어 참조: 함수 정의](./syntax)를 참조하세요.

## Markdown 코드 블록(`no fmt -md`)

`no fmt -md` 는 ```` ```no ```` / ```` ```nolang ```` 펜스 **내부**의 내용만 정리하며, 펜스 줄과 나머지 Markdown 은 글자 단위로 유지합니다. 블록 내용은 Nolang 소스로 파싱하고, 파싱할 수 없으면 블록 전체를 원대로 남기고 줄 번호를 보고하며 손상시키지 않습니다. (`-md` 와 `-fix` 는 상호 배타적이며 포맷만 담당합니다.)

### 올바른 예제와 잘못된 예제는 각각 별도 블록으로

같은 블록에 "올바른 표기"와 "잘못된 표기"를 함께 쓰면 둘이 한 프로그램으로 취급됩니다. 올바른 절반은 `no fmt` 검증을 잃고, 잘못된 절반은 포맷 과정에서 "일단 고쳐져" 문제가 보이지 않게 될 수 있습니다. 따라서:

- **올바른 예제**는 별도 블록으로 만들고 주석을 넣지 않아 `no fmt` 가 포맷하고 검증하도록 합니다.
- **잘못된 예제**는 별도 블록으로 만들고 첫 줄에 `#{fmt-skip}` 을 써서 검증도 수정도 하지 않도록 합니다.

```no
; ✅ 正確：每條語句獨佔一行
cond -> {
    print('X')
    return
}
```

```no
#{fmt-skip}
; ❌ 錯誤：`;` 之後整行都是註釋，塊的 `}` 隨之消失
cond -> { print('X'); return }
```

### `#{fmt-skip}` 의 세 가지 용도

1. **잘못된 예제 / 반례** — 애초에 유효한 프로그램이 아니므로 포맷은 오히려 방해가 됩니다.
2. **의사 코드 및 시그니처 요약** — 구현이 없는 형태만 있는 조각(예: `f = (a i64) (r i64) { ... }` 의 시그니처 골격).
3. **주석 열을 정렬한 빠른 참조 표** — `no fmt` 은 `code      ; 설명` 을 `code; 설명` 으로 압축하는데, 열 정렬이 바로 이런 표의 가독성 원천이므로 필터링해야 합니다.

### "전개 막기"를 위해 주석을 넣지 마세요

`no fmt` 는 빈 블록 `{ }` 과 단일 줄 분기 `-> { x() }` 를 여러 줄로 전개합니다.

```no
ok = (b bool) (yes bool) {
}

dispatch = (cmd str) {
    cmd == 'a' -> {
        fa()
    }
}
```

이는 **받아들여야 하는** 규범적 형태입니다. 전개된 뒤에야 블록 안에 후속 문장을 삽입할 독립된 줄이 생기며, 그렇지 않으면 한 줄을 추가할 때마다 먼저 블록을 수동으로 분리해야 합니다. 마찬가지로 `true -> {}` 가 `true -> {\n}` 로 바뀌어도 되돌릴 필요가 없습니다. 정말로 `#{fmt-skip}` 이 필요한 곳은 위의 세 가지(반례, 의사 코드, 정렬 표)뿐입니다.

### 주석만 있는 블록에는 애노테이션이 필요하지 않습니다

블록 전체에 주석만 적은(올바른 표기를 "주석 처리한") 블록은 문장이 0개로 파싱되며, `no fmt` 은 "정리할 것이 없다"고 보고 원대로 남기고 아무것도 보고하지 **않습니다**. 애초에 문법 오류가 아니므로 `#{fmt-skip}` 을 넣으면 오히려 사실을 숨길 뿐입니다.

### 순서: 먼저 애노테이션을 넣고, 그다음 포맷

`no fmt -md -w` 는 필터링되지 않은 모든 블록을 제자리에서 다시 씁니다. 잘못된 예제가 포맷 도구에 의해 "수정"되는 순간 반례가 성립하지 않게 되고 원래 표기는 복구할 수 없습니다. **먼저 `#{fmt-skip}` 을 보태고, 그다음 `-w` 를 실행하세요.**
