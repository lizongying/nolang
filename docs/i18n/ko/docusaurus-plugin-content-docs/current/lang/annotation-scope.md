# 애노테이션과 주석의 스코프

`#{...}` 애노테이션 자체에는 "내가 얼마나 넓은 범위를 관장하는가"에 대한 정보가 없습니다. 범위는 **어느 노드에 붙어 있는가**에 따라 결정됩니다.
이 페이지는 이를 확정합니다. 하나의 위치, 하나의 판정 체계, 네 단계, 그리고 "어떤 키는 그중 일부 단계만 지원할 수 있다"는 규칙(`overflow` 이 L3 만 인정하는 그 키입니다. §4.1 참조)을 통해 작성자, `no fmt`, `no vet`, codegen, LSP 가 같은 줄의 애노테이션에 대해 동일한 답을 내도록 합니다.

> 왜 반드시 확정해야 하는가: 같은 `#{overflow=wrap}` 에 대해 `no vet` 는 전체 함수를 관장한다고 보고 codegen 은 다음 줄만 관장한다고 보면 "vet 는 전부 통과인데 런타임에는 여전히 `err` 를 반환"하는 조용한 의미 드리프트가 발생합니다.
> 스코프는 애노테이션의 속성이 아니라 **독자 간의 합의**입니다. 합의를 문서로 고정하지 않으면 저마다 흘러갑니다.

---

## 1. 한 가지 원칙: 스코프는 호스트가 결정한다

애노테이션이 올 수 있는 합법적인 위치는 두 가지뿐입니다(위치 규칙 자체는 [`syntax.md`](syntax.md)의 〈애노테이션 위치〉 참조):

```no
; ① 上方：獨佔一行，置於目標之上
#{overflow=wrap}
x i8 = a + b

; ② 尾隨：寫在目標同一行的後方
x i8 = a + b #{overflow=wrap}

; 多行目標（函式、區塊）的尾隨寫在收尾 `}` 之後
greet = () {
    print('hi')
} #{mac-arm64}
```

**두 가지는 완전히 동등**합니다. 같은 키, 같은 호스트, 같은 스코프이며, `no fmt` 도 한쪽을 다른 쪽으로 바꾸지 않습니다(끝에 붙인 것은 끝에, 위에 둔 것은 위에 그대로). 어떤 것을 선택할지는 가독성만 보면 됩니다. 짧은 문장은 끝에 붙이는 것이 줄을 하나 아끼고, 연산 전체에 주석을 달아야 하거나 문장이 길 때는 위에 둡니다.

**대상 앞의 같은 줄에 쓰는 것은 컴파일 오류**이며, "전위 애노테이션이 뒤에 작용한다"는 길은 없습니다.

```no
#{overflow = wrap} x i8 = a + b   ; ✗ 前綴 → 報錯
```

판정은 세 단계로 이루어지며 각 단계에는 답이 하나뿐입니다.

| 단계 | 질문 | 답의 근거 |
| --- | --- | --- |
| 1 | 호스트가 누구인가? | 위치: 위쪽의 첫 번째 애노테이션/주석이 아닌 줄의 문장, 또는 같은 줄의 이전 문장 |
| 2 | 호스트는 어느 단계에 속하는가? 해당 키가 그 단계를 지원하는가? | §2 의 표 + §4 의 행렬(지원하지 않으면 컴파일 오류) |
| 3 | 어디까지 덮이는가? | 호스트 서브트리에서 내부 하드 경계를 뺀 범위(§3) |

## 2. 네 단계

| 단계 | 호스트 | 적용 범위 | 표기 예시 |
| --- | --- | --- | --- |
| **L0 모듈 단계** | 파일 머리 | 해당 파일의 모든 선언과 문장 | 파일 맨 위에 두고, 이후 내용과 빈 줄 하나로 구분 |
| **L1 선언 단계** | 상수/전역 변수, 구조체, 인터페이스, 태그 열거형, 함수, 메서드 | 해당 선언의 전체 정의(함수는 함수체와 모든 중첩 블록 포함) | 선언 바로 위에 붙이거나 선언 줄 끝에 붙임 |
| **L2 블록 단계** | 코루틴 그룹, if 그룹, `cond -> body`, match, `for`/카운트/범위 반복문, 베어 블록 | 해당 블록체 안의 모든 문장(중첩 블록 포함, 내부 L1 경계에서 멈춤) | 블록 헤드 문장 바로 위에 붙이거나 블록 끝 `}` 뒤에 작성 |
| **L3 단일 줄 단계** | 단일 문장(`let`, 할당, `?=`, `return`, 호출, `cond ->` 분기) | 해당 문장 자체와 그 표현식 | 문장 바로 위에 붙이거나 같은 줄 끝에 붙임 |

### L0 모듈 단계

위치는 **파일 맨 앞** (앞에 어떤 문장이나 import 도 없음)이며, 애노테이션 그룹과 첫 문장 사이에 **빈 줄이 하나 이상** 있어야 합니다. 여기서 빈 줄은 "스코프 종결자"로, 이 애노테이션 그룹이 다음 문장이 아니라 파일 전체에 속한다는 뜻입니다.

```no
#{win-amd64}

; ↑ 空行 → 模組級：本檔只在 Windows x86_64 編譯
; 以下所有宣告與語句都在管轄內
helper = () {
    print('windows only')
}

label = 'win'
```

빈 줄이 없으면 일반적인 L1 입니다(첫 선언에 붙음). 이 경계 덕분에 기존 코드를 마이그레이션할 필요가 없습니다.

```no
#{buildin}
bool.to-str = () (out str) {
}
```

모듈 단계는 "파일 전체에 의미가 있는" 키에만 유용합니다(현재는 플랫폼 키뿐). 선언 키 (`buildin`, `generic`, `embed`…) 가 L0 에 나타나는 것은 "범위를 넓힌 것"이 아니라 오류입니다. `overflow` 도 L0 을 받지 **않습니다**. L3 만 인정하기 때문입니다.

파일 간 설정은 애노테이션에 속하지 않으며 `package.noml` 에 작성합니다.

### L1 선언 단계

```no
; 整個結構體：欄位佈局由型別標記決定
#{inline}
holder {
    inl point
    out point
}

; 整個函式：進出日誌自動帶呼叫者
#{track-caller}
log.write = (msg str) {
    ...
}

; 整個常量宣告：嵌入目錄（路徑相對 package.noml）
#{embed='assets'}
ASSETS fs.embed

; 編譯期剔除整棵子樹（含函式體）
#{mac-arm64, linux-arm64}
greet = () {
    print('hello from unix')
}
```

L1 내부에는 **멤버 단위**도 있습니다. 구조체 필드, 태그 열거형 변형, C 스타일 열거형 멤버 위의 애노테이션(`a pt #{inline}`, `ok(v i64) #{inline}`) 은 전체 타입이 아니라 해당 멤버를 관장합니다. 멤버 애노테이션도 위치는 두 가지뿐입니다. 멤버 바로 위 한 줄에 붙이거나 멤버와 같은 줄 뒤에 작성합니다(끝에 붙이는 것이 관례).

### L2 블록 단계

호스트가 "블록 헤드 문장"일 때 스코프는 블록체 전체입니다.

```no
; 整塊被排除（不生成 IR，也不做型別檢查）
#{win-amd64}
2 * {
    print('windows only')
}

; if 組同樣以整組為單位
x = 1
#{win-amd64}
{
    x == 1 -> print('arm-1')
    -> print('arm-other')
}
```

네 종류의 블록 헤드 모두 적용됩니다: 코루틴 그룹(`awy { ... }`), if 그룹(`{ cond -> … }`), 단일 조건 문장(`cond -> body`), match, `for` / 카운트 / 범위 반복문.

`cond -> body` 의 body 가 단일 문장이면 L2 와 L3 의 결과가 같습니다. 블록으로 작성해야 차이가 생깁니다.

**모든 키가 네 단계를 다 사용하는 것은 아닙니다.** 어떤 키는 그중 일부 단계만 지원할 수 있으며, 지원하지 않는 단계에 쓰는 것은 **컴파일 오류**이지 "한 줄 더 쓴 무해한 중복"이 아닙니다. 현재 유일하게 제한된 키는 `overflow` 이며 L3 만 인정합니다. 이유는 §4.1 참조.

### L3 단일 줄 단계

```no
a i8 = 100
b i8 = 100
; 只管緊跟的下一條陳述（尾隨寫法 `c = a + b #{overflow=wrap}` 等價）
#{overflow=wrap}
c = a + b
c: {
    ok -> print('wrap:' - (it == -56).to-str())
    nil -> print('nil')
    err -> print('err')
}
```

블록 안에서 독립된 줄에 있는 애노테이션은 "바로 뒤에 오는 그 한 문장"만 인정합니다. 중간에 무관한 애노테이션 줄이 끼어 있어도(예: `#{overflow=wrap}` 뒤에 다시 `#{...}` 가 오는 경우) 중단되지 않고 여전히 첫 번째 실제 문장을 찾습니다. 다만 다음 애노테이션 자체가 같은 이름의 키를 가지고 있으면 앞의 것은 어떤 문장도 관장하지 못합니다(뒤 것이 우선).

⚠️ 블록 match `{ … }: { … }` 는 "하나의 문장"이며 **관통되지 않습니다**. 애노테이션을 그 `{` 위에 쓰면 호스트는 그 블록 문장 자체이며 블록 안의 `?=` 수식으로 가라앉지 **않습니다** (실측: `#{overflow=wrap}` 을 블록 밖에 두면 블록 안의 `np ?= np + 1` 은 그대로 오버플로 → `err`, 대상이 0 으로 초기화됨). 블록 안 수식에 `overflow` 를 적용하려면 블록 안의 그 `?=` 바로 위에 쓰세요. 두 소비 형태의 차이는 [syntax.md](syntax.md)의 〈블록 match 와 값 위치 match 의 선택〉 참조.

## 3. 상속, 덮어쓰기, 하드 경계

**바깥에서 안으로 상속하고, 가까운 것이 덮어씁니다.** 여러 단계를 지원하는 키(플랫폼 키)에 대해 L0 → L1 → L2 → L3 이 단계별로 적용됩니다. 같은 노드에 같은 이름의 키가 여러 번 나오면 뒤 것이 앞 것을 덮어씁니다(`#{mac-arm64} #{mac-arm64, win-amd64}` 는 뒤 것이 기준).

**함수체는 하드 경계입니다.** L2 블록의 스코프는 구문 서브트리에서 멈춥니다. 호출 관계를 따라 확산되지 않으며 어떤 함수 / 메서드 / 익명 함수의 정의체에도 들어가지 않습니다. 함수체 안에서 어떤 모드를 쓰는지는 그 함수 자신의 L1 애노테이션이나 내부 L3 애노테이션으로만 결정되며, 이를 호출하는 블록에 붙은 애노테이션과는 무관합니다.

```no
; L1：整個函式連同函式體一起被剔除（macOS 上不生成 IR）
#{win-amd64}
windows-only = () {
    print('never compiled on mac')
}

; 沒有自己的 L1 註解 → 任何平台都編譯，也不會因為被誰呼叫而改變
always = () {
    print('always compiled')
}
```

이유: 외부 애노테이션이 함수체를 관통할 수 있다면 호출 지점의 한 줄이 호출된 함수의 의미를 조용히 바꾸게 되며, 디버깅할 때 전혀 알아차릴 수 없습니다. 반면 L1 애노테이션은 그 함수 머리에 직접 적혀 있으므로 선언의 일부입니다.

**하드 경계 목록**(여기까지 상속됨): 함수체, 메서드체, 익명 함수/lambda 체, `#{c}` 외부 선언. **비경계**(정상적으로 상속됨): `{}` 베어 블록, if 그룹, match 분기, 반복문체.

## 4. 키 × 단계 행렬

`✓` 적용됨 ／ `✗` 불법(컴파일 오류를 내야 함) ／ `—` 해당 단계에서 의미 없음(마찬가지로 오류를 내야 하며 조용히 버리면 안 됨)

| 키 | L0 모듈 | L1 선언 | L2 블록 | L3 단일 줄 |
| --- | --- | --- | --- | --- |
| `overflow` | ✗ | ✗ | ✗ | ✓ |
| 플랫폼 키(`mac-arm64` 등) | ✓ | ✓ | ✓ | ✓ |
| `buildin` | ✗ | ✓ 함수 / 태그 열거형 / 레이아웃 구조체 | ✗ | ✗ |
| `inline` | ✗ | ✓ 구조체 / 필드 / 변형 / 함수 | ✗ | ✓ 멤버 끝에 붙임 |
| `generic` | ✗ | ✓ 함수 / 구조체 | ✗ | ✗ |
| `track-caller` | ✗ | ✓ 함수 | ✗ | ✗ |
| `embed` | ✗ | ✓ 최상위 `let` | ✗ | ✗ |
| `bind` | ✗ | ✓ import 줄 | ✗ | ✗ |
| `c` / `cpp` / `rust` | ✗ | ✓ 바로 뒤의 함수 선언 | ✗ | ✗ |
| `fmt-skip` | ✗ | ✗ | ✓ markdown 펜스 블록 | ✗ |
| 메타데이터(`derive` / `range` / `max` / `debug`…) | ✗ | ✓ 선언 / 멤버 | ✗ | ✗ |
| `index-out` | — | — | — | — D11 에서 제거됨, 나타나면 즉시 오류 |

"불법"과 "의미 없음"은 모두 **오류를 내야** 하며 조용히 무효화되면 안 됩니다. `for` 반복문 위에 적은 `#{buildin}` 이 몰래 무시되면 작성자는 내장 선언이 적용되었다고 착각할 것입니다.

### 4.0 `#{buildin}` 의 세 가지 매개체와 "레이아웃 구조체"의 특수성

`#{buildin}` 은 선언에 표시되지만 세 가지 매개체에 대한 의미는 완전히 다릅니다.

| 매개체 | 의미 | 예시 |
| --- | --- | --- |
| 함수 | 빈 본문 스텁: 컴파일러 / FFI 가 구현을 제공하며 Nolang 쪽에서는 함수체를 생성하지 않음 | `#{buildin}`<br/>`fs.remove = (p str) (ok bool) { }` |
| 태그 열거형 | 변형을 매칭 및 완전성 검사에 사용하며, 내부 표현과 생성은 내장 런타임이 제공 | `#{buildin}`<br/>`option { ok(v t), nil, err(e err.err), }` |
| **레이아웃 구조체** | **단순한 레이아웃 문서**: 이 `struct` 는 의미상 존재하지 않으며 유일한 산출물은 필드 타입입니다(`t.len` 은 `u8`) | `#{buildin}`<br/>`txt { data [255]byte; len u8 }` |

세 번째는 따로 분명히 해야 합니다. 앞의 두 가지는 방향이 반대이기 때문입니다. 함수 스텁과 태그 열거형은 "컴파일러가 실제로 이 선언을 사용한다"지만, 레이아웃 구조체는 "컴파일러가 이 선언을 사용하지 **않으며**, 단지 필드 타입의 출처이자 사람이 읽을 수 있는 레이아웃 설명일 뿐"입니다. 실제 레이아웃과 문서 링크는 다른 곳에 있습니다.

| 타입 | 실제 레이아웃의 출처 | 문서 / 링크의 출처 |
| --- | --- | --- |
| `str` | MIR 수동 기술자 `%str-long = { i32 len, i32 cap, i8* data }` | `parser.BuiltinTypes()` |
| `vec` | MIR 수동 기술자 `%vec = { i32 len, i32 cap, i64 data }` | `parser.BuiltinTypes()` |
| `txt` | MIR 수동 기술자 `%txt = { [255 x i8] data, i8 len }` | `parser.BuiltinTypes()` |
| `arr` | 기술자 없음: `[n]t` 는 그대로 베어 집계 `[N x T]` 이며 `.len` 은 컴파일 타임 상수 `n` | `parser.BuiltinTypes()` |

`parser.BuiltinTypes()` (`src/parser/builtintype.go`) 은 "이름 → std 모듈 → 모듈 문서 앵커 → 레이아웃"의 유일한 등록표이며, LSP 의 hover / 정의로 이동 / 자동 완성과 `IsBuiltinLayoutStructName` 이 모두 이를 읽습니다. 바로 이 때문에 레이아웃 구조체는 더 이상 링크를 담당하지 않습니다. 이를 삭제해도 hover 와 F12 는 그대로 동작합니다. 다만 checker 가 `t.len` 의 필드 타입을 잃게 되므로 현재는 남겨 두고 있습니다.

이로부터 두 가지 하드 규칙이 도출되며, 하나라도 깨지면 실제 레이아웃과 모순되는 "그림자 구조체"가 즉시 생깁니다.

1. **`#{buildin}` 이 붙은 struct 는 내장 레이아웃 이름(`str` / `vec` / `txt` / `arr`)을 사용해야 합니다.** 다른 struct 에 붙이면 오류입니다. 그 선언은 MIR 에서 "레이아웃을 컴파일러가 보유한다"고 간주되어 건너뛰어지고 필드가 전혀 적용되지 않아 작성자에게는 `unknown field` 가 잔뜩 남습니다.
2. **내장 레이아웃 이름으로 struct 를 선언하려면 반드시 `#{buildin}` 이 있어야 합니다.** 사용자가 베어 `str { … }` 를 작성하면 이는 해당 모듈의 보통 타입으로 취급되어 접두사가 붙(`m.str`) codegen 이 `%str-long` 과 충돌하는 `%m_str` 을 생성합니다.

두 규칙 모두 `checker.ValidateBuiltinStructDecls` 가 오류를 보고하며(`1a8m445h` / `3lu6n4np`), `no build` 와 `no vet` 모두 이를 잡습니다. 반대로 **오직** `#{buildin}` + 레이아웃 이름 조합만 모듈 접두사 단계와 MIR 의 `collectStructFields` 에서 건너뛰어집니다(`src/build/module_prefix.go` 의 Phase 1 과 `src/mir/hir2mir.go` 의 `isBuiltinLayoutStruct` 참조). 판단 근거는 이름 자체가 아니라 "애노테이션 + 이름"이라는 조합입니다.

### 4.1 `overflow` 가 L3 에만 주어지는 이유

`#{overflow}` 는 선언의 메타데이터가 아니라 **연산별 의미 스위치**입니다. 함수나 블록에 쓰는 것을 허용하면 "특정 연산이 실제로 어떤 모드를 쓰는지"가 애노테이션에서 얼마나 떨어져 있는지, 중간에 다른 애노테이션이 끼어 있는지, 블록이 몇 겹인지에 달라집니다. 코드 한 줄을 읽기 위해 위로 거슬러 올라가야 답할 수 있으며, `no fmt` / `no vet` / codegen 세 쪽이 같은 답을 유지하기는 극히 어렵습니다(실측으로 이미 드리프트가 발생했습니다. §7 참조).

더구나 타입을 바꾸지 **않습니다**. 결과는 항상 `?T` 입니다. 블록 수준이나 함수 수준의 `wrap` 은 `?T` 를 `T` 로 바꾸지 않고, "오버플로 즉 `err`"를 "조용한 되감기"로 조용히 바꿀 뿐입니다. 오류가 "명시적 실패"에서 "성공처럼 보이는 잘못된 값"이 되는 것으로, 바로 이런 것이 멀리 있는 한 줄의 애노테이션이 결정해서는 안 되는 일입니다.

그래서 "한 줄에 하나의 애노테이션"으로 못 박았습니다.

- 바로 뒤의 그 한 문장만 인정하며, 끝에 붙이는 표기 (`x = a + b #{overflow=wrap}`) 도 동등합니다.
- 전체에 적용하려면 문장마다 적습니다. `no fmt --fix=overflow` 와 LSP quickfix 가 생성하는 것도 이 형태입니다.
- 함수 머리, 블록 머리, 파일 머리에 쓰면 **컴파일 오류**이며 "무효하지만 무해"가 아닙니다.

부수적인 이점: 애노테이션이 항상 관장하는 문장과 같은 화면에 있어 코드를 옮길 때 서로 떨어지지 않습니다. `wrap` 이 들여쓰기 조정 한 번으로 옆 연산을 실수로 덮는 일도 없습니다.

## 5. 주석(`;` / `//` / `;;`)의 스코프

주석은 컴파일 의미에 관여하지 않으며, 귀속은 `no fmt` 의 포맷과 API 문서의 연결에만 영향을 줍니다. 표기 문법은 [`code-style.md`](code-style.md)의 〈주석 표기〉 참조.

| 주석 | 귀속 |
| --- | --- |
| 줄 끝 (`x = 1 ; 설명`) | 해당 줄 |
| 줄 위에 연속된 주석 줄 | 바로 뒤의 다음 문장/선언(L1 또는 L3, 애노테이션과 동일한 호스트 판정) |
| 대상과 사이에 빈 줄이 있음 | 어느 노드에도 귀속되지 않으며 블록/파일의 구분 설명으로 취급(파일 머리는 예외, L0 참조) |
| `;; … ;;` 블록 주석 | 자체 닫는 구분자까지만 유효하며 스코프를 넘지 않음 |
| 애노테이션과 대상 사이의 주석 | 대상을 따라가며 출력 순서는 "문서 주석 → 애노테이션 → 문장"으로 고정 |

`;` 와 `//` 는 의미가 같습니다. `no fmt` 는 원래 표기를 유지하며 고치지 **않습니다**. 문서 주석의 번역 앵커 (`[get](#args.get)`) 는 주석 그룹의 **마지막 줄**이어야 하고 같은 호스트에 속해야 하며 노드를 넘을 수 없습니다.

## 6. 네 독자는 반드시 일치해야 한다

같은 애노테이션에 대해 네 독자가 동일한 스코프를 얻어야 합니다.

| 독자 | 알아야 할 것 |
| --- | --- |
| parser / codegen | 이 노드와 그 서브트리가 어떤 모드를 쓰는지 |
| checker / `no vet` | "표기됨"의 판정 범위 |
| `no fmt` | 애노테이션을 원래 위치로 출력하며 호스트를 넘겨 옮기지 않음 |
| LSP | hover/quickfix 가 삽입하는 위치가 실제로 적용되는 위치와 같음 |

여기서 네 가지 불변식이 도출됩니다.

1. **표기 판정 일치**: codegen 이 "표기됨"이라고 보는 범위는 반드시 `no vet` 가 처리했다고 보는 범위이기도 하며, 그 역도 성립합니다.
2. **fmt 는 옮기지 않음**: `no fmt` 는 같은 호스트 안에서만 위치를 조정할 수 있습니다(위 ↔ 끝). 호스트를 넘겨 옮기는 것은 의미를 바꾸는 것과 같습니다.
3. **무효화되면 반드시 오류**: 애노테이션이 대응하는 의미가 없는 단계(§4 의 `✗` / `—` 참조)에 떨어지면 오류를 내고 조용히 무시하지 않습니다.
4. **단계 제한**: 키는 행렬이 허용하는 단계에서만 적용됩니다. `overflow` 가 L0/L1/L2 에 쓰이면 네 독자 모두 이를 **오류**로 취급해야 합니다. "vet 는 인정하고 codegen 은 인정하지 않는" 분기가 생겨서는 안 됩니다(현황은 §7 참조).

## 7. 현황과 격차(2026-11-11 실측)

`bin/no` 로 항목별로 검증했으며, 형태는 "두 개의 `i8 = 100` 을 더한 결과가 `err` 인지 `-56` (wrap) 인지 보는 것"으로 통일했습니다. 플랫폼 키는 `#{win-amd64}` 를 macOS 에서 제외되는지 검증했습니다.

| 단계 | `overflow` (설계: L3 전용) | 플랫폼 키 | 선언 키 |
| --- | --- | --- | --- |
| L0 모듈 | ✗ 설계상 금지됨. 현재는 첫 문장에 붙음(L1 과 동일) | 미구현 | 미구현 |
| L1 선언 | ✗ 설계상 금지됨. **현황은 결함**: `no vet` 는 인정(함수 전체 건너뜀), codegen 은 인정하지 않음(여전히 `err`) | ✓ 전체 서브트리 제외 | ✓ |
| L2 블록 | ✗ 설계상 금지됨. codegen 은 인정하지 않음. `for` / if 그룹 / match 분기 헤드는 `no vet` 가 블록을 따라 조용히 만들 수 있음. **문장 위치의 베어 블록 `{` 는 조용히 만들지도 못함**(아래 참조) | ✗ 블록 내부가 여전히 컴파일에 참여 | — |
| L3 단일 줄 | ✓ | ✓ | — |

실측 증거:

```text
a-none.no    (無註解)                     → err
b-line.no    (陳述上方 #{overflow=wrap})   → result:true  (-56，生效)
c-fn.no      (函式上方 #{overflow=wrap})   → err           (vet: No issues found)
d-block.no   (for 上方 #{overflow=wrap})   → err ×2        (vet: 2 hints)

p1-block.no  (#{win-amd64} + 2 * {…})      → 塊體仍執行    (未過濾)
p2-stmt.no   (#{win-amd64} + 單條 print)   → 該行被排除    (生效)
p4-fn.no     (#{win-amd64} + 函式宣告)     → 函式被排除    (生效)
p6-ifgroup.no(#{win-amd64} + if 組)        → 臂仍執行      (未過濾)

; 編譯期對照：`for` 頭加註解 vs 不加，15w45dqk 逐字相同
k2.no (for 頭 #{overflow=wrap} + 體內 `x i8 = a + a`) → cannot assign ?i8 to i8
k3.no (刪掉那一行，其餘逐字相同)                       → cannot assign ?i8 to i8
```

베어 블록이 왜 조용히 만들지도 못하는가: `parseAnnotationStatement` 의 부착 가능 대상은 IDENT / USE / IN / RARROW / 배열 타입 메서드뿐이며 `{` 는 여기에 없습니다. 따라서 아래와 같은 표기에서 애노테이션은 블록에도, 블록 안 문장에도 붙지 **않고**, 독립적인 `AnnotationStatement` 로 퇴화하여 parser, codegen, `no vet` 세 쪽 모두에게 죽은 줄이 됩니다.

```no
#{overflow=wrap}
{
    ...
}
```

`for` / if 그룹 / match 분기의 헤드가 식별자 또는 `in` 으로 시작하기에 바로 부착 가능 대상에 들어갑니다.

조여야 할 세 가지 구멍 (`overflow` 의 "L3 전용"이 아직 강제되지 않았습니다):

1. **`no vet` 가 함수 수준 `overflow` 를 보면 함수 전체를 건너뜀** (`walkStmtForOverflow` 의 `fn.OverflowMode == ""` 단락) → 검사는 전부 통과인데 런타임에는 여전히 `err`.
2. **`no vet` 가 블록을 따라 아래로 상속** (`enclosingOverflow`) → 블록 헤드의 한 줄 애노테이션이 전체 블록을 조용히 만들며, codegen 이 전혀 인정하지 않아도 마찬가지입니다.
3. **parser / codegen 이 L1/L2 의 `overflow` 를 조용히 무시**하고 오류를 내지 않음 → 작성자는 적용되지 않았다는 사실을 알 수 없습니다.

기존 코드 점검 및 처리(`src/std`, `no fmt --fix=overflow` 로 세 차례 하향 푸시 실행):

| 분류 | 마이그레이션 전 | 1차 후 | 2차 후 | 3차 후 |
| --- | --- | --- | --- | --- |
| `overflow` 애노테이션 줄 합계 | 4580 | 4083 | 3861 | 4080 |
| 그중 "어떤 노드에도 붙지 않는" 죽은 줄 | 330(형태 기준) | 87 | **0** | **0** |
| `no vet` 가 보고했지만 표기할 수 없는 줄 | — | ~270 | 270 | **51** |

1차(2026-11-11) 순변화: 스코프 수준 애노테이션 816 줄을 삭제하고 문장별 애노테이션 325 줄을 삽입했습니다. A/B 로 나눠 보면 325 줄 중 약 218 줄은 원래 표기가 빠져 있어 하향 푸시와 무관한 지점이며(삽입만 실행하고 가려진 것을 제거하지 않아도 채워졌을 것입니다), 약 97 줄은 블록 수준 의도가 줄 단위로 구체화된 것입니다.

2차(2026-11-12)는 순수 정리였습니다. 원인은 `findFixTargetNode` 가 분기체로 내려가지 않고 "삽입 후 자체 검사"도 없었기 때문입니다. 381 줄 삭제, 159 줄 추가였으며 모두 `#{...}` 애노테이션 줄이고 코드는 0 줄이었습니다(`diff` 로 줄 단위 확인). 그중 159 줄은 "블록 헤드/분기 헤드에서 문장 위로 옮긴" 위치 이동이며, 나머지 222 줄은 죽은 줄과 불필요한 스코프 수준 애노테이션을 바로 삭제한 것입니다. 이 위치들은 원래 적용되지 않았으므로 삭제해도 컴파일/검사 결과는 바뀌지 않습니다.

2차에서 함께 고친 도구 결함 세 가지:

1. **`checker` 가 보고하는 줄 번호가 컨테이너로 무너짐**: `walkExprForIntOverflow` 의 `emit` 이 컨테이너의 `stmt.Pos().Line` 과 연산자의 column 을 섞어 써서 `{ ... }` / if 그룹 / match 분기 안의 모든 보고 줄 번호가 헤더 줄이 되었습니다. 진단이 잘못된 위치를 가리키는 것은 겉으로 드러난 증상일 뿐이며, 진짜 문제는 `--fix` 의 `findFixTargetNode` 가 "해당 줄을 포함하는 가장 안쪽 문장"을 취해 컨테이너만 되찾아 애노테이션이 블록 헤드에 다시 삽입된다는 것이었습니다. 이제 **연산자 자신의 줄** (`x.Token.Line`) 을 취하도록 고쳤고, token 줄 번호가 없으면 컨테이너 줄로 되돌아갑니다.
2. **분기체로 내려가지 않음**: `findFixTargetNode` 는 원래 의도적으로 전체 match 문장 위에서 멈췄습니다. 이제 **블록 형태의 분기체** (`cond -> {` 의 `{ ... }`, `{ ... }: { ... }` 의 `BlockMatchStatement.Body` 포함) 로 내려갑니다. 줄 끝 형태의 분기체는 여전히 내려가지 않습니다(`w i64 -> w + 1` 의 문장과 분기 패턴이 같은 줄에 있어 그 위에 삽입하면 match 안으로 들어가 분기 패턴 줄 앞에 놓이게 되기 때문).
3. **붙지 않는 위치에도 그대로 삽입**: 이제 `#{overflow}` 는 삽입 후 **한 번 더 파싱하여 자체 검사**하고, "삽입했지만 독립적인 `AnnotationStatement` 로 퇴화한" 애노테이션을 철회합니다(죽은 줄을 남기지 않음). 철회 후 두 번째 `--fix` 가 받는 소스 코드는 그대로이므로 멱등성이 유지됩니다.

3차(2026-11-12)는 parser 를 건드렸습니다. `parseAnnotationStatement` 의 부착 대상에 **DOT** 이 추가되었습니다. `.n = .n + 1` / `.cnt == 0 -> …` 처럼 수신자로 시작하는 문장은 `x = …` 과 같은 부류(단일 문장, L3)인데도 예전에는 부착 대상에 없어 애노테이션이 독립적인 `AnnotationStatement` (죽은 줄) 로 퇴화했고, 지점은 계속 보고되고 `--fix` 가 삽입해도 자체 검사로 철회되었습니다. 완화 후 219 곳의 지점이 L3 애노테이션을 얻었고(애노테이션 줄 3861 → 4080), 표기할 수 없는 곳이 270 에서 51 로 줄었습니다. 그 결과 AST 형태가 바뀌었고(`AnnotationStatement` 하나가 줄고 대상 문장에 side-table 기록과 `OverflowMode` 가 하나씩 추가됨) `parser.ASTVersion` 이 `2026-11-12.1` 로 올라갔으며, 수정 후 반드시 `make gen no` 를 실행해야 합니다.

**`{` 와 `(` 는 의도적으로 완화하지 않았습니다**: `{` (문장 위치의 베어 블록 / 괄호가 있는 match) 와 `(` (`(cond) { }` 반복문 헤드) 는 L2 블록 호스트인 반면 `overflow` 의 설계는 L3 전용입니다. 이를 허용하면 `overflowAnnotatedNode` 가 전체 블록에 대해 일찍 반환하여 L2 의미를 합법화하게 되며, §8 의 "먼저 조이고 그다음 완화" 순서와 충돌합니다. 남은 51 곳의 대부분이 이 두 부류에 해당하며 §8 4b 단계에 속합니다.

검수 기준(격리 트리 A/B, 동일 소스·동일 컴파일러, `src/std` 만 다르고 파일별로 `no vet` 실행): 영향을 받은 73 개 파일 모두 error 0 개(컴파일 손상 없음), 25 개 파일은 진단이 줄었고 19 개 파일은 늘었습니다. 늘어난 것은 모두 가려진 것을 제거한 뒤 드러난 `ovfhndld` " `?T` 에 묶였지만 오버플로 값 추출을 선언하지 않음"이며, §8 1 단계의 예상 결과이지 새로운 결함이 아닙니다. 또한 `nolang-overflow-ineffective` 경고 9 건은 도구 본래의 "빈 곳 채우기" 동작이 bigint / 문자열 재정의 연산에 걸린 오래된 문제로 하향 푸시와 무관합니다. 2차 이후 `bin/no run test-std/src/*.no` 전체(zstd / tls / str / json / set / base32 …)를 다시 실행했고 모두 PASSED 였습니다.

3차 재실행 기준: parser 테스트의 3 건 실패(`TestAnnotationsLiveOnAST` / `TestCachedASTLowersToIdenticalHIR` / `TestBuildSemViewsMatchesFreshParse`) 는 완화 전후로 글자 단위 동일했고, `only 288 files parsed cleanly` 도 두 번 모두 같아 완화로 새로운 파싱 실패가 생기지 않았음을 보여 줍니다. 이들은 병행 작업 중인 parser/annotation 리팩터링의 진행 중 상태입니다. `no fmt -d src/std` 의 출력도 완화 전후로 **바이트 단위 동일**했으며, 즉 formatter 가 `.` 위의 애노테이션을 원래 위치에 그대로 출력하여 포맷 드리프트가 없었습니다. `test-std/src` 의 heap / zstd / tls / json / set / map / regexp 도 모두 통과했습니다.

**남은 76 곳의 분기 헤드 애노테이션** (`#{overflow=wrap}` 이 `cond -> {` 바로 위에 있음): 이들은 죽은 줄이 **아닙니다**. parser 가 분기 수준 애노테이션을 분기체 안의 모든 문장에 복사하므로 분기체에는 적용됩니다(실측: 분기 헤드의 한 줄 애노테이션이 분기체 `r = i * 2` 를 조용히 만들고, 헤더 조건 그 줄만 그대로 보고됨). 다만 **분기 조건 자체에는 적용되지 않습니다** (조건은 문장이 아님). 이 76 곳은 그대로 둡니다. 문장별 삽입으로는 이들을 잡을 수 없고(분기체 지점이 이미 조용해져 더 이상 보고되지 않음), 떼었다가 다시 붙이면 헤더 줄에서만 제자리 맴돌기 때문입니다.

**아직 `no vet` 가 보고하고 현재 언어로는 표기할 수 없는 51 곳** (2차 때는 270 곳이었고 3차에서 DOT 을 완화한 뒤 이만 남았습니다): 대상 문장이 `{` (문장 위치의 베어 블록 / 괄호가 있는 match) 또는 `(` (`(cond) { }` 반복문 헤드) 로 시작하는 경우와 소수의 분기 헤더 조건이 해당합니다. 이들은 지금도 보고되며(원래 애노테이션이 적용되지 않았음) 철회가 회귀는 아닙니다. 0 으로 만들려면 먼저 §8 1–2 단계(L2 의 `overflow` 를 오류로 판정)를 수행한 뒤 L2 를 실제로 지원할지 결정해야 합니다. §8 4b 단계 참조.

`archive/bzip2.no:315` 같은 위치를 표본 검사하면 블록 헤드와 블록 안에 동시에 `#{overflow=wrap}` 이 있습니다. 블록 헤드층은 현재 적용되지 않고 실제로 동작하는 것은 블록 안의 문장별층입니다(`--fix=overflow` 가 이미 보완함). 따라서 블록 수준층을 삭제해도 의미는 바뀌지 않습니다. 다만 삭제 후 `no vet` 를 다시 실행하면 "외부 애노테이션에만 의지해 조용해졌던" 위치가 드러납니다. 이는 **부작용이 아니라 조여야 할 목적**입니다. 실측으로 `crypto/rsa.no` 의 `ovfhndld` hint 가 19 건에서 22 건으로 늘었고 모두 " `?T` 에 묶였지만 오버플로 값 추출을 선언하지 않은" 문장에 나타났으며 의미는 변하지 않았습니다.

L0 의 기존 코드 영향: `src/**/*.no` 중 애노테이션이 파일의 첫 유효 줄인 파일이 21 개인데, 그중 17 개는 `#{js}` 이고 나머지는 선언 바로 뒤의 `#{buildin}` 등입니다. 모두 빈 줄이 없으므로 §2 의 L0 판정 기준에 따르면 여전히 L1 이며 `no fmt` 와 컴파일 동작은 변하지 않습니다. `str.no` 에 "애노테이션 + 빈 줄 + cond 분기"가 2 곳 있지만 함수체 안에 있어 L0 판정을 발동하지 않습니다.

## 8. 조이는 순서

1. **먼저 `no vet` 가 L1/L2 의 `overflow` 를 더 이상 인정하지 않게 합니다**: "함수 수준이면 함수 전체를 건너뛴다"는 단락을 삭제하고 `enclosingOverflow` 를 같은 문장의 서브트리 안으로 제한합니다(블록을 넘어 아래로 전달하지 않음).
2. **그다음 parser 가 오류를 내게 합니다**: `#{overflow}` 가 L0/L1/L2 에 떨어지면 컴파일 오류가 되며 메시지가 "문장마다 표기하거나 `no fmt --fix=overflow` 를 실행하세요"를 가리켜야 합니다. 이 단계에서 모든 기존 코드가 한꺼번에 드러납니다.
3. **기존 코드 정리**: `no fmt --fix=overflow` 에 이미 하향 푸시 능력이 있습니다(스코프 수준층을 제거한 뒤 checker 보고에 따라 L3 를 문장마다 보충). `src/std` 에 세 차례 실행했습니다(§7 의 기존 코드 표 참조). 수정 후에는 반드시 `make gen no` 를 실행해야 하고(blob 과 StdSigKey 재베이킹) `src/std` 에 `no fmt -w` 를 실행해서는 안 됩니다. 마이그레이션은 애노테이션 줄만 변경하므로 파일별로 `no fmt -fix=overflow -w <f>` 로 수행하고 `diff` 로 다른 변경이 없음을 보장합니다.
4. **parser 의 부착 대상 완화** (3차에서 절반 완료):
   - **4a 완료**: `parseAnnotationStatement` 가 DOT 으로 시작하는 문장을 받아들입니다. `.n = .n + 1` / `.cnt == 0 -> …` 는 `x = …` 과 같은 단일 문장(L3)인데도 예전에는 애노테이션을 붙일 수 없어 `src/std` 의 219 곳 `#{overflow=wrap}` 이 한 번도 적용되지 않았습니다. 완화 후 표기할 수 없는 곳이 270 에서 51 로 줄었고 `parser.ASTVersion` 이 `2026-11-12.1` 로 올라갔습니다.
   - **4b 결정 대기**: `{` (문장 위치의 베어 블록 / 괄호가 있는 match) 와 `(` (`(cond) { }` 반복문 헤드) 는 **L2 블록 호스트**입니다. 이를 완화하는 것은 `overflow` 에 L2 의미를 합법화하는 것과 같습니다(`overflowAnnotatedNode` 가 전체 블록에 대해 일찍 반환함). 1–2 단계의 조이는 방향과 반대입니다. 올바른 순서는 먼저 1–2 단계(L2 의 `overflow` 를 오류로 판정)를 수행한 뒤, 남은 51 곳을 "블록 없는 문장으로 다시 쓰기" 또는 "arm body 에 문장별로 보충"으로 해결할지 결정하는 것이지 `{` / `(` 를 무조건 풀어주는 것이 아닙니다.
5. **나머지 키는 단계적으로 조입니다**: 선언 키 (`buildin` / `generic` / `embed`…) 를 L2/L3 에 쓰는 것을 "무효"에서 "오류"로 바꿉니다.
6. 모든 단계에서 `no fmt` 의 멱등성을 보장하고 네 독자가 같은 입력에 대해 같은 결론을 내려야 합니다(§6).
