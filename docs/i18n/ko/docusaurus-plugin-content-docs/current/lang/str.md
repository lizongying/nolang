# 문자열

Nolang의 문자열(`str`)은 힙에 할당된 바이트 시퀀스이며, 다양한 연산자와 메서드를 지원합니다.

## 내부 레이아웃과 외부 API

`str`의 디스크립터(`%str-long`)는 64비트 플랫폼에서 **16바이트**입니다.

```llvm
%str-long = type { i32, i32, i8* }   ; u32 len, u32 cap, data
```

| 필드 | 내부 타입 | 외부 타입 | 설명 |
|---|---|---|---|
| `len` | `u32`(LLVM `i32`) | `i64` | 논리적 바이트 길이; `s.len-bytes()`, `len(s)`, `s._len()` |
| `cap` | `u32`(LLVM `i32`) | `i64` | 실제 용량(str-long에만 유효); `s.cap()`, `s._cap()` |
| `data` | `i8*` | `[]byte` / `*byte` | 힙 버퍼를 가리킵니다 |

내부에서 `len` / `cap`을 `u32`로 좁힌 이유는 디스크립터를 24바이트에서 16바이트로 줄이기 위해서입니다(`i32` + `i32` + 8바이트 정렬된 포인터). **외부 API는 항상 `i64`입니다**: 읽을 때 경계에서 `zext i32 -> i64`를 수행하고, 쓸 때는 `trunc i64 -> i32`를 수행합니다. 표준 라이브러리와 사용자 프로그램은 이 변환 계층을 다룰 필요가 없으며(그렇게 해서도 안 됩니다). `s.len-bytes()`, `s.len()`, `s.cap()`, `s._len()` / `s._cap()` / `s._set-len()` / `s._set-cap()`의 시그니처는 `i64`로 유지됩니다.

> ⚠️ 내부 카운터가 `u32`이므로 단일 `str`의 길이/용량 상한은 4 GiB(`4294967295`)입니다. 이 값을 넘는 `i64`를 전달하면 경계에서 잘립니다. 일반적인 문자열 처리에는 영향이 없지만, 거대한 버퍼를 미리 할당하기 전에는 직접 확인해야 합니다.
>
> `txt`는 **이번 변경의 영향을 받지 않습니다**: 여전히 고정 256바이트의 `{ [255 x i8] data, i8 len }`이며, `cap` 필드가 없고 길이는 1바이트입니다.

## 문자열 연산자

### 연결(`-`)

`-` 연산자로 문자열을 연결합니다.

```no
; 字面量拼接
s = 'Hello' - ' ' - 'World'

; 與變量拼接
greeting = 'Hello, ' - name
```

### 반복(`*`)

`*` 연산자로 문자열을 반복합니다.

```no
s = 'Hello' * 3
```

### 비교(`==` / `!=` / `str.compare`)

`str`은 **동등 비교만 구현합니다**: `==` / `!=`는 런타임의 `@str_eq`를 거치며, 여러 문자로 된 문자열도 완전히 허용됩니다.

관계 연산자(<code>&lt;</code> `>` <code>&lt;=</code> `>=`)에는 **문자열 사전순 의미가 없으며**, 문자열에 사용하면 컴파일 오류가 발생합니다.

- **허용**: **한 문자** 문자열 리터럴 `'a'`는 암시적으로 `char`(코드 포인트)로 간주되며, 다른 한 문자 리터럴이나 `char`(`"a"`)와 비교할 수 있습니다.
- **오류**: 여러 문자로 된 문자열 — `'ab'`, `str` 변수, `str`을 반환하는 호출(과거에는 **조용히 false를 반환**했습니다).

사전순 비교가 필요할 때는 `str.compare(b)`를 사용합니다.

```no
s = 'abc'
b = 'abd'
c = s.compare(b); -1（s < b）/ 0（相等）/ 1（s > b）

'a' <= 'z'; true — 單字元字串隱式 char
ch >= 'a'; ch 為 char，OK
s < b; 編譯錯誤：多字元字串
s.compare(b) < 0; 正確寫法
```

## 인덱싱과 슬라이스

**인덱싱**: `s[i]`의 추론 타입은 **`?char`**(유니코드 코드 포인트)이며 `byte`가 아닙니다. 범위를 벗어나면 `err`(`code.index-out`)를 반환하고, 범위 안에서는 `ok(코드 포인트)`를 반환합니다(정수 `+ - * / %`와 동일한 통합 규칙). 여러 바이트 문자를 포함한 문자열에서 `s[i]`는 문자열 앞에서부터 UTF-8을 디코딩하며 i번째 코드 포인트까지 셉니다(아래 성능 설명 참조).

```no
#{fmt-skip}
s = 'Hello World'
c = s[0]: { ok -> it  -> _ }   ; 'H' 的碼點（?char 必須顯式解包，空臂取 '\0'）
```

> `?char`를 소비하는 방법은 세 가지뿐입니다(**`#{index-out=DEF}`는 D11에서 폐기 및 제거되었습니다**. 남아 있는 애노테이션은 컴파일 오류입니다.
> 또한 "명시적 plain 타입으로 다시 plain을 가져오기" 같은 지름길도 없습니다. `c char = s[i]` 역시 명시적으로 소비해야 합니다):
> **match 언패킹**(`x = s[i]: { ok -> it, -> _ }`, 빈 갈래는 `char`의 영값 `'\0'` 사용),
> **place-match 기록**(`s[i]: { ok -> it = x, -> _ }`), 또는 **축약형 `?=` 전파**(함수에 `?T` 결과 매개변수가 있거나
> 문장이 블록 match 본문 안에 있는 경우). 자세한 내용과 예제는 〈syntax · 안전한 인덱싱〉 참조.

**슬라이스**: `s[a..b]`는 기반 문자열의 **뷰**를 반환하며, 타입은 여전히 **`str`**입니다(메모리를 공유하며 복사하지 않음). 슬라이스 인덱스는 `s[i]`와 마찬가지로 **코드 포인트 위치**입니다.

```no
sub = s[6..]; 'World'
sub = s[6..11]; 'World'
sub = s[0..5); 'Hello'（左閉右開）
```

> 슬라이스의 인덱스는 **코드 포인트 위치**이며 바이트 오프셋이 아닙니다. 바이트 오프셋 기준의 슬라이스가 필요하면(예: `s.byte(i)`와 함께 순회) `s.slice-bytes(start, end)`를 사용하세요.

```no
; 長度
n = s.len(); code point 數（Unicode 字符數）
n = s.count(); 同上（舊方法名，仍可用）
n = s.len-bytes(); byte 長度（UTF-8 位元組數）
; 注意：裸 s.len（結構體欄位）已不再支援，讀寫都會報錯；請改用 s.len() / s.len-bytes()
```

### 암시적 변환(char → str)

`char`는 `str`로 **암시적으로 변환**될 수 있습니다. 해당 코드 포인트를 UTF-8로 인코딩하여 새 문자열을 만듭니다. 따라서 다음 표현식들은 모두 허용되며 `char.to-str()`을 수동으로 호출할 **필요가 없습니다**.

```no
s = 'héllo'; 'h' 'é' 'l' 'l' 'o'（é 為多字節）

; 1) s[i] 的 char 直接賦值給 str 變數 → 隱式轉成單字元字串
a str = s[0]; 'h'

; 2) 切片結果本身型別已是 str，直接賦值即可
b str = s[0..1]; 'hé'（下標 0..1，兩端皆含）

; 3) char 參與字串拼接（-）時隱式轉為 str
msg = 'first: ' - s[0]; 'first: h'

; 4) char 與 str 比較時隱式轉為 str
ok = s[0] == 'h'; true
```

> **`'...'`는 `str` 리터럴이고 `"..."`는 `char` 리터럴입니다** — `'x'`에 코드 포인트가 하나뿐이어도 여전히 `str`입니다. 따라서 `+` / `-`의 **양쪽이 모두 리터럴**일 때(`'...'`와 `"..."` 조합) 위의 암시적 변환이 적용되어 결과는 정수 연산이 아닌 **연결**이 됩니다.
>
> ```no
> 'x' - "a"                ; "xa"（拼接；不是 120-97 = 23）
> "a" + 'x'                ; "ax"
> 'xy' + "a"               ; "xya"
> ```
>
> 한쪽이라도 **리터럴이 아니면**(char 변수, `s[i]`, 정수) 한 문자 `'...'`는 **바이트**로서 정수 연산에 참여합니다. 이는 의도된 동작이며 숫자 문자 값을 얻는 관용 표현이 성립하는 이유입니다.
>
> ```no
> c char = "5"
> n = c - '0'              ; 5（位元組相減，不是 "50"）
> m = 'A' + 1              ; 66
> "z" - "a"                ; 25（兩側都是 char 字面量，char 相減）
> 'x' - c                  ; 23（c 是變數 → 位元組運算）
> ```
>
> 반대로 바이트 퇴화는 **상대방이 정수나 문자일 때만** 발생합니다. 상대방이 `bool`, `f64`, 구조체처럼 **바이트 의미가 없는** 값이면 `'...'`는 여전히 문자열이고 전체 표현식은 **연결**이 되며, 상대방은 `to-str`로 렌더링됩니다.
>
> ```no
> b = true
> 'x' - b                  ; "xtrue"（不是 120 - 1 = 119）
> 'x' - 1.5                ; "x1.5"
> 'x' - 'y'                ; "xy"（兩側都是字串字面量）
> ```
>
> 따라서 `'x' - b`는 `str`에 할당할 수 있습니다. `s str = 'x' - b`는 `"xtrue"`가 됩니다. 반면 `s str = 'x' - 1`은 바이트 연산(결과가 숫자)이므로 여전히 거부됩니다.

> 암시적 변환은 **단일 코드 포인트**만 `str`로 인코딩합니다. 숫자 값이 필요하다면 `char` 자체를 사용하세요(예: `print(c)`는 해당 코드 포인트의 10진 값을 출력합니다). 명시적 변환이 필요하면 여전히 `c.to-str()`을 사용할 수 있습니다(암시적 변환과 동일).
>
> `char`는 단일 유니코드 스칼라 코드 포인트를 나타내며, 내부 저장 타입은 **`i32`**입니다(유효 범위 `0 ..= 0x10FFFF`).
>
> `char`는 **정수 연산에 정상적으로 참여**할 수 있습니다(`z = a + 25`, `u = ch - 32` 등). 코드 포인트 값을 i32 폭에서 계산합니다. 정수 계열과 달리 기본적으로 `option<int>`를 반환하지 않으므로 "처리되지 않은 정수 오버플로" 컴파일 오류가 발생하지 않습니다.
>
> **렌더링 방식**: `char`를 텍스트로 변환할 때는 항상 **코드 포인트의 10진 값**을 출력합니다(`"A"` → `65`, `"é"` → `233`).
> 또한 `print(c)`와 문자열 보간 `print('{c}')`의 결과는 **반드시 일치**해야 합니다. char 산술은 **부호 있는 i32**로 계산하므로 `"x" - "y"`는 `-1`이며, 두 경로 모두 `-1`을 출력합니다(한쪽이 `4294967295`를 출력하는 일은 없습니다).
> 유효한 코드 포인트는 항상 `0 ..= 0x10FFFF` 범위에 있으며(비트 31이 0), 이 영역에서 부호 확장과 무부호 확장은 동일합니다.
> 따라서 이 규칙은 char 산술이 범위를 벗어나 얻은 음수 값에만 영향을 줍니다. 숫자가 아닌 **문자 자체**가 필요하다면
> `c.to-str()`(`"A".to-str()` → `"A"`)을 사용하세요. 이는 별개의 연산입니다.

## ASCII 최적화와 성능 팁

`str`/`txt`의 인덱스 `s[i]`는 i번째 **바이트**가 아니라 i번째 **코드 포인트(유니코드 문자)**를 가져옵니다. 따라서 중국어, 이모지, `é`처럼 여러 바이트 UTF-8 문자가 포함될 수 있는 문자열에서 `s[i]`를 호출할 때마다 문자열 앞에서부터 UTF-8을 순회하며 i번째 코드 포인트까지 세어야 합니다. 시간 복잡도는 **O(n)**입니다.

컴파일러가 해당 문자열이 전부 ASCII 문자(코드 포인트 0–127)로 이루어졌음을 **증명**할 수 있다면, 각 바이트가 정확히 한 문자가 되므로 `s[i]`가 기반 바이트를 직접 주소 지정하여 **O(1)**로 퇴화합니다. 컴파일러는 다음 규칙으로 순수 ASCII를 증명합니다.

- 명시적 애노테이션: 선언이나 할당 위치에 `#{ascii}` 애노테이션 추가
- ASCII 문자열 리터럴 할당(예: `'hello'`)
- 식별자 전파: `b = a`에서 `a`가 ASCII로 증명되었다면 `b`도 ASCII
- 연결(`-`) 양쪽이 모두 ASCII로 증명된 경우

```no
; ASCII 字面量 → 编译器证明为纯 ASCII，s[i] 为 O(1)
name = 'hello'
c = name[1]; O(1)，取字节 'e'

; 含多字节字符 → 无法证明 ASCII，s[i] 为 O(n) 码点迭代
s = 'héllo'
c = s[1]; O(n)，取第 1 个码点 'é'（而非字节）
```

### 성능 경고(LSP / `no vet`)

ASCII로 증명되지 않은 `str`/`txt`를 **반복문에서 코드 포인트 인덱스로 수동 순회**할 때(즉 `for i <- [0..s.count()): { s[i] }`처럼 코드 포인트 인덱스로 문자를 하나씩 가져오는 표현), `no vet`와 편집기 LSP가 **WARNING** 수준의 정적 경고를 표시합니다(문법을 금지하지는 않으며 안내만 합니다). 이 표현은 `s[i]`마다 문자열 앞에서부터 UTF-8을 순회해 i번째 코드 포인트를 가져오므로 반복문 전체가 **O(n²)**로 퇴화합니다.

단발성 `s[i]`(예: `s[5]`, O(n) 한 번)는 경고하지 **않습니다**. `for c <- s`로 문자를 직접 순회하는 것도 경고하지 **않습니다**(아래 참조).

더 빠른 방법을 권장합니다.

- 각 문자를 순회해야 한다면 `for c <- s`로 전방 순회를 사용하세요. 이는 `s[i]`를 반복해서 호출할 때의 O(n²)를 피하는 최선의 O(n) 단일 스캔 표현입니다. 컴파일러는 **UTF-8 코드 포인트(유니코드 문자)** 단위로 진행하며, 디코딩된 코드 포인트 값을 반복 변수 `c`에 저장합니다. 의미적으로 `for c <- s.to-chars()`와 동일합니다.
  ```no
  c <- s: {
      ; c 는 현재 코드 포인트, 타입은 char (UTF-8로 디코딩됨, 바이트 아님)
  }
  ```
- 바이트 단위 접근만 필요하다면(인코딩/디코딩, 해시, memcmp 등) 탈출구 `s.byte(i)`를 사용하세요. 항상 i번째 바이트를 직접 주소 지정하며 **항상 O(1)**이고, std 함수 본문에 진입하지 않습니다.
  ```no
  b = s.byte(0); 取第 0 個字節，類型 ?byte，O(1)
  out = 0
  b: {
      ok -> {
          out = it; 在界內：ok(byte)
      }

      -> {
          out = 0; 越界：nil（空臂合成零值）
      }
  }
  ```
  > `s.byte(i)`의 결과는 **`?byte`**입니다(2026-10-21부터). 이전의 날것의 바이트 읽기는 경계 검사를 하지 않았고,
  > 범위를 벗어난 인덱스는 미정의 동작이었습니다. 이제 범위를 벗어나면 `nil`을 반환합니다. 컨테이너 인덱스 `arr[i]` / `s[i]`가 범위 초과 시 `err`를
  > (`code.index-out`)를 반환하는 것과는 **다르다는 점에 유의하세요**: `s.byte(i)`는 바이트 수준 탈출구이므로 범위 초과는 "그 바이트가 없다"는 의미일 뿐 오류가 아닙니다.
  > (design/option-unified.md §3.1 5번 항목 참조). 따라서 `b i64 = s.byte(0)`은
  > `15w45dqk` 오류를 발생시킵니다. 명시적 plain 표기와 option 호출이 결합되면 조용한 언패킹이 되어 하드 컴파일 오류입니다.
  > `?=`, 2단계 match(`b = s.byte(0): { ok -> it, -> _ }`), 또는 `_ =`로 소비해야 합니다.
  > `txt.byte(i)`의 의미도 동일합니다(`txt`의 `byte` field 1이 곧 바이트 길이).

> 표준 라이브러리(src/std) 내부의 바이트 접근은 모두 `s.byte(i)`로 마이그레이션되었습니다. `str.no`/`txt.no`의 UTF-8 인코딩/디코딩(`decode-cp`), 비교(`compare`/`starts-with`/`ends-with`), 해시, 슬라이스 복사(`slice`/`repeat`/`trim`/`copy`), `to-bytes`/`to-upper`/`to-lower`/`reverse`/`replace-char`/`count`/`index` 등이 포함됩니다. 따라서 `no vet`가 표준 라이브러리 파일을 건너뛸 필요가 없습니다. 나머지 `[]byte`/슬라이스/배열 타입의 요소 접근 `x[i]`는 본래 요소(바이트) 단위 인덱스이므로 의미가 바뀌지 않으며 경고도 발생하지 않습니다.

| 표기 | 의미 | 복잡도 | 설명 |
|---|---|---|---|
| `s[i]`(ASCII 증명됨) | i번째 바이트 = i번째 문자 | O(1) | 자동으로 증명되며 수정 불필요 |
| `s[i]`(ASCII 미증명, 반복문 내부) | i번째 코드 포인트 | O(n²) 안티패턴 | LSP 경고 발생 |
| `s[i]`(ASCII 미증명, 반복문 외부) | i번째 코드 포인트 | O(n) 한 번 | 경고 없음 |
| `s.byte(i)` | i번째 바이트(`?byte`, 범위 초과 시 `nil`) | O(1) | 바이트 접근 탈출구 |
| `for c <- s` | 코드 포인트별 순회 | O(n) 단일 스캔 | 순회 시 우선 선택, 경고 없음 |

## 인덱스 쓰기 금지(`str` 2026-11-11 / `txt` 2026-11-12)

> **`s[i] = v`는 컴파일 오류 `idxwrite`입니다**. `with-cap` / `with-len` / `with-cap-len` 세 가지 기반 모두 예외가 없습니다.
> **`txt`의 `t[i] = c`도 마찬가지로 금지됩니다**(이유는 아래 참조).
>
> `str`의 경우: "할당된 버퍼 외부에 쓰기"의 유일한 원인입니다. len=0 버퍼를 직접 쓰기로 증가시키는데,
> `i >= cap` 위치에 쓰면 할당 영역을 벗어납니다. codegen의 `ensureStrLongBuffer` 증가 가드 원래도
> 이를 위해 마련되었으나, 직접 쓰기를 금지한 뒤로는 사용자 코드에서 도달할 수 없어 방어적 코드로만 남았습니다.
>
> `txt`의 이유는 다르지만 죄는 같습니다. `t[i] = c`는 코드 포인트 단위로 **재인코딩하여 다시 쓰는** 방식이라 길이가 쓰기와 함께 암시적으로 바뀝니다
> (`i`가 코드 포인트 수와 같으면 추가와 동일하고, 255를 초과하는 부분은 조용히 버려집니다). txt에는 힙도 확장도 없지만,
> "한 번의 인덱스 쓰기가 길이를 몰래 바꾼다"는 점에서 같은 종류의 위험입니다.

여전히 허용되는 네 가지 표기:

```no
; ① 逐位元組「構造」：[]byte 緩衝承接，收尾整體轉回 str
b []byte = with-cap-len(n, n)
b[0] = 48
b[i] = src.byte(i): {
    ok -> it

    -> 0
}
s = b.slice(0, k).to-str(); 也可 b.to-str()（整段）

; ② 原位「覆寫」既有內容：str.fill 把 len 個位元組全填成同一個值，長度不變
s = 'hello'
s.fill(72); 'HHHHH'

; ③ 下標寫只剩 place-match（以「讀」作閘門：i >= len 時靜默跳過，不增長、不越界）
s[i]: {
    ok -> it = v
    -> _
}

; ④ 要變長：用 push 家族（顯式、可審計的一次呼叫）
s.push("中");      按碼點追加（UTF-8）
s.push-str('de');  按位元組追加（原地擴容）
```

> ⚠️ **place-match는 "코드 포인트" 게이트이지 "바이트" 게이트가 아닙니다.** 이 게이트는 `s[i]`라는
> **읽기**에서 비롯되며, `str`의 인덱스 읽기는 코드 포인트 단위로 셉니다. 따라서 ③은 "한 코드 포인트를 한 칸에 쓰는"
> ASCII 상황(uuid에 하이픈 넣기, time에 숫자 넣기, hex 테이블 조회)에만 적합합니다. **바이트** 단위로 내용을 이어 붙이려면
> (`>= 0x80`인 바이트가 포함되거나 비 ASCII일 수 있는 모든 원본 문자열) ①의 `[]byte`를 사용해야 합니다.
> 실제로 `f = with-len(8)` 후 place-match로 224..231을 순서대로 쓰면 앞의 4칸만 반영되고,
> 나머지는 게이트에 의해 조용히 건너뛰어집니다. `path.split`의 "비 ASCII 파일명"이 바로 이렇게 잘려 나갑니다.

> **길이 자르기**: 날것의 `s.len = n`은 더 이상 지원되지 않으므로 슬라이스를 사용하세요. `s.slice(0, n)`은 **코드 포인트** 슬라이스이고,
> `s.slice-bytes(0, n)`만이 바이트 슬라이스입니다(`[]byte` 버퍼의 `b.slice(0, k)`는 당연히 바이트 슬라이스입니다).
>
> **`with-cap(n)`로 str를 만든 뒤 `push`로 증가시키기**: `s str = with-cap(256)`은 len=0이지만 이미
> 용량이 있는 버퍼이므로 첫 `push`가 바로 기록되며 확장이 발생하지 않습니다(`push-str`은 `len + 추가 길이`가
> `cap`을 넘을 때만 realloc하며 배로 증가합니다). 바이트 단위의 `buf[i] = b`는 str에 대해 여전히 금지됩니다.

### 증가: `push` 계열(2026-11-12)

직접 쓰기가 금지된 뒤로 **가변 길이 변경은 명시적인 한 번의 호출이어야 합니다**.

| 메서드 | 의미 |
|---|---|
| `s.push(c char)` | 코드 포인트 하나를 추가하며 UTF-8로 인코딩합니다(내부적으로 `push-str`에 위임) |
| `s.push-str(t str)` | 문자열을 추가하며 **바이트 단위**로 복사하고 제자리에서 확장합니다 |

```no
s = 'ab'
s.push("中");      'ab中'，len-bytes 5、len 3
s.push-str('de');  'ab中de'，len-bytes 7

t = 'zz'
t.push-str(t);     'zzzz'（自我追加安全：先 retain 源、再用 memmove 拷貝）

u = ''
u.push-str('');    ''（空源不改變任何東西，也不分配）
```

> `push-str`는 컴파일러 내장 함수입니다(`#{buildin}`, MIR에서 "제자리 확장 + memmove + 길이 변경"으로 전개됨).
> std 반복문이 아닙니다. 한 번 추가할 때 O(추가 길이)이고, 반복 추가 시 분할 상환 O(1)입니다(배가 증가).
> `push`는 UTF-8 인코딩을 거치므로 `len-bytes`의 증가량은 해당 코드 포인트의 인코딩 길이와 같고, `len`은 항상 1씩 증가합니다.

> **`txt`의 쓰기도 마찬가지로 금지되었습니다(2026-11-12)**: `t[i] = c`는 **코드 포인트 수준의 재인코딩 쓰기**로, 길이가
> 쓰기와 함께 암시적으로 바뀝니다. `i`가 코드 포인트 수와 같으면 추가와 동일하고, 전체 바이트 길이가 255를 넘는 부분은 조용히 버려집니다.
> "한 번의 인덱스 쓰기가 길이를 몰래 바꾼다"는 것이 바로 이 금지령이 없애려는 대상이며, txt도 str과 같은 방식으로 처리됩니다. txt의 가변 길이
> 진입점은 `t.push(c)` / `t.push-str(s)` / `t.push-txt(u)`이고, 제자리에서 값을 바꾸려면 place-match를 사용합니다.
> `t[i]` 읽기는 여전히 코드 포인트 `char`를 반환하며, 이 점은 바뀌지 않았습니다.
>
> 바이트 수준 원시 기록기 `str._set-byte` / `txt._set-byte`는 2026-11-11부터 **std 전용**입니다
> (std 내부의 `str.fill` / `txt.push` 등만 호출하며), 사용자 코드에서는 사용할 수 없습니다.
> 바이트 단위로 `txt`를 이어 붙여야 한다면 먼저 `[]byte`를 모은 뒤 `txt.from-bytes(b)`로 한 번에 복사하세요
> (255바이트를 넘으면 자동으로 잘리며, 길이는 실제 바이트 수로 설정됩니다).

## 사전 할당(내장 문법)

`with-cap`, `with-len`, `with-cap-len` 세 가지 내장 문법으로 힙 메모리를 미리 할당하면 이후 `push`로 인한 반복 확장을 피할 수 있습니다.

```no
; with-cap(cap)：配置 cap 容量，len=0（需 push 後才能索引）
s = with-cap(256); str，len=0, cap=256

; with-len(len)：配置 len 容量，len=cap（可直接索引讀）
s = with-len(128); str，len=128, cap=128

; with-cap-len(cap, len)：同時指定容量與長度，適合「預留成長空間」場景
s = with-cap-len(512, 64); str，len=64, cap=512
```

| 내장 문법 | 매개변수 | len | cap | 적용 상황 |
|---|---|---|---|---|
| `with-cap(cap)` | 1 | 0 | cap | 상한만 알고 길이는 push로 증가시키는 경우 |
| `with-len(len)` | 1 | len | len | 고정 길이이며 바로 인덱스로 읽을 수 있는 경우 |
| `with-cap-len(cap, len)` | 2 | len | cap | 초기 길이를 알고 확장 공간도 미리 확보해야 하는 경우 |

> 매개변수와 `s.cap()` / `s.len-bytes()`의 반환값은 모두 **`i64`**입니다(외부 API는 그대로). 하지만 디스크립터 내부에는
> **`u32`**로 len / cap을 저장합니다. 호출자가 보는 값은 여전히 64비트 숫자이며, 변환은 컴파일러가 디스크립터 경계에서 수행합니다.
> 자세한 내용은 〈내부 레이아웃과 외부 API〉 참조. `s.len = n` / `s.cap = n` 같은 필드 쓰기도 이 경계를 거치므로,
> 인접한 헤더 필드를 덮어쓰지 않습니다.

> ⚠️ **`str`의 버퍼에는 인덱스 직접 쓰기가 전혀 허용되지 않습니다**(2026-11-11부터 `with-cap` 기반도 더 이상 예외가 아님).
> `idxwrite`의 with-cap 예외는 이제 **`[]byte` / `[]T` / 고정 배열**만 해당됩니다. 이들의 len=0
> 버퍼는 여전히 `buf[i] = b`로 길이를 증가시키며, 이에 대체할 표현이 없습니다. `str`은 `[]byte` 버퍼 +
> `to-str()`를 사용하세요(〈인덱스 쓰기 금지〉 절 참조).
> `with-len(n)` / `with-cap-len(cap, len)`의 len은 이미 제자리에 있습니다. **쓰기는 place-match
> `buf[i]: { ok -> it = v / -> _ }` 또는 `buf[i] ?= v`를 사용해야 합니다**. 다른 모든 컨테이너와 마찬가지로 직접 쓰기는
> 컴파일 오류 `idxwrite`입니다(2026-11-10부터 `with-len`도 예외가 아님).

> **타입 추론**: 세 가지 내장 문법의 결과 타입은 할당문 왼쪽에서 추론되며, `str`이나 `[]T` 슬라이스에 사용할 수 있습니다.
