# 문법


## 주석

Nolang은 **한 줄 주석** 기호와 **여러 줄(블록) 주석** 기호를 지원합니다:

- `;` — 한 줄 기호(줄 끝까지 주석 처리)
- `;; <내용>` — 한 줄 기호(`;;` 뒤 **같은 줄**에 내용이 있으면 줄 끝까지 주석 처리하며, 의미는 `;`와 동일)
- `;;\n` — 여러 줄(블록) 주석: `;;` 뒤에 **바로 줄바꿈**이 오면(공백만 허용) 여러 줄 모드가 시작되고, 같은 방식으로 줄바꿈/EOF가 뒤따르는 `;;`를 만날 때까지 지속됩니다

```no
; 這是註釋
; 這也是註釋，語義相同
;; 這還是單行註釋（;; 後沒有換行）
x = 1; 行內註釋，註釋到行尾
x = 2;; 行內單行註釋，語義相同

;;
這是多行（塊）註釋
可以跨多行
直到遇到單獨的 ';;'
;;

y = 3
;;
結束 ;; 後必須換行或文件尾
才會被視為結束定界符
;;
```

> **여러 줄 시작 규칙:** `;;` 뒤에는 줄바꿈이나 EOF까지 **공백(스페이스/탭)만** 있어야 여러 줄 모드로 진입합니다. `;;` 뒤 같은 줄에 공백이 아닌 문자가 하나라도 있으면 한 줄 주석(줄 끝까지 주석)으로 처리됩니다.
>
> **여러 줄 종료 규칙:** 종료용 `;;` 역시 뒤에 줄바꿈이나 EOF가 와야 합니다(중간에는 공백만 허용). 닫히지 않은 여러 줄 주석은 파일 끝까지 계속 주석 처리됩니다.

> **규칙: 한 줄에 하나의 문장만 작성하며, 한 줄에 여러 문장을 쓰는 것은 금지됩니다.**
> 세미콜론 `;`은 **주석 기호**이지 문장 구분자가 아닙니다. 쉼표 `,`로도 여러 문장을 연결할 수 없습니다. 같은 블록 `{ ... }` 안의 모든 문장은 각각 한 줄을 단독으로 차지해야 합니다.
> 이 규칙은 주석 안의 코드 예제에도 동일하게 적용됩니다. 주석 안에서도 `;`나 `,`로 여러 문장을 한 줄에 쓰지 마세요. 독자를 오도할 수 있습니다.

```no
#{fmt-skip}
; ❌ 錯誤：用 `;` 分隔多條語句 —— `;` 之後整行都是註釋，
; 連塊的 `}` 也被一起註釋掉，塊無法閉合，後續程式碼被靜默丟棄
; cond -> { print('X'); return }

; ❌ 錯誤：用逗號連接多條語句
; h0 = 1732584193, h1 = 4023233417
; out = from-i64(v), out = from-u64(v)
; debug(msg), info(msg), warn(msg)
```

```no
; ✅ 正確：每條語句獨佔一行
cond -> {
    print('X')
    return
}

; ✅ 正確：每條語句獨佔一行
; h0 = 1732584193
; h1 = 4023233417
; out = from-i64(v)
; out = from-u64(v)
; debug(msg)
; info(msg)
; warn(msg)
```

> **`;`가 특히 위험한 이유:** `cond -> { print('X'); return }`에서 `; return }` 전체가 주석으로 처리되어 실제 코드는 `cond -> { print('X')}`만 남습니다. 블록이 닫히지 않으므로 `}` 뒤의 모든 문장(대개 해당 함수의 나머지 전체 함수 본문)이 통째로 삼켜지고, 오류 위치도 크게 어긋날 수 있어 원인을 찾기 매우 어렵습니다.

### char 타입(Unicode 코드 포인트)

`char`는 **단일 Unicode 스칼라 코드 포인트**(scalar value)를 나타냅니다. 내부 저장 타입은 `i64`가 아닌 **`i32`**입니다:

- **허용 범위**: `0 ..= 0x10FFFF`(즉 `0 ..= 1114111`). 코드 포인트 최대값은 21비트면 충분하므로 `i32`에 완전히 들어갑니다.
- **범위 초과 시 오류**: 리터럴이 이 범위를 벗어나면 컴파일 타임(`no vet` 포함)에 **즉시 오류가 발생합니다**. 예: `c char = 0x110000` ✗, `c char = 1114112` ✗; `c char = 1114111` ✓.
- **숫자 연산 허용**: `char`는 **정수 연산에 직접 참여할 수 있습니다**. `z = a + 25`나 `u = ch - 32`(`ch`는 `for ch <- s`의 반복 변수)는 모두 **정상적인 표현**이며, 코드 포인트 값을 기준으로 더하거나 뺍니다. 연산은 항상 **i32 너비**로 수행되고 결과는 일반 정수 값으로 간주됩니다. 바로 이 때문에 `char`의 `+ - * /`는 **정수 계열처럼 기본적으로 `option<int>`를 반환하지 않아** "처리되지 않은 정수 오버플로" 컴파일 오류가 발생하지 않습니다. 주의할 점은 범위뿐입니다. 코드 포인트는 최대 `0x10FFFF`이므로, `i32`/코드 포인트 의미를 벗어나는 용도(오프셋이나 누적 카운트 등)에는 먼저 `i32`/`i64`로 명시적으로 변환한 뒤 계산하는 편이 의도를 더 분명히 드러냅니다.
- **`str`와의 관계**: `s[i]`는 `char`를 반환하고, `char`는 `str`로 암시적 변환됩니다(UTF-8 인코딩). 자세한 내용은 [문자열 — 암시적 변환](str.md)을 참고하세요.

> **"내부 타입"과 "호출 시 변환"은 별개입니다.** `char` 자체가 곧 `i32`입니다. 내장 함수 `str_from_cp(cp char) -> ?str`의 **소스 코드 시그니처**상 매개변수는 `char`입니다. **외부 런타임을 호출할 때만** 컴파일러가 이 i32 인자를 `@str_from_cp`의 IR 입력에 맞추기 위해 **제로 확장**(`zext i32 → i64`)합니다. 이는 인자를 준비하는 단계의 임시 변환일 뿐 **`char`의 타입은 바뀌지 않습니다**. C의 `char c='a'; f((long)c);`와 비슷합니다. `c` 자체는 1바이트이며, 호출 시점에 일시적으로 승격됩니다.

## 타입 별칭과 유니온 타입

타입 별칭은 기존 타입에 새로운 이름을 붙입니다. 등호 문법 `name = type`을 사용하며, 단일 타입 별칭과 여러 타입의 유니온을 지원합니다.

### 문법

```no
; 聯合類型：多個類型用 | 分隔
int = i8 | i16 | i32 | i64 | i128 | u8 | u16 | u32 | u64 | u128
float = f32 | f64
num = int | float
string = str | txt

; 單一類型別名
bytes = []byte
buf = [16]u8
```

> `int`, `float`, `num`은 `std/number`에, `string`은 `std/str`에 정의되어 있습니다. 이들은 컴파일러 내장 키워드가 아니라 표준 라이브러리가 동일한 별칭 문법으로 작성한 유니온 타입입니다.

### 유니온 타입의 연결 참조

유니온 타입은 다른 유니온 타입을 참조하여 계층 구조를 형성할 수 있습니다:

```no
int = i8 | i16 | i32 | i64 | i128 | u8 | u16 | u32 | u64 | u128
float = f32 | f64
num = int | float; num 是 int 和 float 的聯合
string = str | txt; string 直接聯合兩個具體字符串類型
```

### 함수에서 사용

유니온 타입은 함수 매개변수와 반환값에 사용할 수 있으며, 컴파일러가 자동으로 단형화(monomorphization)를 수행하여 각 구성원 타입마다 별도의 함수 버전을 생성합니다:

```no
; 參數類型為 num 聯合
max = (a ..num) (r num) {
    r = a[0]
    n = len(a)
    i <- [1..n): {
        a[i] > r -> r = a[i]
    }
}

; 方法定義在聯合類型上
num.sign = () (r num) {
    {
        . > 0 -> r = 1

        . < 0 -> r = -1

        -> r = 0
    }
}
```

`string`(= `str | txt`)도 매개변수와 반환값에 사용할 수 있습니다:

```no
; str 與 txt 實參都能傳入，各自單態化一份具體函數
take = (s string) (n i64) {
    n = len(s)
}

a str = 'hello'
b txt = 'hi'
n1 = take(a); take__str
n2 = take(b); take__txt
```

> 유니온 타입 함수 본문의 기존 제한(`num`과 `string` 동일): 함수 본문에서 union 매개변수의 멤버 메서드(예: `s.len()`)를 호출하는 것은 아직 지원되지 않으므로, 전역 내장 함수(`len(s)`, 바이트 수)를 사용하거나 구체 타입 전용 함수로 나눠야 합니다. 유니온 타입의 변수 선언(`s string = 'x'`)도 아직 지원되지 않습니다. 또한 멤버 메서드와 이름이 같은 별칭 메서드(예: `string.len`)를 정의하지 마세요. 그렇게 하면 `s.len()` 호출을 가로채 메서드 본문에서 자기 자신으로 재귀 디스패치됩니다.

### 감지 규칙

등호 문법은 다음 경우에 타입 별칭으로 인식됩니다(변수 할당이 아님):

- `name = type | type | ...`: 유니온 타입(`|` 포함)
- `name = []type`: 슬라이스 타입
- `name = [N]type`: 배열 타입
- `name = ?type`: 옵션 타입
- `name = known-type`: 단일 타입 별칭. 여기서 `known-type`은 내장 타입 이름(예: `i64`, `f64`, `bool`, `str` 등)이거나 이미 정의된 타입 별칭의 이름입니다

## 원시 문자열(Raw String)

한 쌍의 백틱 `` ` `` ` ` `` ` ``으로 원시 문자열을 선언하며, 타입은 `str`입니다.

### 문법

```
sql = `
SELECT id,name
FROM user
WHERE id > 100
`
```

### 강제 형식 제약

1. **시작** `` ` `` 뒤에는 **반드시 소스 코드의 줄바꿈**이 이어져야 합니다(LF; Windows 파일의 CRLF도 허용);
2. **끝** `` ` ``은 **반드시 한 줄을 단독으로 차지**해야 하며, 그 줄에는 공백 + 닫는 백틱만 허용됩니다;
3. **첫 줄과 마지막 줄의 백틱이 있는 줄은 문자열 내용에 포함되지 않으며**, 구분 기호로만 사용됩니다;
4. **이스케이프 규칙**: 내부의 `\`、`\n`、`\t`、`\'`、`\"`은 모두 **그대로 유지**하며, 이스케이프 처리를 전혀 하지 않습니다;
5. **소스 코드의 줄바꿈과 들여쓰기 공백을 문자열 바이트에 온전히 보존**합니다. CR(`\r`)은 예외로 **항상 버립니다**. 따라서 CRLF 파일과 LF 파일은 바이트 단위로 동일한 값을 얻습니다;
6. **백틱 문자를 직접 삽입할 수 없습니다.** 포함해야 한다면 `` ` ``을 일반 작은따옴표 문자열과 연결해야 합니다.

### 예

```
; 內容為 "SELECT id,name\nFROM user\nWHERE id > 100\n"
; 轉義字符 \n \t 原樣保留，不解釋
raw = `
line1\nline2
\ttabbed
`
```

## 정규식 리터럴(Regex Literal)

Nolang은 JavaScript 스타일의 정규식 리터럴 문법 `/pattern/flags`을 지원하여 컴파일된 `regexp` 인스턴스를 생성합니다.

### 문법

```no
; 基本正則字面量
re = /\d+/

; 帶旗標（flags）
re = /hello/gi

; 字符類、錨點、量詞
re = /[a-z]+/
re = /^hello.*world$/

; 轉義斜線
re = /a\/b/
```

### 플래그

| 플래그  | 의미        |
| --- | --------- |
| `g` | 전체 일치      |
| `i` | 대소문자 구분 없음    |
| `m` | 여러 줄 모드      |
| `s` | `.`가 줄바꿈과 일치 |

플래그는 선택 사항이며, 끝의 `/` 뒤에 오고 ASCII 문자로 구성됩니다.

### 문맥 의존적 렉싱

`/`는 나눗셈 연산자이자 정규식 리터럴의 시작 기호이므로, Nolang은 JavaScript와 동일한 **문맥 의존** 렉싱으로 이를 구분합니다:

- **표현식 시작 위치**(문장 시작, `=` / `(` / `[` / `{` / `,` / `:` / `;` 등 뒤) → `/`가 정규식 리터럴을 시작합니다
- **값 생성 위치**(식별자, 리터럴, `)` / `]` / `}` 등 뒤) → `/`는 나눗셈 연산자입니다
- `//`는 항상 한 줄 주석입니다(우선순위가 가장 높음)

```no
; 正則字面量（= 後是表達式起始位置）
re = /\d+/
result = match-text(/[a-z]+/, text)

; 除法運算符（標識符後是值產生位置）
ratio = 100 / 4
x = a / b
```

### 디슈가링

정규식 리터럴은 코드 생성 단계에서 표준 라이브러리 `regexp-compile` 함수 호출로 디슈가링됩니다:

```no
; 源碼
re = /\d+/

; 脫糖後等價於
re = regexp-compile('\\d+')
```

`regexp-compile`은 `std/regexp.no`에 정의되어 있으며, `regexp` 구조체를 만들고 `.compile()`을 호출해 패턴을 컴파일합니다.

### 사용 예

```no
; 創建正則並匹配
re = /\d+/
matched = re.matches('hello 123 world')
print(matched); true

; 查找匹配
re = /[a-z]+/g
result = re.find('hello 42 world')
print(result); "hello"

; 作為函數參數
result = match-text(/\d+/, text)
```

> **주의:** 빈 패턴 `//`은 한 줄 주석과 충돌합니다(JavaScript와 동일한 동작). 빈 일치가 필요하다면 `/(?:)/`를 사용하세요.

## 명명 규칙

변수명, 함수명, 구조체명 등은 밑줄로 시작할 수 있으며, 이후에는 하이픈, 문자, 숫자를 사용할 수 있습니다. 숫자로 시작할 수 없고, 하이픈으로 끝날 수 없으며, 하이픈을 연속으로 여러 개 사용할 수 없습니다

**대소문자 규칙(반드시 준수):**

- **전역 상수, 전역 변수**: **반드시** 대문자로 시작해야 합니다(예: `NOLANG`, `MAX-SIZE`, `HEX-CHARS`). 비공개 전역 변수는 밑줄로 시작하며 그 다음은 역시 대문자여야 합니다(예: `_NOLANG`, `_PRIVATE-CONST`).
- **지역 변수, 함수 매개변수**: 소문자를 사용합니다(예: `hex-chars`, `data-len`). `_` 접두사는 **사용하지 마세요**. 지역 변수는 이미 스코프 안에서 비공개이므로 가시성 표기가 필요 없습니다. `_` 접두사는 비공개 전역 변수와 FFI 비공개 선언에만 사용합니다.
- **함수명, 구조체명**: 소문자를 사용합니다(예: `sha1-block`, `db-mysql`)

**함수 명명 관례(강력 권장):**

- **함수명에 모듈명 접두사를 붙이지 마세요**. 모듈 안의 함수는 짧고 직관적인 이름이면 충분하며, 모듈 접두사는 다른 모듈에서 호출할 때 `ShortName.`으로 자동으로 붙습니다. 예를 들어 `tail.no`에서 진입 함수를 `tail-run`이 아닌 `tail`로, 보조 함수를 `tail-atoi`가 아닌 `atoi`로 정의하세요. 이렇게 하면 코드가 더 간결해지고, `tail.tail()`처럼 다른 모듈에서 호출할 때도 직관적입니다.
- **진입 함수**는 모듈명 자체를 그대로 사용하는 것이 좋습니다(예: `ping.no` → `ping`, `cat.no` → `cat`). 다른 모듈에서 가져올 때는 `# /src/tail.tail` 형태가 됩니다.
- **키워드를 피하세요**: `awy`(코루틴 그룹 키워드), `match`(조건 매치 키워드) 등은 함수명으로 쓸 수 없습니다. `run`은 제거되었으므로 일반 식별자로 사용할 수 있습니다.
- **`main`은 예약 이름이므로 함수명으로 사용할 수 없습니다**: Nolang의 프로그램 진입점은 **최상위 문장에서 자동으로 합성**되므로(`hir2mir.synthesizeMainForTopLevel` 참조) `main`을 명시적으로 정의할 필요가 없으며 **허용되지도 않습니다**. `main = (...) { }`이 나타나면(`recv.main` 메서드나 다른 함수 안에 중첩된 `main` 포함) 컴파일러가 즉시 오류를 냅니다(`'main' is a reserved name and cannot be used as a function name`). 진입점이 필요하다면 문장을 최상위에 직접 작성하면 됩니다.

> **전역 변수는 대문자로 시작해야 합니다.** 이는 관례가 아닌 강제 규칙입니다. 소문자로 시작하는 최상위 변수는 컴파일러에 의해 지역 변수로 취급되어 미정의 참조 등의 오류가 발생할 수 있습니다.

```no
; ✅ 正確：全局數據使用大寫字母
NOLANG = 'nolang'
MAX-SIZE = 1024
HEX-CHARS = '0123456789abcdef'

; ✅ 私有全局變量：下劃線開頭，其後仍需大寫
_NOLANG = 'nolang'
_PRIVATE-CONST = 42
```

```no
#{fmt-skip}
; ❌ 錯誤：全局變量不能使用小寫字母開頭
; x1 = 10
; x = 10
; foo-bar = 42
; hello-world = 'Hello World'
```
```

```no
#{fmt-skip}
; ✅ 局部變量（函數內）使用小寫字母，不加 _ 前綴
; fn-example = () {
;     x1 = 10
;     x = 10
;     foo-bar = 42
;     hello-world = 'Hello World'
;     ; ❌ 錯誤：局部變量不需要 _ 前綴
;     ; _x = 10
; }
```
```

### 모듈에서 전역 변수 사용 피하기

**강력 권장: 꼭 필요한 경우가 아니라면 모듈(`.no` 파일)에서 전역 변수를 사용하지 마세요.** 전역 변수는 다음과 같은 문제를 일으킵니다:

- **컴파일러 버그 위험**: Nolang 컴파일러는 전역 구조체 변수의 함수 간 메모리 주소 처리에 알려진 한계가 있어, 함수마다 다른 주소를 볼 수 있어 상태가 불일치할 수 있습니다.
- **동시성 안전**: 전역 가변 상태는 fork나 비동기 상황에서 추적이 어렵고 경쟁 조건을 유발하기 쉽습니다.
- **테스트 용이성**: 전역 상태는 함수에 암묵적인 의존성을 생기게 해 테스트를 격리하기 어렵습니다.
- **코드 가독성**: 전역 변수는 데이터 흐름을 불분명하게 만들어, 독자가 모듈 전체를 따라가야 함수 동작을 이해할 수 있습니다.

**권장 사항:**

1. **지역 변수를 우선 사용**: 상태를 함수 안의 지역 변수에 두고 매개변수와 반환값으로 전달하세요.
2. **구조체로 상태 캡슐화**: 관련 상태를 구조체로 묶고 메서드로 조작하세요(메서드 수신자가 지역 변수이므로 주소가 일치합니다).
3. **꼭 필요할 때만 전역 변수 사용**: 모듈 수준 상수(불변), 싱글턴 리소스(예: 전역 로그 버퍼) 같은 경우입니다.
4. **전역 변수는 대문자로**: 이는 강제 규칙입니다(위 참조). 소문자로 시작하는 최상위 변수는 컴파일러가 지역 변수로 취급합니다.

```no
#{fmt-skip}
; ❌ 避免：在模組中使用全局可變變量
; g-conn = tls.conn {}
; g-buf = ' '
;
; fn-a = () {
;     g-conn.send(g-buf)   ; 全局變量跨函式可能位址不一致
; }
```
```

```no
; ✅ 推薦：使用局部變量，狀態透過參數/返回值傳遞
fn-a = () {
    conn = tls.conn {}; 局部變量，位址一致
    buf = ' '
    conn.send(buf)
}

; ✅ 推薦：將完整流程封裝在單一函式中，避免狀態跨函式傳遞
serve-once = (listen-fd fd, body str) (ok bool) {
    ok = false
    client-fd = net.net-accept(listen-fd)
    conn = tls.server-init(client-fd); 局部變量
    conn: {
        ok -> {
            c = it
            c.handshake()
            c.send(body)
            c.close()
            ok = true
        }

        -> fs.close(client-fd)
    }
}
```

> **실제 사례**: `std/net/tls.no`의 `https-serve-once` 함수는 전체 HTTPS 요청-응답 주기(accept + handshake + recv + send + close)를 하나의 함수에 캡슐화하고 모든 TLS 상태를 지역 변수에 유지함으로써, 전역 변수의 함수 간 주소 불일치 컴파일러 버그를 성공적으로 피했습니다.

## API 문서 규범

함수의 문서 주석에는 매개변수 이름과 타입, 반환 매개변수 이름과 타입을 모두 포함해야 합니다.

**규칙:**

- 함수 정의 위의 문서 주석에는 각 매개변수의 이름과 타입, 반환 매개변수의 이름과 타입을 모두 나열해야 합니다
- 모듈 상단의 API 요약도 생략형을 쓰지 말고 전체 시그니처(매개변수 이름, 타입, 반환 이름, 타입 포함)를 사용해야 합니다

```no
#{fmt-skip}
; ❌ 錯誤：缺少型別，缺少返回參數名
; sha1(data) (hash)
; sha1-block(s, h0..h4)
```
```

```no
; ✅ 正確：包含參數名、型別、返回參數名、型別
; sha1(data []byte) (hash [20]byte) — 完整雜湊
; sha1-block(s []u32, h0 u32, h1 u32, h2 u32, h3 u32, h4 u32) — 處理單一區塊

; 函數定義上方的文檔註釋也應遵守同樣規範：
; sha1: 計算 SHA-1 雜湊
; data []byte: 輸入位元組陣列

sha1 = (data []byte) (hash [20]byte) {

}
```

### 번역 가능한 문서 주석(Markdown 링크)

문서 주석은 **독립적인 Markdown 링크** 한 줄로 끝맺어, 주석 전체를 번역 디렉터리의 한 항목으로 가리킬 수 있습니다:

```no
; get: 獲取第 i 個參數
; 委派至 os.arg(i) builtin（讀取 main 的 argv[i]）；越界回傳 nil
; [get](#args.get)
get = (i i64) (val ?str) {
    val = os.arg(i)
}
```

**규칙:**

- 링크는 주석 그룹의 **마지막 줄**에 있어야 하며 한 줄을 단독으로 차지해야 합니다. 그 위의 모든 줄이 하나의 전체 메시지를 이루며 통째로 번역됩니다
- 대상은 `#`으로 시작하는 앵커여야 합니다(같은 디렉터리 안의 항목). `[설명](https://example.com)` 같은 외부 링크는 사람이 읽는 일반 링크이며 **번역 표식으로 취급되지 않습니다**
- 앵커가 곧 키입니다(`args.get`). 작성자가 지정하고 번역자가 디렉터리에서 확인하며, 텍스트에서 유도되지 않으므로 표현을 바꿔도 기존 번역이 무효화되지 않습니다. 앵커에는 문자, 숫자, `.`, `_`, `-`가 허용되며 전역이므로 모듈 접두사를 붙이는 것이 좋습니다
- 접두사는 **디렉터리명이 아닌 평탄화된 모듈명**입니다. 컴파일러는 std 파일을 파일명으로 평탄화합니다. `std/collection/linked-hash-map.no`의 모듈은 `linked-hash-map`이며, `use std/collection`을 써도 심볼에 `collection.` 접두사가 붙지 않습니다. 따라서 `linked-hash-map.clear`의 앵커는 `linked-hash-map.linked-hash-map.clear`(모듈명 + 그대로의 이름)이며, **`collection.linked-hash-map.linked-hash-map.clear`가 아닙니다**. `collection`／`net`／`crypto`／`archive`／`encoding`／`database` 같은 디렉터리 구간은 어떤 심볼에도 속하지 않으므로 앵커에 포함되지 않습니다
- 대괄호 안의 글자(`[get]`)는 원본 코드를 읽는 사람을 위한 힌트일 뿐이며, 표시될 때 해당 줄 전체가 제거됩니다. `[](#args.get)`도 유효합니다
- `;` 한 줄 주석만 링크를 가질 수 있습니다(`;;`와 `;;block`은 해당하지 않음)

번역문은 `locales/<언어>-doc.noml`에 앵커를 키로 하여 둡니다. 번역이 없으면 주석 원문으로 되돌아가며, 빈칸이 되지는 않습니다. 파일명은 `.no`의 명명 규칙(소문자, 숫자, 단일 하이픈)을 따르며, 태그 자체가 그 형태입니다. 즉 `--lang=zh-tw`는 `zh-tw-doc.noml`을 읽습니다.

표준 라이브러리에서 주석이 있는 모든 함수와 메서드에는 앵커가 붙어 있어(약 2000건) 번역 하나가 반영되는 즉시 LSP에서 사용할 수 있습니다. `make i18n`은 **번역된** 항목만 디렉터리에 기록하며, 원문을 번역처럼 넣지 않습니다. 그렇지 않으면 영어 디렉터리에 다시 중국어가 나타납니다. `go run ./i18n/cmd/genen -doc-missing`은 아직 번역되지 않은 앵커를 나열합니다.

**LSP 팁:** 함수명에 마우스를 올리면 번역된 설명 전체가 표시되고, 링크가 있는 줄에 올리면 앵커 자체가 가리키는 내용(역시 현재 언어)이 표시되어 번역을 즉석에서 확인할 수 있습니다.

## 표준 라이브러리 우선 사용

Nolang 표준 라이브러리는 문자열 조작, 바이트 변환, 해시 계산, 네트워크 통신 등을 포함한 풍부한 공통 기능을 제공합니다.

**규칙: 표준 라이브러리에 이미 해당 기능이 있다면 직접 다시 구현하지 않는 것이 좋습니다.** 개발자는 표준 라이브러리 문서(`docs/docs/std/overview.md`)를 자세히 살펴 바퀴를 다시 만들지 않도록 해야 합니다.

```no
#{fmt-skip}
; ❌ 錯誤：自行實現 str → []byte 轉換
str-to-bytes = (s str) (out []byte) {
    n = s.len-bytes()
    i = 0
    (i < n) {
        out[i] = s[i]
        i = i + 1
    }
}
```
```

```no
; ✅ 正確：使用標準庫 str.to-bytes() 方法
data []byte = s.to-bytes()
```

자주 쓰이는 표준 라이브러리 대체 수단:

- `str.to-bytes()` — 문자열을 바이트 배열로 변환(수작업 `str-to-bytes` 대체)
- `[]byte.to-str()` — 바이트 배열을 문자열로 변환(수작업 `bytes-to-str` 대체)
- `[n]t.to-vec()` — 고정 길이 배열을 슬라이스로 변환(`[20]byte` → `[]byte`)
- `[]byte.to-hex()` / `[]byte.to-hex-lower()` — 바이트 배열을 16진수 문자열로 변환
- `str.to-i64()` / `str.to-f64()` — 문자열을 숫자로 파싱
- `int.to-str()` / `float.to-str()` — 숫자를 문자열로 변환
- `std/crypto/sha1`、`std/crypto/sha256`、`std/crypto/sha512` — 해시 계산

### TOML 설정 파일(`toml`)

표준 라이브러리 `toml`은 TOML 1.0 설정 파일의 파싱과 직렬화를 제공합니다. 파서에는 주석, bare/quoted/dotted keys, `[table]`, `[[array-of-tables]]`, basic/literal/multiline strings, 정수(10진/16진/8진/2진), 부동소수점, 불리언, 날짜 시간, 배열과 inline table을 지원합니다. 값은 TOML 원시 리터럴로 보관되므로 배열이나 날짜 시간 같은 정보가 손실되지 않습니다.

```no
cfg = toml.parse('title = "Nolang"\n[server]\nport = 8080\n[[server.backends]]\nname = "local"')

doc = toml.new()
doc.put('name', '"nolang"')
doc.put('server.port', '8080')
doc.put('enabled', 'true')
text = toml.stringify(doc)
```

자주 쓰이는 API:

- `toml.new()` — 빈 `toml` 생성
- `toml.parse(text)` — TOML을 파싱하여 `?toml` 반환
- `doc.put(key, raw-value)` — 원시 TOML 값 추가 또는 갱신; 잘못된 값은 거부하며 중복 키는 파서가 오류를 냄
- `toml.get(doc, key)` — 원시 값 가져오기(`?str`)
- `toml.get-str(doc, key)`、`toml.get-i64(doc, key)`、`toml.get-f64(doc, key)`、`toml.get-bool(doc, key)` — 변환된 스칼라 가져오기
- `toml.stringify(doc)` — TOML 출력; array-of-tables는 `[[...]]` 헤더로 출력됨

현재 문서 모델은 하나의 문서에 최대 4개의 key, 2개의 일반 테이블, 2개의 array-of-tables로 제한합니다. 단일 key는 최대 32바이트, 단일 value는 최대 128바이트이며, 이를 넘으면 설정 파일을 나누거나 호출 측에서 처리해야 합니다.

### YAML 문서(`yaml`)

표준 라이브러리 `yaml`은 YAML 1.2 core schema 문서를 파싱하고 생성하며, 블록 매핑, 블록 시퀀스, 흐름 컬렉션, 세 가지 인용 스칼라, 블록 스칼라 `|` / `>`, 주석, 여러 문서, 앵커와 별칭, 병합 키 `<<`, 명시적 키, 그리고 타입 추론(null / bool / int / float / `.inf` / `.nan`)을 지원합니다.

```no
doc ?yaml = yaml.parse('name: Alice\nserver:\n  port: 8080\ntags:\n  - a\n  - b\n')
doc: {
    nil -> print('nil')

    err -> print(it.msg())

    -> {
        doc = it
        name = doc.find-str('name'); ?str
        port = doc.find-i64('server.port'); ?i64
        name: {
            ok -> print(it)

            -> print('')
        }
        print(doc.to-json())
    }
}
```

자주 쓰이는 API：

- `yaml.parse(text)` / `yaml.parse-all(text)` — 파싱하여 `?yaml` 반환
- `yaml.valid-of(text)` / `yaml.error-of(text)` — 유효성 검사만 수행
- `it.find(path)` / `it.get(key)` — 하위 노드를 가져와 `?yaml` 반환
- `it.find-str(path)`, `find-i64`, `find-f64`, `find-bool` — 편의 값 가져오기, `?值` 반환
- `it.to-json()` / `it.to-yaml()` — 직렬화

> 참고: 하위 노드는 `?yaml`, 값 조회 도우미 함수는 `?值`를 반환하므로 match로 언패킹하세요(`child = it.find(path)`, 그 `ok` 갈래는 `it`로 하위 노드를 바인딩하고 기본 갈래가 빈 값을 처리하며, 각 갈래는 한 줄을 단독으로 차지합니다).

## 파일 명명 규칙

`.no` 파일명(폴더명 포함)은 단어를 하이픈 `-`으로 연결하며, **밑줄 `_`은 사용하지 않습니다**. 이는 변수명, 함수명, 구조체명 등 Nolang 식별자의 명명 스타일과 일치합니다.

컴파일러는 `run` / `build` / `test` / `vet` / `fmt` / `ast` 명령에서 이 규칙을 **강제 검사**하며, 경로의 일부(폴더명 또는 파일명 본문, `.no` 확장자는 제외)라도 규칙을 어기면 **즉시 오류가 발생합니다**:

- 허용 문자: 소문자 `a-z`, 숫자 `0-9`, 하이픈 `-`.
- 금지 문자: 밑줄 `_`, 대문자, 그 밖의 특수 기호.
- 하이픈은 구간의 처음이나 끝에 올 수 없으며, 연속해서 사용할 수도 없습니다(`--`).

예를 들어 `tmp/zz_stridx/r_index.no`는 `zz_stridx`와 `r_index`에 밑줄이 있어 거부되며, `tmp/zz-stridx/r-index.no`로 바꾸면 규칙에 맞습니다. 절대 OS 경로(예: `/Users/me/proj/a.no`)는 현재 작업 디렉터리 아래에 있는 부분만 검증하므로, 상위 디렉터리명(예: `Users`) 때문에 오류가 나지 않습니다.

```shell
✅ 推薦：
utils/
├── string-helper.no
├── hash-table.no
└── http-client.no
```

```shell
❌ 避免：
utils/
├── string_helper.no
├── hash_table.no
└── http_client.no
```

## 함수 정의

함수는 **명명된 결과 매개변수(named result parameters)**를 통해 결과를 출력할 수 있으며, 이는 본질적으로  
**출력 매개변수(out-parameter)의 문법 설탕**입니다. `return`(및 그 축약형 `***`, 현재는 사용을 권장하지 않음)은 조기 종료에만 쓰이며 결과를 따라갈 수 없습니다.

Nolang의 함수 정의 형태는 `name = (in-params) (out-params) { body }`입니다. 두 번째  
괄호 그룹 `(out-params)`은 명명된 결과 매개변수를 선언합니다(문법 설탕). 함수 본문에서 이들에 값을 할당하면  
(일반 입력 매개변수와 마찬가지로 참조 타입입니다). **결과를 실제로 받는 변수는 호출하는 쪽에서 정의해야 합니다.**  
정의 안의 결과 매개변수 이름은 자리표시자일 뿐이며, 호출 측의 LHS(또는 뒤따르는 인자)가 결과가 어느  
변수에 담길지 결정합니다:

```no
parse-line = (s str, max-fields ?i64) (fields []str) {
    ...; 函數體內對 fields 賦值
}

; 調用處定義接收變數（LHS 綁定，型別由簽名推斷）
fields = parse-line(line, nil)

; 多結果按順序綁定
a, b = swap(x, y)

; 或尾隨引數形式：res 作為額外的輸出引數傳入
add1(5, 3, res)
```

Nolang 함수는 다음과 같은 특징이 있습니다:

- **명명된 결과 매개변수는 문법 설탕입니다**: 내부적으로 여전히 입력 매개변수(out-parameter)로 처리되므로  
  새로운 반환값 객체를 만들지 않아 내부적으로 안전합니다.
- **입력 매개변수는 읽기 전용**: 스칼라는 값으로, 복합 타입은 읽기 전용 참조로 전달됩니다. 함수 본문에서 입력 매개변수와 그 하위 필드에 쓰는 것은 금지됩니다.
- **출력 매개변수는 쓰기 가능**: 호출측은 기존 변수를 출력 슬롯에 바인딩할 수 있고, 함수는 그 메모리를 직접 수정합니다. 바인딩하지 않으면 함수가 새 값을 만들어 전달합니다.
- 함수 안의 변수는 함수가 끝날 때 자동으로 소멸합니다.
- 호출측에는 결과를 받을 변수(LHS 또는 뒤따르는 인자)가 필요합니다. "함수에 반환값이 없다"는 말은 정확하지 않습니다.  
  정확히 말하면 결과는 명명된 결과 매개변수(out-parameter의 문법 설탕)로 전달되며 호출측에서 바인딩합니다.
- **별칭 규칙**: 읽기 전용 입력 참조와 출력 슬롯이 같은 객체를 가리키는 것을 허용합니다. 쓰기 연산이 출력 영역에서만 일어나고 입력을 읽기만 한다면 적법합니다. 컴파일러는 정적 별칭 검사를 하지 않습니다.

### 출력 슬롯을 기존 변수에 직접 바인딩하기(중개 변수 피하기)

호출측의 출력 슬롯은 **이미 존재하는 변수에 직접 바인딩**할 수 있으며, 함수는 그 메모리를 제자리에서 고칩니다(위의 "출력 매개변수는 쓰기 가능" 참조).
따라서 어떤 출력값이 기존 상태를 이어서 갱신하기만 한다면, 일회용 중개 변수를 거쳤다가 다시 쓰는 대신:

```no
; ✅ 推薦：餘數直接寫回 r（r 同時是方法的接收者）
qsq, r = r.div-mod(modulus)
```

```no
; ❌ 避免：msq 只被用一次，純粹是轉存
qsq, msq = r.div-mod(modulus)
r = msq
```

- **수신자가 출력 대상이 될 수도 있습니다**: `r.div-mod(modulus)`의 수신자 `r`는 읽기 전용 입력(암묵적 `self`)이고,
  `r`는 두 번째 출력 슬롯 `r bigint`에 바인딩됩니다. 〈별칭 규칙〉에 따라 입력은 읽기만, 출력은 쓰기만 하면 적법합니다.
  실측(`no build` / `no vet` / `no fmt`) 결과 `q, a = a.div-mod(bigint.from-i64(7))`은
  `a = bigint.from-i64(100)` 다음에 `q = 14`, `a = 2`가 되어 "먼저 `msq`를 받고 `r = msq`"와 완전히 동일합니다.
  `r`가 바깥 함수의 결과 매개변수여도 마찬가지입니다(`src/std/bigint.no`의 `mod-pow`가 바로 이 형태).
- **사용하지 않는 출력은 `_`로 버리기**: 몫을 전혀 쓰지 않는다면 `_, r = r.div-mod(modulus)`는 새 변수 하나조차 만들지 않는
  가장 간결한 표현입니다(뒤의 〈다중 할당〉의 `_` 자리표시자 참조).
- **단일 출력도 마찬가지**: `r = r._mul(r)`, `s = s.trim()`, `out = out.replace-str(...)`는 모두 stdlib에 있는 제자리 갱신입니다.
- **이미 올바른 코드를 이 때문에 고칠 필요는 없습니다**: 이는 새 코드를 작성할 때의 권장 표현일 뿐 리팩터링 명령이 아닙니다. 〈황금률: 올바른 코드를 수정하지 마세요〉를 따라,
  스타일 때문에 이미 정확한 코드를 건드리지 마세요.

### 매개변수 기본값

**지원하지 않습니다.** 매개변수 목록의 `name type = expr`(예: `foo = (a i64, b ?i64 = 10)`)은 **문법 오류**(`E_DEFAULT_PARAM`)입니다. 컴파일러는 기본 표현식을 파싱하지 않으며, 어떤 호출 지점에서도 기본값을 채우지 않습니다. 이는 "하나의 선언, 여러 가지 유효한 arity"라는 모호성을 없애고, 모든 호출 지점에서 기본 표현식을 반복적으로 낮추어 생기는 단형화 팽창도 피합니다.

옵션 의미가 필요하다면 매개변수를 option 타입 `?T`로 선언하고, 호출측에서 **명시적으로** `nil` / `ok(...)`를 전달한 뒤 함수 본문에서 `match`로 처리하세요:

```no
parse-line = (s str, max-fields ?i64) (fields []str) {
    limit = 1024
    max-fields: {
        ok(v) -> limit = v

        nil ->

        err ->
    }
    ...; limit 即上限
}

; 調用端必須顯式傳參
fields = csv.parse-line(line, nil); 回退 1024
fields = csv.parse-line(line, ok(256)); 上限 256
```

```no
add = (a i64, b i64) (result i64) {
    result = a + b; 通過參數返回結果
    ...; 佔位陳述：不做任何事，build 時整條丟棄（見〈佔位陳述〉）
}

; 可變參數
add3 = (a ..i64) {
}

; 函數調用
sum = add(1, 2); sum == 3

; 匿名函數 和for？ 有傳參？
(a i64) {
    print(a)
}(10)

; 函数调用
add(a, b)

; 也可能有多个返回值
a, b = swap(5, 3)
```

## 흐름 제어

> **지원 중단 문법(n 버전 이후 제거 예정)**: `for { }` / `for cond { }` / `for init, cond, update { }` / `for i in [..) { }` / `match x { }` / `if/elif/else { }`는 여전히 파싱되지만 deprecation warning이 출력됩니다. 아래 "**새 문법**"을 사용하세요.

### 새 문법과 옛 문법 대조

| 옛 문법 / 후위식(suffix)           | 전위식(prefix, format 기본값)                   |
| -------------------------- | --------------------------------------- |
| `{ } (true)` 무한 반복          | `!! { }` 또는 `true { }`                   |
| `{ } (cond)` 조건 반복          | `(cond) { }`(빈 `()`는 false로 보아 실행하지 않음)       |
| `{ } ()` 실행하지 않음               | `! { }` 또는 `false { }` 또는 `() { }`        |
| `{ } * n` 상수 횟수 반복             | `n * { }`(N ≤ 0이면 반복 본문을 실행하지 않음)                |
| `for i=0, i<n, i++ { }` 카운트 | `n * { }`(상수 횟수) 또는 `i <- [0..n): { }`(변수) |
| `for i <- [a..b] { }` 범위   | `i <- [a..b]: { }`                      |
| `for i in [a..b) { }` 범위   | `i <- [a..b): { }`                      |
| `match x { ... }` 매치       | `x: { ... }`                            |
| `if/elif/else { }` 분기      | `{ cond -> body }`(단락 평가, `{}`로 감싸야 함)      |
| `continue`                 | `*`(축약형, 현재 권장하지 않음)                        |
| `break`                    | `**`(축약형, 현재 권장하지 않음)                       |
| `return`                   | `***`(축약형, 현재 권장하지 않음)                      |

### Loop / While / for-in

> **두 가지 동일한 표현**: 같은 반복문에서 "전위식 `(cond) { }`"과 "후위식 `{ } (cond)`"을 모두 지원합니다.  
> 의미는 완전히 같으며, 조건과 본문의 순서만 다릅니다. `no fmt`는 기본적으로 **전위식**을 출력하며,  
> `no fmt -loop-style=suffix`로 후위식으로 되돌릴 수 있습니다(두 표현 모두 형식화 멱등성이 보장됨).

```no
#{fmt-skip}
; === 前置式（prefix，條件寫在主體前面）===

; 無限循環（條件恆為 true）—— 以下兩種等價
!! {
    ...
}
!! {
    ...
}

; 不執行（條件恆為 false）—— 以下三種等價
! {
    ...
}
! {
    ...
}
! {
    ...
}

; 條件循環（檢查 cond，為真時執行主體）
(x == 1) {
    do-something()
}

; 限定執行次數（前置式計數）
10 * {
    do-something()
}

; N ≤ 0 時循環體不執行（0 次或負數次均跳過）
0 * {
    print('不會執行')
}
-3 * {
    print('也不會執行')
}

; 可加標籤（label 寫在條件/計數之前）
#1 (x == 1) {
    do-something()
}

; === 後綴式（suffix，條件寫在主體後面，舊式）===
!! {
    ...
}

; 不執行（空括號代表 false）
! {
    ...
}

; 條件循環
(x == 1) {
    do-something()
}

; 限定執行次數
10 * {
}

; N ≤ 0 時循環體不執行（0 次或負數次均跳過）
0 * {
    print('不會執行')
}

-3 * {
    print('也不會執行')
}

; 區間語法（已支持 i64/u8 等數值類型、arr、vec、str）
; 共 16 種組合：'[' 包含左端點，'(' 不包含；']' 包含右端點，')' 不包含。
; 有界（4 種）：兩端都有值
i <- [a..b]: {
}
i <- (a..b]: {
}
i <- [a..b): {
}
i <- (a..b): {
}

; 無上限（4 種）：省略右端點，迭代至類型最大值
i <- [a..]: {
}
i <- [a..): {
}
i <- (a..]: {
}
i <- (a..): {
}

; 無下限（4 種）：省略左端點，從類型最小值開始迭代
i <- [..b]: {
}
i <- [..b): {
}
i <- (..b]: {
}
i <- (..b): {
}

; 完全無界（4 種）：兩端都省略，基於類型最小值/最大值
i <- [..]: {
}
i <- [..): {
}
i <- (..]: {
}
i <- (..): {
}
i <- [5..0]: {
}
i <- abc: {
}

; 运行时方向检测：当 start > end 时，迭代自动递减（步长 -1）。
; 四种括号组合均支持递减：
;   [5..1]  → 5 4 3 2 1   左闭右闭，递减
;   (5..1]  → 4 3 2 1     左开右闭，递减
;   [5..1)  → 5 4 3 2     左闭右开，递减
;   (5..1)  → 4 3 2       左开右开，递减
;   (3..0]  → 2 1 0       左开右闭，递减到 0
; 当 start <= end 时，按递增方向迭代（步长 +1）。
;
; 無界區間的端點由變量的靜態類型決定：
;   i64 的 [..]  從 i64.MIN (-9223372036854775808) 到 i64.MAX (9223372036854775807)
;   u8  的 [..]  從 0 到 255
;   i64 的 [..)  從 i64.MIN 到 i64.MAX - 1（不包含最大值）
;   i64 的 (..]  從 i64.MIN + 1 到 i64.MAX（不包含最小值）
;   i64 的 (..)  從 i64.MIN + 1 到 i64.MAX - 1（兩端都不包含）
; 規律：'[' 包含類型最小值，'(' 從最小值+1 開始；
;       ']' 包含類型最大值，')' 到最大值-1 結束。

; ❌ 明確拒絕
;   區間邊界必須是整數；不支持嵌套表達式
;   for i <- [1.5..5.5] { }   ; 編譯錯誤
;   for i <- [0..[1..5][0]] { } ; 語法錯誤

; ⚠️ 避免 ... 歧義
;   範圍運算子是 ..（兩點），self 方法調用是 .len()。
;   連寫時 [0.. .len()) → [0...len())，三個點看起來像單一運算子
;   （而 return 簡寫已定為 ***，暫不推薦使用；但三點連寫仍干擾辨讀）。
;   應使用 self.len() 代替 .len() 消歧：i <- [0..self.len()): { }
;   （方法體內 self 與 . 語義等價）

; 條件循環（新式：前置式 (cond) { }，`no fmt` 預設；取代舊式 for cond { }）
; 後綴式 { } (cond) 與之完全等價（舊式寫法）
; 大多數情況可改用 range-for：i <- [0..n): { }
(x == 1) {
    do-something()
}
```
```

### 빠져나가기 / 건너뛰기 / 조기 반환

> ⚠️ `*`(이번 회차 건너뛰기) / `**`(반복문 탈출) / `***`(반환 종료) 이 축약형은 **현재 사용을 권장하지 않습니다**. 다음과 같이
> 영어 키워드 `continue` / `break` / `return`을 사용하세요. `no fmt`는 지원되는 축약형을 모두 키워드 형태로 정규화합니다.

```no
i <- [0..10): {

    ; continue（跳過本輪，暫不推薦）
    continue

    ; break（跳出循環，暫不推薦）
    break

    ; return/terminate（提前返回，僅終止函數；規劃中，暫不推薦）
    break
    continue
}

; 推薦使用英文關鍵字（與 C/Rust 一致，便於移植、且能正常編譯執行）：
i <- [0..10): {

    ; 等價 *（暫不推薦）
    continue

    ; 等價 **（暫不推薦）
    break

    ; 等價 ***（暫不推薦），僅提前終止函數
    return
}

; 關鍵字別名（lexer 完整支援，與原關鍵字完全等價）：
;   ctn ≡ continue、brk ≡ break、rtn ≡ return；`no fmt` 保留別名原拼寫
i <- [0..10): {

    ; 等價 continue
    ctn

    ; 等價 break
    brk
}

; 等價 return，僅提前終止函數
rtn
```

> ⚠️ `return`(및 그 축약형 `***`, 축약형은 현재 권장하지 않음)은 **알몸으로만 사용할 수 있고 값을 붙일 수 없습니다.**  
> Nolang 함수에는 "반환값" 메커니즘이 없습니다. 결과는 모두 **명명된 결과 매개변수(out-param)**를 통해 함수 본문에서 값을 할당해 전달합니다("함수 정의" 참조).  
> 따라서 `return <값>`, `return(expr)`, `*** <값>`는 모두 **금지**되며, 컴파일러 / formatter / LSP 모두 오류를 냅니다：
>
> - 컴파일러(`no build`): `Error: compilation error: parser errors: line L, column C: 'return' 後不能跟返回值；… [E_GENERAL]`
> - `no vet`: `<file>:L:C: [ERROR] nolang-compile: 'return' 後不能跟返回值；… [E_GENERAL]`(다른 진단과 같은 형식이며, 한 줄에 하나씩)
> - `no fmt`: `format error: …`을 출력하고 0이 아닌 상태로 종료
> - LSP: 해당 줄에 빨간색 오류 진단을 표시
>
> 잘못된 사용:
>
> ```no
> has = (n i64) (r i64) {
>     n == 0 -> return 0        ; ❌ 編譯 / formatter / LSP 均報錯
>     r = n
> }
> ```
>
> 올바른 사용(먼저 결과 매개변수에 값을 할당한 뒤 알몸 `return`으로 조기 종료; 갈래 본문의 여러 문장은 각각 한 줄만 차지해야 함):
>
> ```no
> has = (n i64) (r i64) {
>     n == 0 -> {
>         r = 0
>         return
>     }
>     r = n
> }
> ```
>
> ⚠️ `n == 0 -> { r = 0; return }`처럼 한 줄로 압축하는 것은 축약형이 아닙니다. `; return }` 전체가 주석이므로
> 블록이 영원히 닫히지 않고, 이후의 모든 문장(대개 함수 본문 전체의 나머지)이 이 갈래로 조용히 빨려 들어갑니다.
> 실측상 `no vet`는 오류를 내지 않으며, 함수는 호출된 적이 없습니다.

## 채널(`chan[T]`)

채널은 **크기가 제한되어 있고, 증가 가능하며, 송신은 논블로킹, 수신은 대기**하는 값 큐이며, 수신측은 삼상태 `?T`로 값을 하나씩 가져갑니다.
문법 기호는 `<-` 하나만 유지합니다(그 밖의 용법은 "흐름 제어"의 `i <- range:` 순회 참조).

```no
ch chan[i64] = with-cap(8)   ; 顯式初始容量
buf chan[i64]                 ; 裸宣告：等價於 with-cap(0)，發送時按需增長

ch <- 1                       ; 發送（左側型別是 chan[T] 才算發送）
n = ch.len()                  ; 當前積壓數
c = ch.cap()                  ; 初始容量
ch.close()                    ; 關閉：不再接受發送，既有值仍可取
```

### 수신: 삼상태 반복문

`v <- ch: { ... }`는 **반복문**이며, 매 회차마다 삼상태 `?T`를 `v`에 바인딩합니다. `break`로 조기 종료할 수 있습니다.
`ok`는 값을 가져왔음을, `nil`은 채널이 닫히고 비었음을, `err`는 **진짜 오류**(초기화되지 않은
영값 핸들——기다릴 것이 없음)를 뜻합니다. **뒤의 두 가지는 반복문을 종료합니다**(같은 회차의 갈래는 평소대로 실행됩니다).

`ok` 말고 가장 중요한 점: **빈 읽기는 "값을 기다리는 것"이지 "값이 없는 것"이 아닙니다.** 채널은 열려 있지만 비어 있으면 읽는 쪽이
일시 중단되어 누군가 `send`하거나 `close`할 때까지 기다립니다:

- 코루틴에서는(`co`가 만든 `-async` 복제본) 정말로 park합니다. 상태 번호를 힙의 프레임에 기록하고, 작업을
  채널의 대기 연결 목록에 등록한 뒤 스케줄러로 반환합니다("코루틴" 절 참조);
- 일반 함수에서는 park할 수 없으므로 **블록**됩니다. 준비 큐를 계속 끌어 값을 가져올 수 있을 때까지 반복합니다.

따라서 "비움"은 `close()`로 반복문을 끝내야 합니다. 형태는 Go의 channel에 대한 `range`와 같습니다.

```no
ch chan[i64] = with-cap(2)
ch <- 10
ch.close()

<- ch: {
    ok -> print('got {it}')      ; it 是本輪的元素
    nil -> print('closed')       ; 取空後落到這裡
    err -> print('bad channel')  ; 只有零值句柄才會落到這裡
}
```

반복 변수를 버릴 때는 `<- ch: { ... }`처럼 씁니다. 본문의 첫 문장이 `v`에 대한 match가 아니면
`v`는 **요소 자체**(`?T`가 아닌 `T`)에 바로 바인딩되며, `ok`인 회차에만 본문이 실행됩니다:

```no
i <- ch: {
    print(i)                     ; i 是 i64，不是 ?i64
}
```

삼상태를 직접 구분하면서 반복 변수를 유지하고 싶다면 본문 시작에서 그것을 match하면 됩니다. 갈래만 쓰는 것(`v:` 생략)은
동의어 축약형입니다. 판단 근거는 **갈래 이름**에 있으며, `ok` / `nil` / `err` 세 이름이 모두 나타나야 삼상태로 인식됩니다:

```no
i <- ch: {
    ok -> print('got {it}')      ; it 是本輪元素，i 是本輪的 ?i64
    nil -> print('closed')
    err -> print('empty')
}
```

판단은 타입이 아니라 문법적입니다(아래 "형태 판정" 참조). `no fmt`는 위 축약형을
명시적 주어 `i: { ... }`로 보완합니다. 두 표현 모두 다시 파싱되며 형식화는 멱등입니다.

### 형태 판정

| 본문 시작 | 형태 | `v`의 타입 |
|---|---|---|
| `co bar(i)`, `print(i)` 등 일반 문장 | 요소 | `T` |
| `v: { ... }` | 삼상태 | `?T` |
| `ok -> ...` / `nil -> ...` / `err -> ...` | 삼상태(축약형) | `?T` |
| 그 밖의 일반 match(예: `i > 5 -> ...`) | 요소 | `T` |

판정은 **본문을 파싱하기 전에** 완료해야 합니다. 블록 시작이 match면 파서가 즉시 `if` 체인으로 디슈가링해
이후에는 원래 의미를 알아낼 수 없습니다. 이 칸 전체가 한때 완전히 고장난 적이 있습니다. `i <- ch:`가 항상 요소 형태로 취급되어
삼상태 갈래가 서로 무관한 독립 guard로 퇴화(매 회차 모두 실행)하고 `it`가 빈 값에 바인딩되었습니다.

### 의미

| 측면 | 규칙 |
|---|---|
| 용량 | `with-cap(n)`의 `n`은 **초기** 용량이며, 가득 차면 두 배로 늘어납니다. `send`는 **절대 블록하지 않고 값을 잃지도 않습니다** |
| 빈 읽기 | **대기**: 코루틴은 park, 일반 함수는 준비 큐를 블록 구동; `err`는 영값 핸들 같은 진짜 오류에만 남음 |
| 닫기 | `close()` 이후 `send`는 프로세스를 중단; 이미 큐에 든 값은 순서대로 가져올 수 있고 다 가져오면 `nil` 보고; 닫으면 모든 대기자를 동시에 깨움 |
| 페이로드 | 송신 시 **깊은 복사**(`str` / `%vec`는 clone 사용), 수신측은 독립적인 사본을 받음; 원본 변수가 바뀌거나 일찍 해제되는 걱정이 없음 |
| 동시성 | 채널 자체는 락을 쓰지 않음(단일 스레드 협력적 스케줄링): 대기자가 제어 블록의 `waiters` 연결 목록에 매달리고, `send` / `close`가 전체 목록을 떼어 하나씩 다시 큐에 넣음; **깨어난 것과 값을 얻은 것은 다르므로**, 복구 후 읽기 가능 여부를 다시 판정해야 하며, 그래서 코루틴의 복구 지점은 park 블록 자체임 |
| 교착 상태 | 준비 큐가 비었는데 대상 작업이 끝나지 않으면 ⇒ 더 이상 진행 불가: 런타임이 stderr에 `nolang: deadlock: …`를 출력하고 abort함. 아무도 보내지 않은 값이나 빈 회전을 돌려주지 않음 |

> 빈 읽기 일시 중단의 직접적 결과: **배수 반복문은 반드시 `close()`로 끝내야 합니다.** 초기 버전은 "열려 있지만 비어 있음"을
> `err`로 보고해 반복문이 자연스럽게 끝나도록 했고, 그래서 `for` 형태는 채널을 닫지 않아도 되었습니다. 지금은 그 경로가 대기이므로,
> `close()`를 잊은 프로그램은 마지막 회차에 멈춥니다(코루틴에서는 일시 중단, 일반 함수에서는 교착 판정).

### 제한

- **LLVM 백엔드에서만 구현되었습니다.** `no build --js` / `--wasm`은 채널 노드를 만나면 명확한 오류(`[chbkn001]`)를 내며,
  불완전한 코드를 조용히 생성하지 않습니다.
- 채널은 **값 타입**(한 머신 워드 크기의 핸들)으로 매개변수, 결과, 요소로 전달할 수 있습니다.
  `chan[chan[T]]`, `?chan[T]`도 선언할 수 있습니다(아직 `tests/chan.no`의 검증 범위에는 포함되지 않음).

## 자리표시 문장(`...`)

`...`는 언어의 **자리표시 문장**입니다. 문법적으로 유효하지만 의미적으로 **아무 일도 하지 않습니다**. 주로 문서 시연,
코드 뼈대, `TODO` 자리표시자에 쓰입니다. 컴파일 시 AST→HIR 단계에서 문장 전체가 버려지므로 산출물은 "그 줄을 쓴 적이 없던"
상태와 완전히 동일합니다(같은 소스에 `...`를 넣거나 빼서 컴파일한 바이너리의 `sha256`이 동일함을 실측).

```no
parse-line = (s str) (fields []str) {

    ; TODO: 這裡還要處理跳脫字元
    ...

    fields = csv.parse-line(s)
}

add = (a i64, b i64) (result i64) {
    result = a + b
    ...
}
```

규칙：

- **반드시 한 줄을 단독으로 차지**(줄 끝에 `;` 주석은 가능). `fail -> ...`, `x = ...`, `[0...n)` 같은 표현은
  모두 문법 오류입니다. `...`에는 값이 없으므로 표현식 위치나 문장의 다른 부분에 올 수 없습니다.
- `return`의 별칭도 **아니며**, **범위 연산자도 아닙니다**. 범위는 `..`(두 점)이고 조기 반환은 `return`으로 씁니다.
- `no fmt`는 그대로 유지하며 삭제하거나 옮기지 않습니다.

다음 표현은 모두 유효하지 않습니다:

```no
#{fmt-skip}
add = (a i64, b i64) (result i64) {
    result = a + b
    ...          ; ✅ 唯一合法形式：獨佔一行
}

ok -> ...        ; ❌ 語法錯誤：`...` 不能出現在表達式位置
x = ...          ; ❌ 語法錯誤：同上
i <- [0...n): {  ; ❌ 語法錯誤：`...` 不是範圍運算子，應寫 [0..self.n)
}
```

### Match

```no
; 簡單寫法，it 用於取參數
x: {
    err -> log(it.msg()); it 是結構化錯誤 err.err

    nil -> log('nil')

    -> do-right-thing(it)
}

; 析構寫法
x: {
    err(e) -> log(e.msg())

    nil -> log('nil')

    ok(v) -> do-right-thing(v)
}

; 註：struct 模式匹配（`user: { User{id=1} -> ... }`）與欄位綁定尚未支援，故不示範

score: {
    [0..59] -> print('不及格')

    [60..89] -> print('良好')

    [90..100] -> print('優秀')

    -> print('分數非法')
}

; 區間語法共 16 種組合，規律：'[' 表示包含左端點，'(' 表示不包含；
;                     ']' 表示包含右端點，')' 表示不包含。
;
; 【有界區間】（4 種）— 兩端都有具體值
;   [a..b]  → x >= a && x <= b   兩端都包含
;   [a..b)  → x >= a && x <  b   左包含右不包含
;   (a..b]  → x >  a && x <= b   左不包含右包含
;   (a..b)  → x >  a && x <  b   兩端都不包含
;
; 【無上限區間】（4 種）— 省略右端點（End=nil），僅檢查下界
;   [a..)   → x >= a              左包含，無上限
;   [a..]   → x >= a              左包含，無上限
;   (a..)   → x >  a              左不包含，無上限
;   (a..]   → x >  a              左不包含，無上限
;
; 【無下限區間】（4 種）— 省略左端點（Start=nil），僅檢查上界
;   [..b]   → x <= b              無下限，右包含
;   [..b)   → x <  b              無下限，右不包含
;   (..b]   → x <= b              無下限，右包含
;   (..b)   → x <  b              無下限，右不包含
;
; 【完全無界區間】（4 種）— 兩端都省略，基於類型最小值/最大值
;   [..]    → true                類型最小值 ≤ x ≤ 類型最大值（兩端都包含）
;   [..)    → true                類型最小值 ≤ x < 類型最大值
;   (..]    → true                類型最小值 < x ≤ 類型最大值
;   (..)    → true                類型最小值 < x < 類型最大值
;
; 在 match 中，完全無界區間基於被匹配變量的類型值域（必然為真，等同 catch-all）。
; 在 range-for 中，基於迭代變量的類型範圍（如 i64 的 [..] 從 i64.MIN 到 i64.MAX）。
;
; 範例：使用無界區間做完整分類
v = 85
result = v: {
    [..0) -> 'negative'

    [0..60) -> 'fail'

    [60..80) -> 'pass'

    [80..90) -> 'good'

    [90..100] -> 'excellent'

    (100..) -> 'extraordinary'
}
print(result)

num: {
    1 || 3 || 5 || 7 -> print('奇數小數')

    2 || 4 || 6 -> print('偶數小數')

    -> print('更大數字')
}

; 有返回值，最後一個語句/值
result = x: {
    1 -> 1

    2 -> 2 + 1

    -> a + b
}

; 多行 arm body 必須使用大括號 -> { ... }
x: {
    nil -> {
        log('nil')
        do-cleanup()
        return
    }

    err -> {
        log(it.msg())
        do-cleanup()
        return
    }

    ok -> print(it)
}
```

> **여러 줄 arm body 규칙**: arm body에 문장이 여러 개라면 중괄호 `-> { ... }`로 감싸야 합니다. 한 줄 body는 `->` 뒤에 바로 쓸 수 있습니다. 여러 줄 body를 중괄호로 감싸지 않으면 option match의 `it` 바인딩을 올바르게 삽입할 수 없어 컴파일 오류가 발생하기 때문입니다.

> **for-in 본문 안의 match 의미**: `i <- (a..b]: { 1 -> ... 2 -> ... }`는 반복 변수 `i`마다 match 본문을 한 번씩 실행합니다(`1 ->`은 `i == 1 ->`과 같으며 이하 마찬가지). 매 반복마다 match를 한 번 실행하는 문법 설탕(syntax sugar)입니다.

#### Match 주어의 세 가지 형태

match 주어는 **값**, **표현식**, 또는 **블록**일 수 있습니다:

| 형태 | 작성법 | 평가 방식 |
| --- | --- | --- |
| 값 | `x: { ... }` | `x`를 직접 매치 |
| 표현식 | `x + 1: { ... }` | 표현식의 값을 먼저 계산한 뒤 매치 |
| 블록 | `{ ... }: { ... }` | 문장 본체를 실행하고 그동안의 `?=` 결과를 매치 |

앞의 두 형태는 **표현식**입니다: 문장으로도 쓸 수 있고, 값 맥락에서 값을 취할 수도 있습니다(`v = x: { ok -> it, -> 0 }`).
세 번째 형태는 **문장일 뿐**입니다—표현식이 아니며, 할당할 수 없고, 블록 끝 값도 없으며, `-> _`로 결과를 버립니다.
`no fmt`는 `}: {`를 원래 그대로 왕복하며, arm 사이 빈 줄 규칙은 일반 match와 같습니다.

##### 표현식 주어 (`expr: { ... }`)

`expr: { ... }`에서 `: {`의 우선순위는 `=`보다 **높습니다**: 할당 오른쪽에서는 전체 RHS가 되며,
" `r = <expr>`을 먼저 끝내고 뒤에 독립적인 match가 따라오는" 것이 아닙니다. 따라서 option 산술을 한 단계로 언패킹할 수 있습니다:

```no
#{overflow=wrap}
rem = seconds % 3600: {
    ok -> it

    -> 0
}

#{overflow=wrap}
sec = rem % 60: {
    ok -> it

    -> 0
}
```

이전에 반드시 나눠 써야 했던 세 단계 표기 `rem-opt = seconds % 3600` / `rem = 0` /
`rem = rem-opt: { ok -> it  -> 0 }`와 동등합니다. 첫 할당에는 명시적 타입을 붙일 수 있고
(`rem i64 = seconds % 3600: { ... }`), 두 번째 할당은 `rem = ...: { ... }`를 바로 씁니다.
둘 다 단일 값 위치 match이며, 결과 타입은 arm 끝 표현식이 결정합니다.

의미 및 제약:

- 주어가 D6 option 산술(`+ - * / %`)이면 결과는 `?T`입니다. match는 이를
  `__match_subj_L_C ?T` 합성 임시 변수로 정규화합니다: 주어는 **정확히 한 번만 평가**되고, `ok -> it`는 payload에 바인딩되며,
  조건은 option tag 비교로 처리되고 `-> 0`은 `nil` / `err`를 폴백합니다. 합성 이름은 진단이나
  `no fmt` 출력에 나타나지 않습니다.
- match의 결과는 **plain T**이며 의미 보조 테이블에 등록됩니다. 따라서 이어서 다음과 같이 쓸 수 있습니다.
  `sec = rem % 60: { ... }`처럼 연속으로 여러 단계의 값 위치 match를 써도 payload가 손실되지 않습니다.
- 값 위치 match는 **값 맥락**에서만 부착되며(할당 / `?=` / 복합 할당의 오른쪽), `: { ... }`는
  반드시 실제 match 블록이어야 합니다. `cond: { body }` 같은 문장 수준의 조건 반복문과 struct 리터럴은
  기존 파싱 경로를 그대로 따르며 영향을 받지 않습니다.
- **필드 대상 할당도 값 맥락입니다**(2026-11-09부터): `d.month = mp - 9: { ... }`,
  `b.n ?= b.n + 1: { ... }`에서 `: {`는 전체 할당이 아니라 **우변값**에 결합됩니다. 이전에는 이 두
  분기가 우변값을 파싱할 때 `CTX_EXPR`을 추론하지 못했습니다(식별자 대상은 `let`으로 추론했지만, `obj.f =` / `a[i] =`는
  추론하지 못함). 그 결과 `: {`를 문장 수준이 가져가 전체 할당 바깥에 씌워
  `match(주어 = (d.month = mp - 9))`로 파싱되었습니다. 할당은 평소처럼 실행되어 `?T`를 암시적으로 언패킹한 뒤 필드에 기록하고,
  `ok -> it` / `-> 0` 두 arm은 사실상 죽은 코드가 되었습니다. 이제 arm 값이 비로소 필드에 제대로 반영됩니다.
- 인덱스 대상(`a[i] = …: { ... }`)의 형태도 같지만, D9에서 원래 첨자 직접 쓰기를 금지하므로 이런 표기도
  checker가 `idxwrite`로 거부합니다. place-match(`a[i]: { ok -> it = v }`)로 바꾸거나
  `?=`를 사용해야 합니다.
- `no fmt`는 `expr: { ... }`를 원래 그대로 왕복시키며, 할당 + 독립 match 두 문장으로 분리하지 않습니다.
- **타입 가시성 경계**: option 산술 주어를 `?T`로 정규화하려면 두 피연산자의 선언 타입이
  parser가 정적으로 볼 수 있어야 합니다. 피연산자가 깊은 메서드 체인에서 왔다면(수신자 타입을 AST 리플레이로도 추론할 수 없다면),
  선언에 명시적 타입을 추가하세요. 예: `e i64 = flr.to-i64()`. 그렇지 않으면 정규화가 보수적으로
  건너뛰어 `ok -> it`에 바인딩이 없고 MIR이 0으로 채워져 관측값이 항상 0이 됩니다. `src/std/number.no`의
  `f64.to-str-general`이 바로 그렇습니다. 이 표기가 없으면 `fmt.fmt-f64(2.5, '')`가
  `'2.5'`에서 `'3'`으로 퇴화합니다. 회귀 테스트는
  `src/parser/value_match_expr_subject_test.go::TestValueMatchExprSubjectASTAnnotatedOperand`에 고정되어 있습니다
  (표기를 제거하면 바로 실패합니다).

`src/std`는 2026-11-09에 **122곳 / 22개 모듈**의 option 언패킹을 이 한 단계 표기로 변경했습니다:
처음의 세 단계 표기(`x-opt = expr` / `x = 0` / `x = x-opt: { ... }`) 외에도 두 단계 표기와
(영값 초기화 없음), 명시적 타입 첫 할당(`x i64 = expr: { ... }`), 그리고 중간 변수가 같은 함수 안에서
여러 번 짝지어 선언되는 표기도 포함합니다. 접은 뒤 주어는 메서드 호출, 인덱스, 또는 option 산술일 수 있고,
`ok -> it` / `ok(v) -> v` / 상수 arm / `-> _`는 모두 실측상 동등하며, `no fmt`는 이 지점들에 대해 멱등합니다.
컴파일러의 타입 추론은 "의미 보조 테이블에서는 `?T`로 보이지만 선언은 실제로 `i64`"인 이런 전역 동명 잔류값도 함께 처리하여,
`ok -> it`가 바인딩을 잃지 않도록 합니다.

유지된 경우(9곳): ① 내부 match가 `-opt` 변수 자체에 다시 기록합니다(그 변수는 이후 값 위치 match의
주어입니다); ② 두 겹으로 연결된 option match; ③ 값에 따라 분기하는 값 위치 match(예: errno → 메시지, option
언패킹이 아님); ④ 선언과 match 사이에 다른 문장이 있거나, 중간 변수가 분기를 넘나들며 누적한 결과인 경우
(접으면 평가 시점이 바뀝니다).

##### 블록 주어 (`}: {`)

블록 주어는 문장 시퀀스를 감싸서, **`?T` 결과 매개변수가 없는 함수**도 `?=`의 상위 전파를 즉석에서 처리할 수 있게 합니다:

```no
; d i64: 除數，0 時 6/d 得 err
f = (d i64) {
    {
        v ?= 6 / d; 失敗不再要求函式有 ?T 結果參數
        print(v.to-str()); 失敗時不會執行
    }: {
        err -> print(it.msg())

        nil -> print('nil')

        -> _; 丟棄結果
    }
    print('之後照常執行'); arms 跑完後流程繼續
}
```

의미:

- 본문 안의 `?=`는 **가장 가까운** 블록 match가 잡습니다(중첩 시 가장 안쪽 우선; 함수에
  `?T` 결과 매개변수가 있어도 블록 match가 우선). 포착은 재귀적입니다: 벌거벗은 블록, if 본문, 반복문 본문,
  match arm 안의 `?=`도 모두 해당합니다. 함수 정의는 경계이지만 함수 리터럴은 경계가 아닙니다.
- 매치 대상은 3상태 `?T`이며, 표준 option match의 **완전성 검사**를 그대로 따릅니다: 폴백 arm이 없으면,
  `ok ->`가 런타임에 도달 불가능하더라도 `nil` / `err` / `ok` 세 arm을 모두 채워야 합니다.
- 본문이 정상적으로 끝나면(`?=`가 없거나 모두 성공) ⇒ `nil`에 매치됩니다. 어떤 `?=`가 실패하면 ⇒ 그때의
  `nil` 또는 `err`에 매치됩니다(`err` arm의 `it`는 완전한 `err.err`입니다. 〈`it`의 타입〉 참조).
- **한 번 실패하면 본문 전체가 멈춥니다**: 이후 문장과 이후 루프 반복은 모두 실행되지 않고, arm은 한 번만 실행됩니다.
  이는 "블록 정지"이며 함수의 `return`이 아닙니다. 사용자가 직접 쓴 `return` / `break` / `continue`는
  바인딩에 영향을 주지 않습니다.
- 전개는 기존 핵심 AST로만 이루어집니다(합성 `?T` 지역 변수 + `if` 가드 체인 + 일반 match).
  새로운 HIR / MIR 노드는 없습니다. 합성 변수 이름은 진단이나 `no fmt` 출력에 나타나지 않습니다.

> `=`의 즉석 포착과의 역할 분담: `=`는 실패를 **대상 변수에 저장**하고 흐름을 계속합니다. `}: {`는 실패를
> **하나의 match로 수렴**시키고 본문의 나머지를 정지합니다. "실패 후에도 계속"이 필요하면 `=` +
> 이후 match를 사용하고, "실패하면 곧바로 정리 arm으로"가 필요하면 `}: {`를 사용하세요.

##### 블록 match와 값 위치 match의 선택

같은 일, 즉 option 산술의 결과를 plain 변수로 가져오는 데에는 두 가지 표기가 있습니다. **블록 본문에 이 문장 하나뿐이면
둘은 동등합니다. 그러나 본문에 다른 문장이 더 있거나 우변값이 다른 곳에서 실패할 수 있으면 의미가 갈라집니다.**

```no
; A：塊 match + `?=`（區塊級「try」）
{
    #{overflow=wrap}
    np ?= np + 1
}: {
    err -> _

    -> _
}

; B：值位 match 直接綁目標（陳述級）
#{overflow=wrap}
np = np + 1: {
    ok -> it

    -> _
}
```

`#{overflow=wrap}`에서 `np + 1`의 결과는 **항상 `ok`(감싼 값)**이며, 둘 다 검사 없는
 `add i64` 한 줄만 생성하고 오버플로 검사 분기가 없습니다. 실패 arm은 "덧셈 자체"에 대해 죽은 코드입니다. 이것이 대부분 지점에서
"완전히 동등"해 보이는 이유입니다. 진짜 차이는 **작용 범위**와 **실패 경로**에 있습니다:

| 기준 | A: 블록 match + `?=` | B: 값 위치 match |
| --- | --- | --- |
| 문법 위치 | **문장**: 끝 값 없음, 할당 불가 | **표현식**: 할당 오른쪽, 필드 대상, `?=` 오른쪽에 위치 가능 |
| 실패 시 대상에 기록되는 값 | **영값**(`i64` → `0`, `str` → `''`) | 폴백 arm이 결정: `-> _`는 **기록하지 않음**(원래 값 유지), `-> 0`은 0 기록, `-> sum`은 이전 값을 다시 기록 |
| 본문의 나머지 문장 | **모두 건너뜀**(이후 루프 반복 포함) | 평소처럼 실행 |
| 하나의 `err` arm이 다루는 범위 | 블록 안의 **모든** `?=` | 이 문장 하나뿐 |
| 대상에 타입 선언이 있을 때 | ❌ `q i64 ?= …`는 파싱 오류(`yh8904fm`) | ✅ `q i64 = …: { … }` |
| 우변값이 상수 폴딩일 때 | ❌ `s8gh6opt`(`4 / 2`가 plain으로 접혀 더 이상 option이 아님) | ✅ 주어는 여전히 `?T`로 정규화됨 |
| 사용 가능한 전제 | 함수에 `?T` 결과 매개변수가 있거나 자체가 블록 match 안에 있음(그렇지 않으면 `l86f91me`) | 없음 |
| 성공 시 arm | 역시 arm에 한 번 들어감(본문이 끝나 `nil`에 매치), arm에는 버리기나 순수 처리만 두어야 함 | `ok` arm만 실행됨 |

선택 순서:

1. **문장이 하나이고, 실패하면 0으로 처리하며, 뒤에 실행할 것이 없는 경우** → 둘은 동등하며 B를 우선: 들여쓰기 한 단계와
   store 한 번이 줄고, `no fmt`는 두 형태 모두 멱등하게 왕복합니다.
2. **연속된 fallible 문장이 하나의 오류 처리를 공유해야 할 때**(파일 읽기 → 파싱 → 다시 쓰기) → A: `?=`를 한 줄에 하나씩 쓰고,
   같은 `err ->` arm을 공유하며, 첫 실패에서 정리 arm에 멈춥니다.
3. **실패 시 원래 값을 유지 / 구체적인 폴백 값으로 교체 / 이후 문장을 평소처럼 실행해야 할 때** → B(`-> sum`, `-> 0`, `-> it`).
4. **그 값이 이어서 연산에 참여해야 할 때**(할당 오른쪽, 필드 대상, `?=` 오른쪽) → B: A는 문장이라 값이 없습니다.
5. **요소별로 처리하며 한 건의 실패가 전체를 망치면 안 될 때** → B; **전체가 함께 실패하면 중단** → A(루프 반복까지 멈춥니다).

쉽게 빠질 수 있는 두 가지:

- 🔴 **애노테이션 위치**: `#{overflow=wrap}`는 **블록 안**에, `?=` 줄 바로 위에 써야 합니다. 블록
  match 바깥(`{` 위)에 쓰면 **효과가 없습니다**. 실측상 오버플로는 그대로 `err`를 반환하고 `np`가 `?=`에 의해 0으로 초기화됩니다.
- 🔴 **누산기는 A를 그대로 따라 하지 마세요**: `sum ?= 1 / (i - 1)`은 실패한 그 회차에 **누적된 `sum`까지 함께 `0`으로 지워버립니다**
  (`?=`의 영값 기록). 누적값을 유지하려면 B의 `-> sum`을 사용하세요.

#### Match 스타일 지침

```no
#{fmt-skip}
; ❌ 避免重複分支體
w = tls-c.send(req)
w: {
    nil -> {
        tls-c.close()
        return
    }

    err -> {
        tls-c.close()
        return
    }

    ok -> n = it
}
```
```

```no
; ✅ 公共邏輯放 -> catch-all
w = tls-c.send(req)
w: {
    ok -> n = it

    -> {
        tls-c.close()
        return
    }
}

; ✅ 反之亦然：簡單分支命名，複雜邏輯放 ->
val: {
    nil -> return

    err -> log(it.msg())

    -> {
        n = it
        total = total + n
        process(n)
    }
}
```

```no
; 單語句 — 不加大括號
val: {
    ok -> print(it)

    -> print('empty or error')
}

; 多語句 — 必須加大括號
val: {
    ok -> {
        n = it
        total = total + n
    }

    -> {
        log('failed')
        return
    }
}
```

```no
; it 隱式綁定
val: {
    ok -> process(it); it = 解包後的值

    err -> log(it.msg()); it = 結構化錯誤 err.err（非 str）

    -> log('empty'); catch-all，此處為 nil
}
```

```no
#{fmt-skip}
; it 的作用域：巢狀 match 按層還原
; （佔位函數名寫 keep —— `use` 是導入關鍵字，不能當函數名；
;   且裸 `->` 臂在 nil/err 未同時認領時讀 it 是編譯錯誤，故各層都寫 ok ->）
outer: {
    ok -> {
        keep(it)            ; 外層 it
        inner ?T = f(it)
        inner: {
            ok -> keep(it)  ; 內層 it = inner 的解包值
        }
        keep(it)            ; ✅ 內層臂結束後 it 已還原成外層值
    }
}
```

> **주의**: 복원은 **중첩된** match에서만 일어납니다. 가장 바깥쪽 match가 끝난 뒤에도 `it`는 마지막 arm의 값을 그대로 유지하므로,  
> match 바깥에서 `it`를 사용하지 마세요. 여러 겹에 걸쳐 써야 한다면 이름 있는 변수에 저장(`doc = it`)하거나 구조 분해 바인딩  
> `ok(v) -> ...`로 payload를 자신의 이름에 바인딩하세요.

> **모범 사례(option 언패킹은 `it` 우선)**: 매치 대상이 **option `?t`**라면 `ok(v) -> ...(v)...`보다 `ok -> ...(it)...`를 우선하세요.  
> 추가 바인딩 이름을 만들지 않으므로 "서로 다른 arm에서 같은 이름의 변수가 codegen 타입을 섞는" 함정을 자연스럽게 피할 수 있습니다.  
> **이름 있는 바인딩** `ok(v) ->`를 반드시 유지해야 하는 경우는 두 가지뿐입니다: (1) 매치 대상이 **사용자 정의 열거형 변형**일 때(예:  
> `res { ok(v str) }`, `shape { rect(w, h) }`). 이때 `it`는 payload가 아니라 **열거형 전체**이므로 payload를 얻으려면 이름을 붙여야 합니다;  
> (2) **중첩 match 이후**에도 그 값을 계속 써야 할 때—내부 match가 `it`를 다시 바인딩하므로 이름 있는 바인딩을 쓰거나 미리 이름 있는 지역 변수에 복사하세요.

### 첨자 쓰기에는 명시적 언패킹이 필요합니다

인덱스 읽기의 반환값은 option입니다(범위를 벗어나면 `err`, `code.index-out`). **첨자에 직접 할당하면 범위 초과가 검사되지 않는 out-of-bounds 쓰기로 바뀌므로** 허용되지 않으며, 다음 두 가지 중 하나를 골라야 합니다:

```no
#{fmt-skip}
; ❌ 不允許：a[1] = 2
```
```

```no
; ✅ place-match：自行處理越界臂（it = 元素位置，可讀可寫）
a[1]: {
    ok -> it = 2

    -> _
}

; ✅ 錯誤上拋：所在函式有 option 結果參數時（越界 → 上拋）
a[1] ?= 2
```

- 컴파일러가 첨자의 범위 초과가 없음을 증명할 수 있으면(고정 길이 배열 + 상수 첨자, 반복 변수의 범위 내 증명 등) **내부적으로 검사를 제거하고 직접 할당하여 런타임 오버헤드가 없습니다**. 그러나 문법상 여전히 언패킹 형태로 써야 하며, 사용자 측에는 어떤 예외도 없습니다.
- map(`[str]i64` 등)은 **이 규칙의 적용을 전혀 받지 않습니다**: `m['b'] = c`를 그대로 쓰면 되고 place-match도 `?=`도 필요 없습니다. map의 첨자는 위치가 아니라 **키**이며, 쓰기는 put/insert(키가 없으면 삽입, 있으면 덮어쓰기)라 항상 정의되어 "범위 초과 쓰기"가 존재하지 않습니다. 구조체 필드 기반(`self.keys[i] = v`)은 현재 이 규칙의 적용을 받지 않습니다.
- map의 **읽기** 측은 여전히 option 규칙을 따릅니다(배열/vec/slice의 `a[i]`와 완전히 동일한 규칙). 함수 안에서 `x = m[k]`는 `?V`를 얻고, 키가 없으면 `nil`입니다. `m[k]`는 `m.get(k)`와, `m[k] = v`는 `m.put(k, v)`와 동의어이며 두 표기를 자유롭게 섞어 쓸 수 있습니다.
- `m[k] ?= v`는 **컴파일 오류**입니다(단순히 불필요한 것이 아님). `?=`의 ok arm은 "요소를 읽어 **위치**에 다시 쓰는" 동작인데, map이 읽은 `?V`는 `get`의 사본일 뿐이라 그것을 다시 써도 map으로 돌아가지 않습니다. `m[k] = v`를 바로 쓰세요. `m[k]: { ok -> it = v }` 같은 place-match 표기는 여전히 사용할 수 있습니다(put과 동등).

### 반복 변수도 요소의 "위치"입니다

`x <- a`(`a`가 `arr` / `vec` / `slice` / 고정 길이 배열)가 바인딩하는 `x`는 매 회차 불러온 사본이 아니라 **요소 자체의 위치**입니다:

- `x`를 **읽으면** `a[__i]`를 다시 읽습니다—같은 회차에서 먼저 쓰고 읽으면 새 값을 볼 수 있으며, `x = x + 1`이 바로 읽기-수정-쓰기입니다;
- `x = v`에 **쓰면** `a[__i]`로 반영됩니다;
- match arm 안의 `it`는 같은 위치의 **별칭**이며(그 arm 안에서만 유효), 따라서 `x: { ok -> it = v }`와 `a[i]: { ok -> it = v }`는 완전히 동등합니다.

```no
; 以下兩段結果相同：a 的每個元素都變成 5
a []i64 = [0, 0, 0]
i <- [0..3): {
    a[i]: {
        ok -> it = 5

        -> _
    }
}

b []i64 = [0, 0, 0]
x <- b: {
    x: {
        ok -> it = 5

        -> _
    }
}
```

- 요소 자체가 option(`[]?T`)일 때 `it`는 **payload**이며, 다시 쓸 때 자동으로 `ok`로 감싸집니다.
- arm이 끝나면 별칭이 무효해집니다. match 뒤에 `it = v`를 써도 컨테이너로 돌아가지 않습니다.

**위치가 아닌 경우**(쓰기가 지역에만 남음):

- `c <- s`(`str`): 요소는 디코딩된 **코드 포인트**이며, 문자열에는 대응하는 저장 칸이 없습니다.
- `k <- m`(map): 첨자는 위치가 아니라 **키**이므로 쓰기가 테이블로 반영되지 않습니다.

### `it`는 "단일 경우임을 증명할 수 있는" arm에서만 사용할 수 있습니다

catch-all `->` arm은 앞의 명시적 arm이 가져가지 않은 모든 경우를 받습니다. 남은 경우가 **정확히 하나일 때만**
 `it`가 단일하고 명확한 의미를 가집니다:

```no
; ✅ -> 就是 ok（nil / err 都已被認領）
v: {
    nil -> log('empty')

    err -> log(it.msg())

    -> process(it)
}

; ✅ -> 就是 err（ok / nil 都已被認領）
v: {
    ok -> process(it)

    nil -> log('empty')

    -> log(it.msg())
}
```

```no
#{fmt-skip}
; ❌ -> 可能是 nil 也可能是 err —— 編譯錯誤
v: {
    ok -> process(it)

    -> log(it)
}
```
```

 `nil ->` / `err ->`를 보충하거나 `ok ->`를 쓰면 통과합니다. enum과 벌거벗은 match(`{ cond -> ... }`)는  
이 예외에 해당하지 않습니다: `it`는 매치된 값 자체를 가리키며 nil / err일 가능성이 없습니다.

> `err ->` arm의 `it`는 **항상 오류 값(`err.err`)**이며 option의 요소 타입과 무관합니다—  
> `option { ok(v t), nil, err(e err.err) }`. 따라서 `?i64` / `?bool`처럼  
> 스칼라 option을 매치하더라도 `err ->` arm의 `it`는 구조화된 오류입니다: 메시지는 `msg = it.msg()`로 읽고,  
> 오류 코드는 `it.is(code.io)`로 비교하며, 발생 위치는 `it.file` / `it.line` / `it.col`에 있습니다  
> (컴파일러가 `err(...)` 생성 지점에 자동으로 주입합니다).

```no
; ✅ 組合 option 模式：nil || err -> body
; 當 option 為 nil 或 err 時共用同一個分支
val: {
    nil || err -> {
        cleanup()
        return
    }

    ok -> process(it)
}

; ✅ 也可與 -> catch-all 混用
val: {
    nil || err -> log('failed')

    ok -> process(it)
}
```

### 단락 파이프라인 (`->`)

`->`는 **좌결합 단락 파이프라인 연산자**로 의미가 고정되어 있으며, **바깥에서 할당하는지, match arm 안인지에 영향을 받지 않습니다**. 벌거벗은 문장, match arm의 한 줄 body, 할당 오른쪽 세 곳이 동일한 lowering을 공유합니다.

파이프라인 안의 노드는 세 종류로 나뉩니다:

| 노드                                | 파이프라인 state에 미치는 영향                             |
| --------------------------------- | ----------------------------------------- |
| 부수 효과 호출(반환값 없음, 예: `print('A')`)         | 실행되며 **state를 바꾸지 않음**; 이전이 Ok였다면 다음 노드로 계속        |
| `?T`를 반환하는 호출(실패 가능, 예: `might-fail()`) | 실행되며 **state를 덮어씀**; nil/err가 되면 **이후 노드 전부 건너뜀** |
| 맨 끝의 일반 값 표현식                          | state가 여전히 Ok일 때만 평가                        |

**`?T`를 반환하는 노드만 파이프라인을 실패로 전환할 수 있습니다**. `print` 같은 부수 효과는 결코 그렇지 않습니다. 따라서 "전체 체인이 `print`"라면 단락이 없는 것처럼 보이지만, 실제로는 실패를 만들 노드가 없을 뿐입니다.

```no
; 沒有可失敗節點 → 全部執行
ok -> print('A') -> print('B')

; might-fail() 回傳 ?T → 失敗時 print('B') 不執行
ok -> print('A') -> might-fail(x) -> print('B')

; 賦值右側：同一套語義
r = print('E') -> might-fail(x) -> 42
```

**경계 명확화:**

1. `->`의 의미는 하나뿐이며, 벌거벗은 문장과 할당 표현식이 같은 파이프라인 lowering을 공유합니다. 바깥에 할당이 있는지에 따라 모드가 바뀌지 않습니다.
2. match arm의 **한 줄 body 안에서 `->`는 파이프라인 연속이며 새 arm이 아닙니다**. arm과 arm은 **줄바꿈**으로 구분됩니다:

```no
; ✅ 一個臂，body 是管道 → 兩行都印
ok -> print('A') -> print('B')

; ✅ 兩個臂（換行分隔）→ 命中 ok 就不會印 'miss'
v: {
    ok -> print('hit')

    -> print('miss')
}
```

> ⚠️ arm은 줄바꿈으로 구분되므로, 같은 줄에 쓴 `pat -> A -> B`는 **한 arm의 파이프라인**이지 "if A else B"가 아닙니다. if/else가 필요하면 arm을 여러 줄로 쓰거나 `{}`로 감싼 단락 그룹을 사용하세요.

1. **파이프라인은 값을 만들 수 있습니다**: 할당 오른쪽에 쓰면 파이프라인의 결과는 **맨 끝의 값 노드**입니다(state가 여전히 Ok일 때만 평가).

```no
n = 7
x = 1 > 2 -> 42; 條件不成立 → x 保持原值 7
y = 2 > 1 -> 42; y == 42
s str = 'old'
s = 1 > 2 -> 'new'; 短路 → s 仍是 'old'
r = print('E') -> might-fail(bad) -> 99; 中段失敗 → r 保持原值
```

실패(조건이 성립하지 않거나 `?T` 노드에 의해 단락됨) 시 **할당이 적용되지 않습니다**: 변수는 원래 값을 유지하며, 처음 선언이라면 해당 타입의 영값이 됩니다. 이는 문장 형태와도 같습니다—`{ 1 > 2 -> x = 42 }` 역시 `x`를 바꾸지 않습니다.

값의 타입은 arm의 마지막 표현식으로 추론되며(`str` / `i64` / `?T` 모두 가능), 기존의 match 값 취득 형태인 `x = subject: { arms }`와 같은 추론 규칙을 공유합니다.

### If / Else

if-else 그룹(단락)은 **반드시** `{}`로 감싸야 합니다. 첫 번째로 맞는 조건이 이기고 이후 조건은 검사하지 않습니다.

```no
; 多分支（推薦新式）— 短路 if-else 鏈
{
    a == 1 -> {
        a = 1
        b = 2
    }

    a == 2 || a == 3 -> do-something()

    -> {
        c = 0
    }
}

; 單 if（保留）— 獨立 if，不短路
x == 1 -> do-something()

; 三元表達式 condition ? true-value : false-value
c = flag ? 1 : 2
max = sum > 10 ? sum : 10
```

**중요 규칙:**

1. **단락 그룹** — 여러 `cond -> body`를 `{}`로 감싸면 if-elif-else 체인을 이루며 첫 번째로 맞는 분기만 실행됩니다.
2. **독립 if** — 함수 본문/반복문 본문에 `cond -> body`를 직접 쓰면(`{}`로 감싸지 않음) 독립 if이며, 이웃하는 if-then과 단락되지 않습니다.
   **else가 등장하는 순간 반드시 그룹을 만들어야 합니다** — 줄바꿈된 `->` 폴백 arm을 `{}` 바깥에 쓰면 **컴파일 오류**입니다: 독립된 `cond ->`에 `->`를 붙이면 `k3r7mbqd`, 그 위에 형제 `cond ->` arm이 있으면 `m7vq3xrt`가 발생합니다(메시지에 버려진 arm 수가 표시됨). 파서는 줄바꿈된 `->`를 **가장 가까운** 벌거벗은 if에만 접고 나머지 arm은 조용히 무효화합니다. 글자 그대로 읽힌 의미와 실제 컴파일 결과가 완전히 달라지므로 경고가 아닌 규칙으로 정했습니다. 모든 arm을 `{ ... }` 안에 넣으세요. **else가 없는 독립 `cond -> body`는 여전히 벌거벗은 채로 허용됩니다**.
3. **혼용 금지** — `{}` 단락 그룹의 직계 자식 노드는 모두 `cond -> body` 분기여야 하며, 일반 문장을 섞을 수 없습니다.

```no
#{fmt-skip}
; ❌ 不會短路 — 這些是獨立 if，所有條件都會被檢查
git-dispatch = (cmd str) {
    cmd == 'a' -> {
        fa()
    }
    cmd == 'b' -> {
        fb()
    }
}
```
```

```no
; ✅ 短路 — 用 {} 包裹，第一個匹配勝出
git-dispatch = (cmd str) {
    {
        cmd == 'a' -> {
            fa()
        }

        cmd == 'b' -> {
            fb()
        }

        true -> {
        }
    }
}
```

```no
#{fmt-skip}
; ❌ if/else 寫在短路組外面 — 編譯錯誤
; 換行的 `-> break` 只掛在 `c == 43` 上，命中 `c == 45` 之後仍會被 break 掐斷
;   c == 45 -> {
;       exp-sign = -1
;       i = i + 1
;   }
;   c == 43 -> i = i + 1
;   -> break
```
```

```no

### 비동기 프로그래밍: `awy { ... }` 코루틴 그룹 + `co`

Nolang에는 표면적인 동시성 문법이 하나뿐입니다: `awy { ... }` 코루틴 그룹이며, 그룹 안에서 `co`로 태스크를 파생합니다.
`run` 키워드는 제거되었습니다(`run`은 이제 일반 식별자); `awy <handle>` 대기 접두사와 문장 위치의 벌거벗은 블록
코루틴 그룹도 모두 폐지되었습니다. **그룹 밖에서 `co`를 쓰면 컴파일 오류**입니다(`E_CO_OUTSIDE_GROUP`).

`co`에는 두 가지 형태가 있으며, 둘 다 **프로시저**만 시작하고 값을 만들지 않습니다:

```no
; 過程：只寫通道，沒有宣告回傳值
produce = (ch chan[i64], v i64) {
    ch <- v
    ch.close()
}

ch chan[i64] = with-cap(2)
awy {
    co produce(ch, 1)          ; ① 過程 spawn：co f(args)
    co {                       ; ② 閉包 spawn：co { ... }
        ch <- 2
        ch.close()
    }
}
sum = 0
i <- ch: {
    sum = sum + i
}
print(sum.to-str())            ; => 3
```

#### ① 프로시저 spawn: `co f(args)`

`f`는 **반환값을 선언할 수 없습니다**. spawn 결과를 받을 곳이 없고(`co`는 값이 아니므로), 반환값이 있는 함수를
`co`로 호출하면 `c0retval` 오류가 납니다:

```no
worker = (n i64) (r i64) { r = n }   ; 有宣告回傳值
awy { co worker(1) }                  ; ✗ c0retval
```

메서드가 암시적으로 반환하는 `self`는 반환값으로 **쳐지지 않습니다**. 모든 메서드가 가진 수신자 출력 매개변수이며, 호출을 연결할 수 있게 하는 것이 목적이므로
 `co obj.flush()` 같은 표기는 전혀 문제없습니다:

```no
queue {
    n i64
}
queue.flush = () {          ; 隱式 (self queue)，沒有其它回傳值
    self.n = 0
}
awy { co q.flush() }        ; ✓
```

결과가 필요하면 채널을 쓰세요: 프로시저가 값을 채널로 보낸 뒤 `close()`하고, 호출자가 그룹 바깥에서 비웁니다. 이는 스타일 권고가 아니라
한 가지 규칙입니다—spawn된 호출의 결과는 그룹이 join된 뒤에만 읽을 수 있고, 읽는 장소가
join 지점이 아닙니다. 바로 이런 상황을 위해 `chan`이 존재합니다.

#### ② 클로저 spawn: `co { ... }`

`co { ... }`는 프로시저 한 단락을 즉석에서 코루틴에 실행하도록 넘깁니다. 블록 안의 **자유 변수는 값으로 포착**됩니다
(spawn 시점의 스냅샷으로, 일반 spawn의 인자 깊은 복사와 같은 의미입니다):

```no
seed = 33
ch chan[i64] = with-cap(1)
awy {
    co {
        ch <- seed
        ch.close()
    }
}
r = 0
<- ch: { ok -> r = it }
print(r.to-str())          ; => 33
```

#### `co`는 값이 아닙니다: 독립 문장으로만 사용

`co`는 void를 만들므로 한 문장을 통째로 차지해야 합니다. 할당 오른쪽, 인자 위치, 반환값 위치는 모두
`E_CO_NOT_STATEMENT`(`c0nostmt`)입니다:

```no
r = co produce(ch, 1)      ; ✗ c0nostmt
print(co produce(ch, 1))   ; ✗ c0nostmt
```

또한 `co` 뒤에는 "호출"이나 "블록"만 올 수 있으며, 다른 형태는 `E_CO_NOT_CALL`(`c0notcal`) 오류가 납니다.

#### 무색 async: 자동 단형화(monomorphization)

`co`는 무색(colorless) 문법입니다: 색이 칠해지지 않은 함수 이름 `produce`를 쓰면 컴파일러가 자동으로
`produce-async` 변형을 단형화하여 내부에서 색이 있는 스택리스 코루틴으로 실행합니다. 애플리케이션 코드에 `-async` 접미사를 직접 쓰지 마세요.

규칙:

- **단형화**: `co produce(ch, 1)`은 자동으로 `produce-async`를 생성합니다(`produce`의 본체를 복사해 이름을 바꿈). `produce`가 동기로도 호출되면 둘이 공존합니다.
- **전이성**: 어떤 프로시저 내부에도 `awy { co child(n) }`가 있으면 그 프로시저 자신도 `-async`로 단형화되며, 비동기 색상이 호출 체인을 거쳐 위로 전달됩니다.
- **장벽**: 그룹 안에서 `co`가 아닌 문장(일반 할당, `print`, 반복문, `if`, **채널 읽기`…`)는 먼저 비행 중인 모든 태스크를 기다립니다. 따라서 그룹 안의 데이터 의존성은 "먼저 채널을 읽고, 읽은 값으로 spawn하기" 형태로 씁니다. 채널 읽기 자체가 장벽이어서 암묵적인 변수 의존보다 읽기 쉽습니다.
- **함수 본문은 코루틴 그룹이 아닙니다**: 그룹을 만드는 것은 `awy { ... }`뿐입니다. 함수 본문, `if` 분기, 반복문 본문 안의 `co`는 모두 거부됩니다.
- **결과를 버려도 기다립니다**: `awy { co side(5) }`도 spawn + await를 수행하여 기다려지지 않는 태스크를 남기지 않습니다.

#### 스케줄링 모델: 진짜 일시 중단

`-async` 복제본은 "한 번에 다 실행하고 보고"하는 것이 아니라 **재개 가능한 상태 머신**입니다: 지역 변수를
`%task.frame`에 매달린 힙 프레임으로 옮기고, 각 일시 중단 지점은 블록의 종결자(프레임에 상태 번호를 기록하고 반환)가 되며,
함수 진입점은 상태 비교 체인(`__state == k` ⇒ k번째 재개 지점으로 바로 점프)으로 바뀝니다.

따라서 세 곳에서 블록하지 않고 **일시 중단**됩니다:

| 일시 중단 지점 | 재개 조건 |
|---|---|
| `async-yield()` | 자신을 큐 끝에 다시 넣고 큐 맨 앞에 설 때까지 기다림 |
| 아직 끝나지 않은 자식 태스크를 `awy` | 자식 태스크가 끝나면 깨움(`%task.waiters` 체인에 등록되며 한 번에 전체 체인을 깨움) |
| 빈 채널 수신(`v <- ch:` / `<- ch:`) | `send` / `close`가 대기 체인 전체를 떼어 하나씩 다시 큐에 넣음 |

스케줄링은 단일 스레드 협동식이며 준비 큐는 FIFO라서 **순서를 완전히 단정할 수 있고** sleep이 필요 없습니다:
두 태스크가 각각 한 번씩 양보하면 반드시 `a1 b1 a2 b2`가 됩니다(`tests/coro-yield.no`가 이벤트 코드를 고정합니다).
깨어난 대기자가 **값을 얻었다는 뜻은 아닙니다**. 한 번의 `send`가 요소 하나만 추가하지만 여러 대기자를 깨울 수 있으므로,
채널의 재개 지점은 park 블록 자체이며, 읽기 가능 여부 판정을 다시 실행해 값을 가져갈지 계속 기다릴지 결정합니다.

> 교착 상태는 감지할 수 있습니다: 준비 큐가 비었는데 대상 태스크가 끝나지 않았다면 ⇒ 런타임이
> `nolang: deadlock: …`를 stderr에 출력하고 abort합니다. "아무도 보내지 않은 영값을 반환"하는 것보다 훨씬 정직합니다.

> **하위 lowering**(사용자 문법이 아님): 각 `co`는 `OpRun`이 되고, 그룹 끝에 각 태스크용 `OpAwait`가 삽입됩니다;
> `KRun` / `KAwait` / `OpRun` / `OpAwait`는 HIR/MIR에만 존재합니다. 코루틴 변환은 MIR의
> `PlanCoroutines`가 `Analyze` 이후에 수행합니다(`src/mir/coro.go`).

취소: `cancelled()`는 코루틴 함수 안에서 협동식 자체 검사에 쓸 수 있습니다. `cancel(h)`는 하위 핸들 조작이며,
새 문법은 task 핸들을 노출하지 않으므로 애플리케이션 코드에서는 쓰지 않습니다.

### 다중 할당

함수는 여러 값을 반환할 수 있으며, 호출할 때 다중 할당으로 받습니다:

```no
; 函數定義返回多個結果參數
swap = (a i64, b i64) (x i64, y i64) {
    x = b
    y = a
}

; 多重賦值
a, b = swap(5, 3)

; 使用 _ 忽略不需要的返回值（占位變數）
_, b = swap(5, 3); 只取第二個值，忽略第一個
a, _ = swap(5, 3); 只取第一個值，忽略第二個
_, _ = swap(5, 3); 忽略全部返回值（呼叫僅為副作用）

; 也支援作為 match arm 的 body
val: {
    ok -> {
        a, b = parse-pair(it)
    }

    -> return
}
```

## 연산자 오버로딩

왼쪽 피연산자의 정적 타입이 특정 `_op` 메서드를 정의하면, 컴파일러는 lowering 단계에서 중위 연산 `a op b`를 메서드 호출 `a._op(b)`로 자동으로 다시 씁니다. 오버로딩 집합은 닫힌 5개의 대칭 이항 산술 연산자입니다:

| 연산자 | 오버로딩 메서드 |
|--------|----------|
| `+` | `_add` |
| `-` | `_sub` |
| `*` | `_mul` |
| `/` | `_div` |
| `%` | `_mod` |

```no
big {
    v i64
}

; 回傳型別書寫 ?big，編譯器視作純 payload big
big._add = (b big) (c ?big) {
    c = big {
        v: .v + b.v
    }
}

f = (a big, b big) (out big) {
    r big = a + b; 編譯器改寫為 a._add(b)
    out = r
}
```

**타입 규약**: 연산자 오버로딩 메서드의 결과 매개변수는 **`?T`로 쓰지만 실제 타입은 순수 payload `T`**입니다—컴파일러는 option 포장/언패킹을 하지 않으며, 메서드 본문에서 `c`에 `T` 값을 바로 할당하고 호출자도 `T`를 받습니다. 0으로 나누기 같은 오류는 내장 숫자 타입과 마찬가지로 런타임에 바로 trap되며 option을 만들지 않습니다.

**의미상의 핵심:**

- 왼쪽 피연산자의 정적 타입이 해당 `_op` 메서드를 정의했을 때만 다시 씁니다. 내장 숫자 타입(i64, f64 등)은 내장 산술을 그대로 사용합니다.
- 명시적 메서드 호출 `a._add(b)`와 `a + b`는 완전히 동등합니다.
- 왼쪽으로 중첩된 연쇄 연산은 단계별로 다시 쓰입니다: `a + b + c` → `(a._add(b))._add(c)`. 중간 결과 타입은 여전히 `T`이므로 연산이나 메서드 호출에 계속 참여할 수 있습니다.
- 표준 라이브러리 `bigint`도 이 메커니즘으로 `+ - * / %`를 지원합니다("표준 라이브러리 > 기타 모듈"의 bigint 항목 참조).

## 배열과 슬라이스

컨테이너는 데이터 사본을 저장하며, 원래 변수와 컨테이너는 서로 독립적이어서 dangling reference를 없앱니다.

**고정 길이 배열 arr:**

```no
; 使用定長数组
a [3] = [1, 2, 3]; 길이가 3인 고정 길이 배열 i64
a [3]u16 = [1, 2, 3]; 타입을 지정한 고정 길이 배열

a[nil]
u16 = [1, 2, 3]; 自動推斷長度（指定類型）
a[nil] = [1, 2, 3]; 自動推斷長度（i64）
```

**가변 길이 배열 vec:**

```no
v = [1, 2, 3]; 變長數組 i64
bs = [0x11, 0x22, 0x33]
v []u8 = [1, 2, 3]; 타입을 지정한 가변 길이 배열

; 預分配（避免反覆擴容）
v = with-cap(100); len=0, cap=100（需 push 後索引）
v = with-len(100); len=100, cap=100（可直接索引）
v = with-cap-len(200, 100); len=100, cap=200（預留擴容空間）
```

**슬라이스 slice(뷰, 독립 타입이 아님):**

슬라이스는 원본 데이터에 대한 **뷰(view)**이며, 데이터를 복사하지도 새로운 독립 타입을 만들지도 않습니다.  
슬라이스 내부에는 원본 버퍼를 가리키는 포인터, 길이, 용량만 기록되므로:

- 슬라이스로 요소를 수정하면 원본 데이터에 영향을 주고, 그 반대도 마찬가지입니다
- 슬라이스는 데이터를 소유하지 않으며, 원래 변수가 해제되면 슬라이스도 무효해집니다
- 슬라이스의 타입은 원본 타입이 결정하므로 메서드가 자연스럽게 적용되며 "상속" 메커니즘이 필요 없습니다

```no
; 支持arr/vec/str
; 支持範圍 和for <- 的表示一致
nums [5]u8 = [0, 1, 2, 3, 4]

nums[..]; [0 1 2 3 4]   完全無界，等同整個切片
nums[1..]; [1 2 3 4]     無上限，從索引 1 到末尾
nums[..4]; [0 1 2 3 4]   無下限，從開頭到索引 4
nums[2..3]; [2 3]        有界，兩端都包含
nums[1..3]; [1 2 3]      有界，兩端都包含
nums[1..3); [1 2]        左閉右開
nums(1..3); [2]          兩端開區間

; 字符串（切片結果型別為 str 視圖，共享底層記憶體；下標為碼點位置，與 s[i] 一致）
s = 'abc'
s[1..]; 'bc'
s[1..s.len()); 'bc'
b str = s[0..1]; 切片結果已是 str，可直接賦值給 str 變數
```

> 슬라이스 문법은 match/range-for와 동일한 16가지 범위 조합을 지원합니다. 슬라이스 맥락에서 무한 범위는 슬라이스 길이를 기준으로 합니다: `[..]`는 전체 슬라이스, `[a..]`는 인덱스 a부터 끝까지, `[..b]`는 처음부터 인덱스 b까지를 뜻합니다.

**슬라이스의 타입과 메서드:**

슬라이스는 새로운 독립 타입을 만들지 않으며, 원본 타입의 뷰일 뿐입니다(시작 포인터와 길이를 조정한 것).  
따라서 원본 타입의 메서드를 그대로 사용할 수 있습니다:

| 원본 타입           | 슬라이스 뷰 타입       | 사용 가능한 메서드                                                                             |
| -------------- | ------------ | -------------------------------------------------------------------------------- |
| `arr` (`[n]t`) | `[]t<range>` | `[]t`의 모든 메서드(`len`, `push`, `pop`, `contains`, `reverse`, `clone`, `fill`, `to-arr` 등) |
| `vec` (`[]t`)  | `[]<range>`  | 위와 같음                                                                               |
| `str`          | `str<range>` | `str`의 모든 메서드(`to-upper`, `to-lower`, `index`, `contains`, `slice`, `copy`, `fill` 등)  |

```no
; arr 切片 → vec 視圖，共享 arr 的底層記憶體
a [5]u8 = [0, 1, 2, 3, 4]
s = a[1..4]; s 是 []u8 視圖，指向 a 的記憶體
n = s.len(); slice.len()

; vec 切片 → vec 視圖，共享 vec 的底層記憶體
v = [10, 20, 30, 40, 50]
s = v[2..]; s 是 []i64 視圖
s.reverse(s.len()); slice.reverse

; str 切片 → str 視圖，共享 str 的底層記憶體
s = 'Hello World'
sub = s[6..]; sub 是 'World' 視圖
upper = sub.to-upper(); str.to-upper

; 通過切片修改元素會影響原始資料
data = [10, 20, 30, 40, 50]
view = data[1..4]; view = [20, 30, 40]
view[0] = 99; 修改 view 的元素
; data[1] 現在也是 99，因為 view 共享 data 的記憶體
```

### 인덱싱

```no
; 字符串索引 → 回傳 ?char（Unicode 碼點，不是字節）
c char = s[i]; 顯式 plain 型別把結果拉回 char（見〈安全索引〉）

; arr、vec獲取元素
arr[i]; → ?elem
vec[i]; → ?elem

; map 獲取 value
map[str]
```

> **인덱스 읽기의 결과는 항상 `?T`입니다**: `arr[i]` / `vec[i]` / 고정 길이 배열 / `slice` → `?elem`,  
> `str` / `txt`의 `s[i]` 인덱싱 → `?char`(D6, 정수 산술과 동일한 통합 규칙).  
> 따라서 `str[i]`의 **추론 타입은 `?char`**이며, plain `char`를 얻는 방법은 두 가지입니다:  
> 바인딩에 명시적 plain 타입을 쓰기(`c char = s[i]`, lower 단계에서 단락 합성되어 plain 값을 읽음),  
> 또는 match / `?=`로 언패킹하기.  
> `str[a..b]` 슬라이스는 여전히 `str`을 반환합니다(코드 포인트 의미의 뷰로, 기반 메모리를 공유).  
> `char`는 **`str`로 암시적 변환**이 가능해(한 문자 문자열로 인코딩) 아래 표기들이 모두 유효하며 `char.to-str()`를 수동으로 호출할 필요가 없습니다:

```no
s = 'héllo'
c char = s[1]; 'é'（char，其碼點為 233）
a str = s[1]; 'é'（char → str 隱式轉換）
b str = s[0..1]; 'hé'（切片結果本身已是 str）
msg = 'first: ' - s[0]; char 參與拼接（-）時隱式轉為 str
ok = s[0] == 'h'; char 與 str 比較時隱式轉為 str
```

### 안전한 인덱싱(Safe Indexing)

`arr` / `vec` / `slice`(`[]T`) / 고정 길이 배열 / `str` / `txt`의 인덱스 `v[i]`에 대해 **결과는 항상 `?T`**입니다: 범위를 벗어나면 첨자의 소스 위치가 첨부된 `err`(`err('index out of range', code.index-out)`)를 반환하고, 범위 안이면 `ok(값)`을 반환하며, 절대 abort하지 않습니다(runtime error: index out of bounds). 이는 정수 `+ - * / %`의 표기 없는 오버플로 동작과 같은 규칙입니다(〈정수 연산 오버플로〉 참조).

`?T`를 사용하는 방법은 세 가지뿐입니다(**`#{index-out=DEF}` 애노테이션은 D11에서 폐기 및 제거되었습니다**. 남아 있는 애노테이션은 컴파일 오류입니다;
"명시적 plain 타입으로 plain을 얻기" 같은 지름길도 없습니다. `v i64 = a[i]`역시 명시적으로 소비해야 합니다):

**1. 읽기 — match 언패킹**

값 match로 값을 직접 얻거나, 문장 match의 `ok` arm 안에서 할당합니다. `-> _`는 "버리기" arm이며,
값 맥락에서 **요소 타입의 영값**을 생성합니다(i64→0, str→'', byte→0, 컨테이너→빈 컨테이너).

```no
; 值 match
x = state[5]: {
    ok -> it

    -> _
}

; 陳述 match
state[5]: {
    ok -> x = it

    -> _
}
```

**2. 쓰기 — place-match**

`it`는 `ok` arm 안에서 값 사본이 아니라 **요소 위치**(읽고 쓰기 가능)입니다.

```no
state[5]: {
    ok -> it = x

    -> _
}
```

> **map 예외**: `m['k'] = 1` 쓰기는 **언패킹이 필요 없습니다**. map의 첨자는 키이고 쓰기는 put/insert이면,
> 키가 없으면 삽입, 있으면 덮어쓰기로 항상 정의되어 guard할 "범위 초과 쓰기"가 없습니다. 다만 **map 읽기 `m['k']`는 여전히 `?V`를 반환하므로 언패킹해야 합니다**.
> `m[k] ?= v`는 **컴파일 오류**입니다(`get`이 읽은 `?V`는 사본일 뿐이라 다시 써도 map으로 돌아가지 않습니다). `m[k] = v`를 바로 쓰세요.

**3. 축약형 `?=` — 오류 상위 전파**

`x ?= state[5]`(읽기), `state[5] ?= x`(쓰기)는 위 두 match의 축약형입니다: 실패하면 전체 option을
위로 던집니다. 다음 **두 경우 중 하나**에서만 유효합니다:

- 해당 함수에 `?T` 결과 매개변수가 있음 — 실패 시 결과 매개변수에 기록하고 일찍 `return`합니다;
-문장이 **문장 수준 블록 match** `{ ... }: { ... }`의 본문 안에 있음 — 가장 가까운 블록 match가 포착하며,
  본문이 정지되고 arm은 한 번만 실행되며, 함수에는 `?T` 결과 매개변수가 **필요하지 않습니다**.

둘 다 아니면 컴파일 오류입니다. 따라서 "반환값이 option이 아닌데도 축약형을 쓰고 싶다"면 표준 폴백은 함수 본문을 블록 match로 감싸는 것입니다:

```no
handle = (x i64) {
    {
        y ?= x + 1
        print(1)
    }: {
        err -> _

        -> _
    }
}
```

**중첩 읽기**: 내부 match가 `it`를 다시 바인딩하므로 내부에서는 이름 있는 바인딩 `ok(it1) -> it1`을 씁니다. 사용자가 준 정확한 형태
(값 match를 place-match의 `it = ...` 오른쪽에 바로 씀)는 2026-11-06부터 **컨테이너에 올바르게 다시 기록됩니다**: 컴파일러가
lowering 시 그 값 match를 합성 임시 변수로 끌어올린 뒤 `it`를 다시 바인딩합니다. 회귀 테스트는 `tests/match.no`의
 `place-write-value-match` 항목을 참조하세요. **직접 쓰기를 우선**: 값 match의 결과를 최종적으로 쓸 그 이름에 바로 바인딩하고,
일회용 임시 변수에 넣었다가 한 번 더 복사하지 마세요.

```no
#{fmt-skip}
; ✅ 直接綁定目標變數
at = argt[i]: {
    ok -> it

    -> _
}
s.farg.push(at)

; ❌ 不要為單次使用引入一次性暫存
ixout1 = argt[i]: { ok -> it  -> _ }
at = ixout1
s.farg.push(at)
```

"값 match를 arm 밖의 이름 있는 임시 변수로 끌어올리고 arm 안에서 `it = ixout1`을 쓰는 것"은 **직접 쓰기와 동등하지 않으며**, 자유롭게
바꿔 쓸 수 있는 서식 선택이 아닙니다: 평가 시점이 다릅니다(밖으로 끌어올리면 바깥쪽 `nil` / `err` / catch-all도 먼저 한 번 읽습니다);
`it`는 arm 안에서만 유효하고 요소 위치를 가리키므로 복사는 arm 안에 남아야 합니다. 이름 있는 임시 변수는 새 바인딩이라 자체 move /
소유권과 스코프 종료 시 파괴가 있습니다. 또한 중첩 시 내부에서는 이름 있는 바인딩 `ok(it1) -> it1`을 써야 하며 arm 밖의
 `ok -> it`를 그대로 따라 쓸 수 없습니다. 같은 값을 여러 곳에서 정말 재사용할 때만 끌어올리고 의미 있는 변수 이름을 쓰세요. `ixout…`처럼
마이그레이션 도구가 만든 자리표시자 이름을 남기지 마세요.

#### `?=`와 블록 match로 남은 일회용 임시 변수 정리하기

위에서는 "한 번만 쓰면 바로 바인딩"을 설명했습니다. 한 걸음 더: 안전한 인덱싱은 `?T`를 반환하므로, **함수의
결과 매개변수 자체가 `?T`라면 값 match조차 쓰지 않고 `?=` 한 줄로 바로 상위 전파할 수 있습니다**:

```no
#{fmt-skip}
; ✅ 函式有 ?T 結果參數：無暫存、無 match
at ?= argt[i]
s.farg.push(at)
```

**함수 결과가 option이 아닐 때**(가장 흔한 경우: 반환값 없는 보조 함수, 또는 컨테이너에 다시 쓰기만 하는 경우), 이런
"try 비슷한" 표기로 해당 문장을 감싸세요:

```no
#{fmt-skip}
handle = (x i64) {
    {
        y ?= x + 1
        print(y)
    }: {
        err -> _

        -> _
    }
    print('continues afterwards')
}
```

⚠️ **새로운 `try` 문법이 아니며, 언어에 `try` 키워드도 없습니다.** 이는 바로 **문장 수준의 블록
match**(`{ ... }: { ... }`)이며, 주어는 3상태 `?T`입니다. `?=`는 실패를 **가장 가까운** 블록 match로 던집니다
(〈`?=` 오류 상위 전파〉와 〈Match 주어의 세 가지 형태〉 참조). 실패 시 블록 본문의 남은 문장—이후
루프 반복까지—전부 건너뛰고, arm은 한 번만 실행된 뒤 **블록 뒤의 코드를 계속 실행합니다**. 함수의
`return`이 아닙니다. `err -> _`는 오류를 버리고, `-> _`는 성공 결과를 폴백으로 버립니다. 오류를 처리하려면
 `err -> print(it.msg())`를 쓰세요.

⚠️ **의미 차이를 분명히 해야 합니다**(실측에 근거할 것, 직관에 의지하지 마세요): `?=`가 실패하면 **대상은 여전히 영값으로 기록됩니다**—`i64`는
`0`, `str`은 `''`, `out[1]`은 `0`이 됩니다. 반면 값 위치 match의 폴백 arm `-> _`는 **대상에 기록하지 않습니다**. 대상이
**새 선언**이라면 원래 영초기화이므로 일치해 보이지만, 대상에 **이미 값이 있으면** 둘이 갈라집니다(`?=`는 0으로 만들고, `-> _`는
원래 값을 유지하며 0으로 만들려면 `-> 0`을 써야 합니다). 다른 차이는 제어 흐름입니다: `?=`는 **블록 본문에서 자기 뒤의 문장을 건너뜁니다**
(`?T` 함수에서는 일찍 `return`, 블록 match에서는 곧바로 arm으로 이동).

따라서: **블록 본문에 그 문장 하나뿐이고 실패 이전의 옛 값에 의미가 없을 때** 폴백 arm을 `-> 0`으로 쓰면 완전히
동등합니다(이것이 바로 이 저장소에서 일괄로 다시 쓴 형태이며 `ixout…` 임시 변수는 대부분 새 선언이었습니다). 그러나 본문에 `?=` 뒤에
다른 문장이 더 있거나(루프 카운트, 후속 할당), 대상의 옛 값에 의미가 있으면 갈라지므로 그 지점은 기계적으로 바꿀 수 없습니다. 전체
선택 표는 〈블록 match와 값 위치 match의 선택〉을 참조하세요.

또 하나 쉽게 빠지는 지점: **성공할 때도 arm이 한 번 실행되어** catch-all이 성공 값을 받습니다(`-> print('x')`가 출력됩니다).
따라서 arm에는 버리기나 순수 처리만 두어야 합니다. `err -> _` / `-> _` 형태는 부수 효과가 없습니다.

여기서 `ixout…` 일회용 임시 변수를 정리하는 순서가 도출됩니다:

1. 값이 한 곳에서만 한 번 쓰임 → 최종 대상 이름에 바로 바인딩(위 참조).
2. 함수에 `?T` 결과 매개변수가 있음 → `TARGET ?= EXPR`, 임시 변수 불필요.
3. 그 외 → 해당 문장을 블록 match에 넣은 뒤 `TARGET ?= EXPR`을 씀; place-match 쓰기 반영은
   (`SUBJ: { ok -> it = temp  -> _ }`)도 바로 `SUBJ ?= EXPR`로 줄일 수 있습니다.
4. 같은 값을 여러 곳에서 정말 재사용할 때만 이름 있는 임시 변수를 남기고, 의미 있는 변수 이름을 쓰세요.

두 가지 경계: `?=`는 `?T` 결과 매개변수도 없고 블록 match 본문 안에도 아닐 때 컴파일 오류입니다
(`l86f91me`); **타입 선언이 붙은 LHS에는 `?=`를 쓸 수 없습니다**(`ai i64 ?= a[i]`는 파싱 오류
`yh8904fm`, `expected assignment operator`). `byte → i64`처럼 명시적 승격이 필요하면 타입 선언이 있는 직접 값 match로 바꾸세요:

```no
#{fmt-skip}
ai i64 = a[i]: {
    ok -> it

    -> _
}
```

> **적용 범위**: `arr` / `vec` / `slice` / 고정 길이 배열 / `str` / `txt`에 모두 적용됩니다. **직접 변수 기반**의
> 인덱스(`v[i]`)만 안전한 형태로 다시 쓰이며, `receiver.field[i]`는 기존 bounds-check 경로를 따릅니다.
> 비교 연산자 안의 인덱스 읽기는 `{tag, payload}` 전체가 아니라 payload를 비교합니다(`a[i] == 5`).

> ⛔ **하드 오류**: `?T`를 일반 값으로 쓰면(예: `crc = crc ^ s[i]`, `f(s[i])`, `v i64 = a[i]`)
> `no build`가 중단되며, 컴파일러가 match나 `?=` 사용을 안내합니다(`?T` 결과 매개변수가 없으면 블록 match로 감쌉니다).
> 기존 코퍼스는 `no fmt --fix=index-out`으로 일괄 마이그레이션되었으며, 해당 도구는 D11과 함께 퇴역했습니다.

> **핵심 보장**: 범위 초과는 절대 조용히 충돌하지 않습니다—match로 처리되거나 `?=`로 상위 전파됩니다.

> **비교 연산자 안의 인덱스 읽기**에도 안전한 인덱싱이 적용됩니다: `a[i] == 5`는 `{tag, payload}` 전체가 아니라 payload를 비교합니다(`?T == 5`와 같은 규칙).
> 범위를 벗어나면 `err`(`code.index-out`)가 읽혀 어떤 값과 비교해도 **거짓**이 되며
> (`a[i] == 0`과 `a[i] == 5` 모두 거짓), 범위 밖 메모리를 **읽지 않습니다**.
> `s[0] == 'a'`도 같습니다: 코드 포인트와 한 문자 문자열을 비교할 때 `char → str` 암시적 변환을 사용합니다.

> **중첩 첨자** `a[i][j]`: **두 단계 모두 안전한 인덱싱**입니다. 바깥쪽 `a[i]`가 먼저 범위 검사와 존재 여부를 판단하고,
> 존재할 때만 거기서 `[j]`를 취합니다. 어느 단계든 범위를 벗어나면 전체 표현식이 `err`입니다.
> 따라서 `a[oob][0] == 'c'`는 abort하지 않고 거짓이 됩니다.

> **컨테이너 비교** `[]T == []T`(그리고 `[N]T == [N]T`)는 **구조 비교**입니다: 먼저 길이를 비교한 뒤 요소별로 비교합니다.
> 요소 자체가 컨테이너(`[][]i64`)라면 단계별로 재귀하고, 요소가 `str`이면 data 포인터가 아니라 **내용**을 비교합니다.
> 순서 비교(`<` / `<=` / `>` / `>=`)는 컨테이너에 정의되어 있지 않으며 `==` / `!=`만 지원됩니다.

> **`nil`은 option하고만 비교할 수 있습니다**: `?T == nil` / `?T != nil`은 유효합니다. option이 아닌
> `T == nil`(`str`, `[]i64`, `[N]T`, `txt`, `i64`, 구조체…)은 **컴파일 오류**입니다(`q4nilcmp`).
> 이유는 깔끔함을 좋아해서가 아닙니다. `str == nil`은 항상 false(%str-long 구조체와 0을 비교)이고,
> `[]i64 == nil`은 정수 비교 경로로 떨어져 잘못된 LLVM을 만듭니다(`icmp eq i64 %vec, i64`).
> 둘 다 조용히 틀린 답을 줍니다. "값이 없을 수도 있음"을 표현하려면 타입을 `?T`로 선언한 뒤 `nil`과 비교하세요.

## 구조체

구조체 정의와 리터럴은 모두 여러 줄 형식을 사용해야 합니다. 각 필드가 한 줄을 차지하고, 필드 사이에 쉼표를 쓰지 않으며, 끝에도 쉼표를 붙이지 않습니다.

```no
user {
    name str
    age i64
}

u = user {
    name: 'Alice'
    age: 30
}
u.name = 'Bob'
u.age = 25
print(u.name)
```

### 구조체가 인터페이스 구현하기

## 메서드

메서드는 타입에 정의하며, `.`로 수신자(receiver)를 참조합니다.

### 문법

```no
#{fmt-skip}
type.method-name = (params) (results) {
    ; . 是接收者
}
```

### 규칙

1. 메서드 이름은 `type.method` 형식을 사용하며, type은 이미 정의된 타입이어야 합니다
2. 수신자는 명시적으로 매개변수를 선언할 필요가 없으며, 메서드 본문에서 `.`로 참조합니다
3. 호출할 때는 `receiver.method(args)` 문법을 사용합니다
4. 반환값은 일반 함수와 마찬가지로 두 번째 괄호에 넣습니다
5. **문법 설탕 탈당**: `type.method = (inputs) (rest-outputs...) {}`는 일반 함수와 동등합니다  
   `method = (inputs) (self type, rest-outputs...) {}`. `instance.method(args)` 호출 시  
   instance가 출력 목록의 첫 매개변수 `self`에 바인딩되고, 함수 본문의 `.`는 출력 영역의 `self`를 가리키며,  
   함수가 `self`에 쓰는 값은 원래 인스턴스를 직접 수정합니다. 출력 목록에서 `self` 이외의 나머지 출력은  
   선택적 구조 분해로 받거나 그냥 버릴 수 있습니다.

### 예

```no
; str 方法
str.to-upper = () (out str) {
    n = .len-bytes()
    b []byte = with-cap-len(n, n)
    i <- [0..n): {
        c ?byte = .byte(i)
        v = c: {
            ok -> it

            nil -> 0

            err -> 0
        }
        {
            v >= 97 && v <= 122 -> b[i] = v - 32

            -> b[i] = v
        }
    }
    out = b.to-bytes-str()
}

; char 方法
char.is-digit = () (result bool) {
    result = false
    . >= 48 && . <= 57 -> result = true
}

; struct 方法
user {
    name str
    age i64
}

user.greet = () {
    print('Hello, ' - .name)
}

; 調用
s = 'hello'
u = s.to-upper(); receiver.method()
c char = 5
d = c.is-digit(); receiver.method()
u = user {
    name: 'Alice'
    age: 30
}
u.greet()
```

```no
; 定義接口

    ; 當前實現
    .to-json()

    ; 父實現

}
```

### 인터페이스 병합

인터페이스는 다른 인터페이스의 메서드를 "병합"할 수 있습니다. 부모 인터페이스 이름은 인터페이스 본문 안에 **한 줄에 하나씩** 씁니다(모듈 접두사를 붙일 수 있음). 쉼표도 괄호도 붙이지 않습니다:

```no
json {
    to-json()
}
noml {
    to-noml()
}

serialize {
    json
    noml
}

; 傳遞合併：roundtrip 同時獲得 serialize、json、noml 的全部方法
roundtrip {
    serialize
    roundtrip-json()
}
```

규칙:

- **재귀 병합**: 병합은 전이적입니다—`roundtrip`이 `serialize`를 병합하고, `serialize`가 다시 `json` / `noml`을 병합하면 `roundtrip`은 세 인터페이스의 메서드를 모두 가집니다.
- **한 줄에 하나, 쉼표 금지**: `serialize { json, noml }`은 C 스타일 열거형(`color { red, green }`)과 형태가 같으므로 여전히 열거형으로 해석되며, 인터페이스 병합이 아닙니다.
- **같은 이름의 메서드**: 시그니처가 같으면(매개변수와 반환 타입이 일치하고 수신자 이름은 달라도 됨) 중복을 제거해 하나만 남깁니다. 시그니처가 다르면 진단 오류가 납니다.
- **구현 측**: 타입은 구현 선언(선행 목록 `user serialize { name str }`)만 쓰면 되며, 부모 인터페이스의 메서드도 구현된 것으로 간주합니다. 시그니처 검사는 부모 인터페이스를 통과합니다.
- **`no fmt`**: 예전 "선행 목록" 표기(`serialize json, noml { }`)는 여전히 해석되지만, `no fmt`는 이를 본문 안 형태로 다시 쓰고 `no vet`는 이에 대해 WARNING을 냅니다.

진단(`no vet`과 편집기 진단은 동일한 소스, TraceID `ifmrg001`):

| 상황 | 메시지 |
| --- | --- |
| 부모 인터페이스 미선언 | `interface 'serialize': unknown parent interface 'noml'` |
| 순환 병합 | `interface 'a': merge cycle a -> b -> a` |
| 같은 이름, 다른 시그니처 | `interface 'serialize': merged method 'to-str' has conflicting signatures ('json.to-str', 'noml.to-str')` |

> `serialize = json \| noml` 같은 표기는 **유니온 타입**(union type) 문법이며 인터페이스 병합과 무관합니다. 인터페이스 병합은 "타입이 어떤 메서드를 가져야 하는지"에만 영향을 줍니다.

### 태그 열거형(페이로드 포함)

변형은 이름이 있는 페이로드 필드를 가질 수 있으며, 괄호 형태 `變體(欄位 型別)`으로 씁니다. 페이로드가 없는 변형은 그냥 이름만 씁니다.  
한 변형에 **여러 개** 필드를 둘 수 있습니다(여러 필드 페이로드는 힙에 합성 구조체로 표현됩니다):

```no
#{fmt-skip}
; 標籤列舉：變體可帶載荷，tag 依聲明順序為 0,1,2...
result {
    ok(v t),
    nil,
    err(e str),
}

; 有值：載荷欄位 v，型別 t
; 空值：無載荷
; 錯誤：載荷欄位 e，型別 str（用戶自定義枚舉，與內建 option 無關）

shape {
    circle(r f64),
    rect(w f64, h f64),
    dot,
}
; 單欄位
; 多欄位
; 無載荷
```
```

매치할 때는 변형 이름을 암 패턴으로 사용하며, 페이로드가 있는 변형은 페이로드를 분해해 바인딩할 수 있습니다(여러 필드는 위치 순서대로 1:1 바인딩):

```no
r result = ok(42)
r: {
    ok(v) -> print(v); 把 ok 的載荷綁定到 v

    nil -> print('empty')

    err(e) -> print(e)
}

s shape = rect(3.0, 4.0)
s: {
    circle(r) -> print(r); 綁定單欄位

    rect(w, h) -> print(w * h); 按位置綁定多欄位

    dot -> print('dot')
}
```

변형은 **식 위치**에서 직접 구성하여 함수 인자나 다른 변형의 페이로드로 쓸 수 있습니다:

```no
x f64 = perimeter(rect(3.0, 4.0)); 內聯建構並傳參
o outer = wrap(a(5)); 枚舉載荷本身是另一個枚舉
```

> **네임스페이스와 벌거벗은 이름 해석**: 컴파일러는 내부에서 변형을 "완전한 정규화 이름"(`模組.枚舉.變體`,  
> 예: `option.option.ok`, `some-mod.my-result.ok`). 서로 다른 열거형의 같은 이름 변형은 충돌하지 않습니다.  
> 사용자는 벌거벗은 이름(`ok`, `rect`)만 쓰고, 컴파일러가 **매치되거나 구성되는 변수의 정적 타입에 따라**  
> 완전한 이름을 자동으로 완성합니다. 따라서 두 열거형이 모두 `ok` 변형을 가지고 tag 순서가 달라도 올바르게 구분할 수 있습니다.
>
> 예전 방식의 공백으로 구분된 타입 `ok t`도 쓸 수 있으며, 이는 `ok(v t)`와 동일합니다(필드 이름 생략).  
> 태그 열거형의 변형 이름은 컴파일러의 열거형 변형 표에 등록되어 매치와 망라성 검사에 사용됩니다.

### 내장 태그 열거형(`#{buildin}`)

태그 열거형 앞에 `#{buildin}`을 붙이면 **내장 열거형**임을 나타냅니다. 변형(이름, 순서, 페이로드 타입)은  
매치와 망라성 검사에 사용되지만, 기본 표현과 생성은 runtime/builtin이 제공하며 **사용자에게 보이는  
struct/union은 생성되지 않습니다**. `?t` option도 이 방식으로 선언됩니다:

```no
; src/std/global.no
#{buildin}
option {
    ok(v t),
    nil,
    err(e err.err),
}
```

`option`의 tag는 순서대로 `0=ok`, `1=nil`, `2=err`이며, 내장 option 표현과 일치합니다. 사용자는  
option을 직접 선언할 필요가 없습니다. 여기서의 `#{buildin}`은 내장 option의 변형 출처를 하나로 통일합니다("null 허용 타입(option)" 참조).

### 열거형 애노테이션과 메모리 레이아웃

열거형은 `#{...}` 애노테이션을 지원하며, 위치는 다른 대상과 같습니다(〈애노테이션 위치〉 참조): **위쪽**(독립된 줄) 또는  
**뒤쪽**(같은 줄 끝에 이어서). 대상 **앞쪽 같은 줄**에 쓰는 것은 컴파일 오류입니다.

애노테이션은 **두 곳**에 둘 수 있습니다:

1. **enum 전체 위쪽** — enum 정의 자체에 작용합니다(`#{buildin}`, `#{inline=true}` 등);
2. **개별 멤버의 위쪽이나 같은 줄 끝** — 그 멤버에 작용합니다(C 스타일 열거형의 "값"과 태그 열거형의 "변형" 모두 가능).

```no
; ① 整個 enum：獨立成行置於 enum 上方
#{inline=true}
box {
    full(v i64) #{doc='有值'},
    empty #{doc='空值'},
}

; ② 單個變體：獨立成行置於變體上方

; ② 單個變體：同一行尾隨

; `#{inline=false}`：明確寫出「不用 inline 佈局」
#{inline=false}
plain {
    a,
    b,
}

color {
    red #{deprecated},
    green #{deprecated},
    blue,
}
; C 風格枚舉的單個值同樣支援這兩種寫法
```

**애노테이션은 enum의 구조를 바꾸지 않습니다**: 변형 이름, 선언 순서(tag), 페이로드 필드와 타입은 애노테이션의 영향을 받지 않으며,  
매치와 망라성 검사도 전혀 변하지 않습니다. 애노테이션은 정의에 덧붙이는 **메타데이터**일 뿐입니다.

#### 메모리 레이아웃(스택 방식)

태그 열거형은 메모리에서 **스택 방식 레이아웃**(inline stack form)을 사용합니다. 값으로 저장되는 작은 객체이며, 페이로드가 힙에 흩어지지 않습니다:

```llvm
%tenum_<name> = type { iN tag, [K x i64] payload }   ; 一般情形
%tenum_<name> = type { iN tag }                      ; 所有變體皆無載荷
```

- `tag`의 너비는 **변형 개수**에 따라 달라지며, `u8/u16/u32/u64` 중 하나입니다:
  `<= 256` → `i8`, `<= 65536` → `i16`, `< 2^32` → `i32`, 그 외에는 `i64`. 판별값은 선언 순서대로 `0, 1, 2...`를 취합니다.
- `payload`는 **모든 변형이 공유하는** union입니다(각 변형이 자신의 필드를 같은 저장 영역에 씁니다). `K`는 **가장 넓은 변형이**
  필요한 8바이트 워드 수이며, **모든 변형의 합이 아닙니다**. 최솟값은 1입니다.
- 변형 내부에서는 필드가 **자연 정렬**로 배치되므로 필드 오프셋이 반드시 8의 배수는 아닙니다(`(a char, b char, c char)`
  의 오프셋은 0 / 4 / 8). 읽기와 쓰기는 항상 **바이트 오프셋**으로 주소를 지정하며(`bitcast`로 `i8*`한 뒤 `getelementptr`),
  따라서 "쓰는 오프셋"과 "읽는 오프셋"은 같은 레이아웃 표에 의해 결정됩니다.

크기는 `8 + 8K`입니다(`tag`가 배열의 8바이트 정렬에 맞춰 한 워드로 패딩됨). 페이로드가 없는 열거형만 순수 태그 크기를 가집니다:

| 경우 | `K` | 크기 |
| ---------------------------------------------- | ----------------- | ---------- |
| 모든 변형에 페이로드가 없음 | —(payload 필드 없음) | **1바이트**(`{ i8 }`; 변형이 256개를 넘으면 2 / 4 / 8) |
| 가장 넓은 변형이 `i64` / `i32` / `f64` / 포인터 | 1 | 16바이트 |
| 가장 넓은 변형이 `char`(4바이트) / `bool`(1바이트) | 1 | 16바이트 |
| 가장 넓은 변형이 `(a char, b char, c char)`(12바이트) | 2 | 24바이트 |
| 가장 넓은 변형이 `str` / `vec` / `[]T`(16바이트 디스크립터) | 2 | 24바이트 |
| 가장 넓은 변형이 구조체 `T` | `ceil(sizeof(T) / 8)` | `8 + 8K` |

즉, **기본값은 16바이트부터 시작**하며, 어떤 변형의 페이로드가 실제로 더 넓을 때만 커집니다—
"기본 16바이트 고정"과 "크기가 변형에 따라 달라진다"는 같은 일의 두 면입니다. `char` / `bool` 같은 작은 페이로드는
정렬만 결정할 뿐 union을 키우지 않습니다. `payload`의 너비는 "가장 넓은 변형 하나"이지 모두의 합이 아닙니다.

> 레이아웃의 유일한 출처는 `src/mir/layout.go`입니다. `tagWidth`가 `iN`을 정하고, `enumVariantLayout`이 각
> 변형의 필드 오프셋과 자체 크기를 정하며, `enumUnionLayout`이 최댓값을 취해 `K`를 얻습니다. `hir2mir.fillEnumLayout`은
> 표를 만들 때 이 숫자들을 `TaggedEnumInfo`에 기록하고, emitter는 읽기만 계산하지 않습니다—양쪽이 서로 다른 답을 낼 수 없습니다.

#### `#{inline}`의 세 가지 표기

`inline`은 **불리언** 애노테이션으로, 세 가지 표기가 있으며 **값이 실제로 반영됩니다**:

| 표기 | 의미 |
| ----------------- | --------------------------- |
| `#{inline}` | 축약형, `inline=true`와 동일(독립 키는 참) |
| `#{inline=true}` | 명시적으로 참(`#{inline=1}`도 가능) |
| `#{inline=false}` | 명시적으로 거짓(`#{inline=0}`도 가능) |

불리언이 아닌 값은 **컴파일 오류**(`#{inline=foo}`, `#{inline='true'}`)이며, 조용히 참으로 취급되지 않습니다.  
`ValidateFieldTags`(TraceID `fieldtag1`)는 구조체 필드와 enum 정의 모두에서 오류를 보고합니다.

enum 전체 위쪽에 `#{inline=true}`를 쓰는 것은 스택 방식 레이아웃의 **명시적 표시**이며, "이 열거형은 스택 방식 레이아웃을 사용한다"는 뜻입니다.  
컴파일러는 이를 `TaggedEnumInfo.Inline`에 기록합니다. **현재 기본 레이아웃은 원래 스택 방식**이므로  
애노테이션을 쓰지 않거나 `true` / `false` 중 무엇을 써도 레이아웃은 완전히 같습니다. 표시의 목적은 의도를 명확히 하고,  
향후 기본 레이아웃이 바뀔 때 안정적인 선택 스위치로 쓰기 위한 것입니다.

> `#{inline}`을 **enum 전체 위쪽**에 쓰면 "이 열거형은 스택 방식 레이아웃을 사용한다"는 뜻이고, **개별 변형**에 쓰면  
> 현재 레이아웃을 바꾸지 않으며, 해당 변형의 메타데이터로만 남습니다(구조체 필드와 다름, 다음 절 참조).

#### 구조체 필드의 `#{inline}`

enum과 달리 **구조체 필드**의 `#{inline}`은 **실제 효과**가 있습니다. 해당 필드가  
**값으로 인라인**되어 호스트 구조체 안에 저장될지(`%pt`), 아니면 **포인터**(`ptr`)로 저장될지를 직접 결정합니다.

```no
pt {
    x i64
    y i64
}

holder {
    inl pt #{inline=true}; 按值：結構體直接長在 holder 裡
    out pt #{inline=false}; 指標：欄位存的是指向 pt 的指標
    bare pt #{inline}; 簡寫，等於 inline=true
}
```

| 표기 | 필드 레이아웃 |
| ---------------------------------------------- | --------------------------- |
| `#{inline}` / `#{inline=true}` / `#{inline=1}` | 호스트 내부에 **값으로** 인라인(`%pt`) |
| `#{inline=false}` / `#{inline=0}` | **포인터**(`ptr`) |
| 표기하지 않음 | `NOLANG_FIELD_PTR`에 따라 결정(아래 표 참조) |
| `#{inline=foo}` / `#{inline='true'}` | **컴파일 오류**—불리언이 아님 |

**애노테이션이 없을 때의 기본 레이아웃은 `NOLANG_FIELD_PTR`가 결정합니다.** `mir.FieldPtrLayout`은  
`os.Getenv("NOLANG_FIELD_PTR") != ""`과 같으며, **기본값은 꺼짐**입니다. 켜면 "1단계 레이아웃 뒤집기"가 시작되어  
구조체 필드의 기본값을 값에서 포인터로 바꿉니다.

| 필드 | 플래그 꺼짐(기본) | 플래그 켜짐(`NOLANG_FIELD_PTR=1`) |
| ------------------------------ | --------- | ------------------------- |
| 애노테이션 없음 | `%pt`(값) | `ptr`(포인터) |
| `#{inline}` / `#{inline=true}` | `%pt` | `%pt` |
| `#{inline=false}` | `ptr` | `ptr` |

즉, **애노테이션은 항상 적용되며 이 환경 변수의 영향을 받지 않습니다**. 플래그는 "애노테이션이 없을 때"의 기본값만 바꿉니다. 따라서  
기본 설정에서 `#{inline=false}`는 "포인터를 명시적으로 요청"이고, `#{inline=true}`는  
원래 그런 레이아웃을 한 번 더 명시한 것일 뿐입니다. 뒤집기가 켜지면 둘의 역할이 서로 바뀝니다.

검사기에 두 가지 규칙이 있습니다(TraceID `fieldtag1`, `ValidateFieldTags`):

1. **구조체 타입의 필드에만 의미가 있습니다.** 스칼라 / `str` / `vec` / 배열 / 슬라이스 / map / option /  
   포인터 필드는 원래 항상 값으로 저장되므로 `#{inline}`을 쓰는 것은 아무 말도 하지 않은 것과 같아 오류가 납니다. 다음도  
   `#{inline=false}`도 컴파일러 동작과 반대되는 레이아웃을 선언하는 것이므로 마찬가지로 오류입니다.
2. **값 인라인은 순환을 만들 수 없습니다.** 인라인된 구조체는 호스트 **내부**에 저장되므로  
   `a { #{inline} b b }`와 `b { #{inline} a a }`가 함께 있으면 크기가 무한해지므로 오류여야 합니다(직접 자기  
   참조는 퇴화 사례). `=true`일 때만 값 간선이 생기므로, 서로 재귀적인 구조체는 **양쪽 모두  
   `#{inline=false}`를 쓸 때** 합법입니다.
   > ⚠️ **"애노테이션을 쓰지 않는 것"이 "inline을 쓰지 않는 것"과 같지 않습니다.** 기본 설정에서는 애노테이션을 쓰지 않으면 값 인라인이므로,  
   > `a { x b }`와 `b { y a }`(모두 애노테이션 없음)는 **기본 설정에서 합법이 아니며**,  
   > `opt: error: identified structure type 'b' is recursive`로 실패합니다—그리고 이 오류는 현재  
   > 검사기가 **보고하지 않고** LLVM 검증 단계에서 터집니다. 기본 설정에서 재귀 타입을 쓰려면 **반드시  
   > `#{inline=false}`를 명시해야 합니다. `NOLANG_FIELD_PTR=1`일 때만 "쓰지 않음"이 포인터를 뜻합니다.

#### 재귀 타입: `inline=false`가 필요한 이유

자신을 값으로 인라인하는 구조체는 크기가 무한하므로 **자기 참조**를 값으로 저장할 수 없습니다. 기본 설정  
(`NOLANG_FIELD_PTR` 꺼짐)에서 구조체 필드는 기본적으로 값이므로, `node`가 자기를 참조하려면  
포인터를 명시적으로 요청하는 것뿐입니다:

```no
node {
    v i64
    next node #{inline=false}; 指標：這樣 node 才有有限大小
}

n node
n.v = 1
n.next.v = 2
print(n.next.v); 2
```

위의 `#{inline=false}`를 빼거나 `#{inline=true}`로 쓰면 LLVM이 이 타입을  
바로 거부합니다: `identified structure type 'node' is recursive`.

포인터 필드는 대상(pointee)을 **소유**하며, 수명 주기는 컴파일러가 처리합니다:

- pointee는 **첫 쓰기 시 지연 할당**됩니다(`@__nolang_get_<T>`, `malloc` + 0 초기화 포함),  
  호스트를 구성할 때 한 번에 할당하는 것이 아닙니다;
- 호스트가 스코프를 벗어날 때 `@__nolang_drop_<T>`가 **null 검사 후 해제**합니다;
- 값 복사(`b = a`, 인자 전달, 컨테이너에 저장)는 pointee를 **깊은 복사**하므로,  
  두 호스트가 같은 메모리를 공유하지 않고 이중 해제도 되지 않습니다.

종단 간 테스트는 `tests/field-inline-annotation.no`를 참조하세요.

### 열거형 값 참조

**규칙: 열거형 값은 `枚舉類型.值` 형태로 한정해 참조해야 하며, 벌거벗은 값을 직접 쓸 수 없습니다.**  
이렇게 하면 이름 충돌을 막고, 외부 패키지가 구체적인 값을 직접 쓰지 못하게 할 수 있습니다.

```no
#{fmt-skip}
; ❌ 錯誤：直接使用裸值
kind = null
yes = e.is(io)
```
```

```no
; ✅ 正確：使用限定方式
kind = json-kind.null
yes = e.is(code.io)
```

> 열거형 타입은 구조체 필드 타입, 함수 매개변수 타입, 반환 타입에 쓸 수 있습니다.  
> 열거형을 정의한 모듈 안과 밖 모두에서 `枚舉類型.值` 방식으로 값을 참조해야 합니다.

## enter/leave

`enter` / `leave` 인터페이스를 구현한 타입은 스코프에 진입하고 벗어날 때 자동으로 호출됩니다:

```no
file enter, leave {
    path str
}

file.enter = () {
    .open()
}

file.leave = () {
    .close()
}

read-file = () {

    ; 自動 f.enter()
    f = file {
        path: 'data.txt'
    }

    ; 使用 f
    ; 自動 f.leave()
    read(f)
}
```

### null 허용 타입(option)

타입 앞에 `?`를 붙이면 null 허용 타입입니다:

null 허용 타입 변수는 null 값/오류 값을 합법적으로 가질 수 있고, 컴파일러가 그에 맞는 null 검사를 수행합니다.

`?t`는 내장 태그 열거형이며, 변형은 `src/std/global.no`에 정의되어 있습니다:

```no
#{buildin}
option {
    ok(v t),
    nil,
    err(e err.err),
}
; tag 0：有值
; tag 1：空值
; tag 2：錯誤（std 結構化錯誤 err.err）
```

`err` 변형의 페이로드는 **`str`가 아니라** `std/err`의 `err` 구조체(`code` / `msg` / `file` / `line` / `col`)입니다.
`err('msg', code)`는 `err.new('msg', code)`의 별칭 생성자입니다. 오류 코드 `code`는 **필수** 매개변수이며
(매개변수 기본값은 언어에서 제거됨), 구체적인 오류 코드가 없으면 `code.unknown`을 명시적으로 전달합니다;
위치 필드는 컴파일러가 생성 지점에서 자동으로 주입합니다. 매개변수를 하나만 쓰는 `err('msg')`는 이 별칭이 아니라
option의 `err` 변형 생성자입니다(아래 참조).

`#{buildin}`은 기본 표현과 생성이 내장 런타임에서 제공됨을 뜻합니다(`%option` 타입, `ok(...)`/`nil`/`err(...)`  
생성자). `option`의 열거형 선언은 매치와 망라성 검사에만 쓰입니다. 자세한 내용은 "태그 열거형"과 "내장 태그 열거형"을 참조하세요.

#### 메모리 레이아웃

`?T`는 **페이로드에 따라 타입이 정해집니다**. 각 페이로드 타입마다 LLVM 타입이 하나씩 있고, 이름은 페이로드 타입에서 유도되므로(단사 대응)
"페이로드 타입이 같으면 ⇒ 레이아웃도 같습니다". `?i32` / `?i64` / `?bool`은 같은 타입을 공유합니다:

```llvm
%option_<key> = type { i8 tag, [K x i64] payload }   ; 內聯
%option_<key> = type { i8 tag, [1 x i64] payload }   ; 裝箱（payload 存 i8* 指標）
```

- `tag`는 항상 **1바이트**입니다. `option`은 변형이 3개(`0=ok`, `1=nil`, `2=err`)뿐이어서
  "`<= 256`개 변형 → `i8`" 구간에 해당합니다. 열거형의 tag 너비 규칙은 〈메모리 레이아웃(스택 방식)〉을 참조하세요.
- 태그 다음에는 **정렬 패딩**이 옵니다(1바이트 태그 → 7바이트 패딩), 그다음이 페이로드입니다.
- 페이로드 크기 `K`는 `T`의 실제 크기로 정해지고 8의 배수로 올림됩니다. **고정 슬롯이 아닙니다**:
  `?i64`는 16바이트(8 + 8), `?str`은 24바이트(8 + 16), `?txt`는 264바이트(8 + 256)입니다.
- 임계값을 넘는 페이로드는 **힙 박싱**으로 바뀝니다. `payload`에는 8바이트 포인터 하나만 들어가고 option 전체는 16바이트입니다.

임계값 `option-payload-inline-threshold`는 **option 구조체 전체**의 바이트 수로 셉니다(기본값 **264** = 1바이트 태그 +
7바이트 패딩 + 256바이트 페이로드, 최소 **16**). 페이로드 인라인 조건은
`8 + roundUp8(sizeof(T)) <= 門檻`입니다. 따라서 기본값은 "페이로드가 256바이트 이하이면 인라인"이고, `?txt`
(256바이트 인라인 버퍼)는 정확히 경계 안에 들어옵니다.

| `?T`의 `T` | 인라인? | `%option_<key>` 크기 |
| --- | --- | --- |
| `i64` / `i32` / `bool` / `char` / `f64` / 포인터 | 예 | 16바이트 |
| `str` / `[]T` / `vec`(16바이트 디스크립터) | 예 | 24바이트 |
| `txt`(256바이트 인라인 버퍼) | 예 | 264바이트(기본 상한에 정확히 도달) |
| 크기 > 256바이트인 구조체 / 배열 | 아니오 | 16바이트(페이로드가 힙에 있음) |
| 자기 참조 페이로드(`node { next ?node }`) | 아니오 | 16바이트(자기 참조는 포인터로만 끊을 수 있음) |

> **`err`의 페이로드는 항상 박싱됩니다**: `err` 변형에는 `std/err`의 `err` 구조체 포인터가 들어가므로 위
> 페이로드 예산을 차지하지 않습니다. 따라서 `?str`은 `ok`일 때 24바이트 인라인 문자열이고, `err`일 때도 같은 24바이트
> 구조체입니다—다만 `payload`의 그 워드에는 오류 객체의 포인터가 들어갑니다. 이 규칙 덕분에 "같은 `?T` 타입,
> 두 변형, 두 종류의 페이로드"가 추가 공간 없이 가능합니다.

> **인라인과 박싱은 "어디에 두는지"만 바꾸고 소유권은 바꾸지 않습니다**: 두 경로 모두 **복사**가 일어날 때
> 구조체 페이로드의 힙 부분을 새로 만듭니다(포인터 필드는 재귀적으로, 인라인으로 소유한 `str` / `[]T` 버퍼는 복제). 따라서 `?T`의 값 의미는
> 인라인 여부와 무관합니다. 같은 프로그램은 어떤 `option-payload-inline-threshold`에서도 출력이 완전히 같아야 합니다.
> 임계값 하나 차이로 동작이 바뀐다면 그것은 컴파일러 결함이지 기능이 아닙니다. (순수 이동 대입은 복제하지 않고 option이
> 원본의 힙을 넘겨받습니다.)

> 레이아웃의 유일한 출처는 `src/mir/layout.go`입니다. `optLayoutOfPayload`가 `K`와 박싱 여부를 정하고,
> `optionPayloadOffset`(8)은 페이로드의 고정 바이트 오프셋입니다. `hir2mir`가 모듈 수준 `?T` 상수를 접고
> codegen이 읽기/쓰기를 발행할 때 모두 같은 함수를 묻습니다.

#### `?=`의 페이로드 간 상위 전파

`?=`는 먼저 "오른쪽 값 사슬의 **뿌리**에 있는 option"을 결과 매개변수에 복사해 `nil` / `err`가 바로 위로 전파되게 하고,
성공 경로는 `ok` 암이 덮어씁니다:

```no
pick = (p pool) (out ?i64) {
    out ?= p.nodes[0].kind; 根是 ?node，結果槽是 ?i64
}
```

따라서 양쪽의 페이로드 타입은 **달라도 됩니다**. 이는 실제 ABI 경계입니다(`?node` 112바이트, `?i64` 16바이트),
같은 레이아웃의 두 가지 표기가 아닙니다. 타입을 넘어 전달할 수 있는 것은 두 가지뿐입니다:

- `tag`—각 option의 0번째 바이트;
- `err`—`err` 변형은 option의 속성으로 페이로드와 무관하며 항상 박싱되므로,
  양쪽 모두 페이로드 영역 0번째 워드에 8바이트 박스 포인터가 들어갑니다(박스는 **복사**되고 공유되지 않습니다. 양쪽 모두 drop하기 때문).

`ok` 페이로드는 **타입 간에 옮겨가지 않습니다**. 대상의 페이로드 영역을 먼저 0으로 지우고, 성공 값은 항상 `ok` 암이 다시 씁니다.
구현은 `@__nolang_opt_prop_<dst>__<src>`(`src/mir/codegen.go`의 `optPropagateState`)에 있으며,
`?=`처럼 컴파일러가 생성한 상위 전파 대입에서만 등장합니다.

```no
o ?i64
o = nil; 設為空
o = 42; 設為有值
o = err('msg'); 設為錯誤

nullableValue ?[]str
nullableString ?str

; 修改可空類型
nullableString = 'test'

; 設置錯誤
nullableString = err('some error')

; 可通過match判斷
x: {
    err -> log(it.msg()); it 是 err.err，訊息靠 .msg()

    nil -> log('nil')

    -> do-right-thing(it)
}

; 強制解包
; 取消實現
; !x.say()
```

### 스타일 지침: (val, ok) 대신 ?t option 사용하기

함수가 실패하거나 빈 값을 반환할 수 있다면 **`?t` option 타입을 우선 사용**해야 합니다. `(val t, ok bool)` 두 반환값 패턴보다 낫습니다.

`?t`는 태그 열거형으로 세 가지 상태가 있습니다: `ok`(값 있음), `nil`(빈 값), `err`(오류). 정상 값은 묵시적으로 바인딩되고, 값을 찾지 못했을 때는 `nil`, 실제 오류가 발생했을 때는 `err(...)`를 씁니다.

```no
#{fmt-skip}
; ❌ 不推薦：雙返回值模式
stack.pop = () (val i64, ok bool) {
    .n == 0 -> return
    val = .data[.n]
    ok = true
}
```
```

```no
; ✅ 推薦：option 類型（nil 表示空，err 表示錯誤）
stack.pop = () (val ?i64) {
    .n == 0 -> {
        val = nil
        return
    }
    val = .data[.n]
}

; ✅ 返回錯誤
file.read = () (data ?str) {
    .fd < 0 -> {
        data = err('file not open')
        return
    }

    ; ... 讀取資料
    data = buf
}
```

match로 option을 언패킹합니다:

```no
val = s.pop()
val: {
    nil -> print('empty')

    err -> print(it.msg()); it = 結構化錯誤 err.err

    -> print(it); it = 彈出的值
}
```

## 정수 연산 오버플로(`#{overflow}` 애노테이션)

Nolang은 panic을 지원하지 않습니다. 오버플로가 가능한 모든 연산은 `option`이나 명시적 애노테이션으로 처리해야 하며, 런타임에 정수 오버플로 예외가 던져지는 일은 절대 없습니다. 다음 **정수 사칙 연산**의 오버플로 동작은 `#{overflow = ...}` 애노테이션이 제어합니다:

- 부호 있는/없는 **`+` `-` `*`**: 좌우 피연산자가 정수(`int` 리터럴 포함)이면 모두 적용됩니다;
- 부호 있는 **`/`**: `INT_MIN / -1` 한 가지 경우만 오버플로합니다(부호 없는 나눗셈 `a/b ≤ a`는 절대 오버플로하지 않으므로 해당 없음).

> 부호 없는 정수(`u8`/`u16`/`u32`/`u64`/`u128`)의 `+ - *`는 부호 있는 정수와 **완전히 같은 규칙**을 따릅니다. 애노테이션이 없으면 마찬가지로 기본값으로 `option<int>`를 반환하고, 오버플로 시 `err`가 됩니다. 이는 설계상 의도된 선택입니다—"컴파일 타임에 오버플로 불가능을 증명할 수 없는 한 같은 규칙으로 처리한다".

### 특례: `byte`와 `char` 산술

`byte`와 `char`는 오버플로 의미의 **특례**입니다. 이들의 산술은 **option을 만들지 않고** `#{overflow}` 애노테이션의 적용 대상도 아닙니다.

- **`byte`(u8)**: `+ - *`가 오버플로하면 **암묵적으로 2의 보수 랩어라운드**합니다(`250 + 10` → `4`, `0 - 1` → `255`). `byte`는 바이트 버퍼, hex 인코딩/디코딩처럼 "랩어라운드를 자연스럽게 허용하는" 상황을 위해 만들어졌으며, 해시/카운터의 `#{overflow = wrap}`과 같은 의미입니다. 다만 내장이므로 애노테이션이 필요 없습니다.
- **`char`(Unicode 코드 포인트)**: `+ -`는 **코드 포인트 산술**이며, 결과가 올바른 코드 포인트 범위(`< 0` 또는 `> 0x10FFFF`)를 벗어나면 **`-1`**(유효하지 않은 코드 포인트 센티넬)이 됩니다. `err`도 아니고 랩어라운드도 하지 않습니다.

**설계 이유**: `i8`–`i128` / `u8`–`u128`는 일반적으로 **실제 업무 수치**(금액, 개수, 용량)에 쓰이는데, 암묵적 랩어라운드는 오버플로 버그를 숨기므로 기본값을 `err`로 두고 명시적 선택을 강제합니다. 반면 `byte` / `char`의 전형적 용도(바이트 스트림, 코드 포인트 순회)는 의미상 랩어라운드를 자연스럽게 허용하며(오히려 기대하기까지 합니다), option으로 만들면 언패킹 노이즈만 늘어납니다. `byte` / `char` 연산의 오버플로를 검사해야 한다면 먼저 더 넓은 타입(예: `b.to-i64()`)으로 변환한 뒤 계산하세요.

| 모드 | 애노테이션 | 오버플로 시 | 결과 타입 | 적용 상황 |
| ----------- | ------------------------ | --------------------------- | ------ | ------------------ |
| **기본값(애노테이션 없음)** | — | 오버플로 → `err`, 정상 → `ok(value)` | `?int` | 오버플로를 검사해야 하는 연산 |
| **랩어라운드** | `#{overflow = wrap}` | 암묵적 2의 보수 랩어라운드 | `?int` | 해시, 암호, 카운터 등 의미상 랩어라운드를 허용하는 경우 |
| **0으로 만들기** | `#{overflow = clamp0}` | 오버플로(오버플로 또는 언더플로) 시 `0` | `?int` | 차이가 음수가 되어서는 안 되는 의미(잔량 등) |
| **최솟값 클램프** | `#{overflow = min}` | 오버플로 시 타입 최솟값으로 클램프 | `?int` | 카운터 하한, 인덱스 보호 |
| **최댓값 클램프** | `#{overflow = max}` | 오버플로 시 타입 최댓값으로 클램프 | `?int` | 용량 상한, 포화 누적 |
| **포화** | `#{overflow = saturate}` | 오버플로 → 최댓값, 언더플로 → 최솟값 | `?int` | 신호/색상 포화 등 |

> ⚠️ **애노테이션은 언패킹하지 않습니다**(D1): `#{overflow = …}`은 **"실패 시 값을 어떻게 얻을지"만 결정합니다**.
> 결과 타입은 항상 `?T`입니다. 결과를 plain으로 되돌리려면 match나 `?=`로 소비해야 합니다. 두 소비 형태
> (`?=` + 블록 match / 값 위치 match)의 차이와 선택은 〈블록 match와 값 위치 match의 선택〉을 참조하세요.
> plain 타입으로 명시적으로 표기하는 것(`w i64 = a - b  #{overflow=wrap}`)은 **탈출구가 아닙니다**—
> 실제로는 여전히 `15w45dqk`(cannot assign `?i8` value to `i8` variable)이 보고됩니다.

또한 모든 모드는 **타입 접두사 형태**를 지원하여 특정 좁은 타입의 포화 경계를 정확히 지정할 수 있습니다. 예: `#{overflow = u8-max}`, `#{overflow = i8-min}`, `#{overflow = u16-saturate}`.

> **애노테이션 단위**: `#{overflow = ...}`는 **행 애노테이션**입니다—**바로 다음 문장에만** 작용합니다.
> 이는 **설계상 유일하게 허용되는** 형태입니다(남용 방지). 실행 의미(codegen)와 `ovfhndld` 하드 오류 모두 이를 인식합니다.
> 또한 이는 "오버플로 시 값 얻기"만 바꾸고 타입은 바꾸지 않습니다. 블록 수준이나 함수 수준으로 넓히면 넓은 범위의 연산 의미가 멀리 떨어진 한 줄의
> 애노테이션에 결정되게 됩니다. 이유는 [〈애노테이션과 주석의 스코프〉](annotation-scope.md) §4.1을 참조하세요.
>
> ⛔ **함수 정의 위, 블록 머리, 파일 머리에 두는 것은 불법입니다**. 현재 유일한 허점은 함수 수준 애노테이션이
> `ovf-int-default` lint가 함수 전체를 건너뛰게 한다는 것입니다(목록이 "깨끗해" 보임). 함수 본문의 애노테이션 없는 연산은 그대로
> `ovfhndld`를 발생시킵니다. 블록 수준 애노테이션은 lint가 아래로 상속해 조용해지게 하지만 codegen은 전혀 인식하지 않습니다. 문장마다 애노테이션을 붙이세요.
> `no fmt --fix=overflow`가 생성하는 것도 바로 이 문장 단위 형태입니다.
>
> 전체 모델(L0 모듈 / L1 선언 / L2 블록 / L3 단행, 그리고 어떤 키가 어떤 계층을 지원하는지)은
> [〈애노테이션과 주석의 스코프〉](annotation-scope.md)을 참조하세요. 해당 페이지 §7은 기존 항목과 허점을, §8은 강화 순서를 다룹니다.

> **LSP 빠른 수정**: 편집기(nolang-lsp)는 애노테이션 없는 정수 연산에 **힌트**(`nolang-overflow`, trace id `ovfhndld`)를 보고하고 다섯 가지 quickfix—**Add `#{overflow = wrap}`** / **`clamp0`** / **`min`** / **`max`** / **`saturate`**—를 제공합니다. 해당 연산이 있는 문장 위에 그 줄과 같은 들여쓰기로 애노테이션을 자동 삽입해 오버플로 동작을 지정합니다(결과는 여전히 `?T`이며, 별도로 match / `?=`로 소비해야 합니다). 명령줄 동등 명령은 `no fmt --fix=overflow`입니다(아래 참조).

### 기본값: `option<int>` 반환

애노테이션이 없으면 `a - b`의 결과 타입은 `option<int>`입니다. 받는 쪽은 `?T`(null 허용 타입)여야 하며, match로 `err` / `nil` / `ok` 세 분기를 분해해야 합니다:

```nolang
main = () {
    x i64 = 100
    d ?i64 = x - 1; 默認：返回 option<i64>
    d: {
        err -> print(-1); 溢出（如 x - 2^63 下溢）

        nil -> print(0)

        -> print(1); ok(value)：正常結果
    }
}
main()
```

> `%option`의 `data` 필드는 `i64`입니다. 좁은 타입(`i8`/`i16`/`i32`)의 결과는 먼저 부호 확장(sext)되어 저장되고, 언패킹 시 원래 너비로 잘립니다.

### wrap: 암묵적 랩어라운드

```nolang
#{overflow=wrap}
sub-wrap = (a i64, b i64) (r i64) {
    r = a - b; 溢出時靜默 2's 補數回繞；r 是 plain i64（顯式型別）
}
```

문장 수준:

```nolang
x i64 = -9223372036854775807

#{overflow=wrap}
w i64 = x - 2; 下溢回繞 → 9223372036854775807
print(w)
```

### clamp0: 오버플로 시 0으로 만들기

```nolang
x i64 = -9223372036854775807

#{overflow=clamp0}
c i64 = x - 2; 下溢 → 0（上溢同樣歸零）
print(c)
```

### min / max / saturate: 포화 클램프

세 모드는 오버플로 결과를 랩어라운드나 0 만들기가 아니라 타입이 표현할 수 있는 구간 안에 "가둡니다":

```nolang
#{overflow=min}
floor = (a i64, b i64) (r i64) {
    r = a - b; 下溢 → i64 最小值；上溢 → i64 最大值
}

#{overflow=max}
cap = (a i64, b i64) (r i64) {
    r = a * b; 上溢 → i64 最大值；下溢 → i64 最小值
}

#{overflow=saturate}
sat = (a i64, b i64) (r i64) {
    r = a + b; 上溢→max、下溢→min
}
```

타입 접두사 형태로 좁은 타입의 포화 경계를 정확히 제어할 수 있습니다(함수 수준 애노테이션은 본문의 모든 해당 타입 연산에 적용됩니다):

```nolang
#{overflow=max}
inc = (x u8) (r u8) {
    r = x + 1; x = 255 時上溢 → 255（而非回繞成 0）
}

#{overflow=min}
dec = (x i8) (r i8) {
    r = x - 1; x = -128 時下溢 → -128（而非回繞成 127）
}
```

### 컴파일러 강제

애노테이션 없는 정수 연산은 기본적으로 `option<int>`를 반환하므로 "미처리"가 강제로 걸러집니다. **미처리 여부는 병렬로 판단**합니다. 다음 중 하나라도 만족하면 오류가 나지 않습니다:

- **`?=` 상위 전파**(함수에 option 결과 매개변수가 있어야 함);
- **제자리 캡처**: `=`로 **새** 변수에 바인딩하면(변수가 `?T`로 자동 추론됨), 또는 `?T`를 명시적으로 선언하면(`x ?i64 = a + b` 같은 형태) 해당됩니다;
- **`_ = expr` 명시적 버리기**(평가 자체는 안전 경로를 타고, 오류도 함께 무시됩니다);
- **애노테이션 추가**: `#{overflow = wrap}` / `clamp0` / `min` / `max` / `saturate`(또는 `u8-max`, `i8-min` 같은 타입 접두사 형태)로 랩어라운드/포화 의미를 받아들인다고 선언합니다.

네 가지 모두 해당하지 않을 때만 오류가 납니다(`ovfhndld`).

> **순수 산술은 오류 원천이 아닙니다**: `+ - * <<`와 단항 마이너스 자체는 캡처를 유발하지 않습니다(그러면 모든 산술이 option이 되어 표준 라이브러리가 폭발합니다). 따라서 `d = x - 1`(`/` `%` 없음, 안전 인덱싱 없음, option 피연산자 없음)은 여전히 오류입니다—애노테이션을 추가하거나 `d ?i64 = x - 1`로 쓰세요.
>
> **기존 변수는 타입이 바뀌지 않습니다**: 캡처는 "이 문장에서 처음 선언된" 대상에만 적용됩니다. 변수가 이미 있다면(예: `d = 0` 다음 `d = x - 1`, 또는 `v i64 = 0` 다음 `v = arr[i]`) 컴파일러는 이를 제자리에서 option으로 바꾸지 않고, 의미를 명시적으로 선택하라고 오류를 냅니다.

위 면제 규칙의 영향을 받지 않는 하드 오류가 두 가지 더 있습니다:

- 애노테이션 없는 정수 연산을 **명시적 plain `int`** 변수에 대입하면 컴파일러가 오류(`cannot assign ?i64 value to i64 variable`)를 내며, `#{overflow = wrap}` / `#{overflow = clamp0}` / `#{overflow = min}` / `#{overflow = max}` / `#{overflow = saturate}`(또는 타입 접두사 형태)를 추가하거나 명명된 `?T`를 쓰도록 강제합니다.
- 애노테이션 없는 정수 연산을 **이미 존재하며** 타입이 option이 아닌 변수(`d = 0` 다음의 `d = x - 1`)에 대입하면 컴파일러가 오류를 내고 애노테이션 추가나 `?i64` 선언을 안내합니다. 잘못된 IR이 생기는 것을 막기 위해서입니다.

그 밖의 규칙:

- 부호 없는 정수 연산(`u8`/`u16`/`u32`/`u64`/`u128`)도 **동일하게 적용**됩니다. 애노테이션이 없으면 `+ - *`가 기본적으로 `option<int>`를 반환하고 오버플로 시 `err`가 되며, 부호 있는 정수 규칙과 같습니다.
- `i128` 연산은 `option` 경로를 지원하지 않습니다(data 필드가 `i64`뿐). 정확성을 보존하기 위해 모두 암묵적 랩어라운드로 퇴화합니다.

> **왜 기본값이 wrap이 아니라 option인가?** 암묵적 랩어라운드는 오버플로 버그를 숨깁니다. 기본적으로 `option`을 반환하면 호출자가 오버플로를 명시적으로 처리하도록 강제되고(또는 `wrap`을 직접 표기해 "랩어라운드를 받아들인다"는 뜻을 밝힐 수 있고), "오버플로를 허용할지"가 보이는 설계 결정이 됩니다.

### 0으로 나누기(division by zero)

정수 `/`와 `%`의 제수가 `0`인 것은 **미정의 동작(UB)**이며, 오버플로와는 **별개의 문제**입니다. 어떤 애노테이션도 이를 면제할 수 없습니다:

- **컴파일 타임에 판별 가능**: 제수가 **리터럴 상수 0**(`10 / 0`, `a % 0`, `x / 0`)이면 ⇒ **하드 오류**(trace id `div-by-zero`). `#{overflow = wrap}`은 이를 면제하지 않습니다(그 애노테이션은 오버플로를 다루며, 0으로 나누기가 아님).
- **런타임에만 알 수 있음**: 제수가 변수/외부 입력에서 오면 ⇒ 컴파일러가 **두 경로 모두에 0 검사를 삽입**하며, 차이는 "어떻게 보고하느냐"뿐입니다:

| 결과 타입 | 발생 조건 | 제수가 0일 때 |
| ----------- | ----------------------- | ------------------------------------------------------------------------------ |
| `?int`(기본값) | 문장에 애노테이션 없음 | option tag = `err`, `?=` / match로 처리 |
| plain `int` | 문장에 `#{overflow = ...}` 있음 | 결과를 `0`으로 강제하고 **stderr**에 `nolang: integer division or remainder by zero ...` 출력 |

```nolang
safe = (a i64, b i64) (r ?i64) {
    r = a / b; b == 0 → err（呼叫方必須處理）
}

#{overflow=wrap}
fast = (a i64, b i64) (r i64) {
    r = a / b; b == 0 → 0 並印一行 stderr 診斷（不再是裸 sdiv 的 UB）
}
```

> **왜 `#{overflow = wrap}`이 0 나눗셈 가드를 면제할 수 없는가**: 이는 **오버플로 동작**(결과 타입은 여전히 `?int`)을 바꿀 뿐, 제수의 안전성은 바꾸지 않습니다. 면제한다면 컴파일러가 벌거벗은 `sdiv`를 내보내고 최적화기가 제수가 절대 0이 아니라고 가정할 권한을 얻어(`a / 0`을 임의의 값으로 접음), x86-64의 `idiv`는 #DE로 바로 충돌합니다—UB이면서 진단도 없습니다. 따라서 zero-divisor 가드는 **애노테이션과 독립적으로** 존재합니다. plain 경로가 stderr 한 줄을 더 출력하는 이유도 그 경로에는 호출자가 검사할 option이 없기 때문입니다.
>
> **같은 가드가 `sdiv (INT_MIN, -1)`도 덮습니다**(결과가 표현 불가능하며 역시 UB; x86-64에서는 SIGFPE 발생). option 경로는 이를 `err`에 합치고, plain 경로는 2의 보수 랩어라운드 값을 취합니다(`INT_MIN / -1 → INT_MIN`, `INT_MIN % -1 → 0`).

부동소수점 나눗셈은 대상이 아닙니다. `1.0 / 0.0`은 IEEE-754에 따라 `inf` / `nan`으로 정의되며 UB가 아닙니다.

### 애노테이션 없는 연산을 오류로 간주(`ovf-int-default`)

`no vet`는 **애노테이션 없는** 정수 연산을 **힌트**(trace id `ovfhndld`, HINT)로 보고합니다. 이유: 기본 `?T`가 사용자에게 보이지 않으므로 알려야 하기 때문입니다. `#{overflow = ...}`로 오버플로 동작을 지정하거나 `?T` + `?=` / match / 명시적 plain 타입으로 소비할 수 있습니다. 실제로 빌드를 막아야 하는 것은 `optunuse`(option이 상위 전파도 언패킹도 되지 않음)입니다.

### 자동 수정: `no fmt --fix=overflow`

일괄로 애노테이션을 추가할 때 일일이 쓸 필요 없이 `no fmt`의 수정 범주 매개변수를 쓰세요:

```bash
no fmt --fix=overflow -w src/std          # 就地修復整個目錄
no fmt --fix=overflow -d src/std/str.no   # 只印 diff，不寫檔
no fmt --fix=overflow src/std/str.no      # 印出修復後的內容
```

수정은 **정확하고 오염되지 않습니다**. lint가 실제로 보고한 연산이 있는 문장 위에만 `#{overflow=wrap}`을 삽입하고, 다른 문장은 건드리지 않으며, 재배열하지 않고, 기존 애노테이션도 건드리지 않습니다. 다시 실행해도 멱등합니다(이미 표기된 것은 더 바뀌지 않음). `no fmt -w`를 직접 실행하는 것과 다릅니다. 후자는 전체 재포맷입니다.

> 수정 후 `no vet`를 한 번 더 실행해 0이 되었는지 확인하세요. 대부분 한 번에 비워집니다(`src/std`가 4728건에서 0건으로 감소). 알려진 유일한 예외 형태: 보고가 match arm의 **조건**에 떨어졌는데 그 arm 본문에는 표기할 문장이 없는 경우—행 애노테이션은 바로 다음 문장에만 작용하므로 arm 자체의 조건 연산을 덮지 못하고, 이때 `no vet`가 다시 보고합니다. 이런 경우에는 먼저 해당 연산을 독립 문장으로 뽑아낸 뒤 표기하세요.

### 자동 수정: 중복 타입 표기

변수 선언의 **타입 표기가 오른쪽 값에서 추론된 타입과 완전히 같을** 때 그 표기는 중복입니다(`no vet`가 hint `tcpoxtfd`, `type annotation '<T>' can be omitted (inferred from value)`로 보고합니다).

- **기본 `no fmt`가 자동 제거**: `no fmt -w`는 포맷하면서 중복 표기도 함께 제거합니다(일반 재포맷도 수행). `no fmt -d`는 이 변경을 포함한 미리보기이고, `-w`는 기록합니다.

```bash
no fmt -w main.no          # 格式化並去掉冗餘標註
no fmt -d main.no          # 只印 diff（含標註移除）
no fmt -w src/             # 整個目錄
```

- **`--fix=redundant`(수술적, 표기만 변경)**: 중복 표기만 제거하고 전체 재포맷은 원하지 않을 때(예: `src/std`가 `no fmt`을 잃어버리는 `#{index-out}`) 쓰세요. 표기만 삭제하고 재배열하지 않습니다:

```bash
no fmt --fix=redundant -w src/std          # 就地移除整個目錄的冗餘標註（不重排版）
no fmt --fix=redundant -d src/std/str.no   # 只印 diff，不寫檔
no fmt --fix=redundant src/std/str.no      # 印出修復後的內容
```

```nolang
; 修復前
x str = ''
b i64 = 5
m [str]i64 = make-map()

; 修復後（標註 == 推斷型別，去掉）
x = ''
b = 5
m = make-map()
```

규칙 요점:

- **표기 타입 == 추론 타입**일 때만 제거합니다(`str`/`i64`/`[str]i64`가 추론 값과 일치할 때 등).
- **암묵 변환은 가능하지만 같지 않은** 경우에는 **제거하지 않습니다**. 변환 의미를 남기려면 표기가 필요합니다. 예: `c i16 = 5`(`5`는 `i64`로 추론되어 `i16`과 다름), `p ?i64 = nil`, `last txt = ''`(`txt`와 `str`은 암묵 상호 변환되지만 타입이 다름).
- **타입 표기가 없는** 표현(`d = 'x'` 등)은 애초에 보고되지 않으므로 변경되지도 않습니다.
- **고정 길이 배열 표기 `[N]T` / `[?]T`는 항상 유지**합니다(절대 중복으로 보지 않음). `[N]`은 단순한 타입 힌트가 아니라 **표현 형태**를 결정하는 스위치입니다. 쓰면 오른쪽 `[...]` 리터럴이 고정 길이 스택 배열로 해석되고, 쓰면 추론 결과가 표기와 "정확히 같아"집니다—표기가 만들어낸 순환 논증입니다. 지우면 같은 줄이 다시 해석되어 힙에 증가 가능한 슬라이스 `[]T`가 되고 의미가 바뀝니다. `fixed [3]char = ["x", "y", "z"]`의 `.push()`는 무효(`.len()`이 항상 3)인데, `fixed = ["x", "y", "z"]`로 퇴화하면 `.push()`가 `.len()`을 4로 만듭니다. 슬라이스 표기 `[]T`는 여기에 해당하지 않습니다—지워도 슬라이스로 남아 진짜 중복입니다.
- **16진수 리터럴을 포함한 값은 항상 표기를 유지**합니다(보수적 예외). `no vet`의 타입 추론은 `0xNN`에 대해 "`byte`로 추론"하는 휴리스틱을 쓰는데, 이는 컴파일러의 "표기가 없으면 정수 리터럴은 기본값 `i64`"라는 실제 의미와 다릅니다. 따라서 `IP-TBL [64]byte = [0x3a, ...]`, `s []byte = [0x50, 0x4b]`가 중복으로 오판됩니다. 제거하면 리터럴이 `i64` 요소로 퇴화해 `expected '[]byte', got '[]i64'` 같은 타입 오류가 생깁니다. 그러므로 값 표현식 텍스트에 `0x` / `0X`가 나타나면 hint도 제거도 일어나지 않습니다.
- **오른쪽 값이 필드 읽기일 때 항상 표기를 유지**합니다(보수적 예외). `i i64 = .pos` 같은 표기는 단순 타입 힌트가 아니라 이후 정수 산술이 `?T`를 만드는지 결정하는 스위치입니다. 필드에서 타입을 추론하도록 바꾸면 `i + N`이 더 이상 "부호 있는 연산"이 아니어서 `?i64`를 반환하지 않고, 2단 언패킹의 `ok` 암이 절대 실행되지 않으며 반복문 카운터가 제자리에서 멈춥니다. 실제 사례: `src/std/yaml.no`의 `parser.looks-like-map-entry`에서 `i64`를 지우면 `yaml.parse('abc')`가 무한 루프에 빠집니다. 따라서 `x = .field`, `x = obj.field`(괄호나 접두사로 감싼 형태 포함)의 표기는 `tcpoxtfd`를 보고하지도 않고, 기본 `no fmt`나 `--fix=redundant`로 삭제되지도 않습니다.

기본 `no fmt`를 쓰든 `--fix=redundant`를 쓰든, 제거는 보고된 그 타입 표기와 앞쪽 공백만 삭제하고 다시 실행해도 멱등합니다(제거된 것은 다시 변하지 않음). 수정 후 `no vet`를 한 번 더 실행해 `tcpoxtfd`가 0인지 확인하세요.

### 자동 수정: option 소비(`--fix=unwrap`)

통합 규칙에서 "option을 만들었지만 한 번도 소비하지 않은 경우"가 빌드를 막아야 하는 유일한 진단(trace `optunuse`)입니다. 이를 명시적 소비 형태로 일괄 변환하려면 `--fix=unwrap`을 쓰세요:

```bash
no fmt --fix=unwrap -w src/std            # 就地修復整個目錄
no fmt --fix=unwrap -d src/std/str.no     # 只印 diff，不寫檔
no fmt --fix=unwrap src/std/str.no        # 印出修復後的內容
```

수정 형태(〈안전 인덱싱〉 참조): **해당 함수에 이미 `?T` 결과 매개변수가 있음** → 상위 전파(`x ?= <expr>`); 그렇지 않으면 → 이름 변경 + match 언패킹:

```nolang
; 修復前
x = a + b

; 修復後（所在函式有 ?T 結果參數）
x ?= a + b

; 修復後（否則，4 行標準形；空兜底臂 = 零值）
x-opt = a + b
x = x-opt: {
    ok -> it

    ->
}
```

다른 fix 범주와 마찬가지로 수술적 텍스트 치환이며, 배열을 바꾸지 않고 문장 위의 `#{overflow=…}` / `#{index-out=…}` 애노테이션을 건드리지 않습니다(그것들은 여전히 "실패 시 값 얻기"를 담당). 다시 실행해도 멱등합니다. 수정 후 `no vet`를 한 번 더 실행해 `optunuse`가 0인지 확인하세요.

### 애노테이션 바인딩과 한 줄 병합

`#{...}` 애노테이션은 **노드에 바인딩**되므로 한 문장에 여러 키를 동시에 붙일 수 있습니다. 여러 애노테이션은 항상 **한 줄로 병합**됩니다:

```nolang
#{fmt-skip}
i <- [0..16): {

    #{index-out=0, overflow=wrap}
    buf[base + i] = data[i]
}
```

위 문장은 "범위 밖 값 기본값 가져오기"(`index-out`)와 "오버플로 랩어라운드"(`overflow`) 두 의미를 동시에 필요로 합니다. 두 줄로 나눠 쓰면 해석 결과는 같지만, `no fmt --fix=overflow`는 병합된 한 줄 형태를 출력합니다.

> **행 애노테이션의 적용 범위**: `#{overflow = ...}`는 **바로 다음 문장에만** 작용합니다. 중간에 무관한 애노테이션이 있어도 해당 문장에 올바르게 적용됩니다. 안전 인덱스 쓰기(`arr[base + i] = v`, `.buf[.pos + i] = v`)는 match 형태로 desugar되는데, `#{overflow = wrap}`은 desugar 이후 노드에도 함께 전달되므로 인덱스 연산식도 애노테이션의 적용을 받아 미표기로 오진되지 않습니다.

### 오류 상위 전파(`?=` 연산자)

`?=`은 option 언패킹 + 오류 상위 전파의 **간편 표기**입니다. **함수가 option을 반환하는 것은 필수 조건이 아닙니다.** 다음 두 경우 중 하나만 해당하면 됩니다,
따라서 반환값이 option이 아닌 함수도 본체를 블록 match로 감싸기만 하면 `y ?= x + 1`을 그대로 쓸 수 있습니다.

**문법:**

```no
v ?= expr
```

**의미:**

- `expr`이 `ok(value)`를 반환하면 `v`에 언패킹된 내부 값이 대입됩니다(자동 언패킹).
- `expr`이 `nil` 또는 `err`를 반환하면:
  - 함수에 `?T` 결과 매개변수가 있으면 → 그 option을 결과 매개변수에 쓰고 즉시 `return`합니다(자동 상위 전파);
  - 문장이 **문장 수준 블록 match** `{ ... }: { ... }` 본문 안에 있으면 → **가장 가까운** 블록 match가 잡아서,
    **본체 전체가 멈추고** arms는 한 번만 실행됩니다(`return`이 **아님**). 함수에 `?T` 결과 매개변수가 필요하지 않습니다.

**사용 조건(둘 중 하나만 해당하면 됨):**

1. 해당 함수에 option 타입 결과 매개변수가 있음;
2. 문장이 문장 수준 블록 match `{ ... }: { ... }`의 본문 안에 있음(〈Match 주어의 세 가지 형태〉 참조).

둘 다 해당하지 않으면 컴파일러가 오류를 냅니다. `err -> _` / `-> _` 두 arm은 상위로 전파된 오류를 제자리에서 삼킬 수 있어, "`?T` 결과 매개변수 없이
간편 표기를 쓰고 싶을 때"의 표준 대안입니다:

```no
handle = (x i64) {
    {
        y ?= x + 1
        print(1)
    }: {
        err -> _

        -> _
    }
}
```

**결과 매개변수는 미리 값을 넣을 필요가 없습니다.** 함수 prologue는 0 초기화를 하지 않지만, return 시 명시적으로 대입되지 않은 출력 매개변수는 자동으로 0으로 채워집니다(정수 → `0`, `str` / 구조체 → 0값, option → `nil`). 따라서 예제에서 `result = nil` 보일러플레이트를 쓰지 않고 성공 경로의 대입만 써도 됩니다.

**예:**

```no
; 逐行讀取檔案並處理 — 使用 ?= 簡化錯誤傳播
process-file = (path str) (result ?str) {
    f ?= open(path); 失敗時自動 result = f; return
    line ?= f.read-line(); EOF 或錯誤時自動上拋
    result = line
}
```

동등한 전개 형태(컴파일러가 자동 생성하는 match 사슬):

```no
#{fmt-skip}
process-file = (path str) (result ?str) {
    result = nil
    __tmp = open(path)
    __tmp: {
        nil || err -> {
            result = __tmp
            return
        }
        -> f = it
    }
    __tmp2 = f.read-line()
    __tmp2: {
        nil || err -> {
            result = __tmp2
            return
        }
        -> line = it
    }
    result = line
}
```

**연쇄 사용:** 여러 `?=`를 연결해 파이프라인 방식의 오류 전파를 구현할 수 있습니다:

```no
pipeline = (input str) (result ?str) {
    a ?= step1(input); 失敗則上拋
    b ?= step2(a); 失敗則上拋
    result = b
}
```

**벌거벗은 산술 연산:** `?=`의 오른쪽은 함수 호출에 한정되지 않습니다. `option`을 반환하는 모든 정수 연산(예: 애노테이션 없는 `a - b`, `a + b`, `a * b`)을 `?=`로 바로 상위 전파하여 오버플로 오류를 처리할 수 있으며, 중간 변수에 먼저 바인딩할 필요가 없습니다:

```no
; 溢出時自動 result = err; return，正常時 v 解包為內部值
sub-safe = (a i64, b i64) (result ?i64) {
    v ?= a - b; 下溢/上溢 → err 自動上拋；否則 v = 內部 i64
    result = v
}

add-safe = (a i64, b i64) (result ?i64) {
    v ?= a + b; 同上，適用於 + * 與有號 /
    result = v
}
```

동등한 전개(컴파일러 자동 생성):

```no
#{fmt-skip}
sub-safe = (a i64, b i64) (result ?i64) {
    result = nil
    __unwrap = a - b            ; option<i64>
    __unwrap: {
        nil -> {
            result = __unwrap
            return
        }
        err -> {
            result = __unwrap
            return
        }
        -> v = it               ; ok(value)：解包內部值
    }
    result = v
}
```

**복합 오른쪽(compound RHS):** `?=`의 오른쪽에는 여러 option 피연산자를 포함한 복합 식이 올 수 있습니다. 각 option 피연산자는 자동으로 언패킹되고 전파 가드가 삽입됩니다. 어떤 피연산자라도 `nil` / `err`이면 현재 함수의 option 결과 매개변수에 그 값이 설정되고 `return`하여 위로 전파됩니다. 모두 성공해야 내부 값이 왼쪽에 대입됩니다:

```no
sum3 = () (result ?i64) {
    a ?i64 = ok(10)
    b ?i64 = ok(20)
    c ?i64 = ok(30)
    total ?= a + b + c; 每個 option 運算元自動解包並傳播
    result = total
}

comp = () (result ?i64) {
    a ?i64 = ok(4)
    b ?i64 = ok(6)
    v ?= dbl(a + b); a + b 可能是 option，同樣自動解包並傳播
    result = v
}
```

> 「피연산자 위치」에 있는 option만 자동으로 언래핑됩니다(예: `a + b + c`, `f(b + c)`). 함수 인수로 직접 전달되는 option 변수는 여기에 해당하지 않습니다——이 경우 `?=`의 기존 '그대로의 option 인수' 면제 규칙을 따릅니다(`a ?= f(v)`. 여기서 `v`는 `?i64`이고 `f`는 plain `i64`를 받습니다).

**option이 아닌 우변은 오류:** `=`를 `?=`로 대량으로 잘못 쓰는 것을 방지하기 위해, 우변이 컴파일 타임에 "명백히 option이 아님"으로 판명될 수 있으면 컴파일러가 오류를 내고 `=`를 사용하라고 안내합니다:

- 리터럴: `v ?= 42`
- 상수 접이가 가능한 정수 연산: `v ?= 10 + 20`
- 타입이 알려져 있고 option이 아닌 지역 변수: `v ?= x`(여기서 `x i64 = 5`)

오류 메시지는 다음과 같은 형식입니다: `` `?=` RHS `42` is not an option — use `=` instead ``.

> 산술 연산은 피연산자 중 어느 하나라도 option이거나(또는 타입을 알 수 없거나 함수 호출이어서 option을 반환할 수 있음) "option 가능"으로 보고 통과시키므로 오류를 잘못 보고하지 않습니다. 예를 들어 `v ?= a + b + c`(a/b/c가 `?i64`)나 `v ?= b + c`(b/c 타입 미지) 모두 정상적으로 컴파일됩니다.

**적용 시나리오:**

- `pop` / `peek` 등 비어 있을 수 있는 컨테이너 연산 → `?t`(`nil` = 비어 있음)
- `read-line` / `read-byte` 등 I/O 연산 → `?str` / `?i64`(`nil` = EOF, `err` = 오류)
- `lookup` / `get` 등 조회 연산 → `?t`(`nil` = 찾지 못함)
- `parse` / `from-str` 등 파싱 연산 → `?t`(`nil` = 비어 있음, `err` = 잘못된 입력)
- `accept` / `dial` 등 네트워크 연결 → `?conn`(`nil` = 연결 없음, `err` = 오류)

**nil vs err:** 결측이 정상적/예상된 결과(빈 스택, 키 없음, EOF)일 때는 `nil`을 사용하고, 결측이 실제 오류 상태(I/O 실패, 잘못된 입력, 연결 거부)를 나타낼 때는 `err('msg')`를 사용합니다.

**예외:** 함수가 여러 개의 독립된 값을 반환해야 할 때(예: `(name str, value str, ok bool)`)는 다중 반환 패턴을 유지할 수 있습니다.

**다중 반환값에는 `?T`가 최대 하나뿐입니다(하드 오류):** 함수 선언의 반환 매개변수 중 `?T`는 최대 하나입니다. `?T`는 **단일** 오류 채널입니다——함수 본문에서 `?=`로 조기 반환할 때 실패는 그 유일한 option 반환 매개변수에만 담을 수 있습니다. `?T`를 두 개 선언하면 컴파일러는 첫 번째만 채울 수 있고, 호출자는 절반만 채워진 tuple(`(err, nil)`)을 받게 되며 어떤 값이 실패를 나타내는지 알 수 없습니다:

```no
#{fmt-skip}
pair = () (a ?i64, b ?i64) {; 錯誤：兩個 ?T 返回參數
    a = ok(1)
    v ?= boom(); boom() 回 err('boom')
    a = v
    b = ok(2); 永不執行 —— 呼叫方看到 (err, nil)
}
```
```

올바른 작성법은 독립된 값을 plain 타입으로 선언하고, 오류 채널 역할을 하는 `?T` 하나만 남기는 것입니다:

```no
lookup = (k str) (value str, found bool, err ?str) {
    value = ''
    found = false
    err = nil
}
```

오류 메시지는 다음과 같은 형식입니다: `` function 'pair' declares 2 option (?T) results ('a', 'b'); only one result may be ?T … [moptres1] ``. 메서드 정의의 암묵적 `self` 수신자는 호출자가 별칭을 붙인 출력 매개변수이며 이 할당량을 차지하지 않습니다. `#{c}` extern 선언도 동일한 제한을 받습니다.

### 오류 포착 대입 (`=` 제자리 포착)

`?=`의 의미는 "오류를 위로 던지기"입니다——소속 함수에 option 결과 매개변수가 있어야 하며, 실패 시 조기 `return`합니다. 조기 반환 대신 제자리에서 오류를 처리하려면 일반 `=`를 사용하세요. 우변에 **오류 가능 소스**가 포함되어 있으면 대상 변수가 자동으로 `?T`로 추론되고, `nil` / `err`가 **제자리에 그 변수에 저장**되며 흐름이 계속됩니다.

```no
handle = (b i64, c i64, d i64) (r i64) {
    a = b + c / d; a 推斷為 ?i64；除零 → a = err
    a: {
        err -> {
            r = -1; 就地處理錯誤
        }

        nil -> {
            r = -1
        }

        -> {
            r = it; 成功：r = b + c/d
        }
    }
}
```

**오류 가능 소스(포착 트리거):**

| 출처                    | 예                                   | 포착 결과                          |
| --------------------- | ----------------------------------- | ----------------------------- |
| 정수 나눗셈 / 나머지             | `a = b + c / d`, `a = b % c`         | 0으로 나눔, `MIN / -1` → `err`         |
| 안전한 인덱싱                  | `a = v[i]`(`arr` / `vec` / `slice`) | 범위 초과 → `err`(`code.index-out`)  |
| option 타입 피연산자           | `a = x + 1`(`x ?i64`)               | `x`가 `nil` / `err`일 때 그대로 `a`에 저장 |
| option을 반환하는 호출(산술 피연산자) | `a = f(x) + 1`(`f`가 `?i64` 반환)       | 위와 같음                            |

> 함수 인수로 **직접** 전달되는 option은 여기에 해당하지 않습니다——그 처리는 피호출자에게 맡깁니다(`?=`의 그대로의 option 인수 면제와 동일).

**순수 산술은 오류 가능 소스가 아닙니다**: `+ - * <<`와 단항 마이너스 자체는 포착을 트리거하지 않습니다(그러면 모든 산술이 option이 됨). 하지만 option 경로에 놓이면(예: 우변에 `/`가 더 있거나 대상이 명시적으로 `?T`로 선언된 경우) 이러한 연산에는 **런타임 오버플로 검사**가 붙고, 오버플로 시 → `err`가 됩니다:

```no
ovf = (x i64) (r i64) {
    a ?i64 = x + 1; 顯式 ?T → 走 option 包裝路徑
    a: {
        err -> {
            r = 0; x = i64-max 時溢出 → err
        }

        nil -> {
            r = 0
        }

        -> {
            r = it
        }
    }
}
```

**포착 vs 상향 전파:**

| 작성법            | 실패 시                                 | option 결과 매개변수 필요 | 이후 값 얻는 방법             |
| ------------- | ----------------------------------- | -------------- | ------------------ |
| `a ?= expr`   | 결과 매개변수를 `nil`/`err`로 설정하고 `return`(조기 반환) | 예              | 해당 없음(이미 반환됨)           |
| `a = expr`    | `a`에 `nil`/`err`를 제자리 저장하고 흐름 계속            | 아니오              | `a: { ok -> ... }` |
| `a ?T = expr` | `=`와 동일(명시적 표기, 내부 오류 가능 하위 표현식 포함)               | 아니오              | 위와 같음                 |
| `_ = expr`    |값을 평가하되 결과와 오류를 버림(오류 없음, unused lint 미트리거)     | 아니오              | 해당 없음                |

**적용 범위:** 안전한 인덱싱의 포착은 `?=`와 마찬가지로 **`?T` 결과를 반환하는 함수 안에서만 적용됩니다**(〈안전한 인덱싱〉의 세 번째 작성법 참조). `/` `%` 및 option 피연산자의 포착은 모든 함수에 적용됩니다.

**기존 변수는 타입을 바꾸지 않습니다:** 포착은 "이 문장에서 처음 선언된" 대상에만 적용됩니다. 대상이 이미 존재하는 경우(`v i64 = 0` 이후의 `v = arr[i]`, 또는 `d = 0` 이후의 `d = x - 1`), 컴파일러는 제자리에서 타입을 바꾸지 않고 의미를 명시적으로 선택하라고 오류를 냅니다(`#{overflow=...}` / `#{index-out=...}` 애노테이션 추가, `?=` 사용, 또는 `?T` 선언).

### 정수 대입 타입 검사

컴파일러는 정수 대입에 대해 타입 검사를 수행하여, 안전하지 않은 축소(narrowing)로 인한 데이터 손실을 방지합니다. 규칙은 다음과 같습니다:

#### 암묵적 확장(안전, 자동 허용)

좁은 정수 타입의 값은 대상 타입의 범위가 원래 타입의 범위를 완전히 포함하므로 더 넓은 타입에 자동으로 대입할 수 있습니다:

```no
b byte = 200
i i64 = b; ✓ byte 範圍 [0,255] ⊆ i64 範圍
u u32 = b; ✓ byte 範圍 ⊆ u32 範圍
```

#### 정수 리터럴 대입

정수 리터럴(기본적으로 `i64`로 추론됨)은 해당 값을 범위에 포함하는 모든 정수 타입에 대입할 수 있습니다:

```no
#{fmt-skip}
n u8 = 200; ✓ 200 ∈ [0,255]
m u8 = 300; ✗ 300 > 255，編譯錯誤
big u64 = 18446744073709551615; ✓ 2^64-1，u64 最大值
```
```

#### 안전하지 않은 축소(컴파일 오류)

넓은 타입의 변수를 좁은 타입에 직접 대입하면 데이터 손실이 발생할 수 있으므로 컴파일 오류가 됩니다. 오류 메시지에는 **실행 가능한 수정 힌트**가 함께 붙어, 비트 연산으로 안전하게 축소하는 방법을 안내합니다:

```no
#{fmt-skip}
d u64 = 42
h u32 = d; ✗ cannot assign u64 value to u32 variable 'h'; hint: narrow safely with a bitwise mask (e.g. `& 4294967295`) or right shift (e.g. `>> 32`)
h u16 = d; ✗ cannot assign u64 value to u16 variable 'h'; hint: narrow safely with a bitwise mask (e.g. `& 65535`) or right shift (e.g. `>> 48`)
h u8 = d; ✗ cannot assign u64 value to u8 variable 'h'; hint: narrow safely with a bitwise mask (e.g. `& 255`) or right shift (e.g. `>> 56`)
x u32 = d + 1; ✗ 加法結果仍為 u64，不安全
y u32 = foo(); ✗ 函式呼叫結果型別不匹配
```
```

> **수정 힌트**: 컴파일러가 대상 타입에 맞춰 정확한 mask 값과 시프트량을 자동으로 계산합니다. 힌트대로 mask나 시프트를 적용하면 안전하게 축소할 수 있습니다(다음 절 참조).
>
> **부호 있는 대상 타입**: `i8`/`i16`/`i32`/`i64` 등 부호 있는 정수에는 비트 축소가 적용되지 않는다고 힌트가 알려줍니다(부호 비트 절단의 의미가 불명확). 대신 명시적 범위 검사를 사용하도록 권장합니다.

#### 비트 연산을 이용한 안전한 축소(자동 허용)

대입 우변이 **비트 연산 표현식**(`&`, `|`, `^`, `<<`, `>>`)이고 대상 타입이 **부호 없는 정수**(`u8`/`u16`/`u32`/`u64`/`byte`)일 때, 컴파일러는 암묵적 축소를 허용합니다——상위 비트 절단은 비트 연산의 표준 의미이며 예상치 못한 데이터 손실을 일으키지 않기 때문입니다:

```no
d u64 = 42

; ✓ mask 運算：結果必 ≤ mask 值，安全落入 u32
h u32 = d & 67108863; mask = 2^26-1 < 2^32
h u32 = d & 4294967295; mask = 2^32-1，正好 u32 範圍

; ✓ 位移運算：右移後高位為 0，安全
hi u32 = d >> 32; u64 >> 32 留 32 bits

; ✓ XOR / OR 組合
c u32 = a ^ b; 位元運算結果
b byte = v & 255; mask 到 byte 範圍

; ✓ 複合位元運算（常見於密碼學/編解碼）
s u32 = (key[0] & 255) | ((key[1] & 255) << 8) | ((key[2] & 255) << 16) | ((key[3] & 255) << 24)
```

> **왜 허용되나요?** 비트 연산(mask, 시프트, XOR, OR)의 의미는 비트 패턴을 구성하는 것입니다. 좁은 부호 없는 타입에 대입할 때 상위 비트를 자르는 것은 의도된 동작입니다——개발자가 mask나 시프트로 결과 범위를 보장했거나 의도적으로 상위 비트를 버린 것이기 때문입니다. 이는 암호화(ChaCha20, Poly1305, Blake2 등)와 인코딩/디코딩 코드의 표준 패턴입니다.

> **부호 없는 대상 타입에만 해당합니다.** 부호 있는 정수 대상(`i8`/`i16`/`i32`/`i64`)은 우변이 비트 연산이어도 오류가 납니다. 부호 비트 절단의 의미가 불명확하기 때문입니다:
>
> ```no
> d u64 = 42
> h i32 = d & 4294967295   ; ✗ 仍報錯：有號目標不適用安全窄化
> ```

> **최상위 연산자가 비트 연산이어야 합니다.** 표현식의 최상위 연산자가 `&`/`|`/`^`/`<<`/`>>`일 때만 허용됩니다. 덧셈, 뺄셈, 함수 호출, 직접 변수 참조 등은 해당하지 않습니다:
>
> ```no
> d u64 = 42
> h u32 = d              ; ✗ 頂層是 Identifier，不是位元運算
> h u32 = d + 1          ; ✗ 頂層是 +，不是位元運算
> ```

#### `.noml` 설정 파일 직접 가져오기

.noml 파일은 `#`로 직접 가져올 수 있습니다. 해석 순서는 먼저 같은 이름의 `.no`를 찾고, 없으면 `.noml`을 찾습니다. 가져온 후
**구조체 이름은 기본적으로 파일명입니다**(확장자를 제거하며, 파일 상단의 `#{name = '...'}` 애노테이션으로 바꿀 수 있음),
각 멤버는 해당 구조체의 필드가 됩니다. 동시에 파일 내용을 담는 같은 이름의 전역 값도 생성되므로
`server.port`로 설정을 읽습니다.

```noml
; cfg/server.noml
{
  host: 'localhost'
  port: 8080
  tags: [] #{type = '[]str'}
  compiler: {
    version: 'v0.1.0'
  }
}
```

```no
# /cfg/server

print(server.port); 8080
print(server.compiler.version); v0.1.0
```

- 필드 타입은 멤버의 `#{type = '...'}` 애노테이션을 우선 사용합니다(값은 완전한 nolang 타입 표현식, 예:
  `'[]str'`, `'[]i64'`, `'?i64'`); 애노테이션이 없으면 값에서 추론합니다: 문자열 → `str`, 정수 → `i64`,
  소수 → `f64`, 불리언 → `bool`, 객체 → 자동 생성된 중첩 구조체(`server-compiler`),
  배열 → `[]요소타입`.
- 빈 컨테이너(`[]`, `{}`)는 **반드시** `#{type = '...'}`를 써야 합니다: noml 값 자체에는 타입이 없어 빈 컨테이너는
  추론할 수 없습니다. 객체 멤버에 `#{type = 'x'}`가 붙어 있으면 `x`를 그대로 사용하고(직접 정의 필요), 자동으로 중첩
  구조체를 생성하지 않습니다.
- 중첩 객체의 구조체 이름은 파일명을 접두사로 사용합니다(`server-compiler`); 정의 순서는 중첩 구조체 먼저, 호스트 구조체가 나중입니다.
- **상단(파일 수준) 애노테이션으로 구조체 이름을 바꿀 수 있습니다**: `#{name = '...'}`(`#{type = '...'}`와 동일한 표기,
  `name` 우선)를 최상위 `{` 위의 별도 줄에 씁니다(또는 최상위 값과 같은 줄 끝에 붙입니다). 바꾸면 값 바인딩 이름과
  중첩 구조체 접두사도 함께 따라가지만, **가져오기 경로는 여전히 파일명으로 해석됩니다**:

```noml
; cfg/db.noml
#{name = 'db-options'}
{
  host: 'localhost'
}
```

```no
# /cfg/db
# /cfg/db as db2

print(db-options.host); localhost
print(db2.host); localhost
```

- 서로 다른 두 파일이 같은 타입 이름을 생성하면(예: 다른 디렉터리에 있는 같은 이름의 파일) 오류가 납니다. 상단의
  `#{name = '...'}`로 구분하면 됩니다. 같은 파일이 여러 번 가져와지면(예: `as` 별칭 추가) 타입 정의는 한 번만 병합됩니다.
- 키 이름은 nolang 규칙에 따라 하이픈 소문자로 변환됩니다(`anonymous-fn-type`): 숫자로 시작하면 `f-`를, 키워드와
  같으면 `x-`를 붙입니다.
- `as` 별칭으로 값 바인딩 이름을 바꿀 수 있으며 구조체 이름은 그대로입니다: `# /cfg/server as cfg`.
- `.noml` 타입은 모듈 접두사에 참여하지 않습니다. 파일명이 표준 라이브러리 모듈과 같아도(예: `server`) 타입은 여전히 순수 이름입니다.
- `package.noml` / `workspace.noml`에도 `#{...}` 애노테이션을 쓸 수 있습니다(예: `#{type = '[]str'}`):
  해석 시 무시되며, 외부 도구가 강타입 구조를 재구성하기 위한 용도입니다. 문법은 nolang의 `#{...}`와 완전히 동일합니다.

### FFI (`#{c}` 애노테이션)

`#{c}` 애노테이션으로 외부 C 함수를 선언해 FFI(Foreign Function Interface)를 구현합니다.

**문법**: `#{c}`는 별도 줄에 쓰며, 다음 줄을 FFI 선언으로 표시합니다. `#{c}`는 애노테이션 시스템의 FFI 언어 키이며 `#{cpp}`, `#{rust}` 등 다른 언어도 지원합니다. 기존 문법 `#c`는 계속 호환됩니다.

**비공개 선언**: 이름이 `_`로 시작하면 비공개(내보내지 않음)이며, C ABI 심볼은 자동으로 접두사 `_`를 제거하고 하이픈을 밑줄로 바꿉니다.

**별도 파일이 필요 없습니다**: FFI 선언과 일반 코드를 같은 `.no` 파일에 쓸 수 있습니다.

**포인터 타입 문법**: FFI에서는 C 스타일의 `*T`, `**T`, `***T`로 포인터를 표현하며, 구체적인 타입 `T`가 있어야 합니다. 일반 코드에서는 이 문법을 쓸 수 없습니다.

| 문법        | 의미          | LLVM IR | 용도                  |
| --------- | ----------- | ------- | ------------------- |
| `*byte`   | byte를 가리키는 포인터 | `i8*`   | 불투명 포인터(예: db handle)  |
| `**byte`  | 이중 포인터        | `i8**`  | 출력 매개변수(예: `sqlite3**`) |
| `***byte` | 삼중 포인터        | `i8***` | 드물게 쓰는 삼중 간접            |

```no
; sqlite.no — FFI 綁定與安全包裝在同一檔案
; 編譯器自動將連字號 (-) 轉為底線 (_) 以匹配 C ABI 符號
; 以 _ 開頭的名稱為私有，C ABI 符號自動去除前綴 _

; 基本型別參數
#{c}
c-strlen = (s str) (n i64)

; 指針參數（*byte = 不透明指標），私有宣告
#{c}
_sqlite3-close = (db *byte) (rc i32)

; 雙重指針（**byte = 輸出參數，呼叫後值自動存回變數），私有宣告
#{c}
_sqlite3-open = (filename str, db **byte) (rc i32)

; 多個指針參數，私有宣告
#{c}
_sqlite3-exec = (db *byte, sql str, callback *byte, arg *byte, errmsg *byte) (rc i32)
```

```no
; 同一檔案中的安全包裝

open = (dsn str) (d db-sqlite) {
    handle i64 = 0
    rc i32 = _sqlite3-open(dsn, handle)
    rc != SQLITE-OK -> {
        return
    }
    d.handle = handle
}
```

**규칙:**

1. `#{c}`는 별도 줄에 쓰며 다음 줄을 FFI 선언으로 표시합니다(기존 문법 `#c`도 호환)
2. FFI는 선언만 있으며 함수 본문이 없습니다
3. 포인터에는 구체적인 타입이 있어야 합니다(예: `*byte`). 순수 `ptr`는 허용되지 않습니다
4. `**byte`는 출력 매개변수에 사용합니다: 호출 후 C 함수가 쓴 포인터 값이 자동으로 `i64`로 변환되어 호출자 변수에 저장됩니다
5. 모든 포인터는 Nolang 측에서 `i64`로 저장됩니다(`ptrtoint`)
6. `str` 타입 매개변수는 자동으로 null 종료 `i8*`로 변환됩니다
7. 이름이 `_`로 시작하면 비공개(내보내지 않음)이며, C ABI 심볼에서 접두사 `_`가 제거됩니다
8. FFI 선언과 일반 코드를 같은 `.no` 파일에 쓸 수 있습니다

> 반대 방향(C / C++ / Rust / Go / Java / Python / C#이 Nolang을 호출하는 방향)은 `#{cabi='symbol'}`와 `no build --shared`를 사용합니다. [호스트 언어에서 Nolang 호출](./host-interop) 참조.

### 애노테이션 시스템 (`#{...}`)

`#{...}`는 범용 애노테이션 시스템으로, 쉼표로 구분된 키-값 쌍 목록입니다. 다음 값 타입을 지원합니다:

| 문법  | 타입  | 예                                   |
| --- | --- | ------------------------------------ |
| 독립 키 | 불리언 | `#{debug}`                           |
| 불리언 값 | 불리언 | `#{inline=true}` / `#{inline=false}` |
| 숫자  | 정수  | `#{max=100}`                         |
| 텍스트  | 문자열  | `#{name='hello'}`                    |
| 식별자 | 식별자 | `#{mode=fast}`                       |
| 배열  | 배열  | `#{derive=[Serialize, Deserialize]}` |
| 범위  | 범위  | `#{range=[0..256)}`                  |

여러 키-값 쌍은 쉼표로 구분합니다:

```no
#{derive=[Serialize, Deserialize], range=[0..256), max=100, debug}
```

#### 애노테이션 위치

`#{...}`는 다음 두 가지 형태만 허용됩니다:

- **위쪽**: 별도 줄로 대상(문장, 구조체 필드, 열거형 멤버, 선언, match 암) 위에 둡니다;
- **뒤쪽**: 대상과 같은 줄의 끝에 붙입니다(`res = arr[i] #{index-out=zero}`, `a pt #{inline}`,  
  `green #{deprecated}`).

대상 **앞쪽 같은 줄**(접두사, 예: `#{index-out=zero} res = arr[i]`)에 쓰는 것은 **컴파일 오류**이며, 컴파일러와  
LSP가 같은 진단을 보고합니다. 판정 방법: 애노테이션 그룹의 `}` 뒤에 같은 줄에 더 이상 코드가 있으면 안 됩니다(줄바꿈,  
`;` 줄 주석, 또는 바로 이어지는 다른 애노테이션 그룹은 코드로 치지 않습니다).

```no
; ✓ 上方：獨立成行
#{overflow=wrap}
x i8 = a + 100

; ✓ 後方：同一行尾隨
x i8 = a + 100 #{overflow=wrap}
```

```no
#{fmt-skip}
; ✗ 前方：同一行前綴 → 報錯
#{overflow = wrap} x i8 = a + 100
```

구조체 필드와 열거형 멤버(C 스타일 열거형의 값, 태그 열거형의 변형)의 애노테이션도 위쪽 또는 뒤쪽만  
허용됩니다(`a pt #{inline}`, `a pt #{inline=true}`, `green #{deprecated}`, `ok(v i64) #{inline}`).  
`#{inline}`의 **값**도 지원됩니다. `#{inline=false}`는 유효합니다(아래  
〈구조체 필드의 `#{inline}`〉 참조).

`if <cond> { ... }` 형태에서 애노테이션을 조건과 `{` 사이에 두는 것(`if x > 0 #{overflow=wrap} {`)도  
"앞쪽" 위치이므로 마찬가지로 오류입니다. 이 지점의 스캔은 관대해서, 과거에는 애노테이션 그룹 전체를 통째로  
삼켜 버렸습니다——적용되지도 않고 오류도 나지 않아 가장 알아차리기 어려운 무효화였습니다.

범위 문법은 16가지 괄호 조합을 지원합니다(규칙: `[`는 왼쪽 끝점을 포함하고 `(`는 포함하지 않음; `]`는 오른쪽 끝점을 포함하고 `)`는 포함하지 않음):

**유계 구간(4가지)** — 양 끝에 값이 있는 경우:

- `[a..b]` — 양 끝 모두 닫힌 구간(`x >= a && x <= b`)
- `[a..b)` — 왼쪽 닫힘, 오른쪽 열림(`x >= a && x < b`)
- `(a..b]` — 왼쪽 열림, 오른쪽 닫힘(`x > a && x <= b`)
- `(a..b)` — 양 끝 모두 열린 구간(`x > a && x < b`)

**상한 없음 구간(4가지)** — 오른쪽 끝점 생략:

- `[a..]`, `[a..)` — 왼쪽 포함, 상한 없음(`x >= a`)
- `(a..]`, `(a..)` — 왼쪽 미포함, 상한 없음(`x > a`)

**하한 없음 구간(4가지)** — 왼쪽 끝점 생략:

- `[..b]`, `(..b]` — 하한 없음, 오른쪽 포함(`x <= b`)
- `[..b)`, `(..b)` — 하한 없음, 오른쪽 미포함(`x < b`)

**완전 무계 구간(4가지)** — 양 끝을 모두 생략하며, 타입의 최솟값/최댓값을 기준으로 합니다:

- `[..]` — 타입 최솟값 ≤ x ≤ 타입 최댓값(양 끝 포함)
- `[..)` — 타입 최솟값 ≤ x < 타입 최댓값
- `(..]` — 타입 최솟값 < x ≤ 타입 최댓값
- `(..)` — 타입 최솟값 < x < 타입 최댓값

#### 애노테이션의 스코프

애노테이션의 **위치**가 호스트를 결정하고, 호스트의 **종류**가 적용 범위를 결정합니다. 모두 네 단계이며, 바깥에서 안쪽으로 적용되고
가까운 것이 덮어씁니다. 함수 본문은 상속의 단단한 경계입니다:

| 단계 | 호스트 | 적용 범위 |
| --- | --- | --- |
| **L0 모듈 수준** | 파일 머리 | 해당 파일의 모든 선언과 문장(파일 머리 애노테이션 + 빈 줄 하나) |
| **L1 선언 수준** | 상수/전역 변수, 구조체, 인터페이스, 태그 열거형, 함수, 메서드 | 해당 선언의 전체 정의(함수는 함수 본문과 모든 중첩 블록 포함) |
| **L2 블록 수준** | 코루틴 그룹, if 그룹, `cond -> body`, match, `for`/횟수/범위 반복문 | 해당 블록 본문의 모든 문장(중첩 블록 포함, 안쪽 L1 경계에서 멈춤) |
| **L3 단일 줄 수준** | 단일 문장(`let`, 대입, `?=`, `return`, 호출, `cond ->` 암) | 해당 문장 자신과 그 표현식 |

```no
; L1：整個函式
#{overflow=wrap}
sum = (xs []i64) (total i64) {
    ; L3：只管下一條陳述
    #{overflow=wrap}
    total = xs.len() - 1
    ; L2：整個循環體
    #{overflow=wrap}
    i <- [0..xs.len()): {
        total = total + xs[i]
    }
}
```

전체 판정 규칙, 키 × 단계 행렬, 현재 구현과의 차이는
[〈애노테이션과 주석의 스코프〉](annotation-scope.md)를 참조하세요.

FFI 애노테이션 `#{c}`는 애노테이션 시스템의 특수 형태입니다. 애노테이션에 FFI 언어 키(`c`, `cpp`, `rust` 등)가 포함되어 있고 뒤이어 함수 선언이 오면, 컴파일러는 이를 FFI 바인딩으로 인식합니다:

```no
; #{c} 帶額外註解
#{c, debug}
_sqlite3-open = (filename str, db **byte) (rc i32)
```

#### 애노테이션을 선언에 붙이기

FFI가 아닌 애노테이션은 바로 뒤따르는 선언(변수 선언, 구조체 정의)에 자동으로 붙습니다. 숫자 타입(예: `num`, `i64`)에 범위 제한 같은 메타데이터를 표시하는 데 쓸 수 있습니다:

```no
; 變數宣告帶 range 註解
#{range=[0..256)}
x num = 42

; 結構體定義帶註解
#{derive=[Serialize, Deserialize]}
point {
    x i64
    y i64
}

; 結構體欄位帶 range 註解（可用於 num 等數值型別）
person {
    age num #{range=[0..150]}
    score i64 #{range=[0..256)}
    name str
}
```

`range` 애노테이션은 `num` 타입(`num = int | float`)에 특히 유용하며, 숫자의 유효 범위를 표시합니다. 범위 값은 정수 또는 식별자일 수 있습니다:

```no
; 使用常量識別字作為範圍邊界
#{range=['i8.MIN'..'i8.MAX']}
val i8 = 100
```

#### 파일 임베딩 (`#{embed=...}`)

`#{embed=...}` 애노테이션은 컴파일 타임에 외부 파일 내용을 `[]byte` 읽기 전용 상수로 임베딩합니다. Go의 `//go:embed`와 유사합니다. 임베딩된 데이터는 실행 파일에 직접 컴파일되어 단일 바이너리 배포가 가능하며, 런타임에 파일을 읽을 필요가 없습니다.

**문법**:

```no
#{embed='path/to/file'}
ICON []byte

; 或使用裸路徑（無引號）
#{embed='assets/icon.ico'}
ICON []byte
```

`embed` 애노테이션은 바로 뒤따르는 `[]byte` 변수 선언에 붙습니다. 변수 선언에는 **명시적 초기값이 있을 수 없습니다**——값은 임베딩된 파일 내용에서 제공됩니다.

**경로 해석**:

- 상대 경로는 패키지 루트 디렉터리(`package.noml`이 있는 디렉터리)를 기준으로 해석됩니다
- 절대 경로를 지원합니다
- 경로에 `/`, `.`, `-` 문자가 포함될 수 있습니다

**예**:

```no
; 嵌入 Windows 圖標
#{embed='assets/win-icon.ico'}
WIN-ICON []byte

; 嵌入 SSL 證書
#{embed='certs/server.pem'}
SERVER-CERT []byte

; 嵌入配置文件
#{embed='config/default.json'}
CONFIG []byte

; 使用嵌入數據
print('icon size: ', len(WIN-ICON))
print('first byte: ', WIN-ICON[0])
```

**주의 사항**:

1. 임베딩된 데이터는 **읽기 전용** 상수이며, 읽기 전용 메모리 영역을 가리킵니다. 임베딩된 데이터에 쓰는 동작은 정의되지 않습니다(Go `//go:embed` 의미와 동일)
2. 임베딩된 변수는 힙 해제에 참여하지 않습니다——프로그램이 종료될 때 임베딩 데이터의 포인터를 free하지 않습니다
3. `[]byte` 타입 선언만 지원합니다(`[N]byte` 고정 배열도 가능)
4. 파일이 컴파일 타임에 존재해야 하며, 그렇지 않으면 오류가 납니다
5. 명시적 초기값과 함께 쓸 수 없습니다(예: `ICON []byte = [1, 2, 3]`은 오류)

#### 디렉터리 임베딩 (`#{embed='dir'}`)

`#{embed=...}`는 전체 디렉터리 임베딩도 지원합니다. 경로가 디렉터리를 가리키면 컴파일러가 그 아래의 모든 파일을 재귀적으로 읽어 `fs.embed` 타입의 읽기 전용 파일 시스템으로 임베딩합니다. 런타임에는 `read()`, `exists()` 메서드로 경로를 통해 임베딩된 파일에 접근하며 C 함수가 전혀 필요 없습니다——조회 로직은 전부 Nolang로 구현되어 있습니다.

**문법**:

```no
; 嵌入整個前端目錄
#{embed='../frontend/dist'}
DIST fs.embed

; 從嵌入的文件系統讀取文件
data = DIST.read('index.html')

; 檢查文件是否存在
ok = DIST.exists('css/style.css')
```

**`fs.embed` 타입**:

`fs.embed`는 Nolang 표준 라이브러리 `fs` 모듈에 정의된 구조체로, 임베딩된 파일의 메타데이터(경로, 오프셋, 길이)를 담고 있습니다. 컴파일러가 컴파일 타임에 디렉터리를 읽어 모든 파일 내용을 상수 전역 변수로 이어 붙이고, 런타임에는 순수 Nolang로 구현된 `read` 메서드가 순회하며 찾습니다.

| 메서드       | 시그니처                                  | 설명                |
| -------- | ----------------------------------- | ----------------- |
| `read`   | `(path str) (data ?[]byte)`           | 임베딩된 파일을 읽어 내용을 반환(찾지 못하면 nil) |
| `exists` | `(path str) (yes bool)`             | 임베딩된 파일이 존재하는지 확인       |

**예**:

```no
; HTTP 靜態文件伺服器：將前端文件嵌入單一二進制
#{embed='../frontend/dist'}
DIST fs.embed

serve = (conn server-conn) {
    conn.parse()
    path = conn.path
    path == '/' -> path = '/index.html'

    ; 去掉前導 / 得到相對路徑
    rel = path.slice(1, path.len-bytes())

    ; 從嵌入的文件系統讀取
    data []byte = DIST.read(rel)
    {
        ok -> it

        -> {
            conn.write-html(404, 'Not Found')
            conn.close()
            return
        }
    }
    conn.write-status(200)
    conn.write-header('Content-Type', get-content-type(path))
    conn.write-body(data)
    conn.close()
}
```

**주의 사항**:

1. 디렉터리의 모든 파일(하위 디렉터리 포함)이 재귀적으로 임베딩되며, 경로는 임베딩된 디렉터리를 기준으로 한 상대 경로로 저장됩니다(예: `css/style.css`)
2. 경로 구분자는 슬래시 `/`로 통일됩니다(플랫폼 간 동일)
3. `fs.embed` 타입 변수는 읽기 전용이며 힙 해제에 참여하지 않습니다
4. 단일 바이너리 배포 시나리오(예: HTTP 정적 파일 서버, CLI 도구의 리소스 임베딩)에 적합합니다

#### 플랫폼 애노테이션

플랫폼 애노테이션은 컴파일 타임 필터로, 대상 플랫폼에 따라 코드 포함 여부를 결정합니다. **평탄화된 키**(예: `#{mac-arm64}`)로 OS와 아키텍처를 동시에 지정해 모호함이 없으며, 바로 뒤따르는 선언에 붙습니다. 일치하지 않는 코드는 컴파일에 전혀 참여하지 않습니다——LLVM IR도 생성되지 않고 타입 검사도 수행되지 않습니다.

**지원되는 플랫폼 키(6가지 평탄한 조합):**

| 키                | 일치 대상                         |
| ---------------- | -------------------------- |
| `#{linux-amd64}` | Linux x86_64               |
| `#{linux-arm64}` | Linux ARM64                |
| `#{win-amd64}`   | Windows x86_64             |
| `#{win-arm64}`   | Windows ARM64              |
| `#{mac-amd64}`   | macOS x86_64(Intel)        |
| `#{mac-arm64}`   | macOS ARM64(Apple Silicon) |

```no
#{mac-arm64}
print('running on macOS ARM64')

#{linux-amd64}
print('running on Linux x86_64')

#{win-amd64}
print('running on Windows x86_64')

; 平台特定的變數
#{mac-amd64, mac-arm64}
sep = '/'

#{win-amd64, win-arm64}
sep = '\\'

; 平台特定的函數
#{mac-arm64, mac-amd64}
greet = () {
    print('hello from mac')
}

#{linux-amd64, linux-arm64}
greet = () {
    print('hello from linux')
}

greet()
```

같은 선언에 여러 키가 있으면 **OR** 관계입니다——하나라도 일치하면 포함됩니다. 각 키가 이미 OS와 아키텍처를 동시에 지정하므로 AND 논리가 필요 없습니다.

| 애노테이션                          | 의미                                |
| --------------------------- | --------------------------------- |
| `#{mac-arm64}`              | macOS ARM64만                     |
| `#{mac-amd64, mac-arm64}`   | macOS 모든 아키텍처                        |
| `#{linux-amd64, win-amd64}` | Linux x86_64 **또는** Windows x86_64 |
| `#{mac-arm64, linux-arm64}` | macOS ARM64 **또는** Linux ARM64     |

```no
; macOS 和 Linux（所有架構）都執行
#{mac-amd64, mac-arm64, linux-amd64, linux-arm64}
shared = () {
    print('unix-like')
}

; 僅 Windows x86_64
#{win-amd64}
reg-key = () {
    print('reading registry on win/x64')
}

; 僅 macOS ARM64（Apple Silicon）
#{mac-arm64}
neural = () {
    print('Apple Neural Engine available')
}
```

`os.get-arch()`를 사용하면 런타임에 현재 아키텍처를 얻을 수 있고, 플랫폼 애노테이션을 사용하면 컴파일 타임에 코드를 포함하거나 제외합니다.

## package.noml 컴파일러 설정

`package.noml`의 `compiler` 블록이 컴파일러 동작을 제어합니다. `version` 값은 앞에 `v`를 붙이는 것이 관례입니다(예: `"v0.1.0"`); 컴파일러는 내부적으로 접두사에 구애받지 않아 `"v0.1.0"`과 `"0.1.0"`을 같은 버전으로 봅니다.

```noml
{
  compiler: {
    version: 'v0.1.0'
    emit: 'js'
  }
}
```

### `emit`

출력 대상 백엔드를 제어합니다:

| 값           | 설명                                      |
| ----------- | --------------------------------------- |
| `""` (비어 있음, 기본값) | LLVM 백엔드로 네이티브 실행 파일 생성                      |
| `"js"`      | JS 백엔드로 JavaScript 생성(타입 소거), LLVM 도구 모음 불필요 |

`"js"`로 설정하면 `no build`가 자동으로 JS 백엔드를 사용하며, 명령줄의 `--js`와 동일합니다. 명령줄 플래그가 설정 파일보다 우선합니다.

```noml
; 自動生成 JavaScript
compiler: {
  emit: 'js'
}
```

### `anonymous-fn-type`

익명 함수 타입 문법(예: `cb ()()`) 허용 여부를 제어합니다. 기본값은 `false`(비활성)이며, 이름이 있는 함수 타입 별칭을 사용해야 합니다.

### `link-libs`

연결할 C 라이브러리 목록을 지정합니다:

```noml
compiler: {
  link-libs: ['crypto', 'ssl']
}
```

## 컴파일 타임 변수 주입 (-ld)

`no build`, `no run`, `no test`는 `-ld-KEY=VALUE` 플래그로 컴파일 타임에 전역 상수를 주입할 수 있습니다. 주입된 변수는 소스 코드 맨 위에 `KEY = VALUE`를 선언한 것과 같으며 프로그램에서 바로 사용할 수 있습니다.

### 문법

```bash
no build -ld-KEY=VALUE [更多 -ld...] <file>
```

- `-ld` 접두사 뒤에 변수명과 값이 `=`로 구분되어 바로 이어집니다
- 여러 `-ld` 플래그를 동시에 사용할 수 있습니다
- 불리언 축약형: `-ld-DEBUG`(`=VALUE` 없음)는 `-ld-DEBUG=true`와 동일합니다

### 값의 타입 추론

| 값의 형태             | 추론 타입            | 예                  |
| ---------------- | --------------- | ------------------- |
| 정수               | `i64`           | `-ld-COUNT=42`      |
| 부동소수점              | `f64`           | `-ld-PI=3.14`       |
| `true` / `false` | `bool`          | `-ld-DEBUG=true`    |
| 기타               | `str`(작은따옴표 문자열 리터럴) | `-ld-VERSION=0.1.2` |

### 예

```no
; 假設使用 -ld-VERSION=0.1.2 -ld-COUNT=42 -ld-DEBUG=true 編譯
print('VERSION:', VERSION); 輸出: VERSION: 0.1.2
print('COUNT:', COUNT); 輸出: COUNT: 42
print('DEBUG:', DEBUG); 輸出: DEBUG: 1 (bool 在原生後端印為 1)
```

```bash
; 注入多個變數
no build -ld-VERSION=0.1.2 -ld-COUNT=42 -ld-DEBUG=true main.no

; 布林簡寫
no run -ld-RELEASE main.no

; JS 後端也支援
no build --js -ld-VERSION=0.1.2 main.no
```

### 소스 코드 선언과의 관계

`-ld`로 주입된 변수와 소스 코드 선언의 상호작용 규칙:

- **소스에 같은 이름의 선언이 있음**: 주입된 값이 소스 안의 그 변수 값을 **제자리에서 대체합니다**. 흔한 패턴은 소스에 자리 표시자 변수(예: `VERSION = ''`)를 선언해 두고 빌드할 때 `-ld-VERSION=0.1.2`로 값을 넣는 것입니다.
- **소스에 없음**: 주입된 변수가 AST 맨 앞에 새로운 전역 상수 선언으로 삽입되어 이후 모든 컴파일 패스(타입 추론, 검증, 모듈 병합, codegen)에 참여합니다.
- **주입하지 않을 때**: 소스의 선언은 그대로 유지되며 영향을 받지 않습니다.

```no
; 源碼聲明占位變數
VERSION = ''
COUNT = 0

print('VERSION:', VERSION)
print('COUNT:', COUNT)

; no build -ld-VERSION=0.1.2 main.no
; 輸出: VERSION: 0.1.2  （注入值覆蓋了源碼的 ''）
;       COUNT: 0        （未注入，保持源碼值）
```
