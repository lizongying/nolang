# 註解與註釋的作用域

`#{...}` 註解本身不帶「我能管多大範圍」的資訊——範圍由**它附着在哪個節點上**決定。
這頁把這件事固定下來：一個位置、一套判定、四個層級，再加一條「某個鍵可以只支持其中幾層」
（`overflow` 就是只認 L3 的那個，見 §4.1），讓作者、`no fmt`、`no vet`、codegen 與 LSP
對同一行註解給出同一個答案。

> 為什麼必須固定：同一條 `#{overflow=wrap}`，若 `no vet` 認為它管整個函式、codegen
> 認為它只管下一行，就會出現「vet 全綠、運行期照樣回 `err`」的靜默語義漂移。
> 作用域不是註解的屬性，而是**讀者的共識**；共識不寫下來就會各自漂。

---

## 1. 一個原則：作用域由宿主決定

註解只有兩種合法位置（位置規則本身見 [`syntax.md`](syntax.md)〈註解位置〉）：

```no
; ① 上方：獨佔一行，置於目標之上
#{overflow=wrap}
x i8 = a + b

; ② 尾隨：寫在目標同一行的後方
x i8 = a + b #{overflow=wrap}

; 多行目標（函式、區塊）的尾隨寫在收尾 `}` 之後
greet = () {
    print('hi')
} #{mac-arm64}
```

**兩者完全等價**——同一個鍵、同一個宿主、同一個作用域，`no fmt` 也不會把一種改寫成
另一種（尾隨留在尾隨，上方留在上方）。選哪種只看可讀性：短述句用尾隨更省一行，
需要給整段運算加註、或述句很長時用上方。

**寫在目標前方同一行是編譯錯誤**，不存在「前綴作用到後方」這條路：

```no
#{overflow = wrap} x i8 = a + b   ; ✗ 前綴 → 報錯
```

判定分三步，每一步都只有一個答案：

| 步驟 | 問題 | 答案來源 |
| --- | --- | --- |
| 1 | 宿主是誰？ | 位置：上方的第一條非註解/非註解行陳述，或同一行的前一條陳述 |
| 2 | 宿主屬於哪一層？該鍵支持這一層嗎？ | §2 的表 + §4 的矩陣（不支持就是編譯錯誤） |
| 3 | 覆蓋到哪裡？ | 宿主子樹，減去內層硬邊界（§3） |

## 2. 四個層級

| 層級 | 宿主 | 生效範圍 | 寫法示例 |
| --- | --- | --- | --- |
| **L0 模組級** | 檔案頭 | 本檔案全部宣告與語句 | 檔案最頂端，且與後續內容之間空一行 |
| **L1 宣告級** | 常量/全局變數、結構體、介面、標籤列舉、函式、方法 | 該宣告的整個定義（函式含函式體與全部巢狀區塊） | 緊貼宣告上方，或宣告行尾隨 |
| **L2 區塊級** | 協程組、if 組、`cond -> body`、match、`for`/計數/區間循環、裸塊 | 該塊體內全部語句（含巢狀塊，止於內層 L1 邊界） | 緊貼塊頭那條語句上方，或寫在塊尾 `}` 之後 |
| **L3 單行級** | 單條陳述（`let`、賦值、`?=`、`return`、呼叫、`cond ->` 臂） | 該陳述自身及其運算式 | 緊貼陳述上方，或同行尾隨 |

### L0 模組級

位置是**檔案最開頭**（前面沒有任何語句或 import），且註解群組與第一條語句之間
**至少一個空行**——空行在這裡是「作用域終止符」，表示這組註解不屬於下一條陳述，
而屬於整個檔案。

```no
#{win-amd64}

; ↑ 空行 → 模組級：本檔只在 Windows x86_64 編譯
; 以下所有宣告與語句都在管轄內
helper = () {
    print('windows only')
}

label = 'win'
```

沒有空行就是一般的 L1（附着首個宣告），這條邊界讓既有程式碼不需遷移：

```no
#{buildin}
bool.to-str = () (out str) {
}
```

模組級只對「整檔有意義」的鍵有用（目前只有平台鍵）；宣告鍵（`buildin`、`generic`、
`embed`…）出現在 L0 是錯誤，不是「擴大範圍」。`overflow` 也不吃 L0——它只認 L3。

跨檔案的配置不屬於註解，寫在 `package.noml`。

### L1 宣告級

```no
; 整個結構體：欄位佈局由型別標記決定
#{inline}
holder {
    inl point
    out point
}

; 整個函式：進出日誌自動帶呼叫者
#{track-caller}
log.write = (msg str) {
    ...
}

; 整個常量宣告：嵌入目錄（路徑相對 package.noml）
#{embed='assets'}
ASSETS fs.embed

; 編譯期剔除整棵子樹（含函式體）
#{mac-arm64, linux-arm64}
greet = () {
    print('hello from unix')
}
```

L1 內部還有**成員粒度**：結構體欄位、標籤列舉變體、C 風格列舉成員上的註解
（`a pt #{inline}`、`ok(v i64) #{inline}`）管的是該成員，不是整個型別。成員註解
同樣只有兩種位置：緊貼成員上方一行，或寫在該成員同一行的後方（慣用尾隨）。

### L2 區塊級

宿主是「塊頭陳述」時，作用域是整個塊體：

```no
; 整塊被排除（不生成 IR，也不做型別檢查）
#{win-amd64}
2 * {
    print('windows only')
}

; if 組同樣以整組為單位
x = 1
#{win-amd64}
{
    x == 1 -> print('arm-1')
    -> print('arm-other')
}
```

四種塊頭都適用：協程組（語句位置的裸塊）、if 組（`{ cond -> … }`）、單條件語句
（`cond -> body`）、match、`for` / 計數 / 區間循環。

`cond -> body` 的 body 若只是單條陳述，L2 與 L3 的結果相同；寫成塊才有區別。

**不是每個鍵都吃滿四層。** 一個鍵可以只支持其中幾層，寫到它不支持的層是**編譯錯誤**，
不是「多寫一行的無害冗餘」。目前唯一的受限鍵是 `overflow`：它只認 L3，理由見 §4.1。

### L3 單行級

```no
a i8 = 100
b i8 = 100
; 只管緊跟的下一條陳述（尾隨寫法 `c = a + b #{overflow=wrap}` 等價）
#{overflow=wrap}
c = a + b
c: {
    ok -> print('wrap:' - (it == -56).to-str())
    nil -> print('nil')
    err -> print('err')
}
```

區塊內一個獨立成行的註解只認「緊跟其後的那一條陳述」。中間夾着無關的註解行
（例如 `#{overflow=wrap}` 之後再來一個 `#{...}`）不會中斷，仍找到第一條真正的陳述；
但若下一條註解本身也帶同名鍵，則以前者不轄制任何陳述（後者勝）。

## 3. 繼承、覆蓋與硬邊界

**由外向內繼承，就近覆蓋。** 對支持多層的鍵（平台鍵），L0 → L1 → L2 → L3 逐層生效；
同一節點上若出現同名鍵，後者覆蓋前者（`#{mac-arm64} #{mac-arm64, win-amd64}`
以後者為準）。

**函式體是硬邊界。** L2 塊的作用域止於**語法子樹**：它不沿呼叫關係擴散，也不進入任何
函式 / 方法 / 匿名函式的定義體。一個函式體內用什麼模式，只由它自己的 L1 註解或內部
的 L3 註解決定，與呼叫它的那個塊上的註解無關。

```no
; L1：整個函式連同函式體一起被剔除（macOS 上不生成 IR）
#{win-amd64}
windows-only = () {
    print('never compiled on mac')
}

; 沒有自己的 L1 註解 → 任何平台都編譯，也不會因為被誰呼叫而改變
always = () {
    print('always compiled')
}
```

理由：外層註解若能穿透進函式體，呼叫點上一行字就會靜默改變被呼叫函式的語義——除錯時
完全看不出來。L1 註解則相反：它就寫在這個函式頭上，是宣告的一部分。

**硬邊界清單**（繼承到此為止）：函式體、方法體、匿名函式/lambda 體、`#{c}` 外部宣告。
**非邊界**（照常繼承）：`{}` 裸塊、if 組、match 臂、循環體。

**硬邊界清單**（繼承到此為止）：函式體、方法體、匿名函式/lambda 體、`#{c}` 外部宣告。
**非邊界**（照常繼承）：`{}` 裸塊、if 組、match 臂、循環體。

## 4. 鍵 × 層級矩陣

`✓` 生效 ／ `✗` 非法（應報編譯錯誤）／ `—` 對該層無意義（同樣應報錯，而不是靜默丟棄）

| 鍵 | L0 模組 | L1 宣告 | L2 區塊 | L3 單行 |
| --- | --- | --- | --- | --- |
| `overflow` | ✗ | ✗ | ✗ | ✓ |
| 平台鍵（`mac-arm64` 等） | ✓ | ✓ | ✓ | ✓ |
| `buildin` | ✗ | ✓ 函式 / 標籤列舉 / 佈局結構體 | ✗ | ✗ |
| `inline` | ✗ | ✓ 結構體 / 欄位 / 變體 / 函式 | ✗ | ✓ 成員尾隨 |
| `generic` | ✗ | ✓ 函式 / 結構體 | ✗ | ✗ |
| `track-caller` | ✗ | ✓ 函式 | ✗ | ✗ |
| `embed` | ✗ | ✓ 頂層 `let` | ✗ | ✗ |
| `bind` | ✗ | ✓ import 行 | ✗ | ✗ |
| `c` / `cpp` / `rust` | ✗ | ✓ 緊隨的函式宣告 | ✗ | ✗ |
| `fmt-skip` | ✗ | ✗ | ✓ markdown 圍欄塊 | ✗ |
| 元資料（`derive` / `range` / `max` / `debug`…） | ✗ | ✓ 宣告 / 成員 | ✗ | ✗ |
| `index-out` | — | — | — | — 已於 D11 移除，出現即報錯 |

「非法」與「無意義」都必須**報錯**，不能靜默失效：一條寫在 for 迴圈上方的
`#{buildin}` 若被悄悄忽略，作者會以為內建聲明生效了。

### 4.0 `#{buildin}` 的三個載體，以及「佈局結構體」的特殊性

`#{buildin}` 標在宣告上，但它對三種載體的語義完全不同：

| 載體 | 語義 | 例子 |
| --- | --- | --- |
| 函式 | 空體樁：編譯器 / FFI 提供實現，Nolang 側不生成函式體 | `#{buildin}`<br>`fs.remove = (p str) (ok bool) { }` |
| 標籤列舉 | 變體供匹配與窮盡性檢查，底層表示與構造由內建 runtime 提供 | `#{buildin}`<br>`option { ok(v t), nil, err(e err.err), }` |
| **佈局結構體** | **只是佈局文檔**：這份 `struct` 在語義上不存在 | `#{buildin}`<br>`txt { data [255]byte; len u8 }` |

第三種要單獨說清楚，因為它與前兩種的方向相反：函式樁與標籤列舉都是「編譯器真的
要用這份聲明」，而佈局結構體是「編譯器**不用**這份聲明，它只給 LSP hover 與
docs 一個可引用的形狀」。真實佈局在別處：

| 型別 | 真實佈局的來源 |
| --- | --- |
| `str` | MIR 手寫描述符 `%str-long = { i32 len, i32 cap, i8* data }` |
| `vec` | MIR 手寫描述符 `%vec = { i32 len, i32 cap, i64 data }` |
| `txt` | MIR 手寫描述符 `%txt = { [255 x i8] data, i8 len }` |
| `arr` | 沒有描述符：`[n]t` 就是裸聚合 `[N x T]`，`.len` 是編譯期常量 `n` |

由此得出兩條硬性規則，任一被破壞都會立刻產生一份與真實佈局矛盾的「影子結構體」：

1. **帶 `#{buildin}` 的 struct 必須用內建佈局名**（`str` / `vec` / `txt` / `arr`）。
   貼在別的 struct 上是錯誤：那份聲明會被 MIR 當「佈局由編譯器持有」而跳過，
   欄位全部不生效，留給作者的是一堆 `unknown field`。
2. **用內建佈局名宣告 struct 必須帶 `#{buildin}`**。使用者若寫一份裸的
   `str { … }`，它會被當成本模組的普通型別加前綴（`m.str`），codegen 於是生成
   一個與 `%str-long` 打架的 `%m_str`。

兩條都由 `checker.ValidateBuiltinStructDecls` 報錯（`1a8m445h` / `3lu6n4np`），
`no build` 與 `no vet` 都會命中。反過來，**只有** `#{buildin}` + 佈局名的組合會被
模組前綴階段與 MIR 的 `collectStructFields` 跳過（見 `src/build/module_prefix.go`
的 Phase 1 與 `src/mir/hir2mir.go` 的 `isBuiltinLayoutStruct`）——判據是「註解 +
名字」這個組合，不是名字本身。

### 4.1 為什麼 `overflow` 只給 L3

`#{overflow}` 是**逐運算**的語義開關，不是宣告的元數據。它一旦允許寫在函式或塊上，
「某條運算實際用哪個模式」就取決於它離註解多遠、中間有沒有夾別的註解、疊了幾層塊——
讀一行程式碼要向上追溯才能回答，而 `no fmt` / `no vet` / codegen 三方維持同一個答案
極難（實測已經漂了，見 §7）。

而且它**不改型別**：結果恆為 `?T`。塊級或函式級的 `wrap` 不會把 `?T` 變成 `T`，只會把
「溢出即 `err`」靜默換成「靜默回繞」——錯誤從「顯式失敗」變成「看起來成功的錯值」，
這正是最不該由一行遠處註解決定的事。

所以定死成一行一註解：

- 只認緊跟的那一條陳述；尾隨寫法（`x = a + b #{overflow=wrap}`）等價。
- 要整片生效就逐條寫——`no fmt --fix=overflow` 與 LSP quickfix 產生的都是這個形式。
- 寫在函式頭、塊頭、檔案頭 → **編譯錯誤**，不是「無效但無害」。

附帶好處：註解永遠與它管的那條陳述同屏，移動程式碼時不會彼此脫離；`wrap` 也不會
因為一次縮排調整而意外覆蓋到隔壁的運算。

## 5. 註釋（`;` / `//` / `;;`）的作用域

註釋不參與編譯語意，歸屬只影響 `no fmt` 的排版與 API 文件的掛載。標記語法見
[`code-style.md`](code-style.md)〈註釋標記〉。

| 註釋 | 歸屬 |
| --- | --- |
| 行內（`x = 1 ; 說明`） | 該行 |
| 行上方連續註釋行 | 緊跟的下一條陳述/宣告（L1 或 L3，同註解的宿主判定） |
| 與目標之間有空行 | 不歸屬任何節點，作為區塊/檔案的分隔說明（檔案頭除外，見 L0） |
| `;; … ;;` 塊註釋 | 只到自己的結束定界符，不跨作用域 |
| 註解與目標之間的註釋 | 隨目標走，輸出順序固定為「文件註釋 → 註解 → 陳述」 |

`;` 與 `//` 語義相同；`no fmt` 保留原始標記不改寫。文件註釋的翻譯錨點
（`[get](#args.get)`）必須是註釋群組的**最後一行**，屬於同一宿主，不能跨節點。

## 6. 四個讀者必須一致

同一條註解，四個讀者必須得到同一個作用域：

| 讀者 | 需要知道的 |
| --- | --- |
| parser / codegen | 這個節點及其子樹用哪個模式 |
| checker / `no vet` | 「已標註」的判定範圍 |
| `no fmt` | 註解印回原位，不得跨宿主搬移 |
| LSP | hover/quickfix 插入的位置等於它實際生效的位置 |

由此推出四條不變量：

1. **標註判定一致**：codegen 認為「已標註」的範圍，必然也是 `no vet` 認為已處理的範圍，反之亦然。
2. **fmt 不搬移**：`no fmt` 只能在同一宿主內調整位置（上方 ↔ 尾隨），跨宿主搬移等於改語義。
3. **失效必報**：註解落在沒有對應語意的層級（見 §4 的 `✗` / `—`）時報錯，不靜默忽略。
4. **層級受限**：鍵只在矩陣允許的層級生效。`overflow` 寫到 L0/L1/L2 時，四個讀者都必須
   當它是**錯誤**——不能出現「vet 認、codegen 不認」這種分叉（現況見 §7）。

## 7. 現況與差距（2026-11-11 實測）

用 `bin/no` 逐項驗證，形狀統一為「兩個 `i8 = 100` 相加，看結果是 `err` 還是 `-56`
（wrap）」；平台鍵用 `#{win-amd64}` 在 macOS 上驗證是否被排除。

| 層級 | `overflow`（設計：僅 L3） | 平台鍵 | 宣告鍵 |
| --- | --- | --- | --- |
| L0 模組 | ✗ 設計禁止；目前會附着到首條陳述（等於 L1） | 未實作 | 未實作 |
| L1 宣告 | ✗ 設計禁止；**現況是漏洞**：`no vet` 認（整函跳過）、codegen 不認（仍 `err`） | ✓ 整棵子樹排除 | ✓ |
| L2 區塊 | ✗ 設計禁止；codegen 不認。`for` / if 組 / match 臂頭能讓 `no vet` 沿塊閉嘴；**語句位置裸塊 `{` 連閉嘴都做不到**（見下） | ✗ 塊內仍參與編譯 | — |
| L3 單行 | ✓ | ✓ | — |

實測證據：

```text
a-none.no    (無註解)                     → err
b-line.no    (陳述上方 #{overflow=wrap})   → result:true  (-56，生效)
c-fn.no      (函式上方 #{overflow=wrap})   → err           (vet: No issues found)
d-block.no   (for 上方 #{overflow=wrap})   → err ×2        (vet: 2 hints)

p1-block.no  (#{win-amd64} + 2 * {…})      → 塊體仍執行    (未過濾)
p2-stmt.no   (#{win-amd64} + 單條 print)   → 該行被排除    (生效)
p4-fn.no     (#{win-amd64} + 函式宣告)     → 函式被排除    (生效)
p6-ifgroup.no(#{win-amd64} + if 組)        → 臂仍執行      (未過濾)

; 編譯期對照：`for` 頭加註解 vs 不加，15w45dqk 逐字相同
k2.no (for 頭 #{overflow=wrap} + 體內 `x i8 = a + a`) → cannot assign ?i8 to i8
k3.no (刪掉那一行，其餘逐字相同)                       → cannot assign ?i8 to i8
```

裸塊為什麼連閉嘴都做不到：`parseAnnotationStatement` 的可附加目標只有 IDENT / USE /
IN / RARROW / 陣列型別方法，`{` 不在其中。所以下面這種寫法裡的註解既沒掛到塊上、也沒
掛到塊內陳述上——它退化成一條獨立的 `AnnotationStatement`，對 parser、codegen、
`no vet` 三者都是死行：

```no
#{overflow=wrap}
{
    ...
}
```

`for` / if 組 / match 臂的頭以識別符或 `in` 起首，才恰好落在可附加目標裡。

三個要收緊的洞（`overflow` 的「只給 L3」尚未強制）：

1. **`no vet` 見到函式級 `overflow` 就跳過整個函式**（`walkStmtForOverflow` 的
   `fn.OverflowMode == ""` 短路）→ 檢查全綠、執行期照舊 `err`。
2. **`no vet` 沿塊向下繼承**（`enclosingOverflow`）→ 塊頭一行註解讓整個塊閉嘴，
   即使 codegen 根本不認。
3. **parser / codegen 對 L1/L2 的 `overflow` 靜默忽略**，不報錯 → 作者無從得知它沒生效。

約 97 行是塊級意圖被物化成逐條。

第二輪（2026-11-12）是**純清掃**，成因是 `findFixTargetNode` 不下鑽臂體、也沒有「插完自檢」：
381 行刪除、159 行新增，**全部是 `#{...}` 注解行，0 行代碼**（`diff` 逐行核對）。其中

第二輪一併修掉的三個工具缺陷：

1. **`checker` 報行號塌到容器**：`walkExprForIntOverflow` 的 `emit` 混用了容器的
   `stmt.Pos().Line` 與運算子的 column，於是 `{ ... }` / if 組 / match 臂裡每一處報告的
   行號都是 header 行。診斷指錯位置只是表象，真問題是 `--fix` 的 `findFixTargetNode`
   取「包含該行的最內層陳述」，只能拿回容器，注解被插回塊頭。現在改取**運算子自身行**
   （`x.Token.Line`），token 行號缺失時回退容器行。
2. **不下鑽臂體**：`findFixTargetNode` 原本刻意停在整个 match 陳述上方。現在下鑽
   **塊形式臂體**（`cond -> {` 的 `{ ... }`，含 `{ ... }: { ... }` 的 `BlockMatchStatement.Body`），
   行內臂體仍不下鑽（`w i64 -> w + 1` 的陳述與臂模式同行，插到它上方等於插進 match、
   落在臂模式行之前）。
3. **插到掛不上的位置也照插**：`#{overflow}` 現在插完會**再解析一次自檢**，把「插了但
   退化成一條獨立 `AnnotationStatement`」的注解撤回（不再留死行）。撤回後第二趟 `--fix`
   拿到的源碼不動，冪等保持。

第三輪（2026-11-12）動的是 parser：`parseAnnotationStatement` 的附加目標新增 **DOT**。
`.n = .n + 1` / `.cnt == 0 -> …` 這種以接收者起首的陳述與 `x = …` 是同一類（單條陳述、L3），
過去卻不在附加目標之列 ⇒ 注解退化成獨立 `AnnotationStatement`（死行），站點永遠被報告、
`--fix` 插了也被自檢撤回。放寬後 219 處站點拿到了 L3 注解（注解行 3861 → 4080），
標不了的從 270 降到 51。AST 形狀因此改變（少一條 AnnotationStatement、目標陳述多一條
side-table 記錄與 `OverflowMode`），`parser.ASTVersion` bump 到 `2026-11-12.1`，改完必須
`make gen no`。

**`{` 與 `(` 刻意沒放寬**：`{`（語句位置裸塊 / 帶括號 match）與 `(`（`(cond) { }` 迴圈頭）
是 L2 區塊宿主，而 `overflow` 的設計是只認 L3。放它們進來會讓 `overflowAnnotatedNode`

## 8. 收緊順序

1. **先讓 `no vet` 不再認 L1/L2 的 `overflow`**：刪掉「函式級整函跳過」的短路，
   並把 `enclosingOverflow` 限制在同一陳述的子樹內（不跨塊向下傳）。
2. **再讓 parser 報錯**：`#{overflow}` 落在 L0/L1/L2 → 編譯錯誤，訊息指向「請逐條標註，
   或跑 `no fmt --fix=overflow`」。這一步會一次性暴露所有存量。
3. **清理存量**：`no fmt --fix=overflow` 已具備下推能力（摘掉作用域級那層，再按 checker
   的報告逐條補 L3），`src/std` 跑過三輪（見 §7 的存量表）。改完必須 `make gen no`（重烤
   blob 與 StdSigKey），且不得對 `src/std` 跑 `no fmt -w`——遷移只動注解行，用逐檔
   `no fmt -fix=overflow -w <f>` 完成，`diff` 保證沒有其它改動。
4. **放寬 parser 的附加目標**（第三輪已完成一半）：
   - **4a 已完成**：`parseAnnotationStatement` 接受 **DOT** 起首的陳述。`.n = .n + 1` /
     `.cnt == 0 -> …` 與 `x = …` 同屬單條陳述（L3），過去卻掛不上注解 ⇒ `src/std` 有 219 處
     `#{overflow=wrap}` 從未生效。放寬後標不了的從 270 降到 51，`parser.ASTVersion` bump 到
     `2026-11-12.1`。
   - **4b 待決策**：`{`（語句位置裸塊 / 帶括號 match）與 `(`（`(cond) { }` 迴圈頭）是 **L2
     區塊宿主**。放寬它們等於給 `overflow` 合法化 L2 語義（`overflowAnnotatedNode` 會對整個
     塊提前返回），與第 1–2 步的收緊方向相反。正確順序是先做第 1–2 步（L2 的 `overflow`
     判錯），再看剩下這 51 處要不要靠「改寫成不帶塊的陳述」或「逐條補 arm body」解決，
     而不是無條件放開 `{` / `(`。
5. **其餘鍵逐步收緊**：把宣告鍵（`buildin` / `generic` / `embed`…）寫在 L2/L3 從
   「無效」改成「報錯」。
6. 每一步都要保證 `no fmt` 冪等，且四個讀者對同一份輸入結論一致（§6）。
